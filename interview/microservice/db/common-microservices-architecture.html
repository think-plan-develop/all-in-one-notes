2Service responsibilities

In microservices architecture, an application is divided into multiple independent services, each responsible for a particular business capability. For example, a Digital Property Transfer System might contain:

🔐

Auth Service

Users, login, registration, and authentication.

🏠

Property Service

Property information and transactions.

📄

Document Service

Document metadata and verification.

⭐

Review Service

Property ratings and reviews.

💳

Payment Service

Payment processing and refunds.

Most important database design principleEach microservice should own its data. Other services should communicate through APIs or events instead of directly accessing another service's database tables or collections.

There are three common ways to organize microservice data in MongoDB and PostgreSQL:

ApproachMongoDBPostgreSQL
1Same database, separate collectionsSame database, separate schemas
2 ⭐Same cluster, separate databasesSame instance, separate databases
3Separate clustersSeparate instances/clusters

These approaches differ mainly in logical isolation, security boundaries, resource sharing, infrastructure scaling, and operational cost.

4Why choose separate databases?

Why is Level 2 preferred over Level 1?

Consider the Auth and Property services. With one shared database, a user with unrestricted database-level readWrite permissions could access both Auth and Property collections. With separate MongoDB databases, you can restrict the Auth user to auth_db. Likewise, separate PostgreSQL databases create clearer administrative and access-control boundaries.

5When to use dedicated infrastructure

Why use separate clusters?

Imagine the Document Service experiences a huge increase in traffic. It performs large numbers of metadata reads and writes for document processing.

⚠️ Shared cluster

The Document Service consumes a large share of database resources. Consequences:

  • Property queries may become slower.
  • Auth queries may experience increased latency.
  • All services may encounter connection or resource pressure.

✅ Separate clusters

Document Service runs on its own database infrastructure. Benefits:

  • Scale its database compute and storage independently.
  • Heavy document workload does not directly consume Property cluster resources.
  • Database maintenance can be scheduled separately.
  • Database failures can be isolated from other independent clusters.
NoteApplication-level dependencies can still propagate failures. Separate clusters do not automatically guarantee complete service availability.

Disadvantages

  • More expensive infrastructure.
  • More database deployments to maintain.
  • Additional monitoring and backups.
  • More security and network configurations.
  • Greater operational complexity.
ThereforeSeparate clusters should be introduced when they solve a measurable workload, isolation, security, or availability requirement.

7Ownership & communication ⭐

Database organization alone does not make an application a good microservices architecture. Service ownership is more important than the number of databases or clusters.

Suppose a user submits a review for property P101. The Review Service needs to verify that the property exists.

❌ Incorrect approach

Review Service directly queries the Property Service database.

review-service.js
// Avoid cross-service database access
db.properties.findOne({
  propertyId: "P101"
});

This creates coupling because Review Service depends on the Property Service's internal database structure. If the Property Service changes its schema, Review Service might break.

✅ Recommended approach

  • Frontend → POST /reviews
  • API Gateway routes the request
  • Review Service checks the property ID
  • Property Service API validates the property
  • Review Service saves the review
  • Review database stores the document/row

The Review Service can use a Property Service API to validate the property. For suitable use cases, it may instead maintain locally replicated property information through events.

Logical references between services

A property ID stored by Review Service is a logical reference to data owned by Property Service. Cross-service references need explicit validation and lifecycle rules. The database-specific files include document and table examples.

RememberThe application manages cross-service references and consistency through APIs, events, and appropriate workflow rules.
8Practical communication rules

Common to both databases — practical service communication rules

TopicImportant point
Timeouts and failuresBound dependency calls with deadlines. Choose deliberately between a failed request, cached result, or clearly marked partial response.
Service identityAuthenticate service calls and authorize the requested user/property fields. Internal endpoints are not automatically trusted.
Discovery and configurationKeep service base URLs in configuration. Container or cluster DNS replaces localhost when services run in different environments.
Lists and N+1 callsFor many properties, batch and deduplicate owner IDs through an authorized bulk API or use a local projection. Avoid one HTTP call per item.
ConsistencyAPI composition reads current service data but is not an atomic cross-service snapshot. Events introduce an explicit lag.
Business writesCoordinate multi-service changes with explicit workflows or sagas when needed. Neither an HTTP call nor a local database transaction makes a distributed write atomic.
Reliable eventsPlan an initial load, idempotency, ordering, retries, deletion handling, and reliable event publication.
Operational visibilityLog dependency failures and propagate request/trace IDs so a request can be followed across services.
Connection choice does not change ownershipLevel 1: same database, separate collections/schemas. Level 2: same deployment, separate databases. Level 3: independent deployments. At every level, the owning service controls access to its business data.
9Interview scenarios
🧑‍💼 Interviewer

If separate databases and separate collections both use the same MongoDB cluster, aren't they effectively the same?

🙋 Recommended answer

Both approaches share the same physical database infrastructure, so they have similar resource-sharing and cluster-availability characteristics.

The key difference is logical isolation and access control.

With separate databases, each microservice owns a logical database, making database-level permissions, ownership, and schema management clearer.

With separate collections inside one database, ownership depends on collection-level permissions and stricter development conventions.

Therefore, although the infrastructure is shared, separate databases provide cleaner administrative boundaries. Neither approach automatically gives independent database scaling.

Also applies to PostgreSQLThis explanation also applies to PostgreSQL, replacing collections with schemas.
🧑‍💼 Interviewer

Why would you move a microservice to its own MongoDB cluster or PostgreSQL instance?

🙋 Recommended answer

A dedicated database cluster is useful when a microservice needs independent resource scaling, stronger failure isolation, specialized database configuration, or separate operational controls.

For example, if Document Service generates heavy database traffic, putting it on a dedicated cluster prevents that workload from directly consuming the Property Service database resources.

However, dedicated infrastructure increases cost and operational complexity, so I would introduce it based on measurable requirements rather than using it for every service automatically.

10Frequently asked questions
1Does every microservice need a separate database?▼
Not necessarily a separate physical database — but every service must own its data (its own collections, schemas, or databases). Independent data ownership matters more than the number of databases.
2Does every microservice need a separate MongoDB cluster?▼
No. Separate clusters (Level 3) are for measurable workload, isolation, security, or availability needs. A common start is separate databases on a shared cluster.
3Can two microservices use one PostgreSQL database?▼
Yes. They can own separate schemas with appropriate roles and privileges.
4Can microservices share database tables or collections?▼
They should not. Each service owns its data; other services use its APIs or events instead of directly reading its tables or collections.
5Which approach provides independent database scaling?▼
Level 3 — separate clusters (MongoDB) or separate instances (PostgreSQL).
6Do separate MongoDB databases improve performance automatically?▼
No. Databases on the same cluster still share CPU, memory, storage, and connections. The gain is administrative and logical isolation.
7Can one microservice access another service's database?▼
It should not do so directly — that couples it to the other service's internal structure. Use the owning service's API, or locally replicated data kept in sync through events.
8What if one MongoDB cluster goes down?▼
With a shared cluster (Levels 1–2), every service using it is affected. With separate clusters, the failure is isolated to that service's cluster — though application-level dependencies can still propagate it.
9What is the equivalent of separate collections in PostgreSQL?▼
Separate schemas. Technically a collection is closer to a table, and a schema is a namespace for many objects, so the designs are similar but not identical.
10Should we always start with database-per-service?▼
No. For most small-to-medium projects, start with separate logical databases on shared infrastructure and add dedicated clusters only when requirements justify them. With uncertain boundaries and a small team, consider a modular monolith first.

11Recommended project architecture

For a Node.js-based Digital Property Transfer System, I would choose a hybrid deployment strategy, starting with separate logical databases on shared infrastructure.

For actual document files such as PDFs and signed agreements, use suitable object storage, such as Amazon S3. MongoDB or PostgreSQL can store document metadata, references, ownership, and processing status.

12Final revision

Three lines to remember for interviews

  1. Data ownershipdetermines which service is responsible for reading and modifying a particular set of business data.
  2. Logical isolationseparates service data through collections, schemas, or databases and can be enforced using permissions.
  3. Infrastructure isolationuses dedicated database deployments to provide independent resource scaling and stronger fault isolation.
Final recommendationFor most small-to-medium Node.js microservices projects, start with separate logical databases on shared MongoDB or PostgreSQL infrastructure, enforce permissions and service boundaries, and introduce dedicated clusters only when operational requirements justify them.
