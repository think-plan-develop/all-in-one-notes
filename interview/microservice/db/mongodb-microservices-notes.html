2Level 1
🍃 MongoDB

MongoDB: Same Database, Separate Collections

All microservices connect to one MongoDB database, but every microservice owns specific collections.

🌳 Show text tree
structure.txt
MongoDB Cluster
└── property_portal
    ├── users            → Auth Service
    ├── sessions         → Auth Service
    ├── properties       → Property Service
    ├── documents        → Document Service
    └── reviews          → Review Service

Configuration example

.env
# Auth Service
MONGO_URI=mongodb+srv://auth_user:<password>@cluster.example.mongodb.net/property_portal

# Review Service
MONGO_URI=mongodb+srv://review_user:<password>@cluster.example.mongodb.net/property_portal

Both services use the same database but should have different database users.

ImportantMongoDB's built-in database-level readWrite role would give access to all collections in that database. To enforce collection ownership, configure custom collection-level roles.

👍 Advantages

  • Simple database setup and administration.
  • Suitable for small systems or gradual monolith migrations.
  • Services can independently manage their application logic.
  • Infrastructure cost is low because everything uses the same cluster.

⚠️ Disadvantages

  • Weaker separation between service data.
  • Collection-level access control requires additional configuration.
  • Developers may accidentally access another service's collections.
  • Database-wide changes and operations may affect multiple services.
  • Shared cluster resource contention and failures remain possible.

🍃 MongoDB

MongoDB: Same Cluster, Separate Databases

All microservices use one MongoDB cluster, but each owns a different logical database.

🌳 Show text tree
structure.txt
MongoDB Cluster
├── auth_db
│   ├── users
│   └── sessions
│
├── property_db
│   ├── properties
│   └── transactions
│
├── document_db
│   └── documents
│
└── review_db
    └── reviews

Configuration

.env
# Auth Service
MONGO_URI=mongodb+srv://auth_user:<password>@cluster.example.mongodb.net/auth_db

# Property Service
MONGO_URI=mongodb+srv://property_user:<password>@cluster.example.mongodb.net/property_db

# Review Service
MONGO_URI=mongodb+srv://review_user:<password>@cluster.example.mongodb.net/review_db

Notice

  • The hostname is the same.
  • Each database name is different.
  • Each service can have its own database credentials.
  • Each user should have permissions only for its respective database.

For example, auth_user can receive the readWrite role on auth_db without receiving access to property_db.

Advantages

  1. Clear database ownershipEach service manages its own database.
  2. Simpler permissionsDatabase-level access controls are straightforward.
  3. Independent schema evolutionOne service can modify its collections without changing another service's database.
  4. Easier future migrationIndividual databases can be moved to dedicated clusters.
  5. Lower infrastructure costAll databases share one cluster.

Disadvantages

  • CPU, memory, storage capacity, and database connections are still shared.
  • A cluster-wide outage can affect all services.
  • Heavy traffic from one service may impact another.
  • Database infrastructure cannot scale independently per service.
  • Cross-service data consistency still needs explicit coordination.

🍃 MongoDB — Node.js + Mongoose

M1. What does “New Connection” in Compass mean?

Compass is a database client. A saved connection tells it which MongoDB deployment to contact; clicking New Connection does not create another MongoDB server. Two saved connections pointing to localhost:27017 can reach the same deployment.

ItemYour local exampleMeaning
Deployment / serverlocalhost:27017The running MongoDB process. A production deployment may be a replica set or sharded cluster.
Databasechild-db-1, child-db-2Two sibling logical databases; neither is the parent of the other.
Collectionusers, propertiesA collection belongs to one database.
Document{ _id: "U101", name: "Rahul" }A record inside a collection.
RememberThe word child is only part of your database name. MongoDB databases are not nested. A Mongoose connection also does not create separate infrastructure.

Connection → model → collectioncreateConnection() returns a Connection object. .asPromise() lets you wait until it connects. Register models using authConnection.model(...) or propertyConnection.model(...). mongoose.model(...) uses the default connection instead.

M4. Reusable connection and model files — both levels

Create separate auth-service and property-service folders. In each folder, run these commands and create its selected Level 1 or Level 2 .env. Use a supported Node.js LTS release with built-in fetch and AbortSignal.timeout.

Terminal — run inside each service folder
npm init -y
npm pkg set type=module
npm install express mongoose dotenv
auth-service/db.js
import "dotenv/config";
import mongoose from "mongoose";

export const authConnection = await mongoose.createConnection(
  process.env.MONGO_URI,
  { serverSelectionTimeoutMS: 5000 }
).asPromise();

const userSchema = new mongoose.Schema({
  _id: String, // Makes the example ID "U101" valid
  name: { type: String, required: true },
  email: { type: String, required: true }
});

export const User = authConnection.model("User", userSchema, "users");
property-service/db.js
import "dotenv/config";
import mongoose from "mongoose";

export const propertyConnection = await mongoose.createConnection(
  process.env.MONGO_URI,
  { serverSelectionTimeoutMS: 5000 }
).asPromise();

const propertySchema = new mongoose.Schema({
  propertyId: { type: String, required: true, unique: true },
  title: { type: String, required: true },
  ownerId: { type: String, required: true }
});

export const Property = propertyConnection.model(
  "Property", propertySchema, "properties"
);
  • The third model() argument sets the collection name explicitly.
  • Create connections once at service startup and reuse them. Do not open a new connection for every request.
  • These examples intentionally use string user IDs. If your existing users have ObjectId _id values, use matching ObjectId values/types. If U101 is stored in a separate userId field, query findOne({ userId: req.params.id }).
  • The sample connection strings assume local MongoDB with authentication disabled. Database users, authentication, and permissions must be configured to enforce ownership.
  • A Mongoose Schema describes document fields; it is not a PostgreSQL-style database namespace.

M6. How microservices communicate across MongoDB databases ⭐

Property Service has ownerId, but Auth Service owns the user’s name and email. Store the ID as a reference, then ask the owning service for the permitted fields. This also applies at Level 1: sharing a database does not remove the service boundary.

  1. Frontend requests GET http://localhost:3002/properties/P101.
  2. Property Service queries child-db-2.properties and reads ownerId: "U101".
  3. Property Service requests GET http://localhost:3001/users/U101.
  4. Auth Service queries child-db-1.users and returns the owner’s name and email.
  5. Property Service combines the two results and responds to the frontend.
Method 1 — REST API ⭐Fetching data from owning services and combining it into one response is API composition. This composition lives in Property Service in the example; larger systems may use a dedicated composition layer.
auth-service/server.js
import "dotenv/config";
import express from "express";
import { authConnection, User } from "./db.js";

const app = express();

app.get("/test-db", async (req, res) => {
  try {
    await authConnection.db.command({ ping: 1 });
    res.json({ service: "auth", database: authConnection.name });
  } catch (error) {
    console.error(error);
    res.status(503).json({ message: "Database unavailable" });
  }
});

app.get("/users/:id", async (req, res) => {
  try {
    const user = await User.findById(req.params.id)
      .select("name email -_id")
      .lean();

    if (!user) {
      return res.status(404).json({ message: "User not found" });
    }

    res.json(user);
  } catch (error) {
    console.error(error);
    res.status(500).json({ message: "Unable to retrieve user" });
  }
});

const port = Number(process.env.PORT || 3001);
app.listen(port, () => console.log(`Auth Service: ${port}`));
property-service/server.js
import "dotenv/config";
import express from "express";
import { propertyConnection, Property } from "./db.js";

const app = express();
const authBaseUrl = process.env.AUTH_SERVICE_URL;
if (!authBaseUrl) throw new Error("AUTH_SERVICE_URL is required");

app.get("/test-db", async (req, res) => {
  try {
    await propertyConnection.db.command({ ping: 1 });
    res.json({ service: "property", database: propertyConnection.name });
  } catch (error) {
    console.error(error);
    res.status(503).json({ message: "Database unavailable" });
  }
});

app.get("/properties/:id", async (req, res) => {
  let property;
  try {
    property = await Property.findOne({
      propertyId: req.params.id
    }).lean();
  } catch (error) {
    console.error(error);
    return res.status(500).json({ message: "Unable to read property" });
  }

  if (!property) {
    return res.status(404).json({ message: "Property not found" });
  }

  try {
    const url = new URL(
      `/users/${encodeURIComponent(property.ownerId)}`,
      authBaseUrl
    );
    const signal = AbortSignal.timeout(3000);
    const response = await fetch(url, { signal });

    if (!response.ok) {
      return res.status(502).json({
        message: response.status === 404
          ? "Referenced owner not found"
          : "Unable to retrieve owner details"
      });
    }

    const owner = await response.json();
    if (typeof owner?.name !== "string" || typeof owner?.email !== "string") {
      return res.status(502).json({ message: "Invalid owner response" });
    }

    res.json({
      propertyId: property.propertyId,
      title: property.title,
      owner: { name: owner.name, email: owner.email }
    });
  } catch (error) {
    console.error(error);
    const timedOut = error.name === "TimeoutError" || error.name === "AbortError";
    res.status(timedOut ? 504 : 502).json({
      message: timedOut ? "Owner service timed out" : "Owner service unavailable"
    });
  }
});

const port = Number(process.env.PORT || 3002);
app.listen(port, () => console.log(`Property Service: ${port}`));

M7. Method 2 — Events + a local read model

Auth remains the source of truth. When a user changes, it publishes an event through a broker such as RabbitMQ or Kafka. Property Service consumes it and stores only the user fields it needs in its own user_profiles collection.

Example event — define this contract between services
{
  "eventId": "evt-101",
  "type": "UserUpdated",
  "userId": "U101",
  "version": 2,
  "name": "Rahul Sharma",
  "email": "rahul@example.com"
}
child-db-2.user_profiles — local projection
{
  "userId": "U101",
  "version": 2,
  "name": "Rahul Sharma",
  "email": "rahul@example.com"
}

Property Service now reads the property and profile from its own database. It can combine them in application code, or use a local aggregation. The projection is read-only for business operations; only the event consumer updates it.

AdvantagesTrade-offs
Fast local reads; no Auth HTTP call for every request.The copy may lag behind Auth: eventual consistency.
Reads can continue while Auth is unavailable, if the projection exists.Events, retries, backfills, and recovery need operational work.
Only the required fields are replicated.Duplicates, out-of-order events, and deletes must be handled.
  • Load an initial snapshot or replay events so existing users are present before relying on the projection.
  • Use a unique userId index and idempotent consumers. Apply newer versions atomically so an older event cannot overwrite a newer profile.
  • Use durable delivery, retries, and a dead-letter process for events that repeatedly fail.
  • An outbox pattern helps avoid saving a user change without publishing its event. Handle user deletion and restrict replicated fields.
  • Do not rely on a stale profile projection for critical authorization or account-revocation checks.

M8. Method 3 — Direct cross-database populate (technical demo)

Mongoose can populate through a model on another connection. This is useful in some applications under one ownership boundary. It is generally a poor default between independently owned microservices because the caller needs direct access to another service’s database and data shape.

cross-db-demo.js — standalone demo, not either REST service
import mongoose from "mongoose";

const authConnection = mongoose.createConnection(
  "mongodb://localhost:27017/child-db-1"
);
const propertyConnection = mongoose.createConnection(
  "mongodb://localhost:27017/child-db-2"
);

try {
  await Promise.all([
    authConnection.asPromise(),
    propertyConnection.asPromise()
  ]);

  const User = authConnection.model("User", new mongoose.Schema({
    _id: String,
    name: String,
    email: String
  }), "users");

  const Property = propertyConnection.model("Property", new mongoose.Schema({
    propertyId: String,
    title: String,
    ownerId: String
  }), "properties");

  const property = await Property.findOne({ propertyId: "P101" })
    .populate({
      path: "ownerId",
      model: User, // Actual model on authConnection
      select: "name email -_id"
    })
    .lean();

  console.log(property);
} finally {
  await Promise.allSettled([
    authConnection.close(),
    propertyConnection.close()
  ]);
}
What populate actually doesThis replaces ownerId in the returned object with the populated user (or null if missing). It does not add an owner field or change the stored document. A string ref: "User" alone looks for that model on the same connection; the explicit model: User selects the other connection.
  • The caller becomes coupled to Auth’s database structure and requires its database credentials.
  • Changing Auth’s storage structure can break consumers even if its API contract stays stable.
  • Mongoose population uses additional database queries; it is not a MongoDB server-side join.
  • Ordinary MongoDB $lookup joins a collection in the same database. It does not make child-db-1.users available to an ordinary aggregation in child-db-2.

M9. Which approach should you use? ⭐

ApproachHow it worksBenefitTrade-off
REST / API composition ⭐Property calls Auth’s API.Clear ownership; reads Auth’s current committed data.Latency; Auth must respond; no atomic snapshot across services.
Events + local copyAuth publishes; Property maintains a projection.Fast reads and fewer synchronous dependencies.Eventual consistency, duplicate data, messaging complexity.
Cross-DB populateOne process connects to both databases.Familiar Mongoose syntax.Direct database coupling across ownership boundaries.

Learning order: start with REST and timeouts, then study events and eventual consistency. Use cross-database populate to understand the capability, not as the default service integration pattern.

Interview-ready answer

When related data belongs to another microservice, I store its ID and use the owning service’s API to fetch the required fields. I combine responses using API composition. For frequent reads, I may maintain a local projection through events and accept eventual consistency. Cross-database populate is technically possible, but it couples services to each other’s database structure. The choice depends on freshness, latency, and availability requirements.

M10. MongoDB — essential connection reminders

LevelWhat changes in code?What stays shared?
1Same database URI; service-owned collections/models.Database and server resources.
2 ⭐Database name in MONGO_URI.MongoDB deployment resources.
3Connection endpoint for a genuinely separate deployment.Any remaining application dependencies.
  • authSource identifies the database used to authenticate the database user; it is not necessarily the database storing the application’s data.
  • If localhost resolves to IPv6 but MongoDB listens only on IPv4, use 127.0.0.1 consistently in the local URI.
  • Inside a container, localhost points to that container. Use configured service hostnames for MongoDB and the other service.
  • Different ports can represent separate local MongoDB processes, but processes on one machine still share that machine’s hardware and failure risk.
  • Sharing a host does not make ownerId a foreign key. Model references do not enforce cross-service referential integrity.
