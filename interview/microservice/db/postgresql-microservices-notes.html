🐘 PostgreSQL

PostgreSQL: Same Database, Separate Schemas

In PostgreSQL, the comparable approach is to use separate schemas. A schema is a logical namespace inside a PostgreSQL database that contains tables and other database objects.

🌳 Show text tree
structure.txt
PostgreSQL Instance
└── property_portal
    ├── auth_schema
    │   ├── users
    │   └── sessions
    │
    ├── property_schema
    │   └── properties
    │
    ├── document_schema
    │   └── documents
    │
    └── review_schema
        └── reviews

Example SQL

schemas.sql
CREATE DATABASE property_portal;

-- Connect to property_portal

CREATE SCHEMA auth_schema;
CREATE SCHEMA property_schema;
CREATE SCHEMA review_schema;

CREATE TABLE auth_schema.users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);

CREATE TABLE property_schema.properties (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL
);

Configuration

.env
# Auth Service
DATABASE_URL=postgresql://auth_user:<password>@localhost:5432/property_portal

# Review Service
DATABASE_URL=postgresql://review_user:<password>@localhost:5432/property_portal

The database name is identical. Each service should use its own login role with access restricted to its schema and tables. For example, Auth Service can manage auth_schema.users but should not access property_schema.properties.

👍 Advantages

  • Schemas make business boundaries explicit.
  • Schema-level access controls can enforce ownership.
  • Easy to introduce when splitting a monolith.
  • Centralized database infrastructure simplifies administration.

⚠️ Disadvantages

  • All services share a database and PostgreSQL instance.
  • Incorrect privileges can permit cross-service queries.
  • Database-wide operations create shared dependencies.
  • Independent database-level administration and migration are limited.

PostgreSQL: Same Instance, Separate Databases

In PostgreSQL, one server instance can manage multiple databases.

🌳 Show text tree
structure.txt
PostgreSQL Instance
├── auth_db
│   └── public.users
│
├── property_db
│   └── public.properties
│
├── document_db
│   └── public.documents
│
└── review_db
    └── public.reviews

Configuration

databases.sql
CREATE DATABASE auth_db;
CREATE DATABASE property_db;
CREATE DATABASE document_db;
CREATE DATABASE review_db;
.env
# Auth Service
DATABASE_URL=postgresql://auth_user:<password>@localhost:5432/auth_db

# Property Service
DATABASE_URL=postgresql://property_user:<password>@localhost:5432/property_db

These examples assume roles and their permissions have been configured separately. In production, secure credentials appropriately.

👍 Advantages

  • Clear database separation.
  • Database-level access controls.
  • Independent schema migrations.
  • Independent database object naming.
  • Practical for a limited number of services on shared infrastructure.

⚠️ Disadvantages

  • Instance resources and availability are shared.
  • Independent database scaling is not available without moving databases elsewhere.
  • Database maintenance can create shared operational impact.
  • Queries across different databases are not available through ordinary PostgreSQL joins.
Important PostgreSQL detailYou cannot simply write a normal SQL join across auth_db and property_db using a single PostgreSQL connection. Special mechanisms such as foreign data wrappers are required, and using them to bypass service ownership is generally not recommended.

Level 1 — core Pool configuration
import "dotenv/config";
import pg from "pg";

const { Pool } = pg;
const db = new Pool({
  host: process.env.DB_HOST,
  port: Number(process.env.DB_PORT),
  database: process.env.DB_NAME,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  options: `-c search_path=${process.env.DB_SCHEMA}`
});

This core snippet assumes a trusted configured schema name. The reusable version in P4 validates it. search_path determines where PostgreSQL resolves an unqualified table name.

Queries — each runs in its own service
// Auth Service: testbbps → auth_schema → users
const { rows: users } = await db.query("SELECT * FROM users");

// Property Service: testbbps → property_schema → properties
const { rows: properties } = await db.query("SELECT * FROM properties");

// Explicit schema name, inside the connected database:
await db.query("SELECT * FROM auth_schema.users");
Schema selection ≠ access isolationsearch_path controls name resolution, not permissions. A role with access to another schema can still query it explicitly. Give each service its own login role and only the database, schema, table, and sequence privileges it needs. Do not allow untrusted roles to create objects in schemas on your search path.

P4. Reusable db.js + a working connection-check endpoint

Create a separate PostgreSQL lab with auth-service and property-service folders. In each folder, run the commands below, add the chosen .env, and create the same db.js and server.js.

Terminal — each PostgreSQL service folder
npm init -y
npm pkg set type=module
npm install express pg dotenv
db.js — same file in each service, both levels
import "dotenv/config";
import pg from "pg";

const { Pool } = pg;
const schema = process.env.DB_SCHEMA || "public";

// Keep schema selection in trusted startup configuration.
if (!/^[a-z_][a-z0-9_]*$/.test(schema)) {
  throw new Error("Invalid DB_SCHEMA");
}

export const db = new Pool({
  host: process.env.DB_HOST,
  port: Number(process.env.DB_PORT || 5432),
  database: process.env.DB_NAME,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  options: `-c search_path=${schema}`,
  max: 10,
  connectionTimeoutMillis: 5000,
  idleTimeoutMillis: 30000
});

// Handle errors from idle clients too.
db.on("error", error => {
  console.error("Unexpected idle database client error:", error.message);
});
server.js — same file in each service, both levels
import "dotenv/config";
import express from "express";
import { db } from "./db.js";

const app = express();

app.get("/test-db", async (req, res) => {
  try {
    const { rows } = await db.query(`
      SELECT current_database() AS database,
             current_schema() AS schema,
             current_user AS username
    `);
    res.json({ service: process.env.SERVICE_NAME, ...rows[0] });
  } catch (error) {
    console.error(error);
    res.status(503).json({ message: "Database unavailable" });
  }
});

// Add your service-specific routes here, before app.listen().

// Pool construction alone does not verify connectivity.
await db.query("SELECT 1");
const port = Number(process.env.PORT);
const server = app.listen(port, () => {
  console.log(`${process.env.SERVICE_NAME} Service: ${port}`);
});

function shutdown() {
  server.close(async () => {
    await db.end();
  });
}
process.once("SIGINT", shutdown);
process.once("SIGTERM", shutdown);

P5. How do PostgreSQL services fetch related data?

Use API composition: Property reads its row, calls Auth with owner_id, then combines the results. Each service queries its own database and exposes the agreed HTTP response fields.

Auth Service route — add to its server.js
app.get("/users/:id", async (req, res) => {
  try {
    const { rows } = await db.query(
      "SELECT name, email FROM users WHERE id = $1",
      [req.params.id]
    );
    if (!rows[0]) {
      return res.status(404).json({ message: "User not found" });
    }
    res.json(rows[0]);
  } catch (error) {
    console.error(error);
    res.status(500).json({ message: "Unable to retrieve user" });
  }
});
Property Service route — add to its server.js
app.get("/properties/:id", async (req, res) => {
  let property;
  try {
    const { rows } = await db.query(
      "SELECT property_id, title, owner_id FROM properties WHERE property_id = $1",
      [req.params.id]
    );
    property = rows[0];
  } catch (error) {
    console.error(error);
    return res.status(500).json({ message: "Unable to read property" });
  }

  if (!property) {
    return res.status(404).json({ message: "Property not found" });
  }

  try {
    const url = new URL(
      `/users/${encodeURIComponent(property.owner_id)}`,
      process.env.AUTH_SERVICE_URL
    );
    const response = await fetch(url, {
      signal: AbortSignal.timeout(3000)
    });
    if (!response.ok) {
      return res.status(502).json({ message: "Unable to retrieve owner details" });
    }
    const owner = await response.json();
    if (typeof owner?.name !== "string" || typeof owner?.email !== "string") {
      return res.status(502).json({ message: "Invalid owner response" });
    }
    res.json({
      propertyId: property.property_id,
      title: property.title,
      owner: { name: owner.name, email: owner.email }
    });
  } catch (error) {
    console.error(error);
    const timedOut = error.name === "TimeoutError" || error.name === "AbortError";
    res.status(timedOut ? 504 : 502).json({
      message: timedOut ? "Owner service timed out" : "Owner service unavailable"
    });
  }
});

With the seeded rows, GET http://localhost:3002/properties/P101 returns propertyId, title, and owner: { name, email }. These routes work at both levels because each service’s configuration resolves its own table.

ApproachLevel 1Level 2
REST / API composition ⭐Use the owning service’s API.Use the owning service’s API.
Events + local projectionMaintain required fields in the Property-owned schema.Maintain required fields in the Property-owned database.
Direct SQL joinCross-schema joins are technically possible if privileges permit. Avoid joining across independent service ownership.An ordinary query cannot join another database directly; FDW or dblink requires extra configuration and access.
Same ownership rule, different database toolsPostgreSQL uses SQL joins; populate() is a Mongoose feature. A single PostgreSQL connection targets one database. auth_schema.users means a schema and table in the connected database, not database auth.

For events, Auth can publish UserUpdated and Property can maintain a local user_profiles table. Apply the same initial-load, idempotency, version ordering, retry, deletion, and outbox considerations for any event-driven projection.

P6. PostgreSQL — essential connection reminders

ConfigurationLevel 1Level 2 ⭐
Host / portlocalhost:5432localhost:5432
Auth DBtestbbpsauth
Property DBtestbbpstestbbps
Auth schemaauth_schemapublic
Property schemaproperty_schemapublic
Primary code differencesearch_path changes.database changes.
PermissionsDatabase CONNECT + schema/table/sequence privileges.Separate database access + schema/table/sequence privileges.
  • Create one Pool per service process and reuse it; pool.query() checks out and returns a client for a single query.
  • For a transaction, obtain one client with pool.connect(), use that client for BEGIN, all statements, and COMMIT/ROLLBACK, then release it in finally. Do not scatter a transaction across pool.query() calls.
  • Use $1, $2, etc. for query values. Parameters do not substitute schema or table identifiers; keep those fixed or validate and quote them safely.
  • The max setting applies per process. More service replicas multiply the total potential connection count.
  • Cross-schema foreign keys are technically possible in Level 1, but create cross-service coupling. Ordinary foreign keys cannot reference a different PostgreSQL database.
  • Level 3 means an independent PostgreSQL deployment, not merely another pgAdmin registration. Two local instances on different ports still share their machine.
  • The URI postgresql://user:password@localhost:5432/auth chooses database auth; it does not choose a schema.
