🎯 Questions 1–5
Q1 — What Is Next.js, and Why Use It Over Client-Side React?⭐

Next.js is a React framework that provides routing, server rendering, static generation, server-side functionality, and built-in optimizations.

A client-side React application normally relies on browser JavaScript to render its content. Next.js can generate content on the server, which can improve initial loading and make content available to search engines earlier.

💡 Example: an eCommerce application can use prerendered product pages with interactive Client Components for the cart.
Q2 — How Does the App Router Define Routes?
The App Router uses folders inside app to represent URL segments.
FilePurpose
page.tsxDefines the UI for a publicly accessible page
layout.tsxShares UI across pages and preserves state during navigation within that layout
template.tsxShares UI but remounts when its route segment changes, resetting local state and rerunning effects

For example, app/products/page.tsx creates the /products page.

Q3 — Server Components vs Client Components⭐
Server ComponentsClient Components
Default for pages and layoutsDeclared through a "use client" boundary
Can access databases and server-side secretsCan use state, effects, and event handlers
Component code stays out of the browser bundleComponent code is included in the browser bundle
Suitable for fetching and displaying dataSuitable for interactive UI
💡 Example: fetch product details in a Server Component and render an interactive "Add to cart" button as a Client Component.
Q4 — What Does "use client" Do?⭐
"use client" defines a client entry point. Its imported component tree becomes part of the client bundle.

It allows features such as:

  • useState and useEffect.
  • Event handlers such as onClick.
  • Browser APIs, used in appropriate places such as effects.
⚠️ It does not mean browser-only rendering. On the initial load, Next.js can prerender Client Components on the server and then hydrate them in the browser. Reading window or localStorage directly during rendering can still cause problems.
Q5 — How Do Server and Client Components Work Together?

A Server Component can render a Client Component and pass data to it.

app/products/[id]/page.tsx
// Server Component
export default async function Page() {
  const product = await getProduct();

  return <AddToCart productId={product.id} />;
}

Props crossing the boundary must be serializable by React. Strings, numbers, arrays, and plain objects containing supported values are common examples.

📝 Note: you cannot pass an ordinary server-side callback as an event handler. Server Functions are a supported exception. You can also pass server-rendered UI into a Client Component through children.

Q6 — Explain CSR, SSR, SSG, and ISR⭐
ApproachHow It WorksExample Use Case
CSRBrowser JavaScript renders or updates content, often after fetching dataInteractive dashboard
SSRServer renders content for each requestPersonalized account page
SSGContent is generated ahead of requests, commonly at build timeDocumentation or marketing page
ISRCached static content is regenerated after deploymentProduct catalog or blog

A single application can combine these approaches.

✅ Interview point: Server Components and SSR are different concepts. A Server Component can participate in static or request-time rendering.
Q7 — How Would You Fetch Fresh Data on Every Request?
Use cache: "no-store" for a server-side fetch.
app/products/page.tsx
export default async function Page() {
  const response = await fetch("https://api.example.com/products", {
    cache: "no-store",
  });

  if (!response.ok) {
    throw new Error("Failed to fetch products");
  }

  const products = await response.json();

  return <pre>{JSON.stringify(products, null, 2)}</pre>;
}

In the caching model without Cache Components, you can force the entire route to render dynamically:

force-dynamic.ts
export const dynamic = "force-dynamic";
  • no-store: skips persistent caching for that fetch.
  • force-dynamic: applies request-time rendering at route level.
⚠️ Version note: the route-level dynamic and revalidate settings belong to the previous caching model — don't apply them unchanged when Cache Components is enabled.
Q8 — What Is ISR, and How Does Revalidation Work?⭐
Incremental Static Regeneration updates cached static pages after deployment without rebuilding the entire application.
route-level.ts
// in the model without Cache Components
export const revalidate = 60;

Or configure an individual fetch:

fetch-revalidate.ts
const response = await fetch("https://api.example.com/products", {
  next: { revalidate: 60 },
});

Typical time-based behavior:

  1. Requests receive cached content.
  2. After 60 seconds, the next request can receive stale content while regeneration happens.
  3. Following successful regeneration, later requests receive updated content.
⚠️ It is not a timer that rebuilds the page every 60 seconds.
📝 Event-driven updates: for updates triggered by events, such as editing a product, use on-demand revalidation APIs such as revalidatePath.
Q9 — Fetching Data: Server Components vs Client Components⭐

Server Component: use async/await directly in the component. You can call an API or query a database.

server-fetch.tsx
export default async function Page() {
  const products = await getProducts();

  return <ProductList products={products} />;
}

Client Component: use a client data library such as SWR/TanStack Query, or fetch inside an effect with loading, error, and cleanup handling.

✅ Rule of thumb: use server fetching for initial page content and private server access. Use client fetching for browser-driven updates, polling, and interactive filters. Server fetching also avoids exposing database credentials in the browser bundle.
Q10 — loading.tsx, Suspense & Streaming
  • loading.tsx: defines a route segment's loading fallback.
  • Suspense: lets you show a fallback around a specific part of the UI while it suspends.
  • Streaming: sends ready parts of the page before slower parts finish.
suspense-example.tsx
<Suspense fallback={<p>Loading reviews...</p>}>
  <Reviews />
</Suspense>
💡 Example: show product information immediately while reviews load separately.
⚠️ Gotcha: an ordinary fetch started in useEffect does not automatically activate Suspense.

Q11 — error.tsx vs global-error.tsx vs not-found.tsx
FilePurpose
error.tsxDisplays fallback UI for uncaught rendering errors in the segment's child tree
global-error.tsxHandles errors including those in the root layout; must provide its own <html> and <body>
not-found.tsxDisplays missing-resource UI when notFound() is triggered
📝 Both error.tsx and global-error.tsx must be Client Components.
⚠️ Scope gotcha: an error.tsx boundary does not catch errors in the layout of the same segment — those reach a parent boundary. Handle event-handler errors separately with try...catch.
Q12 — Dynamic, Catch-All & Optional Catch-All Routes⭐

  • Catch-all: one or more segments, such as nested documentation.
  • Optional catch-all: also accepts the base route with no additional segment.
Q13 — Route Parameters vs Query Parameters

For this URL: /products/10?sort=price

  • Route parameter: 10 identifies the product.
  • Query parameter: sort=price supplies an option.

In current App Router Server Component pages, await the props:

app/products/[id]/page.tsx
export default async function Page({ params, searchParams }) {
  const { id } = await params;
  const { sort } = await searchParams;

  return <p>{id} — {sort}</p>;
}

In Client Components:

client-params.tsx
const { id } = useParams();
const searchParams = useSearchParams();
const sort = searchParams.get("sort");
📝 Import both hooks from next/navigation.

Q15 — Nested Layouts & Route Groups

Nested layouts add shared UI to a section of the application. For example, app/dashboard/layout.tsx can provide a sidebar for all dashboard pages.

Route groups use parentheses to organize routes without adding a URL segment.

FileURL
app/(auth)/login/page.tsx/login
app/(auth)/register/page.tsx/register
app/(main)/dashboard/page.tsx/dashboard
✅ Pattern: add a layout inside (auth) for authentication pages and another inside (main) for the main application.
🎯 Questions 16–20
Q16 — How next/image Optimizes Images vs <img>⭐

next/image adds an image optimization pipeline and useful defaults:

  • Generates appropriately sized image variants.
  • Supports efficient formats such as WebP.
  • Lazy-loads images by default.
  • Uses dimensions to reserve space and reduce layout shifts.
  • Generates responsive image candidates for the browser.
next-image.tsx
import Image from "next/image";

<Image
  src="/product.jpg"
  alt="Blue running shoes"
  width={600}
  height={400}
  sizes="(max-width: 768px) 100vw, 600px"
  style={{ width: "100%", height: "auto" }}
/>

For external URLs, configure allowed sources using images.remotePatterns.

💡 Why can it be faster? a mobile browser can download a smaller optimized image instead of the full original. A normal <img> can also be optimized, but you must arrange resizing, formats, and responsive sources yourself.
Q17 — How Do You Implement SEO in Next.js?

Use static metadata for fixed page information:

static-metadata.tsx
export const metadata = {
  title: "Products | My Store",
  description: "Explore our latest products.",
};

Use generateMetadata when metadata depends on route data, such as a product's name and description.

Also configure:

  • Canonical URLs.
  • Open Graph and Twitter metadata for sharing.
  • sitemap.xml and robots.txt.
  • Semantic headings and useful page content.
📝 Metadata exports are supported in Server Components.
Q18 — How next/font Improves Font Loading & Layout Stability
next/font manages font loading and supports self-hosted Google and local fonts.
next-font.tsx
import { Inter } from "next/font/google";

const inter = Inter({
  subsets: ["latin"],
  display: "swap",
});

export default function Layout({ children }) {
  return <div className={inter.className}>{children}</div>;
}

For Google fonts, the browser fetches the font from your application rather than contacting Google.

✅ Benefit: font preloading and adjusted fallback metrics help improve loading and reduce layout shifts when the final font appears.
Q19 — What Causes Hydration Mismatches, and How Do You Fix Them?⭐
A hydration mismatch happens when the server-generated HTML differs from the browser's first render.

Common causes include:

  • Rendering Math.random() or changing timestamps.
  • Reading browser-only values during rendering.
  • Different server and browser locale formatting.
  • Invalid HTML nesting.

For browser-specific data, read it after hydration:

app/components/Theme.tsx
"use client";

import { useEffect, useState } from "react";

export default function Theme() {
  const [theme, setTheme] = useState("light");

  useEffect(() => {
    setTheme(localStorage.getItem("theme") ?? "light");
  }, []);

  return <p>{theme}</p>;
}

Both initial renders use "light"; the effect updates it afterward.

⚠️ Fix the underlying mismatch rather than routinely hiding it with suppressHydrationWarning.
Q20 — How Would You Build and Deploy a Next.js Application?

With the usual package scripts:

terminal
npm run build
npm run start
  • Build: creates the production build.
  • Start: runs the production Next.js server.
DeploymentCapabilities
Node.js server or compatible platformSupports request-time server features, including SSR
Static export using output: "export"Produces static files; does not support features requiring a Next.js server, such as request-time SSR or ISR

You can also deploy a Node.js application using Docker.

For environment variables:

.env
DATABASE_URL=private-server-value
NEXT_PUBLIC_API_URL=https://api.example.com
⚠️ Remember: ordinary variables remain server-side by default. Variables prefixed with NEXT_PUBLIC_ are exposed to browser code and typically embedded at build time, so they must never contain secrets.
