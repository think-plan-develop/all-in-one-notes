What happens between calling a state setter and React updating the screen?

When a state setter is called

setState→schedule update→render→reconciliation/diffing→commit DOM changes→browser paints

React compares the previous React tree with the new React tree, then updates only the required parts of the actual DOM.

How does React reconciliation work, and what role do keys play?EY

Reconciliation, diffing, Fiber, and keys

  • Reconciliation is the process React uses to compare the previous UI tree with the new UI tree.
  • Diffing algorithm helps React determine what changed.
  • Fiber is React's internal architecture used to organize and schedule rendering/reconciliation work.
  • Commit phase applies the required changes to the actual DOM.
  • Keys help React identify which list item is the same between renders.
users.map(user => (
  <User key={user.id} user={user} />
))

Stable keys are important when items are:

  • added
  • removed
  • reordered
3
Why can using an array index as a key cause incorrect behavior in an editable list?

Why array index as key can cause problems

Array indexes change when items are inserted, deleted, or reordered.

Example:

0 → A
1 → B
2 → C

Delete A:

0 → B
1 → C

React may associate the previous component/state of A with B.

Prefer
key={item.id}
Avoid when possible
key={index}

Especially important for editable lists or components with local state.

What is the difference between controlled and uncontrolled inputs?

Controlled vs uncontrolled input

Controlled input

React state is the source of truth.

const [name, setName] = useState("");

<input
  value={name}
  onChange={e => setName(e.target.value)}
/>

Flow:

User types→onChange→setState→rerender→input gets new value
Uncontrolled input

The DOM itself stores the input value.

Usually accessed using ref.

const inputRef = useRef();

<input ref={inputRef} />

Access value:

inputRef.current.value
Key difference:
Controlled → React state owns value
Uncontrolled → DOM owns value
5
When does React preserve a component's state, and when does it reset it?

When React preserves or resets state

React preserves state when the same component stays at the same position in the component tree with the same identity/key.

<Counter />

Parent rerendering does not automatically reset Counter state.

React resets state when:

  • component is removed/unmounted
  • component is replaced by another component
  • component key changes

Example:

<Counter key="A" />

changes to:

<Counter key="B" />

React treats it as a new component instance.

6
Why must hooks be called at the top level of a component or custom hook?

Why hooks must be called at the top level

Hooks are functions, not components.

Examples:

useState()
useEffect()
useRef()
useMemo()

React relies on hooks being called in the same order on every render.

Correct:

const [name, setName] = useState("");
const [age, setAge] = useState(20);

React associates them by order:

Hook #1 → name
Hook #2 → age

Avoid calling hooks inside:

  • if statements
  • loops
  • nested functions
Reason: the hook order can change between renders, so React may associate state with the wrong hook.

When would useLayoutEffect be more appropriate than useEffect?EY

useLayoutEffect vs useEffect

Use useLayoutEffect when you need to:

  • measure DOM layout
  • synchronously change layout before the browser paints
  • avoid visible flicker

Example cases:

measure element width/height
calculate tooltip position
scroll positioning before paint

Difference:

useLayoutEffect → runs after DOM update, before browser paint
useEffect       → generally runs after browser paint
Use useEffect by default. Use useLayoutEffect only when layout timing matters.

What problem does useImperativeHandle solve? Give a practical example.EY

useImperativeHandle

useImperativeHandle lets a child component control what the parent can access through a ref.

Instead of exposing the entire DOM element, the child can expose specific methods.

Practical example:

const CustomInput = forwardRef((props, ref) => {
  const inputRef = useRef(null);

  useImperativeHandle(ref, () => ({
    focus() {
      inputRef.current.focus();
    },
    clear() {
      inputRef.current.value = "";
    }
  }));

  return <input ref={inputRef} />;
});

Parent:

const ref = useRef(null);

<CustomInput ref={ref} />

<button onClick={() => ref.current.focus()}>
  Focus
</button>

Purpose:

Parent should call child functionality
without directly exposing all internal implementation
Think: ref + controlled public methods
11
What is a stale closure? How can it affect a timer that reads state?

Stale closure

A stale closure happens when a function remembers an older value of state or props from the render in which that function was created.

Example:

const [count, setCount] = useState(0);

useEffect(() => {
  const timer = setInterval(() => {
    console.log(count);
  }, 1000);

  return () => clearInterval(timer);
}, []);

Because the dependency array is empty, the callback captures:

count = 0

from the first render.

Even if count later becomes 5, the timer may still log:

0
0
0

This is a stale closure.

One solution:

useEffect(() => {
  const timer = setInterval(() => {
    setCount(prev => prev + 1);
  }, 1000);

  return () => clearInterval(timer);
}, []);

Functional updates use the latest state:

prev => prev + 1

How do you choose between local state, Context, and Redux?Nike

Local state vs Context vs Redux

Local state

Use when data belongs to one component or a small parent-child area.

modal open/close
input value
dropdown state
Context

Use when multiple components need relatively simple shared data without prop drilling.

theme
language
authenticated user
Redux

Use for larger application-wide state where many components read/update the data and you need predictable centralized state management.

complex global state
many related updates
shared API/application data
Compact rule:
Local state → local UI data
Context → simple shared/global data
Redux → complex centralized application state

If two components call the same custom hook, do they share its state? How would you make them share data?

Same custom hook called by two components

If two components call the same custom hook:

const data = useMyHook();

they usually get separate hook state.

Example:

function useCounter() {
  const [count, setCount] = useState(0);
  return { count, setCount };
}

If A and B both call useCounter():

Component A → own count
Component B → own count
Custom hooks share logic, not state instances.

To share the actual data, move the state somewhere shared, such as:

parent component
Context
Redux
external store

So Redux is one solution, but not the only one.

What do React.memo and useMemo each cache?EY

React.memo vs useMemo

  • React.memo prevents unnecessary component re-renders when props are unchanged.
  • useMemo does not prevent the whole component from re-rendering. It caches a calculated value and recalculates it only when dependencies change.
const value = useMemo(() => expensiveCalculation(data), [data]);
15
Why might a memoized child still re-render when its parent renders?

Why a memoized child may still re-render

Even if a child is wrapped with React.memo, it can still re-render in several cases.

Case 1: A prop value actually changes
const Child = React.memo(({ name }) => {
  return <h1>{name}</h1>;
});

If parent changes:

<Child name="Shivam" />

to:

<Child name="Rahul" />

the child re-renders because the prop changed.

Case 2: Object or array reference changes

This is very common.

<Child user={{ name: "Shivam" }} />

Every parent render creates a new object. Even though { name: "Shivam" } looks the same, the references are different:

{} === {} // false

So React.memo sees the prop as changed. You can stabilize it with:

const user = useMemo(() => {
  return { name: "Shivam" };
}, []);

<Child user={user} />
Case 3: Function prop gets recreated
<Child onClick={() => handleClick()} />

Every render creates a new function reference, so the memoized child may re-render. You can use:

const handleClick = useCallback(() => {
  console.log("clicked");
}, []);

Then:

<Child onClick={handleClick} />
Case 4: Child's own state changes

React.memo only helps with parent-prop-based rerenders. If the child has:

const [count, setCount] = useState(0);

and count changes, the child will re-render.

Case 5: Context value changes

If the child uses:

const theme = useContext(ThemeContext);

and context changes, the child re-renders even if props are unchanged.

Interview answer:
A memoized child can still re-render if its props change, if new object/function references are passed, if its own state changes, or if a Context value it consumes changes.

Explain how you would split a React application into lazily loaded routes.EY

Splitting a React app into lazily loaded routes

The purpose of lazy loading is to avoid loading the entire application JavaScript bundle at once. Instead:

User opens /home
→ load Home code

User opens /admin
→ load Admin code only then

Use React.lazy() with dynamic import().

import { lazy, Suspense } from "react";

const Home = lazy(() => import("./Home"));
const Admin = lazy(() => import("./Admin"));

Then routes:

<Routes>
  <Route path="/" element={<Home />} />
  <Route path="/admin" element={<Admin />} />
</Routes>

Because loading is asynchronous, wrap routes with Suspense:

<Suspense fallback={<p>Loading...</p>}>
  <Routes>
    <Route path="/" element={<Home />} />
    <Route path="/admin" element={<Admin />} />
  </Routes>
</Suspense>

Flow:

React.lazy()→dynamic import()→route requested→JS chunk downloaded→component rendered

This is called code splitting. Benefits:

  • smaller initial bundle
  • faster initial load
  • code loaded only when required
Interview answer:
I would use React.lazy() with dynamic import() for route components and wrap them with Suspense. This creates separate JavaScript chunks so a route is loaded only when the user navigates to it.
17
How do nested routes and an outlet work in React Router?EY

Nested routes and Outlet in React Router

Nested routes are used when one route has child pages that share the same parent layout. For example:

/dashboard
/dashboard/profile
/dashboard/settings

Route configuration:

<Routes>
  <Route path="/dashboard" element={<Dashboard />}>
    <Route path="profile" element={<Profile />} />
    <Route path="settings" element={<Settings />} />
  </Route>
</Routes>

Here /dashboard is the parent route, and profile and settings are child routes. Inside Dashboard:

import { Outlet } from "react-router-dom";

function Dashboard() {
  return (
    <>
      <h1>Dashboard</h1>

      <nav>
        ...
      </nav>

      <Outlet />
    </>
  );
}

If URL is /dashboard/profile, React renders:

Dashboard→Outlet→Profile

If URL is /dashboard/settings, then:

Dashboard→Outlet→Settings

So <Outlet /> acts as a placeholder where the matched child route renders.

Interview answer:
Nested routes allow child routes to render inside a parent route. The parent component contains <Outlet />, and React Router renders the currently matched child route at that position.

How would you render thousands of records without making scrolling sluggish?Nike

Rendering thousands of records without sluggish scrolling

Pagination is valid if the user only needs a certain number of records per page:

10 / 20 / 50 records
Page 1 → records 1–50
Page 2 → records 51–100

But if the requirement is show thousands of rows in one scrollable list, the better solution is virtualization/windowing. Instead of rendering 10,000 DOM elements, React renders only the visible elements. If the screen can show 20 rows:

10,000 records exist
        ↓
only ~20–30 rows rendered
        ↓
user scrolls
        ↓
old rows removed
new visible rows rendered

Libraries commonly used:

react-window
react-virtualized
Without virtualization
10,000 data
→ 10,000 DOM nodes
→ expensive rendering
→ slow scrolling
With virtualization
10,000 data
→ render only visible 20–30 rows
→ fewer DOM nodes
→ smooth scrolling

You can also combine backend pagination + virtualization:

  • API sends 100 records at a time
  • virtualization renders only visible rows
  • fetch more records as user scrolls

This is useful for very large datasets.

Interview answer:
If the UI uses pages, I would use pagination. If thousands of records need to appear in a scrollable list, I would use list virtualization/windowing, such as react-window, so only visible rows are rendered in the DOM.

Predict the state update — 4 minutes

Assume count is initially 0.

function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);

    console.log(count);
  }

  return <button onClick={handleClick}>{count}</button>;
}
EXPLAIN
  • What does the console print on the first click?
  • What value appears on the button after the update?
  • How would you make one click increment the count by three?

Predict the state update

1. What does the console print on the first click?

Answer: 0

Reason: count is still 0 inside the current render/event handler. Calling setCount() schedules updates; it does not immediately change the count variable.

console.log(count); // 0
2. What value appears on the button after the update?

Answer: 1

Reason: All three updates use the same current value of count, which is 0.

setCount(count + 1); // setCount(1)
setCount(count + 1); // setCount(1)
setCount(count + 1); // setCount(1)

So React batches them and the final state becomes:

1

not 3.

3. How do you increment the count by three?

Answer: Use functional state updates.

setCount(prev => prev + 1);
setCount(prev => prev + 1);
setCount(prev => prev + 1);

Reason: Each updater receives the latest pending state.

0 → 1
1 → 2
2 → 3

So after one click: button value = 3.

flushSync is not needed here. The correct solution is the functional updater form.

Find and fix the timer problems — 6 minutes
function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    setInterval(() => {
      setSeconds(seconds + 1);
    }, 1000);
  }, []);

  return <p>{seconds}</p>;
}
EXPLAIN
  • Why does the displayed value stop increasing?
  • What cleanup is missing?
  • How would you fix it without recreating the interval every second?

Find and fix the timer problems

1. Why does the displayed value stop increasing?

Correct answer: because of a stale closure.

The effect runs only once because of:

[]

When that effect is created, seconds is 0. So the interval callback keeps remembering:

seconds = 0

and repeatedly does:

setSeconds(0 + 1);

So the value becomes 1 and then stays 1.

It is not simply because the component rerenders. The empty dependency array is part of why the callback keeps the initial value, but the key issue is the stale closure.
2. What cleanup is missing?

You need to store the interval ID and clear it:

useEffect(() => {
  const intervalId = setInterval(() => {
    // update
  }, 1000);

  return () => {
    clearInterval(intervalId);
  };
}, []);

The cleanup runs when the component unmounts.

3. How would you fix it without recreating the interval every second?

Do not switch to setTimeout. Use a functional state update:

useEffect(() => {
  const intervalId = setInterval(() => {
    setSeconds(prev => prev + 1);
  }, 1000);

  return () => {
    clearInterval(intervalId);
  };
}, []);

Why this works:

prev => prev + 1

always receives the latest state value. Flow:

0 → 1
1 → 2
2 → 3
3 → 4

And because the dependency array is still empty ([]), the interval is created only once, not every second.

📌 Company basis: Nike's report includes effect-related race conditions; EY's includes fetching data based on changing input.

A user types "react", then changes it to "redux". The "redux" request finishes first, but the older "react" response arrives later and replaces the results.

Q1

Why does this happen, and how would you prevent it?

Q2

Does debouncing alone solve the problem?

Q3

How would you test this behavior reliably?

Search results in the wrong order

Q1. Why does this happen, and how would you prevent it?

It usually happens because multiple API requests are sent, and an older request may finish after a newer one.

Example:

Search "rea"   → Request A
Search "react" → Request B

Request B finishes first
Request A finishes later

If Request A updates the state last, the UI can show stale data.

Prevent it by:

  • cancelling the previous request using AbortController
  • or ignoring stale responses using a request ID/version
  • optionally combining this with debouncing

Example idea:

useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${query}`, {
    signal: controller.signal
  });

  return () => {
    controller.abort();
  };
}, [query]);
Q2. Does debouncing alone solve the problem?

No.

Debouncing only reduces how often the API is called.

Example:

User types quickly
→ wait 500ms
→ send request

But if multiple requests are already in progress, they can still finish out of order.

So:

Debounce → reduces requests
AbortController / stale-response protection → prevents race condition

A stronger solution is often:

debounce + cancellation
Q3. How would you test this behavior reliably?

Test the race condition by intentionally making responses complete in the wrong order.

Example:

Request 1 → delay 1000ms
Request 2 → delay 200ms

Then verify that the UI shows the result from Request 2, not Request 1.

With React Testing Library/MSW you can:

  1. type the first query
  2. trigger the first API request
  3. type a newer query
  4. make the newer response return first
  5. make the older response return later
  6. verify stale data does not replace the latest result

For debounce behavior, use fake timers:

jest.useFakeTimers();

fireEvent.change(input, {
  target: { value: "react" }
});

jest.advanceTimersByTime(500);

Then verify the API was called only after the debounce delay.

Interview answer:
Debouncing reduces API calls but does not guarantee response order. I would also cancel previous requests or ignore stale responses, and test it by mocking delayed responses that resolve out of order.

A product page feels slow — 5 minutes
📌 Company basis: Nike's report includes a product filtering interface and performance work; Swiggy's includes component design, testing, and monitoring.

Your page contains 2,000 product cards, filters, and a cart. Typing into a filter causes noticeable lag.

Q1

A product page feels slow

1. How would you measure whether the delay comes from rendering, filtering, or network requests?

Use separate measurements for each stage.

For network, check the browser Network tab:

  • request start time
  • response time
  • API duration

If the API itself is slow, the delay will be visible there.

For filtering/calculation, measure the filtering code:

console.time("filter");

const filtered = products.filter(/* condition */);

console.timeEnd("filter");

If this takes a long time, the bottleneck is computation.

For rendering, use the React DevTools Profiler. It shows:

  • which components re-render
  • how long they take
  • whether all 2,000 cards are rendering again
Interview answer:
I would separate network, calculation, and render time. I would use the Network tab for API latency, timing/profiling around the filtering logic for computation cost, and the React Profiler to see which components re-render and how expensive those renders are.
2. How would you decide between moving state, memoizing calculations, and virtualizing the list?

Use the fix based on the actual bottleneck.

Move state when a state update causes too many unrelated components to re-render.

Example:

Filter input changes
↓
entire page rerenders
↓
cart + header + 2000 cards rerender

If only the filter area needs that state, keep the state closer to that component.

Memoize calculations when filtering itself is expensive.

const filteredProducts = useMemo(() => {
  return products.filter(/* condition */);
}, [products, filter]);

This avoids repeating the calculation when unrelated state changes. Also use React.memo if individual product cards rerender even though their props did not change.

Virtualize the list when the main problem is rendering thousands of cards. Instead of rendering all:

2000 cards

render only what is visible:

20–30 cards

using tools like:

react-window
react-virtualized
Compact rule:
Too many unrelated rerenders → move state
Expensive calculation → useMemo
Too many DOM nodes → virtualization
3. What would you test and monitor to confirm the change improves the experience?

Compare before and after. Measure:

  • input-to-screen response time
  • filtering execution time
  • React render duration
  • number of components re-rendered
  • number of DOM nodes rendered
  • API request count and latency
  • scroll smoothness

For example, after virtualization:

Before:
2000 ProductCard renders

After:
~20–30 visible ProductCard renders

Also verify correctness:

  • filtering still returns correct products
  • cart still works
  • scrolling does not lose items/state
  • no stale search/filter result appears
Interview answer:
I would compare profiler data before and after the optimization: render duration, number of rerenders, filtering time, network requests, and responsiveness while typing. I would also run functional tests to make sure filtering, scrolling, and cart behavior still work correctly.
