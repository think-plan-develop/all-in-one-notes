⚛️ 2. React Fundamentals — 10 min
Core Concepts
This block checks whether re-renders, immutability, keys, and event-handler wiring are understood at a working level, not just memorized definitions.
  • Q4. What causes a React component to re-render? Does every render result in a DOM update?
    Rendering versus updating the DOM
    • Render: React calls your component function to calculate the UI.
    • DOM update: React applies the necessary changes to the actual DOM.

    A React component can re-render when:

    • Its state changes.
    • Its parent re-renders, even if the props stay the same.
    • A context value it uses changes.
    • A Redux value it selects changes.

    Does every render update the DOM?
    No. React calculates the new UI and updates the DOM only if something needs to change.

    Does changing let a = 10 to a = 13 re-render the child?
    No. Changing a normal variable does not trigger a render, even if you passed it as a prop. Use state to update the value and trigger a render.

  • Q5. Why should state updates be immutable? How would you update one item inside an array of objects?
    Immutable state updates

    Immutable updates mean creating a new array or object instead of changing the existing state directly.

    State updates should be immutable so React can detect changes through a new reference. Direct mutation keeps the same reference, so React may skip the update.

    To update one item in an array of objects, use map() and spread:

    setUsers(prev =>
  prev.map(user =>
    user.id === 2 ? { ...user, name: "Rakesh" } : user
  )
);

    This creates a new array and a new object for the updated user without changing the previous state.

  • Q6. How do keys affect component identity? What happens if you generate a new random key during every render?
    Random keys

    A new random key makes React treat the item as a completely new component.

    “Keys help React identify the same list items between renders. If we generate new random keys every render, React recreates those components instead of preserving them, causing state loss and unnecessary work.”
  • Q7. What is the difference between passing an event handler and calling it inside JSX?
    Passing vs calling an event handler

    Because handleDelete(id) executes the function, while handleDelete passes the function itself.

    JSX evaluates whatever you write inside {} during rendering.

    CodeWhat React receives
    onClick={handleDelete}The function—to call later on click
    onClick={handleDelete(id)}The result of calling the function immediately
    onClick={() => handleDelete(id)}An arrow function—to call later on click

    Think of the difference in plain JavaScript:

    const handler = handleDelete;           // Store the function
const result = handleDelete(id);        // Run it now and store its result
const wrapper = () => handleDelete(id); // Store a function that runs it later

    onClick needs a function it can call when you click. The arrow function lets you pass id while delaying the call.

Q7-handlers.jsx
<button onClick={handleDelete}>Delete</button>

<button onClick={handleDelete(id)}>Delete</button>

<button onClick={() => handleDelete(id)}>Delete</button>
⚠️ Watch for: the second line calls handleDelete(id) immediately during render (its return value becomes the handler), instead of passing a function reference.
  • Q8. What is an error boundary? Can it catch errors from event handlers and asynchronous callbacks?
📝 Expected answer: no — error boundaries only catch errors during rendering, in lifecycle methods, and in constructors of the tree below them. Event handlers and async code need their own try/catch.
🪝 3. Hooks & State Management — 15 min
Effects, Closures, Reducers, Context & Memoization
  • Q9. Explain the difference between these effects. When does each run?
Q9-effects.jsx
useEffect(() => {
  // ...
});

useEffect(() => {
  // ...
}, []);

useEffect(() => {
  // ...
}, [userId]);
📝 Expected answer: no dependency array → runs after every render; [] → runs once after the first render; [userId] → runs after the first render and again whenever userId changes.

  • Q12. What happens to Context consumers when the provider value changes? How would you reduce unnecessary renders?

🐛 4. Code Debugging — 10 min
Question 16 — Direct State Mutation (5 min)
Identify the problems and rewrite the handler so React actually detects the change.
Q16-buggy.jsx
function Users() {
  const [users, setUsers] = useState([
    { id: 1, name: "Amit", active: false },
    { id: 2, name: "Neha", active: false },
  ]);

  function activateUser(id) {
    const user = users.find(item => item.id === id);

    user.active = true;   // ❌ mutates state directly
    setUsers(users);     // ❌ same array reference — React bails out
  }

  return users.map(user => (
    <button key={user.id} onClick={() => activateUser(user.id)}>
      {user.name}: {user.active ? "Active" : "Inactive"}
    </button>
  ));
}
  • Why might the screen not update?
  • How would you update only the selected user immutably?
  • How would you handle an ID that does not exist?
Q16-fixed.jsx
function activateUser(id) {
  setUsers(current => current.map(user =>
    user.id === id ? { ...user, active: true } : user
  ));
}
💡 Model answer: React compares state by reference; mutating the same array/object and passing it back to setUsers doesn't change that reference, so React skips the re-render. Mapping to a new array with a new object for the matched user fixes it, and a non-existent ID simply matches nothing — the map returns the array unchanged, which is safe.
Question 17 — Incorrect Effect Dependencies (5 min)
Identify the problems in this component.
Q17-buggy.jsx
function UserDetails({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    fetch(`/api/users/${userId}`)
      .then(response => response.json())
      .then(data => setUser(data));
  }, []);   // ❌ missing userId dependency

  return <h2>{user.name}</h2>;   // ❌ crashes while user is still null
}
  • What happens during the first render?
  • What happens when userId changes?
  • How would you handle loading and HTTP errors?
  • How would you prevent an outdated request from replacing the latest user?
⚠️ Two bugs: user.name throws on the first render because user starts as null, and the empty dependency array means the effect never re-fetches when userId changes — it keeps showing the first user forever.
💡 Race condition fix: add userId to the dependency array, guard the render with a loading/null check, and use an ignore flag (or AbortController) in the effect's cleanup so a slow, outdated response can't overwrite a newer one.
