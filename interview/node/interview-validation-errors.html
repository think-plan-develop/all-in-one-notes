🧩 At a Glance — Three Layers of Validation
1️⃣
Zod: validates HTTP body / params / query before the controller ever runs.
2️⃣
Mongoose: schema validators are the DB-side safety net for every write source.
3️⃣
Service checks: DB-dependent business rules — email exists, resource exists, ownership.
🏗️
Error architecture: AppError → asyncHandler → errorHandler.
1️⃣ Zod — API Boundary Validation ⭐⭐⭐⭐⭐
Request→ validate(schema)→ Controller→ Service→ DB

import { z } from "zod";

const createUserSchema = z.object({
  name: z.string().trim().min(2).max(50),
  email: z.string().email().toLowerCase(),
  password: z.string().min(8),
  role: z.enum(["ADMIN", "USER"]).default("USER")
});

type CreateUserDTO = z.infer<typeof createUserSchema>;

🧩 Reusable middleware

validate.middleware.ts
const validate = (schema: z.ZodType) => (req, res, next) => {
  const result = schema.safeParse(req.body);

  if (!result.success) {
    return res.status(400).json({
      success: false,
      errors: result.error.issues.map(e => ({
        field: e.path.join("."), message: e.message
      }))
    });
  }

  req.body = result.data;   // validated + transformed data
  next();
};

router.post("/users", validate(createUserSchema), createUser);
MethodBehavior
parse()Returns parsed data; throws ZodError if invalid.
safeParse()Never throws; returns { success, data | error }. Convenient for validation middleware.

🏗️ Centralized Error Handling — Core Architecture ⭐⭐⭐⭐⭐
Route / Middleware→ Controller→ Service→ throw AppError→ asyncHandler→ errorHandler
PieceRole
AppErrorBase class for expected/operational errors. Stores message, status code and optional details.
errorHandlerOne 4-argument Express middleware registered last. Converts every error to one response format.
asyncHandlerWraps async controllers and forwards promise rejection using .catch(next).
handleMongooseErrorNormalizes validation, duplicate-key and cast errors.

🧱 AppError pattern

AppError.ts
class AppError extends Error {
  constructor(
    message: string,
    public statusCode = 500,
    public errors?: unknown
  ) {
    super(message);
    this.name = this.constructor.name;
  }
}

class NotFoundError extends AppError {
  constructor(resource = "Resource") { super(`${resource} not found`, 404); }
}
class UnauthorizedError extends AppError { constructor(msg="Unauthorized"){ super(msg,401); } }
class ForbiddenError extends AppError { constructor(msg="Forbidden"){ super(msg,403); } }
class ConflictError extends AppError { constructor(msg="Conflict"){ super(msg,409); } }
🔁 asyncHandler — Remove Repeated try/catch
asyncHandler.ts
const asyncHandler = (fn) => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next);

router.get("/:id", asyncHandler(async (req, res) => {
  const user = await userService.getUserById(req.params.id);
  res.json(user);
}));
🧯 Global Error Handler — Decision Order
errorHandler.ts
const errorHandler = (err, req, res, next) => {
  if (err instanceof ZodError)
    return res.status(400).json({ success:false, message:"Validation failed" });

  if (err instanceof AppError)
    return res.status(err.statusCode).json({ success:false, message:err.message });

  const mongo = handleMongooseError(err);
  if (mongo) return res.status(mongo.statusCode).json(mongo.body);

  return res.status(500).json({ success:false, message:"Internal Server Error" });
};

app.use(notFound);
app.use(errorHandler); // LAST

❓ Most Asked Interview Questions
Where should request validation happen?
Reusable middleware before controller/business logic.
Why Zod + Mongoose both?
Zod protects the HTTP boundary; Mongoose protects DB writes from any source.
Why use DTOs?
Type-safe contract between layers; avoids spreading raw any/req.body.
Where do DB-dependent validations belong?
Service layer, because they are business rules requiring queries.
Why centralized error handling?
Consistent responses, no repeated status/message logic, easier logging and maintenance.
Why asyncHandler?
Forwards rejected async controller promises to Express error middleware without repeated try/catch.
Is unique:true validation?
No. It creates a unique index; duplicate inserts surface as error code 11000.
400 vs 409?
400 = invalid input/type/schema. 409 = request conflicts with current state, e.g. duplicate email.
401 vs 403?
401 = authentication failed. 403 = identity known but action not permitted.
Why must errorHandler be last?
It should receive errors forwarded from all earlier routes/middleware.
🎤 30-Second Interview Answer
"I use layered validation and centralized error handling." Zod validates and sanitizes API input in reusable middleware, and z.infer gives typed DTOs. Mongoose schema validators protect database writes, while DB-dependent checks stay in the service layer. Services throw typed AppError errors, async controllers forward failures through asyncHandler, and one global error middleware maps Zod, application and MongoDB errors into consistent HTTP responses.
💡 Golden rule: Route wires → middleware guards → controller orchestrates → service decides → Mongoose persists → errorHandler responds.
