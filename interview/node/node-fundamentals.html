🔄 1. What Is the Event Loop?
Keep Working While I/O Is Pending
The event loop is the mechanism that lets Node.js continue doing other work while asynchronous operations are pending, and run their callbacks when they are ready and the main thread is available.

First, understand two things:

  • Executing JavaScript: running your functions, conditions, loops, etc.
  • Waiting for I/O: waiting for a database response, file read, or network response.

While an asynchronous I/O operation is pending, the main thread can execute other JavaScript.

For example:

import fs from "node:fs";

console.log("1. Start");

fs.readFile("notes.txt", "utf8", (error, data) => {
  if (error) {
    console.error(error);
    return;
  }

  console.log("3. File content:", data);
});

console.log("2. Continue other work");

What happens

Order of execution
STEP 1Node executes the first console.log()
→
STEP 2fs.readFile() starts an async file operation
→
STEP 3Node continues and prints "2. Continue other work"
→
STEP 4When the read completes, its callback becomes ready
→
STEP 5The event loop processes the completion; the callback executes on the main thread

The event loop processes different categories of callbacks in phases. Some main phases are:

PhaseHandles
TimersEligible setTimeout() and setInterval() callbacks
PollI/O events and their callbacks
ChecksetImmediate() callbacks
Close callbacksEvents such as a socket closing
⚠️ A ready callback must wait if the main thread is busy executing synchronous JavaScript. The event loop cannot interrupt a running loop or function.
🧵 2. How Does Node.js Handle Concurrent Requests if Single-Threaded?
One Main Thread, Many Requests in Progress

Node.js executes your JavaScript on one main thread by default, but a request does not need to occupy that thread for its entire lifetime.

A request usually involves two kinds of work:

WorkExampleMain thread’s involvement
Executing JavaScriptValidating input, calculating totals, processing resultsExecutes the code
Waiting for asynchronous I/OWaiting for a database query, API response, or file readCan execute other JavaScript while waiting

When a request starts an asynchronous I/O operation, Node.js uses operating-system facilities or, for certain operations, libuv’s thread pool to handle the underlying work.

The main thread does not remain blocked waiting for the result. It can start or continue other requests. Once the result is available, the associated callback or code after await runs when the main thread is available.

Therefore, multiple requests can be in progress together, even though their JavaScript runs one piece at a time on the main thread. This is called concurrency.
ConcurrencyParallelism
Multiple tasks are in progress during overlapping periodsMultiple tasks execute at exactly the same time
Can happen on one thread by switching between available workRequires multiple execution resources, such as CPU cores
📝 “Single-threaded” does not mean Node.js completes one entire request before accepting the next.
Example 1: Two users request database information

Assume:

  • User A’s database query takes 2 seconds.
  • User B’s database query takes 1 second.

The following is an illustrative sequence:

TimeWhat happens
0 secondsNode handles request A and sends its database query
0.1 secondsWhile A is waiting, Node handles request B and sends its query
Around 1.1 secondsB’s result arrives; Node processes it and responds to B
Around 2 secondsA’s result arrives; Node processes it and responds to A

B does not have to wait for A’s query to finish. Their waiting periods overlap.

The database processes the queries; Node.js handles sending them and processing the responses.

Example 2: An Express route using await 
app.get("/users/:id", async (req, res, next) => {
  try {
    console.log("Request started:", req.params.id);

    const user = await User.findById(req.params.id);

    console.log("Data received:", req.params.id);

    res.json(user);
  } catch (error) {
    next(error);
  }
});

If users A and B call this route, the output could be:

Request started: A
Request started: B
Data received: B
Data received: A

At this line:

const user = await User.findById(req.params.id);

Only that particular handler pauses while its query is pending. The entire server does not pause.

When the query completes, the handler can resume and send its response.

Example 3: When the main thread cannot handle other requests

A heavy synchronous loop keeps the main thread busy:

app.get("/heavy", (req, res) => {
  let total = 0;

  for (let i = 0; i < 1_000_000_000; i++) {
    total += i;
  }

  res.json({ total });
});

While this loop executes, other request handlers on the same main thread cannot run, because the thread is actively calculating rather than waiting for asynchronous I/O.

Adding async to this function does not solve that problem. CPU-heavy JavaScript can be moved to Worker Threads or separate processes.
⚙️ 3. What Is libuv?
Event Loop, Async I/O and a Worker Thread Pool
libuv is a cross-platform library written in C that Node.js uses to provide its event loop, asynchronous I/O support, and a worker thread pool.

Here:

  • Cross-platform means it works across operating systems such as Windows, Linux, and macOS.
  • I/O (input/output) means operations such as reading files and communicating over a network.
  • Asynchronous means the application can continue doing other work while an operation is pending.

libuv helps Node.js handle these operations without blocking the main JavaScript thread while waiting.

Why does Node.js need libuv?

The JavaScript language itself does not provide operating-system features such as reading files or opening network connections. These capabilities come from the runtime.

Node.js provides APIs such as fs.readFile() and uses libuv underneath to arrange supported operations and process their completion.

This allows the main thread to handle other available work instead of waiting for every file read or network response.

What does libuv do?

ResponsibilityPurpose
Event loopProcesses events and completion notifications so associated callbacks can run
File operationsSupports asynchronous file reading, writing, and other filesystem operations
NetworkingSupports non-blocking TCP/UDP communication using operating-system facilities
Worker thread poolExecutes certain native operations outside the main JavaScript thread
TimersProvides timer support used by Node.js APIs such as setTimeout()
DNS supportProvides facilities such as the lookup work used by dns.lookup()
Cross-platform supportHandles differences between operating systems through a common interface

How does libuv work?

There are two important mechanisms:

MechanismHow it worksExamples
Operating-system I/O facilitiesNode manages network activity without dedicating a worker thread to each connectionHTTP requests and database connections
Worker thread poolA worker performs an operation, then reports its completion to the event loopAsynchronous file operations, dns.lookup(), certain crypto and compression operations
Not every asynchronous operation uses the thread pool.

For example, MongoDB executes your database query. Node.js and libuv help manage the network communication used to send that query and receive its result.

Example: reading a file 
import fs from "node:fs";

console.log("1. Start");

fs.readFile("notes.txt", "utf8", (error, data) => {
  if (error) {
    console.error(error);
    return;
  }

  console.log("3. File content:", data);
});

console.log("2. Continue other work");

What happens:

Reading a file through libuv
1Your JavaScript calls fs.readFile()
→
2Node.js delegates the underlying file work through libuv
→
3A libuv worker performs the file operation
4Meanwhile, the main thread prints "2. Continue other work"
→
5When the operation completes, libuv reports completion through the event loop
→
6Your JavaScript callback runs when the main thread is available
The worker performs the file operation; your JavaScript callback runs on the main thread.

Does libuv handle CPU-heavy JavaScript?

No—libuv does not automatically move ordinary JavaScript calculations to its worker pool.

let sum = 0;

for (let i = 0; i < 1_000_000_000; i++) {
  sum += i;
}

This loop executes on the main JavaScript thread and blocks other JavaScript callbacks until it finishes.

Adding async to the surrounding function does not change that. To execute CPU-heavy JavaScript outside the main thread, use Worker Threads or a separate process.

However, libuv’s pool can handle native CPU work submitted by supported APIs, such as certain asynchronous crypto and compression operations. Therefore, saying “libuv only handles I/O” is too restrictive.

What is the libuv thread-pool size?

The default pool size is 4 threads. It can be configured using the UV_THREADPOOL_SIZE environment variable before starting Node.js.

When all workers are busy, additional pool tasks wait for an available worker.

📝 This does not mean Node.js can handle only four concurrent requests. Ordinary network connections do not each require a worker-pool thread.

Do we manage libuv ourselves?

Usually, no. Node.js uses libuv internally when you call the relevant APIs. You do not need to install it separately or manually assign file operations to workers.

You still need to choose appropriate APIs:

  • fs.readFile() allows other JavaScript to run while the read is pending.
  • fs.readFileSync() blocks the calling thread until the read finishes.
  • For large files, use streams to avoid buffering the entire file in memory.

Is libuv part of V8?

No. They are separate components used by Node.js.

ComponentMain responsibility
V8Executes JavaScript, optimizes it, and manages JavaScript memory
libuvProvides the event loop, asynchronous I/O facilities, and worker thread pool
“libuv is a cross-platform C library that provides Node.js with its event loop, asynchronous I/O support, and a worker thread pool. It uses operating-system facilities for network I/O and worker threads for certain operations such as asynchronous file access. This allows the main JavaScript thread to continue handling other work while those operations are pending. It does not automatically offload CPU-heavy JavaScript.”
🚀 4. What Is the Role of V8 in Node.js?
The Engine That Executes Your JavaScript
V8 is Google’s open-source JavaScript engine that Node.js uses to execute JavaScript outside the browser. When you run node app.js, Node.js uses V8 to execute the JavaScript in your application.

Its main responsibilities are:

  1. Execute JavaScript: runs your functions, conditions, loops, request-handler logic, and callbacks.
  2. Optimize performance: uses just-in-time (JIT) compilation to generate machine code and optimize frequently executed code.
  3. Manage memory: allocates memory for JavaScript objects and uses garbage collection to reclaim memory from objects that are no longer reachable.
V8 does not provide Node.js APIs such as fs or http. Node.js supplies those APIs and uses components such as libuv for underlying I/O support.
For example, with fs.readFile(), Node.js and libuv handle the file operation, while V8 executes the JavaScript callback that processes the result.
⛔ 5. Blocking vs Non-blocking Operations
Does the Main Thread Keep Moving?
❌ Blocking

Blocking operations stop the main thread from executing other JavaScript until the operation finishes.

import fs from "node:fs";

const data = fs.readFileSync("notes.txt", "utf8");
console.log(data);
console.log("Next task");

Here, "Next task" prints after the file is read and its content is logged.

✅ Non-blocking

Non-blocking operations let the main thread continue executing other JavaScript while the operation is in progress.

import fs from "node:fs";

fs.readFile("notes.txt", "utf8", (error, data) => {
  if (error) {
    console.error(error);
    return;
  }

  console.log(data);
});

console.log("Next task");

Here, "Next task" prints before the file-reading callback runs.

BlockingNon-blocking
Holds up the main threadAllows the main thread to continue
Delays handling other requestsAllows other requests to progress while waiting
Examples: readFileSync(), heavy synchronous loopsExamples: readFile(), asynchronous network requests
⚡ 6. Why Is Node.js Fast?
Efficient JavaScript + Non-blocking I/O
Node.js is fast mainly because it combines efficient JavaScript execution with non-blocking I/O. It is particularly effective for applications handling many database calls, API requests, and network connections.

1. V8 executes JavaScript efficiently

Node.js uses the V8 engine, which uses JIT compilation and optimizes frequently executed code to improve performance.

2. Non-blocking I/O allows other work to continue

While an asynchronous database query, file read, or API request is pending, the main thread can handle other requests.

For example, if request A waits 2 seconds for a database response, Node.js can handle request B during that time.

The database query does not become faster—the server can do more work while waiting.

3. The event loop efficiently handles concurrent requests

The event loop processes ready callbacks, allowing many requests to remain in progress without requiring a separate JavaScript thread for every request. This reduces thread-management overhead.

4. libuv and the operating system support asynchronous work

Network I/O uses operating-system facilities, while certain operations—such as asynchronous file access—use libuv’s worker pool. This keeps the main JavaScript thread available for other work.

Node.js is not automatically fast for CPU-heavy tasks. Large synchronous loops or expensive calculations can block the main thread and delay other requests.
“Node.js performs well because V8 executes JavaScript efficiently, while non-blocking I/O and the event loop allow it to handle many concurrent requests without waiting for each I/O operation to finish. This makes it especially suitable for I/O-heavy applications.”
