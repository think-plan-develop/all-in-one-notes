🍪 Cookies

What Are Cookies?

Cookies are small pieces of data (usually up to 4KB) that a website stores in the browser. Unlike other storage types, cookies are automatically sent to the server with every HTTP request to the same domain, which makes them useful for session management, authentication, and tracking.

How Cookies Work

A cookie can be set either by the server (via the Set-Cookie HTTP response header) or by client-side JavaScript using document.cookie. Once set, the browser stores it and automatically attaches it to future requests until it expires.

cookies.js
// Setting a cookie with an expiry date and path
document.cookie = "username=John; expires=Fri, 31 Dec 2026 23:59:59 GMT; path=/";

// Setting a secure, HttpOnly-like cookie (HttpOnly only works from server)
document.cookie = "theme=dark; max-age=3600; SameSite=Strict; Secure";

// Reading all cookies
console.log(document.cookie);
// Output: "username=John; theme=dark"

// Deleting a cookie (set expiry in the past)
document.cookie = "username=; expires=Thu, 01 Jan 1970 00:00:00 GMT; path=/";

Key Attributes

AttributePurpose
expires / max-ageControls how long the cookie persists before it's deleted
pathRestricts the cookie to a specific URL path
domainSpecifies which domain(s) can access the cookie
SecureCookie is only sent over HTTPS connections
HttpOnlyPrevents JavaScript from accessing the cookie (server-set only)
SameSiteControls whether the cookie is sent with cross-site requests

Best Use & Trade-offs

✅ Best for: Authentication tokens, session IDs, and any data the server needs to read on every request.
⚠️ Watch out: Cookies are sent with every request, which adds overhead to network traffic if overused or if large amounts of data are stored.
Pros
  • Automatically sent to the server
  • Can set expiration dates
  • Supports HttpOnly for XSS protection
  • Works across subdomains via domain attribute
Cons
  • Very limited size (~4KB)
  • Sent with every HTTP request (slower)
  • Manual parsing needed on client side
  • Vulnerable to CSRF if misconfigured
📦 Local Storage

What is Local Storage?

Local Storage is part of the Web Storage API. It lets you store key-value pairs (as strings) in the browser with no expiration date — the data persists even after the browser is closed and reopened, until it's explicitly cleared.

How Local Storage Works

Data is stored per origin (protocol + domain + port) and is accessible only via JavaScript on the client side. It is never sent to the server automatically, making it lighter on network traffic than cookies.

localStorage.js
// Storing data
localStorage.setItem("username", "John");
localStorage.setItem("preferences", JSON.stringify({ theme: "dark" }));

// Reading data
const user = localStorage.getItem("username");
const prefs = JSON.parse(localStorage.getItem("preferences"));

// Removing a single item
localStorage.removeItem("username");

// Clearing everything
localStorage.clear();

Best Use & Trade-offs

✅ Best for: User preferences, theme settings, cached data, and anything that should persist across browser sessions.
💡 Tip: Since Local Storage only stores strings, always use JSON.stringify() and JSON.parse() when storing objects or arrays.
Pros
  • Large capacity (~5-10MB per origin)
  • Persists indefinitely until cleared
  • Not sent with every request (fast)
  • Simple synchronous API
Cons
  • Accessible via JavaScript, vulnerable to XSS
  • Synchronous — can block the main thread with large data
  • Not shared across origins
  • No built-in expiration mechanism
🗂️ Session Storage

What is Session Storage?

Session Storage works almost identically to Local Storage in terms of API, but the data only persists for the duration of the page session — it's cleared automatically when the browser tab is closed.

How Session Storage Works

Each browser tab gets its own isolated Session Storage instance, even if the tab is loading the same page as another tab. Reloading the page keeps the data, but closing the tab deletes it.

sessionStorage.js
// Storing form progress temporarily
sessionStorage.setItem("formStep", "2");
sessionStorage.setItem("draft", JSON.stringify({ name: "John" }));

// Reading data
const step = sessionStorage.getItem("formStep");

// Removing an item
sessionStorage.removeItem("formStep");

// Data disappears automatically when the tab is closed

Best Use & Trade-offs

✅ Best for: Multi-step form data, temporary UI state, or data that shouldn't outlive a single tab session.
📝 Note: Opening the same URL in a new tab does not share Session Storage — each tab has its own separate store.
Pros
  • Automatically cleared on tab close
  • Isolated per tab (no cross-tab interference)
  • Same easy API as Local Storage
  • Good for sensitive, short-lived data
Cons
  • Data lost when tab is closed
  • Not shared between tabs/windows
  • Still vulnerable to XSS attacks
  • Limited capacity (~5MB)

❓ Frequently Asked Questions
💡 Common Questions
Can Local Storage or Session Storage be sent to a server automatically?
No. Unlike cookies, both are purely client-side. If you need the server to see this data, you must explicitly send it via an AJAX/fetch request.
Are these storage types secure for sensitive data like passwords?
No. None of them are fully secure against XSS attacks since they can be read via JavaScript unless the cookie uses the HttpOnly flag. Sensitive tokens are best kept in HttpOnly, Secure cookies.
What happens to Local Storage data when I close and reopen the browser?
It remains intact. Local Storage persists indefinitely, unless the user clears their browser data or your code removes it explicitly.
If I open two tabs on the same site, do they share Session Storage?
No. Each tab gets an independent Session Storage, even for the exact same URL and origin.
Why would I choose cookies over Local Storage for authentication?
Because cookies can be marked HttpOnly (inaccessible to JavaScript) and are automatically included in requests, making server-side session validation simpler and more secure against XSS.
📋 Quick Reference FAQ

Rapid-Fire Q&A

1

What is Browser Storage?

Browser Storage is used to store data on the client (browser) so it can be reused without making repeated server requests. The main types are Cookies, Local Storage, and Session Storage.

2

What are Cookies?

Cookies are small pieces of data stored by the browser and sent to the server with every HTTP request. They are mainly used for authentication, sessions, and user preferences.

3

What is the maximum size of a cookie?

Around 4 KB per cookie. Browsers also limit the total number of cookies per domain.

4

Are cookies sent to the server automatically?

Yes. Cookies are automatically included in every request to the same domain.

5

Where are cookies commonly used?

User authentication, session management, "Remember Me" functionality, tracking & analytics, and storing user preferences.

6

Can cookies have an expiration date?

Yes. A Session Cookie is deleted when the browser closes, while a Persistent Cookie expires on a specified date.

7

What is Local Storage?

Local Storage stores data permanently in the browser until it is manually removed or cleared by the user.

8

What is the storage limit of Local Storage?

Usually 5MB–10MB depending on the browser.

9

Does Local Storage expire?

No. Data remains until explicitly deleted.

10

Is Local Storage shared across browser tabs?

Yes. All tabs of the same origin can access the same Local Storage.

11

Is Local Storage sent with every HTTP request?

No. It stays only in the browser and is never sent to the server automatically.

12

Common use cases of Local Storage?

Dark/Light theme preference, language preference, shopping cart data, user settings, and offline data caching.

13

What is Session Storage?

Session Storage stores data only for the current browser tab.

14

When is Session Storage cleared?

When the browser tab or window is closed.

15

Is Session Storage shared across tabs?

No. Each tab has its own independent Session Storage.

16

Is Session Storage sent to the server?

No, it stays entirely on the client side.

17

Common use cases of Session Storage?

Multi-step forms, temporary filters, wizard pages, OTP verification flow, and temporary UI state.

19

When would you use Cookies instead of Local Storage?

Use Cookies when the server needs the data on every request, such as authentication tokens or session IDs.
