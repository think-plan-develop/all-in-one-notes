How Hoisting Works — Memory Creation vs Code Execution
Definition

What is Hoisting?

Hoisting is JavaScript's behavior of allocating memory for variables and functions before the code starts executing — during the Memory Creation Phase of the Execution Context.
⚠️ Important: Hoisting doesn't move code physically. JavaScript only processes declarations before execution — the code itself stays exactly where you wrote it.
What Happens During Hoisting?

Memory Creation Phase, Then Code Execution

When JavaScript starts executing a file, it first creates the Global Execution Context.

During the Memory Creation Phase:

  • Memory is allocated for every variable and function
  • Then the Code Execution Phase begins
Memory Allocation — var

var

var-hoisting.js 
console.log(x);
var x = 7;
Output: undefined
Reason: var is hoisted and initialized with undefined.
Memory Allocation — Function Declaration

Function Declaration

function-hoisting.js 
greet();

function greet() {
    console.log("Hello");
}
Output: Hello
Reason: The entire function is hoisted with its implementation — so it can be called before its declaration appears in the code.
let and const

Hoisted, But Not Initialized

let and const are also hoisted, but they are not initialized during the memory creation phase. They're stored in a separate lexical environment — not accessible early like var.

let-hoisting.js 
console.log(a);
let a = 10;
Output: ReferenceError: Cannot access 'a' before initialization
Temporal Dead Zone (TDZ)

What is the TDZ?

The time between memory allocation of a let or const variable and its initialization is called the Temporal Dead Zone (TDZ).
tdz.js 
console.log(a); // TDZ
let a = 10;

After this line runs:

tdz-ends.js 
a = 10;
The TDZ ends the moment execution reaches the variable's declaration line.
Errors Related to Hoisting

ReferenceError

Occurs when accessing a let or const variable before initialization.

reference-error.js 
console.log(a);
let a = 10;
Output: ReferenceError

TypeError

Occurs when performing an invalid operation on an initialized value — like reassigning a const.

type-error.js 
const a = 100;
a = 20;
Output: TypeError: Assignment to constant variable.

SyntaxError

Occurs when declaring the same let or const variable in the same scope.

syntax-error.js 
let a = 10;
let a = 20;
Output: SyntaxError: Identifier 'a' has already been declared

Interview Summary

Key Points to Remember

  • Hoisting happens during the Memory Creation Phase.
  • Memory is allocated for all variables and functions before execution.
  • var is hoisted and initialized with undefined.
  • Function declarations are hoisted with their entire function body.
  • let and const are hoisted but remain uninitialized until execution reaches their declaration.
  • The period before initialization is called the Temporal Dead Zone (TDZ).
  • Accessing let/const inside the TDZ throws a ReferenceError.
  • Reassigning a const throws a TypeError.
  • Redeclaring let/const in the same scope throws a SyntaxError.
💡 Common misconception: "let and const aren't hoisted" is technically wrong — they ARE hoisted, they're just not initialized like var is. That's the distinction interviewers are actually testing for.
Interview Q&A — Hoisting
💡 Interview Q&A
What is hoisting in JavaScript?
Hoisting is a mechanism where variable and function declarations are moved to the top of their scope during the compilation phase. Crucially, it only hoists the declaration, not the assignment. This is why you can reference variables before they are defined in your code.
Are let and const hoisted?
Yes, they are hoisted, but they are not initialized. They exist in a Temporal Dead Zone (TDZ) from the start of the block until the engine processes their declaration. Accessing them before that point results in a ReferenceError.
Why does var return undefined instead of an error?
The JavaScript engine initializes var declarations with undefined during the memory allocation phase. Because it has a value (even if it's "undefined"), the engine considers it defined, whereas let remains strictly uninitialized.
