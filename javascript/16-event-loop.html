Definition
🔁

What is the Event Loop?

The Event Loop is a mechanism that continuously checks the Call Stack, and when the stack becomes empty, it moves tasks from the queues to the Call Stack for execution.

JavaScript is single-threaded, so it can execute only one task at a time. To handle asynchronous operations such as timers, API calls, and DOM events, the browser uses Web APIs and queues, and the Event Loop coordinates their execution.

Components of the Event Loop
📚

Call Stack

The Call Stack is where JavaScript executes functions.

call-stack.js
function one() {
  console.log("One");
}

function two() {
  console.log("Two");
}

one();
two();
The stack must become empty before any queued asynchronous task can run.
🌐

Web APIs

The browser provides Web APIs such as setTimeout(), setInterval(), fetch(), DOM events (click, scroll), localStorage, and location. These APIs run outside the JavaScript engine.

web-api-example.js
setTimeout(() => {
  console.log("Timer finished");
}, 2000);
The timer is handled by the browser, not by the Call Stack.
⏱️

Callback Queue (Macrotask Queue)

When Web API tasks complete, their callbacks are placed in the Callback Queue. Examples: setTimeout, setInterval, DOM event handlers, postMessage.

callback-queue.js
setTimeout(() => console.log("A"), 0);
setTimeout(() => console.log("B"), 0);
Queue order: [ A, B ]

These tasks execute one at a time, per loop cycle.

⚡

Microtask Queue

The Microtask Queue has higher priority than the Callback Queue. It stores Promise.then(), Promise.catch(), Promise.finally(), queueMicrotask(), and MutationObserver.

microtask-queue.js
Promise.resolve().then(() => {
  console.log("Microtask");
});
How the Event Loop Works
📋

The Order of Operations

  1. Execute all synchronous code from the Call Stack.
  2. When async operations complete, place their callbacks into the appropriate queue — Promises → Microtask Queue, Timers/events → Callback Queue.
  3. Check whether the Call Stack is empty.
  4. Execute all microtasks.
  5. Execute one macrotask from the Callback Queue.
  6. Repeat continuously.
QueueExamplesPriority
Microtask QueuePromise.then, catch, finallyHigh
Callback QueuesetTimeout, setInterval, DOM eventsLower
🧭

Walkthrough Example

event-loop-example.js
console.log("Start");

setTimeout(() => {
  console.log("Timeout");
}, 0);

Promise.resolve().then(() => {
  console.log("Promise");
});

console.log("End");
Final Output: Start → End → Promise → Timeout
Why? Promise callbacks are microtasks, setTimeout callbacks are macrotasks, and the Event Loop always executes all microtasks before the next macrotask.
Synchronous vs Asynchronous Execution
➡️

Synchronous Execution

Code runs line by line, and each statement waits for the previous one to finish. Everything runs directly on the Call Stack.

sync.js
console.log("A");
console.log("B");
console.log("C");
// Output: A, B, C
🔀

Asynchronous Execution

JavaScript does not wait for long-running operations — they're handed off to Web APIs.

async.js
console.log("Start");

setTimeout(() => {
  console.log("Async Task");
}, 2000);

console.log("End");
// Output: Start, End, Async Task

Interview Summary
🗣️

The 1-Minute Answer

"Synchronous code executes directly on the Call Stack in order. Asynchronous operations are handled by browser Web APIs, and once completed, their callbacks are placed in the Microtask Queue or Callback Queue. The Event Loop checks the Call Stack, executes all microtasks first, and then executes macrotasks, enabling non-blocking asynchronous behavior in JavaScript."
Interview Q&A
💡 Interview Q&A
Why does Promise.then() execute before setTimeout(fn, 0)?
.then() callbacks go into the Microtask Queue, which the Event Loop always drains completely before it looks at the Macrotask Queue (where setTimeout callbacks live) — even a 0ms delay doesn't change this priority.
What happens if both the Microtask Queue and Macrotask Queue contain pending tasks?
The Event Loop always finishes every microtask first — including any new ones added while draining — before it takes exactly one task from the Macrotask Queue. It then re-checks the Microtask Queue again before touching the next macrotask.
What happens when the Call Stack never becomes empty?
The Event Loop can never push anything from either queue onto the stack, so all pending timers, Promise callbacks, and event handlers stay stuck waiting indefinitely. This is what causes a frozen/unresponsive page — an infinite loop or long synchronous task blocks everything else.
Why is setTimeout(fn, 0) not executed immediately?
It's still placed in the Macrotask Queue, so it must wait for the current synchronous code and the entire Microtask Queue to finish first. Browsers also enforce a small minimum delay in some cases, but the main reason is simply queue priority, not the 0ms value itself.
How does the Event Loop prevent the UI from freezing during asynchronous operations?
Long-running work (network calls, timers) is offloaded to Web APIs running outside the main thread. The main thread only picks up short callback executions when it's free, letting rendering and user input get interleaved between tasks instead of being blocked for the entire duration of the async operation.
Explain the complete lifecycle of an asynchronous operation from function call to callback execution.
The function call triggers a Web API (e.g. a timer or network request). The Web API performs the work outside the Call Stack. Once finished, it places the callback into the Microtask or Macrotask Queue depending on the API. The Event Loop waits until the Call Stack is empty, drains all microtasks, then executes the callback (if it's a macrotask, one per cycle) by pushing it onto the Call Stack.
How does await affect the Event Loop?
await pauses the async function at that point and immediately hands control back to whatever called it, letting synchronous code continue running. The code after await is scheduled to resume as a microtask once the awaited Promise settles — so it runs after current synchronous code, but before any macrotasks.

Nested setTimeout()

predict3.js
console.log("Start");

setTimeout(() => {
    console.log("Timer 1");
    setTimeout(() => console.log("Timer 2"), 0);
}, 0);

console.log("End");
Output: Start → End → Timer 1 → Timer 2

"Timer 2" is only scheduled once "Timer 1" actually runs, so it becomes a brand-new macrotask for the next cycle — it can't run in the same pass.

🔗

Nested Promise Callbacks

predict4.js
console.log("Start");

Promise.resolve().then(() => {
    console.log("A");
    Promise.resolve().then(() => console.log("B"));
});

console.log("End");
Output: Start → End → A → B

Unlike nested timers, a microtask created while draining the Microtask Queue still runs in the same drain — the queue isn't considered empty until nothing new is left in it.

async/await with Promise

predict5.js
async function foo() {
    console.log("1");
    await Promise.resolve();
    console.log("2");
}

console.log("Start");
foo();
console.log("End");
Output: Start → 1 → End → 2

foo() runs synchronously up to the await, then pauses and returns control to the caller. "End" logs before "2" because the code after await is scheduled as a microtask, which only runs once the current synchronous block finishes.

Regardless of which was scheduled first in the code, the microtask (Promise) always wins over the macrotask (setTimeout).

Promise Inside setTimeout()

predict7.js
console.log("Start");

setTimeout(() => {
    console.log("Timeout start");
    Promise.resolve().then(() => console.log("Promise inside timeout"));
    console.log("Timeout end");
}, 0);
Output: Start → Timeout start → Timeout end → Promise inside timeout

The whole timer callback runs as one synchronous block first (macrotask). The Promise it schedules only becomes eligible to run after that block finishes — as the very next microtask, before any further macrotasks.

📤

setTimeout() Inside Promise

predict8.js
console.log("Start");

Promise.resolve().then(() => {
    console.log("Promise");
    setTimeout(() => console.log("Timeout inside promise"), 0);
});

console.log("End");
Output: Start → End → Promise → Timeout inside promise

The Promise callback runs as a microtask before the next macrotask. The setTimeout it schedules is a brand-new macrotask, so it has to wait for the current microtask drain to finish completely.

⏲️

Multiple Timers with Different Delays

predict9.js
console.log("Start");

setTimeout(() => console.log("Timer 500ms"), 500);
setTimeout(() => console.log("Timer 100ms"), 100);
setTimeout(() => console.log("Timer 0ms"), 0);

console.log("End");
Output: Start → End → Timer 0ms → Timer 100ms → Timer 500ms

Timers don't run in the order they were written — they become eligible in order of their delay expiring. The shortest delay always becomes ready first, regardless of the order it appeared in the code.

The Event Loop = Call Stack + Web APIs + Microtask Queue + Callback Queue, coordinated in a continuous cycle · Microtasks (Promises) always fully drain before the next macrotask (timers/events) · A never-empty Call Stack freezes everything · await pauses sync execution and resumes as a microtask.
