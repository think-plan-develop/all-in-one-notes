A. Execution Model — Hoisting, Context, Stack, Closures, Scope
🧠 How JavaScript Actually Runs Your Code

1. What is Hoisting? How does JavaScript hoist variables and functions?

Hoisting is a two-phase behavior baked into how JavaScript prepares code before running it. Before a single line executes, the engine scans the current scope and registers every variable and function declaration in memory — this is the "creation phase." Only after that scan is complete does the engine start executing statements top to bottom in the "execution phase." That's why a function declaration can be called above the line where it's written, while a let variable used above its declaration throws an error instead of silently returning undefined.

The three declaration types behave differently during this scan: var is hoisted and immediately initialized to undefined, so reading it early gives undefined rather than an error. let and const are hoisted too, but they are left "uninitialized" and sit in the Temporal Dead Zone until their actual declaration line runs. Function declarations are hoisted completely — name and body — so they're fully callable from the very top of their scope. Function expressions and arrow functions follow the hoisting rule of whatever keyword (var/let/const) holds them.

hoisting.js
console.log(a);        // undefined (var hoisted, not TDZ)
console.log(sum(2,3)); // 5 (function fully hoisted)
try {
  console.log(b);      // ReferenceError — TDZ
} catch (e) { console.log(e.message); }

var a = 10;
let b = 20;
function sum(x, y) { return x + y; }
Execution flow: Creation phase → memory allocated for a (=undefined), b (=TDZ), sum (=full function). Execution phase → code runs line by line, and each variable's real value is assigned only when its declaration line is reached.

2. What is an Execution Context? Explain the Execution Context lifecycle.

An execution context is the environment JavaScript builds every time it evaluates a chunk of code — it bundles together variable storage, the current value of this, and a link to the outer (lexical) environment. There are three kinds: the Global Execution Context, created once when the script starts; a Function Execution Context, created fresh every time a function is invoked; and an Eval Execution Context for code run via eval().

Every context goes through two lifecycle phases. In the creation phase, the engine sets up the scope, determines this, and hoists variables/functions. In the execution phase, it runs the code line by line, assigning real values and executing statements. When a function returns, its context is destroyed (unless a closure keeps part of it alive).

3. What is the Call Stack? How does it work?

The call stack is the mechanism JavaScript uses to track which function is currently running and what should run next once it finishes — it operates on a strict Last-In-First-Out (LIFO) basis. When the script starts, the Global Execution Context is pushed first. Every time a function is called, a new execution context for that function is pushed on top; when the function returns, its context is popped off, and control returns to whatever is now on top of the stack.

stack.js
function first()  { second(); console.log("first done"); }
function second() { third();  console.log("second done"); }
function third()  { console.log("third done"); }

first();
// Output: third done → second done → first done

Stack trace for the example above:

StepStack (top → bottom)Action
1Globalfirst() called → pushed
2first → Globalsecond() called → pushed
3second → first → Globalthird() called → pushed
4second → first → Globalthird() finishes, logs, popped
5first → Globalsecond() finishes, logs, popped
6Globalfirst() finishes, logs, popped
A chain of calls with no base case (unbounded recursion) keeps pushing without popping, eventually throwing RangeError: Maximum call stack size exceeded.

4. What is a Closure? How does it work internally, and where is it used?

Internally, when a function is created, it doesn't just remember its own code — it keeps a hidden reference to the "Lexical Environment" it was defined in, via an internal property (commonly referred to as [[Environment]]). A closure is what you get when an inner function is returned or passed out of its parent: instead of that parent's variables being garbage collected once the parent returns, they stay alive in memory because the inner function still holds a live link to them. This is why closures can read and even mutate variables from a scope that has technically already "finished executing."

closure-real-world.js
// Real-world use: a bank account module with private balance
function createAccount(initialBalance) {
  let balance = initialBalance; // private — no direct access

  return {
    deposit: amount => balance += amount,
    withdraw: amount => balance -= amount,
    getBalance: () => balance
  };
}

const account = createAccount(1000);
account.deposit(500);
account.getBalance(); // 1500 — balance can't be accessed directly

Beyond data privacy, closures power memoized caches (remembering computed results between calls), event handlers that need setup-time data, currying, and React's useState — the state variable "survives" between renders purely because of a closure over it.

5. What is Scope? Explain Global, Function, Block Scope, and Scope Chain.

Global scope is the outermost layer — anything declared here is visible to every part of the program. Function scope applies to variables declared with var: they're visible anywhere inside the function they were declared in, regardless of nested blocks. Block scope applies to let and const: they're confined strictly to the nearest { }, including if blocks, loops, and standalone braces.

The scope chain is the lookup path the engine follows when it can't find a variable in the current scope — it walks outward, scope by scope, based on where the code is physically nested (lexical scope), until it either finds the variable or reaches the global scope and throws a ReferenceError.

B. Event Loop & Asynchronous JavaScript
🔄 Async Internals — Event Loop, Queues & Promises

6. Explain the Event Loop in JavaScript.

JavaScript itself runs on a single thread with one call stack, so it can only do one thing at a time. Asynchronous behavior — timers, network requests, DOM events — is actually handled outside the JS engine, by Web APIs provided by the browser (or by libuv in Node.js). The event loop is the mechanism that connects these two worlds: it continuously checks whether the call stack is empty, and if it is, it pulls the next task from a queue and pushes it onto the stack to run.

          │   Call Stack   │◄──────────┐

          └───────┬────────┘

        ▼                     ▼
┌───────────────┐   ┌───────────────────┐
│ Microtask Queue│   │ Macrotask Queue   │
│ (Promises,     │   │ (setTimeout,      │
│  queueMicrotask)│   │  setInterval, I/O)│

Crucially, the event loop always fully drains the microtask queue before touching the macrotask queue — this priority rule is the key to predicting async execution order.

8. Explain the execution order of setTimeout(), Promises, and async/await.

The rule that governs everything here: synchronous code runs first, then all microtasks are drained, then one macrotask runs — and this repeats. async/await doesn't introduce new rules; an async function runs synchronously up until its first await, at which point everything after that await is scheduled as a microtask, exactly like a .then() callback.

full-order.js
console.log("A");

setTimeout(() => console.log("B"), 0);

async function demo() {
  console.log("C");
  await null;
  console.log("D"); // scheduled as a microtask
}
demo();

Promise.resolve().then(() => console.log("E"));

console.log("F");

// Output: A → C → F → D → E → B
Trick to remember: everything before the first await is synchronous. Everything after it, and every .then(), joins the microtask queue — which always empties before any setTimeout callback runs.

9. How do Promises work internally? Explain their states and lifecycle.

A Promise is an object representing the eventual result of an asynchronous operation. Internally it holds a state and, once settled, a value or reason. It moves through exactly three states: pending (initial state, operation not yet complete), fulfilled (operation succeeded, holds a resulting value), and rejected (operation failed, holds a reason/error). Once a Promise moves from pending to either fulfilled or rejected, it is permanently "settled" — it can never change state again, which is what makes Promises reliable to chain.

const p1 = Promise.resolve(1);

Promise.all([p1, p2, p3]).catch(e => console.log("all rejects:", e));
Promise.allSettled([p1, p2, p3]).then(r => console.log("allSettled:", r));
Promise.race([p1, p2, p3]).then(r => console.log("race wins:", r));
Promise.any([p2, p3]).then(r => console.log("any wins:", r));

11. How does async/await work behind the scenes?

async/await is syntactic sugar built on top of Promises and generators — it doesn't replace the Promise machinery, it just gives you a way to write asynchronous code that reads like synchronous code. Under the hood, an async function always returns a Promise, and every await pauses the function's execution, registers a continuation as a microtask on the awaited Promise, and hands control back to the caller immediately — the rest of the async function's code effectively becomes the .then() callback of that Promise.

async-desugared.js
// What you write:
async function getUser(id) {
  const res = await fetch(`/users/${id}`);
  const data = await res.json();
  return data;
}

// Roughly what the engine does:
function getUser(id) {
  return fetch(`/users/${id}`)
    .then(res => res.json())
    .then(data => data);
}

12. Explain JavaScript's Single-Threaded Nature. How does it handle asynchronous tasks?

JavaScript's engine executes code on a single thread with a single call stack, meaning only one operation can run at any instant — there's no true parallel execution of JS code within one runtime. What makes it feel asynchronous is that the surrounding environment (browser or Node.js) provides separate systems — Web APIs, timers, and I/O threads — that handle slow work outside the main thread. When that outside work finishes, it doesn't interrupt the running code; instead, it queues a callback that the event loop schedules onto the call stack only once the stack is empty. This design avoids the complexity of multi-threaded programming (locks, race conditions) while still allowing the page to stay responsive during slow operations like network calls.

C. this Keyword, call/apply/bind & Prototypes
🧬 Context Binding & Inheritance

13. What is the this keyword? How is its value determined?

Unlike most variables, this is not determined by where a function is written — it's determined by how the function is called (its "call site"), except for arrow functions, which ignore call-site rules entirely and inherit this lexically from their surrounding scope.

Plain function callundefined (strict mode) or global objectgreet()
Method callThe object before the dotuser.greet() → this = user
Constructor call (new)The newly created objectnew User()
call/apply/bindWhatever object is explicitly passedgreet.call(obj)
Arrow functionInherited from enclosing lexical scope() => this
Event handler (DOM)The element the listener is attached tobutton.onclick
this-examples.js
const user = {
  name: "Riya",
  greetNormal: function() { console.log(this.name); },
  greetArrow: () => { console.log(this.name); }
};

user.greetNormal(); // "Riya" — this = user
user.greetArrow();  // undefined — this = outer (module/global) scope

14. Explain call(), apply(), and bind() with practical examples.

All three let you explicitly control what this refers to inside a function, but they differ in how arguments are passed and when the function actually executes.

MethodArguments formatExecutes
call()Comma-separated listImmediately
apply()Single arrayImmediately
bind()Comma-separated listReturns a new function — runs later
call-apply-bind.js
function introduce(city, country) {
  console.log(`${this.name} from ${city}, ${country}`);
}
const person = { name: "Dev" };

introduce.call(person, "Pune", "India");
introduce.apply(person, ["Pune", "India"]);

const boundIntroduce = introduce.bind(person, "Pune", "India");
boundIntroduce(); // runs later, this already locked to 'person'
bind() is most useful when passing a method as a callback (e.g. to setTimeout or an event listener) where you need to guarantee this doesn't get lost.

15. What is the Prototype Chain? How does JavaScript implement inheritance?

Every JavaScript object has an internal link to another object called its prototype. When you access a property that doesn't exist directly on an object, the engine doesn't give up — it follows this internal link and checks the prototype, then that prototype's prototype, and so on, until it either finds the property or reaches null, the end of the chain. This chain is exactly how inheritance works in JavaScript: methods aren't copied onto every object, they're defined once on a shared prototype and reached through this lookup.

diagram
const arr = [1,2,3];

arr  ──►  Array.prototype  ──►  Object.prototype  ──►  null
(own:      (map, filter,        (toString,
 length,    push, ...)           hasOwnProperty...)

arr.map(...)  → not on arr → found on Array.prototype ✓
inheritance.js
function Animal(name) { this.name = name; }
Animal.prototype.speak = function() {
  console.log(`${this.name} makes a sound`);
};

function Dog(name) { Animal.call(this, name); }
Dog.prototype = Object.create(Animal.prototype); // link prototypes

const rex = new Dog("Rex");
rex.speak(); // "Rex makes a sound" — found via prototype chain

16. What is the difference between prototype and __proto__?

prototype is a property that exists only on functions (specifically, functions meant to be used as constructors) — it's the object that will become the prototype of every instance created with new. __proto__, on the other hand, exists on every object instance and is the actual live reference to that object's prototype — it's the internal link the engine walks when doing a lookup. In short: prototype is the blueprint a constructor hands out, while __proto__ is the link an individual object uses to find that blueprint.

proto-vs-dunder.js
function User(name) { this.name = name; }
const u = new User("Sam");

console.log(User.prototype);        // the blueprint object
console.log(u.__proto__);           // same object as User.prototype
console.log(u.__proto__ === User.prototype); // true
Modern code should use Object.getPrototypeOf(obj) instead of __proto__ directly — __proto__ is a legacy accessor kept mainly for backward compatibility.
D. Memory Management
💾 How JavaScript Stores & Cleans Up Data

17. Explain Primitive vs Reference Types. How does JavaScript store them in memory?

Primitive values (string, number, boolean, null, undefined, symbol, bigint) are stored directly in the variable's own memory slot on the stack, so copying a primitive copies the actual value — the two variables become fully independent. Reference types (objects, arrays, functions) are stored in the heap, and the variable only holds a pointer/address to that heap location. Copying a reference variable copies the address, not the data — so both variables end up pointing at, and able to mutate, the same underlying object.

primitive-vs-reference.js
let a = 10;
let b = a;
b = 20;
console.log(a); // 10 — untouched, separate copy

let obj1 = { value: 10 };
let obj2 = obj1;
obj2.value = 20;
console.log(obj1.value); // 20 — same object in memory

18. Explain Stack Memory and Heap Memory.

The stack is a small, fast, tightly organized region of memory used for static, predictable data — primitive values and the pointers/references to objects. It follows a strict LIFO structure and each function call gets its own frame, cleaned up automatically the moment the function returns. The heap is a much larger, less structured region used for dynamically sized data like objects, arrays, and functions, which don't have a fixed, predictable size known in advance. Heap memory isn't freed automatically when a function returns — it stays until nothing references it anymore, at which point the garbage collector reclaims it.

19. What is Garbage Collection? How does JavaScript manage memory?

Garbage collection is the automatic process by which the JavaScript engine identifies memory that's no longer reachable from any live part of the program and reclaims it, so developers don't have to manually free memory like in C or C++. Modern engines like V8 primarily use a strategy called mark-and-sweep: the engine starts from a set of "roots" (global objects, currently executing functions), marks every object reachable from those roots as "in use," and then sweeps away everything left unmarked, since nothing in the program can reach it anymore.

Real-world example: a common memory leak happens when a DOM element is removed from the page, but a JavaScript variable (often inside a closure or an event listener) still holds a reference to it — the element stays reachable, so garbage collection can never reclaim it, and it silently accumulates in memory until the tab crashes or slows down.

Common leak sources: forgotten setInterval/event listeners, global variables that grow unbounded, and closures unintentionally holding onto large objects.

20. Explain Deep Copy vs Shallow Copy.

A shallow copy duplicates only the first level of an object — if any property value is itself an object or array, the copy still points to the same nested reference as the original, so mutating a nested field affects both. A deep copy recursively duplicates every nested level, producing a completely independent structure with no shared references anywhere.

deep-vs-shallow.js
const original = { name: "Kim", address: { city: "Seoul" } };

// Shallow copy — nested object still shared
const shallow = { ...original };
shallow.address.city = "Busan";
console.log(original.address.city); // "Busan" — original changed too!

// Deep copy — fully independent
const deep = structuredClone(original);
deep.address.city = "Tokyo";
console.log(original.address.city); // "Busan" — untouched this time
Use structuredClone() (native, modern) for true deep copies. JSON.parse(JSON.stringify()) also works but silently drops functions, undefined, and Date/Map/Set objects.
E. Performance Patterns
⚡ Debouncing, Throttling, Currying & Polyfills

21. Explain Debouncing and Throttling with real-world examples.

Debouncing delays execution until a burst of events has completely stopped for a set period — every new event resets the timer. It's ideal for a search-box autocomplete, where you only want to fire the API call once the user has actually paused typing, not on every keystroke. Throttling instead guarantees a function runs at most once every fixed interval, no matter how many events fire in between — ideal for a scroll or resize handler, where you want regular updates but not hundreds per second.

diagram
Events:      X  X X  X       X
Debounce:    ................|──► fires once, after the gap
Throttle:    |──► |──► |──►  |──► fires at fixed intervals
debounce-throttle.js
function debounce(fn, delay) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };
}

function throttle(fn, limit) {
  let waiting = false;
  return (...args) => {
    if (!waiting) {
      fn(...args);
      waiting = true;
      setTimeout(() => waiting = false, limit);
    }
  };
}

searchInput.oninput = debounce(fetchSuggestions, 400);
window.onscroll     = throttle(updateScrollProgress, 200);

22. What is Currying? How is it useful?

Currying transforms a function that expects multiple arguments into a chain of functions that each accept one argument at a time, only computing the final result once every argument has been supplied. It relies on closures — each returned function "remembers" the arguments collected so far. It's useful for building specialized, pre-configured versions of a general function without rewriting logic.

currying.js
const discount = rate => price => price - price * rate;

const tenPercentOff = discount(0.10); // specialized, reusable
tenPercentOff(500); // 450
tenPercentOff(200); // 180

23. What are Polyfills? How would you implement your own map(), filter(), or bind()?

A polyfill is custom code that reproduces a modern JavaScript feature's behavior in environments where that feature doesn't natively exist — typically older browsers. Writing your own polyfill for built-in methods is a common interview exercise because it tests whether you understand what the method does internally, not just how to call it.

polyfills.js
// Custom Array.prototype.map
Array.prototype.myMap = function(callback) {
  const result = [];
  for (let i = 0; i < this.length; i++) {
    result.push(callback(this[i], i, this));
  }
  return result;
};

// Custom Function.prototype.bind
Function.prototype.myBind = function(context, ...boundArgs) {
  const fn = this;
  return function(...callArgs) {
    return fn.apply(context, [...boundArgs, ...callArgs]);
  };
};
F. DOM Events & Browser Storage
🌐 Event Delegation & Client-Side Storage

24. What is Event Delegation? Why is it better than attaching multiple event listeners?

Event delegation relies on event bubbling — when an event fires on an element, it doesn't stay there, it travels up through every ancestor element in turn. Instead of attaching a separate listener to every individual child element, you attach a single listener to a shared parent and inspect event.target to determine which specific child triggered it. This is more memory-efficient (one listener instead of hundreds), and it automatically covers elements added to the DOM later, since the listener lives on the parent, not the children themselves.

</ul>                                       │

delegation.js
document.getElementById("list").addEventListener("click", (e) => {
  if (e.target.tagName === "LI") {
    console.log("Clicked:", e.target.textContent);
  }
});
// Works even for <li> items added to the list after this code runs
