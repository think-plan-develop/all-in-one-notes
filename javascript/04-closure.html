JavaScript Closures

How functions remember the scope they were born in — what closures are, where they show up in real code, and the traps that catch even experienced developers.

A closure is a function bundled together with references to its surrounding scope. That bundle lets the function keep using variables from where it was created, even after that outer scope has technically finished running.
1. What is Closure
A Function That Remembers Its Birthplace Fundamentals

A closure is a feature in JavaScript where an inner function remembers and can access the variables of its outer function even after the outer function has finished executing.

In simple words: A closure allows a function to "remember" the variables from the place where it was created.

Real-Life Example: The Locker

Locker ConceptClosure Equivalent
The locker itselfCreated by the outer function
Items inside the lockerVariables in the outer function's scope
The keyHeld by the inner function
Key still opens it after the person leavesInner function still accesses the variables after the outer function finishes
Even after the person who created the locker leaves, the key still opens it. That's exactly how closures work.
closure-basics.js
function outer() {
  let message = "Hello";

  function inner() {
    console.log(message); // reads from outer's scope
  }

  return inner;
}

const greet = outer(); // outer() has already finished running
greet();               // "Hello" — message is still alive!
StepWhat Happens
1outer() runs and creates message in its scope
2inner() is created, closing over message
3outer() returns inner; its own stack frame pops off
4greet() still reaches message via its closure — not garbage collected

Note

A closure isn't a snapshot or a copy — it's a live reference. If the outer variable changes later, the closure sees the updated value, not the old one.

Q: Do you need to explicitly "create" a closure?

No — every function is technically a closure over its surrounding scope. The term just becomes relevant once a function outlives the scope it was created in and still uses variables from it.
2. Practical Uses
Where Closures Show Up in Real Code Patterns

Closures aren't just an interview topic — they're the mechanism behind several everyday JavaScript patterns.

PatternWhat Closures Enable
Counters & AccumulatorsIncrement a value across multiple calls without exposing it globally
Function FactoriesGenerate pre-configured functions, like multiplyBy(5)
Memoization / CachingStore expensive computed results in a closed-over cache object
Event HandlersA callback that still needs access to state from when it was registered
Debounce & ThrottlePersist a timer ID across repeated calls

Function Factory Example

function-factory.js
function multiplyBy(factor) {
  return function(n) {
    return n * factor; // closes over "factor"
  };
}

const double = multiplyBy(2);
const triple = multiplyBy(3);

double(10); // 20
triple(10); // 30 — each closure remembers its OWN factor

Debounce Example

debounce.js
function debounce(fn, delay) {
  let timerId; // persists across calls via closure

  return function(...args) {
    clearTimeout(timerId);
    timerId = setTimeout(() => fn(...args), delay);
  };
}

const onResize = debounce(() => console.log("resized!"), 300);
window.addEventListener("resize", onResize);

Tip

Any time you see a function returning another function, or a callback that "remembers" something from where it was set up, a closure is doing the work behind the scenes.
3. Data Privacy
Simulating Private Variables Encapsulation

Before JavaScript had native private class fields (#field), closures were — and still are — the standard way to hide internal state that can only be touched through an exposed API.

The Module Pattern

bank-account.js
function createBankAccount(initialBalance) {
  let balance = initialBalance; // truly private — no outside access

  return {
    deposit(amount) {
      balance += amount;
      return balance;
    },
    withdraw(amount) {
      if (amount > balance) throw new Error("Insufficient funds");
      balance -= amount;
      return balance;
    },
    getBalance() {
      return balance;
    }
  };
}

const account = createBankAccount(100);
account.deposit(50);
account.getBalance(); // 150
console.log(account.balance); // undefined — no direct access at all
🔹 Closures for Privacy
  • Works in any JS engine, even very old ones
  • Truly inaccessible — not even via bracket notation
  • Each factory call creates independent private state
🔸 Native #private Fields
  • Modern syntax, built into classes (ES2022+)
  • Slightly better performance in most engines
  • Reads more conventionally for class-based devs

Remember

Both approaches achieve real encapsulation. Closures remain useful outside of classes — for factory functions, modules, and anywhere you don't want a full class.

Yes.

4. Does every inner function create a closure?

Not always. A closure is useful when the inner function captures variables from its outer scope. If it doesn't reference any outer variables, there's nothing meaningful to preserve.

5. Why don't outer variables get destroyed?

Because the returned inner function still has a reference to them. JavaScript's garbage collector keeps those variables alive until no closures reference them anymore.

Interview Definition (Best Answer)

A closure is a JavaScript feature in which an inner function retains access to the variables of its outer lexical scope even after the outer function has completed execution. It is commonly used for data encapsulation, private variables, state management, callbacks, and function factories.

Follow-Up Questions to Expect

1. Why do we need closures?

Closures let a function hold on to state between calls without using global variables. They're the foundation for private data, factory functions, and callbacks that need to "remember" something from setup time.

2. Explain lexical scope.

Lexical scope means a function's access to variables is decided by where it's physically written in the code, not by how or where it's called. A function can always see the variables of the scope it was nested in when written.

3. Difference between closure and scope.

Scope is the set of rules that determines where a variable is visible. A closure is what happens when a function is carried outside its original scope but keeps a live link back to it. Scope is the concept; a closure is the mechanism that preserves it over time.

4. How do closures work internally?

Every function stores a hidden link to the "scope environment" it was created in. As long as something still references the inner function, that environment can't be deleted — even after the outer function returns — so the engine keeps it alive on the heap instead of the stack.
closure-internals.js
function outer() {
  let count = 0; // lives inside outer's environment

  function inner() {
    count++;
    console.log(count);
  }

  return inner; // inner carries a hidden [[Environment]] link back to outer's scope
}

const fn = outer(); // outer() finishes — its stack frame pops off
fn(); // 1
fn(); // 2
StepWhat the engine does internally
1. outer() is calledA new execution context is created with its own variable environment holding count
2. inner is definedinner gets an internal [[Environment]] reference pointing at outer's variable environment — not a copy of count, the environment itself
3. outer() returnsIts call-stack frame is popped, but the variable environment is NOT deleted because inner still references it
4. fn() runs laterIt looks up count through its [[Environment]] link, finds it on the heap, and updates it in place
5. No references remainOnly once every closure pointing to that environment is gone does the garbage collector reclaim it
This is why calling outer() twice gives two independent counters — each call creates a brand-new variable environment, and each returned inner closes over its own separate one, not a shared global copy.

5. Can closures cause memory leaks?

Yes. A closure keeps its entire outer scope alive, not just the variables it uses. If a long-lived closure (like an event listener) shares scope with a large unused object, that object can't be garbage collected — leading to a memory leak if not cleaned up.
5. Interview Examples
Classic Closure Questions Interview Prep

These show up constantly in technical interviews because they test whether you understand scope lifetime, not just closure syntax.

1. The Counter Factory

counter.js
function createCounter() {
  let count = 0;
  return {
    increment: () => ++count,
    reset: () => (count = 0)
  };
}

const counterA = createCounter();
const counterB = createCounter();

counterA.increment(); counterA.increment();
counterB.increment();

console.log(counterA.increment()); // 3
console.log(counterB.increment()); // 2 — independent closures

Q: Why don't counterA and counterB share state?

Each call to createCounter() creates a brand-new execution context, so each returned object closes over its own separate count variable.

2. Fix the Loop Bug

loop-fix.js
for (var i = 1; i <= 3; i++) {
  setTimeout(() => console.log(i), 100);
}
// 4, 4, 4 — all three closures share the same "i"

// Fix 1: use let, which creates a new binding per iteration
for (let j = 1; j <= 3; j++) {
  setTimeout(() => console.log(j), 100);
}
// 1, 2, 3

// Fix 2 (pre-ES6 trick): wrap in an IIFE to capture the value
for (var k = 1; k <= 3; k++) {
  (function(captured) {
    setTimeout(() => console.log(captured), 100);
  })(k);
}
// 1, 2, 3
This is the single most-asked closure question in interviews — it tests whether you understand that var is function-scoped, so all iterations share one variable unless you deliberately create a new scope per iteration.

3. Once — A Function That Runs Only One Time

once.js
function once(fn) {
  let called = false;
  let result;

  return function(...args) {
    if (!called) {
      result = fn(...args);
      called = true;
    }
    return result;
  };
}

const initialize = once(() => console.log("Initializing..."));
initialize(); // "Initializing..."
initialize(); // (nothing — already ran)

7. Common Pitfalls
Where Closures Bite Back Gotchas

Closures are powerful, but misusing them causes some of the sneakiest bugs and performance issues in JavaScript.

❌ Common Mistakes
  • Using var in loops that create closures (stale shared variable)
  • Holding references to large objects/DOM nodes in long-lived closures
  • Assuming a closure captures a value — it captures the variable itself
  • Creating closures inside hot loops or render functions unnecessarily
✅ Good Habits
  • Prefer let/const so each scope is naturally isolated
  • Null out references you no longer need in long-lived closures
  • Keep closures small and intentional, not sprawling
  • Remove event listeners/timers that hold closures when no longer needed

Memory Leaks from Long-Lived Closures

memory-leak.js
function attachHandler() {
  const hugeData = new Array(1000000).fill("data");

  document.getElementById("btn").addEventListener("click", () => {
    console.log("clicked"); // doesn't even use hugeData...
  }); // ...but hugeData still can't be garbage collected —
     // it's in the same closure scope as the listener
}
A closure keeps its entire surrounding scope alive, not just the variables it explicitly uses. If an unused large object shares scope with a long-lived callback, it stays in memory too — split it into a narrower inner scope if this matters.

Capturing the Variable, Not the Value

capture-mistake.js
function buildFunctions() {
  const fns = [];
  let name = "initial";

  fns.push(() => console.log(name));
  name = "changed"; // mutating AFTER the closure was created

  return fns;
}

const [logName] = buildFunctions();
logName(); // "changed" — not "initial"!
The closure holds a live reference to the variable binding, not a frozen snapshot of its value at creation time. This is exactly why the loop-closure bug happens with var.

Q: Are closures inherently bad for performance?

No — modern engines optimize closures well. The real risk is unintentionally retaining large amounts of memory for the lifetime of a long-lived closure, not closures themselves being "slow."
