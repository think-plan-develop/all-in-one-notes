What is a Promise?

Definition, States & The Executor

A Promise is an object representing the eventual result of an asynchronous operation.

It exists in one of three states:

StateMeaning
PendingInitial state, operation not finished yet
FulfilledOperation completed successfully, has a value
RejectedOperation failed, has a reason (error)

A Promise moves from pending to either fulfilled or rejected exactly once — it can never change state again. You attach handlers with .then() for success and .catch() for failure.

fetch-user.js
function fetchUser(userId) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (!userId) {
        reject(new Error("User ID is required"));
      } else {
        resolve({
          id: userId,
          name: "Shivam",
          email: "shivam@example.com"
        });
      }
    }, 1000);
  });
}

fetchUser(101)                    // Promise<User>
  .then(user => {
    console.log("User:", user);
    return user.email;         // Promise<string>
  })
  .then(email => console.log("Email:", email))
  .catch(err => console.error("Error:", err.message));

// Output:
// User: { id: 101, name: 'Shivam', email: 'shivam@example.com' }
// Email: shivam@example.com

Chaining .then(user => user.email) after fetchUser(101) reads clearly once you track what each step returns — the second .then() never sees the full user object, only the string it was handed.

The executor always receives resolve first, reject second

Every Promise executor is called with two callbacks, in this fixed order — resolve() for success, reject() for failure. Whichever one runs first settles the Promise; a Promise can only be settled once, so calling the other one afterward is silently ignored.

resolve-reject.js
const p = new Promise((resolve, reject) => {
  resolve("Success");
  reject("Error"); // ignored — promise is already settled
});

p.then(console.log);

// Output:
// Success
✅ Benefit: Promises are chainable, composable, and let you handle every error in one place with a single .catch(), instead of checking err at every nested level.
Promise.resolve() & Promise.reject()

Creating Already-Settled Promises

Sometimes you don't need an executor at all — you already have the value or the error, and just need it wrapped as a Promise so it fits into a chain.

resolve-reject-static.js
Promise.resolve(42).then(console.log);
// Output: 42

Promise.reject(new Error("Failed"))
  .catch(err => console.log(err.message));
// Output: Failed
  • Promise.resolve(value) → creates an already fulfilled Promise.
  • Promise.reject(error) → creates an already rejected Promise.
💡 Common use: Normalizing a function that might return either a plain value or a Promise, so callers can always safely chain .then() onto the result.
Promise Chaining Rules

Flattening Nested Async Steps

Because .then() always returns a new Promise, you can chain multiple asynchronous steps in a flat, readable sequence instead of nesting them. If you return a value from .then(), it gets wrapped in a resolved Promise; if you return another Promise, the chain waits for it to settle before moving to the next .then().

chaining.js
getUser(1)
  .then(user => getPosts(user.id))
  .then(posts => getComments(posts[0].id))
  .then(comments => getLikes(comments[0].id))
  .then(likes => console.log("Likes:", likes))
  .catch(err => console.error("Something failed:", err.message));
  // one catch handles an error from ANY step above

Always return the Promise

Skipping the return keyword is the single most common chaining mistake. Without it, the next .then() doesn't wait — it fires immediately, with undefined.

❌ Not returned
missing-return.js
fetchUser()
  .then(user => {
    fetchOrders(user.id); // no return
  })
  .then(orders => {
    console.log(orders);
  });

// Output:
// undefined
✅ Returned
with-return.js
fetchUser()
  .then(user => {
    return fetchOrders(user.id); // returned
  })
  .then(orders => {
    console.log(orders.length);
  });

// Output:
// 3

Why undefined specifically?

  • The first .then() callback returns nothing.
  • Functions without a return statement return undefined by default.
  • The next .then() receives that undefined immediately.
  • The chain does not wait for fetchOrders() to finish — it has already moved on.
fetchUser() ↓ .then() ── return fetchOrders() ↓ .then() waits here ↓ orders received

Avoid Promise Hell

Nesting .then() calls inside each other — instead of returning and chaining — recreates the same "Pyramid of Doom" problem callbacks had. This is sometimes called Promise Hell.

❌ Promise Hell
promise-hell.js
login()
  .then(user => {
    return getProfile(user.id)
      .then(profile => {
        return getPosts(profile.id)
          .then(posts => {
            return getComments(posts[0].id)
              .then(comments => {
                console.log(comments);
              });
          });
      });
  });
// 4 levels deep, indentation drifting right each time
✅ Proper Chaining
proper-chaining.js
login()
  .then(user => getProfile(user.id))
  .then(profile => getPosts(profile.id))
  .then(posts => getComments(posts[0].id))
  .then(comments => console.log(comments))
  .catch(console.error);
// same 4 async steps, completely flat
💡 Why the flat version wins: flat structure, better readability, easier error handling with one .catch(), and easier debugging — every one of these degrades as nesting gets deeper.
How .catch() Behaves Mid-Chain

A .catch() Doesn't Have to End the Chain

Many beginners assume a chain stops once .catch() runs. It doesn't — .catch() handles the rejection and then, by default, returns a resolved Promise, so anything chained after it still runs.

A .then() written after a .catch() still executes

then-after-catch.js
Promise.reject("Error")
  .catch((err) => {
    console.log("Caught:", err);
  })
  .then(() => {
    console.log("This will still run");
  });

// Output:
// Caught: Error
// This will still run

Recovering with a fallback value

Because .catch() can return a value (or another Promise), it's a natural place to supply a fallback and let the rest of the chain continue with real, usable data.

catch-recovery.js
fetchData()
  .catch((err) => {
    console.log("Error handled");
    return []; // recover with default value
  })
  .then((data) => {
    console.log("Continue chain:", data);
  });

// Output:
// Error handled
// Continue chain: []
✅ Use cases: providing fallback data, retrying an operation, or letting the rest of the application flow continue even after a step fails — instead of the whole chain dying at the first error.
Promise.finally()

Cleanup That Runs No Matter What

.finally() runs after the Promise settles — whether it was fulfilled or rejected — and doesn't receive any value from the chain, since its job is cleanup, not data handling.

finally.js
fetchUser(1)
  .then(user => console.log(user))
  .catch(err => console.error(err))
  .finally(() => {
    console.log("Hide loader");
  });

// Output:
// { id: 1, name: 'Shivam' }
// Hide loader

Common use cases:

  • Hiding a loading spinner regardless of success/failure
  • Closing a database connection
  • Cleaning up temporary resources
  • Stopping a timer or progress indicator
📌 Note: .finally() passes the original settled value or error straight through, unchanged — so you can still chain further .then()/.catch() after it if needed.
Promise Types — all() / allSettled() / race() / any()
1

⚡ Promise.all()

Promise.all() takes an array (or iterable) of Promises and runs them concurrently. It resolves with an array of all results, in the same order, once every Promise has fulfilled. If any single one rejects, Promise.all() immediately rejects with that error — the other results are discarded, even if they would have succeeded.

promise-all.js
const userP = getUser(1);
const postsP = getPosts(1);
const settingsP = getSettings(1);

Promise.all([userP, postsP, settingsP])
  .then(([user, posts, settings]) => {
    console.log(user.name);
    console.log(posts.length);
    console.log(settings.theme);
    // all 3 finished, total time = slowest one, not the sum
  })
  .catch(err => {
    console.error("One of them failed:", err.message);
  });

// Output:
// Shivam
// 12
// dark
📌 Note: Use Promise.all() when you need all results and can't proceed if even one fails (e.g. loading required data before rendering a page).
2

📋 Promise.allSettled()

Promise.allSettled() also runs Promises concurrently, but unlike Promise.all(), it never short-circuits. It waits for every Promise to settle (fulfilled or rejected) and returns an array of status objects, each shaped as { status, value } or { status, reason }.

promise-allsettled.js
const uploads = [uploadFile("a.png"), uploadFile("b.png"), uploadFile("broken.png")];

Promise.allSettled(uploads).then(results => {
  results.forEach((result, i) => {
    if (result.status === "fulfilled") {
      console.log(`File ${i} uploaded:`, result.value);
    } else {
      console.log(`File ${i} failed:`, result.reason.message);
    }
  });
});
💡 Tip: Use allSettled() when partial success is acceptable — e.g. bulk uploads, sending analytics, notifying multiple services — and you want a full report instead of one failure killing everything.
3

🏁 Promise.race()

Promise.race() settles as soon as the first Promise in the array settles — whether it fulfills or rejects. The rest keep running in the background, but their outcomes are ignored by the race itself.

promise-race.js
function timeout(ms) {
  return new Promise((_, reject) =>
    setTimeout(() => reject(new Error("Request timed out")), ms)
  );
}

Promise.race([fetchData(), timeout(5000)])
  .then(data => console.log("Got data:", data))
  .catch(err => console.error(err.message));
  // whichever settles first (data or timeout) wins the race
📌 Note: This "race against a timeout" is the single most common real-world use of Promise.race().
4

🎯 Promise.any()

Promise.any() resolves as soon as the first Promise fulfills — rejections along the way are ignored. It only rejects if all the Promises reject, in which case it throws an AggregateError containing every individual error.

promise-any.js
Promise.any([
  fetch("https://mirror1.example.com/data"),
  fetch("https://mirror2.example.com/data"),
  fetch("https://mirror3.example.com/data")
])
  .then(response => console.log("First success from:", response.url))
  .catch(aggregateError => {
    console.error("All mirrors failed:");
    aggregateError.errors.forEach(e => console.error(" -", e.message));
  });

When every Promise rejects

promise-any-all-fail.js
Promise.any([
  Promise.reject(new Error("Server 1 down")),
  Promise.reject(new Error("Server 2 down")),
  Promise.reject(new Error("Server 3 down"))
]).catch(err => {
  console.log(err.constructor.name);
  console.log(err.errors.map(e => e.message));
});

// Output:
// AggregateError
// [ 'Server 1 down', 'Server 2 down', 'Server 3 down' ]
🧭 any() vs race(): race() settles on whichever finishes first, success or failure. any() specifically waits for the first success, and ignores failures unless everything fails.

🔬 Output Prediction — Microtask Queue

Promises Jump the Timer Queue

This is one of the most frequently asked JavaScript interview questions — predict the output order.

microtask-order.js
console.log("Start");

Promise.resolve().then(() => console.log("Promise"));

setTimeout(() => console.log("Timeout"), 0);

console.log("End");

// Output:
// Start
// End
// Promise
// Timeout
.then() callbacks are queued on the microtask queue, which the JS engine always drains completely before it looks at the macrotask (timer) queue — even a setTimeout(..., 0) waits behind every pending Promise callback.
Call stack runs synchronous code first "Start" → "End" │ ▼ Microtask queue drained completely "Promise" │ ▼ Macrotask (timer) queue runs next "Timeout"
Promise Chains vs async/await

Same Behavior, Different Syntax

async/await is syntax sugar over Promises — the underlying behavior is still entirely Promise-based; it just reads like synchronous code.

promise-chain.js
// Promise chain
getUser(1)
  .then(user => getPosts(user.id))
  .then(posts => console.log(posts))
  .catch(console.error);
async-await.js
// async/await equivalent
async function load() {
  try {
    const user = await getUser(1);
    const posts = await getPosts(user.id);
    console.log(posts);
  } catch (err) {
    console.error(err);
  }
}
📌 Note: try/catch replaces .catch(), and each await pauses the function until that Promise settles — but it's still Promises underneath, so everything about states, chaining, and the microtask queue above still applies.

Interview Questions
💡 Promise Basics
What is a Promise?
A Promise is an object that represents a value which isn't available yet but will be at some point — either successfully (fulfilled) or with a failure (rejected). It provides .then(), .catch(), and .finally() to attach handlers for those outcomes.
What are the three states of a Promise?
Pending (initial, not yet settled), Fulfilled (operation succeeded, has a value), and Rejected (operation failed, has a reason). A Promise can only transition from pending to one of the other two, and only once — it's immutable after that.
How do you convert callback-based code into Promise-based code?
Wrap the callback-based call inside a new Promise((resolve, reject) => {...}), and call resolve() on success or reject() on error inside the original callback — this is often called "promisifying."
promisify.js
function readFilePromise(path) {
  return new Promise((resolve, reject) => {
    fs.readFile(path, "utf8", (err, data) => {
      if (err) reject(err);
      else resolve(data);
    });
  });
}
Does a .catch() always end the Promise chain?
No. .catch() handles the rejection and returns a resolved Promise by default, so any .then() written after it still runs. It can also recover by returning a fallback value, letting the rest of the chain continue with usable data instead of failing outright.
💡 Promise Methods
What is Promise.all()? When should you use it?
It runs Promises concurrently and resolves with an array of all their values once every one fulfills; it rejects immediately if any one rejects. Use it when you need every result and can't proceed with only partial data — e.g. loading all the data required to render a page.
What is Promise.allSettled()? When should you use it?
It runs Promises concurrently and always waits for all of them to settle, returning a status object for each (fulfilled/value or rejected/reason) — it never short-circuits. Use it when partial failure is acceptable and you want a full report, e.g. bulk uploads or notifying several independent services.
What is Promise.race()? When should you use it?
It settles as soon as the first Promise settles, whether that's a fulfillment or a rejection. Use it for "whichever finishes first wins" scenarios, most commonly implementing timeouts by racing a real request against a rejecting timer.
What is Promise.any()? When should you use it?
It resolves as soon as the first Promise fulfills, ignoring rejections along the way; it only rejects (with an AggregateError) if every Promise rejects. Use it when you have multiple redundant sources and just need one success, e.g. trying several CDN mirrors.

💡 Scenario-Based
Data from Users, Products, and Orders APIs needed before rendering
Promise.all() — the page can't render meaningfully without all three, so it makes sense to fail fast if any one of them fails, rather than rendering an incomplete page.
Five independent API calls — execute simultaneously to reduce response time
Fire all five calls first without awaiting each one individually, put the resulting Promises in an array, and await them together with Promise.all() — total time becomes the slowest call instead of the sum of all five.
One API failure should stop the entire process
Promise.all() — it rejects as soon as any single Promise rejects, which naturally stops the whole process.
Display whatever data is available even if some APIs fail
Promise.allSettled() — it never short-circuits, so you can render the successful results and show a fallback/error state for the failed ones.
Need the fastest response from multiple mirror servers
Promise.race() — it settles with whichever mirror responds first, success or failure.
Need the first successful response from multiple backup servers
Promise.any() — it ignores individual failures and resolves as soon as the first server succeeds, only rejecting if all of them fail.
