A. Execution Model — Hoisting, Context, Stack, Closures, Scope
1

What is Hoisting? How does JavaScript hoist variables and functions?

Hoisting is the engine's two-phase startup: a creation phase registers every declaration in memory before anything runs, then the execution phase runs code top to bottom, assigning real values as each line executes.

var is hoisted and immediately initialized to undefined. let/const are hoisted too, but sit uninitialized in the Temporal Dead Zone until their declaration line runs. Function declarations are hoisted completely — name and body — so they're fully callable from the top of their scope. Function expressions and arrow functions follow the hoisting rule of whatever keyword holds them.

hoisting.js
console.log(a);        // undefined (var hoisted, not TDZ)
console.log(sum(2,3)); // 5 (function fully hoisted)
try {
  console.log(b);      // ReferenceError — TDZ
} catch (e) { console.log(e.message); }

var a = 10;
let b = 20;
function sum(x, y) { return x + y; }
📌 Creation phase → memory allocated for a (=undefined), b (=TDZ), sum (=full function). Execution phase → each variable's real value is assigned only when its declaration line is reached.
2

What is an Execution Context? Explain the Execution Context lifecycle.

An execution context is the environment JS builds every time it evaluates code — bundling variable storage, this, and a link to the outer scope. It goes through a creation phase then an execution phase.

There are three kinds: the Global Execution Context, created once when the script starts; a Function Execution Context, created fresh every time a function is invoked; and an Eval Execution Context for code run via eval(). When a function returns, its context is destroyed unless a closure keeps part of it alive.

Execution Context Lifecycle ┌─────────────────────────────┐ │ 1. CREATION PHASE │ │ • Create scope │ │ • Determine 'this' │ │ • Hoist var → undefined │ │ • Hoist let/const → TDZ │ │ • Hoist functions fully │ ├─────────────────────────────┤ │ 2. EXECUTION PHASE │ │ • Run code top to bottom │ │ • Assign real values │ │ • Execute function calls │ └─────────────────────────────┘

What is the Call Stack? How does it work?

The call stack tracks which function is running now, LIFO-style: every call pushes a new context on top, every return pops it off, handing control back to whatever is now on top.
stack.js
function first()  { second(); console.log("first done"); }
function second() { third();  console.log("second done"); }
function third()  { console.log("third done"); }

first();
// Output: third done → second done → first done
StepStack (top → bottom)Action
1Globalfirst() called → pushed
2first → Globalsecond() called → pushed
3second → first → Globalthird() called → pushed
4second → first → Globalthird() finishes, logs, popped
5first → Globalsecond() finishes, logs, popped
6Globalfirst() finishes, logs, popped
⚠️ A chain of calls with no base case (unbounded recursion) keeps pushing without popping, eventually throwing RangeError: Maximum call stack size exceeded.
4

What is a Closure? How does it work internally, and where is it used?

Common Trap
A closure exists when a function keeps a live reference to its outer Lexical Environment even after that outer scope has finished executing — so it can still read and mutate those variables.

Internally, every function keeps a hidden link (commonly [[Environment]]) to the scope it was defined in. When an inner function is returned or passed out of its parent, that parent's variables stay alive in memory because the inner function still references them.

closure-real-world.js
// Real-world use: a bank account module with private balance
function createAccount(initialBalance) {
  let balance = initialBalance; // private — no direct access

  return {
    deposit: amount => balance += amount,
    withdraw: amount => balance -= amount,
    getBalance: () => balance
  };
}

const account = createAccount(1000);
account.deposit(500);
account.getBalance(); // 1500 — balance can't be accessed directly
💡 Beyond data privacy, closures power memoized caches, event handlers needing setup-time data, currying, and React's useState — the state "survives" between renders purely because of a closure over it.
5

What is Scope? Explain Global, Function, Block Scope, and Scope Chain.

Global scope is visible everywhere. Function scope applies to var: visible anywhere inside the function regardless of nested blocks. Block scope applies to let/const: confined strictly to the nearest { }.

The scope chain is the lookup path the engine follows when a variable isn't found in the current scope — it walks outward, based on lexical nesting, until it finds the variable or reaches global scope and throws a ReferenceError.

Scope Chain Lookup (innermost → outermost) Global Scope { appName } └─ Function Scope { userId } └─ Block Scope (if/for) { tempValue } Looking up 'appName' from inside the block: Block ✗ → Function ✗ → Global ✓ (found)
B. Event Loop & Asynchronous JavaScript
6

Explain the Event Loop in JavaScript.

JS runs on one thread with one call stack. The event loop bridges JS with the browser's Web APIs: it checks if the stack is empty, and if so, pulls the next queued task and pushes it onto the stack.
┌───────────────┐ │ Call Stack │◄──────────┐ └───────┬────────┘ │ │ empty? │ pushes next ▼ │ task when ┌───────────────┐ │ stack is empty │ Event Loop │────────────┘ └───────┬────────┘ ┌──────────┴──────────┐ ▼ ▼ ┌───────────────┐ ┌───────────────────┐ │ Microtask Queue│ │ Macrotask Queue │ │ (Promises, │ │ (setTimeout, │ │ queueMicrotask)│ │ setInterval, I/O)│ └───────────────┘ └───────────────────┘ ▲ │ registered by ┌───────────────┐ │ Web APIs │ (timers, fetch, DOM events) └───────────────┘

The event loop always fully drains the microtask queue before touching the macrotask queue — this priority rule is the key to predicting async execution order.

What is the difference between the Microtask Queue and the Macrotask Queue?

AspectMicrotask QueueMacrotask Queue
ExamplesPromise .then/.catch/.finally, queueMicrotask, MutationObserversetTimeout, setInterval, DOM events, I/O
PriorityHigher — runs firstLower — runs after microtasks are drained
Draining ruleALL microtasks run before the next macrotaskOnly ONE macrotask runs per tick

queue-order.js
console.log("1: sync start");
setTimeout(() => console.log("2: macrotask"), 0);
Promise.resolve().then(() => console.log("3: microtask"));
console.log("4: sync end");
// Output: 1 → 4 → 3 → 2
8

Explain the execution order of setTimeout(), Promises, and async/await.

Rule: sync code → all microtasks drained → one macrotask, repeating. async/await follows the same rule — code after await is scheduled as a microtask, just like a .then().
full-order.js
console.log("A");
setTimeout(() => console.log("B"), 0);

async function demo() {
  console.log("C");
  await null;
  console.log("D"); // scheduled as a microtask
}
demo();

Promise.resolve().then(() => console.log("E"));
console.log("F");
// Output: A → C → F → D → E → B
💡 Trick: everything before the first await is synchronous. Everything after it, and every .then(), joins the microtask queue — which always empties before any setTimeout callback runs.
9

How do Promises work internally? Explain their states and lifecycle.

A Promise moves through exactly three states — pending, fulfilled, or rejected — and once settled, it's permanent, which is what makes chaining reliable.
new Promise((resolve, reject) => {...}) │ ▼ ┌───────────┐ │ PENDING │ (initial) └─────┬─────┘ resolve()│reject() ┌─────────┴─────────┐ ▼ ▼ ┌───────────────┐ ┌───────────────┐ │ FULFILLED │ │ REJECTED │ │ (.then runs) │ │ (.catch runs) │ └───────────────┘ └───────────────┘ settled — state can never change again

What are the differences between Promise.all(), allSettled(), race(), and any()?

MethodResolves whenRejects whenTypical use case
Promise.all()All promises fulfillAny single promise rejectsNeed every result; all-or-nothing
Promise.allSettled()All promises settleNever rejectsWant results of everything, failures included
Promise.race()First promise to settleIf the fastest one rejectsTimeouts, "whichever responds first"
Promise.any()First promise to fulfillOnly if ALL promises rejectTry multiple sources, need just one success
combinators.js
const p1 = Promise.resolve(1);
const p2 = new Promise((_, rej) => setTimeout(() => rej("fail"), 100));
const p3 = new Promise(res => setTimeout(() => res(3), 50));

Promise.all([p1, p2, p3]).catch(e => console.log("all rejects:", e));
Promise.allSettled([p1, p2, p3]).then(r => console.log("allSettled:", r));
Promise.race([p1, p2, p3]).then(r => console.log("race wins:", r));
Promise.any([p2, p3]).then(r => console.log("any wins:", r));
11

How does async/await work behind the scenes?

It's syntactic sugar over Promises. An async function always returns a Promise, and every await pauses execution, registering the rest of the function as a microtask continuation.
async-desugared.js
// What you write:
async function getUser(id) {
  const res = await fetch(`/users/${id}`);
  const data = await res.json();
  return data;
}

// Roughly what the engine does:
function getUser(id) {
  return fetch(`/users/${id}`)
    .then(res => res.json())
    .then(data => data);
}
12

Explain JavaScript's Single-Threaded Nature. How does it handle asynchronous tasks?

The JS engine executes on a single thread with a single call stack — only one operation runs at any instant. Async behavior comes from the surrounding environment (Web APIs, timers, I/O threads) handling slow work outside the main thread, then queuing a callback the event loop schedules once the stack is empty.

┌────────────────────── Browser / Node Runtime ──────────────────────┐ │ ┌───────────────┐ ┌──────────────────────────────────┐ │ │ │ JS Engine │ │ Environment APIs │ │ │ │ (single thread)│◄──────┤ Timers • Network • File I/O │ │ │ │ Call Stack │ │ (run outside the main thread) │ │ │ └───────┬────────┘ └──────────────┬─────────────────────┘ │ │ │ │ task complete │ │ │ ┌────────────────────────▼──────┐ │ │ └───────►│ Event Loop routes callback │ │ │ │ into Micro/Macrotask Queue │ │ │ └────────────────────────────────┘ │ └───────────────────────────────────────────────────────────────────────┘
C. this Keyword, call/apply/bind & Prototypes

What is the this keyword? How is its value determined?

this is determined by how a function is called (its call site) — except arrow functions, which ignore call-site rules and inherit this lexically.
Call patternValue of thisExample
Plain function callundefined (strict) or global objectgreet()
Method callThe object before the dotuser.greet()
Constructor call (new)The newly created objectnew User()
call/apply/bindWhatever object is explicitly passedgreet.call(obj)
Arrow functionInherited from enclosing lexical scope() => this
this-examples.js
const user = {
  name: "Riya",
  greetNormal: function() { console.log(this.name); },
  greetArrow: () => { console.log(this.name); }
};

user.greetNormal(); // "Riya" — this = user
user.greetArrow();  // undefined — this = outer scope

Explain call(), apply(), and bind() with practical examples.

MethodArguments formatExecutes
call()Comma-separated listImmediately
apply()Single arrayImmediately
bind()Comma-separated listReturns a new function — runs later
call-apply-bind.js
function introduce(city, country) {
  console.log(`${this.name} from ${city}, ${country}`);
}
const person = { name: "Dev" };

introduce.call(person, "Pune", "India");
introduce.apply(person, ["Pune", "India"]);

const boundIntroduce = introduce.bind(person, "Pune", "India");
boundIntroduce(); // runs later, this already locked to 'person'
💡 bind() is most useful when passing a method as a callback (e.g. to setTimeout) where you need to guarantee this doesn't get lost.
15

What is the Prototype Chain? How does JavaScript implement inheritance?

Every object has an internal link to a prototype. Missing properties trigger a walk up this chain until found or until null is reached — this lookup is exactly how JS inheritance works.
const arr = [1,2,3]; arr ──► Array.prototype ──► Object.prototype ──► null (own: (map, filter, (toString, length, push, ...) hasOwnProperty...) 0,1,2) arr.map(...) → not on arr → found on Array.prototype ✓
inheritance.js
function Animal(name) { this.name = name; }
Animal.prototype.speak = function() {
  console.log(`${this.name} makes a sound`);
};

function Dog(name) { Animal.call(this, name); }
Dog.prototype = Object.create(Animal.prototype); // link prototypes

const rex = new Dog("Rex");
rex.speak(); // "Rex makes a sound" — found via prototype chain
16

What is the difference between prototype and __proto__?

prototype exists only on functions meant to be used as constructors — it's the blueprint handed to every instance created with new. __proto__ exists on every object instance and is the live reference to that object's actual prototype.

proto-vs-dunder.js
function User(name) { this.name = name; }
const u = new User("Sam");

console.log(u.__proto__ === User.prototype); // true
📌 Modern code should use Object.getPrototypeOf(obj) instead of __proto__ directly — it's a legacy accessor kept mainly for backward compatibility.
D. Memory Management
17

Explain Primitive vs Reference Types. How does JavaScript store them in memory?

Primitives are stored directly in the variable's own stack slot — copying copies the value. Reference types live in the heap, and the variable holds only a pointer — copying copies the address, so both variables share the same object.
primitive-vs-reference.js
let a = 10;
let b = a;
b = 20;
console.log(a); // 10 — untouched, separate copy

let obj1 = { value: 10 };
let obj2 = obj1;
obj2.value = 20;
console.log(obj1.value); // 20 — same object in memory
18

Explain Stack Memory and Heap Memory.

The stack is small, fast, and holds primitives plus references, cleaned up automatically when a function returns. The heap is large and unstructured, holding dynamically sized objects/arrays that stay until nothing references them and the garbage collector reclaims them.

STACK (fast, fixed size) HEAP (large, dynamic) ┌───────────────────┐ ┌─────────────────────────┐ │ a = 10 │ │ {value: 10} ◄───┐ │ │ name = "Sam" │ │ [1,2,3] │ │ │ userRef ──────────┼────────────┼───────────────────┘ │ └───────────────────┘ └─────────────────────────┘ primitives + pointers actual objects/arrays live here
19

What is Garbage Collection? How does JavaScript manage memory?

Modern engines like V8 use mark-and-sweep: mark every object reachable from root references as "in use," then sweep away everything left unmarked.

Real-world example: a common leak happens when a DOM element is removed from the page, but a JS variable (often inside a closure or event listener) still holds a reference to it — the element stays reachable, so it can never be reclaimed.

⚠️ Common leak sources: forgotten setInterval/event listeners, unbounded global variables, and closures unintentionally holding onto large objects.
20

Explain Deep Copy vs Shallow Copy.

A shallow copy duplicates only the first level — nested objects/arrays are still shared by reference. A deep copy recursively duplicates every level, producing a fully independent structure.

deep-vs-shallow.js
const original = { name: "Kim", address: { city: "Seoul" } };

// Shallow copy — nested object still shared
const shallow = { ...original };
shallow.address.city = "Busan";
console.log(original.address.city); // "Busan" — original changed too!

// Deep copy — fully independent
const deep = structuredClone(original);
deep.address.city = "Tokyo";
console.log(original.address.city); // "Busan" — untouched this time
💡 Use structuredClone() for true deep copies. JSON.parse(JSON.stringify()) also works but silently drops functions, undefined, and Date/Map/Set.
E. Performance Patterns
21

Explain Debouncing and Throttling with real-world examples.

Debouncing waits for a burst of events to fully stop before firing once. Throttling fires at most once every fixed interval, no matter how many events occur.
Events: X X X X X Debounce: ................|──► fires once, after the gap Throttle: |──► |──► |──► |──► fires at fixed intervals
debounce-throttle.js
function debounce(fn, delay) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };
}

function throttle(fn, limit) {
  let waiting = false;
  return (...args) => {
    if (!waiting) {
      fn(...args);
      waiting = true;
      setTimeout(() => waiting = false, limit);
    }
  };
}

searchInput.oninput = debounce(fetchSuggestions, 400);
window.onscroll     = throttle(updateScrollProgress, 200);
22

What is Currying? How is it useful?

Currying transforms a multi-argument function into a chain of single-argument functions, relying on closures — each returned function "remembers" the arguments collected so far. Useful for building specialized, pre-configured versions of a general function.

currying.js
const discount = rate => price => price - price * rate;

const tenPercentOff = discount(0.10); // specialized, reusable
tenPercentOff(500); // 450
tenPercentOff(200); // 180
23

What are Polyfills? How would you implement your own map(), filter(), or bind()?

A polyfill reproduces a modern feature's behavior in environments that lack it natively. Writing one for a built-in method tests whether you understand its internals, not just how to call it.

polyfills.js
// Custom Array.prototype.map
Array.prototype.myMap = function(callback) {
  const result = [];
  for (let i = 0; i < this.length; i++) {
    result.push(callback(this[i], i, this));
  }
  return result;
};

// Custom Function.prototype.bind
Function.prototype.myBind = function(context, ...boundArgs) {
  const fn = this;
  return function(...callArgs) {
    return fn.apply(context, [...boundArgs, ...callArgs]);
  };
};
F. DOM Events & Browser Storage
24

What is Event Delegation? Why is it better than attaching multiple event listeners?

Delegation relies on bubbling: attach one listener to a shared parent, and inspect event.target to determine which child triggered it — instead of one listener per child.
<ul id="list"> click on <li> "Item 2" <li>Item 1</li> │ <li>Item 2</li> ◄────────────────┘ event fires here <li>Item 3</li> then bubbles up... </ul> │ ▼ single listener on <ul> catches it, checks event.target
delegation.js
document.getElementById("list").addEventListener("click", (e) => {
  if (e.target.tagName === "LI") {
    console.log("Clicked:", e.target.textContent);
  }
});
// Works even for <li> items added to the list after this code runs
✅ More memory-efficient (one listener instead of hundreds) and automatically covers elements added dynamically later.
