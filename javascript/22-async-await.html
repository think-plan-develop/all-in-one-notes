⏳ Async / Await in JavaScript

How async functions and await work under the hood, execution order vs .then(), error handling, and fetch() end-to-end

📌 In short: async functions always return a Promise. await pauses only that function — not the main thread — until the Promise settles, then resumes via the Microtask Queue. Wrap awaited code in try/catch to handle rejections the same way .catch() does for a Promise chain.
🔑 Key Terms at a Glance
⏳
async: Marks a function as asynchronous — it always returns a Promise, even for a plain return value.
⏸️
await: Suspends the async function until a Promise settles, without blocking the main thread.
🔁
Resumption: Once the awaited Promise settles, the continuation runs as a microtask via the Event Loop.
🛡️
Error Handling: try/catch around await is the async/await equivalent of .catch().
What is async?

async Always Returns a Promise

async is a keyword used to create an asynchronous function. An async function always returns a Promise — even when you return a plain value, JavaScript wraps it automatically.
greet.js
async function greet() {
  return "Hello";
}

Returning a normal value

get-value.js
async function getValue() {
  return "Hello";
}

console.log(getValue());

// Output:
// Promise { : "Hello" }

Internally, JavaScript treats this the same as writing:

internally.js
function getValue() {
  return Promise.resolve("Hello");
}

Returning a Promise manually

An async function can also directly return a Promise you construct yourself — it isn't double-wrapped.

get-data.js
async function getData() {
  return new Promise((resolve) => {
    resolve("Data received");
  });
}

getData().then(console.log);

// Output:
// Data received
📌 Note: Whether you return a plain value or a Promise, the caller always gets back a Promise — .then() (or await) is always the way to read the result.
What is await?

Pausing an async Function Until a Promise Settles

await is a keyword usable only inside an async function (with one exception — top-level await in ES modules). It pauses execution of that function until the Promise settles.
await-basic.js
async function test() {
  const result = await somePromise;
  console.log(result);
}

Before async/await: .then() and .catch()

Async/await didn't replace Promises — it's syntax built on top of them. This is the same flow written the older way:

before-async-await.js
function fetchData() {
  return new Promise((resolve) => {
    setTimeout(() => {
      resolve("Data received");
    }, 2000);
  });
}

fetchData()
  .then((data) => {
    console.log(data);
    return "Next step";
  })
  .then((msg) => {
    console.log(msg);
  })
  .catch((err) => {
    console.error(err);
  });
This works, but multiple chained .then() calls can get harder to read as steps grow — that readability gap is exactly what async/await is designed to close.
Execution Behavior: .then() vs async/await

Promise Behavior — .then()

then-behavior.js
const p = new Promise((resolve) => {
  setTimeout(() => {
    resolve("Promise Resolved");
  }, 3000);
});

console.log("Start");

p.then((data) => {
  console.log(data);
});

console.log("End");

// Output:
// Start
// End
// Promise Resolved

What happens, step by step:

  1. The Promise is created.
  2. The .then() callback is registered.
  3. That callback is stored, waiting on the Microtask Queue.
  4. JavaScript continues executing the next line immediately.
  5. It does not wait for the Promise to resolve.
  6. Once the Promise resolves, the callback finally runs.

async/await Behavior

await-behavior.js
function fetchData() {
  return new Promise((resolve) => {
    setTimeout(() => {
      resolve("Data received");
    }, 3000);
  });
}

async function handleData() {
  console.log("Start");

  const data = await fetchData();

  console.log(data);
  console.log("End");
}

handleData();

// Output (after 3 seconds):
// Start
// Data received
// End

The function waits at await for the Promise to resolve before moving on to the next line — that's the whole point of the keyword.

JavaScript Is NOT Blocked

Even though a function "waits," the JavaScript engine itself is free to keep running everything else.

not-blocked.js
const p = new Promise((resolve) => {
  setTimeout(() => {
    resolve("Promise Resolved Value!!");
  }, 10000);
});

async function handlePromise() {
  console.log("Hello World!!");

  // Function execution is suspended here
  const val = await p;

  console.log("Namaste JavaScript");
  console.log(val);

  // p is already resolved, so this continues immediately
  const val2 = await p;

  console.log("Namaste JavaScript 2");
  console.log(val2);
}

handlePromise();
Important: JavaScript appears to be waiting, but it is not blocking the main thread — other code, timers, and events keep running while this function is suspended.
Step-by-Step Execution Internals

What Happens When JavaScript Hits await

  1. handlePromise() enters the Call Stack.
  2. "Hello World!!" is printed synchronously.
  3. await p is encountered. Since p is still pending, execution of handlePromise is suspended — the execution context of the async function is removed from the Call Stack, while its suspended state is preserved internally by the JavaScript engine.
  4. The Promise itself continues its asynchronous work (timer, network request, etc.) outside the Call Stack, entirely independent of whether the function that's awaiting it is suspended.
  5. The main thread becomes free — the browser or Node.js can continue running other functions, timers, UI events, network callbacks, and other async tasks.
  6. After 10 seconds, the setTimeout callback runs and resolves the Promise.
  7. The continuation of the function (everything after await p) is placed into the Microtask Queue.
  8. Once the Call Stack becomes empty, the Event Loop pushes that microtask back onto the Call Stack, and execution resumes exactly where it left off.
Suspension → main thread stays free → Promise settles → microtask → resume after await
Timing & Concurrency

Two Independent Promises, Awaited in Sequence

two-promises.js
const p1 = new Promise((resolve) => {
  setTimeout(() => {
    resolve("Promise Resolved after 20 sec");
  }, 20000);
});

const p2 = new Promise((resolve) => {
  setTimeout(() => {
    resolve("Promise Resolved after 40 sec");
  }, 40000);

async function handlePromise() {

  console.log(val);

  console.log("Namaste JavaScript 2");
  console.log(val2);
}

handlePromise();

Sequential vs Parallel Requests

🐢 Sequential (slow)
sequential.js
const a = await fetchA(); // waits 2s
const b = await fetchB(); // waits another 2s

// Total ≈ 4 seconds
⚡ Parallel (fast)
parallel.js
const [a, b] = await Promise.all([
  fetchA(),
  fetchB()
]);

// Total ≈ 2 seconds
💡 Interview point: Use Promise.all() when independent async operations can run in parallel — awaiting them one after another wastes time for no reason if they don't depend on each other.
Error Handling with async/await

try/catch Replaces .catch()

Since await unwraps a Promise's resolved value, a rejected Promise instead throws at the await line — so wrap it in a normal try/catch, the same way you'd handle any synchronous error.
Promise chain
catch-style.js
fetchData()
  .then((data) => {
    console.log(data);
  })
  .catch((err) => {
    console.error("Failed:", err.message);
  });
async/await
try-catch-style.js
async function run() {
  try {
    const data = await fetchData();
    console.log(data);
  } catch (err) {
    console.error("Failed:", err.message);
  }
}

One try/catch can guard multiple awaits

A rejection from any awaited call inside the block is caught by the same catch — you don't need a separate try/catch per step.

multi-await-try-catch.js
async function checkout(cart) {
  try {
    const order = await createOrder(cart);
    const payment = await proceedToPayment(order.id);
    const summary = await showOrderSummary(payment);

    console.log("Order complete:", summary);
  } catch (err) {
    // Catches a failure from ANY of the three awaits above
    console.error("Checkout failed:", err.message);
  }
}

Error handling with Promise.all()

Promise.all() rejects as soon as any one Promise rejects. Awaiting it inside a try/catch catches that rejection the same way:

promise-all-try-catch.js
async function loadDashboard() {
  try {
    const [user, posts, settings] = await Promise.all([
      getUser(1),
      getPosts(1),
      getSettings(1)
    ]);

    console.log(user, posts, settings);
  } catch (err) {
    // Fires if ANY of the three requests failed
    console.error("Dashboard load failed:", err.message);
  }
}

try/catch, then keep going with a fallback

Just like recovering with .catch(), you can catch the error and assign a default value so the function continues normally instead of stopping.

recover-with-fallback.js
async function getUserSafely(id) {
  let user;

  try {
    user = await fetchUser(id);
  } catch (err) {
    console.error("Falling back to guest user");
    user = { name: "Guest" };
  }

  return user;
}
⚠️ Common mistake: forgetting the try/catch entirely. An unhandled rejection from an awaited call will crash an async function's Promise silently unless something is listening for it — always wrap awaited calls that can fail.
Working with fetch()

fetch() Returns a Promise<Response>

fetch-returns.js
const responsePromise = fetch("https://api.example.com/users");

fetch() returns a Promise. That Promise resolves with a Response object — not the data itself yet.

fetch-then.js
fetch("https://api.example.com/users")
  .then((response) => {
    console.log(response);
  });

The Response Body Is a Readable Stream

response-body.js
const response = await fetch("https://api.example.com/users");

response.body is a ReadableStream. To convert it into usable JSON:

response-json.js
const data = await response.json();
📌 Important: response.json() also returns a Promise — that's why it needs its own await, separate from the one on fetch() itself.

Complete fetch() Example, with Error Handling

get-users.js
async function getUsers() {
  try {
    console.log("Fetching users...");

    const response = await fetch(
      "https://jsonplaceholder.typicode.com/users"
    );

    if (!response.ok) {
      throw new Error(`Request failed with status ${response.status}`);
    }

    console.log("Response object received");

    const data = await response.json();

    console.log("JSON parsed");
    console.log(data);
  } catch (err) {
    console.error("Could not load users:", err.message);
  }
}

getUsers();

Flow:

  1. fetch() sends the network request and returns a Promise immediately.
  2. await fetch(...) suspends the async function until a response arrives.
  3. The code checks response.ok — fetch() only rejects on network failure, not on HTTP error statuses like 404 or 500, so this check has to be explicit.
  4. response.json() returns another Promise.
  5. await response.json() suspends the function again until parsing finishes.
  6. If any step throws or rejects, the single catch block handles it.
⚠️ Common mistake: assuming fetch() rejects on a 404/500 response. It doesn't — only response.ok tells you that, so always check it before parsing the body.

Most Important Interview Explanation

Q: What happens internally when JavaScript reaches await p?

When JavaScript reaches await p, it checks whether p is resolved. If p is pending, the execution context of the async function is removed from the Call Stack, while its suspended state is preserved internally by the JavaScript engine. The Promise itself continues its asynchronous work (timer, network request, etc.) outside the Call Stack. The main thread becomes free and can continue executing other tasks. When the Promise resolves, the continuation of the async function is placed in the Microtask Queue. Once the Call Stack becomes empty, the Event Loop pushes that microtask back onto the Call Stack, and execution resumes from the point immediately after the await.
This is the most accurate and complete interview answer for this question.

Revision Cheat Sheet

async → Promise → await → suspend → settle → resume (or throw into try/catch)

One-Line Summary

async/await makes asynchronous code look synchronous, but internally JavaScript still uses Promises, the Microtask Queue, and the Event Loop without blocking the main thread — and try/catch gives it the same error-handling power as .catch().

Tricky One: return await vs return

Q: What is the difference between these two?

Version 1
return-await.js
return await fetch(url);
Version 2
return-promise.js
return fetch(url);
In most cases they behave the same. return await is useful when you want the function's own try/catch block to handle the rejection before returning. Otherwise, returning the Promise directly is slightly more efficient, since the caller awaits it one level up instead.
Guess the Output

Guess the Output — 1

guess-1.js
async function test() {
  console.log("A");
  await Promise.resolve();
  console.log("B");
}

test();
console.log("C");
🤔 Think first… what order do A, B, and C print in?
Output: A, C, B

Why? A is synchronous. await Promise.resolve() still schedules the continuation as a microtask, even though the Promise is already resolved. C runs before that microtask. Then B executes.

Guess the Output — 2

guess-2.js
async function foo() {
  return 10;
}

foo().then(console.log);
console.log(20);
🤔 Think first… does 10 or 20 print first?
Output: 20, 10

Why? foo() returns a Promise, and .then() always runs asynchronously — so the synchronous console.log(20) runs first.

Guess the Output — 3

guess-3.js
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3));
console.log(4);
🤔 Think first… what's the print order of 1, 2, 3, 4?
Output: 1, 4, 3, 2

Why? Synchronous code runs first: 1, 4. Then the microtask queue drains: 3. Only then does the macrotask queue run setTimeout's callback: 2. This exact pattern is asked extremely often.

Guess the Output — 4

guess-4.js
async function test() {
  console.log("start");
  const value = await Promise.resolve("done");
  console.log(value);
  console.log("end");
}

test();
console.log("outside");
🤔 Think first… where does "outside" land relative to done and end?
Output: start, outside, done, end

Why? After await, the remaining code (done, end) is scheduled as a microtask and only executes once the current synchronous code — including console.log("outside") — finishes.

Guess the Output — Rejection

guess-rejection.js
async function test() {
  try {
    await Promise.reject("Error occurred");
    console.log("After await");
  } catch (err) {
    console.log("Caught:", err);
  }
  console.log("Done");
}

test();
🤔 Think first… does "After await" print before Done?
Output: Caught: Error occurred, Done

Why? The rejected Promise throws at the await line, so control jumps straight to catch — "After await" is skipped entirely. Execution then continues normally after the catch block.
