Fundamentals
🔄 Synchronous vs Asynchronous Foundation

JavaScript is single-threaded — it has only one call stack, so it can only do one thing at a time. In synchronous code, each line waits for the previous line to finish before it runs. If one line takes a long time, everything after it is blocked, including the browser's ability to repaint the screen or respond to clicks.

Asynchronous code lets JavaScript start a slow task (a timer, a network request, reading a file) and move on immediately, without freezing the rest of the program. When the slow task finishes, JavaScript is notified and runs the follow-up code at the right time — this is coordinated by the event loop, which constantly checks: "Is the call stack empty? If so, take the next task waiting in the queue and run it."

Example: Blocking (synchronous) code

sync.js
function slowTask() {
  const start = Date.now();
  while (Date.now() - start < 3000) {
    // blocks the thread for 3 seconds
  }
  console.log("Slow task done");
}

console.log("Start");
slowTask();               // UI freezes here for 3s
console.log("End");

Example: Non-blocking (asynchronous) code

async.js
console.log("Start");

setTimeout(() => {
  console.log("Slow task done");
}, 3000);              // scheduled, doesn't block

console.log("End");

// Output order: Start -> End -> Slow task done
📌 Note: "End" prints before "Slow task done" because setTimeout hands the callback off to the browser/Node's timer system and continues executing the rest of the script immediately.
✔ Why async matters
  • UI stays responsive during network/file operations
  • Multiple slow operations can overlap in time
  • Server can handle many requests concurrently
✘ Trade-offs
  • Execution order is less predictable to read
  • Requires careful error handling across time
  • Can lead to messy code if not structured well
Callbacks
📞 Callback Functions

A callback is simply a function passed into another function as an argument, to be "called back" later — either immediately (synchronous callback, like in .map()) or after some async operation completes (asynchronous callback, like in setTimeout). Callbacks were JavaScript's original way of handling asynchronous work, before Promises existed.

Example: Simulating an API call with a callback

callback.js
function getUser(id, callback) {
  setTimeout(() => {
    const user = { id, name: "Aisha" };
    callback(null, user);  // (error, result) convention
  }, 1000);
}

getUser(1, (err, user) => {
  if (err) {
    return console.error(err);
  }
  console.log("User loaded:", user.name);
});
💡 Tip: The (error, result) callback signature shown above is called the error-first callback pattern — it's the convention Node.js built its entire core library on (e.g. fs.readFile).
🌀 Callback Hell Anti-pattern

Callback hell (a.k.a. the "pyramid of doom") happens when several asynchronous steps depend on each other, so each callback is nested inside the previous one. The code drifts to the right, becomes hard to read, and error handling has to be repeated at every level.

Example: Nested callbacks

callback-hell.js
getUser(1, (err, user) => {
  if (err) return console.error(err);

  getPosts(user.id, (err, posts) => {
    if (err) return console.error(err);

    getComments(posts[0].id, (err, comments) => {
      if (err) return console.error(err);

      getLikes(comments[0].id, (err, likes) => {
        if (err) return console.error(err);
        console.log(likes);
        // 4 levels deep, and growing...
      });
    });
  });
});
⚠️ Warning: Beyond being ugly, this pattern makes error handling, debugging, and reasoning about control flow genuinely difficult. This exact pain point is what led to the creation of Promises.
Promises
🤝 Promise

A Promise is an object representing the eventual result of an asynchronous operation. It exists in one of three states:

StateMeaning
PendingInitial state, operation not finished yet
FulfilledOperation completed successfully, has a value
RejectedOperation failed, has a reason (error)

A Promise moves from pending to either fulfilled or rejected exactly once — it can never change state again. You attach handlers with .then() for success and .catch() for failure.

Example: Creating and consuming a Promise

promise.js
function getUser(id) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (id <= 0) {
        return reject(new Error("Invalid id"));
      }
      resolve({ id, name: "Aisha" });
    }, 1000);
  });
}

getUser(1)
  .then(user => console.log("Got:", user.name))
  .catch(err => console.error("Failed:", err.message));
✅ Benefit: Promises are chainable, composable, and let you handle every error in one place with a single .catch(), instead of checking err at every nested level.
🔗 Promise Chaining

Because .then() always returns a new Promise, you can chain multiple asynchronous steps in a flat, readable sequence instead of nesting them. If you return a value from .then(), it gets wrapped in a resolved Promise; if you return another Promise, the chain waits for it to settle before moving to the next .then().

Example: The callback-hell example, rewritten flat

chaining.js
getUser(1)
  .then(user => getPosts(user.id))
  .then(posts => getComments(posts[0].id))
  .then(comments => getLikes(comments[0].id))
  .then(likes => console.log("Likes:", likes))
  .catch(err => console.error("Something failed:", err.message));
  // one catch handles an error from ANY step above
💡 Tip: Notice the structure is completely flat — no pyramid, one error handler, and each step's output flows cleanly into the next.
⚡ Promise.all()

Promise.all() takes an array (or iterable) of Promises and runs them concurrently. It resolves with an array of all results, in the same order, once every Promise has fulfilled. If any single one rejects, Promise.all() immediately rejects with that error — the other results are discarded, even if they would have succeeded.

Example: Fetching three resources in parallel

promise-all.js
const userP = getUser(1);
const postsP = getPosts(1);
const settingsP = getSettings(1);

Promise.all([userP, postsP, settingsP])
  .then(([user, posts, settings]) => {
    console.log(user, posts, settings);
    // all 3 finished, total time = slowest one, not the sum
  })
  .catch(err => {
    console.error("One of them failed:", err.message);
  });
📌 Note: Use Promise.all() when you need all results and can't proceed if even one fails (e.g. loading required data before rendering a page).
📋 Promise.allSettled()

Promise.allSettled() also runs Promises concurrently, but unlike Promise.all(), it never short-circuits. It waits for every Promise to settle (fulfilled or rejected) and returns an array of status objects, each shaped as { status, value } or { status, reason }.

Example: Uploading multiple files, some may fail

promise-allsettled.js
const uploads = [uploadFile("a.png"), uploadFile("b.png"), uploadFile("broken.png")];

Promise.allSettled(uploads).then(results => {
  results.forEach((result, i) => {
    if (result.status === "fulfilled") {
      console.log(`File ${i} uploaded:`, result.value);
    } else {
      console.log(`File ${i} failed:`, result.reason.message);
    }
  });
});
💡 Tip: Use allSettled() when partial success is acceptable — e.g. bulk uploads, sending analytics, notifying multiple services — and you want a full report instead of one failure killing everything.
🏁 Promise.race()

Promise.race() settles as soon as the first Promise in the array settles — whether it fulfills or rejects. The rest keep running in the background, but their outcomes are ignored by the race itself.

Example: Timeout pattern — fail if a request takes too long

promise-race.js
function timeout(ms) {
  return new Promise((_, reject) =>
    setTimeout(() => reject(new Error("Request timed out")), ms)
  );
}

Promise.race([fetchData(), timeout(5000)])
  .then(data => console.log("Got data:", data))
  .catch(err => console.error(err.message));
  // whichever settles first (data or timeout) wins the race
📌 Note: This "race against a timeout" is the single most common real-world use of Promise.race().
🎯 Promise.any()

Promise.any() resolves as soon as the first Promise fulfills — rejections along the way are ignored. It only rejects if all the Promises reject, in which case it throws an AggregateError containing every individual error.

Example: Trying multiple mirrors, use whichever responds first successfully

promise-any.js
Promise.any([
  fetch("https://mirror1.example.com/data"),
  fetch("https://mirror2.example.com/data"),
  fetch("https://mirror3.example.com/data")
])
  .then(response => console.log("First success from:", response.url))
  .catch(aggregateError => {
    console.error("All mirrors failed:");
    aggregateError.errors.forEach(e => console.error(" -", e.message));
  });
🧭 any() vs race(): race() settles on whichever finishes first, success or failure. any() specifically waits for the first success, and ignores failures unless everything fails.

Comparison of the four combinators

MethodSettles whenRejects when
Promise.all()All fulfillAny one rejects (immediately)
Promise.allSettled()All settle (any outcome)Never rejects
Promise.race()First one settlesIf the first to settle is a rejection
Promise.any()First one fulfillsOnly if all reject (AggregateError)
Modern Async Syntax
⏳ async/await

async/await is syntactic sugar built on top of Promises, introduced to make asynchronous code look and read like synchronous code. Marking a function async makes it always return a Promise. Inside it, await pauses execution of that function (without blocking the rest of the program) until the awaited Promise settles, then unwraps its value.

Example: Same chain as before, written with async/await

async-await.js
async function loadFeed() {
  try {
    const user = await getUser(1);
    const posts = await getPosts(user.id);
    const comments = await getComments(posts[0].id);
    console.log("Comments:", comments);
  } catch (err) {
    console.error("Feed failed to load:", err.message);
  }
}

loadFeed();

Example: Running independent awaits in parallel

parallel-await.js
// Slower: each await waits for the previous one to finish
const user = await getUser(1);
const settings = await getSettings(1);   // waits unnecessarily

// Faster: start both requests at once, then await together
const [user2, settings2] = await Promise.all([
  getUser(1),
  getSettings(1)
]);
⚠️ Common mistake: Writing several unrelated await calls one after another runs them sequentially, wasting time. If the operations don't depend on each other, start them together and await with Promise.all().
Error Handling
🛡️ Error Handling in Async Code

Errors in asynchronous code can't be caught by a plain try/catch wrapped around the call itself, because the error happens later, after the surrounding code has already finished executing. Each async style has its own correct way to handle errors.

1. Callbacks — error-first convention

error-callback.js
getUser(-1, (err, user) => {
  if (err) {
    return console.error("Error:", err.message);
  }
  console.log(user);
});

2. Promises — .catch() at the end of the chain

error-promise.js
getUser(-1)
  .then(user => getPosts(user.id))
  .catch(err => console.error("Chain failed:", err.message));
  // catches an error from getUser() OR getPosts()

3. async/await — try/catch blocks

error-async-await.js
async function loadFeed() {
  try {
    const user = await getUser(-1);
    const posts = await getPosts(user.id);
    console.log(posts);
  } catch (err) {
    console.error("Feed failed:", err.message);
  } finally {
    console.log("Done attempting to load feed");
  }
}
⚠️ Unhandled rejections: If a Promise rejects and nothing catches it — no .catch(), no surrounding try/catch around an await — JavaScript raises an UnhandledPromiseRejection. In Node.js this can even crash the process, so every async chain should end in a catch.
✔ Good practice
  • Always end Promise chains with .catch()
  • Wrap await calls in try/catch
  • Use finally for cleanup that must always run
  • Create custom Error types for clearer messages
✘ Common mistakes
  • Forgetting to return a Promise inside .then()
  • Swallowing errors silently (empty catch blocks)
  • Mixing callbacks and Promises inconsistently
  • Not handling rejection in "fire and forget" calls
Iteration Protocols
🔁 Generators & Iterators

An iterator is any object that implements a next() method returning { value, done }. It's the low-level protocol JavaScript uses under the hood for for...of, spread (...), and destructuring. A generator is a special function — declared with function* — that automatically builds an iterator for you and can pause and resume its execution using the yield keyword.

Example: A manual iterator (no generator)

iterator.js
function makeCounter() {
  let count = 1;
  return {
    next() {
      return count <= 3
        ? { value: count++, done: false }
        : { value: undefined, done: true };
    }
  };
}

const it = makeCounter();
console.log(it.next()); // { value: 1, done: false }
console.log(it.next()); // { value: 2, done: false }
console.log(it.next()); // { value: 3, done: false }
console.log(it.next()); // { value: undefined, done: true }

Example: The same counter written as a generator

generator.js
function* counter() {
  yield 1;
  yield 2;
  yield 3;
}

const gen = counter();     // calling it returns an iterator, body hasn't run yet
console.log(gen.next()); // { value: 1, done: false }
console.log(gen.next()); // { value: 2, done: false }

// Generators are iterable, so for...of works directly:
for (const n of counter()) {
  console.log(n);        // 1, 2, 3
}

Example: An infinite ID generator (lazy evaluation)

infinite-generator.js
function* idGenerator() {
  let id = 1;
  while (true) {
    yield id++;   // pauses here until next() is called again
  }
}

const ids = idGenerator();
console.log(ids.next().value); // 1
console.log(ids.next().value); // 2
// values are produced one at a time, on demand — never all at once
💡 Tip: Generators are the mechanism behind async/await under the hood, and they're the standard way to build custom iterables (e.g. a class-based data structure that supports for...of).
🗂️ Map, Set & Their Weak Variants Quick Reference

Map stores key-value pairs where keys can be any type. Set stores a collection of unique values. Their Weak variants only accept object keys/values, aren't iterable, and let the garbage collector reclaim memory once nothing else references the key — useful for attaching metadata to objects without causing memory leaks.

Map — example

map.js
const map = new Map();
map.set("name", "Aisha");
map.set(1, "numeric key");
map.get("name");      // "Aisha"
map.has(1);           // true
map.size;                // 2
map.delete(1);
for (const [k, v] of map) { console.log(k, v); }

set.js
const set = new Set([1, 2, 2, 3]);
console.log(set.size);   // 3 -> duplicates auto-removed
set.add(4);
set.has(2);          // true
set.delete(1);
for (const val of set) { console.log(val); }

let user = { name: "Aisha" };
const wm = new WeakMap();
wm.set(user, { lastLogin: "today" }); // key MUST be an object
wm.get(user);   // { lastLogin: "today" }
user = null;      // no other refs -> entry becomes garbage-collectible

Interview Questions
🎤 Async JavaScript & Promises — Interview Questions

Basics

1. Is JavaScript synchronous or asynchronous?

JavaScript itself is single-threaded and synchronous by design — it has one call stack and runs one line at a time. It feels asynchronous because the runtime environment (browser or Node.js) provides APIs like setTimeout, network requests, and file I/O that run outside the main thread, and the event loop schedules their callbacks back onto the stack once they finish.

2. What is asynchronous programming?

It's a way of writing code where long-running operations (timers, network calls, disk reads) don't block the rest of the program. Instead of waiting, the program registers what to do when the operation finishes and continues executing other code in the meantime.

3. What is a Promise?

A Promise is an object that represents a value which isn't available yet but will be at some point — either successfully (fulfilled) or with a failure (rejected). It provides .then(), .catch(), and .finally() to attach handlers for those outcomes.

4. What are the three states of a Promise?

Pending (initial, not yet settled), Fulfilled (operation succeeded, has a value), and Rejected (operation failed, has a reason). A Promise can only transition from pending to one of the other two, and only once — it's immutable after that.

5. What is an async function?

A function declared with the async keyword. It always returns a Promise, even if you write a plain return statement inside it (the returned value gets automatically wrapped). It also unlocks the ability to use await inside its body.

6. What does the await keyword do?

await pauses execution of the surrounding async function until the Promise on its right settles. If the Promise fulfills, await returns its value; if it rejects, await throws the error, which you can catch with a normal try/catch. Importantly, it only pauses that function — the rest of the program keeps running.

7. What happens if an async function contains no await?

It still returns a Promise, but it runs to completion synchronously (top to bottom) the same as any regular function, with its return value wrapped in a resolved Promise. There's no actual pausing since there's nothing to wait on.

8. What are the advantages of async/await over Promise chaining?

async/await reads like sequential, synchronous code, which makes it easier to follow multi-step logic, use normal try/catch for errors, use loops/conditionals naturally around asynchronous calls, and avoid the visual noise of stacked .then() calls. Under the hood it's still Promises — just easier syntax.

9. How do you convert callback-based code into Promise-based code?

Wrap the callback-based call inside a new Promise((resolve, reject) => {...}), and call resolve() on success or reject() on error inside the original callback — this is often called "promisifying."

promisify.js
function readFilePromise(path) {
  return new Promise((resolve, reject) => {
    fs.readFile(path, "utf8", (err, data) => {
      if (err) reject(err);
      else resolve(data);
    });
  });
}

10. How do you convert Promise chaining into async/await?

Replace each .then(value => ...) with const value = await ... on its own line, and replace the trailing .catch(err => ...) with a try/catch wrapped around the whole sequence.

convert.js
// Before (chaining)
getUser(1).then(u => getPosts(u.id)).catch(console.error);

// After (async/await)
try {
  const u = await getUser(1);
  const posts = await getPosts(u.id);
} catch (err) { console.error(err); }

Promise Methods

1. What is Promise.all()? When should you use it?

It runs Promises concurrently and resolves with an array of all their values once every one fulfills; it rejects immediately if any one rejects. Use it when you need every result and can't proceed with only partial data — e.g. loading all the data required to render a page.

2. What is Promise.allSettled()? When should you use it?

It runs Promises concurrently and always waits for all of them to settle, returning a status object for each (fulfilled/value or rejected/reason) — it never short-circuits. Use it when partial failure is acceptable and you want a full report, e.g. bulk uploads or notifying several independent services.

3. What is Promise.race()? When should you use it?

It settles as soon as the first Promise settles, whether that's a fulfillment or a rejection. Use it for "whichever finishes first wins" scenarios, most commonly implementing timeouts by racing a real request against a rejecting timer.

4. What is Promise.any()? When should you use it?

It resolves as soon as the first Promise fulfills, ignoring rejections along the way; it only rejects (with an AggregateError) if every Promise rejects. Use it when you have multiple redundant sources and just need one success, e.g. trying several CDN mirrors.

5. Difference between all(), allSettled(), race(), and any()?

MethodSettles whenRejects when
all()All fulfillAny one rejects (immediately)
allSettled()All settle (any outcome)Never rejects
race()First one settlesIf the first to settle rejects
any()First one fulfillsOnly if all reject

Async Execution

1. How do you execute multiple asynchronous operations one after another?

Use sequential await calls, one per line — each waits for the previous one to finish before starting. This is correct when a later call actually depends on an earlier call's result.

2. How do you execute multiple asynchronous operations in parallel?

Start all the async calls first (without awaiting each individually), collect the resulting Promises in an array, then await them together with Promise.all() (or allSettled() if partial failure is fine).

3. How would you execute three API calls sequentially?

sequential.js
const a = await callApi1();
const b = await callApi2(a);   // depends on 'a'
const c = await callApi3(b);   // depends on 'b'

4. How would you execute three independent API calls simultaneously?

parallel.js
const [a, b, c] = await Promise.all([
  callApi1(), callApi2(), callApi3()
]);   // total time = slowest call, not the sum

Error Handling

1. How do you handle errors with async/await?

Wrap the await calls in a try/catch block. Any rejection thrown by an awaited Promise is caught just like a thrown exception, and a finally block can run cleanup regardless of outcome.

2. How do you retry a failed API request?

retry.js
async function retry(fn, attempts = 3) {
  for (let i = 1; i <= attempts; i++) {
    try {
      return await fn();
    } catch (err) {
      if (i === attempts) throw err;
      console.log(`Attempt ${i} failed, retrying...`);
    }
  }
}

3. How would you implement a timeout for an API request?

timeout.js
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error("Timed out")), ms)
  );
  return Promise.race([promise, timeout]);
}

4. How would you avoid Callback Hell in a large application?

Replace nested callbacks with Promises and chain them flat with .then(), or better, use async/await for sequential logic. Breaking large flows into small, named, reusable async functions also keeps nesting shallow and error handling centralized.

🧩 Scenario-Based Applied

1. Your page needs data from Users, Products, and Orders APIs before rendering. Which Promise method would you use and why?

Promise.all() — the page can't render meaningfully without all three, so it makes sense to fail fast if any one of them fails, rather than rendering an incomplete page.

2. You have five independent API calls. How can you execute all of them simultaneously to reduce response time?

Fire all five calls first without awaiting each one individually, put the resulting Promises in an array, and await them together with Promise.all() — total time becomes the slowest call instead of the sum of all five.

3. One API failure should stop the entire process. Which Promise method is appropriate?

Promise.all() — it rejects as soon as any single Promise rejects, which naturally stops the whole process.

4. You want to display whatever data is available even if some APIs fail. Which Promise method would you use?

Promise.allSettled() — it never short-circuits, so you can render the successful results and show a fallback/error state for the failed ones.

5. You need the fastest response from multiple mirror servers. Which Promise method would you choose?

Promise.race() — it settles with whichever mirror responds first, success or failure.

6. You need the first successful response from multiple backup servers. Which Promise method should you use?

Promise.any() — it ignores individual failures and resolves as soon as the first server succeeds, only rejecting if all of them fail.

7. How would you implement a 5-second timeout for an API request using Promise.race()?

race-timeout.js
const timeout = new Promise((_, reject) =>
  setTimeout(() => reject(new Error("Request timed out")), 5000)
);

Promise.race([fetchData(), timeout])
  .then(data => console.log("Data:", data))
  .catch(err => console.error(err.message));  // fires if request > 5s
