A. Event Model
🫧 Event Bubbling, Capturing & Propagation Control

1. What is Event Bubbling?

Event bubbling is JavaScript's default propagation behavior: when an event fires on an element, it doesn't stay there. After triggering the handler on the target, the event "bubbles up" through every ancestor in the DOM tree — parent, grandparent, all the way to the document — giving each one a chance to respond. This bottom-up flow is why attaching a single listener on a parent can catch events from all of its children, a technique called Event Delegation.

diagram
     document
        ↑
     <div id="parent">
        ↑
     <button id="child">  ← event starts HERE (target)
        then bubbles upward ↑↑↑
bubbling.js
document.getElementById("parent").addEventListener("click", () => {
  console.log("Parent Clicked");
});

document.getElementById("child").addEventListener("click", () => {
  console.log("Button Clicked");
});

// Click the button → Output:
// "Button Clicked"  (target fires first)
// "Parent Clicked"  (bubbles up to parent)

Real-world use — Event Delegation: instead of attaching a click listener to each <li> individually, you attach one listener to the parent <ul> and let bubbling do the work. This is both more memory-efficient and automatically handles list items added to the DOM later.

event-delegation.js
document.getElementById("products").addEventListener("click", (event) => {
  console.log(event.target.textContent);
  // works for every <li>, including ones added dynamically
});

2. What is Event Capturing?

Event capturing (also called "trickling") is the opposite direction of propagation — the event begins at the document and travels downward through ancestors until it reaches the target. Capturing happens in the first phase of event flow, before bubbling. It's rarely needed in everyday code, but it's useful when you need to intercept an event at a parent level before it reaches its target. You opt in by passing true or { capture: true } as the third argument to addEventListener.

diagram
Full event flow:

  ┌─── 1. CAPTURING PHASE ──────────────────────────┐
  │  document → html → body → parent → target        │
  └─────────────────────────────────────────────────-┘
  ┌─── 2. TARGET PHASE ─────────────────────────────┐
  │  handlers on the target itself                   │
  └──────────────────────────────────────────────────┘
  ┌─── 3. BUBBLING PHASE ───────────────────────────┐
  │  target → parent → body → html → document        │
  └──────────────────────────────────────────────────┘
capturing.js
document.getElementById("parent").addEventListener("click", () => {
  console.log("Parent");
}, true); // true = capturing phase

document.getElementById("child").addEventListener("click", () => {
  console.log("Child");
}, true);

// Click the child → Output:
// "Parent"  (captured on the way down)
// "Child"
Bubbling is the default — no extra argument needed. Capturing must be explicitly enabled. In practice, most code only ever uses bubbling.

3. What is the difference between preventDefault() and stopPropagation()?

These two methods are often confused because they both appear inside event handlers, but they solve completely different problems. preventDefault() stops the browser's built-in reaction to an event — like following a link or submitting a form — while still allowing the event to propagate normally through the DOM. stopPropagation() does the opposite: it allows the browser's default action to happen but stops the event from traveling any further up (or down) the DOM tree, so parent element listeners never fire.

preventDefault()stopPropagation()
Stops browser default (link, form submit)✅ Yes❌ No
Stops bubbling/capturing to parent elements❌ No✅ Yes
Typical useForms, links, right-click menusNested elements with conflicting handlers
prevent-stop.js
// preventDefault — stops navigation, bubbling still happens
document.getElementById("link").addEventListener("click", (e) => {
  e.preventDefault();
  console.log("Navigation prevented, event still bubbles");
});

// stopPropagation — parent handler never fires
document.getElementById("parent").addEventListener("click", () => {
  console.log("Parent"); // never runs
});

document.getElementById("child").addEventListener("click", (e) => {
  e.stopPropagation();
  console.log("Child only");
});
They can also be combined: e.preventDefault(); e.stopPropagation(); — stop the browser action AND prevent the event from travelling further.
B. DOM Content
📄 innerHTML vs innerText vs textContent

4. What is the difference between innerHTML, innerText, and textContent?

All three read or set the content of a DOM element, but they differ in what they include and how they treat HTML markup and hidden elements. innerHTML works with the raw HTML string, meaning it parses tags when reading and renders them when writing. innerText gives you the rendered, human-visible text, respecting CSS — hidden elements are excluded, just as they would be from a user's perspective. textContent gives you everything from the DOM tree as a raw text string, regardless of CSS visibility, and is faster because it doesn't trigger a layout recalculation.

innerHTMLinnerTexttextContent
Reads/writes HTML tags✅ Yes❌ No❌ No
Respects CSS visibility❌ No✅ Yes (hides hidden)❌ No (includes all)
PerformanceSlowerSlower (needs layout)✅ Fastest
XSS risk if using user input⚠️ High risk✅ Safe✅ Safe
dom-content.js
<div id="demo">
  Hello <b>World</b>
  <span style="display:none">Hidden</span>
</div>

const el = document.getElementById("demo");

el.innerHTML;     // 'Hello <b>World</b> <span style...>Hidden</span>'
el.innerText;     // 'Hello World'  (hidden span excluded)
el.textContent;   // 'Hello World Hidden'  (all text, ignores CSS)

// Writing HTML — only innerHTML renders tags
el.innerHTML  = "<h2>Welcome</h2>"; // renders an h2
el.textContent = "<h2>Welcome</h2>"; // shows the literal string
Security note: never assign user-provided input to innerHTML without sanitizing it first — malicious scripts embedded in the string will execute, creating a Cross-Site Scripting (XSS) vulnerability. Use textContent when inserting plain text.
C. Fetch API & AbortController
🌐 Fetch API & Request Cancellation

5. What is the Fetch API?

The Fetch API is the modern, Promise-based replacement for the older XMLHttpRequest. Calling fetch(url) returns a Promise that resolves to a Response object once the server responds. Because it's Promise-based, it works naturally with .then().catch() chaining and even more naturally with async/await. You can configure every aspect of the request — method, headers, body, credentials — through an options object passed as the second argument.

fetch.js
// GET request with async/await
async function getUsers() {
  try {
    const response = await fetch("https://jsonplaceholder.typicode.com/users");

    // fetch only rejects for network failures —
    // a 404 or 500 still "resolves", so check manually:
    if (!response.ok) {
      throw new Error(`HTTP error: ${response.status}`);
    }

    const users = await response.json();
    console.log(users);
  } catch (error) {
    console.error(error);
  }
}

// POST request
fetch("https://example.com/api", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "John" })
});
Critical interview point: fetch() only rejects the Promise on a network failure (e.g. no internet, DNS error). HTTP error codes like 404 Not Found or 500 Server Error still resolve normally — you must check response.ok or response.status manually to detect them.

6. What is AbortController?

AbortController gives you a way to programmatically cancel a fetch() request that's already in flight. You create a controller, pass its signal to fetch(), and call controller.abort() whenever you want to cancel — the Promise rejects with an AbortError. The canonical real-world scenario is a search-as-you-type input: every new keystroke cancels the previous request so only the latest query's result ever arrives, avoiding race conditions where an older, slower response overwrites a newer one.

abort-controller.js
// Basic usage
const controller = new AbortController();

fetch("https://jsonplaceholder.typicode.com/users", {
  signal: controller.signal
})
  .then(r => r.json())
  .then(console.log)
  .catch(err => {
    if (err.name === "AbortError") {
      console.log("Request was cancelled");
    }
  });

controller.abort(); // cancel it

// Real-world: cancel previous search on each keystroke
let controller;

function search(query) {
  if (controller) controller.abort(); // cancel the previous

  controller = new AbortController();

  fetch(`/search?q=${query}`, { signal: controller.signal })
    .then(r => r.json())
    .then(showResults)
    .catch(err => { if (err.name !== "AbortError") throw err; });
}
D. Strict Mode
🔒 Strict Mode — "use strict"

7. What is Strict Mode?

Strict mode is an opt-in feature introduced in ES5 that makes the JavaScript engine enforce a stricter, safer set of parsing and runtime rules. Without it, many common mistakes — like forgetting to declare a variable — are silently ignored and produce hard-to-trace bugs. In strict mode those same mistakes throw clear errors immediately, making the source of the problem obvious. You enable it by placing the string "use strict" at the top of a file or function. ES6 modules and classes run in strict mode automatically, which is why modern JavaScript codebases effectively operate under it without explicitly writing the directive.

strict-mode.js
// Without strict mode — silent bug
x = 10;
console.log(x); // 10 — accidentally created a global variable

// With strict mode — immediate, clear error
"use strict";
x = 10; // ReferenceError: x is not defined
What strict mode prevents: accidental global variables · assigning to read-only properties · deleting undeletable properties · duplicate parameter names · using reserved future keywords like implements, interface, let (in non-ES6 contexts) · with statements.
E. Browser Storage
💾 Cookies, Local Storage & Session Storage

8. What is the difference between Cookies, Local Storage, and Session Storage?

All three store key-value data in the browser, but they differ significantly in how much they hold, how long they persist, whether they travel to the server, and how they're scoped. The right choice depends on the use case: if the server needs the data (e.g. auth tokens for session management), cookies are the only option. If the data should survive the browser being closed and reopened, Local Storage is the answer. If the data only needs to last for a single tab session, Session Storage is the cleanest fit.

Sent with every HTTP request✅ Yes❌ No❌ No
Accessible via JavaScript✅ Yes✅ Yes✅ Yes

Typical use caseAuth tokens, session IDs, user preferences the server needsTheme, language, shopping cart, cached dataMulti-step forms, OTP flow, temporary tab state
storage.js
// Cookies
document.cookie = "username=John; max-age=3600";

// Local Storage — survives tab/browser close
localStorage.setItem("theme", "dark");
console.log(localStorage.getItem("theme")); // "dark"
localStorage.removeItem("theme");

// Session Storage — cleared when the tab closes
sessionStorage.setItem("user", "John");
console.log(sessionStorage.getItem("user")); // "John"
F. Memoization
⚡ Memoization — Cache Results for Performance

9. What is Memoization?

Memoization is a performance optimization technique where a function caches its output for each unique set of inputs the first time it's called. On subsequent calls with the same inputs, instead of repeating the computation, it returns the stored result instantly. It's a specific application of the caching concept, and it works particularly well for pure functions — functions that always return the same result for the same input and have no side effects. The cache is typically held alive by a closure over the memoized function.

memoize.js
// Without memoization — recalculates every call
function square(num) {
  console.log("Calculating...");
  return num * num;
}
square(5); // "Calculating..." → 25
square(5); // "Calculating..." → 25  (same work done again)

// With memoization — second call hits the cache
function memoize(fn) {
  const cache = {};
  return function(...args) {
    const key = JSON.stringify(args);
    if (cache[key] !== undefined) {
      return cache[key]; // cache hit
    }
    console.log("Calculating...");
    cache[key] = fn(...args);
    return cache[key];
  };
}

const memoSquare = memoize(num => num * num);
memoSquare(5); // "Calculating..." → 25  (computed, stored)
memoSquare(5); // 25  (returned from cache instantly)
memoSquare(6); // "Calculating..." → 36  (new input, computed)
Common real-world uses: expensive mathematical or recursive computations (e.g. Fibonacci) · API response caching to avoid duplicate network requests · React's useMemo hook to skip recalculating derived state on every render · selector caching in Redux with Reselect.
When NOT to memoize: functions with side effects, functions whose results change over time (non-pure), or functions called with too many unique inputs — the cache can grow large and waste memory instead of saving time.
G. Memory Leaks
🚨 Memory Leaks — Causes & Prevention

10. What causes Memory Leaks? How do you prevent them?

A memory leak happens when the application allocates memory for something, then loses the ability or intention to use it — but the garbage collector can't reclaim it because at least one reference to it still exists somewhere. Since the mark-and-sweep garbage collector only frees memory that is completely unreachable, even a single forgotten reference is enough to keep a large object alive indefinitely. Over time, leaked memory accumulates and can slow down or crash the application.

Cause 1 — Accidental Global Variables

Assigning to an undeclared variable in non-strict mode creates a property on the global object. Global variables are always reachable (from the root), so they never get collected.

leak-globals.js
data = []; // no 'const/let/var' — creates window.data globally
// Fix: always use const / let / var, or enable strict mode

Cause 2 — Forgotten Event Listeners

Attaching an event listener to a DOM element holds a reference to both the listener function and its closure scope. If the element is removed from the DOM but the listener is never detached, both the element and everything the listener closes over stay in memory.

leak-listeners.js
button.addEventListener("click", handleClick);

// When done, remove it:
button.removeEventListener("click", handleClick);

Cause 3 — Uncleared Timers

setInterval keeps its callback (and everything in that callback's closure) alive forever unless the interval is cleared. Removing a component from the UI doesn't automatically stop its running intervals.

leak-timers.js
const id = setInterval(() => {
  console.log("Running...");
}, 1000);

// When the feature is done:
clearInterval(id);

Cause 4 — Closures Holding Large References

A closure keeps its entire outer scope alive. If an inner function captures a reference to a large data structure and that inner function itself stays reachable (e.g. attached to an event listener or stored in a long-lived variable), the large object can never be collected.

leak-closures.js
function outer() {
  const largeData = new Array(1000000).fill("x");

  return function inner() {
    console.log(largeData.length); // largeData stays alive as long as inner does
  };
}

Cause 5 — Detached DOM Elements

Removing an element from the page with removeChild or innerHTML = "" disconnects it from the document, but if your JavaScript still holds a reference to that element in a variable, the element object remains in heap memory and can't be garbage collected.
