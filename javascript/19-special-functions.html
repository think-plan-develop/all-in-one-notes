1. Currying
🍛

Turning Multi-Argument Functions Into a Chain

Functional

Currying transforms a function that takes multiple arguments into a sequence of functions that each take a single argument, one at a time.

currying-basics.js
// Normal function
function add(a, b, c) {
  return a + b + c;
}
add(1, 2, 3); // 6

// Curried version — one argument at a time
function curriedAdd(a) {
  return function (b) {
    return function (c) {
      return a + b + c;
    };
  };
}
curriedAdd(1)(2)(3); // 6

// Same thing with arrow functions
const curriedAddArrow = a => b => c => a + b + c;
curriedAddArrow(1)(2)(3); // 6

A Generic Curry Helper

curry-helper.js
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) {
      return fn(...args);
    }
    return (...moreArgs) => curried(...args, ...moreArgs);
  };
}

const add = (a, b, c) => a + b + c;
const curriedAdd = curry(add);

curriedAdd(1)(2)(3);    // 6
curriedAdd(1, 2)(3);   // 6 — can also take multiple args per call
curriedAdd(1, 2, 3);  // 6 — or all at once

Why Use It?

BenefitExample
Reusable, pre-configured functionsconst addTax = curriedMultiply(1.18)
Cleaner function compositionSingle-argument functions pipe together naturally
Delayed executionBuild up arguments over time before finally calling
💡 Currying relies entirely on closures — each returned function closes over the arguments collected so far.
2. Partial Application
🧩

Pre-Filling Some Arguments Now, Rest Later

Functional

Partial application fixes a few arguments of a function upfront, producing a new function that only needs the remaining arguments — unlike currying, it isn't restricted to one argument per call.

partial-application.js
function partial(fn, ...presetArgs) {
  return function (...remainingArgs) {
    return fn(...presetArgs, ...remainingArgs);
  };
}

function greet(greeting, name, punctuation) {
  return `${greeting}, ${name}${punctuation}`;
}

const sayHello = partial(greet, "Hello");
sayHello("Sam", "!");       // "Hello, Sam!"

const sayHelloToSam = partial(greet, "Hello", "Sam");
sayHelloToSam(".");         // "Hello, Sam."

Currying vs. Partial Application

CurryingPartial Application
Always takes exactly one argument per callCan take any number of arguments per call
Returns a function until all args are collectedReturns a function that runs once remaining args arrive
Built for composing single-argument pipelinesBuilt for "pre-configuring" a function's behavior
📌 bind() is actually a built-in form of partial application — fn.bind(null, arg1, arg2) pre-fills the first arguments and returns a new function.
3. Function Composition
🧵

Combining Small Functions Into a Pipeline

Functional

Function composition combines multiple simple functions into one, where the output of one becomes the input of the next.

compose.js
const compose = (...fns) => x => fns.reduceRight((acc, fn) => fn(acc), x);
const pipe = (...fns) => x => fns.reduce((acc, fn) => fn(acc), x);

const double = n => n * 2;
const addOne = n => n + 1;
const square = n => n * n;

// compose runs right-to-left
const composed = compose(square, addOne, double);
composed(3); // double(3)=6 → addOne(6)=7 → square(7)=49

// pipe runs left-to-right — often easier to read
const piped = pipe(double, addOne, square);
piped(3);    // same result: 49
compose()pipe()
Applies functions right-to-leftApplies functions left-to-right
Mirrors mathematical notation: f(g(x))Mirrors reading order: step 1, then step 2...
💡 Composition works best with small, single-purpose, pure functions — each one doing exactly one transformation, chained together instead of nested in one large function.
4. Memoization
🗃️

Caching Results to Skip Repeated Work (React)

Performance

In React, memoization means avoiding expensive recalculations or unnecessary re-renders. React ships three built-in tools for it: useMemo, useCallback, and React.memo.

useMemo — Cache an Expensive Calculated Value

UseMemoExample.jsx
import { useMemo, useState } from "react";

function ProductList({ products, query }) {
  const [sortOrder, setSortOrder] = useState("asc");

  // Only recompute filteredProducts when products or query change —
  // NOT when sortOrder changes, even though this component re-renders then.
  const filteredProducts = useMemo(() => {
    console.log("filtering...");
    return products.filter(p =>
      p.name.toLowerCase().includes(query.toLowerCase())
    );
  }, [products, query]);

  return (
    <div>
      <button onClick={() => setSortOrder(s => (s === "asc" ? "desc" : "asc"))}>
        Toggle Sort
      </button>
      <ul>
        {filteredProducts.map(p => <li key={p.id}>{p.name}</li>)}
      </ul>
    </div>
  );
}

useCallback — Cache a Function Reference

UseCallbackExample.jsx
import { useCallback, useState } from "react";

function ParentComponent() {
  const [count, setCount] = useState(0);

  // Without useCallback, a brand-new function is created every render,
  // causing ChildButton to re-render even when wrapped in React.memo.
  const handleClick = useCallback(() => {
    console.log("clicked!");
  }, []); // empty deps — same function reference forever

  return (
    <>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>Increment</button>
      <ChildButton onClick={handleClick} />
    </>
  );
}

React.memo — Skip Re-Rendering a Component

MemoizedChild.jsx
import { memo } from "react";

// Only re-renders if its props actually change (shallow comparison)
const ChildButton = memo(function ChildButton({ onClick }) {
  console.log("ChildButton rendered");
  return <button onClick={onClick}>Click me</button>;
});

export default ChildButton;
ToolMemoizesUse When
useMemoA computed valueAn expensive calculation shouldn't rerun every render
useCallbackA function referencePassing a stable callback to a memoized child, or as a dependency
React.memoAn entire component's outputA component re-renders often but its props rarely actually change
⚠️ useMemo/useCallback aren't free — they carry their own overhead. Reach for them when profiling shows an actual bottleneck, not as a default habit on every value and function.
5. Debouncing
⏳

Wait for a Pause Before Reacting (React)

Performance

In React, debouncing is usually built as a reusable custom hook — useDebounce — that delays updating a value until the user stops changing it for a set period.

A Reusable useDebounce Hook

useDebounce.js
import { useState, useEffect } from "react";

function useDebounce(value, delay) {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => {
      setDebouncedValue(value);
    }, delay);

    // cleanup — cancels the pending update if value changes again before delay ends
    return () => clearTimeout(timer);
  }, [value, delay]);

  return debouncedValue;
}

export default useDebounce;

Using It in a Search Input

SearchBox.jsx
import { useState, useEffect } from "react";
import useDebounce from "./useDebounce";

function SearchBox() {
  const [query, setQuery] = useState("");
  const debouncedQuery = useDebounce(query, 500);

  useEffect(() => {
    if (!debouncedQuery) return;
    console.log("Calling API with:", debouncedQuery);
    // fetch(`/api/search?q=${debouncedQuery}`)
  }, [debouncedQuery]); // only fires when the DEBOUNCED value settles

  return (
    <input
      value={query}
      onChange={(e) => setQuery(e.target.value)}
      placeholder="Search..."
    />
  );
}

export default SearchBox;
💡 The input stays instantly responsive because query updates on every keystroke — only the expensive API call waits for debouncedQuery to settle 500ms after typing stops.

Without a Custom Hook — Debounce Inline in One Component

You don't always need a separate hook file. For a one-off case, setTimeout + useRef inside the component itself does the same job.

InlineDebounceSearch.jsx
import { useState, useRef } from "react";

function InlineDebounceSearch() {
  const [query, setQuery] = useState("");
  const timerRef = useRef(null); // holds the timeout id across renders

  function handleChange(e) {
    const value = e.target.value;
    setQuery(value); // input stays instantly responsive

    clearTimeout(timerRef.current); // cancel the previous pending call

    timerRef.current = setTimeout(() => {
      console.log("Calling API with:", value);
      // fetch(`/api/search?q=${value}`)
    }, 500);
  }

  return (
    <input
      value={query}
      onChange={handleChange}
      placeholder="Search..."
    />
  );
}

export default InlineDebounceSearch;
📌 This works because useRef gives a value that persists across renders without causing a re-render itself — exactly what's needed to hold onto the "current pending timer" between keystrokes. It's a fine choice for a single component; reach for a useDebounce hook once you need the same behavior in more than one place.

Where React Debouncing Shows Up

Use CaseWhy
Search-as-you-type inputsAvoid firing an API call on every keystroke
Form field validationValidate once the user pauses, not on every character
Auto-save draftsPersist only after edits settle down
Window resize-driven layout stateRecalculate once resizing stops, inside a useEffect
⚠️ Always clean up the timer in the useEffect return function. Without it, a component that unmounts mid-delay can trigger a "state update on an unmounted component" warning.
6. Throttling
🚦

Run at Most Once Every Interval (React)

Performance

In React, throttling is typically implemented as a custom hook that wraps a handler in a stable, rate-limited version using useRef to persist timing state across renders without triggering re-renders itself.

A Reusable useThrottle Hook

useThrottle.js
import { useRef, useCallback } from "react";

function useThrottle(callback, interval) {
  const isWaiting = useRef(false); // ref persists across renders, no re-render on change

  return useCallback(
    (...args) => {
      if (isWaiting.current) return;

      callback(...args);
      isWaiting.current = true;

      setTimeout(() => {
        isWaiting.current = false;
      }, interval);
    },
    [callback, interval]
  );
}

export default useThrottle;

Using It on a Scroll Listener

ScrollTracker.jsx
import { useState, useEffect, useCallback } from "react";
import useThrottle from "./useThrottle";

function ScrollTracker() {
  const [scrollY, setScrollY] = useState(0);

  const handleScroll = useCallback(() => {
    setScrollY(window.scrollY);
  }, []);

  const throttledScroll = useThrottle(handleScroll, 200);

  useEffect(() => {
    window.addEventListener("scroll", throttledScroll);
    return () => window.removeEventListener("scroll", throttledScroll);
  }, [throttledScroll]);

  return <p>Scroll position: {scrollY}px</p>;
}

export default ScrollTracker;
💡 useRef is the key ingredient here — updating isWaiting.current doesn't trigger a re-render, so the throttle's internal timing state stays cheap to update on every scroll event.

Real Example: Infinite Scroll

A common production use case — load more items as the user nears the bottom of the page, without checking scroll position on every single scroll event.

InfiniteScrollList.jsx
import { useState, useEffect, useCallback } from "react";
import useThrottle from "./useThrottle";

function InfiniteScrollList() {
  const [items, setItems] = useState(() => Array.from({ length: 20 }, (_, i) => i + 1));
  const [isLoading, setIsLoading] = useState(false);

  const loadMoreItems = useCallback(() => {
    const nearBottom =
      window.innerHeight + window.scrollY >= document.body.offsetHeight - 200;

    if (nearBottom) {
      setIsLoading(true);
      // simulate an API call fetching the next page
      setTimeout(() => {
        setItems(prev => [
          ...prev,
          ...Array.from({ length: 20 }, (_, i) => prev.length + i + 1)
        ]);
        setIsLoading(false);
      }, 500);
    }
  }, []);

  // Without throttling, this scroll handler could fire dozens of
  // times per second, triggering repeated "nearBottom" checks and
  // duplicate load requests before isLoading even gets set.
  const throttledLoadMore = useThrottle(loadMoreItems, 300);

  useEffect(() => {
    window.addEventListener("scroll", throttledLoadMore);
    return () => window.removeEventListener("scroll", throttledLoadMore);
  }, [throttledLoadMore]);

  return (
    <div>
      <ul>
        {items.map(item => <li key={item}>Item #{item}</li>)}
      </ul>
      {isLoading && <p>Loading more...</p>}
    </div>
  );
}

export default InfiniteScrollList;
✅ The throttle caps how often the "am I near the bottom?" check even runs — at most once every 300ms — instead of on every one of the many scroll events a browser fires per second. The isLoading flag then prevents duplicate fetches within that window too.

Debounce vs. Throttle in React

useDebounceuseThrottle
Waits for a pause in activityRuns at a steady, capped rate
Built around a delayed state updateBuilt around a rate-limited callback ref
Good for: search input, form validationGood for: scroll, resize, drag, mouse-move handlers
⚠️ Always clean up event listeners in the useEffect return function — an un-removed scroll or resize listener is a common source of memory leaks in React apps.
7. Interview Questions & Answers

Basic Level 1

1

What is currying?

Currying transforms a function that takes multiple arguments into a sequence of functions that each accept a single argument, returning a new function until all arguments are supplied.

what-is-currying.js
const add = a => b => a + b;
add(2)(3); // 5
2

What is memoization?

Memoization is an optimization technique that caches the results of expensive function calls, returning the cached result when the same inputs occur again.

3

What is debouncing?

Debouncing delays a function's execution until a specified time has passed without it being called again — resetting the timer on every new call.

4

What is throttling?

Throttling limits a function to run at most once within a fixed time interval, regardless of how many times it's triggered.

5

Difference between debouncing and throttling.

DebouncingThrottling
Runs once after activity stopsRuns at a steady, limited rate during activity
Delays execution repeatedly on each callIgnores extra calls until the interval passes

Intermediate Level 2

6

Difference between currying and partial application.

CurryingPartial Application
Always one argument per callAny number of arguments per call
Returns nested single-argument functionsPre-fills some arguments, returns a function for the rest
7

What is function composition?

Function composition combines multiple simple functions into one, where each function's output feeds into the next function as input.

composition-example.js
const pipe = (...fns) => x => fns.reduce((acc, fn) => fn(acc), x);
const shout = pipe(s => s.trim(), s => s.toUpperCase(), s => s + "!");
shout("  hello  "); // "HELLO!"
8

Why does memoization only work reliably on pure functions?

A pure function always returns the same output for the same input, so caching by input is safe. A function with side effects or that reads changing external state could return a stale, incorrect cached value.

9

How would you implement a simple debounce function?

simple-debounce.js
function debounce(fn, delay) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };
}
10

How would you implement a simple throttle function?

simple-throttle.js
function throttle(fn, interval) {
  let waiting = false;
  return (...args) => {
    if (waiting) return;
    fn(...args);
    waiting = true;
    setTimeout(() => (waiting = false), interval);
  };
}

Advanced Level 3

11

Why do currying, memoization, debouncing, and throttling all rely on closures?

Each pattern needs to preserve state — collected arguments, a cache, a timer ID, or a waiting flag — across multiple separate function calls. A closure is exactly what lets a returned function keep a live reference to that state instead of losing it when the outer function finishes.

12

What's a real trade-off of memoization?

Memory usage grows unboundedly as more unique argument combinations are cached, since the cache is never automatically cleared. For functions called with many distinct inputs, this can leak memory — consider capping cache size or using a WeakMap for object keys so entries can be garbage collected.

13

Implement compose() and explain the order of execution.

compose-order.js
const compose = (...fns) => x => fns.reduceRight((acc, fn) => fn(acc), x);

const result = compose(f, g, h)(5);
// Executes right-to-left: f(g(h(5)))
// h runs first, then g, then f
14

Leading vs. trailing edge in debounce/throttle implementations.

A "trailing edge" debounce (the common version) fires after the pause. A "leading edge" version fires immediately on the first call, then ignores subsequent calls until the wait period passes — useful when you want instant feedback but still want to prevent rapid re-firing.

15

Guess the Output — Throttle Timing

throttle-timing.js
const log = throttle(() => console.log("tick"), 1000);

log(); // "tick" — runs immediately
log(); // ignored — still within the 1000ms window
log(); // ignored — still within the 1000ms window
// after 1000ms passes, the next call to log() will run again
✅ Throttle guarantees at most one execution per interval — extra calls inside that window are simply dropped, not queued or delayed.
Currying: one argument at a time · Partial application: pre-fill some arguments, call with the rest · Composition: chain small functions into a pipeline (pipe left-to-right, compose right-to-left) · Memoization: cache results of pure functions to skip repeated work · Debounce: wait for a pause before running · Throttle: run at most once per interval, no matter the pause.
