Event Loop ⭐⭐⭐⭐⭐

JavaScript is single-threaded but never blocks — the Event Loop is the mechanism that makes async code, timers, and network calls possible.

Why This Matters Core Concept

JavaScript runs on a single thread — it can only do one thing at a time. Yet it handles timers, network requests, and user clicks without freezing the page. The Event Loop, working together with the Call Stack, Web APIs, and two task queues, is what makes that possible.

Interview Definition: The Event Loop is the mechanism that continuously checks whether the Call Stack is empty, and if so, moves pending callbacks from the Microtask Queue (first) and Macrotask Queue (second) onto the stack for execution.
1. Event Loop
The Mechanism Itself ⭐⭐⭐⭐⭐

The Event Loop continuously checks whether the Call Stack is empty. If it is, it pulls the next pending task from the Microtask Queue or Macrotask Queue and pushes it onto the Call Stack for execution. Without it, JavaScript couldn't run asynchronous operations like API calls, timers, or DOM events.

event-loop-example.js
console.log("Start");

setTimeout(() => {
    console.log("Timer");
}, 1000);

console.log("End");
Output: Start → End → Timer

The timer callback is handled outside the Call Stack by a Web API. The Event Loop only pushes it back onto the stack once the stack is empty — which is why "End" logs before "Timer", even though the timer was scheduled first.

2. Call Stack
Where Synchronous Code Runs

The Call Stack is a LIFO (Last In, First Out) structure that tracks function execution. Every function call is pushed on; once it returns, it's popped off.

call-stack.js
function one() {
    two();
}

function two() {
    console.log("Hello");
}

one();

Stack Overflow: Infinite recursion fills the Call Stack until it runs out of space.

    test();
}

// RangeError: Maximum call stack size exceeded
Why "single-threaded": JavaScript has exactly one Call Stack, so it can only execute one piece of code at a time — that's what people mean when they call JS single-threaded.
3. Web APIs
Provided by the Browser, Not JavaScript

Web APIs are features the browser (or Node.js runtime) provides to do asynchronous work outside the Call Stack. JavaScript itself doesn't know how to set a timer or make a network request — the environment around it does.

4. Callback Queue (Task Queue)
Where Timer & Event Callbacks Wait

The Callback Queue (also called the Task Queue) stores callbacks from completed asynchronous operations, such as setTimeout(), setInterval(), and DOM Events. The Event Loop only moves these to the Call Stack once the stack is empty and the Microtask Queue has been fully drained.

callback-queue.js
setTimeout(() => {
    console.log("Hello");
}, 0);
Even with a 0ms delay, the callback still waits in the queue until the Call Stack becomes completely empty — it never jumps the line.
Terminology note: "Callback Queue" and "Macrotask Queue" refer to essentially the same queue — most modern explanations use "Macrotask Queue" to contrast it directly with the Microtask Queue.

6. Macrotask Queue
Lower Priority Queue

The Macrotask Queue stores lower-priority async tasks. The Event Loop processes exactly one macrotask per cycle, and only after both the Call Stack and the Microtask Queue are completely empty.

One at a time: After each single macrotask runs, the Event Loop checks the Microtask Queue again before running the next macrotask — new microtasks always cut in line ahead of the next macrotask.

8. setTimeout()
Delay ≠ Guarantee

setTimeout() schedules a callback to run after at least the given delay — never exactly at it. Actual execution also depends on whether the Call Stack is free and the Microtask Queue is empty.

setTimeout(0) — still not immediate

Even with a 0ms delay, the callback still waits until all synchronous code and every pending microtask has finished.

9. Promise Execution Order
Why Promises Beat Timers ⭐⭐⭐⭐⭐

Promise callbacks (.then(), .catch(), .finally()) go into the Microtask Queue, so they always run before anything in the Macrotask Queue — regardless of which was scheduled first.

Example 1 — Basic ordering

promise-example1.js
console.log("Start");

setTimeout(() => {
    console.log("Timer");
}, 0);

Promise.resolve().then(() => {
    console.log("Promise");
});

console.log("End");
Output: Start → End → Promise → Timer

Example 2 — Multiple microtasks before the macrotask

promise-example2.js
console.log(1);

Promise.resolve().then(() => {
    console.log(2);
});

Promise.resolve().then(() => {
    console.log(3);
});

setTimeout(() => {
    console.log(4);
}, 0);

console.log(5);
Output: 1 → 5 → 2 → 3 → 4

Both .then() callbacks are microtasks, so they both run before the single macrotask (the timer), no matter how many there are.

Example 3 — Nested microtasks

promise-example3.js
console.log("Start");

Promise.resolve().then(() => {
    console.log("A");

    Promise.resolve().then(() => {
        console.log("B");
    });
});

setTimeout(() => {
    console.log("Timer");
}, 0);

console.log("End");
Output: Start → End → A → B → Timer
Key insight: Even a microtask created while draining the Microtask Queue (like "B" here) still runs before the next macrotask. The Event Loop keeps draining microtasks until there truly are none left — a macrotask never cuts in early.

Rule to remember: Synchronous code always runs first → then all Microtasks → then one Macrotask → repeat. This is the foundation of JavaScript's asynchronous behavior and one of the most frequently tested topics in interviews.
10. Interview Questions & Answers
Event Loop ⭐⭐⭐⭐⭐

Q: What is the Event Loop?
A: A mechanism that continuously checks whether the Call Stack is empty, and if so, moves the next pending callback from the Microtask Queue (first) or Macrotask Queue (second) onto the Call Stack to run.

Q: Why is the Event Loop needed?
A: JavaScript has only one Call Stack and can't block waiting for slow operations like timers or network calls. The Event Loop lets those operations run elsewhere and rejoin execution later, without freezing the page.

Q: How does JavaScript handle asynchronous code?
A: It hands the async work off to Web APIs (browser/runtime features), which do the waiting outside the Call Stack. When the work completes, the callback is placed in a queue, and the Event Loop pushes it onto the Call Stack once the stack is empty.

Q: Does JavaScript have multiple threads?
A: The JavaScript engine itself runs on a single thread with one Call Stack. However, the surrounding environment (browser or Node.js) uses separate background threads for things like timers and network I/O — JS just never runs your code on more than one thread at once.

Q: When does the Event Loop move tasks to the Call Stack?
A: Only when the Call Stack is completely empty. It always drains the entire Microtask Queue first, then takes exactly one task from the Macrotask Queue, then repeats.

Call Stack

Q: What is the Call Stack?
A: A LIFO (Last In, First Out) data structure that tracks function execution — each function call is pushed on when invoked and popped off when it returns.

Q: Why is JavaScript called single-threaded?
A: Because it has exactly one Call Stack, meaning it can only execute one piece of code at a time — there's no parallel execution of JS code itself.

Q: What causes Stack Overflow?
A: Uncontrolled or infinite recursion — each recursive call pushes a new frame onto the stack, and once it exceeds the engine's stack size limit, it throws RangeError: Maximum call stack size exceeded.

Q: Explain Call Stack execution.
A: When a function is called, a new frame is pushed on top of the stack. When that function calls another, another frame is pushed. As each function finishes and returns, its frame is popped off, until the stack is empty again.

Web APIs

Q: What are Web APIs?
A: Features provided by the browser (or Node.js runtime) — like timers, fetch(), and DOM events — that perform work outside the JavaScript engine's Call Stack.

Q: Are Web APIs part of JavaScript?
A: No. They belong to the host environment (browser or Node.js), not the JavaScript language specification itself. That's why the same JS engine behaves differently in a browser vs. Node.

Q: Name some browser Web APIs.
A: setTimeout(), setInterval(), fetch(), DOM Events, Geolocation, localStorage, and XMLHttpRequest.

Q: Where does setTimeout execute?
A: The timer itself is handled by the browser's Web API (not the JS engine). Once the delay elapses, the browser places the callback into the Macrotask Queue — the JS engine only executes it once the Event Loop pushes it onto the Call Stack.

Callback Queue

Q: What is the Callback Queue?
A: A queue that holds callbacks from completed asynchronous operations — such as setTimeout(), setInterval(), and DOM events — waiting for their turn on the Call Stack.

Q: Who places callbacks into the Callback Queue?
A: The Web APIs. Once a timer finishes counting down or an event fires, the browser places the associated callback into this queue.

Q: When are callbacks executed?
A: Only when the Call Stack is empty and the entire Microtask Queue has already been drained — the Callback (Macrotask) Queue always waits its turn behind microtasks.

Microtask Queue ⭐⭐⭐⭐⭐

Q: What is the Microtask Queue?
A: The highest-priority queue in the Event Loop system — it holds Promise callbacks and similar tasks, and is fully emptied before any macrotask is allowed to run.

Q: Why do Promises execute before setTimeout?
A: Because Promise callbacks go into the Microtask Queue, while setTimeout callbacks go into the Macrotask Queue — and the Event Loop always finishes all microtasks before it even looks at the macrotask queue, regardless of scheduling order.

Q: What goes into the Microtask Queue?
A: Promise.then(), .catch(), .finally() callbacks, calls to queueMicrotask(), and MutationObserver callbacks.

Macrotask Queue

Q: What is the Macrotask Queue?
A: A lower-priority queue that holds tasks like timers and DOM events — processed one at a time, only after the Call Stack and Microtask Queue are both empty.

Q: Which APIs create macrotasks?
A: setTimeout(), setInterval(), DOM Events, MessageChannel, and postMessage.

Q: When is a macrotask executed?
A: After the Call Stack is empty and every pending microtask (including any created while draining) has finished running. The Event Loop then executes exactly one macrotask before checking microtasks again.

Event Loop Flow ⭐⭐⭐⭐⭐

Q: Explain the complete Event Loop flow.
A: Synchronous code runs first on the Call Stack. Any async operations are handed to Web APIs. When they complete, Promise callbacks go into the Microtask Queue and timer/event callbacks go into the Macrotask Queue. The Event Loop waits for the Call Stack to empty, then drains the entire Microtask Queue, then runs one macrotask, then repeats the cycle.

Q: What is the execution order of synchronous, microtask, and macrotask code?
A: Synchronous code always runs first, then all microtasks (fully drained, including new ones added during the drain), then exactly one macrotask — then the cycle repeats.

Q: How does JavaScript execute asynchronous operations internally?
A: It doesn't — the JS engine itself is synchronous. The surrounding environment (Web APIs) does the actual waiting, and hands a callback back to JS through the queues and Event Loop once the work is done.

setTimeout()

Q: Does setTimeout(0) execute immediately?
A: No. It's still placed in the Macrotask Queue and must wait for all synchronous code and every pending microtask to finish first — "0ms" only means "as soon as possible after that," not "instantly."

Q: Is the timeout delay guaranteed?
A: No. The delay is a minimum, not a guarantee — actual execution can be pushed later depending on what else is on the Call Stack or in the Microtask Queue at the time.

Q: Why can setTimeout() be delayed?
A: Because JavaScript is single-threaded — if the Call Stack is busy running other synchronous code, or the Microtask Queue still has pending work, the timer callback simply has to wait its turn.

Promise Execution Order ⭐⭐⭐⭐⭐

Q: Why do Promises execute before setTimeout()?
A: Promise callbacks are microtasks, and the Microtask Queue is always fully drained before the Event Loop processes anything from the Macrotask Queue (where setTimeout callbacks live) — even if the timeout was scheduled first or with a 0ms delay.

Q: What is the execution order of synchronous code, Promises, and timers?
A: Synchronous code first, then all Promise (microtask) callbacks, then timer (macrotask) callbacks.

Q: What queue do Promise callbacks use?
A: The Microtask Queue.

Q: Can a Promise callback interrupt synchronous code?
A: No. A Promise callback can only run once the Call Stack is completely empty — it always waits for all currently running synchronous code to finish first.

Q: How are nested Promise callbacks executed?
A: Any new microtask created while the Microtask Queue is being drained (like a .then() scheduled inside another .then()) is still executed before the Event Loop moves on to the next macrotask — the queue is drained until it's truly empty, however many new microtasks appear along the way.

12. More Interview Questions
Conceptual Questions ⭐⭐⭐⭐⭐

Q: Why does Promise.then() execute before setTimeout(fn, 0)?
A: .then() callbacks go into the Microtask Queue, which the Event Loop always drains completely before it looks at the Macrotask Queue (where setTimeout callbacks live) — even a 0ms delay doesn't change this priority.

Q: What happens if both the Microtask Queue and Macrotask Queue contain pending tasks?
A: The Event Loop always finishes every microtask first — including any new ones added while draining — before it takes exactly one task from the Macrotask Queue. It then re-checks the Microtask Queue again before touching the next macrotask.

Q: What happens when the Call Stack never becomes empty?
A: The Event Loop can never push anything from either queue onto the stack, so all pending timers, Promise callbacks, and event handlers stay stuck waiting indefinitely. This is what causes a frozen/unresponsive page — an infinite loop or long synchronous task blocks everything else.

Q: Why is setTimeout(fn, 0) not executed immediately?
A: It's still placed in the Macrotask Queue, so it must wait for the current synchronous code and the entire Microtask Queue to finish first. Browsers also enforce a small minimum delay in some cases, but the main reason is simply queue priority, not the 0ms value itself.

Q: How does the Event Loop prevent the UI from freezing during asynchronous operations?
A: Long-running work (network calls, timers) is offloaded to Web APIs running outside the main thread. The main thread only picks up short callback executions when it's free, letting rendering and user input get interleaved between tasks instead of being blocked for the entire duration of the async operation.

Q: Explain the complete lifecycle of an asynchronous operation from function call to callback execution.
A: The function call triggers a Web API (e.g. a timer or network request). The Web API performs the work outside the Call Stack. Once finished, it places the callback into the Microtask or Macrotask Queue depending on the API. The Event Loop waits until the Call Stack is empty, drains all microtasks, then executes the callback (if it's a macrotask, one per cycle) by pushing it onto the Call Stack.

Q: How does await affect the Event Loop?
A: await pauses the async function at that point and immediately hands control back to whatever called it, letting synchronous code continue running. The code after await is scheduled to resume as a microtask once the awaited Promise settles — so it runs after current synchronous code, but before any macrotasks.
