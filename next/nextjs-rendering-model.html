🖥️ 1. Server Components vs Client Components
Server Components (Default) & Client Components ("use client")
By default, all components in the app/ folder are React Server Components. Add the "use client" directive at the very top of a file to opt-in to Client-side execution.

Server Components Characteristics

  • Runs exclusively on the server (no browser context access like window or localStorage).
  • Can directly fetch data asynchronously inside the component using async/await.
  • Generates zero client-side JavaScript, resulting in lighter page load footprints and better SEO.
  • Cannot use interactive hooks like useState or useEffect.

Default Server Component Example

app/products/page.js 
export default async function Products() {
  // This fetch happens entirely on the server during request execution
  const res = await fetch("https://dummyjson.com/products");
  const data = await res.json();

  return (
    <>
      <h1>Products</h1>
      {data.products.map((item) => (
        <p key={item.id}>{item.title}</p>
      ))}
    </>
  );
}

Client Components Characteristics

  • Runs in the browser environment (after hydration) but is pre-rendered on the server first.
  • Full support for state hooks, lifecycle hooks, and local event listeners.
  • Increases client-side bundle size due to carrying hydrated interactivity code.

Client Component Example

app/components/Counter.jsx 
"use client";

import { useState } from "react";

export default function Counter() {
  const [count, setCount] = useState(0);

  return (
    <>
      <h2>{count}</h2>
      <button onClick={() => setCount(count + 1)}>
        Increment
      </button>
    </>
  );
}

Mixing Server and Client Components

A Server Component can render and import Client Components seamlessly, acting as a dynamic parent container shell.

app/page.js (Server Component Container) 
import Counter from "./Counter";

export default function Home() {
  return (
    <>
      <h1>Home Page</h1>
      {/* Server component directly passes control to dynamic interactive boundaries */}
      <Counter />
    </>
  );
}
🚀 2. Rendering Strategies (SSR, SSG, ISR, CSR)
Dynamic Rendering & Static Site Strategies

A. SSR (Server-Side Rendering / Dynamic Rendering)

The page compiles HTML on demand for every incoming client request. Perfect for live data sources, user profiles, or dashboard interfaces.

SSR Route Implementation 
export const dynamic = "force-dynamic";

export default async function Users() {
  const res = await fetch("https://dummyjson.com/users", {
    cache: "no-store", // Instructs engine to bypass standard cache layers
  });
  const data = await res.json();

  return (
    <>
      {data.users.map(user => (
        <p key={user.id}>{user.firstName}</p>
      ))}
    </>
  );
}

B. SSG (Static Site Generation)

HTML is built once at deploy time. If standard data calls are fetch-cacheable, Next.js generates static assets by default. Excellent for documentation, blogs, or product marketing landing sites.

SSG Route Implementation 
export default async function Blog() {
  const res = await fetch("https://dummyjson.com/posts"); // Cached by default
  const data = await res.json();

  return (
    <>
      {data.posts.map(post => (
        <p key={post.id}>{post.title}</p>
      ))}
    </>
  );
}

C. ISR (Incremental Static Regeneration)

The static page rebuilds incrementally in the background after a set period of seconds when a new visit hits the server.

ISR Route Implementation 
export const revalidate = 60; // Re-evaluates target data cache after 60 seconds max

export default async function StoreFront() {
  const res = await fetch("https://dummyjson.com/products");
  const data = await res.json();

  return (
    <>
      {data.products.map(product => (
        <p key={product.id}>{product.title}</p>
      ))}
    </>
  );
}

D. CSR (Client-Side Rendering)

A blank shell page is served immediately. The client's browser downloads, compiles JavaScript files, and performs API fetching queries post-hydration.

CSR Route Implementation 
"use client";

import { useEffect, useState } from "react";

export default function ClientDashboard() {
  const [products, setProducts] = useState([]);

  useEffect(() => {
    fetch("https://dummyjson.com/products")
      .then(res => res.json())
      .then(data => setProducts(data.products));
  }, []);

  return (
    <>
      {products.map(product => (
        <p key={product.id}>{product.title}</p>
      ))}
    </>
  );
}

Rendering Configuration Strategy Lookup

Configuration Setting Matched Strategy Result Target Fetch Behavior
Default setup / fetch caches SSG Static generation during workspace build time
{ cache: "no-store" } SSR Performs fresh network load on every visit
export const revalidate = 60 ISR Regenerates cache boundaries after specified seconds
"use client" + useEffect() CSR Loads base shell and queries APIs directly in browser
export const dynamic = "force-dynamic" SSR Forces path routing to render per client request
🌊 3. Streaming SSR with <Suspense>
Progressive HTML Delivery and Component Loading States
Streaming permits Next.js to compile pages into separate chunks. Instantly send down static frames, while resolving dynamic server-side fetches inside loading placeholders.

Implementation Blueprint

app/page.js 
import { Suspense } from "react";
import ProductList from "./ProductList";

export default function StorePage() {
  return (
    <>
      <h1>Storefront Catalogue</h1>
      {/* Renders the fallback block instantly while ProductList loads */}
      <Suspense fallback={<p>Loading Products...</p>}>
        <ProductList />
      </Suspense>
    </>
  );
}
app/ProductList.js 
export default async function ProductList() {
  const res = await fetch("https://dummyjson.com/products");
  const data = await res.json();

  return (
    <>
      {data.products.map(product => (
        <p key={product.id}>{product.title}</p>
      ))}
    </>
  );
}
Why use Streaming SSR? Users see structural layout shells (navigation headers, sidebars) immediately, dramatically improving core Web Vitals like First Contentful Paint (FCP) and Largest Contentful Paint (LCP).
⚡ 4. Partial Pre-rendering (PPR)
Static Page Shells with Dynamic Streaming Holes

Partial Pre-rendering (PPR) lets Next.js pre-render static HTML structures while embedding dynamic React Suspense zones that stream personalized user details or dynamic database items on the fly.

Partial Pre-rendering Setup

app/page.js 
import { Suspense } from "react";
import LatestOrders from "./LatestOrders";

export default function Home() {
  return (
    <>
      {/* Static Shell Elements generated at build time */}
      <header>Navbar</header>
      <section>
        <h1>Welcome Back!</h1>
      </section>

      {/* Dynamic order stream placeholder */}
      <Suspense fallback={<p>Loading Orders...</p>}>
        <LatestOrders />
      </Suspense>
    </>
  );
}
app/LatestOrders.js 
export default async function LatestOrders() {
  // Dynamic database fetch bypasses standard SSG build time
  const res = await fetch("https://dummyjson.com/carts", {
    cache: "no-store",
  });
  const data = await res.json();

  return (
    <>
      {data.carts.map(cart => (
        <p key={cart.id}>Order #{cart.id}</p>
      ))}
    </>
  );
}
🎓 5. Rendering Model Interview Cheat Sheet
Quick Review Definitions for Next.js Architectural Questions
Architecture Feature How it works Optimal Use Case
Server Component Default server runtime; zero client bundle JS Direct database queries, static pages, heavy logic libraries
Client Component Requires "use client"; hydrates in browser Dynamic form states, local click event listeners, browser API use
SSR Fetches data and generates markup per request Stock price feeds, real-time live tickers, user feed lists
SSG Creates static static assets at compilation time Static homepage shells, blog directories, standard documentation
ISR Updates cached static assets background dynamically Product catalogs, high-frequency article listings, pricing tiers
CSR Hydrates static page and initiates UI data calls on client Interacted Search filters, dashboards behind security wall gates
Streaming SSR Delivers progressive parts of UI elements via Suspense Long, multi-database query views, massive interactive web platforms
PPR Merges static template shells with fast streamed dynamic views Ecommerce product paths (constant static info with custom customer info)
