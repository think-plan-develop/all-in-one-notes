The Kubernetes Core Four

For a backend developer, these four concepts give you everything you need to actually run and reach an application in Kubernetes.

Namespace YAML Deployment Service The Big Picture
1. Namespace
💬 A Namespace is a logical separation inside a Kubernetes cluster.
Kubernetes Cluster │ ├── development │ ├── backend │ ├── frontend │ └── redis │ ├── testing │ ├── backend │ └── redis │ └── production ├── backend └── redis

Instead of dumping everything into one big space, you separate resources by namespace.

Why use it?

namespace: dev backend redis namespace: test backend redis namespace: prod backend redis

The backend in dev and the backend in prod can share the exact same name, because they live in different namespaces — no collision.

namespace commands
# create it
kubectl create namespace dev

# check it exists
kubectl get namespaces

# create a Pod inside it
kubectl run backend --image=nginx --namespace=dev

# see Pods scoped to that namespace
kubectl get pods -n dev

Commands worth knowing

kubectl get nsList all namespaces
kubectl get pods -n devList Pods scoped to one namespace
kubectl get all -n devList everything in that namespace
kubectl delete namespace devDelete the namespace and everything inside it
✅ Backend developer takeaway: you don't need to be a namespace administration expert. Just know: Namespace = logical environment/group for Kubernetes resources.
2. YAML

Kubernetes resources are normally defined using YAML files — this is the most important skill on this list.

apiVersion: v1
kind: Pod

metadata:
  name: backend

spec:
  containers:
    - name: backend
      image: nginx
      ports:
        - containerPort: 80
apply
kubectl apply -f backend.yaml

Kubernetes reads the YAML file and creates whatever resource it describes.

The basic structure, every time

apiVersionWhich API version you're using — e.g. apps/v1
kindWhat resource you're creating — Deployment, Service, etc.
metadataInfo about the resource — name, namespace
specThe desired configuration — e.g. replicas: 2
💡 Desired State: Kubernetes is declarative. You don't say "create Pod 1, then create Pod 2." You write replicas: 2, and Kubernetes continuously works to keep that state true — no matter what happens to individual Pods along the way.
3. Deployment

For a backend app, you'll almost always use a Deployment rather than creating Pods by hand.

Deployment │ ▼ ReplicaSet │ ▼ Pods │ ▼ Container │ ▼ Your Node.js application
apiVersion: apps/v1
kind: Deployment

metadata:
  name: backend

spec:
  replicas: 2

  selector:
    matchLabels:
      app: backend

  template:
    metadata:
      labels:
        app: backend

    spec:
      containers:
        - name: backend
          image: my-backend:1.0
          ports:
            - containerPort: 3000
apply + check
kubectl apply -f deployment.yaml
kubectl get deployments
kubectl get pods

Why Deployment instead of a bare Pod?

Deployment
│
Pod ✅ Pod ❌
↓ Kubernetes notices and reconciles
Pod ✅ Pod ✅ (new)

If a Pod disappears — crash, node failure, anything — the Deployment (via its ReplicaSet) notices the mismatch against replicas: 2 and creates a replacement automatically. You never handle that manually.

Deployments also drive controlled, zero-downtime updates:

backend:1.0 ↓ rolling update ↓ backend:2.0
⚠️ Don't confuse the chain: Deployment → ReplicaSet → Pod → Container. A Deployment manages ReplicaSets; the ReplicaSet is what actually maintains the desired Pod count.
4. Service

Extremely important for backend work: a Pod's IP address is not something you should ever rely on directly.

backend Pod IP = 10.244.0.5 Pod gets deleted. New Pod: backend Pod IP = 10.244.0.9

So how does another app reliably reach your backend when its IP keeps changing? A Service gives you a stable network endpoint that doesn't change, no matter what happens underneath it.

Service — backend-service
┌─────────┴─────────┐
Pod 1 — 10.244.0.5 Pod 2 — 10.244.0.9

Your frontend never needs to know either Pod IP — it just talks to backend-service.

apiVersion: v1
kind: Service

metadata:
  name: backend-service

spec:
  selector:
    app: backend

  ports:
    - port: 80
      targetPort: 3000
💡 The selector: app: backend here is exactly what links this Service to your Deployment's labels: app: backend. That match is how the Service finds which Pods to send traffic to — Services never hard-code Pod names or IPs, only label selectors.
PieceRole
selectorWhich Pods (by label) this Service sends traffic to
portThe port other things use to reach this Service
targetPortThe port your container actually listens on inside the Pod
The Most Important Picture

As a backend developer, this is the architecture worth holding in your head:

Kubernetes Cluster │ Namespace │ backend namespace │ Deployment │ ReplicaSet │ ┌──────────┴──────────┐ ↓ ↓ Pod 1 Pod 2 │ │ Node.js app Node.js app ↑ ↑ └─────────┬───────────┘ │ Service │ ↓ Other application
✅ Namespace groups it. YAML defines it. Deployment keeps it running. Service makes it reachable. That's the full loop for shipping a backend app to Kubernetes.
