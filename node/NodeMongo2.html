🗄 Database Connection
🔌 src/config/db.ts — MongoDB Connection with Logging
🟣 What to log on connect? Log the DB host and DB name so you instantly know which database you're connected to — critical when switching between dev/staging/prod.
src/config/db.ts
import mongoose from 'mongoose'

export const connectDB = async (): Promise<void> => {
  try {
    const conn = await mongoose.connect(process.env.MONGO_URI as string)

    // ✅ Log host + DB name on successful connection
    console.log(`✅ MongoDB Connected`)
    console.log(`   Host : ${conn.connection.host}`)
    console.log(`   DB   : ${conn.connection.name}`)
    console.log(`   Port : ${conn.connection.port}`)

  } catch (err: any) {
    console.error(`❌ MongoDB Connection Failed: ${err.message}`)
    process.exit(1) // stop server if DB fails
  }
}
✅ What you see in terminal when server starts:
✅ MongoDB Connected
   Host : localhost
   DB   : mydb
   Port : 27017
💡 process.exit(1) — if MongoDB fails to connect, crash the server immediately. Do NOT let it silently start without a DB — every request would fail anyway.
🟢 conn.connection.host — the server address
Dev: localhost
Prod: cluster0.xyz.mongodb.net
🩷 conn.connection.name — the database name
Comes from your MONGO_URI: mongodb://localhost:27017/mydb

🚀 src/server.ts — Entry Point
src/server.ts
import dotenv from 'dotenv'
dotenv.config()  // ← load .env FIRST before anything else

import app from './app'
import { connectDB } from './config/db'

const PORT = Number(process.env.PORT) || 3000

const start = async () => {
  await connectDB()          // connect DB first
  app.listen(PORT, () => {
    console.log(`🚀 Server running on http://localhost:${PORT}`)
  })
}

🎮 Controller Layer
src/controllers/user.controller.ts
import { Request, Response } from 'express'
import { getAllUsers, createUser } from '../services/user.service'

export const fetchUsers = async (
  req: Request, res: Response
) => {
  const users = await getAllUsers()
  res.json(users)
}

export const addUser = async (
  req: Request, res: Response
) => {
  const user = await createUser(req.body)
  res.status(201).json(user)
}

⚡ Complete Request Lifecycle
🔄 GET /api/users — End to End Flow
Frontend / Postman ↓ GET /api/users Express Middleware (helmet, cors, morgan, json) ↓ Route → userRouter.get('/') ↓ Controller → fetchUsers(req, res) ↓ Service → getAllUsers() ↓ Model → User.find() ↓ Mongoose → builds MongoDB query ↓ MongoDB → returns documents ↓ (back up the chain) Service returns data to Controller ↓ Controller sends res.json(users) ↓ Frontend / Postman receives JSON ✅
✅ Key point: Controller never touches the DB directly. It always goes through Service → Model → Mongoose → MongoDB. This separation makes code testable and reusable.
🎯 Interview Questions & Answers
💬 Must-Know Questions
Q01 What is Mongoose and why use it over the native MongoDB driver?
Mongoose is an ODM (Object Document Mapper) — it sits between your Node.js code and MongoDB, adding a schema layer on top of the schema-less MongoDB.

Native driver: raw queries, no validation, no structure
Mongoose adds: schema definition, data validation, type casting, middleware (pre/post hooks), virtuals, and clean query API like User.find()
Your Code ↓ Mongoose (schema, validation, hooks) ↓ MongoDB Driver ↓ MongoDB
Q02 Why do we call dotenv.config() before importing app.ts in server.ts?
Node.js loads and executes imports at the top of the file before any other code runs. If you import app.ts first and it references process.env.MONGO_URI, those values will be undefined because dotenv hasn't loaded yet.

Wrong order:
import app ← app.ts runs, reads process.env → undefined ❌ dotenv.config() ← too late
Correct order:
dotenv.config() ← loads .env into process.env first ✅ import app ← now process.env values are available
Q03 Why separate app.ts and server.ts?
app.ts creates and configures the Express app (middleware, routes) but doesn't start listening.
server.ts is the entry point — connects DB and starts the server.

Why split? Testing — in tests you can import app without starting the real server or connecting to the real DB. You just call supertest(app) directly.
app.ts → just Express config, no listen() call server.ts → connects DB + calls app.listen(PORT)
Q04 Why use a Service layer? Can't the Controller just query the DB directly?
Technically yes, but it's bad practice. The Service layer exists for:

1. Separation of concerns — Controller handles HTTP (req/res), Service handles business logic
2. Reusability — multiple controllers or cron jobs can call the same service function
3. Testability — you can unit test service functions without HTTP layer
4. Maintainability — if DB query changes, only service changes, not every controller
Controller → handles req/res only Service → handles DB queries + business logic Model → defines schema + provides DB methods
Q05 What does conn.connection.host and conn.connection.name give you?
After await mongoose.connect(uri), the returned conn object has a connection property with details about the active DB connection:

conn.connection.host — the server address (localhost in dev, Atlas cluster URL in prod)
conn.connection.name — the database name (parsed from the URI, e.g. mydb)
conn.connection.port — the port number (27017 by default)

Logging these on startup lets you instantly verify which DB environment is connected — prevents accidental dev code running against prod DB.
MONGO_URI = mongodb://localhost:27017/mydb ↑host ↑port ↑name conn.connection.host → localhost conn.connection.port → 27017 conn.connection.name → mydb

Q07 What does helmet and cors middleware actually do?
helmet() — sets secure HTTP response headers automatically. Protects against XSS, clickjacking, MIME sniffing etc. One line replaces ~11 manual header settings.

cors() — browsers block cross-origin requests by default (e.g. React on port 5173 calling API on port 3000). CORS middleware adds the Access-Control-Allow-Origin header to tell browsers the request is allowed.
Without cors(): React → API ← browser blocks it ❌ With cors(): React → API ← allowed ✅
Q08 Why call process.exit(1) if MongoDB fails to connect?
If MongoDB fails to connect and you let the server start anyway, every single incoming request will fail with a DB error. The server would be running but completely broken — silently.

process.exit(1) crashes the server immediately with a non-zero exit code (1 = error). This:
• Tells your process manager (PM2, Docker, K8s) the app failed
• Triggers automatic restart logic
• Makes the failure loud and obvious, not silent
DB connect fails ↓ process.exit(1) ← crash loudly ✅ ↓ PM2 / Docker sees exit code 1 ↓ Auto-restarts the process
Q09 What does tsc actually do?
tsc is the TypeScript Compiler. Node.js can only run .js files — not .ts. Running tsc compiles all your TypeScript source files into plain JavaScript inside the dist/ folder.

In development you use tsx which does this on-the-fly without a build step. In production you pre-compile with tsc first, then run the output with node dist/server.js — faster and zero TypeScript overhead at runtime.
Development: tsx watch src/server.ts ← compiles in memory, no dist/ Production: tsc ← writes dist/server.js to disk node dist/server.js ← runs pure JavaScript ✅
Q10 Why use path.resolve(__dirname, '../.env') in dotenv?
After tsc builds your project, the compiled code runs from dist/server.js — so __dirname points to /project/dist. But your .env files live at /project/ (one level up). The ../ goes up one directory to reach the project root.

Without this, dotenv looks for the file in the wrong place, finds nothing, and all your environment variables are silently undefined.
Running: node dist/server.js __dirname = /project/dist dotenv.config({ path: '.env' }) ← looks in /project/dist/.env ❌ dotenv.config({ path: '../.env' }) ← looks in /project/.env ✅ dotenv.config({ path: path.resolve(__dirname, '../.env') }) ← safest ✅
Q11 What is prestart and how does it differ from build?
"build": "tsc" must be run manually with npm run build.

"prestart": "tsc" runs automatically every time you run npm start — npm lifecycle hooks trigger pre<script> before <script>. So npm start compiles TypeScript first, then starts the server. You never need to remember to build manually before deploying.
"scripts": { "prestart": "tsc", ← runs automatically before start "start": "node dist/server.js", "dev": "tsx watch src/server.ts" } npm start → tsc runs first → node dist/server.js ✅ npm run dev → tsx watch (no build needed) ✅
Q12 Difference between dependencies and devDependencies?
dependencies — packages the app needs at runtime in production (express, mongoose, dotenv). Always installed.

devDependencies (installed with -D) — packages only needed during development or build time (typescript, tsx, @types/*). Skipped when you deploy with npm ci --omit=dev. This keeps your Docker image lean and reduces attack surface.
PackageTypeNeeded in prod?
express, mongoose, dotenvdependenciesYes
tsx, typescript, @types/*devDependenciesNo
Q13 Why process.exit(1) instead of just throwing an error?
In an async startup function, a thrown error can be silently swallowed if there's no outer try/catch wrapping the call. process.exit(1) guarantees the process terminates with exit code 1 — the universal signal for "something failed".

Docker, PM2, Kubernetes, and systemd all watch exit codes to decide whether to restart and fire alerts.
throw new Error(...) ← may be swallowed silently in async context ❌ process.exit(1) ← guaranteed hard stop, exit code 1 seen by PM2/Docker ✅
Q14 What is maxPoolSize in mongoose.connect?
MongoDB uses a connection pool — a set of persistent connections reused across requests, rather than opening and closing a new connection per query. maxPoolSize: 10 means at most 10 simultaneous DB connections.

For low-traffic apps the default (5) is fine. Increase for high-traffic APIs, but don't exceed your MongoDB Atlas tier's connection limit — free tier allows 500 total connections.
await mongoose.connect(MONGO_URI, { maxPoolSize: 10, ← up to 10 concurrent DB connections serverSelectionTimeoutMS: 5000, ← fail fast if Atlas unreachable socketTimeoutMS: 45000 ← close idle socket after 45s })
Q15 findByIdAndUpdate vs updateOne — when to use which?
Use findByIdAndUpdate(id, data, { new: true }) when your REST API needs to return the updated resource to the client — the { new: true } option returns the document after the update, not before.

Use updateOne({ _id: id }, data) when you only care whether the update succeeded (returns { matchedCount, modifiedCount }, not the document). Slightly faster since it skips fetching the full document.
MethodReturnsUse when
findByIdAndUpdate(..., { new: true })Updated documentREST API needs to return updated resource
updateOne(){ matchedCount, modifiedCount }Fire-and-forget update, no return needed
Q16 What is SIGTERM vs SIGINT and why handle them?
SIGINT — sent when you press Ctrl+C in the terminal. Used during local development.
SIGTERM — sent by Docker (docker stop), Kubernetes, PM2, or systemd when they want to gracefully shut down your process. You get a short window (10–30s) to finish in-flight requests before a hard kill.

Handling both ensures your HTTP server stops accepting new connections, active requests finish, and the MongoDB connection closes cleanly — no data corruption.
process.on('SIGTERM', async () => { await mongoose.connection.close() ← close DB cleanly server.close(() => process.exit(0)) ← stop HTTP server, exit 0 = success }) process.on('SIGINT', async () => { await mongoose.connection.close() process.exit(0) })
Q17 Why does morgan log only in development?
In production, logging every HTTP request to stdout is noisy, wastes resources, and can leak sensitive path/query information into logs. Production apps use dedicated log aggregators (Datadog, CloudWatch, Loki) with structured JSON logging instead of morgan's plain text output.

Keeping morgan dev-only keeps production logs clean and intentional.
// app.ts — only enable morgan in dev if (process.env.NODE_ENV === 'development') { app.use(morgan('dev')) // ← dev only ✅ } // production: use a structured logger like winston or pino instead
💡 morgan('dev') output: GET /api/users 200 5.234 ms — great for dev, too noisy for prod.
Q18 What does conn.connection.readyState tell you?
After connecting, mongoose.connection.readyState is a number representing the current connection state. Useful for health-check endpoints.
