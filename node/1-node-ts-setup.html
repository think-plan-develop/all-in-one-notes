Old Way (ts-node + nodemon) vs New Way (tsx) — install commands, scripts, dev/build flows, dependencies, and interview Q&A · 2026 Edition

📌 In short: Node.js can't run TypeScript directly, so development needs a tool that strips or compiles types on the fly. The old way pairs ts-node (compiles) with nodemon (watches) — two packages, and ts-node is now stale. The new way uses tsx, a single actively-maintained package powered by esbuild that does both jobs, 10–100× faster. Production is identical either way: tsc compiles to dist/, then plain node runs it.
🔑 Key Terms at a Glance
🛠️
tsc: The TypeScript compiler — converts .ts files to real .js files on disk. Used for production builds.
🐢
ts-node: Compiles TypeScript in memory and runs it immediately — dev-only, archived/stale as of Dec 2025.
⚡
tsx: Runs + watches TypeScript using esbuild. Replaces ts-node + nodemon in one actively-maintained package.
📦
@types/*: Community-maintained .d.ts type declarations for JS packages (like Express, Node built-ins) that ship no types of their own.
Old Way — ts-node + nodemon

Status & Install Commands

⚠️ Archived — No Longer Recommended. ts-node-dev was archived in December 2025, and ts-node hasn't been updated in 2+ years. This approach still works but should only be used on existing / legacy projects. For new projects, use tsx (see the next section).
terminal
mkdir node-ts-app
cd node-ts-app
npm init -y
npm install express
npm install -D typescript ts-node nodemon @types/node @types/express
npx tsc --init
💡 Remember: -D means devDependency — these packages are only needed during development, not in production.

Project Structure

node-ts-app/ ├── src/ │ └── app.ts ← write code here ├── dist/ ← compiled JS output ├── package.json ├── tsconfig.json ← TS config └── .gitignore

package.json Scripts

package.json
{
  "scripts": {
    "dev":   "nodemon --exec ts-node src/app.ts",
    "build": "tsc",
    "start": "node dist/app.js"
  }
}

Dev Flow

npm run dev ↓ nodemon ← watches files ↓ ts-node src/app.ts ↓ App Starts ✅ ── Save a file ── ↓ nodemon detects change ↓ ts-node recompiles ↓ App Restarts

Build Flow (Production)

src/app.ts ↓ npm run build ↓ tsc ← TypeScript compiler ↓ dist/app.js ← plain JS file ↓ npm start ↓ node dist/app.js ✅
💡 Production never uses ts-node. Always compile first, then run with plain node.
New Way — tsx (2025/26 Recommended)

Status & Install Commands

tsx replaces both ts-node AND nodemon in a single package. Powered by esbuild — significantly faster, ESM-ready, actively maintained, with watch mode built right in.
terminal
mkdir node-ts-app
cd node-ts-app
npm init -y
npm install express
npm install -D tsx typescript @types/node @types/express
npx tsc --init
✅ Notice: No ts-node. No nodemon. Just tsx — one package does both jobs.

Project Structure

node-ts-app/ ├── src/ │ └── app.ts ← write code here ├── dist/ ← compiled JS output ├── package.json ├── tsconfig.json └── .gitignore

✅ Same structure as the old way — just fewer packages installed.

package.json Scripts

package.json
{
  "scripts": {
    "dev":   "tsx watch src/app.ts",
    "build": "tsc",
    "start": "node dist/app.js"
  }
}

💡 Only the "dev" script changes. Build and start remain identical.

Dev Flow

npm run dev ↓ tsx watch src/app.ts ← one command ↓ esbuild strips types ← super fast ↓ App Starts ✅ ── Save a file ── ↓ tsx detects instantly ↓ App Restarts (faster ⚡)

Build Flow (Production)

src/app.ts ↓ npm run build ↓ tsc ← same as before ↓ dist/app.js ↓ npm start ↓ node dist/app.js ✅
✅ Production flow is exactly the same as the old way.
Bonus — Node 22+ Native TypeScript

Zero Dependencies Option

Node.js 22+ can strip TypeScript types natively using a built-in flag — no tsx, no ts-node, no transpiler package needed at all.
package.json
{
  "scripts": {
    "dev":   "node --watch --experimental-strip-types src/app.ts",
    "build": "tsc",
    "start": "node dist/app.js"
  }
}
✅ Install only: npm install -D typescript @types/node @types/express — no tsx, no nodemon needed!
⚠️ Limitation: Requires Node 22+. Still experimental. Some advanced TS syntax not supported. Best for simple projects / scripts.
Old Way vs New Way

The Core Shift

With the old way, three packages coordinate to run and watch your TypeScript. With tsx, one esbuild-powered package does both — faster startup, faster restarts, and it's the actively maintained option.

Side-by-Side Comparison

Old Way (ts-node + nodemon)New Way (tsx)
3 packages — ts-node + nodemon + typescript 2 packages — tsx + typescript
Two separate tools have to be installed and configured together: one to compile, one to watch and restart. tsx alone handles both running and watching, so there's one less moving part to configure or update.
Engine: tsc (TypeScript compiler) — slow Engine: esbuild — 10–100× faster
ts-node compiles using the full TypeScript compiler on every run, which is thorough but slow. tsx uses esbuild, which just strips type annotations — it doesn't type-check, which is exactly why it's so much faster.
ESM support is tricky — needs extra config flags ESM support is native — works out of the box
Getting ES modules working with ts-node historically requires loader flags and extra tsconfig tweaks. tsx was built with modern module resolution in mind, so ESM projects just work without extra setup.
Maintenance: archived / stale Maintenance: active, regularly updated
ts-node-dev was archived in December 2025, and ts-node itself hasn't shipped meaningful updates in 2+ years. tsx is under active development, which matters for security patches and compatibility with newer Node/TS releases.

🎤 Interview Summary

Key Points to Remember

  • Node.js can only run JavaScript — TypeScript must be compiled or stripped of types first, either on disk (tsc) or on the fly (ts-node/tsx).
  • The old way — ts-node + nodemon — needs two packages and is now stale/archived; use it only for legacy projects.
  • The new way — tsx — is one actively maintained package, powered by esbuild, with watch mode built in.
  • tsx/esbuild is faster because it only strips types instead of fully type-checking; run tsc --noEmit separately if you need type safety during development.
  • Production is identical either way: tsc compiles to dist/, then node dist/app.js runs the plain JS — tsx and ts-node never touch production.
  • @types/* packages exist because plain-JS packages (like Express or Node's own built-ins) ship no .d.ts files of their own.
💡 30-second answer: "Node.js can't run TypeScript directly, so development needs a tool to strip or compile types on the fly. The older setup pairs ts-node with nodemon — two packages, and ts-node is now stale. The modern approach uses tsx, a single actively-maintained package powered by esbuild that both runs and watches TypeScript, 10 to 100 times faster because it only strips types instead of type-checking. Regardless of which one you use in development, production is identical: tsc compiles everything to a dist folder, and plain node runs the compiled JavaScript with zero TypeScript overhead."
💡 Interview Q&A — Node.js + TypeScript
💡 Interview Q&A
What is TypeScript?
TypeScript is a superset of JavaScript that adds static typing, interfaces, enums, generics, and compile-time error checking. It must be compiled to JavaScript before Node.js can run it — Node only understands JS.
Difference between ts-node and tsc?
tsc — TypeScript compiler. Converts .ts → .js files on disk. Used for production builds.
ts-node — Compiles TypeScript in memory and immediately runs it. No files written to disk. Used only in development.
tsc: app.ts → compile → dist/app.js (file on disk) ts-node: app.ts → compile in memory → execute (no file)
Why do we use nodemon?
Nodemon watches your files for changes and auto-restarts the app — replacing the manual stop/start cycle.

Without nodemon: change code → manually Ctrl+C → manually run again
With nodemon: change code → save → auto restarts

In the new approach, tsx watch replaces nodemon entirely.
Why is @types/node required? How does TypeScript find types for any package?
The core rule: when you import a package, TypeScript looks for a .d.ts (declaration file) describing that package's shape — what functions exist, what they accept, what they return. There are two cases:

✅ Case 1 — Package ships its own .d.ts (no @types needed)
Some packages are written in TypeScript or bundle their own type declarations. TypeScript finds the .d.ts automatically — no extra install needed.
node_modules/ axios/ index.js ← actual runtime code index.d.ts ← types built-in ✅ → Just install axios. TypeScript is happy. No @types/axios needed.
Packages like axios, zod, prisma work this way.

❌ Case 2 — Package has no .d.ts (must install @types/)
Some packages are written in plain JavaScript with no type info bundled. TypeScript has no idea what the API looks like and throws errors.
node_modules/ express/ index.js ← runtime code only, no .d.ts ❌ → TypeScript: "I don't know what req, res, Router look like!" ❌ Solution: npm install -D @types/express @types/express → just a folder of .d.ts files, zero runtime code ✅
Node.js itself is Case 2. Built-ins like fs, path, process, Buffer, http are C++ internals — there's no JS file for TypeScript to inspect. So @types/node is a package that's purely .d.ts descriptions of every Node.js API.

🔍 How to check before installing @types:
ls node_modules/axios/ → see index.d.ts? ✅ No @types needed ls node_modules/express/ → no .d.ts? ❌ Install @types/express
Or check the npm page — packages show a TS badge if types are bundled, or say "install @types/..." if not.
💡 One line rule: If the package has a .d.ts → TypeScript is happy. If not → install the matching @types/ package, which is just a .d.ts file written for it by the community.

zodYesJust install zod — done
expressNoInstall express + @types/express
Node.js built-insNoInstall @types/node
What does ts-node do internally?
ts-node hooks into Node's module loading system. When you run a .ts file, it intercepts the require/import, compiles it using the TypeScript compiler in memory, then passes the JavaScript to Node for execution. No files are written to disk.
app.ts → ts-node intercepts → tsc compiles in RAM → Node executes JS
What does tsx do internally?
tsx works similarly but uses esbuild instead of tsc. esbuild simply strips TypeScript type annotations — it does not type-check. This is why it's 10–100× faster. For type checking during development, run tsc --noEmit separately.
app.ts → tsx intercepts → esbuild strips types → Node executes JS (no type checking — just fast!)
Explain tsconfig.json in detail — all key fields and their alternate options
tsconfig.json is the configuration file for the TypeScript compiler (tsc). It tells TypeScript how to compile your code, where to find files, and how strict to be. All settings live inside "compilerOptions".

📄 A typical Node.js tsconfig.json:
{ "compilerOptions": { "target": "ES2020", "module": "commonjs", "rootDir": "./src", "outDir": "./dist", "strict": true, "esModuleInterop": true, "moduleResolution": "node", "skipLibCheck": true }, "include": ["src"], "exclude": ["node_modules", "dist"] }

ES2020Optional chaining ?., nullish ??Recommended for Node
ES2022Top-level await, class fieldsNode 16+
ESNextLatest JS featuresCutting edge — use carefully
💡 Rule: Match target to the Node.js version you run in production. ES2020 is safe for most projects.

── 6. esModuleInterop — clean imports for CommonJS packages
Without (esModuleInterop: false): import * as express from 'express' ← ugly ❌ With (esModuleInterop: true): import express from 'express' ← clean ✅

💡 Set "skipLibCheck": true always. Some @types packages have minor internal type conflicts — you don't want your build to fail because of someone else's type package bug.

What is rootDir and outDir in tsconfig?
rootDir: "./src" — tells TypeScript where your source .ts files live.
outDir: "./dist" — tells TypeScript where to output compiled .js files.

This ensures the folder structure is mirrored: src/app.ts → dist/app.js
Why do we generate the dist folder?
Node.js can only execute JavaScript. The dist/ folder holds the compiled JS that gets deployed to production servers. TypeScript files (.ts) never go to production — only the compiled output does.
Why can't Node.js run TypeScript directly?
Node.js is a JavaScript runtime — it only understands valid JavaScript syntax. TypeScript's type annotations are not valid JavaScript:
const age: number = 25; ← invalid JS (TypeScript) const age = 25; ← valid JS (after compilation)
The colon syntax must be removed before Node can run it. Tools like tsx/ts-node do this on the fly; tsc writes the output to disk.
What is strict mode in TypeScript?
Enabling "strict": true in tsconfig turns on a bundle of type safety rules:

• noImplicitAny — variables can't silently be any type
• strictNullChecks — null / undefined must be handled explicitly
• strictFunctionTypes — safer function parameter checking

It catches more bugs at compile time before they reach production.
What is moduleResolution?
Tells TypeScript how to find imported modules when you write import express from 'express'.

node — classic Node.js resolution (looks in node_modules)
node16 / bundler — modern ESM-aware resolution

Wrong setting causes "cannot find module" errors even when the package is installed.
Why use esModuleInterop?
Express is a CommonJS module (old format). Without esModuleInterop you must write ugly imports:
import * as express from 'express'

With "esModuleInterop": true you can write clean ES6 style:
import express from 'express'

It adds a compatibility wrapper so CJS default exports work with ES import syntax.
Explain the complete Node.js + TypeScript startup flow
── DEVELOPMENT (Old) ────────────────── npm run dev → nodemon → ts-node → app.ts runs in memory ── DEVELOPMENT (New) ────────────────── npm run dev → tsx watch → esbuild strips types → runs ── PRODUCTION (Both same) ───────────── npm run build → tsc → dist/app.js created npm start → node dist/app.js
Why don't we use tsx in production? How does production actually run?
tsx is a dev-only tool — it is never used in production. Here's exactly why and what happens instead:

❌ Why NOT tsx in production?

1. No type checking — tsx uses esbuild which only strips types. It never verifies your types are correct. In production you want full compile-time validation via tsc.

2. Performance overhead — tsx transpiles TypeScript on-the-fly every time the file is loaded. In production, plain node running pre-compiled JS is faster with zero transpilation cost.

3. Extra dependency risk — shipping tsx to a production server means an extra package that could have bugs, security issues, or break. Less is safer.

4. Not designed for it — tsx was built for developer experience (fast feedback loop). Production needs reliability and speed, not DX convenience.
── WHY tsx is DEV only ───────────────────────── tsx in dev: fast feedback → okay if a type slips through tsx in prod: type errors can reach live users ← dangerous ❌ overhead on every request ← slow ❌ extra package on server ← risky ❌
✅ How production actually runs:
Step 1 — Build (on your machine or CI/CD pipeline) npm run build ↓ tsc ← full TypeScript compiler ↓ ✅ Type checks ALL your code ↓ Generates dist/app.js ← plain JavaScript Step 2 — Deploy (ship dist/ folder to server) Copy dist/ + package.json → production server npm install --omit=dev ← installs only express, no tsx/typescript Step 3 — Start (on production server) npm start ↓ node dist/app.js ← plain Node.js, zero TypeScript overhead ↓ 🚀 Running pure JavaScript, maximum performance
💡 Key rule: TypeScript is a development tool. By the time code reaches production, all TypeScript has been compiled away. The server runs 100% plain JavaScript — it never knows TypeScript existed.
