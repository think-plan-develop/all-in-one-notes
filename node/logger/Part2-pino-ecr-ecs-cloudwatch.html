1–4. Pino in the Node.js project
1

Create Pino Logger

Install:

bash
npm install pino pino-http

Create:

logger.js

Example:

logger.js
import pino from 'pino';

const logger = pino({
  level: process.env.LOG_LEVEL || 'info',

  base: {
    service: 'pino-demo',
    env: process.env.NODE_ENV || 'development'
  }
});

export default logger;

The responsibility of Pino is:

Application
↓
Pino
↓
JSON log
↓
stdout

Pino does not directly send the log to CloudWatch.

2

Connect Pino to Express

Example:

app.js
import express from 'express';
import pinoHttp from 'pino-http';

import logger from './logger.js';

const app = express();

const httpLogger = pinoHttp({ logger });

app.use(httpLogger);

app.get('/', (req, res) => {
  req.log.info('Handling root route');

  res.send('Hello world');
});

app.get('/warn-example', (req, res) => {
  logger.warn(
    { userId: 42 },
    'User approaching rate limit'
  );

  res.send('warned');
});

app.get('/error', (req, res) => {
  try {
    throw new Error('Something broke');
  } catch (err) {
    logger.error(
      { err },
      'Failed handling /error route'
    );

    res.status(500).send('Internal error');
  }
});

app.listen(3000, () => {
  logger.info('Server started on port 3000');
});
3

Add Trace ID

Generate a trace ID for each request.

For example:

app.js
import crypto from 'crypto';

app.use((req, res, next) => {
  const traceId = crypto.randomUUID();

  req.traceId = traceId;

  res.setHeader('x-trace-id', traceId);

  next();
});

Then use:

app.js
req.log.info(
  { traceId: req.traceId },
  'Handling root route'
);

Your logs can then contain:

json
{
  "traceId": "7fba02e3-9b64-4de3-942d-b1881f0aab85"
}

This allows you to search CloudWatch using the trace ID later.

12

Important — latest Does NOT Automatically Update ECS

This is important from the issue you experienced earlier.

Suppose ECS previously pulled:

sha256:339da...

You push a new latest:

sha256:22a69...

ECS does not automatically restart the existing container.

Therefore after pushing a new image:

ECR updated
↓
ECS must launch a new task

You should deploy a new ECS revision / force a new deployment.

13–16. CloudWatch log group · streams · awslogs · IAM
13

Create CloudWatch Log Group

Now create the AWS-side logging destination.

Go to:

AWS Console → CloudWatch → Logs → Log groups → Create log group

Create:

/ecs/pino-logger-task

This is your application's CloudWatch log group.

Think:

CloudWatch │ └── /ecs/pino-logger-task
14

You Do NOT Create Log Streams Manually

This is important.

You create:

Log Group

but ECS creates the streams.

For example:

/ecs/pino-logger-task │ ├── ecs/Main/62c31cb... ├── ecs/Main/4f5f86e... └── ecs/Main/edc0cb9...

Each ECS task can have its own stream.

15

Connect ECS Container to CloudWatch

Go to:

ECS → Task Definitions → pino-logger-task → Create new revision

Open your:

Main

container.

Find:

Logging

Configure the log driver:

awslogs

Set:

awslogs-group /ecs/pino-logger-task awslogs-region us-east-1 awslogs-stream-prefix ecs

Conceptually:

Pino
↓
stdout
↓
Docker
↓
ECS
↓
awslogs
↓
CloudWatch
16

IAM — ECS Permission to Send Logs

Your ECS task execution role is:

ecsTaskExecutionRole

It needs the appropriate CloudWatch Logs permissions.

The standard:

AmazonECSTaskExecutionRolePolicy

covers the normal ECS execution-role requirements, including sending container logs through the awslogs driver.

Deploy the New ECS Revision

After changing the task definition logging configuration:

Create new revision

Then:

ECS → Cluster → Service → Update service

Select the new task definition revision.

If the image was updated but the task definition still references latest, make sure you trigger:

Force new deployment

This causes ECS to replace the running task.

22–28. How it connects · streams · Logs Insights queries
22

How Logger and CloudWatch Are Actually Connected

There is no code like this:

pino → CloudWatch

Instead:

logger.info()
↓
Pino
↓
console/stdout
↓
Docker
↓
ECS awslogs driver
↓
CloudWatch Log Group

That's the actual connection.

23

Find the Latest Log Stream

In:

CloudWatch → /ecs/pino-logger-task

you may see:

ecs/Main/62c31cb... ecs/Main/4f5f86e... ecs/Main/edc0cb9...

Look at:

Last event time

The most recent one is normally the latest active/recent stream.

However, the best way to identify the logs for your current deployment is:

ECS → Service → Tasks → RUNNING task → Logs

This ties the logs directly to the current task.

24

Search Logs Using CloudWatch Logs Insights

Go to:

CloudWatch → Logs Insights

Select:

/ecs/pino-logger-task

Basic query:

Logs Insights
fields @timestamp, level, msg
| sort @timestamp desc
25

Search Errors

Logs Insights
fields @timestamp, level, traceId, msg
| filter level >= 50
| sort @timestamp desc

This finds Pino error and fatal logs.

26

Search Warnings

Logs Insights
fields @timestamp, level, traceId, msg
| filter level = 40
| sort @timestamp desc
27

Search HTTP 500

Logs Insights
fields @timestamp, req.method, req.url, res.statusCode, traceId
| filter res.statusCode >= 500
| sort @timestamp desc
28

Search by Trace ID

Suppose your trace ID is:

7fba02e3-9b64-4de3-942d-b1881f0aab85

Use:

Logs Insights
fields @timestamp, level, traceId, req.method, req.url, res.statusCode, msg
| filter traceId = "7fba02e3-9b64-4de3-942d-b1881f0aab85"
| sort @timestamp asc

This is one of the most useful production debugging techniques.

29–30. Deployment flow · final relationship
29

Complete Updated-Code Deployment Flow

Whenever you change your Node.js code:

  1. Change code
  2. Test locally
  3. Build Docker image
  4. Test Docker locally
  5. Login to ECR
  6. Tag image
  7. Push image to ECR
  8. Create/update ECS task definition revision
  9. Verify ECR image configuration
  10. Deploy/update ECS service
  11. Force new deployment if using :latest
  12. Wait for RUNNING task
  13. Check task IP
  14. Test port 3000
  15. Test API endpoints
  16. Open CloudWatch
  17. Check latest log stream
  18. Search logs with Logs Insights
  19. Search by traceId/error/status
30

Final Relationship Between Everything

Keep this diagram in your notes:

YOUR CODE │ ↓ ┌─────────┐ │ Pino │ └────┬────┘ │ ↓ stdout │ ↓ ┌───────────┐ │ Docker │ │ Container │ └─────┬─────┘ │ image ↓ ┌───────────┐ │ ECR │ │ Repository│ └─────┬─────┘ │ pull ↓ ┌───────────┐ │ ECS │ │ Fargate │ └─────┬─────┘ │ awslogs ↓ ┌──────────────┐ │ CloudWatch │ │ Log Group │ └──────┬───────┘ ↓ Log Streams ↓ Logs Insights │ ┌────┼──────────┐ ↓ ↓ ↓ traceId errors HTTP 500

The key distinction

Docker/ECR/ECS handles your application image and execution:

Docker → ECR → ECS

Pino/CloudWatch handles your application logs:

Pino → stdout → ECS awslogs → CloudWatch

They meet at the ECS container. This is the central piece connecting your Dockerized application to AWS logging.

Image + run

Docker → ECR → ECS

Logs

Pino → stdout → ECS awslogs → CloudWatch
