📇 8. Indexes — Simple, Compound, Sparse
🏎 Indexes for Performance

Indexes make queries faster by letting MongoDB find documents without scanning the entire collection. Without an index on a queried field, MongoDB does a full collection scan (slow for large data).

indexes on schema fields
const userSchema = new Schema({
  email:    { type: String, unique: true,  index: true },  // simple index
  username: { type: String, index: true },
  role:     { type: String, index: true },

  // sparse index — only indexes docs where field exists (not null/undefined)
  phone: {
    type:   String,
    sparse: true,
    index:  true
  }
})

// compound index — defined at schema level (indexes combination of fields)
userSchema.index({ role: 1, createdAt: -1 })  // sort by role asc, date desc
userSchema.index({ email: 1, isActive: 1 })   // query users by email AND status

// text index — for full-text search
postSchema.index({ title: 'text', body: 'text' })

// TTL index — auto-delete documents after N seconds
sessionSchema.index({ createdAt: 1 }, { expireAfterSeconds: 3600 })  // 1 hour
🩵 1 = ascending, -1 = descending. Direction matters for compound indexes depending on query patterns.
💡 Sparse index — only indexes documents where the field actually exists. Without sparse, unique: true on an optional field would fail if two documents have null — both have the same "null" value, which violates unique. Sparse skips nulls.
💗 Compound index rule: A compound index on { a, b } can serve queries on a alone or a + b together — but NOT on b alone. Always put the most selective field first.
⚠️ Don't over-index. Every index slows down insert/update/delete because MongoDB must maintain each index. Only index fields you actually query.
🗂 Index Types — In Detail
🔍 Simple Index

An index on a single field. MongoDB maintains a sorted data structure (B-tree) for that field so lookups are O(log n) instead of O(n).

simple index — define + query
// define
const userSchema = new Schema({
  email: { type: String, index: true }
})

// query — uses the index, very fast
await User.findOne({ email: 'john@example.com' })

// OUTPUT — explain() shows IXSCAN (index scan) not COLLSCAN
await User.findOne({ email: 'john@example.com' }).explain('executionStats')
// {
//   winningPlan: { stage: 'FETCH', inputStage: { stage: 'IXSCAN' } },
//   executionStats: { totalDocsExamined: 1, totalKeysExamined: 1 }  ← only 1 doc scanned!
// }
Without index (COLLSCAN): scans ALL 1,000,000 docs → slow 🐢 With index (IXSCAN): scans exactly 1 doc → fast ⚡
🔗 Compound Index

An index on multiple fields combined. Covers queries that filter/sort on those fields together.

compound index — define + usage + output
// define compound index
userSchema.index({ role: 1, createdAt: -1 })

// ✅ uses index — both fields covered
await User.find({ role: 'admin' }).sort({ createdAt: -1 })

// ✅ uses index — leading field (role) alone is fine
await User.find({ role: 'user' })

// ❌ does NOT use index — createdAt alone (not the leading field)
await User.find({}).sort({ createdAt: -1 })

// OUTPUT from explain():
// ✅ { stage: 'IXSCAN', keyPattern: { role: 1, createdAt: -1 } }
// ❌ { stage: 'COLLSCAN' }  ← full scan, index not used
Compound index { role: 1, createdAt: -1 }: Query on role → ✅ uses index (leading field) Query on role + createdAt → ✅ uses index (both fields) Query on createdAt only → ❌ no index (non-leading field alone)
💡 This is called the ESR rule — put Equality fields first, Sort fields second, Range fields last in compound indexes.
🕳 Sparse Index

Only indexes documents where the field exists. Documents where the field is null or missing are excluded from the index entirely.

sparse index — problem + solution + output
// PROBLEM — unique on optional field WITHOUT sparse
const userSchema = new Schema({
  phone: { type: String, unique: true }  // ← no sparse!
})

// inserting 2 users without phone → FAILS
await User.create({ name: 'Alice' })  // phone = null
await User.create({ name: 'Bob'   })  // phone = null
// OUTPUT: MongoServerError: E11000 duplicate key error
// { keyValue: { phone: null } }  ← null treated as duplicate!

// ─────────────────────────────────────────
// SOLUTION — add sparse: true
const userSchema = new Schema({
  phone: { type: String, unique: true, sparse: true }
})

await User.create({ name: 'Alice' })  // ✅ no phone — not indexed
await User.create({ name: 'Bob'   })  // ✅ no phone — not indexed
await User.create({ name: 'Carol', phone: '9876543210' })  // ✅ indexed
await User.create({ name: 'Dave',  phone: '9876543210' })
// OUTPUT: MongoServerError: E11000 — duplicate phone (only real values are unique)
Documents in DB: { name: 'Alice' } ← NOT in index (no phone) { name: 'Bob' } ← NOT in index (no phone) { name: 'Carol', phone: '9876...' } ← IN index ✅ { name: 'Dave', phone: '1234...' } ← IN index ✅
⏳ TTL Index — Auto-Expiry

TTL (Time To Live) index auto-deletes documents after a specified number of seconds. Perfect for sessions, OTP tokens, temporary data, password reset links.

TTL index — sessions + OTP
// Session — expires after 1 hour (3600 seconds)
const sessionSchema = new Schema({
  userId:    { type: Schema.Types.ObjectId, ref: 'User' },
  token:     String,
  createdAt: { type: Date, default: Date.now }
})
sessionSchema.index({ createdAt: 1 }, { expireAfterSeconds: 3600 })

// OTP — expires after 5 minutes (300 seconds)
const otpSchema = new Schema({
  email:     String,
  otp:       String,
  createdAt: { type: Date, default: Date.now }
})
otpSchema.index({ createdAt: 1 }, { expireAfterSeconds: 300 })

// OUTPUT — after 5 min, OTP doc is automatically deleted by MongoDB
// No cron job needed. MongoDB background task runs every ~60 seconds.
// { _id: ..., email: 'a@b.com', otp: '4821', createdAt: ISODate("...") }
// ↑ this document disappears from DB automatically after 5 minutes
⚠️ TTL deletion is not instant — MongoDB's background task runs every 60 seconds. Documents may persist up to ~60 seconds after expiry.
createdAt = 10:00:00 + expireAfterSeconds: 300 → document deleted at approximately 10:05:00–10:06:00
🔤 Text Index — Full-Text Search

Text indexes let you search string content with $text operator. Supports stemming, stop words, case-insensitive search across multiple fields.

text index — define + query + output
// define text index on title and body
const postSchema = new Schema({
  title: String,
  body:  String,
  tags:  [String]
})
postSchema.index({ title: 'text', body: 'text' })

// query — search for posts containing 'mongoose' or 'schema'
const results = await Post.find(
  { $text: { $search: 'mongoose schema' } },
  { score: { $meta: 'textScore' } }           // include relevance score
).sort({ score: { $meta: 'textScore' } })    // sort by relevance

// OUTPUT
// [
//   { title: 'Mongoose Schema Guide', score: 2.5 },   ← most relevant
//   { title: 'MongoDB Basics', score: 0.75 },
//   { title: 'Node.js with Mongoose', score: 0.5 }
// ]

// exclude a word — posts with 'mongoose' but NOT 'schema'
await Post.find({ $text: { $search: 'mongoose -schema' } })
🩵 Only one text index is allowed per collection. To search multiple fields, define all of them in a single text index — { title: 'text', body: 'text', tags: 'text' }.
🎯 Interview Q&A — General
💼 Most Asked Interview Questions
Q1 What is the difference between a Mongoose Schema and a Model?
A Schema is just the blueprint — it defines the shape of documents, field types, validation rules, defaults, and methods. It doesn't interact with the database at all.

A Model is the compiled version of a schema — it's the class you use to actually perform CRUD operations against the MongoDB collection.
Schema → blueprint (no DB interaction) Model → mongoose.model('User', schema) — gives you User.find(), User.create(), etc. Document → new User({...}) — instance of a Model (a single record)
Q2 Why is unique: true NOT a Mongoose validator?
unique: true tells Mongoose to create a MongoDB unique index on that field — it's handled at the database level, not by Mongoose's validation pipeline. When you try to insert a duplicate, MongoDB throws a MongoServerError with code 11000, not a Mongoose ValidationError.

This means it won't be caught by your normal validation error handler — you need to specifically check err.code === 11000.
Q3 What is the difference between minlength and min?
minlength / maxlength are String validators — they check the length of a string (number of characters).
min / max are Number validators — they check the value of a number.
name: { type: String, minlength: 2 } ← min 2 characters age: { type: Number, min: 0 } ← min value of 0
Q4 Why should you use function keyword (not arrow) in schema methods and hooks?
Arrow functions don't have their own this binding — they inherit this from the enclosing scope (the module), not the document or query. In Mongoose middleware and methods, this must refer to the current document (in instance methods / pre save) or the current query (in pre find hooks).

Using an arrow function breaks this.fieldName, this.isModified(), and similar patterns entirely.
Q5 Does findByIdAndUpdate trigger the pre('save') hook?
No. findByIdAndUpdate bypasses Mongoose completely and sends the update directly to MongoDB. It does not trigger pre('save'), post('save'), or any instance method validators.

To run validation on update: pass { runValidators: true, new: true } in options.
To intercept it with middleware: use pre('findOneAndUpdate').
Q6 What is a Virtual field and when would you use it?
A virtual is a computed property derived from other fields at runtime — it's never stored in MongoDB. You define a getter (and optionally a setter) using schema.virtual('fieldName').get(fn).

Use cases: fullName from firstName + lastName, age from birthYear, profileUrl from username. Anything you want in your API response but don't need to persist.
Q7 What is the difference between embedded documents and references (ref)?
Embedded — the child data is stored inside the parent document. Faster reads (one query), but data duplication if used in multiple places. Good for: address inside user, items inside an order.

Reference — store only the ObjectId, fetch the related doc with populate(). Better for: shared data (user → posts → comments), large datasets where embedding would bloat documents.
Embed when: data belongs only to this parent, always read together Reference when: data is shared, updated independently, or large
Q8 When would you use Mixed type and what's the catch?
Use Mixed when the shape of a field is truly unknown or varies per document — like an audit log payload, third-party API response, or arbitrary metadata.

The catch: Mongoose can't detect changes to Mixed fields automatically. If you mutate a Mixed field, you must call doc.markModified('fieldName') before doc.save(), otherwise the change won't be persisted.
Q9 What is the difference between instance methods and static methods?
Instance methods (schema.methods.fn) — called on a single document (user.comparePassword()). this = the document.

Static methods (schema.statics.fn) — called on the Model class itself (User.findByEmail()). this = the Model. Good for custom finders and factory methods that don't need an existing document.
Q10 What is a sparse index and why is it needed?
A sparse index only indexes documents where the field exists (is not null/undefined). Without sparse, a unique index on an optional field fails because two documents both with null violate the unique constraint — null is treated as a value.

With sparse: true, documents where the field is null/missing are excluded from the index entirely.
📇 Interview Q&A — Indexes (with Output)
🔥 Index-Specific Interview Questions
Q11 What happens internally when you run a query without an index vs with an index? Show output.
Without an index, MongoDB does a COLLSCAN (collection scan) — it reads every document. With an index, it does an IXSCAN (index scan) — reads only matching documents. Use .explain() to see which plan MongoDB chose.
explain() output comparison
// ❌ NO INDEX on 'email' — full collection scan
await User.findOne({ email: 'john@gmail.com' }).explain('executionStats')
// OUTPUT:
// {
//   winningPlan: { stage: 'COLLSCAN' },
//   executionStats: {
//     totalDocsExamined: 100000,   ← scanned ALL 100k docs
//     totalKeysExamined: 0,
//     executionTimeMillis: 340     ← slow!
//   }
// }

// ✅ WITH INDEX on 'email'
await User.findOne({ email: 'john@gmail.com' }).explain('executionStats')
// OUTPUT:
// {
//   winningPlan: { stage: 'FETCH', inputStage: { stage: 'IXSCAN',
//     keyPattern: { email: 1 } } },
//   executionStats: {
//     totalDocsExamined: 1,        ← only 1 doc!
//     totalKeysExamined: 1,
//     executionTimeMillis: 1       ← 340x faster!
//   }
// }
Q12 Does a compound index { role: 1, createdAt: -1 } help a query on createdAt alone? Show output.
No — a compound index can only be used when the query includes the leading field (role). Querying on createdAt alone skips the index entirely.
compound index — what uses it vs what doesn't
userSchema.index({ role: 1, createdAt: -1 })

// ✅ uses index — leading field 'role' present
await User.find({ role: 'admin' })
// OUTPUT: winningPlan: { stage: 'IXSCAN', keyPattern: { role: 1, createdAt: -1 } }

// ✅ uses index — both fields present
await User.find({ role: 'admin' }).sort({ createdAt: -1 })
// OUTPUT: winningPlan: { stage: 'IXSCAN', keyPattern: { role: 1, createdAt: -1 } }

// ❌ does NOT use index — createdAt is not the leading field
await User.find({}).sort({ createdAt: -1 })
// OUTPUT: winningPlan: { stage: 'COLLSCAN' }  ← full scan!
Index { role: 1, createdAt: -1 }: query { role } → ✅ IXSCAN query { role, createdAt } → ✅ IXSCAN query { createdAt } → ❌ COLLSCAN (missing leading field)
Q13 What is a TTL index and what is the output when a document expires?
A TTL (Time To Live) index automatically deletes documents after a specified number of seconds from a Date field. MongoDB runs a background task every ~60 seconds that checks and removes expired documents. No code needed — the DB handles it.
TTL — create + expiry output
otpSchema.index({ createdAt: 1 }, { expireAfterSeconds: 300 })

// Create OTP document
const otp = await OTP.create({ email: 'a@b.com', code: '8821' })
// OUTPUT: { _id: ObjectId("..."), email: 'a@b.com', code: '8821',
//           createdAt: ISODate("2026-01-01T10:00:00Z") }

// After 5 minutes (+ up to 60s MongoDB background delay)...
await OTP.findOne({ email: 'a@b.com' })
// OUTPUT: null  ← document is gone, deleted by MongoDB automatically ✅
10:00:00 → OTP created { email: 'a@b.com', code: '8821' } 10:05:00 → TTL fires MongoDB background task runs 10:05:00 → OTP deleted findOne() returns null
Q14 What is a text index and how does $text search work? Show output with score.
A text index tokenizes string fields and allows full-text search with $text: { $search: '...' }. It supports stemming (run/running match), case-insensitivity, and relevance scoring via textScore.
text search with score output
postSchema.index({ title: 'text', body: 'text' })

const results = await Post
  .find(
    { $text: { $search: 'mongoose indexes' } },
    { score: { $meta: 'textScore' } }
  )
  .sort({ score: { $meta: 'textScore' } })

// OUTPUT:
// [
//   { title: 'Mongoose Indexes Guide',  score: 3.25 },  ← both words match
//   { title: 'MongoDB Indexes Deep Dive', score: 1.5 }, ← one word matches
//   { title: 'Learn Mongoose Basics',    score: 0.75 }  ← partial match
// ]

// Phrase search — exact phrase
await Post.find({ $text: { $search: '"mongoose schema"' } })
// OUTPUT: only docs with exact phrase "mongoose schema"

// Exclude word — mongoose but NOT indexes
await Post.find({ $text: { $search: 'mongoose -indexes' } })
Q15 How do you check what indexes exist on a collection? Show output.
Use Model.collection.getIndexes() to list all indexes currently on a collection — useful for debugging and verifying indexes were created.
list indexes — output
const indexes = await User.collection.getIndexes()
console.log(indexes)

// OUTPUT:
// {
//   '_id_':            { key: { _id: 1 }, name: '_id_' },
//   'email_1':         { key: { email: 1 }, name: 'email_1', unique: true },
//   'username_1':      { key: { username: 1 }, name: 'username_1' },
//   'role_1_createdAt_-1': { key: { role: 1, createdAt: -1 }, name: 'role_1_createdAt_-1' },
//   'phone_1':         { key: { phone: 1 }, name: 'phone_1', sparse: true }
// }

// Drop a specific index
await User.collection.dropIndex('username_1')
// OUTPUT: { nIndexesWas: 5, ok: 1 }
Q16 Why does adding too many indexes slow down writes? Explain with example.
Every index is a separate B-tree data structure that MongoDB must keep in sync with the collection. On every insert, update, or delete, MongoDB must update all indexes on that collection — more indexes = more write operations per document change.
over-indexing impact
// Collection with 6 indexes
userSchema.index({ email: 1 })
userSchema.index({ username: 1 })
userSchema.index({ role: 1 })
userSchema.index({ createdAt: -1 })
userSchema.index({ role: 1, createdAt: -1 })
userSchema.index({ city: 1, country: 1 })

// Single insert — MongoDB updates ALL 6 indexes + _id index = 7 write ops
await User.create({ name: 'John', email: 'j@x.com', role: 'user' })
// internally: write doc + update 7 index trees

// Bulk insert of 10,000 users — with 6 indexes
// vs same bulk insert with only 2 essential indexes
// → 6-index version can be 3-4x slower on writes
1 index → 1 doc write + 2 index updates (fast) 6 indexes → 1 doc write + 7 index updates (3-4x slower on writes) Rule: index what you QUERY, not every field you have.
