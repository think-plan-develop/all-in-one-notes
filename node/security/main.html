1. Authentication — who the user is

Tokens + hashing

  • JWT — signed claims (user ID, role); verified by signature, not a DB lookup every request.
  • Argon2 — memory-hard password hash; never store plain text.
  • Access token — short-lived, sent with each API request.
  • Refresh token — long-lived, HttpOnly cookie, used to get a new access token.
  • Token rotation — new refresh token each use; old one invalidated.

2. Authorization — what they may do

RBAC

  • RBAC — decisions from assigned role(s), not per-user rules.
  • Roles — named groupings (ADMIN, USER).
  • Permissions — granular actions (user:delete) on roles. Effective access = union of role permissions.

3. Network Security

3.1 HTTPS / TLS

Protects data in transit. HTTPS = HTTP + TLS.

  • Server authentication — certificate confirms the real server.
  • Encryption — hides passwords, cookies, tokens from eavesdroppers.
  • Integrity — detects tampering in transit.
⚠️ TLS protects the channel only — not SQL injection or XSS.

4. Cookie Security

HttpOnly · Secure · SameSite · CSRF

  • HttpOnly — JS cannot read the cookie; mitigates XSS token theft.
  • Secure — sent only over HTTPS.
  • SameSite — strict / lax / none; primary CSRF mitigation.
  • CSRF — forged authenticated requests. Defend with SameSite + CSRF tokens on POST/PUT/PATCH/DELETE.
cookie
res.cookie("refreshToken", token, { httpOnly: true, secure: true, sameSite: "strict" });
5. API Security

5.1 Input validation

Reject malformed data before business logic or the DB (zod / joi). Type, format, length, allowed values — every field.

5.2 Rate limiting

Cap requests per IP/user/key. Stops brute-force, credential stuffing, abuse.

rateLimit
app.use(rateLimit({ windowMs: 15 * 60 * 1000, max: 100 }));

5.3 Request size limits

Cap body size to prevent memory DoS.

json limit
app.use(express.json({ limit: "1mb" }));

5.4 SQL injection

Never let user input become executable SQL.

Dangerous

SELECT * FROM users WHERE email = '${email}'

Parameterized / ORM

prisma.user.findUnique({ where: { email } })

User input
↓
Parameter
↓
Database query
📌 Validation checks if input is valid. Parameterization treats input as data, not code. You need both.

5.5 Error handling

Generic messages to clients. Log full details server-side. Consistent shapes. Status codes: 400, 401, 403, 404, 409, 500. Never leak stack traces, SQL errors, or file paths.

6. Frontend Security

XSS · CSP · DOM · storage · routes · deps

  • XSS — injected JS. Defend with output encoding, no unsanitized innerHTML / dangerouslySetInnerHTML, DOMPurify for rich text.
  • CSP — restricts what scripts/resources can load; limits XSS even if injection occurs.
  • Safe DOM — prefer textContent; never eval() or unsanitized strings.
  • Secure storage — tokens in HttpOnly cookies, not localStorage/sessionStorage (JS-readable).
  • Route protection — client guards are UX only. Always re-enforce on the server.
  • Dependencies — keep packages updated; npm audit.
7. Environment Security

7.1 .env — local

project/ ├── .env ← local secrets (gitignored) ├── .env.example ← names only, committed └── .gitignore

Add .env to .gitignore. Commit only .env.example.

7.2 Production — AWS / server

Never store production secrets in Git or the Docker image.

Image = code + deps + Node. Not JWT_SECRET, DB passwords, API keys. Inject at runtime.

7.4 What must be protected

JWT secrets DB credentials Redis credentials API keys Third-party creds
  • Never hardcode secrets in source.
  • Never commit .env.
  • Never expose server secrets to the frontend.
  • Different secrets per env (dev / staging / prod).
  • Least privilege per environment.
  • Rotate immediately if compromised.
✅ Code goes into Git/Docker. Secrets are supplied at runtime.
8. Database Security

Postgres · Redis · privilege · constraints · TLS · backups

  • PostgreSQL — parameterized queries / ORM; restrict network (firewall/VPC); SSL connections.
  • Redis — requirepass; bind internal only; never public; TLS if available.
  • Least privilege — app DB user: no SUPERUSER, no DROP in prod. Don't connect as admin/root.
  • Constraints — UNIQUE, NOT NULL, FKs so invalid states fail even if app logic is buggy.
  • Encryption/TLS — in transit; consider at rest for sensitive columns/disks.
  • Backups — automated, stored securely (see 9.7).
9. Operational Security

9.1–9.4 Logging · monitoring · alerting · audit

  • Logging — requests, errors, auth attempts. Never passwords, tokens, full card numbers.
  • Monitoring — latency, error rates, resource usage.
  • Alerting — notify on thresholds (500 spike, failed-login surge).
  • Audit logs — immutable record of role changes, grants, admin actions, deletions. Critical for RBAC and incidents.
