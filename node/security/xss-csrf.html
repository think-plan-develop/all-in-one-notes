Notes — CSRF Protection + XSS Protection

Compact notes. Full text. Cookie flags, SameSite, CSRF tokens, XSS types and defenses.

CSRF 1–13 XSS 1–6
CSRF Protection — Compact Notes
1

What is CSRF?

CSRF (Cross-Site Request Forgery) — an attack where a malicious site tricks a user's browser into sending an authenticated request to your API. Relevant because refresh tokens are stored in cookies, and browsers auto-attach cookies to matching requests — no JavaScript needed.

User logs in → Server sends refresh token → Stored in HttpOnly cookie → Browser auto-sends it to API
2

Why It Matters for Your Auth System

Login → Access Token → Refresh Token → HttpOnly Cookie
ts
res.cookie("refreshToken", token, { httpOnly: true, secure: true, sameSite: "strict" });

Since the browser manages this cookie automatically, cookie-based auth = potential CSRF risk = needs a CSRF strategy.

3

HttpOnly is NOT CSRF Protection ⚠️ Key Concept

ts
httpOnly: true

Means JavaScript cannot read the cookie (document.cookie fails), but the browser can still send it with requests.

JavaScript → ❌ cannot read cookie Browser → ✅ can still send cookie
  • HttpOnly → protects against JS/XSS reading the cookie
  • CSRF protection → protects against forged requests using the cookie
⚠️ HttpOnly ≠ CSRF protection. You still need SameSite and/or an explicit CSRF token.
4

Secure

ts
secure: true

Cookie is sent only over HTTPS, never plain HTTP. Use true in production; may need false for local HTTP development.

5

SameSite

Controls whether the cookie is sent in cross-site requests — a core CSRF defense.

ValueBehavior
strictMost restrictive — cookie sent only for same-site requests. Blocks most CSRF.
laxAllows some cross-site cases (e.g., top-level navigation); still meaningful protection. Useful when strict breaks legitimate flows.
noneAllows cross-site cookie sending. Must be paired with secure: true. Needed for genuine cross-site frontend/backend setups — but requires an explicit CSRF token strategy since SameSite alone no longer protects you.
6

CSRF Token

An extra value the legitimate frontend sends alongside the cookie; the server validates it before processing the request.

Browser
↓
[Auth cookie + CSRF token]
↓
API
↓
Validate CSRF token
↓
Allow / Reject

Why it works: an attacker's site can trigger a request that includes the cookie, but it won't know/have the legitimate CSRF token → request is rejected (403 Forbidden).

7

CSRF Token vs Refresh Token

TokenPurpose
Refresh TokenAuthentication — get a new access token
CSRF TokenVerifies the request legitimately came from your app
8

Cookie Security Responsibilities

httpOnly → JS cannot read cookie secure → HTTPS only sameSite → controls cross-site sending CSRF token → explicit validation request is legitimate
9

CSRF vs XSS

AttackMechanismMain Defense
XSSAttacker injects malicious JS into your pageHttpOnly (stops JS from reading the cookie)
CSRFAttacker tricks browser into sending an authenticated requestSameSite + CSRF token
10

Which Requests Need CSRF Protection?

Focus on state-changing methods: POST, PUT, PATCH, DELETE.

Priority endpoints for an auth project:

http
POST /auth/login
POST /auth/refresh
POST /auth/logout
POST /auth/register
11

Recommended Configurations

Same-site production (preferred, simpler):

ts
res.cookie("refreshToken", refreshToken, {
  httpOnly: true,
  secure: true,
  sameSite: "strict",
});

Cross-site architecture (frontend/backend on different domains):

ts
res.cookie("refreshToken", refreshToken, {
  httpOnly: true,
  secure: true,
  sameSite: "none",
});
⚠️ With sameSite: "none", do not rely on SameSite alone — implement explicit CSRF token validation.
12

Architecture Checklist (Before Adding CSRF Tokens)

Don't add a CSRF token just because you use cookies — first ask:

  1. Are frontend and backend same-site or cross-site?
  2. What SameSite policy are you using?
  3. Do you actually need cross-site cookies?
  4. Which endpoints are state-changing/protected?
  5. Does your CSRF defense match your cookie config?
13

Final Mental Model

Refresh Token → HttpOnly Cookie │ ┌─────────────┼─────────────┐ ↓ ↓ ↓ HttpOnly Secure SameSite (JS can't (HTTPS (cross-site read it) only) control) │ ↓ CSRF Strategy (if needed) │ ↓ Valid ✅ → Allow Invalid ❌ → 403 Forbidden
One-line summary: HttpOnly blocks JS from reading the cookie, Secure protects it in transit, SameSite limits cross-site sending, and a CSRF token gives explicit proof a protected request came from your legitimate app.
XSS Protection — Compact Notes
1

What is XSS?

XSS (Cross-Site Scripting) — an attack where a malicious actor injects JavaScript into your web page, which then runs in the victim's browser under your app's trusted origin. Unlike CSRF (which forges a request), XSS injects and runs code.

Attacker
↓
Injects malicious script
↓
Your webpage renders it
↓
Runs in victim's browser

Once injected, that script can steal readable cookies/tokens, make API calls as the user, log keystrokes, redirect to phishing pages, or modify the DOM.

2

Types of XSS

TypeHow it happens
Stored XSSMalicious script is saved server-side (e.g., in a comment/profile field) and served to every viewer. Most dangerous — persistent, affects many users.
Reflected XSSScript is embedded in a request (e.g., URL query param) and immediately reflected back in the response without sanitization. Requires tricking the victim into clicking a crafted link.
DOM-based XSSVulnerability exists purely in client-side JS — untrusted data is written into the DOM (e.g., via innerHTML) without ever touching the server.
3

Why It Matters for Your Auth System

If an attacker achieves XSS on your site, they can run JS in the same origin as your app:

Malicious script runs
↓
Can read anything JS-accessible: localStorage, sessionStorage, non-HttpOnly cookies
↓
Can call your API using the victim's live session

This is exactly why the refresh token should be HttpOnly — even if XSS occurs, the script still cannot read that cookie directly. It's a mitigation for XSS's impact, not a fix for XSS itself.

4

Core Defenses

Output Encoding / Escaping

Always escape untrusted data before rendering it in HTML, attributes, JS, or URLs — convert <, >, ", ', & into safe entities so injected markup is displayed as text, not executed as code. Most modern frameworks (React, Vue, Angular) auto-escape by default when using standard templating — the risk appears when you bypass it.

Avoid Dangerous Sinks

Don't insert unsanitized data into places that execute code:

js
// Dangerous
element.innerHTML = userInput;

// Safer
element.textContent = userInput;

In React, avoid dangerouslySetInnerHTML unless the content is sanitized first (e.g., via a library like DOMPurify).

Content Security Policy (CSP)

An HTTP response header that restricts what scripts/resources a page is allowed to load and run — a strong defense-in-depth layer even if an injection slips through:

http
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'

This blocks inline scripts and scripts from untrusted origins, significantly limiting what an injected payload can do.

Input Validation & Sanitization

Validate input format server-side (e.g., reject unexpected HTML in a "name" field), and sanitize rich-text input (e.g., blog content) using a trusted library (like DOMPurify) rather than a custom regex/blocklist, which is easy to bypass.

HttpOnly Cookies

As covered above — makes tokens unreadable via document.cookie, limiting what a successful XSS attack can steal.

Avoid Storing Sensitive Tokens in localStorage

localStorage/sessionStorage are fully readable by any JS running on the page — including injected XSS payloads. Prefer HttpOnly cookies for tokens like refresh tokens over storing them in localStorage.

5

CSRF vs XSS — Quick Comparison

CSRFXSS
What's exploitedBrowser auto-sending cookiesTrust in rendered page content
Attacker injectsA forged requestMalicious JavaScript
Main defensesSameSite, CSRF tokensOutput encoding, CSP, sanitization
HttpOnly roleNot a defenseLimits token theft if XSS occurs
6

Quick Checklist

  1. Escape/encode all untrusted output rendered into HTML.
  2. Avoid innerHTML/dangerouslySetInnerHTML with unsanitized input — sanitize with a library like DOMPurify if rich text is required.
  3. Set a strict Content-Security-Policy header.
  4. Validate and sanitize all user input server-side, not just client-side.
  5. Keep sensitive tokens in HttpOnly cookies, not localStorage/sessionStorage.
  6. Keep frontend framework and templating libraries up to date (auto-escaping behavior can have historical CVEs).
One-line summary: XSS lets an attacker run their own JavaScript inside your trusted page — defend with output encoding, CSP, input sanitization, and by keeping sensitive tokens out of JS-readable storage (HttpOnly cookies), since XSS and CSRF are different attacks requiring different (complementary) defenses.
