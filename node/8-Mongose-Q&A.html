📐 1. Schema Creation
🏗 What is a Mongoose Schema?

A Schema defines the shape (structure) of documents in a MongoDB collection. It's the blueprint — you define what fields exist, their types, and rules. The Model is the compiled class you use to actually create, read, update, delete documents.

Schema → defines the shape + rules of documents Model → compiled class to interact with the collection Document → single record / instance created from a Model
src/models/user.model.ts
import mongoose, { Schema, Document, Model } from 'mongoose'

// 1. TypeScript interface — shape of the document
interface IUser extends Document {
  name:     string
  email:    string
  age:      number
  isActive: boolean
}

// 2. Schema — rules and structure
const userSchema = new Schema<IUser>({
  name:     { type: String,  required: true },
  email:    { type: String,  required: true, unique: true },
  age:      { type: Number },
  isActive: { type: Boolean, default: true }
})

// 3. Model — compiled class
const User: Model<IUser> = mongoose.model<IUser>('User', userSchema)

export default User
🩵 Naming convention: mongoose.model('User', schema) — Mongoose automatically looks for/creates the collection named 'users' (pluralized, lowercased). You don't create the collection manually.

Buffer — Binary Data

Used to store raw binary data like uploaded images, PDFs, or files directly in MongoDB.

Buffer example
const fileSchema = new Schema({
  filename: String,
  data:     Buffer,       // raw bytes
  mimeType: String
})

// store a file
const fileDoc = new File({
  filename: 'photo.jpg',
  data:     fs.readFileSync('photo.jpg'),
  mimeType: 'image/jpeg'
})
⚠️ Storing large files in MongoDB is not recommended. Use GridFS for files >16MB or store in S3 and save only the URL.

Map Data Type

Use when document has dynamic/unknown keys — like user preferences or metadata where key names aren't predefined.

Map example
const userSchema = new Schema({
  name: String,
  // Map with string values
  preferences: {
    type: Map,
    of: String
  }
})

// usage
user.preferences.set('theme', 'dark')
user.preferences.set('lang',  'en')
user.preferences.get('theme') // 'dark'

Mixed Data Type

Accepts any value — Mongoose won't validate or cast it. Use when you truly don't know the shape ahead of time.

Mixed type
const logSchema = new Schema({
  event:   String,
  payload: Schema.Types.Mixed  // anything goes
})

// payload can be anything
{ event: 'login',  payload: { ip: '1.2.3.4', browser: 'Chrome' } }
{ event: 'purchase', payload: ['item1', 'item2'] }
{ event: 'error',   payload: 'something broke' }
⚠️ When you modify a Mixed field, Mongoose can't detect the change — you must call doc.markModified('payload') before doc.save() or the change won't be persisted.

Decimal128

High-precision decimal — use for money, financial calculations where floating point errors in Number are unacceptable.

Decimal128 example
const orderSchema = new Schema({
  product: String,
  amount:  { type: Schema.Types.Decimal128 }
})

// create
const order = new Order({
  product: 'Laptop',
  amount:  mongoose.Types.Decimal128.fromString('1299.99')
})

// read — returns Decimal128 object, convert to string
order.amount.toString()  // '1299.99'
✅ 3. Validations — Required, Min/Max, Enum, Custom
🛡 Built-in Validators

Required

Makes a field mandatory. If not provided, Mongoose throws a ValidationError before saving.

required validator
const userSchema = new Schema({
  // simple required
  name: { type: String, required: true },

  // required with custom error message
  email: {
    type: String,
    required: [true, 'Email is required']
  },

  // required only when another field is set (conditional)
  companyName: {
    type: String,
    required: function() {
      return this.role === 'business'
    }
  }
})

String Validations — trim, lowercase, minlength, maxlength

string validators
const userSchema = new Schema({
  name: {
    type:      String,
    required:  true,
    trim:      true,        // removes leading/trailing spaces before saving
    minlength: [2,  'Name must be at least 2 characters'],
    maxlength: [50, 'Name cannot exceed 50 characters']
  },

  email: {
    type:      String,
    required:  true,
    trim:      true,
    lowercase: true,       // "USER@Email.COM" → stored as "user@email.com"
    minlength: 5,
    maxlength: 100
  },

  username: {
    type:      String,
    trim:      true,
    lowercase: true,       // "JohnDoe" → "johndoe"
    minlength: [3,  'Username min 3 chars'],
    maxlength: [20, 'Username max 20 chars']
  }
})
🩵 trim — runs before saving. " John " becomes "John" in the DB. It does NOT affect queries — trimming happens on the value being set.
🩵 lowercase — converts the string to lowercase before saving. Great for emails so USER@EMAIL.COM and user@email.com are treated the same.
💗 uppercase also exists — uppercase: true — converts to uppercase before saving. Less common but useful for things like country codes.
💡 minlength/maxlength are String validators. For Number, use min/max. They are different properties — don't mix them up.

Number Validations — min, max

number validators
const productSchema = new Schema({
  price: {
    type: Number,
    required: true,
    min: [0,    'Price cannot be negative'],
    max: [99999, 'Price too high']
  },

  age: {
    type: Number,
    min: [0,   'Age must be 0 or above'],
    max: [120, 'Age must be 120 or below']
  },

  quantity: {
    type:     Number,
    default:  0,
    min:      0     // stock can't go below 0
  }
})

Default Values

default values
const userSchema = new Schema({
  isActive: { type: Boolean, default: true      },  // static default
  role:     { type: String,  default: 'user'     },  // static default
  score:    { type: Number,  default: 0           },  // static default
  joinedAt: { type: Date,    default: Date.now    },  // function — called at insert time
  token:    { type: String,  default: () => generateToken() } // arrow fn
})
💗 default: Date.now — pass the function reference, NOT Date.now() (with parentheses). With parentheses it evaluates once at schema definition time. Without, it runs each time a document is created.

Enum Validation

Restricts a field to a specific set of allowed values. If any other value is provided, Mongoose throws a ValidationError.

enum validator
const userSchema = new Schema({
  role: {
    type:    String,
    enum:    ['user', 'admin', 'moderator'],
    default: 'user'
  },

  // enum with custom error message
  status: {
    type: String,
    enum: {
      values:  ['active', 'inactive', 'banned'],
      message: '{VALUE} is not a valid status'   // {VALUE} = what user sent
    },
    default: 'active'
  }
})

// ❌ this throws: ValidationError: role: 'superadmin' is not a valid enum value
await User.create({ role: 'superadmin', email: 'a@b.com' })
💗 TypeScript tip: Define enum as a const array and use as const so your interface type matches the enum automatically — no duplication.
TypeScript enum pattern
const ROLES = ['user', 'admin', 'moderator'] as const
type Role = typeof ROLES[number]  // 'user' | 'admin' | 'moderator'

interface IUser {
  role: Role
}

const userSchema = new Schema<IUser>({
  role: { type: String, enum: ROLES, default: 'user' }
})

Unique Index

unique field
const userSchema = new Schema({
  email:    { type: String, required: true, unique: true },
  username: { type: String, required: true, unique: true }
})
⚠️ unique is NOT a Mongoose validator — it creates a MongoDB index. It won't throw a Mongoose ValidationError, it throws a MongoServerError with code 11000 (duplicate key). You must handle this separately in your error middleware.
handle duplicate key error
try {
  await User.create({ email: 'existing@email.com' })
} catch (err: any) {
  if (err.code === 11000) {
    // err.keyValue tells you which field was duplicate
    const field = Object.keys(err.keyValue)[0]
    throw new Error(`${field} already exists`)
  }
}

Custom Validation

Use the validate property to write your own validation logic for any field.

custom validators
import validator from 'validator'   // npm install validator

const userSchema = new Schema({

  // simple custom validate
  age: {
    type: Number,
    validate: {
      validator: (v: number) => v >= 18,
      message:   'User must be at least 18 years old'
    }
  },

  // email validation using validator package
  email: {
    type: String,
    required: true,
    validate: {
      validator: (v: string) => validator.isEmail(v),
      message:   'Please provide a valid email address'
    }
  },

  // phone number custom regex
  phone: {
    type: String,
    validate: {
      validator: (v: string) => /^\d{10}$/.test(v),
      message:   'Phone must be exactly 10 digits'
    }
  },

  // async validator (e.g., check if username is taken via DB)
  username: {
    type: String,
    validate: {
      validator: async function(v: string) {
        const exists = await User.findOne({ username: v })
        return !exists
      },
      message: 'Username is already taken'
    }
  }
})
🧩 4. Arrays, Nested Objects & ObjectId References
📚 Arrays in Mongoose

Arrays of Primitives

arrays of strings, numbers
const postSchema = new Schema({
  tags:    [String],                          // shorthand
  scores:  [Number],
  flags:   [Boolean],

  // longhand with validation on each element
  keywords: [{
    type:      String,
    trim:      true,
    lowercase: true,
    maxlength: 30
  }]
})

// usage
post.tags.push('nodejs')
post.tags.pull('nodejs')     // Mongoose array method to remove
post.tags.addToSet('react')  // adds only if not already in array

Arrays of Subdocuments

arrays of objects
const orderSchema = new Schema({
  userId: { type: Schema.Types.ObjectId, ref: 'User' },

  items: [{            // array of embedded objects
    productId: { type: Schema.Types.ObjectId, ref: 'Product' },
    name:      { type: String, required: true },
    quantity:  { type: Number, min: 1, required: true },
    price:     { type: Number, required: true }
  }],

  total: Number
})
🩵 Each item in the array automatically gets its own _id — Mongoose adds it. You can disable this with { _id: false } inside the array object definition.
🏠 Nested Objects / Embedded Schemas

Inline Nested Object

inline nested
const userSchema = new Schema({
  name: String,

  // nested object — inline
  address: {
    street: { type: String, required: true },
    city:   { type: String, required: true },
    state:  { type: String },
    zip:    { type: String, minlength: 5 },
    country:{ type: String, default: 'India' }
  }
})

// access
user.address.city  // 'Hyderabad'
user.address.zip   // '500001'

Embedded Schema (Reusable)

reusable embedded schema
// define address schema separately — reusable
const addressSchema = new Schema({
  street:  { type: String, required: true },
  city:    { type: String, required: true },
  zip:     String,
  country: { type: String, default: 'India' }
}, { _id: false })  // no _id on subdoc

const userSchema = new Schema({
  name:            String,
  address:         addressSchema,  // embedded
  billingAddress:  addressSchema   // reused!
})
💡 Nested object vs ref — embed data that always belongs to the parent (address, profile). Use a ref when data is shared across documents (user → orders, product → category).
🔗 ObjectId References — ref & populate

References link documents across collections. Store just the ObjectId in the document, then use populate() to join the related document at query time.

defining references
// User model
const userSchema = new Schema({
  name:  String,
  email: String
})
const User = mongoose.model('User', userSchema)

// Post model — references User
const postSchema = new Schema({
  title:  { type: String, required: true },
  body:   String,
  author: {
    type: Schema.Types.ObjectId,
    ref:  'User',               // 'User' = the model name
    required: true
  },
  tags: [{ type: Schema.Types.ObjectId, ref: 'Tag' }]  // array of refs
})
const Post = mongoose.model('Post', postSchema)
populate — basic
// Without populate — author is just an ObjectId string
const post = await Post.findById(id)
post.author  // ObjectId("64abc...")

// With populate — author is the full User document
const post = await Post.findById(id).populate('author')
post.author.name   // 'John Doe'
post.author.email  // 'john@example.com'

// Populate with field selection — only get name and email
const post = await Post.findById(id).populate('author', 'name email -_id')

// Populate multiple fields
const post = await Post.findById(id)
  .populate('author', 'name')
  .populate('tags', 'name color')

// Deep populate — populate inside populated doc
const post = await Post.findById(id).populate({
  path:     'author',
  populate: { path: 'department', select: 'name' }  // nested populate
})
🩵 populate does a second query — it fetches the referenced documents separately. For large datasets, consider using MongoDB's $lookup aggregation for better performance.
⚙️ 5. Schema Features — Timestamps, Virtuals
🕐 Timestamps & Virtual Fields

Timestamps

Passing { timestamps: true } as schema options auto-adds createdAt and updatedAt fields — Mongoose manages them automatically.

timestamps option
const userSchema = new Schema({
  name:  String,
  email: String
}, {
  timestamps: true   // ← adds createdAt and updatedAt automatically
})

// custom field names
const userSchema = new Schema({...}, {
  timestamps: {
    createdAt: 'created_at',   // custom name
    updatedAt: 'updated_at'
  }
})

// result in MongoDB
{
  _id:       ObjectId("..."),
  name:      "John",
  email:     "john@example.com",
  createdAt: ISODate("2026-01-01T10:00:00Z"),  // auto set on create
  updatedAt: ISODate("2026-01-05T14:30:00Z")   // auto updated on every save
}

Virtual Fields

Virtuals are computed properties that don't get stored in MongoDB. They're derived from other fields at runtime.

virtual fields
const userSchema = new Schema({
  firstName: String,
  lastName:  String,
  birthYear: Number
}, { timestamps: true })

// Virtual: fullName = firstName + lastName (not stored in DB)
userSchema.virtual('fullName')
  .get(function() {
    return `${this.firstName} ${this.lastName}`
  })
  .set(function(v: string) {           // optional setter
    const [first, ...rest] = v.split(' ')
    this.firstName = first
    this.lastName  = rest.join(' ')
  })

// Virtual: age — computed from birthYear
userSchema.virtual('age').get(function() {
  return new Date().getFullYear() - this.birthYear
})

// usage
const user = await User.findById(id)
user.fullName  // 'John Doe' — computed, not stored
user.age       // 25 — computed from birthYear

// Include virtuals in JSON output
const userSchema = new Schema({...}, {
  timestamps: true,
  toJSON:   { virtuals: true },  // include when JSON.stringify() called
  toObject: { virtuals: true }   // include when .toObject() called
})
💗 Virtuals are great for things like fullName, age, profileUrl, totalPrice — computed values you want to expose in your API but don't need to persist.
🔧 6. Instance Methods, Static Methods & Query Helpers
⚡ Methods on Schemas

Instance Methods

Called on a single document instance. Use schema.methods.methodName. Must use regular function (not arrow) so this refers to the document.

instance methods
import bcrypt from 'bcryptjs'

userSchema.methods.comparePassword = async function(
  candidate: string
): Promise<boolean> {
  return bcrypt.compare(candidate, this.password)
}

userSchema.methods.getPublicProfile = function() {
  return {
    id:    this._id,
    name:  this.name,
    email: this.email
    // password excluded
  }
}

// usage — called on a document
const user = await User.findById(id)
const match = await user.comparePassword('mypassword')
const pub   = user.getPublicProfile()

Static Methods

Called on the Model class itself, not on an instance. Use schema.statics.methodName. Good for custom finders.

static methods
userSchema.statics.findByEmail = function(
  email: string
) {
  return this.findOne({ email: email.toLowerCase() })
}

userSchema.statics.findActiveUsers = function() {
  return this.find({ isActive: true })
}

// usage — called on the Model
const user  = await User.findByEmail('john@example.com')
const users = await User.findActiveUsers()

Query Helpers

Extend Mongoose queries — chainable query methods on any query object for that model.

query helpers
userSchema.query.byActive = function() {
  return this.where({ isActive: true })
}

userSchema.query.byRole = function(role: string) {
  return this.where({ role })
}

// chainable on queries
const admins = await User.find().byActive().byRole('admin')
TypeCalled onUse case
Instance methodDocument instance (user.method())Operations on a single doc — hashing, formatting, auth
Static methodModel class (User.method())Custom finders, factory methods
Query helperQuery chain (User.find().helper())Reusable query filters
🪝 7. Middleware — Pre & Post Hooks
🔄 Mongoose Middleware (Hooks)

Middleware runs before (pre) or after (post) specific operations — save, find, delete, validate, etc. Perfect for hashing passwords, logging, cascading deletes.

pre hook — hash password before save
import bcrypt from 'bcryptjs'

// runs BEFORE every .save()
userSchema.pre('save', async function(next) {
  // only hash if password was modified (not on every save)
  if (!this.isModified('password')) return next()

  const salt    = await bcrypt.genSalt(12)
  this.password = await bcrypt.hash(this.password, salt)
  next()
})

// pre validate — runs before validation
userSchema.pre('validate', function(next) {
  if (this.name) this.name = this.name.trim()
  next()
})
post hook — after save / find
// runs AFTER save completes
userSchema.post('save', function(doc) {
  console.log(`User saved: ${doc.email}`)
})

// post find — runs after findOne, find etc.
userSchema.post('findOne', function(doc) {
  if (doc) console.log(`Fetched user: ${doc.email}`)
})

// pre deleteOne — cascade delete (delete related docs before this one)
userSchema.pre('deleteOne', { document: true, query: false }, async function() {
  await Post.deleteMany({ author: this._id })  // delete user's posts
})
HookTriggers on
pre('save')doc.save(), Model.create()
pre('validate')Before validation runs
pre('find')Model.find(), Model.findOne()
pre('findOneAndUpdate')Model.findByIdAndUpdate()
pre('deleteOne')doc.deleteOne()
post('save')After save completes successfully
post('find')After find query returns
⚠️ findByIdAndUpdate does NOT trigger pre('save') — it bypasses Mongoose and goes straight to MongoDB. Use pre('findOneAndUpdate') to intercept it, or use runValidators: true in options to run validation.
🎯 Interview Q&A — Mongoose Schema
💼 Most Asked Interview Questions
Q1 What is the difference between a Mongoose Schema and a Model?
A Schema is just the blueprint — it defines the shape of documents, field types, validation rules, defaults, and methods. It doesn't interact with the database at all.

A Model is the compiled version of a schema — it's the class you use to actually perform CRUD operations (create, read, update, delete) against the MongoDB collection.
Schema → blueprint (no DB interaction) Model → mongoose.model('User', schema) — gives you User.find(), User.create(), etc. Document → new User({...}) — instance of a Model (a single record)
Q2 Why is unique: true NOT a Mongoose validator?
unique: true tells Mongoose to create a MongoDB unique index on that field — it's handled at the database level, not by Mongoose's validation pipeline. When you try to insert a duplicate, MongoDB throws a MongoServerError with code 11000, not a Mongoose ValidationError.

This means it won't be caught by your normal validation error handler — you need to specifically check err.code === 11000.
Q3 What is the difference between minlength and min?
minlength / maxlength are String validators — they check the length of a string (number of characters).
min / max are Number validators — they check the value of a number.

Using minlength on a Number field or min on a String field won't work as expected.
name: { type: String, minlength: 2 } ← min 2 characters age: { type: Number, min: 0 } ← min value of 0
Q4 Why should you use function keyword (not arrow) in schema methods and hooks?
Arrow functions don't have their own this binding — they inherit this from the enclosing scope (the module), not the document or query. In Mongoose middleware and methods, this must refer to the current document (in instance methods / pre save) or the current query (in pre find hooks).

Using an arrow function breaks this.fieldName, this.isModified(), and similar patterns entirely.
Q5 Does findByIdAndUpdate trigger the pre('save') hook?
No. findByIdAndUpdate bypasses Mongoose completely and sends the update directly to MongoDB. It does not trigger pre('save'), post('save'), or any instance method validators.

To run validation on update: pass { runValidators: true, new: true } in options.
To intercept it with middleware: use pre('findOneAndUpdate').
Q6 What is a Virtual field and when would you use it?
A virtual is a computed property derived from other fields at runtime — it's never stored in MongoDB. You define a getter (and optionally a setter) using schema.virtual('fieldName').get(fn).

Use cases: fullName from firstName + lastName, age from birthYear, profileUrl from username, totalPrice from quantity × unitPrice. Anything you want in your API response but don't need to persist.
Q7 What is the difference between embedded documents and references (ref)?
Embedded — the child data is stored inside the parent document. Faster reads (one query), but data duplication if used in multiple places. Good for: address inside user, items inside an order.

Reference — store only the ObjectId, fetch the related doc with populate(). Better for: shared data (user → posts → comments), large datasets where embedding would bloat documents.
Embed when: data belongs only to this parent, read together always Reference when: data is shared, updated independently, or large
Q8 What is a sparse index and why is it needed?
A sparse index only indexes documents where the field exists (is not null/undefined). Without sparse, a unique index on an optional field fails because two documents both with null violate the unique constraint — null is treated as a value.

With sparse: true, documents where the field is null/missing are excluded from the index, so multiple documents can have the field absent without triggering a duplicate key error.
Q9 When would you use Mixed type and what's the catch?
Use Mixed when the shape of a field is truly unknown or varies per document — like an audit log payload, third-party API response, or arbitrary metadata.

The catch: Mongoose can't detect changes to Mixed fields automatically. If you mutate a Mixed field, you must call doc.markModified('fieldName') before doc.save(), otherwise the change won't be persisted.
Q10 What is the difference between instance methods and static methods?
Instance methods (schema.methods.fn) — called on a single document (user.comparePassword()). this = the document.

Static methods (schema.statics.fn) — called on the Model class itself (User.findByEmail()). this = the Model. Good for custom finders and factory methods that don't need an existing document.
