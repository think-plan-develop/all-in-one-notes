6. Relations

RBAC mental model

★★★★★
Role 1 ──────── N User

One Role can be assigned to many Users. Each User has only one Role (simple RBAC).

One-to-One

Each record in A relates to exactly one in B, and vice versa. Example: User and Profile. @unique on the FK enforces one-to-one.

schema.prisma
model User {
  id      Int      @id @default(autoincrement())
  profile Profile?
}

model Profile {
  id     Int  @id @default(autoincrement())
  userId Int  @unique
  user   User @relation(fields: [userId], references: [id])
}

One-to-Many

One record in A relates to many in B. Example: one Role has many Users.

schema.prisma
model Role {
  id    Int    @id @default(autoincrement())
  users User[]
}

model User {
  id     Int  @id @default(autoincrement())
  roleId Int
  role   Role @relation(fields: [roleId], references: [id])
}

Many-to-Many

Records in both tables can relate to multiple records in the other. Prisma auto-creates a hidden join table for implicit M:N.

implicit
model User {
  id          Int          @id @default(autoincrement())
  permissions Permission[]
}

model Permission {
  id    Int    @id @default(autoincrement())
  users User[]
}

Use an explicit join model if you need extra fields on the relationship:

explicit join
model UserPermission {
  userId       Int
  permissionId Int
  assignedAt   DateTime @default(now())
  user         User       @relation(fields: [userId], references: [id])
  permission   Permission @relation(fields: [permissionId], references: [id])
  @@id([userId, permissionId])
}

Self-relations

A model relating to itself — hierarchies (e.g. Role with parentRole):

schema.prisma
model Role {
  id       Int    @id @default(autoincrement())
  name     String
  parentId Int?
  parent   Role?  @relation("RoleHierarchy", fields: [parentId], references: [id])
  children Role[] @relation("RoleHierarchy")
}

Foreign keys vs relation fields

Foreign key

The column storing a reference to another table's PK — e.g. roleId → Role.id.

Relation field

The virtual field for the related object — e.g. role Role @relation(...) — enables user.role.name.

include · nested create / update · connectOrCreate

include eagerly loads related data (like a SQL JOIN):

include
const user = await prisma.user.findUnique({
  where: { id: userId },
  include: { role: true },
});

Nested filter / create / update:

nested
prisma.user.findMany({ where: { role: { name: "ADMIN" } } });

prisma.user.create({
  data: {
    email: "test@example.com",
    role: { connect: { id: 1 } }, // link existing
  },
});

prisma.user.create({
  data: {
    email: "test@example.com",
    role: { create: { name: "GUEST" } }, // create related at same time
  },
});

prisma.user.update({
  where: { id: 1 },
  data: { role: { connect: { id: 2 } } },
});

connectOrCreate — connect if exists, otherwise create (avoids a find-or-create round trip):

connectOrCreate
prisma.user.create({
  data: {
    email: "test@example.com",
    role: {
      connectOrCreate: {
        where: { name: "GUEST" },
        create: { name: "GUEST" },
      },
    },
  },
});

disconnect / set

  • disconnect — removes a relation link without deleting the related record.
  • set — replaces an entire many-to-many list with a new set.
disconnect / set
prisma.user.update({ where: { id: 1 }, data: { role: { disconnect: true } } });

prisma.user.update({
  where: { id: 1 },
  data: { permissions: { set: [{ id: 2 }, { id: 3 }] } },
});
7. Relation Queries

Filter, nest, count, paginate nested

★★★★
relation queries
prisma.user.findMany({ where: { role: { name: "ADMIN" } } });

prisma.role.findMany({
  where: { users: { some: { email: { contains: "gmail" } } } }, // at least one
});
prisma.role.findMany({
  where: { users: { none: { roleId: 3 } } }, // no match
});
prisma.role.findMany({
  where: { users: { every: { isActive: true } } }, // all match
});

prisma.user.findMany({
  include: { role: { include: { permissions: true } } },
});

prisma.user.findMany({
  select: { email: true, role: { select: { name: true } } },
});

prisma.user.findMany({ orderBy: { role: { name: "asc" } } });

prisma.role.findMany({
  include: { _count: { select: { users: true } } },
});

prisma.role.findMany({
  include: { users: { take: 5, orderBy: { createdAt: "desc" } } },
});

some / every / none apply to one-to-many and many-to-many. _count.users returns a count field per role.

8. Filtering & Querying

String, list, comparison, logical

KindOperators
Stringequals · contains · startsWith · endsWith · mode: "insensitive"
Listin · notIn
Comparisongt · gte · lt · lte
LogicalAND · OR · NOT
filters
prisma.user.findMany({
  where: {
    AND: [
      { email: { contains: "gmail" } },
      { roleId: { in: [1, 2] } },
    ],
    NOT: { email: { startsWith: "test" } },
  },
});

// case-insensitive (PostgreSQL)
where: { email: { contains: "GMAIL", mode: "insensitive" } }

// JSON path
prisma.user.findMany({
  where: { metadata: { path: ["theme"], equals: "dark" } },
});

// null
prisma.user.findMany({ where: { deletedAt: null } });
prisma.user.findMany({ where: { deletedAt: { not: null } } });
9. Transactions

All succeed or all fail

★★★★★

Critical for data consistency. API: prisma.$transaction()

Sequential

Array of independent queries, atomically. Use when operations don't depend on each other's results.

Interactive

Callback with tx. Use when a later query needs data (like an ID) from an earlier query.

transactions
await prisma.$transaction([
  prisma.user.create({ data: { email: "a@b.com" } }),
  prisma.auditLog.create({ data: { action: "USER_CREATED" } }),
]);

await prisma.$transaction(async (tx) => {
  const user = await tx.user.create({ data: { email: "a@b.com" } });
  await tx.auditLog.create({
    data: { userId: user.id, action: "USER_CREATED" },
  });
});

await prisma.$transaction(async (tx) => { /* ... */ }, {
  maxWait: 5000,
  timeout: 10000,
  isolationLevel: "Serializable",
});
  • Atomicity — all-or-nothing.
  • Commit — save once every step succeeds.
  • Rollback — undo all if any step fails.
  • Isolation — PostgreSQL default is Read Committed.
  • When — money transfers, user + audit log, inventory + order — any multi-write needing consistency.

11. Raw Queries

Escape hatches

Use when Prisma's API can't express something (complex joins, window functions, CTEs).

raw
const users = await prisma.$queryRaw`SELECT * FROM "User" WHERE email = ${email}`;

await prisma.$executeRaw`UPDATE "User" SET "roleId" = ${2} WHERE "id" = ${1}`;
  • $queryRaw — typed rows; tagged templates are safe from SQL injection.
  • $executeRaw — UPDATE / DELETE / INSERT; returns affected row count.
  • $queryRawUnsafe / $executeRawUnsafe — plain strings; you must sanitize. Only for fully dynamic, trusted queries.
12. Error Handling

Prisma error types

★★★★
TypeWhen
PrismaClientKnownRequestErrorExpected DB errors with a code (unique violation, etc.)
PrismaClientValidationErrorMalformed query (missing required field)
PrismaClientUnknownRequestErrorUnclassified DB errors
PrismaClientInitializationErrorFailed to connect to the database
errors
import { Prisma } from "@prisma/client";

try {
  await prisma.user.create({ data: { email: "test@example.com" } });
} catch (e) {
  if (e instanceof Prisma.PrismaClientKnownRequestError) {
    if (e.code === "P2002") console.log("Email already exists");
    if (e.code === "P2003") console.log("Related record does not exist");
    if (e.code === "P2025") console.log("Record not found");
  }
  throw e;
}
CodeMeaning
P2002Unique constraint failed
P2003Foreign key constraint failed
P2025Record not found (update/delete on missing row)
P2014Relation violation (deleting a still-referenced record)
13. Pagination

Offset vs cursor

★★★★

Offset

Simple, but slows on large offsets — PostgreSQL still scans skipped rows.

Cursor

Faster for large datasets. Unique field as a pointer. Preferred for infinite scroll.

pagination
prisma.user.findMany({ skip: 20, take: 10, orderBy: { id: "asc" } });

prisma.user.findMany({
  take: 10,
  skip: 1, // skip the cursor row itself
  cursor: { id: lastSeenId },
  orderBy: { id: "asc" },
});
14. Prisma Client Configuration

Generate, adapter, singleton

Run prisma generate after every schema change. Custom output:

schema.prisma
generator client {
  provider = "prisma-client-js"
  output   = "../src/generated/prisma"
}

Prisma 7+ uses driver adapters. @prisma/adapter-pg wraps the pg Node driver:

db.ts
import { PrismaClient } from "./generated/prisma";
import { PrismaPg } from "@prisma/adapter-pg";

const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL });
const prisma = new PrismaClient({ adapter });
⚠️ Create one PrismaClient and reuse it. Call prisma.$disconnect() on shutdown. In serverless, use pooling (PgBouncer).

Singleton (avoids exhausting connections during hot-reload):

db.ts
import { PrismaClient } from "@prisma/client";

const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient };

export const prisma = globalForPrisma.prisma ?? new PrismaClient();

if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma;

DATABASE_URL="postgresql://user:password@localhost:5432/mydb" — never commit .env.

15. Security & Best Practices

Regular-use checklist

  • Never pass raw client input into where without validation.
  • Use $queryRaw tagged templates — never string concatenation.
  • Hash passwords (bcrypt/argon2) before create / update.
  • Use select to exclude sensitive fields like passwordHash.
  • Keep DATABASE_URL in env vars, never hardcoded.
  • Reuse a single PrismaClient app-wide.
  • Prefer updateMany / deleteMany / createMany over loops for batch work.
