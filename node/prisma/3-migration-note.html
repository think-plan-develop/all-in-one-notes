1. Migration vs Seed

Keep this distinction very clear

Migration = database structure

Creates or changes: tables, columns, primary keys, foreign keys, indexes, constraints, relations.

Example: Role table, User table, Product table.

Seed = initial / default records

Inserts data into existing tables.

Example Role table:
1 user · 2 admin

📌 Migration → creates/changes structure · Seed → inserts initial/default data
2. What is a Prisma Migration?

You define structure in schema.prisma

prisma/ └── schema.prisma
schema.prisma
model Role {
  id    Int    @id @default(autoincrement())
  name  String @unique
  users User[]
}

model User {
  id            Int      @id @default(autoincrement())
  email         String   @unique
  password_hash String
  role_id       Int
  role          Role     @relation(fields: [role_id], references: [id])
  created_at    DateTime @default(now())
  updated_at    DateTime @updatedAt
}

Prisma compares your schema with the migration history and generates SQL. You don't normally write the SQL yourself.

3. First Migration in a New Project

Building from scratch

You create Role + User models, then:

terminal
npx prisma migrate dev --name init

init is simply the name of the migration. Prisma creates:

prisma/ ├── schema.prisma └── migrations/ └── 20260822xxxxxx_init/ └── migration.sql
schema.prisma
↓
init migration
↓
Role + User tables
4. Why is it called init?

init = initial database structure

It is not a special Prisma keyword. You could write:

terminal
npx prisma migrate dev --name abc

and Prisma would accept it. But --name init is meaningful for the first migration.

5. Adding a New Model Later

Project already has Role + User

Now you add Product. You changed the database structure — create a new migration:

schema.prisma
model Product {
  id   Int    @id @default(autoincrement())
  name String
}
terminal
npx prisma migrate dev --name add_product
prisma/ └── migrations/ ├── 20260801_init/ ├── 20260810_add_roles/ ├── 20260815_add_users/ └── 20260822_add_product/

The new migration contains the SQL required to create the Product table.

6. Why Not Use --name init Again?

You technically can — you shouldn't

Reusing init could create 004_init — confusing. Use a description of the change:

001_init 002_add_roles 003_add_users 004_add_product 005_add_order 006_add_payment
💡 Migration names are descriptions of database changes.
7. What Happens in a Company Project?

You join an existing repo

Git already contains migration history. You do not create init again.

prisma/ ├── schema.prisma └── migrations/ ├── 001_init ├── 002_add_roles ├── 003_add_users └── 004_add_orders

Set up your local database, then:

terminal
npx prisma migrate dev

Prisma checks history. Your local DB might have 001 + 002. The repo has 003 + 004 missing. Prisma applies the missing ones. Your local DB syncs with the project's history.

8. What Does "Apply Existing Migrations" Mean?

Execute files that exist but aren't on your DB yet

Git repository
↓
prisma/migrations/
↓
001_init · 002_users · 003_roles · 004_orders
↓
npx prisma migrate dev
↓
Your local PostgreSQL

You don't manually create those tables. The migration files describe how to create them.

9. How Does Prisma Know What's Already Applied?

Special table: _prisma_migrations

Prisma records migration history in the database:

_prisma_migrations 001_init 002_add_roles 003_add_users

Already applied

Skip

Not applied

Execute

📌 This is why multiple developers can share the same migration history.
10–11. Developer A Adds a Model · Developer B Pulls

Developer A

  1. Adds model Product in schema
  2. Runs npx prisma migrate dev --name add_product
  3. Prisma creates prisma/migrations/20260822_add_product/migration.sql
  4. Commits schema.prisma + migration folder, then pushes to Git

Developer B

Pulls latest code. Does not create another migration. Runs:

terminal
npx prisma migrate dev

Prisma sees 004_add_product missing on B's DB and applies it. Now B also has the Product table.

12. The Two Commands You Need to Remember

You changed schema.prisma

create a migration
npx prisma migrate dev --name add_product
💡 I changed the schema → create a migration.

You cloned / pulled an existing project

apply missing history
npx prisma migrate dev
📌 The migrations already exist → apply what's missing.
13. Complete Developer Workflow

New project

Create / modify schema
↓
npx prisma migrate dev --name init
↓
Migration created
↓
Database structure created

Existing project — joining company

  1. Clone repository
  2. Install dependencies
  3. Configure .env
  4. Create local database
  5. Run npx prisma migrate dev
  6. Existing migrations applied → local DB synchronized

Existing project — you add a model

  1. Modify schema.prisma
  2. npx prisma migrate dev --name add_product
  3. New migration created
  4. Commit migration to Git and push

Other developer

Git pull
↓
npx prisma migrate dev
↓
New migration applied
14. Where Seed Fits

Seed happens after structure exists

Migration
↓
Creates Role table
↓
Seed
↓
Inserts user · admin
prisma/ ├── schema.prisma ├── migrations/ └── seed.ts
⚠️ Follow the company's documented seed command. Don't assume it is safe to run against shared environments.
