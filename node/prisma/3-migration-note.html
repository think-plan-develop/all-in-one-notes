Migration vs seed, how migrate dev works, joining an existing project, and the team workflow

📌 One-line summary: Migration files are the version history of your database structure — developers who change the schema create a new migration, while other developers simply apply that migration to their own database.
🔑 Key Terms at a Glance
🏗️
Migration: Creates or changes database structure — tables, columns, keys, indexes, relations.
🌱
Seed: Inserts initial or default records into tables that already exist.
📜
_prisma_migrations: A special table Prisma maintains to record which migrations have already been applied.
⚙️
migrate dev: With --name it creates a new migration; without it, it applies migrations that already exist but haven't run locally.
1. Migration vs Seed

Migration = Database Structure

It creates or changes things like:

structure
Tables
Columns
Primary keys
Foreign keys
Indexes
Constraints
Relations

Example:

tables
Role table
User table
Product table

Seed = Initial/Default Records

For example:

idname
1user
2admin
💡 Migration → creates/changes structure. Seed → inserts initial/default data.
2. What is a Prisma Migration?

You Define Structure in schema.prisma

schema.prisma
model Role {
  id    Int    @id @default(autoincrement())
  name  String @unique
  users User[]
}

model User {
  id            Int      @id @default(autoincrement())
  email         String   @unique
  password_hash String
  role_id       Int
  role          Role     @relation(fields: [role_id], references: [id])
  created_at    DateTime @default(now())
  updated_at    DateTime @updatedAt
}

Prisma compares your schema with the migration history and generates SQL. You don't normally write the SQL yourself.

3–4. First Migration & the "init" Name

First Migration in a New Project

Suppose you are building your project from scratch, and you define your Role and User models. Then run:

terminal
npx prisma migrate dev --name init

init is simply the name of the migration. Prisma creates:

project structure
prisma/
├── schema.prisma
└── migrations/
    └── 20260822xxxxxx_init/
        └── migration.sql

Why is it Called "init"?

init usually means "initial database structure." It is not a special Prisma keyword — you could technically write:

terminal
npx prisma migrate dev --name abc

and Prisma would accept it. But --name init is meaningful specifically for the first migration.

5–6. Adding a New Model Later

Adding Product to an Existing Project

Suppose the project already has Role and User. Now you add:

schema.prisma
model Product {
  id   Int    @id @default(autoincrement())
  name String
}

You have changed the database structure, so create a new migration:

terminal
npx prisma migrate dev --name add_product

Prisma creates:

migrations/
prisma/
└── migrations/
    ├── 20260801_init/
    ├── 20260810_add_roles/
    ├── 20260815_add_users/
    └── 20260822_add_product/
💡 The new migration contains only the SQL required to create the Product table.

Why Not Reuse --name init?

You technically can, but you shouldn't — it would create something confusing like 004_init. Instead, --name add_product creates 004_add_product, so anyone can read the migration history as a changelog:

migration history
001_init
002_add_roles
003_add_users
004_add_product
005_add_order
006_add_payment
⚠️ Migration names are basically descriptions of database changes — keep them descriptive.
7–9. What Happens in a Company Project

Joining an Existing Company Project

Suppose you join an existing company project. The Git repository already contains:

repository
prisma/
├── schema.prisma
└── migrations/
    ├── 001_init
    ├── 002_add_roles
    ├── 003_add_users
    └── 004_add_orders
⚠️ You do not create init again. Set up your local database, then run:
terminal
npx prisma migrate dev

Prisma checks the existing migration history and compares it against your local database:

MigrationYour Local DBRepository
001_init✅ Applied✅ Present
002_add_roles✅ Applied✅ Present
003_add_users⬅️ Missing✅ Present
004_add_orders⬅️ Missing✅ Present
✅ Prisma applies the missing migrations (003_add_users, 004_add_orders), and your local database becomes synchronized with the project's migration history.

What Does "Apply Existing Migrations" Mean?

It simply means: execute migration files that already exist in the project but have not yet been applied to your local database.

💡 You don't manually create those tables — the migration files describe exactly how to create them.
How Prisma Knows What's Already Applied

The _prisma_migrations Table

Prisma maintains a special table in the database that records migration history:

_prisma_migrations
001_init
002_add_roles
003_add_users

So Prisma can determine, for every migration file:

  • Already applied → skip
  • Not applied → execute
✅ This is why multiple developers can work with the same migration history without stepping on each other.
10–11. Developer A Adds a Model, Developer B Gets It

Developer A Adds a New Model

Developer A adds a Product model, then runs:

terminal
npx prisma migrate dev --name add_product

Prisma creates prisma/migrations/20260822_add_product/migration.sql. Developer A commits schema.prisma and the migration folder, and pushes them to Git.

Developer B Gets the Change

Developer B pulls the latest code. They don't create another migration — they run:

terminal
npx prisma migrate dev
MigrationDeveloper B's DBRepository
001_init✅✅
002_roles✅✅
003_users✅✅
004_add_product❌✅
✅ Prisma applies 004_add_product, and now Developer B also has the Product table.
12. The Two Commands You Need to Remember
⭐ Important — Remember This

You Changed schema.prisma

Create a new migration:

terminal
npx prisma migrate dev --name add_product
💭 Think: I changed the schema → create a migration.

You Cloned/Pulled an Existing Project

Apply existing migration history:

terminal
npx prisma migrate dev
💭 Think: The migrations already exist → apply what's missing.

14. Where Seed Fits

Seed Happens After Structure Exists

A company project may have:

structure
prisma/
├── schema.prisma
├── migrations/
└── seed.ts
⚠️ Follow the company's documented seed command rather than assuming it's safe to run against shared environments.
15. Final Mental Model

Four Cases to Remember

SituationCommand
First database structurenpx prisma migrate dev --name init
You add/change schemanpx prisma migrate dev --name describe_change
You pull existing migrationsnpx prisma migrate dev
Need initial/default recordsSeed command

The Easiest Way to Remember

schema.prisma ↓ "I changed the structure" ↓ migrate dev --name <what_changed>

Whereas:

Git repository ↓ "Migration already exists" ↓ migrate dev

And:

"Tables exist, but need default records" ↓ seed
