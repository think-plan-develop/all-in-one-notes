Q1. Input Validation
Zod Middleware
What it means:

Every request — body, params, query — must be validated at the route/middleware level before your controller or DB ever sees it. Use Zod (recommended with TypeScript) to define a schema and reject bad data immediately with a structured error response.

How the Flow Works

Request ↓ Zod Middleware ↓ ✅ Valid → Controller → Service → DB ❌ Invalid → 400 Bad Request (structured error returned)

Install

terminal
npm install zod

Define Schema + Infer Type

schemas/user.schema.ts
import { z } from 'zod';

export const userSchema = z.object({

  firstName: z.string()
    .trim()
    .min(2)
    .max(50),

  lastName: z.string()
    .trim()
    .min(1),

  email: z.email()
    .toLowerCase(),

  role: z.enum([
    "ADMIN",
    "USER",
    "MASTER_USER"
  ]).default("USER"),

  isActive: z.boolean()
    .default(true),

  age: z.number()
    .int()
    .min(18)
    .max(100),

  birthDate: z.coerce.date()
    .optional(),

  salary: z.number()
    .optional(),

  skills: z.array(
    z.string()
  ).optional(),

  phoneNumbers: z.array(
    z.number()
  ).optional(),

  address: z.object({
    city:    z.string().optional(),
    state:   z.string().optional(),
    country: z.string().optional(),
    zipCode: z.number().optional()
  }).optional(),

  socialLinks: z.object({
    github:   z.url().optional(),
    linkedin: z.url().optional(),
    website:  z.url().optional()
  }).optional(),

  settings: z.record(
    z.string(),
    z.string()
  ).optional(),

  posts: z.array(
    z.string()
  ).optional()

});

// Infer TypeScript type from schema — no duplication!
export type UserInput = z.infer<typeof userSchema>;

Reusable Validate Middleware

middleware/validate.ts
import type { Request, Response, NextFunction } from "express";
import { z } from "zod";

export const validate =
  (schema: z.ZodType) =>
  (req: Request, res: Response, next: NextFunction) => {

    const result = schema.safeParse(req.body);

     if (!result.success) {
      const errors = result.error.issues.map(e => ({
        field:   e.path.join('.'),
        message: e.message,
      }));
      return res.status(400).json({ success: false, errors });
    }

    req.body = result.data;   // replace with sanitised + typed data
    next();
  };

Use in Route

routes/user.route.ts
router.post('/users', validate(userSchema), createUser);
// If body is invalid → 400 auto. Never reaches createUser.

Key Points

  • →safeParse never throws — returns { success, data, error } safely
  • →Zod infers TypeScript types from the schema — write once, types are free
  • →Assigning req.body = result.data automatically strips unknown fields
💬 Interview Question

Q: Where should validation happen — middleware or controller?
A: Middleware. Controllers should only handle business logic. Validation is a cross-cutting concern — one reusable middleware handles it for all routes without any code repetition.

💬 Interview Question

Q: What's the difference between .parse() and .safeParse()?
A: .parse() throws a ZodError on failure — you'd need a try/catch and risk an unhandled rejection if you forget it. .safeParse() never throws; it always returns { success, data | error }, which is exactly what an Express middleware needs since you can't easily catch sync throws inside route handlers without extra wrappers.

💬 Interview Question

Q: What does z.ZodType mean as a parameter type, and why use it instead of a specific schema type?
A: z.ZodType is the base type for any Zod schema. Typing the validate factory's parameter as schema: z.ZodType makes it generic — the same validate() function can be reused for userSchema, loginSchema, productSchema, etc., instead of writing a separate middleware per schema.

💬 Interview Question

Q: What is e.path in a Zod issue, and why do we call .join('.') on it?
A: e.path is an array representing the location of the failed field inside a (possibly nested) object — e.g. ['address', 'zipCode']. .join('.') converts it into a single dotted string "address.zipCode", which is easier to display in API error responses and map to frontend form fields.

💬 Interview Question

Q: Why reassign req.body = result.data instead of just leaving the original req.body?
A: result.data is the output of Zod's parsing — it has defaults applied (e.g. role defaults to "USER"), transforms run (e.g. .trim(), .toLowerCase()), coercions done (e.g. z.coerce.date()), and unknown keys stripped. The original req.body is raw, untyped, and untransformed — using it instead would throw away all of Zod's work.

🧠 Syntax Cheat Sheet — Memorize the Pattern

📝 The Curried Middleware Pattern

(schema: z.ZodType) => (req: Request, res: Response, next: NextFunction) => {...}

Read it as "a function that returns a function":
  • →Outer function — takes the schema as a config argument. This runs once, when you write validate(userSchema) in your route file.
  • →Inner function — the actual Express middleware (req, res, next). This runs every time a request hits that route, and it "remembers" the schema via closure.
  • →This is why you write validate(userSchema) — not validate(req, res, next, userSchema) — in router.post().
// 1. CHECK SUCCESS const result = schema.safeParse(req.body); // result = { success: true, data: {...} } ← validation passed // | { success: false, error: {...} } ← validation failed if (!result.success) { /* handle error */ } // 2. MAP ERRORS result.error.issues.map(e => ({ field: e.path.join('.'), // e.path = ['address','zipCode'] → "address.zipCode" message: e.message, // human-readable message, e.g. "Expected number, received string" })); // 3. PASS DATA FORWARD req.body = result.data; // typed + sanitised — old req.body is discarded next(); // hand control to the next middleware/controller
PieceMeaning
safeParse()Never throws. Always returns { success, data | error }. Use this in middleware — never .parse() (which throws).
result.successboolean — the gate. true → use result.data. false → use result.error.
result.error.issuesArray of every failed rule. Each issue has .path (array) and .message (string).
e.path.join('.')Turns a nested path array into a dotted string for frontend display, e.g. address.zipCode.
result.dataOnly present when success: true. Fully typed, defaults applied, unknown keys stripped.
z.ZodTypeGeneric type for "any Zod schema" — lets validate() accept userSchema, loginSchema, etc.
💬 Interview Question

Q: Why does validate have two sets of parentheses — (schema) => (req, res, next) => {}?
A: It's a higher-order function (factory pattern). Express middleware signatures are fixed to (req, res, next) — you can't pass extra arguments directly. By wrapping it in an outer function that takes schema and returns the real middleware, the returned function "closes over" schema and still matches Express's expected signature.

Q2. Schema-Level Validation (Mongoose)
Mongoose Last Safety Net
What it means:

Even after input validation, define constraints directly in your Mongoose schema. This is a backup layer — it catches invalid data that bypasses the API entirely, such as seeding scripts, admin tools, or internal service calls that write directly to the DB.

Two Layers of Protection

1
Layer 1 — Zod (API layer)

Catches bad HTTP request input before it reaches your controller.
2
Layer 2 — Mongoose Schema

Catches bad data from ANY source — API, scripts, cron jobs, seeds.

Mongoose Schema with Validators

models/User.ts
import { Schema, model } from 'mongoose';

const userSchema = new Schema({

  name: {
    type:      String,
    required:  [true, 'Name is required'],
    trim:      true,
    minlength: [2,  'Min 2 characters'],
    maxlength: [50, 'Max 50 characters'],
  },

  email: {
    type:      String,
    required:  [true, 'Email is required'],
    unique:    true,   // DB index — NOT a validator
    lowercase: true,
    validate: {
      validator: (v: string) => /\S+@\S+\.\S+/.test(v),
      message:  'Invalid email format',
    },
  },

  role: {
    type:    String,
    enum:    { values: ['admin', 'user', 'guest'],
               message: '{VALUE} is not a valid role' },
    default: 'user',
  },

  age: {
    type: Number,
    min:  [18,  'Must be 18 or above'],
    max:  [100, 'Must be 100 or below'],
  },

}, { timestamps: true });

export const User = model('User', userSchema);

Flow — How an Error Reaches errorHandler

1
Controller calls Mongoose
await User.create(req.body) — req.body already cleaned by Zod (Layer 1).
2
Mongoose runs schema validators
required, min, max, enum, custom validate, etc.
✅ all pass → document saved → normal res.json(...)
❌ fails → Mongoose throws ValidationError | CastError | driver E11000
3
Your async controller must catch it
try { await User.create(req.body) } catch (err) { next(err) }
→ next(err) passes the error to Express.
4
Express sees next(err) was called
→ SKIPS all normal routes/middleware
→ looks for middleware with 4 params: (err, req, res, next)
5
errorHandler(err, req, res, next) runs
→ checks err instanceof ValidationError / CastError / err.code
→ sends formatted { success:false, errors:[...] } response
controllers/user.controller.ts
export const createUser = async (req: Request, res: Response, next: NextFunction) => {
  try {
    const user = await User.create(req.body);  // req.body already cleaned by Zod (Layer 1)
    return res.status(201).json({ success: true, data: user });
  } catch (err) {
    next(err);  // ← hand off to errorHandler, do NOT res.json() here
  }
};
app.ts
import express from "express";
import userRoutes from "./routes/user.routes";
import { errorHandler } from "./middleware/errorHandler";

const app = express();

app.use(express.json());
app.use("/users", userRoutes);

// ⚠️ MUST be registered LAST — after all routes
app.use(errorHandler);
📝 Two Different "Layers", Two Different Catch Points

  • →Layer 1 (Zod) — caught inside the validate() middleware itself via safeParse(). It responds directly with res.status(400).json(...) and never calls next(err) — the request stops here, before req.body ever reaches the controller.
  • →Layer 2 (Mongoose) — caught inside the controller's try/catch (or via an async wrapper), then forwarded with next(err) to the global errorHandler. The controller itself never builds the error response.
💬 Interview Question

Q: What happens if you forget try/catch (or next(err)) in an async controller and Mongoose throws?
A: An unhandled promise rejection — Express (in versions before 5) won't automatically catch it, so the request hangs and never sends a response (or crashes the process depending on setup). This is why teams wrap async controllers in a helper like asyncHandler(fn) that automatically does .catch(next) for every route.

middleware/errorHandler.ts
import type { Request, Response, NextFunction } from "express";
import { Error as MongooseError } from "mongoose";

export const errorHandler = (
  err: any,
  req: Request,
  res: Response,
  next: NextFunction
) => {

  // Mongoose Validation Error
  if (err instanceof MongooseError.ValidationError) {
    const errors = Object.values(err.errors).map(error => ({
      field: error.path,
      message: error.message,
    }));
    return res.status(400).json({
      success: false,
      errors,
    });
  }

  // Duplicate Key Error
  if (err.code === 11000) {
    return res.status(409).json({
      success: false,
      message: "Duplicate value found",
      fields: Object.keys(err.keyPattern),
    });
  }

  // Cast Error (Invalid MongoDB ObjectId)
  if (err instanceof MongooseError.CastError) {
    return res.status(400).json({
      success: false,
      message: `Invalid ${err.path}`,
    });
  }

  return res.status(500).json({
    success: false,
    message: err.message || "Internal Server Error",
  });
};
Error TypeTriggerStatus
MongooseError.ValidationErrorA field fails a schema validator (required, min, enum, custom validate, etc.) during .save() / .create()400
err.code === 11000A unique: true index is violated — duplicate value for a unique field409
MongooseError.CastErrorA value can't be cast to the field's type — most commonly an invalid ObjectId passed in a route param like /users/:id400
Anything elseUnhandled / unexpected error500
📝 Reading err.errors vs err.errors[field].path/.message

err.errors is an object, keyed by field name — e.g. { age: ValidatorError, email: ValidatorError }.
Object.values(err.errors) turns it into an array of ValidatorError objects so you can .map() over them.
Each one has .path (the field name, e.g. "age") and .message (e.g. "Must be 18 or above") — same shape as the Zod error response from Layer 1, so your frontend handles both identically.
// Same response shape from BOTH layers: { success: false, errors: [{ field: "age", message: "Must be 18 or above" }] } // Layer 1 (Zod) → e.path.join('.') → field // Layer 2 (Mongoose)→ error.path → field // Frontend doesn't need to know which layer caught it.
💬 Interview Question

Q: Why check err.code === 11000 separately, outside the ValidationError check?
A: A duplicate-key error is thrown by the MongoDB driver, not by Mongoose's validation pipeline — it's not an instance of MongooseError.ValidationError. It only happens when a unique index is violated at the database level, so it needs its own check with its own status code (409 Conflict instead of 400 Bad Request).

💬 Interview Question

Q: When does a CastError happen, and how is it different from a ValidationError?
A: CastError happens before validation even runs — when Mongoose tries to convert an incoming value to the schema's declared type and fails. The classic case: GET /users/123abc where 123abc isn't a valid ObjectId, so findById("123abc") throws a CastError. ValidationError happens during .save()/.create() when a value is the right type but fails a rule like min, required, or enum.

💬 Interview Question

Q: This errorHandler takes 4 arguments including err — how does Express know to treat it as an error handler?
A: Express identifies error-handling middleware purely by arity (4 params): (err, req, res, next). It must be registered last, after all routes, with app.use(errorHandler). Any next(err) call (or a thrown error in an async route wrapped properly) skips all normal middleware and jumps straight here.

Quick Comparison

⚠️ Remember

unique: true in Mongoose creates a database index, not a Mongoose validator. It throws a duplicate key error (E11000), not a ValidationError. Always handle it separately in your global error middleware.
💬 Interview Question

Q: If you already validate with Zod, why add Mongoose validators?
A: Zod only protects the HTTP API layer. Data can enter the DB from seeding scripts, cron jobs, or internal services. Mongoose validators run on every .save() regardless of the source — they are the true last line of defense.

Q3. DTO Pattern
TypeScript Zod
What it means:

A DTO (Data Transfer Object) is a plain typed object that defines the exact shape of data flowing between layers — request → controller → service → DB. In TypeScript, Zod's z.infer gives you DTOs for free with zero extra boilerplate.

Without DTO vs With DTO

Without DTOWith DTO
Every function accepts any or raw req.body. No type safety, no autocomplete. A typo silently passes through. Every layer knows the exact shape. TypeScript catches mismatches at compile time. Editor autocompletes every field.

Define DTOs from Zod Schemas

dtos/user.dto.ts
import { z } from 'zod';

// Schema = validation rules
export const createUserSchema = z.object({
  name:     z.string().min(2),
  email:    z.string().email(),
  password: z.string().min(8),
});

// DTO = inferred TypeScript type — zero duplication
export type CreateUserDTO = z.infer<typeof createUserSchema>;
// Result: { name: string; email: string; password: string }

// .partial() makes all fields optional — perfect for PATCH
export const updateUserSchema = createUserSchema.partial();
export type UpdateUserDTO   = z.infer<typeof updateUserSchema>;
// Result: { name?: string; email?: string; password?: string }

Use DTO in Service Layer

services/user.service.ts
import { CreateUserDTO } from '../dtos/user.dto';
import { User }          from '../models/User';

export const createUser = (dto: CreateUserDTO) => {
  // dto.name, dto.email — fully typed and autocompleted
  return User.create(dto);
};

Data Flow Across Layers

HTTP req.body (unknown / any) ↓ validate middleware → Zod parses and strips unknown fields CreateUserDTO (fully typed) ↓ Controller passes DTO to service createUser(dto: CreateUserDTO) ↓ Service passes to Mongoose User.create(dto) → MongoDB
💬 Interview Question

Q: What is a DTO and why use it over passing req.body directly?
A: A DTO is a typed contract for data moving between layers. Passing req.body directly spreads the any type everywhere — TypeScript cannot help you. DTOs give compile-time safety, autocomplete, and make refactoring safe across all layers.

Q4. Async Validation
Service Layer DB Checks
What it means:

Some validation requires hitting the database — "is this email already registered?", "does this product ID exist?". These checks cannot live in Zod (Zod handles shape/format). Async validation belongs in the service layer, expressed as reusable helper functions.

Pattern — Service-Level Async Check

services/user.service.ts
import { User }        from '../models/User';
import { CreateUserDTO } from '../dtos/user.dto';
import { AppError }     from '../utils/AppError';

export const createUser = async (dto: CreateUserDTO) => {

  // ✅ Async DB check — is email already taken?
  const existing = await User.findOne({ email: dto.email });
  if (existing)
    throw new AppError('Email already registered', 409);

  return User.create(dto);
};

Reusable Async Validators — Avoid Repetition

utils/dbValidators.ts
import { AppError } from './AppError';

// Generic "must exist" helper
export const mustExist = async (Model: any, id: string, label: string) => {
  const doc = await Model.findById(id);
  if (!doc) throw new AppError(`${label} not found`, 404);
  return doc;
};

// Generic "must be unique" helper
export const mustBeUnique = async (Model: any, filter: object, msg: string) => {
  const doc = await Model.findOne(filter);
  if (doc) throw new AppError(msg, 409);
};

// Usage anywhere in services:
await mustBeUnique(User,    { email }, 'Email already taken');
await mustExist   (Product, productId, 'Product');

Custom AppError Class

utils/AppError.ts
export class AppError extends Error {
  constructor(
    public message:    string,
    public statusCode: number = 400
  ) {
    super(message);
  }
}

Key Points

  • →Zod validates shape and format. Service layer validates business rules that need a DB query
  • →Extract common checks into reusable helpers — never repeat findOne in every service
  • →Always throw AppError with the correct HTTP status code and let the global error handler send the response
💬 Interview Question

Q: Can I do async validation inside Zod using .refine()?
A: Technically yes, but it is not recommended. Zod is for structure and format. Putting DB calls inside Zod middleware creates tight coupling and makes the logic hard to reuse. Async business-rule checks belong in the service layer.

Q5. Sanitization
NoSQL Injection Clean Data
What it means:

Sanitization is transforming incoming data — trimming whitespace, lowercasing emails, stripping unknown fields, removing $ operators that could be used in NoSQL injection attacks. Zod handles most of this automatically when you parse; pair it with express-mongo-sanitize for full protection.

Zod Transforms — Sanitize While You Validate

schemas/user.schema.ts
export const createUserSchema = z.object({

  name: z.string()
    .trim()             // "  John  "  →  "John"
    .min(2),

  email: z.string()
    .email()
    .toLowerCase(),     // "JOHN@GMAIL.COM"  →  "john@gmail.com"

  age: z.string()
    .transform(Number) // query param "25"  →  number 25
    .pipe(z.number().min(18)),

});

// Zod strips unknown fields by default on .parse()
// Extra fields in req.body are silently dropped — safe!

NoSQL Injection Prevention

app.ts
import mongoSanitize from 'express-mongo-sanitize';

// Removes keys starting with $ or containing a dot
// Prevents: { "email": { "$gt": "" } } attacks
app.use(mongoSanitize());

// npm install express-mongo-sanitize
// npm install -D @types/express-mongo-sanitize

💡 Key Insight

When you assign req.body = result.data after Zod parses, you have already sanitized. Zod only returns the fields you defined — all unknown fields are gone. Pair this with express-mongo-sanitize and you cover 95% of sanitization with almost no extra effort.
💬 Interview Question

Q: What is NoSQL injection and how do you prevent it in MongoDB?
A: An attacker sends { "email": { "$gt": "" } } in the request body. MongoDB treats $gt as a query operator and returns all users, bypassing authentication. Prevention: use express-mongo-sanitize to strip $-keyed fields, and use Zod to accept only the exact expected shape.
