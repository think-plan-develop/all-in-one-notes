1. What Is JWT?

Definition

★★★★★

JWT (JSON Web Token) is a token that a server creates after successfully authenticating a user.

The token contains information called claims, such as:

payload.json
{
  "userId": 101,
  "role": "admin"
}

The server also signs the token using a secret key or private key. The client then sends this token with future requests.

Login → Token → Verified Flow

LOGIN — Email + Password
↓
Server verifies user
↓
Server creates JWT
↓
Client receives JWT
↓
Client sends JWT later
↓
Server verifies JWT
↓
Authenticated ✓

Why Do We Need the Signature?

Suppose the JWT contains role: "user". An attacker could decode it and change it to role: "admin".

But changing the payload makes the original signature invalid. The server verifies the signature:

JWT received
↓
Verify signature
↓
Signature valid?
Yes → Continue
No → Reject
💡 The signature helps the server detect that the token was not modified and was created by someone possessing the signing key.
📌 JWT payload is normally encoded, not encrypted. JWT = readable claims + signature — not encrypted secret data. Never put passwords or sensitive data in the payload.
2. Why JWT?

The Core Reason

★★★★★

The main reason JWT is useful is that the server can authenticate a request by verifying the token itself, instead of looking up a server-side session on every request.

Session-Based Authentication

User Login
↓
Server creates session
↓
Redis: abc123 → userId: 101
↓
Session ID → Client
↓
GET /profile · Cookie: abc123
↓
Redis lookup → Auth ✓

How JWT Changes This

User Login
↓
Server verifies credentials
↓
Creates signed JWT
↓
Client receives JWT
↓
GET /profile · Bearer JWT
↓
Verify · exp · claims → userId=101 · Auth ✓
💡 The server doesn't need a traditional sessionId → userId lookup just to identify the user.
3. Why Is This Called Stateless?

What "Stateless" Means Here

★★★★★

Because the server does not need to maintain a session record for each authenticated access token. The token itself carries the information required to identify the user.

Session

Client → Session ID → Server → Redis/DB → Find user

Auth state lives on the server.

JWT

Client → JWT → Server → Verify JWT → Read claims

Auth info travels with the request.

Why Is Stateless Useful?

With multiple backend servers behind a load balancer, each server can verify the JWT using the signing key. It doesn't need to ask "which server has this user's session?"

Load Balancer
Server A
Server B
Server C
Request + JWT → any server can verify independently
💡 Especially useful for: horizontally scaled APIs · microservices · mobile + web clients · distributed systems
📌 Don't say "JWT is better than sessions." Say: JWT is useful for stateless auth in distributed systems. Sessions can be simpler when server-side management and immediate revocation matter.
🎤 Interview Answer — What Is JWT and Why Do We Use It?
JWT stands for JSON Web Token. It is a signed token created by the server after a user successfully logs in. It contains claims such as the user's ID and role. The client sends the JWT with subsequent requests, and the server verifies its signature and expiration to authenticate the user.

JWT is commonly used for stateless authentication because the server can verify the token without maintaining a traditional session record for every request. This makes it especially useful for APIs, distributed systems, and horizontally scaled applications.

Key Terms

  • Header — Metadata: which algorithm signed the token
  • Payload — Claims about the user/token (encoded, not encrypted)
  • Signature — Proof the token wasn't modified after signing
  • Claims — Individual pieces inside the payload (userId, role, exp…)
  • Secret / Private Key — Used to produce (and verify) the signature
  • Expiration (exp) — Timestamp after which the server must reject the token
5. Header

Signing Metadata

★★★★

The header contains metadata: which signing algorithm was used, and what type of token this is.

header.json
{
  "alg": "HS256",
  "typ": "JWT"
}

alg — signing algorithm (HS256, RS256, ES256…). typ — identifies this as a JWT.

⚠️ The header is only Base64URL-encoded, not encrypted — anyone holding the JWT can decode and read it.
6. Payload & Claims

What's Inside the Payload

★★★★★

The payload contains claims — information about the user or the token.

payload.json
{
  "userId": 101,
  "role": "admin"
}

After verification, the server reads these values directly:

read-claims.js
const decoded = jwt.verify(token, process.env.JWT_SECRET);
console.log(decoded.userId); // 101
console.log(decoded.role);   // admin
📌 The payload is not encrypted. Anyone with the token can decode and read it. Signature protects against undetected modification — not visibility. Never put passwords or card numbers in a JWT.

7. Expiration (exp)

Why exp Matters

★★★★★

exp tells the server: after this time, don't accept this JWT. It's a Unix timestamp in seconds.

sign-token.js
const token = jwt.sign(
  { userId: 101, role: "user" },
  process.env.JWT_SECRET,
  { expiresIn: "15m" }
);
⚠️ If a JWT is stolen and has no expiration, it stays valid indefinitely. Short-lived access tokens limit the damage window.
8. Signature

Integrity, Not Confidentiality

★★★★★

The signature lets the server verify the JWT was created with the correct signing key, and that the header/payload weren't modified.

For HS256:

Header + "." + Payload + Secret
↓
HMAC-SHA256
↓
Signature
📌 Signature provides integrity and authenticity, not confidentiality. An attacker can read the payload, but cannot forge a valid new signature without the key.
9. HS256 vs RS256

Symmetric (HS256)

★★★★

One secret key for both signing and verifying. Whoever has the secret can create valid tokens and verify them.

hs256.js
// Signing
const token = jwt.sign({ userId: 101 }, process.env.JWT_SECRET, { expiresIn: "15m" });

// Verifying — same secret
jwt.verify(token, process.env.JWT_SECRET);

Best for: single backend that issues and verifies its own tokens. Simple.

Downside: secret must be shared with every verifying service. One compromised service = can forge tokens for the whole system.

Asymmetric (RS256)

Private key signs. Public key verifies. You cannot derive the private key from the public one.

rs256.js
const privateKey = fs.readFileSync("private.pem");
const publicKey = fs.readFileSync("public.pem");

// Auth server signs with private key
const token = jwt.sign({ userId: 101 }, privateKey, {
  algorithm: "RS256",
  expiresIn: "15m"
});

// Any service verifies with public key only
jwt.verify(token, publicKey, { algorithms: ["RS256"] });

Best for: microservices, central auth server, third-party verification, OAuth/OIDC providers.

Downside: more setup (key pair, rotation, distribution); computationally heavier.

Side-by-Side

HS256RS256
TypeSymmetricAsymmetric
Signing keySecretPrivate key
Verification keySame secretPublic key
Shared with verifiers?YesNo (only public key)
If verifier compromisedCan forge tokensCannot forge (no private key)

📌 Rule of thumb: same server issues and checks → HS256. Multiple services verify tokens from one authority → RS256.
10. What Happens on Every Request?

Verification Pipeline

★★★★★
1. Client sends Authorization: Bearer <JWT>
↓
2. Server reads header → determines algorithm
↓
3. Reads payload → extracts claims
↓
4. Verifies signature with secret / public key
↓
5. Checks expiration (exp)
↓
Invalid/expired → 401 Unauthorized
Valid → check role for authorization
↓
No permission → 403 Forbidden
Else → Allow

11. Node.js Examples

Create & Verify

★★★★★

Create JWT

create-token.js
import jwt from "jsonwebtoken";

const token = jwt.sign(
  { userId: 101, role: "admin" },
  process.env.JWT_SECRET,
  { expiresIn: "15m" }
);

console.log(token);

Verify JWT

verify-token.js
try {
  const decoded = jwt.verify(token, process.env.JWT_SECRET);
  console.log(decoded);
} catch (error) {
  console.log("Invalid or expired token");
}
