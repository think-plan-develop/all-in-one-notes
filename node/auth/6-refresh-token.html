JWT Access + Refresh Token Flow

A complete, interview-ready guide to the authentication lifecycle — from short-lived access tokens to secure refresh-token rotation and revocation.

Why Access Tokens Expire Why Refresh Tokens Exist Access vs Refresh Refresh Token Lifetime /refresh Endpoint Generate Access Token Token Rotation Revocation Logout Token Theft Complete Flow Interview Q&A
📌 In short: Short-lived access tokens authorize API calls; longer-lived refresh tokens silently obtain new access tokens. Rotation, revocation, and reuse detection are what keep this system secure.
🔑 Key Terms at a Glance
🔑
Access Token: Short-lived JWT (e.g. 15 min) sent with every API request to prove identity.
🔄
Refresh Token: Long-lived credential (e.g. 7–30 days) used only to obtain a new access token.
🛡️
Rotation: Every refresh issues a brand-new refresh token and invalidates the old one.
🚫
Revocation: Server-side invalidation of a refresh token on logout, password change, or suspected theft.
🚨
Reuse Detection: Sending an already-rotated refresh token signals theft and revokes the whole token family.
1. Why Access Tokens Expire

What an Access Token Is

★★★★★

An access token is used to access protected APIs.

GET /api/profile
Authorization: Bearer <access_token>

What's Inside a JWT

A JWT has three parts: header.payload.signature

Header
Algorithm + type
(e.g. HS256, JWT)
Payload
Claims: userId, role,
exp (expiry)
Signature
Signed with secret
or private key
The signature lets the server trust the payload without a DB lookup. Any tampering invalidates the signature — this is why JWTs are useful for access tokens.

Short Lifetime, Bounded Damage

Access tokens should have a short lifetime: 15 min

❌ Without expiration

Attacker steals token
↓
Can access APIs
↓
Valid for months/years
↓
Very dangerous

✅ With short expiration

Attacker steals token
↓
Can access APIs
↓
Expires after 15 min
↓
Limited damage
⚠️ Important nuance: Expiry doesn't prevent misuse during the valid window — it only bounds the blast radius. A stolen token still works for those 15 minutes. Short expiry limits how long damage can occur, not whether it can occur.
2. Why Refresh Tokens Exist

The Problem They Solve

★★★★★

If access tokens expire quickly, the user shouldn't have to log in every 15 minutes. That's where the refresh token comes in.

User Login
↓
Access Token 15 min + Refresh Token 7 days

When the Access Token Expires

Client detects access token expired
↓
Send refresh token → POST /refresh
↓
Server validates refresh token
↓
New access token issued

❌ Without refresh token

Access Token expires → User must log in again

✅ With refresh token

Access Token expires → Silent refresh → New Access Token

✅ Key takeaway: Refresh tokens allow short-lived access tokens without forcing frequent logins.

Don't think: "Refresh token is just a longer access token."
Think: Access Token → "I want to access this API". Refresh Token → "I want a new access token".

Where Each One Should Live

Access token: Often kept in memory (a JS variable), not localStorage. localStorage is readable by any injected script — a single XSS bug means instant token theft.

Refresh token: Kept in an HttpOnly cookie so client-side JS can't read it. This limits XSS impact, but opens the door to CSRF (browsers auto-attach cookies). Mitigate with SameSite=Strict/Lax and sometimes an anti-CSRF token.

4. Refresh Token Lifetime

Typical Lifetimes

★★★★

Refresh tokens live much longer than access tokens. Exact lifetime depends on the application's security requirements.

Access Token
15 minutes
Refresh Token
7–30 days
⚠️ Longer refresh-token lifetime = longer convenience + longer potential exposure. If stolen, an attacker may continuously obtain new access tokens.

Sliding vs Absolute Expiration

🔄 Sliding

Every refresh extends the refresh token's expiry. An active user is never forced to log out.

⏳ Absolute

Hard ceiling (e.g. 30 days from original login) regardless of activity. Forces periodic re-login.

Many systems combine both — sliding expiry with an absolute cap.

5. /refresh Endpoint

How It Works

★★★★★

The /refresh endpoint issues a new access token. The refresh token is commonly sent via an HttpOnly Secure cookie.

POST /auth/refresh
Client sends refresh token
↓
Server validates token
↓
Check expiration · revocation · session
↓
Generate new Access Token

CSRF Protection

🛡️ Because the refresh token rides in a cookie, the browser attaches it automatically — including to requests from malicious sites. Use SameSite=Strict/Lax + anti-CSRF token or custom header that cross-site requests can't replicate.

7. Refresh Token Rotation

What Rotation Means

★★★★★

Instead of reusing the same refresh token forever, rotate it on every refresh.

❌ No rotation

RT-A → new Access Token
↓
RT-A again → new Access Token
↓
… forever

✅ With rotation

RT-A → Access-B + RT-B
↓
RT-B → Access-C + RT-C
↓
… each refresh is unique

Why It Matters

Suppose an attacker steals RT-A. The legitimate user uses it first → server issues RT-B and invalidates RT-A. When the attacker later tries RT-A, the server detects reuse of an already-rotated token → strong signal of theft.

Token Families

Rotated tokens are grouped into a family (linked by a shared familyId):

Login → RT1 (family F1)
↓
RT2 (family F1)
↓
RT3 (family F1)

If reuse of any token in the family is detected, the server revokes the entire family — because the attacker may have already rotated forward.

8. Refresh Token Revocation

Server-Side State

★★★★★

JWTs are often called "stateless", but refresh-token systems commonly keep server-side state for revocation and session management.

id | user_id | token_hash | expires_at | revoked_at | created_at

On logout (or password change, etc.) set revoked_at → token can no longer be used.

When to Revoke

  • User logs out
  • User changes password
  • Admin disables account
  • Suspicious activity detected
  • Refresh-token reuse detected
  • Session manually terminated
Revocation checks happen at the /refresh call (DB/Redis lookup by token hash) — not on every API request. This preserves the benefit of stateless JWTs for access tokens.

Revoking an Already-Issued Access Token

Harder, because access JWTs are normally trusted purely via signature. Common approaches:

  • Token versioning: Store a tokenVersion per user; embed it in the JWT. Bump the DB value to invalidate all previously issued tokens instantly.
  • Short-lived denylist: Store revoked token IDs (jti) in Redis until natural expiry and check against it.
9. Logout

What Logout Actually Does

★★★★★

Logout is more than deleting the access token on the frontend. A proper logout must invalidate the refresh-token/session.

User clicks Logout
↓
POST /auth/logout
↓
Server revokes refresh token
↓
Clear refresh-token cookie
app.post("/auth/logout", async (req, res) => {
  const refreshToken = req.cookies.refreshToken;
  if (refreshToken) {
    await revokeRefreshToken(refreshToken);
  }
  res.clearCookie("refreshToken");
  res.json({ message: "Logged out successfully" });
});
What about the access token? If it's a JWT, the server generally doesn't delete it. It simply expires soon. The important part is that the refresh token is revoked, so the attacker cannot obtain another access token.

Single-Device vs All-Device Logout

This session only

Revoke just the one refresh token/family tied to the current device.

All devices

Revoke every refresh token belonging to the user (or bump a global tokenVersion). Useful for "log out everywhere" or after password change.

10. Token Theft Considerations

Access Token Theft

★★★★★
Attacker gets Access Token
↓
Calls protected APIs
↓
Token expires after ~15 min

Protections: short lifetime, HTTPS, avoid unnecessary exposure, secure storage (memory, not localStorage).

Signing Key / Algorithm

🔑 HS256 (symmetric) — if the secret leaks, an attacker can forge tokens for any user. RS256 (asymmetric) — only the server holds the private key; verifiers use the public key. Preferred when multiple services verify but only one issues tokens.

Refresh Token Theft

More dangerous because refresh tokens are long-lived.

Attacker gets Refresh Token
↓
/refresh → New Access Token
↓
Continue accessing APIs

Protections: HttpOnly + Secure cookies, rotation, reuse detection, server-side revocation.

Detecting Refresh-Token Reuse

RT1 → /refresh → RT2. Now RT1 is invalid.

If someone later sends RT1 → server detects reuse 🚨 → revoke the whole token family and force re-authentication.

Interview line: "With rotation, every refresh generates a new refresh token and invalidates the previous one. Reuse of an old token indicates possible theft, so we revoke the associated session/family."

12. Important Interview Questions
💡 Interview Q&A
Basic
Why do access tokens expire?
To limit the damage if an access token is stolen.
Why do we need refresh tokens?
To obtain new access tokens without forcing the user to log in again.
What is the difference between access and refresh tokens?
Access Token → Access APIs. Refresh Token → Get new Access Token.
Why is the refresh token longer-lived?
Because it is not sent to normal APIs; it is used specifically to obtain new access tokens.
Scenario-Based
What happens when the access token expires?
Client calls POST /refresh → Server validates refresh token → Issues new access token.
What happens if the refresh token is stolen?
Attacker may generate new access tokens. Therefore refresh tokens need secure storage, rotation, and revocation.
What happens when the user logs out?
Revoke the refresh token + clear the cookie. The already-issued access token may remain valid until it expires (unless extra invalidation is implemented).
Tricky Questions
If JWT is stateless, how can you revoke a refresh token?
Access tokens can stay stateless. Refresh-token/session state is stored in a DB or Redis and looked up only at /refresh time.
Why not make the access token valid for 30 days?
A stolen access token would give an attacker API access for 30 days. Short-lived tokens reduce that exposure.
Why rotate refresh tokens?
To reduce the impact of theft and detect reuse of an already-consumed token — then revoke the whole token family.
Which is more dangerous to steal: access or refresh token?
Generally the refresh token, because it can be exchanged for multiple new access tokens during its lifetime.
Can logout immediately invalidate a JWT access token?
Not automatically if the server treats the JWT as stateless. Use short expiration, token versioning, or a short-lived denylist if immediate invalidation is required.
Why use RS256 instead of HS256?
HS256 shares one secret for signing and verifying. If any verifier leaks the secret, tokens can be forged. RS256 keeps the private key only on the issuer; verifiers use the public key.
Sliding vs absolute refresh-token expiration — which would you choose?
Depends on the product. Sliding favors convenience for active users; absolute bounds how long a stolen-and-reused token stays valid. Many systems combine both.

One-line Interview Summary

"I use short-lived access tokens for API authorization and longer-lived refresh tokens for maintaining the user's session. When the access token expires, the client calls /refresh; the server validates and rotates the refresh token (as part of a token family) and issues a new access token. On logout, the refresh token is revoked and the cookie is cleared. Rotation, secure storage (HttpOnly cookies + SameSite), reuse detection, and family-level revocation help mitigate refresh-token theft, while RS256 and token versioning address access-token forgery and revocation."

This is the core flow you should be able to explain on a whiteboard in a JWT interview.
