1. Why Password Hashing? & Salt

Why Hash Passwords At All

★★★★★

Never store a user's password as plain text. If the database is ever compromised, the attacker gets every user's real password instantly.

Instead, the password is run through a hashing step before being saved:

Stored value
$2b$12$N9qo8uLOickgx2ZMRZoMye........

That string is not the original password — it can't be reversed back into it.

Hashing vs Encryption

HashingEncryption
DirectionOne-way — cannot recover originalReversible — decrypt with a key
Used forPasswordsData that needs to be read again
Algorithmsbcrypt, Argon2idAES, RSA

Passwords should be hashed, not encrypted — the app only ever needs to verify a password, never see the real one again.

⚠️ Common mix-up: Hashing and encryption sound similar but solve different problems. Reaching for AES on a password field is a frequent interview trap.

Salt — Why Identical Passwords Get Different Hashes

A salt is random data mixed into the password before hashing, so two users with the same password get completely different stored hashes.

This defeats rainbow table attacks — precomputed lookup tables of common password hashes.

💡 Salt is not a secret — it's stored alongside the hash. With bcrypt you don't manage it yourself: bcrypt.hash() generates it automatically and bakes it into the returned string.

Salt + Cost Factor Are Independent

The 12 in bcrypt.hash(password, 12) is the cost factor — how computationally expensive hashing is. It has nothing to do with the salt; they're two separate ingredients baked into the same call.

2. bcrypt in Practice

Hashing on Registration

★★★★★
auth.js
import bcrypt from "bcrypt";

const password = "MyPassword123";
const hashedPassword = await bcrypt.hash(password, 12);

await User.create({ email, password: hashedPassword });

The output packs three things into one string: $2b (version) · $12 (cost) · salt + hash. Store the whole string as-is.

Why bcrypt Cannot Be Decrypted

bcrypt is a hashing algorithm, not encryption. There is no bcrypt.decrypt().

Password
↓ bcrypt (one-way) ↓
Hash — no way back

To verify during login you re-hash the input and compare it with bcrypt.compare().

bcrypt.compare() During Login

login.js
const isValid = await bcrypt.compare("MyPassword123", user.password);

if (!isValid) {
  return res.status(401).json({ message: "Invalid credentials" });
}

bcrypt.compare() extracts the salt from the stored hash, re-hashes the entered password with that salt, and checks whether it matches — returning true / false.

⚠️ Still one-directional: Hash → Password ❌. Only Password + Stored Hash → true/false ✅.

3. Cost Factor & Argon2id

Why Password Hashing Should Be Slow

★★★★★

Password hashing is deliberately computationally expensive on purpose. If hashing were fast, an attacker with a stolen DB could try millions of guesses per second.

CostIterationsApprox. Time
82⁸ = 256~10 ms
102¹⁰ = 1,024~50–80 ms
122¹² = 4,096~200–300 ms
142¹⁴ = 16,384~800 ms – 1.2 s
💡 For one login, ~200–300 ms is unnoticeable. For an attacker trying millions of guesses, that delay makes large-scale brute-forcing impractical.

bcrypt vs Argon2id

Argon2id is expensive in both compute and memory — harder to crack with GPUs/ASICs. Prefer Argon2id for new apps; bcrypt remains solid when already in use.

Where Hashing Fits in the Bigger Picture

Register: password → hashed (bcrypt / Argon2id) → stored in DB.

Login: email + password → bcrypt.compare() → authentication → JWT generated → protected API → authorization → allow / deny.

🚨 Never put the password or hash inside a JWT. Hashing protects the password in the DB; JWT represents auth state after login — they solve different problems and shouldn't overlap.

Interview Points to Remember

  • Never store plain-text passwords.
  • Use password hashing, not encryption.
  • bcrypt and Argon2id are password-hashing algorithms.
  • Salt makes hashes unique even for identical passwords, and bcrypt generates it automatically.
  • Cost factor controls computational work — separate concept from salt.
  • bcrypt.hash() → registration / password change. bcrypt.compare() → login.
  • bcrypt cannot be decrypted — only re-hashed and compared.
  • Argon2id is a strong, memory-hard modern choice for new apps.
  • Hashing protects stored credentials; JWT handles session state — keep them separate.
Interview Q&A
💡 Interview Q&A
Standard Questions
Why shouldn't you store passwords in plain text?
If the database is ever compromised, an attacker gets every user's real password instantly — and those passwords are often reused elsewhere. Hashing means the database only ever holds a one-way derivative of the password.
What's the difference between hashing and encryption?
Hashing is one-way — there's no way to recover the original input, which is exactly why it's right for passwords. Encryption is reversible with a key, which is right for data you need to read again later, not for credentials.
What is a salt and what does it protect against?
Random data mixed into the password before hashing, so identical passwords produce different stored hashes. It defeats rainbow table attacks — precomputed hash lookup tables — since a fresh salt makes precomputation useless.
What is the cost factor in bcrypt.hash(password, 12)?
It controls how computationally expensive each hash operation is — a work factor. Higher cost means slower hashing, which is negligible for a single login but makes large-scale brute-force guessing far more expensive for an attacker.
Can you decrypt a bcrypt hash back into the password?
No — bcrypt is a hashing algorithm, not encryption, so there's no bcrypt.decrypt(). Verification works by re-hashing the entered password with the stored salt and comparing the results with bcrypt.compare().
Tricky / Follow-Up Questions
If two users pick the same password, will their stored hashes match?
No — bcrypt generates a fresh random salt for every call to bcrypt.hash(), so even identical passwords produce completely different stored strings. That's the entire point of salting.
Is a higher cost factor always better?
Not unconditionally. Cost trades off attacker resistance against real login latency and server CPU load. Push it too high and legitimate logins get slow and expensive to serve at scale — pick a value that's slow for attackers but still fast enough for users.
Does hashing the password protect against XSS or a compromised login endpoint?
No. Hashing only protects credentials at rest in the database. If an attacker captures the password in transit or via a compromised client (e.g. XSS reading a login form), hashing on the server never comes into play — that's a different threat entirely.
Why is Argon2id sometimes preferred over bcrypt for new systems?
Argon2id is memory-hard — it costs both compute time and memory to compute — which makes it more resistant to parallelized cracking on GPUs and ASICs than bcrypt, which is compute-hard only. bcrypt remains a solid, established choice where it's already in use.
Frequently Asked
Should the salt be kept secret?
No — the salt isn't a secret and is stored alongside the hash (bcrypt bundles it directly into the output string). Its job is to guarantee uniqueness across hashes, not to add secrecy.
What's stored in a bcrypt output string like $2b$12$N9qo8uLOickgx2ZMRZoMye...?
Three parts in one string: the algorithm version ($2b), the cost factor ($12), and the salt concatenated with the resulting hash. The whole string is stored as-is and passed to bcrypt.compare() later.
Should a password or its hash ever be included in a JWT?
Never. A JWT represents authentication state after a successful login — it should carry identity/claims, not credentials. Hashing protects the password in the database; the JWT is a separate mechanism for session/authorization.
Coding / Theoretical
Write the registration and login handlers using bcrypt correctly.
auth.js
import bcrypt from "bcrypt";

// Registration
app.post("/register", async (req, res) => {
  const { email, password } = req.body;
  const hashedPassword = await bcrypt.hash(password, 12);
  await User.create({ email, password: hashedPassword });
  res.status(201).json({ message: "Registered" });
});

// Login
app.post("/login", async (req, res) => {
  const { email, password } = req.body;
  const user = await User.findOne({ email });

  if (!user) {
    return res.status(401).json({ message: "Invalid credentials" });
  }

  const isValid = await bcrypt.compare(password, user.password);

  if (!isValid) {
    return res.status(401).json({ message: "Invalid credentials" });
  }

  // issue JWT here — never include user.password
  res.json({ message: "Login successful" });
});

Why this shape: registration hashes once at cost 12; login never decrypts anything — it only ever asks bcrypt for a true/false comparison, and the same generic 401 is returned whether the email or the password was wrong.

Explain, in three layers, why "hash + salt + slow cost factor" is stronger than any one of them alone.
Each layer defeats a different attack:

• Hashing means a stolen database never contains a usable plaintext password.
• Salting defeats precomputed rainbow tables and stops identical passwords from being visible as identical hashes.
• A slow cost factor makes brute-forcing every possible password against a stolen hash computationally expensive, even after salting removes the rainbow-table shortcut.

Removing any one layer reopens a specific attack path — together they force an attacker into a slow, per-password brute-force with no shortcuts.
