Password Hashing

Interview notes — why, how, and the gotchas that matter

1 Why Password Hashing?

Never store a user's password as plain text (password: "MyPassword123"). If the database is ever compromised, the attacker gets every user's real password instantly.

Instead, the password is run through a hashing step before being saved:

$2b$12$N9qo8uLOickgx2ZMRZoMye........ — not the original password.
Password hashing protects passwords if the database is compromised.

2 Hashing vs Encryption

HashingEncryption
DirectionOne-way — cannot recover originalReversible — decrypt with a key
Used forPasswordsData that needs to be read again
Algorithmsbcrypt, Argon2idAES, RSA

Hashing: Password → Hash function → Hash (no way back)

Encryption: Data → Encrypt → Encrypted → Decrypt → Original

Passwords should be hashed, not encrypted — the app only needs to verify, never see the real password again.

3 Salt

A salt is random data mixed into the password before hashing, so two users with the same password get completely different stored hashes.

This defeats rainbow table attacks — precomputed lookup tables of common password hashes.

Salt is not a secret — it's stored alongside the hash.
With bcrypt you don't manage it yourself: bcrypt.hash() creates it automatically and bakes it into the returned string.
Salt makes hashes unique even for identical passwords.

4 Salt + bcrypt in Node.js

import bcrypt from "bcrypt";

const password = "MyPassword123";
const hashedPassword = await bcrypt.hash(password, 12);

console.log(hashedPassword);
// $2b$12$N9qo8uLOickgx2ZMRZoMye........

await User.create({ email, password: hashedPassword });

The output packs three things: $2b (version) · $12 (cost) · salt + hash. Store the whole string as-is.

5 Salt Rounds / Cost Factor

The 12 in bcrypt.hash(password, 12) is the cost factor — how computationally expensive hashing is.

Lower cost → faster · Higher cost → slower for attackers to brute-force.

CostIterationsApprox. Time
82⁸ = 256~10 ms
102¹⁰ = 1,024~50–80 ms
122¹² = 4,096~200–300 ms
142¹⁴ = 16,384~800 ms – 1.2 s
For one login, ~200–300 ms is unnoticeable. For an attacker trying millions of guesses, that delay makes large-scale brute-forcing impractical.
Salt = random value. Cost factor = computational work. Independent concepts inside the same bcrypt call.

6 Why bcrypt Cannot Be Decrypted

bcrypt is a hashing algorithm, not encryption. There is no bcrypt.decrypt().

Password → bcrypt → Hash (one way only).

To verify during login you re-hash the input and compare with bcrypt.compare().

7 bcrypt.compare() During Login

const isValid = await bcrypt.compare("MyPassword123", user.password);

if (!isValid) {
  return res.status(401).json({ message: "Invalid credentials" });
}

bcrypt.compare() extracts the salt from the stored hash, re-hashes the entered password with that salt, and checks if it matches — returns true / false.

Still Hash → Password ❌. Only Password + Stored Hash → true/false.

8 Why Password Hashing Should Be Slow

Password hashing is deliberately computationally expensive on purpose.

If hashing were fast, an attacker with a stolen DB could try millions of guesses per second. Higher cost makes each guess slower and large-scale brute-forcing far more expensive.

9 bcrypt vs Argon2id

Argon2id is expensive in both compute and memory — harder to crack with GPUs/ASICs. Prefer Argon2id for new apps; bcrypt remains solid when already in use.

10 Complete Registration + Login Flow

Registration

1 password → bcrypt.hash() (salt + cost factor)
2 password hash → stored in DB
const hashedPassword = await bcrypt.hash(password, 12);
await User.create({ email, password: hashedPassword });

Login

1 entered password → find user → get stored hash
2 bcrypt.compare() → valid? → continue / reject

11 Where Password Hashing Fits

Register: password → hashed (bcrypt / Argon2id) → stored in DB

Login: email + password → bcrypt.compare() → authentication → JWT generated → protected API → authorization → allow / deny

Important: Password hashing and JWT solve different problems. Hashing protects the password in the DB. JWT represents auth state after login.
Never put the password or hash inside a JWT.

★ Interview Points to Remember

  • Never store plain-text passwords.
  • Use password hashing, not encryption.
  • bcrypt and Argon2id are password-hashing algorithms.
  • Salt makes hashes unique even for identical passwords.
  • bcrypt automatically generates and incorporates the salt.
  • Cost factor controls computational work — separate from salt.
  • bcrypt.hash() → registration / password change.
  • bcrypt.compare() → login.
  • bcrypt cannot be decrypted — only re-hashed and compared.
  • Argon2id is a strong, memory-hard modern choice for new apps.
  • Hashing protects stored credentials; JWT handles session — keep them separate.

One-liner

Hash passwords with a slow, salted algorithm (bcrypt / Argon2id), never encrypt them, never store plain text, and verify with compare — never decrypt.
