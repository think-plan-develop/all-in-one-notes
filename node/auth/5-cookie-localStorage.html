Cookie vs Local Storage

Where should you store the JWT? Security trade-offs, explained from the Node.js/backend perspective.

What is localStorage How It Reaches Node.js XSS Risk Cookie vs localStorage Code Patterns Interview Answer
💡 The question: When you use JWT authentication, where should the token live in the browser — localStorage or a Cookie? The key is understanding how the browser sends the token to Express and what security risks each option creates.
🔑 Key Terms at a Glance
💾
localStorage: Browser storage from the Web Storage API, readable and writable by any same-origin JavaScript.
🍪
HttpOnly Cookie: A cookie flagged so client-side JavaScript cannot read it — only the browser can attach it to requests.
📤
Authorization Header: How localStorage tokens reach Node.js — JS must manually attach Bearer <token> to each request.
⚔️
XSS: Malicious same-origin JavaScript that can read anything JS-accessible — including a token sitting in localStorage.
🛡️
CSRF: The trade-off cookies introduce — browsers auto-send cookies, so cross-site requests need separate protection.

How localStorage Works With Node.js

Login API returns a JWT in the response body:

server.js
app.post("/login", async (req, res) => {
  // Verify email/password...
  const token = jwt.sign(
    { userId: 101, role: "user" },
    process.env.JWT_SECRET,
    { expiresIn: "15m" }
  );

  res.json({ token });
});

Frontend stores it:

login.js
const data = await response.json();
localStorage.setItem("accessToken", data.token);

Why Use localStorage at All?

Simple to use and easy to send as a Bearer token:

api.js
localStorage.setItem("accessToken", token);

fetch("/api/profile", {
  headers: { Authorization: `Bearer ${token}` }
});

Common pattern for APIs — but the security trade-off matters when the token is sensitive.

2. How Does the Token Reach Node.js?

JS Has to Send It Manually

★★★★★

Node.js does not automatically receive localStorage data.

Browser JavaScript must read it and explicitly send it:

api.js
const token = localStorage.getItem("accessToken");

fetch("/profile", {
  headers: {
    Authorization: `Bearer ${token}`
  }
});

Express Middleware

authenticate.js
function authenticate(req, res, next) {
  const authHeader = req.headers.authorization;

  if (!authHeader) {
    return res.status(401).json({ message: "Authentication required" });
  }

  const token = authHeader.split(" ")[1];

  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    req.user = decoded;
    next();
  } catch {
    return res.status(401).json({ message: "Invalid or expired token" });
  }
}

JavaScript Can Access localStorage

This is the biggest security consideration. Any JavaScript running in the same origin can do:

console
const token = localStorage.getItem("accessToken");
console.log(token);

There is no HttpOnly protection for localStorage.

3. XSS and localStorage

The Real Threat Model

★★★★★

If your app has an XSS vulnerability, attacker-controlled JavaScript can run in your origin and steal the token:

XSS JavaScript
↓
localStorage.getItem("accessToken")
↓
JWT stolen
↓
Attacker uses token until it expires
📌 Don't say "localStorage causes XSS." Say: XSS allows attacker JS to run in your origin. If the token is in localStorage, that JS can read it — making token theft easier.
💡 The problem isn't that localStorage is "insecure." The problem is: a token in JavaScript-readable storage can be stolen by malicious JS in the same origin.

Main Security Problem

🚨 If that token is long-lived, the impact is worse. Avoid putting highly sensitive, long-lived credentials in JavaScript-readable storage when a safer architecture is available.
4. localStorage vs Cookie — Core Difference

Who Can Access the Token

★★★★★

The biggest difference is who can access the token and how it reaches Node.js.

localStorage

JS reads JWT → sends Authorization header → Node.js

JS can read it · XSS can steal it

HttpOnly Cookie

Browser auto-sends cookie → Node.js

JS cannot read it · XSS cannot steal it easily

★ Interview Answer
🎤 localStorage vs Cookie for JWT
How would you answer this in an interview?
With localStorage, the frontend JavaScript stores and reads the JWT and usually sends it through the Authorization Bearer header. The main security concern is that localStorage is accessible to JavaScript, so if the app has an XSS vulnerability, malicious JS may steal the token.

That's why sensitive authentication tokens are often kept in HttpOnly cookies instead, combined with appropriate CSRF protections and other cookie security settings.
📌 HttpOnly cookies are not automatically secure. You also need: HttpOnly · Secure · SameSite · CSRF protection · HTTPS
