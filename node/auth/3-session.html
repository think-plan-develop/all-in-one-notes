1. Session Fundamentals

What Is a Session?

★★★★★

A session is server-side information that represents a user's logged-in state. After successful login, the server creates a session and associates it with the user.

Example: a user logs in with shivam@example.com + password. The server verifies the credentials and creates:

Session record
{
  sessionId: "abc123",
  userId: 101,
  role: "admin"
}

The server then gives the client only the sessionId — never the full record.

Session ID

A Session ID is a unique random identifier given to the client after successful login. The server uses this ID to find the user's session data.

Client holds: sessionId = abc123
↓
Server looks up abc123
↓
Session Store: abc123 → userId 101
💡 Interview answer: A Session ID is an opaque identifier used to locate a user's server-side session — it carries no meaning by itself.

Server-Side Session

A server-side session means the user's login information is stored on the server, not inside the browser.

The browser only stores and sends the Session ID. The server uses that ID to retrieve the full user data.

✅ This is the key contrast with JWT: session auth keeps authentication state primarily on the server, whereas JWT carries claims inside the token itself.
2. Session Cookies & Redis Storage

Session Cookie

★★★★

A session cookie is a cookie used by the browser to store the Session ID. After successful login, the server sends the Session ID to the browser using the Set-Cookie response header.

1. Server sends the Session Cookie

auth.js
app.post("/login", (req, res) => {
  // After verifying username/password
  const sessionId = "abc123";

  res.cookie("sessionId", sessionId, {
    httpOnly: true,
    secure: true,
    sameSite: "lax"
  });

  res.json({ message: "Login successful" });
});
Response Header
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax

Visible in: DevTools → Network → /login → Response Headers.

2. Browser stores & resends the cookie

Request Header (on /profile)
Cookie: sessionId=abc123

Visible in: DevTools → Application → Cookies (storage) and Network → /profile → Request Headers (transmission).

Set-Cookie

Server → Browser. Used to create or update the cookie.

Cookie

Browser → Server. Sent automatically with subsequent requests.

Login → Server creates Session
↓
Set-Cookie: sessionId=abc123
↓
Browser stores cookie
↓
GET /profile → Cookie: sessionId=abc123
↓
Server finds session → User authenticated

Session Storage — Where Does It Live?

The session store is where the server keeps session information. It can live in memory, a database, or Redis.

⚠️ Important for production: storing sessions only in the memory of one server generally doesn't work once you have multiple servers behind a load balancer.
Server 1
Session found ✓
Server 2
Session not found ✗

A shared session store — like Redis — solves this by giving every backend instance the same place to look up sessions.

Redis Session Store

Redis Session Store means storing server-side session data in Redis instead of a single server's local memory.

redis-cli
# Create / store a session
SET session:abc123 '{"userId":101,"role":"admin"}'

# Set expiration (30 minutes)
EXPIRE session:abc123 1800

# Get the session
GET session:abc123

# Delete during logout
DEL session:abc123
  • Very fast — in-memory data store
  • Shared between multiple backend servers
  • Supports automatic expiration (TTL)
  • Ideal for temporary login sessions
💡 Sessions can be stored in a regular database, but Redis is commonly preferred because session data is temporary, frequently accessed, and needs fast lookup + automatic expiration. Trade-off: extra infrastructure, memory usage, and a need for high availability if sessions are critical.
3. Session Expiration & Logout

Session Expiration (TTL)

★★★★

A session should not remain valid forever — it gets an expiration time (TTL). Redis makes this easy since it natively supports TTL.

session.js
const sessionId = "abc123";

await redis.set(
  `session:${sessionId}`,
  JSON.stringify({ userId: 101, role: "admin" }),
  { EX: 1800 }  // 30 minutes
);
Check remaining TTL
TTL session:abc123
# → 1450  (seconds remaining)

After expiration:

Cookie still sends sessionId=abc123
↓
Server → Redis GET → null
↓
Session expired → 401 Unauthorized

Why expiration matters: if an attacker gets hold of a session ID, without expiration they could use it indefinitely. Expiration limits that damage window.

Expiration

Session becomes invalid automatically after a set time.

Logout

User explicitly logs out; the server destroys the session immediately.

Logout

★★★★

In session-based authentication, logout means destroying the server-side session and clearing the session cookie from the browser.

logout.js
app.post("/logout", async (req, res) => {
  const sessionId = req.cookies.sessionId;

  // 1. Destroy session from Redis
  await redis.del(`session:${sessionId}`);

  // 2. Clear cookie from browser
  res.clearCookie("sessionId");

  res.json({ message: "Logged out successfully" });
});
🚨 Why both steps are required: deleting from Redis means the server no longer accepts the session; clearing the cookie means the browser no longer sends the session ID. If you only clear the cookie, the server-side session may still exist — anyone with a copy of the old Session ID could keep using it until it expires.

💡 Interview one-liner: session-based authentication is a mechanism where the server creates a session after login, stores the user's session information on the server, and sends a unique session ID to the client — usually through an HttpOnly cookie. The client sends that cookie automatically with future requests, so the server can look the session up in its session store and identify the user.
Interview Q&A
💡 Interview Q&A
Standard Questions
What is a session in the context of authentication?
Server-side information representing a user's logged-in state, created after successful login and typically holding fields like userId and role. The client never sees this record directly — only its ID.
What is a Session ID and what is it used for?
A unique random identifier issued to the client after login. The server uses it purely as a lookup key to find the matching session record in the session store — it carries no user data by itself.
What does "server-side session" mean, and how is that different from storing auth state in the browser?
It means the actual login/user data lives on the server, not in the browser. The browser only holds and sends the Session ID; the server does the work of resolving that ID back into user data on every request.
How does a session cookie get set and then sent back on later requests?
After login, the server responds with a Set-Cookie header containing the session ID. The browser stores it and automatically attaches it as a Cookie header on every subsequent request to that origin.
Why is Redis commonly used as a session store instead of in-memory storage?
In-memory storage on a single server breaks once you run multiple backend instances — a session created on Server 1 won't be visible on Server 2. Redis is a fast, shared store every instance can query, and it natively supports automatic expiration.
Tricky / Follow-Up Questions
If you clear the cookie on logout but don't delete the session from Redis, is the user actually logged out?
Not fully. The browser stops sending that session ID, but the server-side session still exists and remains valid until it expires. Anyone who captured a copy of that session ID beforehand could still use it.
Does session expiration alone protect against a stolen session ID?
It limits the window of exposure, not the initial risk. If an attacker steals a session ID before it expires, they can act as that user until expiration or logout. Expiration is a damage-limiting control, not a prevention mechanism — that's what HttpOnly, Secure, and SameSite cookie flags are for.
What happens if two servers behind a load balancer each keep sessions in local memory?
A user could get authenticated on Server 1, then have a later request routed to Server 2, which has no record of that session — resulting in an unexpected logout or 401. This is exactly the problem a shared store like Redis solves.
Is a session cookie automatically secure just because it's a cookie?
No. Its safety depends on the flags set when creating it — HttpOnly stops JavaScript from reading it, Secure ensures it's only sent over HTTPS, and SameSite restricts cross-site sending. Omitting any of these weakens the session cookie's protection.
Frequently Asked
What's the practical difference between session-based auth and JWT-based auth?
Session auth keeps the authentication state on the server and the client only holds a pointer (the session ID); a session can be instantly revoked by deleting the server record. JWTs carry the claims inside the token itself, so the server doesn't need a lookup, but revoking a single token before it expires is harder.
Why set an EXPIRE / TTL on a Redis session key instead of leaving it permanent?
A permanent session key never gets cleaned up and stays valid indefinitely if never explicitly deleted, which is both a security risk (stale sessions never expire) and a memory-growth problem in Redis. TTL keeps both concerns bounded automatically.
What's the difference between the Set-Cookie and Cookie headers?
Set-Cookie is sent by the server to create or update a cookie in the browser. Cookie is sent by the browser back to the server on later requests, automatically including whatever was previously set.
Coding / Theoretical
Write login, an authenticated route, and logout using Express + Redis sessions.
server.js
import express from "express";
import cookieParser from "cookie-parser";
import { createClient } from "redis";
import { randomUUID } from "crypto";

const app = express();
app.use(express.json());
app.use(cookieParser());
const redis = createClient();
await redis.connect();

// Login — create session
app.post("/login", async (req, res) => {
  // ... verify email/password against DB ...
  const sessionId = randomUUID();

  await redis.set(
    `session:${sessionId}`,
    JSON.stringify({ userId: 101, role: "admin" }),
    { EX: 1800 }
  );

  res.cookie("sessionId", sessionId, {
    httpOnly: true, secure: true, sameSite: "lax",
  });
  res.json({ message: "Login successful" });
});

// Authenticated route — look up session
app.get("/profile", async (req, res) => {
  const sessionId = req.cookies.sessionId;
  const raw = sessionId && await redis.get(`session:${sessionId}`);

  if (!raw) {
    return res.status(401).json({ message: "Not authenticated" });
  }
  res.json(JSON.parse(raw));
});

// Logout — destroy session + clear cookie
app.post("/logout", async (req, res) => {
  const sessionId = req.cookies.sessionId;
  await redis.del(`session:${sessionId}`);
  res.clearCookie("sessionId");
  res.json({ message: "Logged out successfully" });
});

app.listen(3000);

Why this shape: the session ID is a random, opaque token (never derived from user data), Redis holds the actual state with a TTL, and logout explicitly deletes both the Redis key and the cookie rather than relying on expiration alone.

Explain, in three layers, why "server-side session + shared store + TTL" is more robust than a naive in-memory session.
Each layer removes a specific failure mode:

• Server-side session means the client never holds sensitive user data — only an opaque pointer, so a leaked cookie doesn't leak the data itself.
• A shared store (Redis) means the session survives load-balancing across multiple servers — no "logged in on one server, logged out on another" bug.
• TTL / expiration means a stolen or abandoned session ID has a bounded lifetime instead of being valid forever.

Together, they mean losing any single server, or even a session ID itself, doesn't compromise the whole system indefinitely.
