Sessions

Interview notes — server-side authentication state explained

1 What is a Session?

A session is server-side information that represents a user's logged-in state.

After successful login, the server creates a session and associates it with the user.

Example

User logs in with shivam@example.com + password.

Server verifies credentials and creates:

{
  sessionId: "abc123",
  userId: 101,
  role: "admin"
}

The server then gives the client the sessionId.

Session = Server-side record that keeps track of a logged-in user.

2 Session ID

A Session ID is a unique random identifier given to the client after successful login.

Example: sessionId = "abc123xyz"

The server uses this ID to find the user's session data.

Session ID = Identifier used to identify a user's server-side session.

3 Server-Side Session

A server-side session means the user's login information is stored on the server, not inside the browser.

The browser only stores / sends the Session ID. The server uses that ID to retrieve the full user data.

Server-side session = Authentication state stored on the server and identified using a Session ID.

4 Session Cookie ★★★★

A session cookie is a cookie used by the browser to store the Session ID.

After successful login, the server sends the Session ID to the browser using the Set-Cookie response header.

1. Server sends the Session Cookie

app.post("/login", (req, res) => {
  // After verifying username/password
  const sessionId = "abc123";

  res.cookie("sessionId", sessionId, {
    httpOnly: true,
    secure: true,
    sameSite: "lax"
  });

  res.json({ message: "Login successful" });
});
Browser receives:
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax

Visible in: DevTools → Network → /login → Response Headers

2. Browser stores the Cookie

Stored as sessionId = abc123

Visible in: DevTools → Application → Cookies

3. Browser sends Cookie with next request

fetch("/profile");
Browser automatically sends:
Cookie: sessionId=abc123

Visible in: Network → /profile → Request Headers

Set-Cookie

Server → Browser
Used to create / update the cookie.

Cookie

Browser → Server
Sent automatically with subsequent requests.

Simple flow

1 Login → Server creates Session
2 Set-Cookie: sessionId=abc123
3 Browser stores cookie
4 GET /profile → Cookie: sessionId=abc123
5 Server finds session → User authenticated
Session Cookie = A browser cookie that carries the Session ID between the client and server.

5 Session Storage

The session store is where the server keeps session information.

It can be stored in: Memory · Database · Redis

Important for production: Storing sessions only in the memory of one server is generally not suitable when you have multiple servers.

A shared session store (like Redis) solves this problem.

6 Redis Session Store ★★★★

Redis Session Store means storing server-side session data in Redis instead of the server's local memory.

Redis Commands

# Create / store a session
SET session:abc123 '{"userId":101,"role":"admin"}'

# Set expiration (30 minutes)
EXPIRE session:abc123 1800

# Get the session
GET session:abc123

# Delete during logout
DEL session:abc123

Why Redis?

  • • Very fast (in-memory)
  • • Shared between multiple backend servers
  • • Supports automatic expiration (TTL)
  • • Ideal for temporary login sessions
Sessions can be stored in a database, but Redis is commonly preferred because session data is temporary, frequently accessed, and needs fast lookup + automatic expiration. Trade-off: extra infrastructure and memory usage; needs high availability if sessions are critical.
Redis Session Store = Using Redis to store and manage server-side user sessions.

7 Session Expiration ★★★★

A session should not remain valid forever. We give it an expiration time (TTL).

With Redis this is easy because Redis supports TTL (Time To Live).

Example: 30-minute session

const sessionId = "abc123";

await redis.set(
  `session:${sessionId}`,
  JSON.stringify({
    userId: 101,
    role: "admin"
  }),
  { EX: 1800 }  // 30 minutes
);
EX: 1800 → key automatically expires after 1800 seconds = 30 minutes.

Check remaining TTL

TTL session:abc123
# → 1450  (seconds remaining)

After expiration

1 Cookie still sends sessionId=abc123
2 Server → Redis GET → null
3 Session expired → 401 Unauthorized

Why expiration matters: If an attacker gets a session ID, without expiration they could use it indefinitely. Expiration limits the damage window.

Expiration

Session becomes invalid automatically after a specified time.

Logout

User explicitly logs out and the server destroys the session immediately.

Session expiration limits how long a session remains valid and reduces the risk from stolen or abandoned session IDs.

8 Logout ★★★★

In session-based authentication, logout means destroying the server-side session and clearing the session cookie from the browser.

Logout API (Express + Redis)

app.post("/logout", async (req, res) => {
  const sessionId = req.cookies.sessionId;

  // 1. Destroy session from Redis
  await redis.del(`session:${sessionId}`);

  // 2. Clear cookie from browser
  res.clearCookie("sessionId");

  res.json({ message: "Logged out successfully" });
});
Why both are required?
1. Delete from Redis → Server no longer accepts the session
2. Clear cookie → Browser no longer sends the session ID

If you only clear the cookie, the server-side session may still exist. Anyone with a copy of the old Session ID could still use it until expiration.
Logout = Destroy the server-side session + clear the session cookie.

★ Session vs Session ID vs Cookie

Term Meaning
Session Server-side login information
Session ID Unique identifier of the session
Cookie Browser mechanism commonly used to store / send the Session ID
Session Store Where session data is stored
Redis Common shared session store
Session Expiration Time after which session becomes invalid
Logout Process of ending the authenticated session

★ Interview Definition

Say this in interviews

Session-based authentication is an authentication mechanism where the server creates a session after successful login, stores the user's session information on the server, and sends a unique session ID to the client — usually through an HTTP-only cookie.

The client automatically sends that cookie with subsequent requests, allowing the server to look up the session in the session store and identify the user.

One-line flow

Login → Create Session → Store Session → Send Session ID Cookie
→ Cookie on every request → Find Session → Authenticate User
→ Logout → Destroy Session

This gives you the foundation for understanding JWT, because the key difference is: session authentication keeps the authentication state primarily on the server, whereas JWT authentication carries claims in the token itself.
