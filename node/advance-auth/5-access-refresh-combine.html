The Core Idea

Two tokens cover each other's weaknesses

✅ Access token is fast but can't be revoked. Refresh token is revocable but only used occasionally. Together: speed and the ability to cut off access.

REUSE DETECTION · LOGOUT

Reuse detection

Old (already-rotated) token presented again → theft signal → revoke ALL sessions → force re-login everywhere.

Logout

Delete Redis session for current hash. Clear cookie. Access token stays valid until its own 15-min expiry — expected.

Combined Code — token.service.ts

Both tokens in one file

src/modules/auth/token.service.ts
import jwt from "jsonwebtoken";
import { randomBytes, createHash, randomUUID } from "crypto";
import { env } from "../../config/env.js";

interface AccessTokenPayload {
  sub: string;
  role: string;
}

// --- Access Token ---
export function generateAccessToken(payload: AccessTokenPayload) {
  return jwt.sign(payload, env.JWT_ACCESS_SECRET, {
    expiresIn: env.ACCESS_TOKEN_EXPIRES_IN, // "15m"
    jwtid: randomUUID(),
  });
}

// --- Refresh Token ---
export function generateRefreshToken(): string {
  return randomBytes(32).toString("hex");
}

export function hashRefreshToken(token: string): string {
  return createHash("sha256").update(token).digest("hex");
}

export async function loginController(req: Request, res: Response) {
  const parsed = loginSchema.safeParse(req.body);
  if (!parsed.success) {
    return res.status(400).json({ success: false, message: "Invalid input" });
  }

  try {
    const user = await verifyLogin(parsed.data);

    const accessToken = generateAccessToken({ sub: user.id, role: user.role });

    const refreshToken = generateRefreshToken();
    const refreshTokenHash = hashRefreshToken(refreshToken);

    await createSession(refreshTokenHash, {
      userId: user.id,
      createdAt: Date.now(),
    });

    res.cookie("refreshToken", refreshToken, {
      httpOnly: true,
      secure: env.NODE_ENV === "production",
      sameSite: "strict",
      maxAge: 7 * 24 * 60 * 60 * 1000,
      path: "/auth/refresh",
    });

    return res.status(200).json({ accessToken });
  } catch (err) {
    if (err instanceof Error && err.message === "INVALID_CREDENTIALS") {
      return res.status(401).json({ success: false, message: "Invalid credentials" });
    }
    return res.status(500).json({ success: false, message: "Something went wrong" });
  }
}
Combined Code — Authenticate Middleware

Reads the access token

authenticate
export function authenticate(req: Request, res: Response, next: NextFunction) {
  const authHeader = req.headers.authorization;
  if (!authHeader?.startsWith("Bearer ")) {
    return res.status(401).json({ success: false, message: "Missing token" });
  }

  const token = authHeader.split(" ")[1];
  try {
    req.user = jwt.verify(token, env.JWT_ACCESS_SECRET) as { sub: string; role: string };
    next();
  } catch {
    return res.status(401).json({ success: false, message: "Invalid or expired token" });
  }
}

export async function refreshController(req: Request, res: Response) {
  const refreshToken = req.cookies.refreshToken;
  if (!refreshToken) {
    return res.status(401).json({ success: false, message: "No refresh token" });
  }

  const refreshTokenHash = hashRefreshToken(refreshToken);
  const session = await getSession(refreshTokenHash);

  if (!session) {
    const reused = await wasTokenAlreadyUsed(refreshTokenHash);
    if (reused) {
      await revokeAllSessions(reused.userId);
      res.clearCookie("refreshToken", { path: "/auth/refresh" });
      return res.status(401).json({ success: false, message: "Session revoked — please log in again" });
    }
    return res.status(401).json({ success: false, message: "Invalid or expired session" });
  }

  const user = await prisma.user.findUnique({
    where: { id: session.userId },
    include: { role: true },
  });
  if (!user) return res.status(401).json({ success: false, message: "User not found" });

  const newAccessToken = generateAccessToken({ sub: user.id, role: user.role.name });
  const newRefreshToken = generateRefreshToken();
  const newRefreshTokenHash = hashRefreshToken(newRefreshToken);

  await rotateSession(refreshTokenHash, newRefreshTokenHash);

  res.cookie("refreshToken", newRefreshToken, {
    httpOnly: true,
    secure: env.NODE_ENV === "production",
    sameSite: "strict",
    maxAge: 7 * 24 * 60 * 60 * 1000,
    path: "/auth/refresh",
  });

  return res.status(200).json({ accessToken: newAccessToken });
}

Theory — The Trust Boundary Shift

Trust moves from “the token itself” to “a record the server controls”

Access token

Trust lives entirely in the signature. Once issued, the server has no further say until it expires.

Refresh token

Trust lives in Redis. The string is just a lookup key. Erase the record (logout, theft, admin) and the token is instantly worthless.

📌 This is why the refresh token needs a database at all — and the single fact that explains almost every design decision in this system.
Interview Questions

Combined system

1. Explain the pattern end to end, as if to a junior engineer.
Login issues both: a short-lived signed JWT for fast per-request checks, and a long-lived random token backed by a server-side record for revocability. Access is used constantly; refresh is only used to quietly get a new access token when the old one expires.
2. Why not just use one token for everything?
A single token forces a bad tradeoff: short-lived → users logged out constantly; long-lived → a leak is a long-term compromise with no revoke. Two tokens split these concerns.
3. Where does each token live in the client, and why differently?
Access in memory (JS variable) — short-lived, no persistence. Refresh in an HttpOnly cookie — long-lived, survives reloads, inaccessible to JS to resist XSS.
4. What's the actual attack this system defends against?
Token theft via XSS, network interception, or leaked logs. Short access life limits exposure; HttpOnly cookie resists XSS; rotation limits stolen refresh to one use; reuse detection shuts down theft that does happen.
5. Walk through: attacker steals a refresh token cookie.
They can use it once to get a new pair. When the real user's browser also refreshes (with the now-rotated original), the server detects reuse and revokes every session — cutting off the attacker's stolen pair too.
6. Why does logout only clear the refresh token, not invalidate the access token immediately?
Access is stateless — no revocation list without a DB call on every request, defeating its purpose. It stays valid for remaining ~15 minutes after logout. Deliberate, documented tradeoff.
7. “This device” vs “all devices” logout?
This device: delete the current session's Redis key (current refresh hash). All devices: Redis Set of every session hash per user, delete them all together.
8. What breaks if you store the raw refresh token in Redis?
Anyone with Redis read access could impersonate any user — identical to storing plaintext passwords.
9. Why is CSRF a concern here but not for the access token?
Refresh rides in a cookie, which browsers attach automatically — including requests from a malicious site. Access is attached via a header by your own JS, which a third-party site can't do cross-origin without CORS cooperation.
10. How do you decide access token expiry in a real system?
Shorter = smaller blast radius, more refresh calls. Longer = fewer refreshes, larger exposure. 15 minutes is a common middle ground; banking often 2–5 min.
11. What happens if you change JWT_ACCESS_SECRET?
Every existing access token fails signature verification — forced global logout for API access. Refresh tokens still work unless you also want a hard logout.
12. Is this still needed if you use HTTPS everywhere?
Yes. HTTPS protects data in transit, not a token already in a compromised browser (XSS) or leaked via logs. Transport security and token-design security solve different threats.
System Design Notes

Where this fits in a larger architecture

  • Microservices — any service holding JWT_ACCESS_SECRET (or a shared public key with RS256) can verify independently. Refresh flow stays centralized in one auth service.
  • Horizontal scaling — access verification needs zero shared state. Refresh needs Redis reachable from every instance — the one piece of shared state.
  • Mobile — cookies don't work the same way. Store refresh in Keychain/Keystore; send as body/header. Rotation/reuse-detection stays identical.
  • Multi-region — Redis session data is small and TTL-bound, cheap to replicate or shard by user ID vs a full user database.
  • Alternative at scale — some systems replace the access JWT with a reference token + in-memory cache to gain revocability on the access token too — trade some statelessness for instant global logout.
