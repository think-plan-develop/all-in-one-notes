What It Is

Cryptographically random opaque string

Not a JWT. Not decodable. Not self-describing. Its only job: an unguessable secret the server looks up in Redis to issue a new access token — without asking the user to log in again.

AspectValue
Format64-character random hex (32 random bytes)
Lifetimelong — 7 days
StorageHttpOnly cookie (browser-managed, invisible to JS)
Server-side recordYES — hash stored in Redis (this is what makes it revocable)
Sent viaBrowser auto-attaches the cookie on requests to /auth/refresh

Access token

Proves identity fast. No DB call. Stateless JWT. 15 min. JSON body.

Refresh token

Exists so the server can revoke access later — something a stateless JWT can never do on its own.

The Full Flow

Login

1. Email + password
↓
2–3. Access JWT (15m) + refresh random string (7d)
↓
4–5. SHA-256 hash → Redis { userId, createdAt } TTL 7d
↓
6. accessToken in JSON · refreshToken in HttpOnly cookie

Access token expires → refresh

7. API calls fail 401
↓
8. POST /auth/refresh · cookie auto-attached
↓
9–10. Hash cookie · lookup auth:session:{hash}
↓
11. Found → rotate: delete old, new hash, new access + refresh
↓
12. Not found → 401, password login again

Rotation · reuse detection · logout

  • Rotation — old refresh token deleted the moment it's used. New one replaces it. Old one can NEVER be used again.
  • Reuse detection — using an already-rotated token = theft signal. Revoke ALL sessions for that user.
  • Logout — delete Redis session, clear cookie. Refresh token is permanently dead.
✅ One sentence: access token proves identity fast; refresh token exists so the server can revoke access later.
Code — Generate & Hash

token.service.ts

src/modules/auth/token.service.ts
import { randomBytes, createHash } from "crypto";

export function generateRefreshToken(): string {
  return randomBytes(32).toString("hex"); // 64-char random string
}

export function hashRefreshToken(token: string): string {
  return createHash("sha256").update(token).digest("hex");
}
Code — Session Storage (Redis)

session.service.ts

src/modules/auth/session.service.ts
import { redis } from "../../config/redis.js";

const SESSION_TTL_SECONDS = 60 * 60 * 24 * 7; // 7 days

interface SessionData {
  userId: string;
  createdAt: number;
}

export async function createSession(refreshTokenHash: string, data: SessionData) {
  await redis.set(`auth:session:${refreshTokenHash}`, JSON.stringify(data), {
    EX: SESSION_TTL_SECONDS,
  });
}

export async function getSession(refreshTokenHash: string): Promise {
  const raw = await redis.get(`auth:session:${refreshTokenHash}`);
  return raw ? JSON.parse(raw) : null;
}

export async function revokeSession(refreshTokenHash: string) {
  await redis.del(`auth:session:${refreshTokenHash}`);
}
Code — Rotation

Single-use: delete old, create new

rotateSession
export async function rotateSession(oldHash: string, newHash: string) {
  const existing = await getSession(oldHash);
  if (!existing) return null;

  await revokeSession(oldHash);
  await createSession(newHash, existing);
  return existing;
}

export async function refreshController(req: Request, res: Response) {
  const refreshToken = req.cookies.refreshToken;
  if (!refreshToken) {
    return res.status(401).json({ success: false, message: "No refresh token" });
  }

  const refreshTokenHash = hashRefreshToken(refreshToken);
  const session = await getSession(refreshTokenHash);

  if (!session) {
    const reused = await wasTokenAlreadyUsed(refreshTokenHash);
    if (reused) {
      await revokeAllSessions(reused.userId);
      res.clearCookie("refreshToken", { path: "/auth/refresh" });
      return res.status(401).json({ success: false, message: "Session revoked — please log in again" });
    }
    return res.status(401).json({ success: false, message: "Invalid or expired session" });
  }

  const user = await prisma.user.findUnique({
    where: { id: session.userId },
    include: { role: true },
  });
  if (!user) return res.status(401).json({ success: false, message: "User not found" });

  const newAccessToken = generateAccessToken({ sub: user.id, role: user.role.name });
  const newRefreshToken = generateRefreshToken();
  const newRefreshTokenHash = hashRefreshToken(newRefreshToken);

  await rotateSession(refreshTokenHash, newRefreshTokenHash);

  res.cookie("refreshToken", newRefreshToken, {
    httpOnly: true,
    secure: env.NODE_ENV === "production",
    sameSite: "strict",
    maxAge: 7 * 24 * 60 * 60 * 1000,
    path: "/auth/refresh",
  });

  return res.status(200).json({ accessToken: newAccessToken });
}
Code — Logout

Revoke Redis + clear cookie

logoutController
export async function logoutController(req: Request, res: Response) {
  const refreshToken = req.cookies.refreshToken;
  if (refreshToken) {
    await revokeSession(hashRefreshToken(refreshToken));
  }
  res.clearCookie("refreshToken", { path: "/auth/refresh" });
  return res.status(204).send();
}
Interview Questions

Q & A

1. Why two tokens instead of one long-lived JWT?
A single long-lived JWT can't be revoked — if leaked, it's valid until it expires. Short-lived access + long-lived revocable refresh limits exposure without constant re-logins.
2. Why is the refresh token not a JWT?
It doesn't need to carry data — it's a lookup key. A JWT would let anyone decode the payload; an opaque random string reveals nothing.
3. Why hash before storing in Redis?
If Redis is compromised, the attacker sees hashes, not usable tokens — same principle as never storing raw passwords.
4. Why SHA-256 for refresh tokens but Argon2 for passwords?
Passwords are low-entropy, so a slow salted hash resists brute-force. Refresh tokens are 256 bits of random data — brute-force is already infeasible, so a fast hash is enough.
5. What is rotation, and why does it matter?
Each use replaces the token and destroys the old one. Stolen tokens work once — damage window is limited instead of indefinite access.
6. What is reuse detection?
An already-rotated token presented again is a theft signal. Revoke all sessions for that user — attacker and legitimate user both re-authenticate.
7. Why HttpOnly cookie instead of the response body?
Invisible to JavaScript, so XSS can't steal it. Access token is fine in the body — short-lived, kept in memory.
8. What does SameSite=Strict protect against?
CSRF — the browser won't send the cookie on cross-site requests, so a malicious site can't trigger refresh on the user's behalf.
9. Why Redis instead of a longer-lived JWT?
Revocability needs a server-side record. A JWT is signature-only — you can't delete one once issued. Redis lets you invalidate on logout, theft, or admin action.
10. Redis down — fail open or fail closed?
Fail closed. getSession() throws or returns nothing; refresh returns 401/500. Never assume the session is valid. Wrap Redis in try/catch.
11. Why is refresh TTL longer than access TTL?
Access is short to limit per-request exposure. Refresh is longer so users aren't password-logging every 15 minutes — still re-auth every 7 days, not forever.
12. How would you implement “log out of all devices”?
Track session hashes per user (Redis Set auth:user-sessions:{userId}). On logout-all, delete every session key in that set plus the set itself.
13. Risk of NOT rotating refresh tokens?
The token becomes a de facto permanent credential. If intercepted, it grants access until the long TTL expires — no way to detect or limit the compromise.
14. Why not just extend the access token expiry?
A longer-lived access token still can't be revoked. You'd trade “annoying re-login” for “can't cut off a compromised token.” Two tokens solve both.
