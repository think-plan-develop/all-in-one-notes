Interview notes — schema basics, data types, validation, arrays & refs, methods, middleware.

Basics & Data Types Validation Arrays, Nested & Refs Virtuals, Methods & Middleware Interview Q&A
💡 Important framing: Schema is the blueprint, Model is the compiled class that talks to MongoDB, and Document is a single record created from a Model.
🔑 Key Terms at a Glance
🏗️
Schema: Defines the shape, types, and rules of documents in a collection — no DB interaction on its own.
🧬
Mixed: An "anything goes" type Mongoose won't validate or auto-detect changes on.
🔗
ObjectId + ref: Store a reference to another document, then join it at query time with populate().
👻
Virtual: A computed field derived at runtime — never stored in MongoDB.
🪝
Middleware (hooks): Functions that run before/after operations like save, find, or delete.
🔑
unique: true: Creates a database index, not a Mongoose validator — failures throw code 11000, not ValidationError.
1. Schema Basics & Data Types

Schema → Model → Document

★★★★★

A Schema defines the shape of documents in a collection — fields, types, rules. The Model is the compiled class you actually use to create/read/update/delete documents.

Schema → defines shape + rules
↓
Model → compiled class for CRUD
↓
Document → a single record / instance
models/user.model.ts
import mongoose, { Schema, Document, Model } from 'mongoose'

interface IUser extends Document {
  name: string; email: string; age: number; isActive: boolean
}

const userSchema = new Schema<IUser>({
  name:     { type: String,  required: true },
  email:    { type: String,  required: true, unique: true },
  age:      { type: Number },
  isActive: { type: Boolean, default: true }
})

const User: Model<IUser> = mongoose.model<IUser>('User', userSchema)
export default User
💡 mongoose.model('User', schema) automatically looks for/creates a collection named users (pluralized, lowercased). You never create the collection manually.

Mixed

Accepts anything — no validation, no cast. Mutating it requires doc.markModified('field') before .save(), or the change is silently lost.

Decimal128

High-precision decimals for money. Use mongoose.Types.Decimal128.fromString('19.99'); read back with .toString().

⚠️ Storing large files as Buffer in MongoDB isn't recommended. Use GridFS for files >16MB, or store in S3 and save only the URL.

Map Type — Dynamic Keys

Use when a document has dynamic/unknown keys — like user preferences or metadata where key names aren't predefined.

Map example
const userSchema = new Schema({
  name: String,
  preferences: { type: Map, of: String }
})

user.preferences.set('theme', 'dark')
user.preferences.get('theme') // 'dark'
2. Validation — Required, Min/Max, Enum, Custom

Required & String Validators

★★★★★
required + string validators
const userSchema = new Schema({
  name: {
    type: String, required: true,
    trim: true,          // removes leading/trailing spaces before saving
    minlength: [2, 'Min 2 characters'],
    maxlength: [50, 'Max 50 characters']
  },
  email: {
    type: String, required: [true, 'Email is required'],
    trim: true, lowercase: true  // "USER@Email.COM" → "user@email.com"
  },
  companyName: {
    type: String,
    required: function() { return this.role === 'business' } // conditional
  }
})
💡 minlength/maxlength are String validators. For Number, use min/max instead — they're different properties, don't mix them up.

Number Validation, Defaults & Enum

number + default + enum
const productSchema = new Schema({
  price: { type: Number, required: true, min: [0, 'Cannot be negative'], max: 99999 },
  joinedAt: { type: Date, default: Date.now },  // pass reference, not Date.now()
  role: {
    type: String,
    enum: { values: ['user', 'admin', 'moderator'], message: '{VALUE} is not valid' },
    default: 'user'
  }
})
⚠️ default: Date.now — pass the function reference, not Date.now(). With parentheses it evaluates once at schema definition time; without, it runs on every document creation.
TypeScript enum pattern
const ROLES = ['user', 'admin', 'moderator'] as const
type Role = typeof ROLES[number]  // 'user' | 'admin' | 'moderator'

const userSchema = new Schema<{ role: Role }>({
  role: { type: String, enum: ROLES, default: 'user' }
})

Unique — Not a Validator

handling duplicate key error
try {
  await User.create({ email: 'existing@email.com' })
} catch (err: any) {
  if (err.code === 11000) {
    const field = Object.keys(err.keyValue)[0]
    throw new Error(`${field} already exists`)
  }
}
🚨 unique: true is NOT a Mongoose validator — it creates a MongoDB index. Violations throw a MongoServerError code 11000, not a Mongoose ValidationError. Handle it separately in your error middleware.

Custom Validation

custom validators
import validator from 'validator'

const userSchema = new Schema({
  age: {
    type: Number,
    validate: { validator: (v: number) => v >= 18, message: 'Must be 18+' }
  },
  email: {
    type: String, required: true,
    validate: { validator: (v: string) => validator.isEmail(v), message: 'Invalid email' }
  },
  username: {
    type: String,
    validate: {
      validator: async function(v: string) {
        const exists = await User.findOne({ username: v })
        return !exists
      },
      message: 'Username is already taken'
    }
  }
})

Custom validators can be sync or async — perfect for uniqueness checks that need a DB query, though for reusable business-rule checks the service layer is often a cleaner home.

3. Arrays, Nested Objects & ObjectId References

Arrays — Primitives & Subdocuments

★★★★★
arrays
const postSchema = new Schema({
  tags: [String],  // shorthand array of primitives

  items: [{  // array of subdocuments
    productId: { type: Schema.Types.ObjectId, ref: 'Product' },
    name: { type: String, required: true },
    quantity: { type: Number, min: 1, required: true }
  }]
})

post.tags.push('nodejs')
post.tags.pull('nodejs')      // Mongoose array method to remove
post.tags.addToSet('react')  // adds only if not already present
💡 Each item in a subdocument array gets its own _id automatically. Disable with { _id: false } inside the array's object definition.

Nested Objects vs Reusable Embedded Schemas

Inline Nested

address: { street, city, zip } defined directly inside the parent schema.

Reusable Embedded Schema

Define addressSchema separately, then reuse it for both address and billingAddress.

reusable embedded schema
const addressSchema = new Schema({
  street: { type: String, required: true },
  city:   { type: String, required: true },
  zip:    String
}, { _id: false })

const userSchema = new Schema({
  name: String,
  address: addressSchema,
  billingAddress: addressSchema  // reused!
})
✅ Rule of thumb: embed data that always belongs to the parent (address, profile). Use a ref when data is shared across documents (user → orders, product → category).

ObjectId References & populate()

References link documents across collections. Store just the ObjectId, then use populate() to join the related document at query time.

populate
// Without populate — author is just an ObjectId
const post = await Post.findById(id)
post.author  // ObjectId("64abc...")

// With populate — author is the full User document
const post = await Post.findById(id).populate('author')
post.author.name  // 'John Doe'

// Deep populate — populate inside a populated doc
const post = await Post.findById(id).populate({
  path: 'author',
  populate: { path: 'department', select: 'name' }
})
💡 populate() runs a second query to fetch referenced documents. For large datasets, consider MongoDB's $lookup aggregation instead for better performance.
4. Virtuals, Methods & Middleware

Timestamps & Virtual Fields

★★★★★
timestamps + virtuals
const userSchema = new Schema({
  firstName: String, lastName: String, birthYear: Number
}, {
  timestamps: true,               // adds createdAt + updatedAt automatically
  toJSON: { virtuals: true }       // include virtuals in JSON.stringify()
})

userSchema.virtual('fullName').get(function() {
  return `${this.firstName} ${this.lastName}`
})

userSchema.virtual('age').get(function() {
  return new Date().getFullYear() - this.birthYear
})
💡 Virtuals are computed properties — never stored in MongoDB. Great for fullName, age, totalPrice — values you want in your API but don't need to persist.

Instance vs Static Methods vs Query Helpers

methods
// Instance method — called on a document
userSchema.methods.comparePassword = async function(candidate: string) {
  return bcrypt.compare(candidate, this.password)
}
const match = await user.comparePassword('pw')

// Static method — called on the Model
userSchema.statics.findByEmail = function(email: string) {
  return this.findOne({ email: email.toLowerCase() })
}
const user = await User.findByEmail('a@b.com')

// Query helper — chainable on a query
userSchema.query.byActive = function() { return this.where({ isActive: true }) }
const admins = await User.find().byActive()
TypeCalled onUse case
Instance methodDocument (user.method())Hashing, formatting, per-doc logic
Static methodModel (User.method())Custom finders, factory methods
Query helperQuery chain (User.find().helper())Reusable query filters
⚠️ Always use function, never an arrow function, in schema methods and hooks — arrow functions don't bind their own this, breaking access to this.fieldName.

Middleware — Pre & Post Hooks

pre/post hooks
// runs BEFORE every .save()
userSchema.pre('save', async function(next) {
  if (!this.isModified('password')) return next()
  const salt = await bcrypt.genSalt(12)
  this.password = await bcrypt.hash(this.password, salt)
  next()
})

// runs AFTER save completes
userSchema.post('save', function(doc) {
  console.log(`User saved: ${doc.email}`)
})

// cascade delete — delete related docs before this one
userSchema.pre('deleteOne', { document: true, query: false }, async function() {
  await Post.deleteMany({ author: this._id })
})
HookTriggers on
pre('save')doc.save(), Model.create()
pre('validate')Before validation runs
pre('find')Model.find(), findOne()
pre('findOneAndUpdate')findByIdAndUpdate()
post('save')After save completes
🚨 findByIdAndUpdate does not trigger pre('save') — it goes straight to MongoDB. Use pre('findOneAndUpdate'), or pass runValidators: true to still run validation.
Interview Q&A
💡 Interview Q&A
Standard Questions
What is the difference between a Mongoose Schema and a Model?
A Schema is the blueprint — field types, validation rules, defaults, methods — with no DB interaction on its own. A Model is the compiled version of a schema, the class you actually use for CRUD operations against the collection (User.find(), User.create()).
Why is unique: true not a Mongoose validator?
It tells Mongoose to create a MongoDB unique index — handled at the database level, not by Mongoose's validation pipeline. A duplicate insert throws a MongoServerError with code 11000, not a Mongoose ValidationError, so it needs its own check in your error handler.
What's the difference between minlength and min?
minlength/maxlength are String validators checking the number of characters. min/max are Number validators checking the numeric value. Using the wrong pair on a field type won't behave as expected.
Why should you use the function keyword, not arrow functions, in schema methods and hooks?
Arrow functions don't have their own this binding — they inherit it from the enclosing scope, not the document or query. Mongoose middleware and methods rely on this referring to the current document or query, which arrow functions break entirely.
What is a virtual field and when would you use one?
A computed property derived from other fields at runtime, defined with schema.virtual('name').get(fn), never stored in MongoDB. Useful for fullName, age, or totalPrice — values your API needs but that don't need to be persisted.
Tricky / Follow-Up Questions
Does findByIdAndUpdate trigger the pre('save') hook?
No. It bypasses Mongoose document middleware entirely and sends the update directly to MongoDB. To run validation on update, pass { runValidators: true, new: true }; to intercept it with middleware, use pre('findOneAndUpdate') instead.
What's the difference between embedding a document and using a ref?
Embedding stores child data inside the parent — faster reads (one query) but data duplication if reused elsewhere; good for data that always belongs to one parent, like an address. A reference stores only an ObjectId and needs populate() to join it — better for shared or large data, like user → orders.
What is a sparse index and why would you need one?
A sparse index only indexes documents where the field exists. Without it, a unique index on an optional field fails once two documents both have the field as null, since MongoDB treats null as a value subject to the unique constraint. sparse: true excludes documents missing the field from the index.
What's the catch with using the Mixed type?
Mongoose can't automatically detect changes to a Mixed field. If you mutate it in place, you must call doc.markModified('fieldName') before .save(), or the change silently won't be persisted.
Frequently Asked
What's the difference between instance methods and static methods?
Instance methods (schema.methods.fn) are called on a single document, with this as the document — e.g. user.comparePassword(). Static methods (schema.statics.fn) are called on the Model class itself, with this as the Model — e.g. User.findByEmail().
Why pass Date.now as a default instead of Date.now()?
Date.now() with parentheses evaluates immediately at schema-definition time, so every document would get the same fixed timestamp. Passing the bare function reference Date.now means Mongoose calls it fresh at document-creation time instead.
What does populate() actually do under the hood?
It runs a second query to fetch the documents referenced by an ObjectId field and replaces the ID with the full document. For very large datasets or performance-sensitive joins, MongoDB's $lookup aggregation stage can be a faster single-query alternative.
Coding / Theoretical
Write a schema with a pre-save password hash hook and an instance method to verify it.
models/User.ts
import bcrypt from 'bcryptjs'
import { Schema, model } from 'mongoose'

const userSchema = new Schema({
  email: { type: String, required: true, unique: true, lowercase: true },
  password: { type: String, required: true, minlength: 8 }
}, { timestamps: true })

userSchema.pre('save', async function(next) {
  if (!this.isModified('password')) return next()
  const salt = await bcrypt.genSalt(12)
  this.password = await bcrypt.hash(this.password, salt)
  next()
})

userSchema.methods.comparePassword = async function(candidate: string) {
  return bcrypt.compare(candidate, this.password)
}

export const User = model('User', userSchema)

Why this shape: isModified('password') avoids re-hashing an already-hashed password on unrelated updates, and the regular function keyword keeps this bound to the document in both the hook and the instance method.

Explain, in three layers, why Mongoose schema validation alone doesn't guarantee data integrity for updates.
Each layer has a specific gap: document validators (defined on the schema) only run automatically on .save()/.create(), not on query-based updates like findByIdAndUpdate, which go straight to MongoDB. Explicit runValidators: true re-enables validation for those update queries, but conditional validators using this may still behave differently since this refers to the query, not the document, in update middleware. Middleware hooks like pre('findOneAndUpdate') are the way to reliably intercept and enforce logic on update paths that bypass save-based validation.
