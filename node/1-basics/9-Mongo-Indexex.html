💡 Important framing: An index turns a full collection scan (COLLSCAN) into a targeted lookup (IXSCAN) — but every index also has a write-time cost, so index what you query, not everything you have.
🔑 Key Terms at a Glance
📇
Index: A sorted data structure (B-tree) MongoDB maintains on a field so lookups are O(log n) instead of a full scan.
🔗
Compound Index: An index across multiple fields together — only usable when the query includes the leading field.
🕳️
Sparse Index: Only indexes documents where the field actually exists — skips null/missing values.
⏳
TTL Index: Auto-deletes documents a set number of seconds after a Date field — no cron job needed.
🔤
Text Index: Enables full-text $text search with stemming and relevance scoring — only one per collection.
🔍
explain(): Shows whether MongoDB used IXSCAN (index) or COLLSCAN (full scan) for a query.
1. Simple & Compound Indexes

Why Indexes Matter

★★★★★

Indexes make queries faster by letting MongoDB find documents without scanning the entire collection. Without an index on a queried field, MongoDB does a full collection scan — slow on large data.

indexes on schema fields
const userSchema = new Schema({
  email:    { type: String, unique: true, index: true },  // simple index
  username: { type: String, index: true },
  phone:    { type: String, sparse: true, index: true }
})

// compound index — defined at schema level
userSchema.index({ role: 1, createdAt: -1 })

// text index — for full-text search
postSchema.index({ title: 'text', body: 'text' })

// TTL index — auto-delete after N seconds
sessionSchema.index({ createdAt: 1 }, { expireAfterSeconds: 3600 })
💡 1 = ascending, -1 = descending. Direction matters for compound indexes depending on query and sort patterns.

Simple Index — B-Tree Lookup

An index on a single field. MongoDB maintains a sorted B-tree for that field so lookups are O(log n) instead of O(n).

simple index — query + explain
const userSchema = new Schema({ email: { type: String, index: true } })

await User.findOne({ email: 'john@example.com' }).explain('executionStats')
explain() output
winningPlan: { stage: 'FETCH', inputStage: { stage: 'IXSCAN' } }
executionStats: { totalDocsExamined: 1, totalKeysExamined: 1 }  ← only 1 doc scanned
Without index (COLLSCAN) → scans all 1,000,000 docs → slow
vs
With index (IXSCAN) → scans exactly 1 doc → fast

Compound Index — the ESR Rule

compound index behavior
userSchema.index({ role: 1, createdAt: -1 })

// ✅ uses index — leading field 'role' present
await User.find({ role: 'admin' })

// ✅ uses index — both fields present
await User.find({ role: 'admin' }).sort({ createdAt: -1 })

// ❌ does NOT use index — createdAt alone, not the leading field
await User.find({}).sort({ createdAt: -1 })
QueryUses index?
{ role }✅ IXSCAN
{ role, createdAt }✅ IXSCAN
{ createdAt } alone❌ COLLSCAN
✅ ESR rule: put Equality fields first, Sort fields second, Range fields last in compound indexes. Always put the most selective field first.
2. Sparse, TTL & Text Indexes

Sparse Index — Skip Missing Fields

★★★★★

Only indexes documents where the field exists. Documents where it's null or missing are excluded from the index entirely.

❌ Without sparse

problem
phone: { type: String, unique: true }

await User.create({ name: 'Alice' }) // phone = null
await User.create({ name: 'Bob' })   // phone = null

Throws E11000 duplicate key error — null is treated as a duplicate value.

✅ With sparse: true

solution
phone: { type: String, unique: true, sparse: true }

await User.create({ name: 'Alice' }) // ✅ not indexed
await User.create({ name: 'Bob' })   // ✅ not indexed

Both succeed — only documents with a real phone value participate in the unique index.

TTL Index — Auto-Expiry

Auto-deletes documents after a specified number of seconds from a Date field. Perfect for sessions, OTP tokens, password-reset links.

TTL index — OTP expires in 5 min
const otpSchema = new Schema({
  email: String, otp: String,
  createdAt: { type: Date, default: Date.now }
})
otpSchema.index({ createdAt: 1 }, { expireAfterSeconds: 300 })
10:00:00 → OTP created
↓
10:05:00 → TTL fires (background task, ~every 60s)
↓
findOne() → null, document auto-deleted
⚠️ TTL deletion isn't instant — MongoDB's background task runs roughly every 60 seconds, so documents may persist briefly past their exact expiry time.

Text Index — Full-Text Search

Lets you search string content with the $text operator — supports stemming, stop words, and relevance scoring across multiple fields.

text index — query with score
postSchema.index({ title: 'text', body: 'text' })

const results = await Post.find(
  { $text: { $search: 'mongoose schema' } },
  { score: { $meta: 'textScore' } }
).sort({ score: { $meta: 'textScore' } })

// exclude a word
await Post.find({ $text: { $search: 'mongoose -schema' } })
Query result, sorted by relevance
[
  { title: 'Mongoose Schema Guide',    score: 2.5  },
  { title: 'MongoDB Basics',           score: 0.75 },
  { title: 'Node.js with Mongoose',    score: 0.5  }
]
💡 Only one text index is allowed per collection. To search multiple fields, put them all in the same text index definition.
3. Performance & Maintenance

COLLSCAN vs IXSCAN — Full Comparison

★★★★★
explain() side by side
// ❌ NO INDEX on 'email' — full collection scan
await User.findOne({ email: 'john@gmail.com' }).explain('executionStats')
Without index
winningPlan: { stage: 'COLLSCAN' }
executionStats: { totalDocsExamined: 100000, executionTimeMillis: 340 }
With index

Why Too Many Indexes Slow Down Writes

Every index is a separate B-tree MongoDB must keep in sync. On every insert, update, or delete, MongoDB must update all indexes on that collection — more indexes means more write work per document change.

1 index → 1 doc write + 2 index updates (fast)
vs
6 indexes → 1 doc write + 7 index updates (3–4x slower)
⚠️ Rule of thumb: index what you query, not every field you have.
Interview Q&A
💡 Interview Q&A
Standard Questions
What is the difference between a Mongoose Schema and a Model?
A Schema is the blueprint — field types, validation rules, defaults, methods — with no DB interaction on its own. A Model is the compiled version of a schema, the class you use for CRUD operations (User.find(), User.create()).
Why is unique: true not a Mongoose validator?
It tells Mongoose to create a MongoDB unique index — handled at the database level, not by Mongoose's validation pipeline. A duplicate insert throws a MongoServerError with code 11000, not a ValidationError, so it needs its own check.
What's the difference between minlength and min?
minlength/maxlength are String validators checking character count. min/max are Number validators checking numeric value — mixing them up on the wrong type won't behave as expected.
What is a sparse index and why is it needed?
A sparse index only indexes documents where the field exists (not null/undefined). Without it, a unique index on an optional field fails once two documents both have null, since null is treated as a value subject to the unique constraint.
What is the difference between embedded documents and references (ref)?
Embedded data lives inside the parent — faster reads (one query) but duplicated if reused elsewhere; good for data that always belongs to one parent. A reference stores only an ObjectId and needs populate() to join — better for shared or large data.
Tricky / Follow-Up Questions
What happens internally when you run a query without an index vs with one?
Without an index, MongoDB does a COLLSCAN (collection scan), reading every document. With an index, it does an IXSCAN (index scan), reading only matching entries. explain('executionStats') shows totalDocsExamined dropping from the full collection size down to just the matches.
Does a compound index { role: 1, createdAt: -1 } help a query on createdAt alone?
No — a compound index can only be used when the query includes the leading field (role). Querying on createdAt alone results in a COLLSCAN, since the index can't be entered without its leading key.
Is TTL deletion instant the moment a document expires?
No. MongoDB runs a background task roughly every 60 seconds to sweep expired documents, so a document may persist for up to about a minute past its exact TTL expiry before actually being removed.
Can you have more than one text index per collection?
No — MongoDB allows only one text index per collection. To search across multiple fields, include all of them in that single text index definition, e.g. { title: 'text', body: 'text', tags: 'text' }.
Frequently Asked
Why does adding too many indexes slow down writes?
Every index is a separate B-tree MongoDB must keep synchronized with the collection. Each insert, update, or delete has to update every index on that collection, so more indexes mean more write-time work per document change — index only what you actually query.
What does the ESR rule mean for compound indexes?
Equality fields first, Sort fields second, Range fields last. Ordering a compound index this way maximizes how many query shapes it can serve efficiently, since MongoDB can only use the index's leading prefix of fields.
How would you check what indexes currently exist on a collection?
Model.collection.getIndexes() lists every index with its key pattern and options (unique, sparse, etc.) — useful for debugging whether an expected index was actually created, and for cleaning up unused ones with dropIndex().
Coding / Theoretical
Write a schema for password-reset tokens that auto-expire after 15 minutes, and show how you'd verify the index worked.
models/ResetToken.ts
import { Schema, model } from 'mongoose'

const resetTokenSchema = new Schema({
  userId: { type: Schema.Types.ObjectId, ref: 'User', required: true },
  token: { type: String, required: true },
  createdAt: { type: Date, default: Date.now }
})

resetTokenSchema.index({ createdAt: 1 }, { expireAfterSeconds: 900 }) // 15 min

export const ResetToken = model('ResetToken', resetTokenSchema)

// verify the index exists
const indexes = await ResetToken.collection.getIndexes()
// { createdAt_1: { key: { createdAt: 1 }, expireAfterSeconds: 900 } }

Why this shape: createdAt defaults automatically to the moment of creation, and the TTL index needs no application code to enforce expiry — MongoDB's background sweep handles deletion on its own.

Explain, in three layers, why indexing strategy needs to balance reads and writes rather than just adding an index for every query.
Each layer trades off differently: a missing index on a frequently-queried field means every read is a COLLSCAN — correct but slow, and it gets worse as the collection grows. An index for every field fixes reads but means every write now updates one more B-tree, so insert/update/delete throughput degrades, especially on write-heavy collections. The right strategy is a small set of compound indexes shaped around actual query patterns (using the ESR rule) — this covers the read paths that matter while keeping the write-time index-maintenance cost bounded.
