Validation — Node + TypeScript + MongoDB

Interview notes — Zod input validation, Mongoose schema validation, DTOs, async checks and sanitization.

Input Validation (Zod) Schema Validation (Mongoose) DTOs, Async Checks & Sanitization Interview Q&A
💡 Important framing: Validation is layered — Zod protects the API boundary, Mongoose is the last line of defense at the database, and sanitization/DTOs tie the two together with type safety.
🔑 Key Terms at a Glance
🧾
Zod: A TypeScript-first schema library used to validate request data at the middleware layer and infer types from it.
🛢️
Mongoose Schema Validators: Constraints defined on the model itself — the last safety net, catching data from any source.
📦
DTO: A typed contract for data moving between layers, usually inferred from a Zod schema with z.infer.
🔎
Async Validation: Business-rule checks that require a DB query — e.g. "is this email already taken?"
🧼
Sanitization: Transforming input — trimming, lowercasing, stripping unknown fields and NoSQL operators.
🚨
Global Error Handler: 4-parameter Express middleware that turns Zod, Mongoose, and driver errors into consistent responses.
1. Input Validation with Zod

What It Means

★★★★★

Every request — body, params, query — must be validated at the route/middleware level before your controller or DB ever sees it. Use Zod (recommended with TypeScript) to define a schema and reject bad data immediately with a structured error response.

Request
↓
Zod Middleware
↓
✅ Valid → Controller → Service → DB
❌ Invalid → 400 Bad Request

Define Schema + Infer Type

schemas/user.schema.ts
import { z } from 'zod';

export const userSchema = z.object({
  firstName: z.string().trim().min(2).max(50),
  lastName:  z.string().trim().min(1),
  email:     z.email().toLowerCase(),
  role:      z.enum(["ADMIN", "USER", "MASTER_USER"]).default("USER"),
  isActive:  z.boolean().default(true),
  age:       z.number().int().min(18).max(100),
});

// Infer TypeScript type from schema — no duplication!
export type UserInput = z.infer<typeof userSchema>;

Reusable Validate Middleware

middleware/validate.ts
import type { Request, Response, NextFunction } from "express";
import { z } from "zod";

export const validate =
  (schema: z.ZodType) =>
  (req: Request, res: Response, next: NextFunction) => {

    const result = schema.safeParse(req.body);

    if (!result.success) {
      const errors = result.error.issues.map(e => ({
        field:   e.path.join('.'),
        message: e.message,
      }));
      return res.status(400).json({ success: false, errors });
    }

    req.body = result.data;   // replace with sanitised + typed data
    next();
  };
routes/user.route.ts
router.post('/users', validate(userSchema), createUser);
// If body is invalid → 400 auto. Never reaches createUser.
  • safeParse never throws — returns { success, data, error } safely
  • Zod infers TypeScript types from the schema — write once, types are free
  • Assigning req.body = result.data automatically strips unknown fields

The Curried Middleware Pattern

(schema: z.ZodType) => (req, res, next) => {...} — read it as "a function that returns a function":

  • Outer function — takes schema as config. Runs once, when you write validate(userSchema).
  • Inner function — the real Express middleware. Runs on every request and "remembers" schema via closure.
💡 This is why you write validate(userSchema) in router.post(), not validate(req, res, next, userSchema).
PieceMeaning
safeParse()Never throws — always returns { success, data | error }
result.successBoolean gate: true → use result.data, false → use result.error
result.error.issuesArray of failed rules, each with .path and .message
e.path.join('.')Turns a nested path array into a dotted string, e.g. address.zipCode
z.ZodTypeGeneric "any Zod schema" type — lets validate() be reused everywhere
2. Schema-Level Validation (Mongoose)

Two Layers of Protection

★★★★★

Even after input validation, define constraints directly in your Mongoose schema. This is a backup layer — it catches invalid data that bypasses the API entirely, such as seeding scripts, admin tools, or internal service calls.

Layer 1 — Zod (API layer)

Catches bad HTTP request input before it reaches your controller.

Layer 2 — Mongoose Schema

Catches bad data from any source — API, scripts, cron jobs, seeds.

Mongoose Schema with Validators

models/User.ts
import { Schema, model } from 'mongoose';

const userSchema = new Schema({
  name: {
    type: String,
    required: [true, 'Name is required'],
    trim: true,
    minlength: [2, 'Min 2 characters'],
    maxlength: [50, 'Max 50 characters'],
  },
  email: {
    type: String,
    required: [true, 'Email is required'],
    unique: true,   // DB index — NOT a validator
    lowercase: true,
    validate: {
      validator: (v: string) => /\S+@\S+\.\S+/.test(v),
      message: 'Invalid email format',
    },
  },
  role: {
    type: String,
    enum: { values: ['admin', 'user', 'guest'], message: '{VALUE} is not a valid role' },
    default: 'user',
  },
  age: {
    type: Number,
    min: [18, 'Must be 18 or above'],
    max: [100, 'Must be 100 or below'],
  },
}, { timestamps: true });

export const User = model('User', userSchema);

Flow — How an Error Reaches errorHandler

Controller calls Mongoose: User.create(req.body)
↓
Mongoose runs schema validators (required, min, max, enum, custom)
↓
✅ all pass → saved → res.json
❌ fails → throws ValidationError / CastError / E11000
↓
Controller's try/catch → next(err)
↓
Express skips normal routes → finds 4-param middleware
↓
errorHandler(err, req, res, next) formats the response
controllers/user.controller.ts
export const createUser = async (req: Request, res: Response, next: NextFunction) => {
  try {
    const user = await User.create(req.body);
    return res.status(201).json({ success: true, data: user });
  } catch (err) {
    next(err);  // ← hand off to errorHandler, do NOT res.json() here
  }
};
✅ Two different layers, two different catch points: Zod is caught inside the validate() middleware via safeParse() and responds directly. Mongoose is caught inside the controller's try/catch and forwarded with next(err) to the global error handler.

Global Error Handler

middleware/errorHandler.ts
import type { Request, Response, NextFunction } from "express";
import { Error as MongooseError } from "mongoose";

export const errorHandler = (err: any, req: Request, res: Response, next: NextFunction) => {

  if (err instanceof MongooseError.ValidationError) {
    const errors = Object.values(err.errors).map(error => ({
      field: error.path, message: error.message,
    }));
    return res.status(400).json({ success: false, errors });
  }

  if (err.code === 11000) {
    return res.status(409).json({
      success: false, message: "Duplicate value found",
      fields: Object.keys(err.keyPattern),
    });
  }

  if (err instanceof MongooseError.CastError) {
    return res.status(400).json({ success: false, message: `Invalid ${err.path}` });
  }

  return res.status(500).json({ success: false, message: err.message || "Internal Server Error" });
};
Error TypeTriggerStatus
MongooseError.ValidationErrorA field fails a schema validator during .save()/.create()400
err.code === 11000A unique index is violated — duplicate value409
MongooseError.CastErrorA value can't cast to the field's type — e.g. invalid ObjectId in /users/:id400
Anything elseUnhandled / unexpected error500
⚠️ Remember: unique: true in Mongoose creates a database index, not a Mongoose validator. It throws a duplicate key error (E11000), not a ValidationError — always handle it separately.
3. DTOs, Async Validation & Sanitization

DTO Pattern

★★★★

A DTO (Data Transfer Object) is a plain typed object that defines the exact shape of data flowing between layers — request → controller → service → DB. In TypeScript, Zod's z.infer gives you DTOs for free.

❌ Without DTO

Every function accepts any or raw req.body. No type safety, no autocomplete. A typo silently passes through.

✅ With DTO

Every layer knows the exact shape. TypeScript catches mismatches at compile time. Editor autocompletes every field.

dtos/user.dto.ts
import { z } from 'zod';

export const createUserSchema = z.object({
  name: z.string().min(2),
  email: z.string().email(),
  password: z.string().min(8),
});

export type CreateUserDTO = z.infer<typeof createUserSchema>;
// { name: string; email: string; password: string }

// .partial() makes all fields optional — perfect for PATCH
export const updateUserSchema = createUserSchema.partial();
export type UpdateUserDTO = z.infer<typeof updateUserSchema>;
HTTP req.body (unknown / any)
↓ validate middleware → Zod parses & strips unknown fields
CreateUserDTO (fully typed)
↓ Controller passes DTO to service
createUser(dto: CreateUserDTO)
↓ Service passes to Mongoose
User.create(dto) → MongoDB

Async Validation

Some validation requires hitting the database — "is this email already registered?" These checks cannot live in Zod (Zod handles shape/format only). Async validation belongs in the service layer.

services/user.service.ts
export const createUser = async (dto: CreateUserDTO) => {
  const existing = await User.findOne({ email: dto.email });
  if (existing) throw new AppError('Email already registered', 409);

  return User.create(dto);
};
utils/dbValidators.ts
// Generic reusable helpers — avoid repeating findOne everywhere
export const mustExist = async (Model: any, id: string, label: string) => {
  const doc = await Model.findById(id);
  if (!doc) throw new AppError(`${label} not found`, 404);
  return doc;
};

export const mustBeUnique = async (Model: any, filter: object, msg: string) => {
  const doc = await Model.findOne(filter);
  if (doc) throw new AppError(msg, 409);
};
  • Zod validates shape and format. Service layer validates business rules that need a DB query.
  • Extract common checks into reusable helpers — never repeat findOne in every service.
  • Always throw AppError with the correct status code and let the global error handler send the response.

Sanitization

Sanitization is transforming incoming data — trimming whitespace, lowercasing emails, stripping unknown fields, removing $ operators that could enable NoSQL injection. Zod handles most of this automatically on parse; pair it with express-mongo-sanitize for full protection.

app.ts
import mongoSanitize from 'express-mongo-sanitize';

// Removes keys starting with $ or containing a dot
// Prevents: { "email": { "$gt": "" } } attacks
app.use(mongoSanitize());

NoSQL injection { $gt: "" }Strip $ operator keysexpress-mongo-sanitize

String query param → number.transform(Number)Zod transform
XSS via stored HTML stringsSanitize HTML before savingDOMPurify
💡 When you assign req.body = result.data after Zod parses, you have already sanitized — only the fields you defined survive. Pair this with express-mongo-sanitize and you cover most sanitization needs with almost no extra effort.
Interview Q&A
💡 Interview Q&A
Standard Questions
Where should input validation happen — middleware or controller?
Middleware. Controllers should only handle business logic. Validation is a cross-cutting concern — one reusable middleware handles it for all routes without any code repetition.
What's the difference between .parse() and .safeParse() in Zod?
.parse() throws a ZodError on failure, requiring a try/catch. .safeParse() never throws — it always returns { success, data | error }, which is exactly what an Express middleware needs since sync throws inside route handlers aren't caught automatically.
If you already validate with Zod, why also add Mongoose validators?
Zod only protects the HTTP API layer. Data can enter the DB from seed scripts, cron jobs, or internal services that never go through your Express routes. Mongoose validators run on every .save() regardless of source — they're the true last line of defense.
What is a DTO and why use it over passing req.body directly?
A DTO is a typed contract for data moving between layers. Passing req.body directly spreads the any type everywhere, so TypeScript can't help you. DTOs give compile-time safety, autocomplete, and safe refactoring across all layers.
What is NoSQL injection and how do you prevent it in MongoDB?
An attacker sends something like { "email": { "$gt": "" } } in the request body; MongoDB treats $gt as a query operator and can return all users, bypassing intended filtering. Prevention: strip $-keyed fields with express-mongo-sanitize, and only accept the exact expected shape via Zod.
Tricky / Follow-Up Questions
What happens if you forget try/catch (or next(err)) in an async controller and Mongoose throws?
An unhandled promise rejection — in versions of Express before 5, this isn't automatically caught, so the request hangs and never sends a response. This is why teams wrap async controllers in a helper like asyncHandler(fn) that automatically does .catch(next) for every route.
Why check err.code === 11000 separately, outside the ValidationError check?
A duplicate-key error is thrown by the MongoDB driver, not Mongoose's validation pipeline — it's not an instance of MongooseError.ValidationError. It only happens when a unique index is violated at the database level, so it needs its own check and its own status code (409 instead of 400).
When does a CastError happen, and how is it different from a ValidationError?
CastError happens before validation even runs — when Mongoose tries to convert an incoming value to the schema's declared type and fails, e.g. an invalid ObjectId in /users/:id. ValidationError happens during .save()/.create() when a value is the right type but fails a rule like min or enum.
Can you do async validation inside Zod using .refine()?
Technically yes, but it's not recommended. Zod is for structure and format. Putting DB calls inside Zod middleware creates tight coupling and makes the logic hard to reuse — async business-rule checks belong in the service layer instead.
Frequently Asked
Why reassign req.body = result.data instead of leaving the original req.body?
result.data has defaults applied, transforms run (.trim(), .toLowerCase()), coercions done, and unknown keys stripped. The original req.body is raw and untransformed — using it instead throws away all of Zod's work.
How does Express know a function like errorHandler(err, req, res, next) is an error handler?
Express identifies error-handling middleware purely by arity — exactly four parameters. It must be registered last, after all routes, with app.use(errorHandler). Any next(err) call skips all normal middleware and jumps straight there.
Why does unique: true in a Mongoose schema not count as a validator?
It creates a database-level index, not something Mongoose's validation pipeline checks. Violating it throws a driver-level duplicate key error (E11000) instead of a ValidationError, so it must be handled as its own case in the error handler.
Coding / Theoretical
Write a generic validate() middleware factory and use it for two different schemas.
middleware/validate.ts
import type { Request, Response, NextFunction } from "express";
import { z } from "zod";

export const validate =
  (schema: z.ZodType) =>
  (req: Request, res: Response, next: NextFunction) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      return res.status(400).json({
        success: false,
        errors: result.error.issues.map(e => ({ field: e.path.join('.'), message: e.message })),
      });
    }
    req.body = result.data;
    next();
  };

// routes/index.ts
router.post("/users", validate(createUserSchema), createUser);
router.post("/login",  validate(loginSchema),      login);

Why this shape: typing the parameter as z.ZodType instead of a specific schema type is what makes validate() reusable across every route — one middleware, any schema.

Explain, in three layers, why "Zod + Mongoose + sanitization" is more robust than any single layer alone.
Each layer defeats a different failure mode:

• Zod rejects malformed HTTP input before it ever reaches business logic, and gives you compile-time DTO types for free.
• Mongoose schema validation catches data written from any source that skips the API — scripts, seeds, internal jobs — since it runs on every .save().
• Sanitization (Zod transforms + express-mongo-sanitize) removes dangerous or messy data — NoSQL operators, stray whitespace, unknown fields — that structurally "valid" data could still carry.

Removing any one layer reopens a specific gap: skip Zod and malformed requests reach the DB layer raw; skip Mongoose validators and non-API writes go unchecked; skip sanitization and structurally valid but malicious payloads (like $gt injection) get through.
