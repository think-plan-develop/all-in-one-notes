1. What is Node.js?

Definition

Node.js is a JavaScript runtime environment that allows JavaScript to run outside the browser — built by Ryan Dahl in 2009.

Normally, JavaScript runs inside a web browser like Chrome or Firefox. Node.js makes it possible to use JavaScript on the server for tasks like:

  • Building APIs
  • Creating web servers
  • Reading and writing files
  • Working with databases
  • Running command-line tools
  • Real-time applications (chat, games)
Why Was Node.js Created?

The Thread-Per-Request Problem

Before Node.js, most web servers (such as Apache running PHP or traditional Java servers) followed a thread-per-request model — every incoming client request got its own thread.

One thread per incoming request
⚠️ Problems: Huge memory usage · Expensive context switching · Slow performance under load.

Node.js solved this using:

  • A single thread
  • An Event Loop
  • Non-blocking I/O

2. The V8 Engine

What is V8?

V8 is the JavaScript engine that actually executes your JavaScript code — created by Google, originally to power Chrome.

Think of it this way: JavaScript is just text/code — something needs to read and run it. V8 is that "something." It takes JavaScript code and converts it into machine code (the low-level instructions your computer's CPU understands) so it can actually execute.

Node.js is built on top of V8. Node takes V8 (the same engine used in Chrome) and adds extra capabilities to it — like the ability to read/write files, work with networks, and access the operating system — things a browser normally wouldn't let JavaScript do for security reasons.

💡 So: V8 runs the JavaScript. Node.js wraps V8 and adds server-side superpowers.

3. Why Node.js is Fast

Reason 1 — V8's Compilation Approach

V8 compiles JavaScript directly into optimized machine code (instead of slowly interpreting it line-by-line), which makes execution quick.

Reason 3 — Event Loop

Node.js uses a single-threaded Event Loop to efficiently handle many concurrent requests.

Client → Event Loop → Worker Threads → Callback Queue → Event Loop

Instead of creating a new thread for every request, Node.js delegates long-running I/O operations (like file access or database queries) to the operating system or a worker thread pool, then continues processing other requests. When the operation finishes, the Event Loop handles the callback — greatly reducing memory usage and thread management overhead.

Event Loop (Deep Dive)

What is the Event Loop?

The Event Loop is the core mechanism in Node.js that enables non-blocking, asynchronous execution. When Node.js encounters a slow operation like reading a file, querying a database, or making an API call, it delegates that task to the operating system or libuv instead of blocking the main thread. The Event Loop continuously checks the Call Stack, and when it becomes empty, it executes completed callbacks from the Callback Queue. This allows Node.js to efficiently handle multiple concurrent requests using a single JavaScript thread.

Why Do We Need an Event Loop?

Imagine reading a file:

Read File │ ▼ Wait 5 Seconds │ ▼ Continue
⚠️ Without an Event Loop, the server would stop processing every other request while waiting — wasting CPU time.

Instead, Node.js delegates the slow operation and continues doing useful work.

event-loop-example.js
const fs = require("fs");

console.log("Start");

fs.readFile("demo.txt", () => {
    console.log("File Read");
});

console.log("End");

End

Event Loop Phases (Interview)

The 6 Phases Per Iteration

One Event Loop iteration — Timers → Pending → Idle/Prepare → Poll → Check → Close, then repeat
#PhaseWhat it does
1TimersExecutes callbacks scheduled by setTimeout() and setInterval().
2Pending CallbacksExecutes certain system-level callbacks deferred from the previous cycle.
3Idle / PrepareInternal phase used by Node.js.
4PollProcesses most I/O events, waits for new I/O if needed, and executes I/O callbacks.
5CheckExecutes callbacks scheduled with setImmediate().
6Close CallbacksExecutes close-event callbacks, such as socket.on("close").
⚡ process.nextTick() and Promise microtasks run before the Event Loop proceeds to the next phase — that's why they execute with higher priority than timer callbacks.
Interview Q&A — Node.js & Event Loop
💡 Interview Q&A
What is Node.js?
Node.js is a JavaScript runtime environment built on Google's V8 JavaScript engine. It allows JavaScript to run outside the browser and is mainly used for building scalable server-side applications, APIs, and real-time services.
What is the V8 Engine?
V8 is Google's open-source JavaScript engine used by Chrome and Node.js. It parses JavaScript and compiles it into optimized machine code using Just-In-Time (JIT) compilation, making execution very fast.
Why is Node.js fast?
Node.js is fast because it uses the V8 engine for optimized JavaScript execution, follows a non-blocking I/O model so it doesn't wait for slow operations, and uses a single-threaded Event Loop to efficiently handle many concurrent I/O requests with low memory overhead.
Why is Node.js called single-threaded?
Because JavaScript execution happens on a single main thread, coordinated by the Event Loop.
If Node.js is single-threaded, how can it handle thousands of users?
Because slow I/O operations are delegated to the operating system or libuv's worker thread pool, allowing the Event Loop to continue processing other requests without blocking.
Can Node.js use multiple threads?
Yes. Although JavaScript runs on one main thread by default, Node.js can use:
  • Worker Threads for CPU-intensive JavaScript.
  • Child Processes for separate Node.js processes.
  • The libuv worker thread pool for specific asynchronous operations like file system access and cryptography.
Give the 30-second interview answer for how Node.js handles concurrency.
Node.js executes JavaScript on a single main thread, but it uses an Event Loop with non-blocking I/O to handle many concurrent requests efficiently. Long-running operations such as file access or cryptography are delegated to the operating system or libuv's worker thread pool, allowing the main thread to keep serving other requests. Once an operation completes, its callback is placed in a queue, and the Event Loop executes it when the Call Stack is empty. This architecture makes Node.js highly efficient for I/O-bound applications while keeping memory usage relatively low.
What order do Start / End / File Read print in, and why?
fs.readFile() is asynchronous, so it never blocks the main thread. The synchronous lines run first, and the callback only runs once the file read finishes and the Event Loop finds the Call Stack empty.
console.log("Start") → synchronous, runs immediately fs.readFile(..., cb) → delegated to background, continues immediately console.log("End") → synchronous, runs immediately ...file finishes... cb() → console.log("File Read") → runs last, via Callback Queue Output: Start, End, File Read
Why do process.nextTick() and Promise microtasks run before timer callbacks?
The microtask queue (process.nextTick() and resolved Promises) is drained completely after the currently executing operation finishes and before the Event Loop is allowed to move into its next phase — including the Timers phase. This gives microtasks a higher priority than setTimeout() or setInterval() callbacks, even a setTimeout(fn, 0).
