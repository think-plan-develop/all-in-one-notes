An **absolute path** is the complete path from the filesystem root to a file or directory. ```text /Users/shivam/project/src/app.js ``` Here `/` is the filesystem root. A relative path is: ```text ./src/app.js ``` The difference is that an **absolute path does not depend on the current working directory**, while a relative path does. ### ESM replacement for `__dirname` and `__filename` ES Modules don't directly provide these variables. Use `import.meta.url`: ```js import path from "path"; import { fileURLToPath } from "url"; const __filename = fileURLToPath(import.meta.url); const __dirname = path.dirname(__filename); ``` Exact replacement: ```text CommonJS ES Module ──────────────────────────────────────────────────── __filename → fileURLToPath(import.meta.url) __dirname → path.dirname( fileURLToPath(import.meta.url) ) ``` `import.meta.url` gives the current module's location as a URL: ```js console.log(import.meta.url); // file:///Users/shivam/project/src/app.js ``` `fileURLToPath()` converts that URL into a normal filesystem path. ### Top-level `await` Normally, `await` works only inside an `async` function. **CommonJS:** ```js const data = await fetch(url); // ❌ ``` You need: ```js async function main() { const data = await fetch(url); console.log(data); } main(); ``` **ES Modules** allow `await` directly at the top level: ```js const response = await fetch("https://example.com"); console.log(response.status); ``` No wrapper function is required. ### Why Top-level `await`? It's not tied to *who* sends it, just *whether* it's valid. **1. Possession = access** The server only checks "Is this JWT valid?" — not who's holding it. - Legitimate user → JWT → API → ✅ - Attacker with stolen JWT → same JWT → API → ✅ (still works) That's what "bearer" means: possession is enough. **2. What `HttpOnly` protects against** If the JWT is stored in an `HttpOnly` cookie, browser JavaScript (`document.cookie`) can't read it directly. This blocks XSS attacks from stealing the token via script injection. **3. What `HttpOnly` doesn't protect against** If a token is stolen another way (device compromise, network leak, etc.), `HttpOnly` doesn't help — the server has no way to know the token was stolen. It just sees a valid JWT and grants access. **4. Why short expiration matters** A short `expiresIn` (e.g. `"15m"`) limits the damage window. If a token is stolen at 10:00, it's only usable until 10:15 — after that it's dead regardless of who has it. **5. Logout has limits** Logout clears the cookie on the legitimate browser — but if an attacker already copied the token, it's still valid until it naturally expires. Clearing your own cookie doesn't invalidate the token elsewhere. **Key takeaway** - **Bearer token** = possession is sufficient to use it. (Bearer token = "if you have it, you can use it." The server doesn't check who you are — it only checks whether the token itself is valid. No extra proof of identity needed, just the token) - **HttpOnly** stops JS from *reading* the token — it doesn't stop a *stolen* token from being *used*.
