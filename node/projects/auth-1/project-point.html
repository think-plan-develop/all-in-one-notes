__dirname and __filename

  • __dirname — absolute path of the directory containing the current file.
  • __filename — absolute path of the current file, including the filename.
app.js
console.log(__dirname);
// /Users/shivam/project/src

console.log(__filename);
// /Users/shivam/project/src/app.js
📌 Absolute path — full path from the filesystem root (/), independent of the current working directory. Relative path (e.g. ./src/app.js) — depends on where you run the command from.

ESM Replacement for __dirname / __filename

ES Modules don't provide these directly — reconstruct them via import.meta.url:

esm
import path from "path";
import { fileURLToPath } from "url";

const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);
CommonJSES Module equivalent
__filenamefileURLToPath(import.meta.url)
__dirnamepath.dirname(fileURLToPath(import.meta.url))
esm
console.log(import.meta.url);
// file:///Users/shivam/project/src/app.js
💡 fileURLToPath() converts that file URL into a normal filesystem path.
2. Top-Level await

How It Works

★★★★★

Normally await only works inside an async function.

CommonJS — needs a wrapper:

cjs
async function main() {
  const data = await fetch(url);
  console.log(data);
}
main();

ES Modules — works directly at the top level:

esm
const response = await fetch("https://example.com");
console.log(response.status);

Why It's Useful

Handy for async initialization before an app starts:

  • Database connection
  • Reading configuration
  • Loading secrets
  • Dynamic module loading
  • Initializing external services
compare
// CommonJS
async function start() {
  await connectDB();
  app.listen(3000);
}
start();

// ESM
await connectDB();
app.listen(3000);

5. Why JWT Is a "Bearer" Token

Possession = Access

★★★★★

A bearer token means whoever holds it can use it — the server checks validity, not identity.

🔑 1. Possession = access

The server only asks "is this JWT valid?" — not who's holding it.

  • Legitimate user → JWT → API → ✅
  • Attacker with stolen JWT → same JWT → API → ✅ (still works)
🛡️ 2. What HttpOnly protects against

Stored in an HttpOnly cookie, the token can't be read by browser JS (document.cookie) — blocking token theft via XSS/script injection.

⚠️ 3. What HttpOnly doesn't protect against

If the token leaks another way (device compromise, network leak, etc.), HttpOnly gives no protection — the server just sees a valid JWT and grants access.

⏱️ 4. Why short expiration matters

A short expiresIn (e.g. 15m) limits the damage window — a token stolen at 10:00 is dead by 10:15, regardless of who holds it.

🚪 5. Logout has limits

Logout only clears the cookie on the legitimate browser. A copy an attacker already made stays valid until it naturally expires.

🚫 Key takeaway
• Bearer token — "if you have it, you can use it." No extra proof of identity required.
• HttpOnly — stops JS from reading the token; doesn't stop a stolen token from being used.
That gap is what refresh-token rotation + reuse detection are designed to close.

HttpOnly Cookie vs Bearer Header

📌 Both are visible in the Network tab. HttpOnly blocks JS from reading the cookie — it does not hide traffic from DevTools. A developer inspecting Request Headers can see the full token either way.

Which one sends what

  • Cookie approach: never attach manually — use credentials: "include" and the browser handles it.
  • Bearer approach: manually grab and attach the token on every request: Authorization: Bearer <token>.

7. Extending Express's Request Type

The Declaration

★★★★★
types/express.d.ts
import "express";

declare global {
  namespace Express {
    interface Request {
      user: {
        userId: string;
      };
    }
  }
}

export {};

Why This File Is Needed

We added a custom user property to Express's req object. Express natively knows about:

req.body
req.params
req.query
req.headers

but not req.user.

Without this declaration

error
req.user.userId
// Error: Property 'user' does not exist on type 'Request'

With this declaration

ok
interface Request {
  user: {
    userId: string;
  };
}

// TypeScript now understands:
req.user.userId → string

Why declare global?

It tells TypeScript to extend the existing Express Request interface rather than create a new one:

Express Request
↓
body
params
query
headers
user ← your custom property
└── userId
