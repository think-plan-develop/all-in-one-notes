Q1. Input Validation
Zod Middleware
What it means:

Every request — body, params, query — must be validated at the route/middleware level before your controller or DB ever sees it. Use Zod (recommended with TypeScript) to define a schema and reject bad data immediately with a structured error response.

How the Flow Works

Request ↓ Zod Middleware ↓ ✅ Valid → Controller → Service → DB ❌ Invalid → 400 Bad Request (structured error returned)

Install

terminal
npm install zod

Define Schema + Infer Type

schemas/user.schema.ts
import { z } from 'zod';

export const createUserSchema = z.object({
  name:     z.string().min(2).max(50),
  email:    z.string().email(),
  age:      z.number().min(18).optional(),
  role:     z.enum(['admin', 'user']),
});

// Infer TypeScript type from schema — no duplication!
export type CreateUserInput = z.infer<typeof createUserSchema>;

Reusable Validate Middleware

middleware/validate.ts
import { Request, Response, NextFunction } from 'express';
import { ZodSchema } from 'zod';

export const validate =
  (schema: ZodSchema) =>
  (req: Request, res: Response, next: NextFunction) => {
    const result = schema.safeParse(req.body);

    if (!result.success) {
      const errors = result.error.errors.map(e => ({
        field:   e.path.join('.'),
        message: e.message,
      }));
      return res.status(400).json({ success: false, errors });
    }

    req.body = result.data;  // replace with parsed+typed data
    next();
  };

Use in Route

routes/user.route.ts
router.post('/users', validate(createUserSchema), createUser);
// If body is invalid → 400 auto. Never reaches createUser.

Key Points

  • →safeParse never throws — returns { success, data, error } safely
  • →Zod infers TypeScript types from the schema — write once, types are free
  • →Assigning req.body = result.data automatically strips unknown fields
💬 Interview Question

Q: Where should validation happen — middleware or controller?
A: Middleware. Controllers should only handle business logic. Validation is a cross-cutting concern — one reusable middleware handles it for all routes without any code repetition.

Q2. Schema-Level Validation (Mongoose)
Mongoose Last Safety Net
What it means:

Even after input validation, define constraints directly in your Mongoose schema. This is a backup layer — it catches invalid data that bypasses the API entirely, such as seeding scripts, admin tools, or internal service calls that write directly to the DB.

Two Layers of Protection

Layer 1 — Zod (API layer) Catches bad HTTP request input before it reaches your controller. Layer 2 — Mongoose Schema Catches bad data from ANY source — API, scripts, cron jobs, seeds.

Mongoose Schema with Validators

models/User.ts
import { Schema, model } from 'mongoose';

const userSchema = new Schema({

  name: {
    type:      String,
    required:  [true, 'Name is required'],
    trim:      true,
    minlength: [2,  'Min 2 characters'],
    maxlength: [50, 'Max 50 characters'],
  },

  email: {
    type:      String,
    required:  [true, 'Email is required'],
    unique:    true,   // DB index — NOT a validator
    lowercase: true,
    validate: {
      validator: (v: string) => /\S+@\S+\.\S+/.test(v),
      message:  'Invalid email format',
    },
  },

  role: {
    type:    String,
    enum:    { values: ['admin', 'user', 'guest'],
               message: '{VALUE} is not a valid role' },
    default: 'user',
  },

  age: {
    type: Number,
    min:  [18,  'Must be 18 or above'],
    max:  [100, 'Must be 100 or below'],
  },

}, { timestamps: true });

export const User = model('User', userSchema);

Catch Mongoose Validation Errors

middleware/errorHandler.ts
import { Error as MongooseError } from 'mongoose';

if (err instanceof MongooseError.ValidationError) {
  const errors = Object.values(err.errors).map(e => ({
    field:   e.path,
    message: e.message,
  }));
  return res.status(400).json({ success: false, errors });
}

Quick Comparison

Mongoose FeaturePurposeNote
requiredField must existUse array form for custom message
enumAllow only specific valuesObject form gives custom message
min / maxNumber or date rangeAlso array form for message
validateCustom validator functionCan be async
uniqueDB indexNOT a validator — handle E11000 separately
⚠️ Remember

unique: true in Mongoose creates a database index, not a Mongoose validator. It throws a duplicate key error (E11000), not a ValidationError. Always handle it separately in your global error middleware.
💬 Interview Question

Q: If you already validate with Zod, why add Mongoose validators?
A: Zod only protects the HTTP API layer. Data can enter the DB from seeding scripts, cron jobs, or internal services. Mongoose validators run on every .save() regardless of the source — they are the true last line of defense.

🟡 High Impact — Do These Next
Q3. DTO Pattern
TypeScript Zod
What it means:

A DTO (Data Transfer Object) is a plain typed object that defines the exact shape of data flowing between layers — request → controller → service → DB. In TypeScript, Zod's z.infer gives you DTOs for free with zero extra boilerplate.

Without DTO vs With DTO

Without DTOWith DTO
Every function accepts any or raw req.body. No type safety, no autocomplete. A typo silently passes through. Every layer knows the exact shape. TypeScript catches mismatches at compile time. Editor autocompletes every field.

Define DTOs from Zod Schemas

dtos/user.dto.ts
import { z } from 'zod';

// Schema = validation rules
export const createUserSchema = z.object({
  name:     z.string().min(2),
  email:    z.string().email(),
  password: z.string().min(8),
});

// DTO = inferred TypeScript type — zero duplication
export type CreateUserDTO = z.infer<typeof createUserSchema>;
// Result: { name: string; email: string; password: string }

// .partial() makes all fields optional — perfect for PATCH
export const updateUserSchema = createUserSchema.partial();
export type UpdateUserDTO   = z.infer<typeof updateUserSchema>;
// Result: { name?: string; email?: string; password?: string }

Use DTO in Service Layer

services/user.service.ts
import { CreateUserDTO } from '../dtos/user.dto';
import { User }          from '../models/User';

export const createUser = (dto: CreateUserDTO) => {
  // dto.name, dto.email — fully typed and autocompleted
  return User.create(dto);
};

Data Flow Across Layers

HTTP req.body (unknown / any) ↓ validate middleware → Zod parses and strips unknown fields CreateUserDTO (fully typed) ↓ Controller passes DTO to service createUser(dto: CreateUserDTO) ↓ Service passes to Mongoose User.create(dto) → MongoDB
💬 Interview Question

Q: What is a DTO and why use it over passing req.body directly?
A: A DTO is a typed contract for data moving between layers. Passing req.body directly spreads the any type everywhere — TypeScript cannot help you. DTOs give compile-time safety, autocomplete, and make refactoring safe across all layers.

Q4. Async Validation
Service Layer DB Checks
What it means:

Some validation requires hitting the database — "is this email already registered?", "does this product ID exist?". These checks cannot live in Zod (Zod handles shape/format). Async validation belongs in the service layer, expressed as reusable helper functions.

Pattern — Service-Level Async Check

services/user.service.ts
import { User }        from '../models/User';
import { CreateUserDTO } from '../dtos/user.dto';
import { AppError }     from '../utils/AppError';

export const createUser = async (dto: CreateUserDTO) => {

  // ✅ Async DB check — is email already taken?
  const existing = await User.findOne({ email: dto.email });
  if (existing)
    throw new AppError('Email already registered', 409);

  return User.create(dto);
};

Reusable Async Validators — Avoid Repetition

utils/dbValidators.ts
import { AppError } from './AppError';

// Generic "must exist" helper
export const mustExist = async (Model: any, id: string, label: string) => {
  const doc = await Model.findById(id);
  if (!doc) throw new AppError(`${label} not found`, 404);
  return doc;
};

// Generic "must be unique" helper
export const mustBeUnique = async (Model: any, filter: object, msg: string) => {
  const doc = await Model.findOne(filter);
  if (doc) throw new AppError(msg, 409);
};

// Usage anywhere in services:
await mustBeUnique(User,    { email }, 'Email already taken');
await mustExist   (Product, productId, 'Product');

Custom AppError Class

utils/AppError.ts
export class AppError extends Error {
  constructor(
    public message:    string,
    public statusCode: number = 400
  ) {
    super(message);
  }
}

Key Points

  • →Zod validates shape and format. Service layer validates business rules that need a DB query
  • →Extract common checks into reusable helpers — never repeat findOne in every service
  • →Always throw AppError with the correct HTTP status code and let the global error handler send the response
💬 Interview Question

Q: Can I do async validation inside Zod using .refine()?
A: Technically yes, but it is not recommended. Zod is for structure and format. Putting DB calls inside Zod middleware creates tight coupling and makes the logic hard to reuse. Async business-rule checks belong in the service layer.

Q5. Sanitization
NoSQL Injection Clean Data
What it means:

Sanitization is transforming incoming data — trimming whitespace, lowercasing emails, stripping unknown fields, removing $ operators that could be used in NoSQL injection attacks. Zod handles most of this automatically when you parse; pair it with express-mongo-sanitize for full protection.

Zod Transforms — Sanitize While You Validate

schemas/user.schema.ts
export const createUserSchema = z.object({

  name: z.string()
    .trim()             // "  John  "  →  "John"
    .min(2),

  email: z.string()
    .email()
    .toLowerCase(),     // "JOHN@GMAIL.COM"  →  "john@gmail.com"

  age: z.string()
    .transform(Number) // query param "25"  →  number 25
    .pipe(z.number().min(18)),

});

// Zod strips unknown fields by default on .parse()
// Extra fields in req.body are silently dropped — safe!

NoSQL Injection Prevention

app.ts
import mongoSanitize from 'express-mongo-sanitize';

// Removes keys starting with $ or containing a dot
// Prevents: { "email": { "$gt": "" } } attacks
app.use(mongoSanitize());

// npm install express-mongo-sanitize
// npm install -D @types/express-mongo-sanitize

What Each Tool Handles

💡 Key Insight

When you assign req.body = result.data after Zod parses, you have already sanitized. Zod only returns the fields you defined — all unknown fields are gone. Pair this with express-mongo-sanitize and you cover 95% of sanitization with almost no extra effort.
💬 Interview Question

Q: What is NoSQL injection and how do you prevent it in MongoDB?
A: An attacker sends { "email": { "$gt": "" } } in the request body. MongoDB treats $gt as a query operator and returns all users, bypassing authentication. Prevention: use express-mongo-sanitize to strip $-keyed fields, and use Zod to accept only the exact expected shape.
