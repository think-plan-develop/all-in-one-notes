🔐 Environment Variables Setup

.env Files — Dev vs Production

Why .env files? Never hardcode secrets (DB passwords, API keys, ports) in your code. Environment variables keep secrets out of Git and let you have different configs per environment.

Development — .env (local)

.env

PORT=3000
NODE_ENV=development

# MongoDB — local

# JWT

JWT_EXPIRES_IN=7d

# CORS
ALLOWED_ORIGIN=http://localhost:5173

Production — .env.production (server)

src/config/env.ts — Dynamic Loader

No fallback, no hardcoded ENV object. NODE_ENV must be explicitly set. If missing — crash immediately with a clear error. Works for any stage (dev, prod, test, staging...) without any code change.
src/config/env.ts
import dotenv from 'dotenv'
import path from 'path'

const NODE_ENV = process.env.NODE_ENV

if (!NODE_ENV) {
  throw new Error('NODE_ENV is not set. Please set it before starting the server.')
}

// development → .env
// production  → .env.production
// any new stage auto-resolves, no code change needed
const envFile = NODE_ENV === 'development'
  ? '.env'
  : `.env.${NODE_ENV}`

dotenv.config({ path: path.resolve(process.cwd(), envFile) })

console.log(`📦 Loaded: ${envFile}  (NODE_ENV=${NODE_ENV})`)
NODE_ENV = 'development' → loads .env NODE_ENV = 'production' → loads .env.production NODE_ENV = 'test' → loads .env.test NODE_ENV = 'staging' → loads .env.staging NODE_ENV = undefined → ❌ throws Error immediately — no silent fallback

Cross-Platform Scripts with cross-env

Why cross-env? NODE_ENV=development syntax works on Mac/Linux but breaks on Windows. cross-env sets environment variables in a cross-platform way — same script works everywhere.

🗄 Database Connection

src/config/db.ts — MongoDB Connection with Logging

What to log on connect? Log the DB host and DB name so you instantly know which database you're connected to — critical when switching between dev/staging/prod.
src/config/db.ts
import mongoose from 'mongoose'

export const connectDB = async (): Promise<void> => {
  try {
    const conn = await mongoose.connect(process.env.MONGO_URI as string)

    // ✅ Log host + DB name on successful connection
    console.log(`✅ MongoDB Connected`)
    console.log(`   Host : ${conn.connection.host}`)
    console.log(`   DB   : ${conn.connection.name}`)
    console.log(`   Port : ${conn.connection.port}`)

  } catch (err: any) {
    console.error(`❌ MongoDB Connection Failed: ${err.message}`)
    process.exit(1) // stop server if DB fails
  }
}
✅ What you see in terminal when server starts:
✅ MongoDB Connected
   Host : localhost
   DB : mydb
   Port : 27017
⚠️ process.exit(1) — if MongoDB fails to connect, crash the server immediately. Do NOT let it silently start without a DB — every request would fail anyway.
FieldMeaning
conn.connection.hostServer address — localhost in dev, Atlas cluster URL in prod
conn.connection.nameDatabase name — parsed from MONGO_URI, e.g. mydb

  email: string

  name:  { type: String, required: true },

Controller Layer

src/controllers/user.controller.ts
import { Request, Response } from 'express'
import { getAllUsers, createUser } from '../services/user.service'

export const fetchUsers = async (
  req: Request, res: Response
) => {
  const users = await getAllUsers()
  res.json(users)
}

export const addUser = async (
  req: Request, res: Response
) => {
  const user = await createUser(req.body)
  res.status(201).json(user)
}

⚡ Complete Request Lifecycle

GET /api/users — End to End Flow

Frontend / Postman ↓ GET /api/users Express Middleware (helmet, cors, morgan, json) ↓ Route → userRouter.get('/') ↓ Controller → fetchUsers(req, res) ↓ Service → getAllUsers() ↓ Model → User.find() ↓ Mongoose → builds MongoDB query ↓ MongoDB → returns documents ↓ (back up the chain) Service returns data to Controller ↓ Controller sends res.json(users) ↓ Frontend / Postman receives JSON ✅
✅ Key point: The controller never touches the DB directly. It always goes through Service → Model → Mongoose → MongoDB. This separation makes code testable and reusable.
🎯 Interview Questions & Answers
💬 Must-Know Questions
What is Mongoose and why use it over the native MongoDB driver?
Mongoose is an ODM (Object Document Mapper) — it sits between your Node.js code and MongoDB, adding a schema layer on top of the schema-less MongoDB. The native driver only gives raw queries, no validation, no structure. Mongoose adds schema definition, data validation, type casting, middleware (pre/post hooks), virtuals, and a clean query API like User.find().
Your Code ↓ Mongoose (schema, validation, hooks) ↓ MongoDB Driver ↓ MongoDB
Why do we call dotenv.config() before importing app.ts in server.ts?
Node.js loads and executes imports at the top of the file before any other code runs. If you import app.ts first and it references process.env.MONGO_URI, those values will be undefined because dotenv hasn't loaded yet.
Wrong order: import app ← app.ts runs, reads process.env → undefined ❌ dotenv.config() ← too late Correct order: dotenv.config() ← loads .env into process.env first ✅ import app ← now process.env values are available
Why separate app.ts and server.ts?
app.ts creates and configures the Express app (middleware, routes) but doesn't start listening. server.ts is the entry point — it connects the DB and starts the server. The reason to split is testing: in tests you can import app without starting the real server or connecting to the real DB, and just call supertest(app) directly.
app.ts → just Express config, no listen() call server.ts → connects DB + calls app.listen(PORT)
Why use a Service layer? Can't the Controller just query the DB directly?
Technically yes, but it's bad practice. The Service layer gives you: separation of concerns (Controller handles HTTP, Service handles business logic), reusability (multiple controllers or cron jobs can call the same service function), testability (unit test service functions without the HTTP layer), and maintainability (if a DB query changes, only the service changes, not every controller).
Controller → handles req/res only Service → handles DB queries + business logic Model → defines schema + provides DB methods
What does conn.connection.host and conn.connection.name give you?
After await mongoose.connect(uri), the returned conn object has a connection property describing the active DB connection. conn.connection.host is the server address, conn.connection.name is the database name parsed from the URI, and conn.connection.port is the port number. Logging these on startup lets you instantly verify which DB environment is connected — preventing accidental dev code running against a prod DB.
MONGO_URI = mongodb://localhost:27017/mydb ↑host ↑port ↑name conn.connection.host → localhost conn.connection.port → 27017 conn.connection.name → mydb

What do helmet and cors middleware actually do?
helmet() sets secure HTTP response headers automatically, protecting against XSS, clickjacking, and MIME sniffing — one line replaces around 11 manual header settings. cors() exists because browsers block cross-origin requests by default (e.g. React on port 5173 calling an API on port 3000); the middleware adds the Access-Control-Allow-Origin header so the browser allows it.
Without cors(): React → API ← browser blocks it ❌ With cors(): React → API ← allowed ✅
Why call process.exit(1) if MongoDB fails to connect?
If MongoDB fails to connect and the server starts anyway, every incoming request will fail with a DB error — the server runs but is completely broken, silently. process.exit(1) crashes the server immediately with a non-zero exit code, which tells a process manager (PM2, Docker, K8s) the app failed, triggers automatic restart logic, and makes the failure loud rather than silent.
DB connect fails ↓ process.exit(1) ← crash loudly ✅ ↓ PM2 / Docker sees exit code 1 ↓ Auto-restarts the process
What does tsc actually do?
tsc is the TypeScript Compiler. Node.js can only run .js files, not .ts, so running tsc compiles all TypeScript source into plain JavaScript inside the dist/ folder. In development, tsx does this on the fly with no build step; in production you pre-compile with tsc and run the output with node dist/server.js — faster and with zero TypeScript overhead at runtime.
Development: tsx watch src/server.ts ← compiles in memory, no dist/ Production: tsc ← writes dist/server.js to disk node dist/server.js ← runs pure JavaScript ✅
Why use path.resolve(__dirname, '../.env') in dotenv?
After tsc builds the project, the compiled code runs from dist/server.js, so __dirname points to /project/dist. But .env files live at /project/, one level up — ../ reaches the project root. Without this, dotenv looks in the wrong place, finds nothing, and every environment variable silently ends up undefined.
Running: node dist/server.js __dirname = /project/dist dotenv.config({ path: '.env' }) ← looks in /project/dist/.env ❌ dotenv.config({ path: '../.env' }) ← looks in /project/.env ✅ dotenv.config({ path: path.resolve(__dirname, '../.env') }) ← safest ✅
What is prestart and how does it differ from build?
"build": "tsc" must be run manually with npm run build. "prestart": "tsc" runs automatically every time npm start runs, because npm lifecycle hooks trigger pre<script> before <script>. So npm start compiles TypeScript first, then starts the server — you never need to remember to build manually before deploying.
"scripts": { "prestart": "tsc", ← runs automatically before start "start": "node dist/server.js", "dev": "tsx watch src/server.ts" } npm start → tsc runs first → node dist/server.js ✅ npm run dev → tsx watch (no build needed) ✅
Difference between dependencies and devDependencies?
dependencies are packages the app needs at runtime in production (express, mongoose, dotenv) — always installed. devDependencies (installed with -D) are only needed during development or build time (typescript, tsx, @types/*) and are skipped when deploying with npm ci --omit=dev, keeping a Docker image lean and reducing attack surface.
PackageTypeNeeded in prod?
express, mongoose, dotenvdependenciesYes
tsx, typescript, @types/*devDependenciesNo
Why process.exit(1) instead of just throwing an error?
In an async startup function, a thrown error can be silently swallowed if there's no outer try/catch wrapping the call. process.exit(1) guarantees the process terminates with exit code 1 — the universal signal for "something failed" — which Docker, PM2, Kubernetes, and systemd all watch to decide whether to restart and fire alerts.
throw new Error(...) ← may be swallowed silently in async context ❌ process.exit(1) ← guaranteed hard stop, exit code 1 seen by PM2/Docker ✅
What is maxPoolSize in mongoose.connect?
MongoDB uses a connection pool — a set of persistent connections reused across requests instead of opening and closing one per query. maxPoolSize: 10 means at most 10 simultaneous DB connections. For low-traffic apps the default (5) is fine; increase for high-traffic APIs, but stay under your MongoDB Atlas tier's connection limit (free tier allows 500 total connections).
db.ts
await mongoose.connect(MONGO_URI, {
  maxPoolSize: 10,                    // up to 10 concurrent DB connections
  serverSelectionTimeoutMS: 5000,     // fail fast if Atlas unreachable
  socketTimeoutMS: 45000              // close idle socket after 45s
})
findByIdAndUpdate vs updateOne — when to use which?
Use findByIdAndUpdate(id, data, { new: true }) when the REST API needs to return the updated resource to the client — { new: true } returns the document after the update, not before. Use updateOne({ _id: id }, data) when you only care whether the update succeeded (returns { matchedCount, modifiedCount }, not the document) — slightly faster since it skips fetching the full document.
MethodReturnsUse when
findByIdAndUpdate(..., { new: true })Updated documentREST API needs to return updated resource
updateOne(){ matchedCount, modifiedCount }Fire-and-forget update, no return needed
What is SIGTERM vs SIGINT and why handle them?
SIGINT is sent when you press Ctrl+C in the terminal, used during local development. SIGTERM is sent by Docker, Kubernetes, PM2, or systemd when they want to gracefully shut down your process, giving a short window (10–30s) to finish in-flight requests before a hard kill. Handling both ensures the HTTP server stops accepting new connections, active requests finish, and the MongoDB connection closes cleanly — no data corruption.
server.ts
process.on('SIGTERM', async () => {
  await mongoose.connection.close()   // close DB cleanly
  server.close(() => process.exit(0))  // stop HTTP server, exit 0 = success
})

process.on('SIGINT', async () => {
  await mongoose.connection.close()
  process.exit(0)
})
Why does morgan log only in development?
In production, logging every HTTP request to stdout is noisy, wastes resources, and can leak sensitive path/query information into logs. Production apps typically use dedicated log aggregators (Datadog, CloudWatch, Loki) with structured JSON logging instead of morgan's plain text output — keeping morgan dev-only keeps production logs clean and intentional.
app.ts
// only enable morgan in dev
if (process.env.NODE_ENV === 'development') {
  app.use(morgan('dev'))    // ← dev only ✅
}
// production: use a structured logger like winston or pino instead
morgan('dev') output looks like GET /api/users 200 5.234 ms — great for dev, too noisy for prod.

Why throw an error if NODE_ENV is not set instead of using a fallback?
A fallback like || 'development' silently loads the wrong config if someone forgets to set NODE_ENV — worst case, a developer runs the production server without setting it, and it silently loads dev config: no error, no warning, wrong DB, wrong secrets. Throwing forces whoever runs the app to be explicit; the crash is immediate, loud, and clear — far safer than a silent wrong config.
NODE_ENV = undefined With fallback → silently loads .env (dev config on prod server) ❌ With throw → ❌ Error: NODE_ENV is not set → fix it before proceeding ✅
How does the dynamic env loader know which file to load?
It uses a single ternary — development gets the plain .env file (no suffix), and every other value uses the template literal .env.${NODE_ENV}, which appends the stage name automatically. This means adding a new environment never requires a code change — just create the file and set NODE_ENV.
const envFile = NODE_ENV === 'development' ? '.env' : `.env.${NODE_ENV}` NODE_ENV = 'development' → '.env' NODE_ENV = 'production' → '.env.production' NODE_ENV = 'test' → '.env.test' NODE_ENV = 'staging' → '.env.staging' ← no code change needed ✅
Why is cross-env a devDependency and not a dependency?
cross-env is only used inside package.json scripts — a CLI tool that sets environment variables before running a command. It is never imported or required inside application code. In real deployments (Docker, Railway, AWS), NODE_ENV is set directly by the platform as a system environment variable, so cross-env has zero role at runtime.
WhereHow NODE_ENV is setcross-env needed?
Local dev (any OS)cross-env NODE_ENV=development in scriptYes
Docker / Railway / AWSPlatform injects it as system env varNo
What problem does cross-env solve? Why not just write NODE_ENV=production?
NODE_ENV=value command is Unix/bash syntax — it works on Mac and Linux but throws an error on Windows, since Windows CMD and PowerShell use completely different syntax to set environment variables. cross-env is a Node.js package that handles this difference: write the script once in Unix syntax and it translates it for Windows automatically.
Mac/Linux: NODE_ENV=production node dist/server.js ✅ works natively Windows CMD: NODE_ENV=production node dist/server.js ❌ 'NODE_ENV' is not recognized With cross-env (all platforms): cross-env NODE_ENV=production node dist/server.js ✅ works everywhere
💡 cross-env is a devDependency — only used in npm scripts, never imported in app code. Install with npm install -D cross-env.
