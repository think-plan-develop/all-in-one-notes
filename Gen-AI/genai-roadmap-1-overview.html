🎯 The Product You Are Building

A purchaser uploads transaction documents. The system extracts information, identifies possible inconsistencies and suggests next actions. A lawyer checks the evidence, edits or approves a clarification request, reviews the purchaser's response and records the resolution.

Demo scenarioThe demonstration should follow a concrete issue: the agreement says unit 12-04, while a supporting document says 12-40. The software displays both sources. The lawyer decides whether to raise a query. A corrected upload becomes a new version, and the lawyer reviews it before closing the issue.
📦 First-Release Scope
  • ✓One law firm, with purchaser and lawyer workflows. Seed users and assignments; a full administration console can follow later.
  • ✓Three synthetic document types: purchase agreement, property details sheet and purchaser information form.
  • ✓Readable PDF uploads, immutable versions and private downloads.
  • ✓Field extraction with evidence, human corrections and document consistency findings.
  • ✓Missing-document recommendations using a configured checklist.
  • ✓Editable suggested actions and clarification drafts approved by the lawyer.
  • ✓Purchaser responses, revised uploads and resolution tracking.
  • ✓Case questions with citations to eligible document versions and pages.
  • ✓A small approved-template library for clause comparison.
  • ✓Read-only AI tools for live case facts, a lawyer worklist, and purchaser guidance.
  • ✓Audit history, a basic review record export, evaluation results and an authenticated deployed demo.
Synthetic data onlyUse synthetic transactions and synthetic templates throughout. Required documents, deadlines and acceptable templates are configured demo rules; they do not assert a country's legal requirements.
🤝 Responsibilities
🤖

AI

Extract candidate information, summarize evidence, explain recorded findings, draft clarification text and answer supported questions.

🟢

Node.js business logic

Enforce authorization, validate inputs/outputs, calculate required-document gaps, determine allowed actions, compare corresponding fields and enforce state transitions.

⚖️

Lawyer

Verify fields and evidence, confirm or dismiss findings, approve outgoing requests, accept revisions and resolve issues.

Golden ruleA suggestion is a draft. It never becomes a sent request or review approval merely because the model generated it. A document's processing success is separate from the lawyer's acceptance.
🧰 Tools & Technical Scope
⚛️

Frontend

React + TypeScript; use familiar routing, forms and styling.

🟢

Backend

Node.js + Express + TypeScript.

🤖

AI calls

Vercel AI SDK with one supported model provider; keep provider credentials on the server. Choose one text model and one embedding model that meet the required capabilities.

✅

Validation

Zod for API requests, model output schemas and tool arguments.

🍃

Data and retrieval

MongoDB for application records and MongoDB Vector Search for document retrieval.

📄

Documents

One PDF text parser with page-level output; private local storage during development and private persistent storage for deployment.

⚙️

Background jobs

BullMQ + Redis; run the worker separately from the API.

🧪

Verification

Your familiar test runner for deterministic behavior, plus labeled fixtures and a small evaluation script for AI behavior.

🚀

Deployment

An environment that supports the web app, Node API, background worker, streaming and persistent private files. Verify service limits and costs before provisioning.

Not prerequisitesPython, fine-tuning and an orchestration framework are not prerequisites for this release. Learn the underlying model, retrieval and tool-call flows first.

🛟 If You Fall Behind

The core outcome is the complete review-and-resolution flow, including recommendations and approval. If a day overruns, use the catch-up time on Days 7, 14 and 21 and the Day 30 finishing buffer. Keep access control, evidence links, version handling and human approval in the first release.

If further scope reduction is needed, defer clause-library comparison, streaming polish and tool calling before weakening the core workflow. Keep their learning sessions as small isolated exercises and label them as not integrated.

After the 30-day release, extend based on measured failures:
