🔗 useCallback — Complete Guide

Memoizing function references in React — syntax, real-world e-commerce and search-form examples, and why it's not just useMemo in disguise.

useCallback Cart & Wishlist Search Handlers vs useMemo
🧩 useCallback at a Glance
🔗
Caches: The function reference itself, not a computed value.
🔁
Recreates: Only when one of its dependencies actually changes.
🧒
Pairs with: React.memo — otherwise the memoized function has no real effect.
🎯
Use when: Passing callbacks to memoized children or other hook deps.
🔗 useCallback
useCallback — Memoize Functions
useCallback returns the same function reference across re-renders, as long as its dependencies haven't changed. It doesn't run any calculation — it just remembers the function itself, so a child component receiving it as a prop doesn't see it as "new."
const memoizedFn = useCallback(() => { doSomething(a) }, [a]);
🛒 Real-World Example 1
Add to Cart / Wishlist (E-commerce)

📋 Scenario

Each product card renders a ❤️ Wishlist button and a 🛒 Add to Cart button. The parent list renders hundreds of ProductCard components, each wrapped in React.memo so they only re-render when their own props change.

ProductList.jsx 
<ProductCard
  product={product}
  onAddToCart={handleAddToCart}
  onWishlist={handleWishlist}
/>

❌ Without useCallback

ProductList.jsx 
const handleAddToCart = (id) => {
  dispatch(addToCart(id));
};

// Every render creates a brand-new function reference.
// Every memoized ProductCard re-renders, even ones untouched.

✅ With useCallback

ProductList.jsx 
const handleAddToCart = useCallback((id) => {
  dispatch(addToCart(id));
}, [dispatch]);

const handleWishlist = useCallback((id) => {
  dispatch(toggleWishlist(id));
}, [dispatch]);
💡 Interview Answer: I used useCallback for Add to Cart and Wishlist handlers because they were passed to memoized ProductCard components. This prevented unnecessary re-renders of every card on the page whenever the parent re-rendered.
🔍 Real-World Example 2
Form / Search Handlers

📋 Scenario

A search page has a memoized SearchBar component and a memoized FilterPanel component. Both receive an onChange-style handler as a prop. The parent also holds unrelated state (like a "results view: grid/list" toggle) that re-renders the parent often.

❌ Without useCallback

SearchPage.jsx 
const handleSearchChange = (value) => {
  setQuery(value);
  fetchResults(value, filters);
};

// New function every render → memoized SearchBar re-renders
// even when only "view: grid/list" toggled

✅ With useCallback

SearchPage.jsx 
import { useState, useCallback, memo } from 'react';

const SearchBar = memo(({ onSearchChange }) => {
  console.log('SearchBar rendered');
  return <input onChange={e => onSearchChange(e.target.value)} />;
});

const FilterPanel = memo(({ onFilterChange }) => {
  console.log('FilterPanel rendered');
  return <select onChange={e => onFilterChange(e.target.value)}>...</select>;
});

function SearchPage() {
  const [query, setQuery] = useState('');
  const [filters, setFilters] = useState({});
  const [view, setView] = useState('grid'); // unrelated UI state

  // ✅ Stable references — SearchBar / FilterPanel skip re-render
  // when only "view" changes
  const handleSearchChange = useCallback((value) => {
    setQuery(value);
  }, []);

  const handleFilterChange = useCallback((value) => {
    setFilters(prev => ({ ...prev, category: value }));
  }, []);

  return (
    <div>
      <SearchBar onSearchChange={handleSearchChange} />
      <FilterPanel onFilterChange={handleFilterChange} />
      <button onClick={() => setView(v => v === 'grid' ? 'list' : 'grid')}>
        Toggle View
      </button>
    </div>
  );
}
💡 Interview Answer: I wrapped the search and filter handlers in useCallback so that toggling an unrelated "view" state didn't force the memoized SearchBar and FilterPanel to re-render on every keystroke elsewhere on the page.
⚖️ useCallback vs useMemo
Why not just use useMemo instead?

What "memoize" means here: React normally throws away everything from a render and rebuilds it from scratch on the next render — including function definitions, which are just objects in JS. Memoizing means "keep the old one in a cache and hand back that same object again, instead of building a new one" — as long as the listed dependencies haven't changed.

💡 useMemo memoizes a VALUE. useCallback memoizes a FUNCTION.

HookCachesRuns on every render?
useMemo(fn, deps)The return value of fn()Calls fn() to get the value, then caches it
useCallback(fn, deps)The function fn itselfNever calls fn — just hands back the same reference

You could technically reproduce useCallback with useMemo:

equivalent.js 
// These two lines do the exact same thing:
const handleClick = useCallback(() => doSomething(a), [a]);
const handleClick = useMemo(() => () => doSomething(a), [a]);

So useCallback isn't doing anything useMemo can't do under the hood — it's really just useMemo with the "return a function" step baked in. That's why it's preferred over useMemo for functions, not because it's more powerful, but because it's clearer:

✅ useCallback(fn, deps)
  • Reads as "keep this function stable"
  • No extra arrow-function wrapper to write
  • Matches how ESLint's exhaustive-deps rule expects it
⚠️ useMemo(() => fn, deps)
  • Extra nested function is easy to misread
  • Easy to forget the outer () => and accidentally memoize the call result instead of the function
  • No real benefit gained for the extra syntax
⚠️ Why useMemo alone "can't" replace useCallback in practice: useMemo's whole job is to run a calculation and cache the result. If you pass it a function directly, like useMemo(() => doSomething(a), [a]), it CALLS that function immediately and caches whatever it returns — not the function. You'd be memoizing the wrong thing (a stale computed value) instead of a stable callback. useCallback exists specifically to skip that "call it now" step.
📝 Bottom line: Reach for useCallback when you're memoizing a function (usually one passed to a memoized child, or used as a dependency elsewhere, like inside another useEffect/useMemo). Reach for useMemo when you're memoizing the result of a computation (a filtered array, a total, a derived object). Same underlying mechanism, different job.
