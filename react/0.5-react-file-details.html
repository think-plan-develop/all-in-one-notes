📜 Scripts Overview

The scripts section defines reusable commands that you can run using npm run <script-name>.

package.json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "lint": "eslint .",
    "test": "vitest",
    "coverage": "vitest run --coverage"
  }
}
ScriptCommandPurpose
devnpm run devStarts the Vite development server with Hot Module Replacement (HMR).
buildnpm run buildCreates an optimized production build inside the dist folder.
previewnpm run previewRuns a local server to preview the production build before deployment.
lintnpm run lintChecks the project for code quality issues using ESLint.
testnpm run testStarts the Vitest test runner in watch mode.
coveragenpm run coverageRuns all tests once and generates a code coverage report.
vite.config.js
⚙️ Configuration File
vite.config.js
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import path from "path";

export default defineConfig({
  plugins: [react()],

  resolve: {
    alias: {
      "@": path.resolve(__dirname, "./src"),
    },
  },

  server: {
    port: 3000,
    open: true,
    host: true,

    proxy: {
      "/api": {
        target: "http://localhost:5000",
        changeOrigin: true,
        secure: false,
      },
    },
  },

  build: {
    outDir: "dist",
    sourcemap: true,
    minify: true,
  },
});
🔍 vite.config.js Explained Click to expand

1. defineConfig()

vite.config.js
export default defineConfig({
  ...
});

Provides IntelliSense and type hints, validates configuration, and makes it easier to read and maintain.

2. Plugins

vite.config.js
plugins: [react()]

Adds React support to Vite — JSX support, Fast Refresh (HMR), React optimization, and a better dev experience.

⚠️ Without this plugin, Vite cannot understand React JSX.

3. Resolve (Alias)

vite.config.js
resolve: {
  alias: {
    "@": path.resolve(__dirname, "./src"),
  },
}

Instead of ../../../components/Button, you can write @/components/Button.

✅ Benefits
  • Cleaner imports
  • Easier refactoring
  • No long relative paths

4. Development Server

vite.config.js
server: {
  port: 3000,
  open: true,
  host: true,
}

port: Runs on http://localhost:3000 instead of the default 5173.
open: Automatically opens the browser after starting the server.
host: Allows access from other devices on the same network — useful for testing responsive apps.

5. Proxy

vite.config.js
proxy: {
  "/api": {
    target: "http://localhost:5000",
    changeOrigin: true,
    secure: false,
  },
},

Instead of the full backend URL, call fetch("/api/users") and Vite forwards it to http://localhost:5000/api/users.

✅ Benefits
  • Avoids CORS issues during development
  • Keeps API URLs clean
  • Easy to switch environments

6. Build

vite.config.js
build: {
  outDir: "dist",
  sourcemap: true,
  minify: true,
}

outDir: Production files go into the dist/ folder.
sourcemap: Generates source maps for debugging production code.
minify: Removes spaces, comments, and unused code to reduce bundle size.

Why doesn't Vite use only Babel?
⚡ Babel vs esbuild

Both Babel and esbuild can transform modern JavaScript and JSX into browser-compatible JavaScript. However, Vite chooses esbuild as its primary transformer because it is significantly faster.

🚀 Why Is esbuild Faster?

1. Written in Go (Compiled Language)

Babel:

babel-flow
Source Code
     │
JavaScript Engine (Node.js)
     │
Execute Babel
     │
Transform Code

Since Babel itself is written in JavaScript, it must run inside the Node.js runtime, which adds interpretation overhead.

esbuild:

esbuild-flow
Source Code
      │
Compiled Go Binary
      │
Direct Native Execution
      │
Transform Code

Go is a compiled language. esbuild runs as a native executable, so there is no JavaScript runtime overhead.

✅ Result: Faster execution.

2. Parallel Processing

Babel:

babel-processing
File 1
   │
File 2
   │
File 3
   │
File 4

Mostly processes files sequentially.

esbuild:

esbuild-processing
        CPU Cores

Core 1   File 1
Core 2   File 2
Core 3   File 3
Core 4   File 4

esbuild processes multiple files simultaneously by utilizing all available CPU cores.

✅ Result: Better performance on modern multi-core processors.
💬 Interview Q&A

Q. Why is esbuild faster than Babel?

1. esbuild is written in Go, a compiled language, while Babel is written in JavaScript and runs on Node.js.
2. esbuild uses parallel processing, utilizing multiple CPU cores to process many files simultaneously.
3. esbuild has a lightweight architecture focused on speed with fewer transformation passes.
4. Babel prioritizes flexibility and plugins, while esbuild prioritizes performance.
5. That's why Vite uses esbuild for fast development and Babel only when React-specific or custom transformations are needed.

🐢 Babel
  • JavaScript
  • Flexible
  • Plugin Rich
  • Slower
⚡ esbuild
  • Go
  • Parallel Processing
  • Native Binary
  • Lightweight
  • Extremely Fast
🎯 Key Takeaway: Vite doesn't replace Babel entirely — it uses the right tool for the right job: esbuild for speed, Babel for specialized React and custom transformations, and Rollup for production bundling.
main.jsx
🚪 Application Entry Point
main.jsx
import React from "react";
import ReactDOM from "react-dom/client";
import App from "./App";
import "./index.css";

ReactDOM.createRoot(document.getElementById("root")).render(
  <App />
);
🔄 How React Starts the Application

Step 1 — Browser loads index.html

At this point the page only contains an empty <div id="root"></div> — nothing else is rendered yet.

Step 2 — Browser executes main.jsx

document.getElementById("root") is plain JavaScript DOM API. It searches the HTML document and returns the root div, so React now knows where it should render the application.

Step 3 — createRoot()

createRoot() creates a React Root — a controller between React and the browser DOM. It keeps track of the component tree, detects changes, and uses the Virtual DOM to efficiently update only the affected DOM nodes.

ℹ️ React 18: createRoot() enables the new concurrent rendering features and replaces the older ReactDOM.render() API.

Step 4 — .render(<App />)

This tells React to render the App component inside the React Root. React starts with App, then renders all child components recursively (Navbar, Sidebar, Dashboard → Card, Chart, Table, and Footer).

🌳 Why Is There Only One id="root"?

Single Root Application Pattern

React follows the Single Root Application pattern — everything is rendered inside one container: index.html's <div id="root"></div>, which then holds App with all its nested children (Navbar, Dashboard, Footer, etc).

Why only one?

A single React Root simplifies rendering and state management. React owns everything inside that container and can efficiently compare the Virtual DOM with the Real DOM, updating only what changed. This is why React applications are often called Single Page Applications (SPAs).

Can React have multiple roots?

Yes. While uncommon for modern SPAs, you can mount multiple independent React applications on the same page, each managing its own independent component tree and state. This is often used when gradually adding React to an existing server-rendered website.

main.jsx
ReactDOM.createRoot(document.getElementById("header")).render(<Header />);
ReactDOM.createRoot(document.getElementById("sidebar")).render(<Sidebar />);
ReactDOM.createRoot(document.getElementById("footer")).render(<Footer />);

🎯 Interview Tip: "Why does React use a single root element?" — React doesn't require only one root, but a single root is the standard architecture for SPAs because it gives React complete control over one section of the page, making rendering, reconciliation, routing, and state management simpler and more efficient. Multiple roots are supported but mainly used when integrating React into existing applications rather than building a full React SPA.
