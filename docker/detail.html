1. Docker Fundamentals
1.1

What is Docker?

Docker is a platform for packaging an application together with everything it needs to run into a container.

Without Docker:

Your Node.js App ↓ Node.js version ↓ npm packages ↓ OS libraries ↓ Server configuration

You can have problems such as:

"It works on my machine!"

For example:

Your machine:

Node 18 PostgreSQL 16 Redis 7 Ubuntu

Another developer:

Node 20 PostgreSQL 15 Windows

The application may behave differently.

With Docker:

┌───────────────────────────────┐ │ Container │ │ │ │ Node.js │ │ Application │ │ npm dependencies │ │ Required OS libraries │ │ │ └───────────────────────────────┘

The container provides a consistent runtime environment.

1.2

Docker vs Virtual Machine

This is one of the most important concepts.

Virtual Machine

Physical Server │ ├── Host OS │ ├── VM 1 │ ├── Guest OS │ └── Application │ ├── VM 2 │ ├── Guest OS │ └── Application │ └── VM 3 ├── Guest OS └── Application

Every VM has its own operating system.

Therefore VMs are generally:

  • heavier
  • slower to start
  • larger

Docker

Physical Server │ ├── Host OS │ ├── Docker Engine │ ├── Container 1 │ └── Node Application │ ├── Container 2 │ └── PostgreSQL │ └── Container 3 └── Redis

Containers share the host kernel instead of running a complete guest OS.

Important distinction

Docker containers are isolated processes, not miniature VMs.

1.3

Docker Architecture

The basic architecture is:

Docker Registry (Docker Hub/ECR) ↑ │ pull/push │ ┌──────────────┐ │ │ Docker CLI │─────┤ │ │ │ │ docker run │ │ │ docker build │ │ │ docker pull │ │ └──────┬───────┘ │ │ API/socket ↓ ┌──────────────────┐ │ Docker Daemon │ │ dockerd │ │ │ │ containers │ │ images │ │ networks │ │ volumes │ └──────────────────┘

When you run:

bash
docker run nginx

the CLI communicates with Docker Engine/daemon, which handles the actual container creation and execution.

1.4

Docker Engine

Docker Engine is the runtime system responsible for managing containers.

Conceptually:

Docker Engine │ ├── dockerd │ ├── containerd │ └── runc

dockerd

Docker daemon.

Responsible for things like:

Images Containers Networks Volumes API

containerd

Responsible for container lifecycle/runtime management.

runc

Low-level container runtime.

It actually creates and starts the container using Linux kernel features.

You don't normally interact with containerd or runc directly as a beginner.

1.5

Docker CLI

You interact with Docker primarily through the CLI.

Examples:

bash
docker run nginx
docker ps
docker images
docker build -t myapp .
docker pull nginx
docker push myimage
docker stop mycontainer
1.6

Image vs Container

This distinction must be crystal clear.

Image

An image is a read-only template.

Example:

node:18-alpine

contains the environment needed to run Node.

Container

A container is a running/created instance of an image.

Image │ ├── Container 1 ├── Container 2 └── Container 3

You can create multiple containers from one image.

For example:

bash
docker run --name api1 node:18-alpine
docker run --name api2 node:18-alpine
docker run --name api3 node:18-alpine

All three use the same image.

1.7

Docker Hub / Registry

A registry stores Docker images.

For example:

Docker Hub │ ├── nginx ├── node ├── postgres └── redis

When you run:

bash
docker pull nginx

Docker downloads the image from a registry.

In AWS, you can use:

Amazon ECR

Typical production flow:

Developer
↓
docker build
↓
Docker Image
↓
Amazon ECR
↓
ECS
↓
Container

This is directly related to the AWS/ECS work you've been doing.

1.8

Basic Practice

Run:

bash
docker run hello-world

Then:

bash
docker ps

You probably won't see hello-world because it exits.

So:

bash
docker ps -a

Now you'll see it.

Then:

bash
docker run -d --name nginx-demo -p 8080:80 nginx

Check:

bash
docker ps

Open:

localhost:8080

You are now running an Nginx container.

2. Docker Images

Now we move deeper into images.

Now we move deeper into images.

2.1

Image Layers

Docker images are composed of layers.

Suppose your Dockerfile is:

Dockerfile
FROM node:18-alpine

WORKDIR /app

COPY package*.json ./

RUN npm install

COPY . .

CMD ["node", "server.js"]

Conceptually:

┌─────────────────────────────┐ │ CMD │ ├─────────────────────────────┤ │ COPY . . │ ├─────────────────────────────┤ │ RUN npm install │ ├─────────────────────────────┤ │ COPY package*.json │ ├─────────────────────────────┤ │ WORKDIR │ ├─────────────────────────────┤ │ node:18-alpine │ └─────────────────────────────┘

Docker can reuse unchanged layers.

This is why Docker builds can become very fast after the first build.

2.2

Why Layer Ordering Matters

Consider:

Dockerfile · inefficient
COPY . .

RUN npm install

Every time you change one source file:

COPY . . ↓ changed ↓ npm install runs again

That's inefficient.

Instead:

Dockerfile · better
COPY package*.json ./

RUN npm install

COPY . .

Now:

package.json unchanged ↓ npm install cached ↓ COPY source code

If you only change:

server.js

Docker can reuse the npm installation layer.

This is a major production optimization.

2.3

Tags

An image normally looks like:

repository:tag

Example:

node:18-alpine

Here:

node → repository 18-alpine → tag

Another example:

myapp:1.0.0

For production, prefer meaningful immutable versioning:

myapp:1.0.0 myapp:1.0.1 myapp:git-a83f21

Don't rely on:

myapp:latest

because latest doesn't necessarily mean "newest production version."

2.4

Build Context

When you execute:

bash
docker build -t myapp .

the final . means:

Current directory

Docker sends that directory as the build context.

If your directory contains:

project/ ├── node_modules/ ├── .git/ ├── .env ├── src/ ├── package.json └── Dockerfile

you don't want to unnecessarily send everything.

That's why .dockerignore is important.

2.5

Image Management

List images:

bash
docker images

Remove an image:

bash
docker rmi myapp

Inspect:

bash
docker inspect myapp

See image history:

bash
docker history myapp

Clean unused Docker resources:

bash
docker system prune

Be careful with prune commands on machines containing important Docker resources.

3. Docker Containers

From the image to the actual running application

Now we move from the image to the actual running application.

3.1

Container Lifecycle

The lifecycle can be understood as:

create
↓
start
↓
running
↓
stop
↓
start
↓
remove

There are also:

pause unpause restart

Example:

bash
docker create --name myapp nginx

Then:

bash
docker start myapp

Or simply:

bash
docker run --name myapp nginx

docker run essentially creates and starts the container.

3.2

Port Mapping

Suppose your Node application listens on:

3000

inside the container.

You run:

bash
docker run -p 8080:3000 myapp

This means:

Host Container 8080 → 3000

So:

Browser
↓
localhost:8080
↓
Docker
↓
container:3000
↓
Node.js

Important

EXPOSE 3000 does not publish the port.

This:

Dockerfile
EXPOSE 3000

is primarily documentation/metadata.

This:

bash
-p 8080:3000

actually publishes/maps the port.

3.3

Environment Variables

You shouldn't hardcode configuration like:

javascript
const dbPassword = "secret123";

Instead:

javascript
process.env.DB_PASSWORD

Run:

bash
docker run \
  -e NODE_ENV=production \
  -e PORT=3000 \
  myapp

Or:

bash
docker run --env-file .env myapp

For production, don't put secrets into the Docker image.

In AWS, you'd generally inject secrets/configuration through services such as:

AWS Secrets Manager AWS Systems Manager Parameter Store ECS task configuration

rather than baking them into the image.

3.4

Docker Logs

If your Node application does:

javascript
console.log("Server started");

Docker captures stdout/stderr.

You can see it with:

bash
docker logs myapp

Follow logs:

bash
docker logs -f myapp

This is important because production containers should generally write application logs to:

stdout stderr

rather than depending on files inside the container.

For your Pino + ECS setup, the flow is roughly:

Node.js
↓
Pino
↓
stdout
↓
Docker
↓
ECS
↓
CloudWatch Logs
3.5

docker exec

Suppose a container is running.

You can enter it:

bash
docker exec -it myapp sh

Now you're inside the container.

You might run:

bash
ls
env
pwd
cat package.json

This is extremely useful for debugging.

3.6

Container Resource Usage

Run:

bash
docker stats

You'll see things such as:

CPU Memory Network Block I/O

For example:

CONTAINER CPU MEM api 2.5% 120MB postgres 4.1% 300MB redis 0.5% 20MB
4. Dockerfile

How your image should be built

The Dockerfile describes how your image should be built.

For a Node.js application:

Dockerfile
FROM node:18-alpine

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 3000

CMD ["node", "server.js"]

Let's understand every instruction.

4.1

FROM

Dockerfile
FROM node:18-alpine

This defines the base image.

You could use:

node:18 node:18-alpine node:22-alpine

For production, select deliberately based on compatibility, security and support requirements rather than blindly using latest.

4.2

WORKDIR

Dockerfile
WORKDIR /app

Now subsequent commands operate from:

/app

Instead of:

bash
cd /app

you use:

Dockerfile
WORKDIR /app
4.3

COPY

Dockerfile
COPY package*.json ./

Copies files from the build context into the image.

Then:

Dockerfile
COPY . .

copies the application source.

Usually prefer COPY.

4.4

RUN

Dockerfile
RUN npm ci

This happens during image building.

For example:

bash
docker build -t myapp .

Docker executes:

npm ci

while building the image.

It does NOT execute every time the container starts.

4.5

ENV

Example:

Dockerfile
ENV NODE_ENV=production

This creates an environment variable inside the image/container.

But don't use Dockerfile ENV for sensitive secrets.

Bad:

Dockerfile · don't
ENV DB_PASSWORD=mySecretPassword

The secret becomes part of the image configuration/history.

4.6

EXPOSE

Dockerfile
EXPOSE 3000

This tells users/tools:

This application expects to listen on 3000.

It doesn't make the application accessible from your host.

You still need:

bash
docker run -p 3000:3000 myapp
4.7

CMD

Dockerfile
CMD ["node", "server.js"]

This is the default command when the container starts.

You can override it:

bash
docker run myapp node another.js
4.8

ENTRYPOINT

Example:

Dockerfile
ENTRYPOINT ["node"]

Then:

Dockerfile
CMD ["server.js"]

Conceptually:

ENTRYPOINT → executable CMD → default arguments

Result:

bash
node server.js

For normal Node applications, CMD alone is often sufficient.

4.9

.dockerignore

Create:

.dockerignore

Example:

.dockerignore
node_modules
.git
.env
npm-debug.log
Dockerfile*
.dockerignore

Why?

Because you don't want:

node_modules .git .env

unnecessarily included in your build context.

Especially:

.env

because it may contain secrets.

4.10

Production Node Dockerfile

A better production-oriented example:

Dockerfile
FROM node:18-alpine

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY . .

USER node

EXPOSE 3000

CMD ["node", "server.js"]

Notice:

Dockerfile
npm ci --omit=dev

Only production dependencies.

And:

Dockerfile
USER node

The application doesn't run as root.

That is a useful production security practice.

4.11

Multi-stage Builds

Multi-stage builds allow you to separate:

Build environment

from:

Runtime environment

Example:

Dockerfile
FROM node:18-alpine AS builder

WORKDIR /app

COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build


FROM node:18-alpine

WORKDIR /app

COPY --from=builder /app/dist ./dist

CMD ["node", "dist/server.js"]

Conceptually:

Builder image
↓
compile/build
↓
dist
↓
Runtime image
↓
only what is needed

This can significantly reduce production image size and attack surface.

5. Docker Networking

When services run as separate containers

This becomes very important when you have:

Node API PostgreSQL Redis Nginx

running as separate containers.

5.1

Default Bridge Network

Docker has a default bridge network.

But for application stacks, you generally want a user-defined network.

Create:

bash
docker network create app-network

Now:

app-network │ ├── api ├── postgres └── redis
5.2

Container-to-Container Communication

Suppose:

API container Postgres container

are on:

app-network

Run:

bash
docker run -d \
  --name postgres \
  --network app-network \
  postgres

Then your API can connect using:

postgres:5432

NOT:

localhost:5432

This is a very important Docker concept.

Inside the API container:

localhost

means:

API container itself

It does not mean your Postgres container.

5.3

Docker DNS

Docker provides DNS resolution on user-defined networks.

For example:

api postgres redis

Docker resolves:

postgres

to the Postgres container's internal IP.

Therefore:

env
DATABASE_HOST=postgres
REDIS_HOST=redis

instead of:

env
DATABASE_HOST=localhost
REDIS_HOST=localhost
5.4

Port Mapping vs Internal Networking

Suppose Postgres:

Container port: 5432

Your API doesn't necessarily need:

bash
-p 5432:5432

if both are on the same Docker network.

They can communicate internally:

API ↓ postgres:5432 ↓ Postgres

You only publish a port to the host when external access is required.

For example:

Browser ↓ localhost:8080 ↓ API container:3000
5.5

Network Isolation

You can create:

frontend-network backend-network

For example:

frontend │ frontend-network │ API │ backend-network ┌────┴────┐ ↓ ↓ Postgres Redis

This allows you to control which services can communicate.

A database shouldn't normally be directly exposed to the public internet.

5.6

Host Network

With:

bash
--network host

the container uses the host's network namespace.

Conceptually:

Host │ └── Container shares host networking

It's useful in specific scenarios, but for normal application deployments, bridge/user-defined networks are more common.

6. Docker Storage

Containers are disposable

Containers are designed to be disposable.

Suppose:

Postgres container ↓ container deleted ↓ data disappears

Unless you persist the data.

That's where volumes come in.

6.1

Docker Volume

Create:

bash
docker volume create postgres-data

Run:

bash
docker run -d \
  --name postgres \
  -v postgres-data:/var/lib/postgresql/data \
  postgres

Now:

Postgres ↓ /var/lib/postgresql/data ↓ Docker Volume ↓ postgres-data

If you remove the container:

bash
docker rm postgres

the volume remains.

Create another container:

bash
docker run -d \
  --name postgres-new \
  -v postgres-data:/var/lib/postgresql/data \
  postgres

The data remains.

6.2

Bind Mount

Instead of a Docker-managed volume:

bash
-v ./data:/app/data

This maps a host directory:

Host ./data ↓ Container /app/data

Very useful during development.

For example:

Host source code ↓ container /app

You can modify code on your machine and have the container see those changes.

6.3

Volume vs Bind Mount

Volume

Docker manages storage

Good for:

Postgres Redis persistence production-style persistent application data

Bind mount

You control the host path

Good for:

local development configuration live code
6.4

tmpfs

tmpfs stores data in memory.

Example:

bash
docker run --tmpfs /tmp myapp

Data is temporary.

Conceptually:

Container ↓ RAM ↓ container stops ↓ data gone

Useful for temporary data where persistence isn't required.

7. Docker Compose

Describe the entire stack in YAML

Until now, imagine starting this manually:

bash
docker network create backend

docker run postgres ...

docker run redis ...

docker run api ...

That's annoying.

Compose lets you describe the entire stack in YAML.

7.1

Example Architecture

Suppose you have:

Client ↓ API :3000 / \ ↓ ↓ PostgreSQL Redis

Compose can define all three.

Example:

docker-compose.yml
services:

  api:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://postgres:password@postgres:5432/appdb
      REDIS_HOST: redis
    depends_on:
      - postgres
      - redis

  postgres:
    image: postgres:16
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: password
      POSTGRES_DB: appdb
    volumes:
      - postgres-data:/var/lib/postgresql/data

  redis:
    image: redis:7

volumes:
  postgres-data:

Then:

bash
docker compose up

Compose creates:

Network │ ├── api ├── postgres └── redis Volume │ └── postgres-data
7.2

Services

Each service represents a container definition.

yaml
services:
  api:
  postgres:
  redis:

You can think:

api → Node container postgres → PostgreSQL container redis → Redis container
7.3

build

yaml
api:
  build: .

Means:

Use Dockerfile in current directory

Compose builds the image.

7.4

image

yaml
postgres:
  image: postgres:16

Instead of building your own image, Compose pulls an existing image.

7.5

Ports

yaml
ports:
  - "3000:3000"

Same concept as:

bash
docker run -p 3000:3000
7.6

Environment

You can do:

yaml
environment:
  NODE_ENV: development
  PORT: 3000

Or:

yaml
env_file:
  - .env

Example:

.env
env
DATABASE_URL=...
REDIS_HOST=redis

Don't commit real secrets to Git.

For production, use a proper secret-management mechanism rather than treating .env as your production secret store.

7.7

depends_on

Example:

yaml
api:
  depends_on:
    - postgres
    - redis

This tells Compose to start dependencies before the API.

But there is an important problem.

It doesn't necessarily mean:

Postgres is ready to accept connections

It primarily controls startup ordering.

7.8

Healthchecks

You can define:

yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U postgres"]
  interval: 10s
  timeout: 5s
  retries: 5

Now Docker can determine whether Postgres is healthy.

Then you can use:

yaml
depends_on:
  postgres:
    condition: service_healthy

Conceptually:

Start Postgres ↓ Healthcheck ↓ Healthy? / \ No Yes | | wait API starts

This is much better than assuming that "container started" means "application ready."

7.9

Compose Commands You Should Know

Start:

bash
docker compose up

Start in background:

bash
docker compose up -d

Build:

bash
docker compose build

Build + start:

bash
docker compose up --build

See containers:

bash
docker compose ps

See logs:

bash
docker compose logs

Follow API logs:

bash
docker compose logs -f api

Stop/remove stack:

bash
docker compose down

Remove stack and its named volumes:

bash
docker compose down -v

Be careful with -v because it removes the Compose-managed volumes and therefore persistent database data stored there.

How Sections 1–7 Connect

The most important mental model

This is the most important mental model.

Suppose you build a Node.js API.

Step 1 — Write application

Node.js Express PostgreSQL Redis

Step 2 — Dockerfile

You describe how to package the API:

Dockerfile ↓ docker build ↓ Docker Image

Step 3 — Run container

Docker Image ↓ Container

Step 4 — Networking

API Container │ ├──── postgres:5432 │ └──── redis:6379

Step 5 — Storage

Postgres Container ↓ Docker Volume ↓ Persistent database data

Step 6 — Compose

Instead of manually managing everything:

docker run API docker run Postgres docker run Redis

you define:

docker-compose.yml

and run:

bash
docker compose up

Complete Development Architecture

After these seven sections, you should be able to understand this:

Developer │ ↓ Dockerfile │ ↓ docker build │ ↓ Docker Image │ ↓ ┌─────────────────┐ │ Docker Network │ │ │ │ ┌───────────┐ │ │ │ Node API │ │ │ │ :3000 │ │ │ └─────┬─────┘ │ │ │ │ │ ┌───┴───┐ │ │ ↓ ↓ │ │ Postgres Redis │ │ :5432 :6379 │ └─────────────────┘ │ ↓ Docker Volume │ ↓ Persistent Data

And Compose manages the whole thing:

docker-compose.yml │ ├── API ├── PostgreSQL ├── Redis ├── Network └── Volumes

What you should be able to do after Sections 1–7

You should be comfortable with:

bash
docker pull
docker build
docker run
docker ps
docker exec
docker logs
docker stop
docker start
docker rm
docker images
docker rmi
docker network
docker volume
docker compose

And, more importantly, understand:

Dockerfile ↓ Image ↓ Container ↓ Network ↓ Other containers Volume ↓ Persistent data Compose ↓ Manages the entire application stack
