1. Docker Images & Containers

Image Layers & Caching

★★★★★

Docker images are composed of layers — each instruction in a Dockerfile produces one. Docker can reuse unchanged layers on rebuild, which is why builds get fast after the first one.

Dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
CMD ["node", "server.js"]

❌ Inefficient ordering

COPY . . before RUN npm install — any source file change invalidates the cache and reinstalls all dependencies.

✅ Better ordering

Copy package*.json first, run install, then copy source. Changing server.js alone reuses the cached install layer.

Tags & Build Context

An image name is repository:tag, e.g. node:18-alpine (repository node, tag 18-alpine). For production, prefer meaningful immutable versioning like myapp:1.0.1 or myapp:git-a83f21 over relying on myapp:latest, which doesn't necessarily mean "newest production version."

docker build -t myapp . — the trailing . is the build context: the directory sent to the daemon. A .dockerignore keeps things like node_modules, .git, and .env out of that context.

image management
docker images            # list images
docker rmi myapp          # remove an image
docker inspect myapp      # full metadata
docker history myapp      # show image layers
docker system prune       # clean unused resources — careful on shared machines

Ports, Env Vars, Logs & Debugging

runtime basics
# Port mapping — host:container
docker run -p 8080:3000 myapp

# Env vars — never hardcode secrets in code
docker run -e NODE_ENV=production -e PORT=3000 myapp
docker run --env-file .env myapp

# Logs — Docker captures stdout/stderr
docker logs myapp
docker logs -f myapp        # follow

# Shell into a running container
docker exec -it myapp sh

# Live resource usage
docker stats

For your Node + Pino + ECS setup, logs flow: Node.js → Pino → stdout → Docker → ECS → CloudWatch Logs — production containers should write to stdout/stderr, not to files inside the container.

🚨 EXPOSE 3000 in a Dockerfile is documentation only — it does not publish the port. Only -p 8080:3000 actually maps host → container.
⚠️ For production, don't bake secrets into the image or Dockerfile. Inject them via AWS Secrets Manager, SSM Parameter Store, or ECS task configuration instead.
2. Dockerfile Instructions in Depth

The Core Instructions

★★★★★
InstructionWhat it does
FROMSets the base image — choose deliberately for compatibility/security, not blindly latest
WORKDIRSets the working directory for subsequent instructions — equivalent of cd, but persistent
COPYCopies files from the build context into the image
RUNExecutes during image build — not on every container start
ENVSets an environment variable baked into the image — never use for secrets
EXPOSEDocumentation only; doesn't publish the port on its own
CMDDefault command when the container starts — overridable at docker run
ENTRYPOINTThe fixed executable; CMD becomes its default arguments
🚨 Never do ENV DB_PASSWORD=mySecretPassword — it becomes part of the image's permanent metadata/history, visible to anyone who can inspect the image.

ENTRYPOINT vs CMD

Dockerfile
ENTRYPOINT ["node"]
CMD ["server.js"]
# Result when run: node server.js

ENTRYPOINT is the fixed executable; CMD supplies default arguments to it. For normal Node apps, CMD alone (["node", "server.js"]) is usually sufficient — you don't need to split them unless you want the container to always run the same binary regardless of overrides.

.dockerignore & Production Dockerfile

.dockerignore

Dockerfile*
.dockerignore

Excludes unneeded (and sensitive, e.g. .env) files from ever entering the build context in the first place.

Production-oriented Dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
USER node
EXPOSE 3000
CMD ["node", "server.js"]
  • npm ci --omit=dev — only production dependencies, and ci installs exactly from the lockfile.
  • USER node — the app doesn't run as root, a real production security practice.

Multi-Stage Builds

Separates the build environment from the runtime environment — significantly reduces production image size and attack surface.

Dockerfile — multi-stage
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
CMD ["node", "dist/server.js"]
Builder image → compile/build
↓
dist/ output only
↓
Runtime image — only what's needed
3. Docker Networking & Storage

User-Defined Networks & Docker DNS

★★★★★

For application stacks, create a user-defined network rather than relying on the default bridge:

networking
docker network create app-network

docker run -d --name postgres --network app-network postgres

Your API then connects using postgres:5432 — not localhost:5432. Inside the API container, localhost means the API container itself, never a sibling container.

✅ Docker provides DNS resolution on user-defined networks — service/container names like postgres and redis resolve automatically to the right internal IP. Use DATABASE_HOST=postgres, not localhost.

Port Mapping vs Internal Networking

Containers on the same network can talk to each other directly — Postgres doesn't need -p 5432:5432 unless you need it reachable from outside Docker entirely.

API → postgres:5432 (internal, no port publish needed)
vs
Browser → localhost:8080 → API container:3000 (published)

You only publish a port to the host when external access is actually required.

Network Isolation & Host Network

frontend → frontend-network → API
↓
API → backend-network → Postgres, Redis

Separate networks let you control which services can talk to which — a database shouldn't normally be directly reachable from the public internet.

💡 --network host makes the container share the host's network namespace directly. Useful in specific cases, but bridge/user-defined networks are the normal choice for application deployments.

Volumes, Bind Mounts & tmpfs

Containers are disposable — deleting one deletes anything it wrote unless that data was routed into a volume.

volumes & bind mounts
# Named volume — Docker manages storage location
docker volume create postgres-data
docker run -d --name postgres -v postgres-data:/var/lib/postgresql/data postgres

# Bind mount — you control the host path (great for live dev)
docker run -v ./data:/app/data myapp

# tmpfs — stored in RAM, gone when the container stops
docker run --tmpfs /tmp myapp
VolumeBind Mount
Managed byDockerYou (host path)
Good forPostgres/Redis persistence, production dataLocal dev, config, live code

Removing a container never removes the volume it was attached to — a new container pointed at the same named volume picks up exactly where the data left off.

4. Docker Compose & the Full Picture

Describing the Stack in YAML

★★★★★

Compose replaces a sequence of manual docker network create / docker run commands with one declarative file describing the whole stack.

docker-compose.yml
services:

  api:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://postgres:password@postgres:5432/appdb
      REDIS_HOST: redis
    depends_on:
      - postgres
      - redis

  postgres:
    image: postgres:16
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: password
      POSTGRES_DB: appdb
    volumes:
      - postgres-data:/var/lib/postgresql/data

  redis:
    image: redis:7

volumes:
  postgres-data:

docker compose up creates the network (api, postgres, redis on it) and the postgres-data volume in one command.

KeyMeaning
build: .Use the Dockerfile in the current directory — Compose builds the image
image: postgres:16Pull an existing image instead of building one
portsSame as -p host:container
environment / env_fileSet env vars inline or load from a file — don't commit real secrets

depends_on vs Healthchecks

⚠️ depends_on only controls startup order — it does not mean "Postgres is ready to accept connections," only that its container has started.
healthcheck + condition
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U postgres"]
  interval: 10s
  timeout: 5s
  retries: 5

# on the dependent service:
depends_on:
  postgres:
    condition: service_healthy
Start Postgres
↓
Healthcheck runs
↓
Not healthy → wait
Healthy → API starts

This is far more reliable than assuming "container started" means "application ready."

Compose Commands to Know

compose commands
docker compose up              # start
docker compose up -d           # start in background
docker compose up --build      # build + start
docker compose ps              # see containers
docker compose logs -f api     # follow one service's logs
docker compose down            # stop + remove containers/networks
docker compose down -v         # ALSO removes named volumes — deletes DB data!
🚨 docker compose down -v removes Compose-managed volumes, which means persistent database data stored there is deleted too. Use with real caution.

Dockerfile → docker build → Docker Image
↓

↓

By the end of this progression you should be comfortable with pull, build, run, ps, exec, logs, stop, start, rm, images, rmi, network, volume, compose — and, more importantly, with the mental model of Dockerfile → Image → Container → Network → Volume → Compose as one continuous chain.

Interview Q&A
💡 Interview Q&A
Standard Questions
Why does instruction order in a Dockerfile matter for build speed?
Docker caches each layer and reuses it if nothing above it changed. Putting rarely-changing steps (like installing dependencies from a lockfile) before frequently-changing steps (like copying source code) means most rebuilds only re-run the small final layers instead of reinstalling everything.
What's the difference between EXPOSE in a Dockerfile and -p on docker run?
EXPOSE is documentation/metadata declaring which port the app expects to use — it doesn't make the app reachable from the host. -p host:container is what actually publishes and maps a port so the host (or outside world) can reach it.
Why can't two containers on the same Docker network reach each other via localhost?
Each container has its own network namespace, so localhost inside a container refers only to that container itself, never a sibling. On a user-defined network, containers should reach each other by service/container name (e.g. postgres), which Docker's built-in DNS resolves to the right internal IP.
What's the difference between a Docker volume and a bind mount?
A volume is fully managed by Docker — you don't control the exact host path — and is the standard choice for persistent data like a database. A bind mount maps a specific host directory directly into the container, which is ideal for local development (e.g. live-reloading source code) but less appropriate for production data.
Why doesn't depends_on guarantee a dependency is actually ready?
It only controls the order containers are started in — a Postgres container can be "started" while the database engine inside it is still initializing. A healthcheck plus depends_on: condition: service_healthy is what actually waits for the dependency to report itself ready.
Tricky / Follow-Up Questions
If you set ENV DB_PASSWORD=... in a Dockerfile, is that safe as long as you don't commit the Dockerfile to a public repo?
No — the value becomes baked into the image's layer history and metadata. Anyone who can pull or inspect that image (e.g. via docker history) can retrieve it, regardless of whether the Dockerfile source itself is public. Secrets should be injected at runtime (env vars, secret managers), never hardcoded into image-building instructions.
Why use multi-stage builds instead of just cleaning up build artifacts at the end of a single-stage Dockerfile?
A single-stage build still leaves every intermediate layer (including build tools, dev dependencies, and the full build cache) baked into the image history, even if you delete files in a later step — those earlier layers still exist and add to image size and attack surface. Multi-stage builds start the final image from a clean base and copy over only the specific build output, so none of the builder stage's extra content is present at all.
Does removing a container that used a named volume delete the data in that volume?
No — the volume is a separate Docker-managed resource from the container. Removing the container leaves the volume intact; a new container attached to the same volume name picks up right where the data left off. The volume itself must be explicitly removed (e.g. via docker volume rm or compose down -v) to actually lose the data.
If Postgres and your API are on the same Docker network, do you need to publish Postgres's port with -p?
No — containers on the same network can already reach each other directly over their internal ports. You'd only add -p 5432:5432 if you specifically need to connect to Postgres from outside Docker entirely, such as from a local database GUI tool on the host.
Frequently Asked
What's the difference between RUN and CMD in a Dockerfile?
RUN executes once, during the image build, and its result is baked into a layer. CMD defines the default command that runs every time a container starts from that image, and it doesn't execute at build time at all.
Why prefer npm ci over npm install in a Dockerfile?
npm ci installs exactly what's in the lockfile and fails if package.json and the lockfile are out of sync, giving reproducible builds. npm install can update the lockfile and resolve slightly different versions across builds, which undermines the consistency Docker is meant to provide.
Why run the container process as a non-root user (USER node) in production?
If an attacker compromises the application process, running as a limited non-root user restricts what they can do inside the container — they can't, for example, modify system files or escalate privileges as easily as they could as root. It's a standard least-privilege hardening step.
Coding / Theoretical
Write a Compose file for a Node API + Postgres where the API only starts once Postgres is actually accepting connections.
docker-compose.yml
services:
  api:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://postgres:password@postgres:5432/appdb
    depends_on:
      postgres:
        condition: service_healthy

  postgres:
    image: postgres:16
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: password
      POSTGRES_DB: appdb
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 5
    volumes:
      - postgres-data:/var/lib/postgresql/data

volumes:
  postgres-data:

Why this shape: the plain depends_on: [postgres] form only waits for the container to start, not for Postgres itself to accept connections. Using the object form with condition: service_healthy plus a real healthcheck means the API won't even attempt to connect until Postgres is actually ready.

Explain, in three layers, why the Dockerfile → Image → Container → Volume chain avoids the classic "container deleted, data gone" problem without giving up the benefits of disposable containers.
Each layer keeps a different concern separate: the image defines the application and its runtime, but is never itself mutated at runtime — it stays a clean, reusable template. The container's writable layer is where runtime state would normally live, but it's explicitly treated as disposable and expected to disappear on removal — this is what keeps containers cheap to recreate, restart, and scale. The volume is the one piece deliberately pulled outside that disposable boundary — Docker keeps it as a separate, independently-managed resource, so recreating or replacing the container (for a deploy, an image update, or a crash recovery) never touches the data as long as the new container points at the same volume.
