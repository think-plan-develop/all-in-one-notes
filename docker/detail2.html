Docker — Node.js, Production & AWS

Interview notes — dockerizing a Node/Express + Postgres + Redis stack, production hardening, security, logging, and the full ECS/Fargate/AWS deployment picture.

Node.js Stack Production Hardening Security & Logging Docker + AWS (ECR/ECS/Fargate) Production AWS Architecture Interview Q&A
💡 Important framing: Docker should package the application; it shouldn't necessarily replace managed infrastructure. Locally you run Node + Postgres + Redis in Compose; in AWS production, Node runs on ECS while Postgres and Redis move to RDS and ElastiCache.
🔑 Key Terms at a Glance
🌐
0.0.0.0: Bind here, not "localhost", so the app accepts connections through the container's network interface.
🛑
SIGTERM / Graceful Shutdown: Finish in-flight requests and close DB/Redis connections before exiting on stop.
📦
ECR: Stores Docker images — it does not run containers.
🧩
Task Definition vs Task: A blueprint (image, CPU, memory, ports, env) vs an actual running instance of it.
🔐
Execution Role vs Task Role: Execution Role = ECS/Fargate infra actions (pull image, send logs); Task Role = your app's own AWS permissions.
🚦
ALB → Target Group → ECS: The load balancer never talks to tasks directly — it routes through a target group that also runs health checks.
1. Docker + Node.js Stack

Dockerizing an Express API

★★★★★
src/server.js
const express = require("express");
const app = express();
app.use(express.json());

app.get("/", (req, res) => res.json({ message: "API is running" }));

// bind to 0.0.0.0, not "localhost" — required for Docker networking
app.listen(3000, "0.0.0.0", () => console.log("Server running on port 3000"));
🚨 If you bind with app.listen(3000, "localhost"), the app may only accept connections from inside the container itself — external traffic (even via published ports) can fail to reach it. Always bind to 0.0.0.0 in a containerized app.
Dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
EXPOSE 3000
CMD ["node", "src/server.js"]

npm install vs npm ci, and Why node_modules Isn't Copied

npm install

Installs dependencies and can modify package-lock.json — not fully reproducible across builds.

npm ci

Clean, reproducible install straight from the lockfile. Preferred for Docker builds, especially with --omit=dev for production.

Never COPY . . before excluding node_modules — your local node_modules (possibly built for the wrong OS/arch, e.g. Windows host → Linux container) could get copied in. A .dockerignore with node_modules, .git, .env keeps the build context clean, and COPY package*.json ./ + RUN npm ci lets Docker build node_modules itself, natively for the container's OS.

Full Stack: API + Postgres + Redis in Compose

docker-compose.yml
services:
  api:
    build: .
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgresql://postgres:password@postgres:5432/myapp
      REDIS_HOST: redis
      REDIS_PORT: 6379
    depends_on:
      postgres: { condition: service_healthy }
      redis: { condition: service_started }

  postgres:
    image: postgres:16
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: password
      POSTGRES_DB: myapp
    volumes: ["postgres-data:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d myapp"]
      interval: 5s
      retries: 5

  redis:
    image: redis:7

volumes:
  postgres-data:
✅ Break down postgresql://postgres:password@postgres:5432/myapp: postgres (user) : password @ postgres (Docker service hostname, not localhost) : 5432 / myapp (database). Same logic for Redis: REDIS_HOST=redis, never localhost.

Development vs Production Containers

Development

Host source bind-mounted into the container, running under nodemon for hot reload:

yaml
volumes: [".:/app", "/app/node_modules"]
command: npm run dev

Production

No bind mount — source is baked into the image via docker build, running as a non-root user with only production deps.

Note: without a volume, deleting the Postgres container in local dev risks losing data — for real production, a managed database (RDS) replaces a Postgres container entirely, covered in Section 5.

2. Production Docker Hardening

Multi-Stage Builds & Minimal Base Images

★★★★★
Dockerfile — multi-stage
FROM node:18-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:18-alpine AS production
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]

The final image never contains the build tools, dev dependencies, or compiler used in the build stage — only the compiled dist/ output and production dependencies. Prefer minimal bases (alpine, or distroless) to shrink both size and attack surface — but test your actual app, since some native dependencies have compatibility quirks on Alpine.

💡 Layer ordering still matters here: COPY package*.json ./ → RUN npm ci → COPY . . means changing server.js reuses the cached dependency layer, speeding up CI/CD builds significantly.

BuildKit Secrets, Non-Root User & Read-Only Filesystem

BuildKit can mount a secret into a build step temporarily, without it ever landing in the final image layers — useful for private registry credentials needed only during npm install.

runtime hardening
USER node   # Dockerfile — don't run the app as root

docker run --read-only myapp        # root FS becomes read-only
docker run --read-only --tmpfs /tmp myapp   # with writable scratch space
✅ If the application is compromised while running as node instead of root, the attacker inherits far fewer privileges — reducing what they can modify or escalate to.

Healthchecks & Graceful Shutdown

Dockerfile HEALTHCHECK + /health route
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD wget --spider -q http://localhost:3000/health || exit 1
graceful shutdown
process.on("SIGTERM", async () => {
  server.close(async () => {
    await db.close();
    await redis.quit();
    process.exit(0);
  });
});
⚠️ "Container running" ≠ "application healthy" — a Node process can be alive with a dead DB connection. A healthcheck actually tests the app. On the other end, SIGTERM handling means deployments don't abruptly cut off in-flight requests.

Resource Limits, Restart Policies & Secrets

bash
docker run --memory=512m --cpus=1 myapp
docker run --restart=on-failure myapp   # no | always | on-failure | unless-stopped

In orchestrated environments (ECS), CPU/memory limits move to the task definition, and restart behavior is handled by the orchestrator's service, not standalone Docker restart policies.

🚨 Never ENV DB_PASSWORD=... in a Dockerfile. Production secrets flow: Secrets Manager → ECS → container environment → Node.js, keeping the same Docker image reusable across dev/test/production with only configuration changing.
3. Security & Logging

Container Isolation & Least Privilege

★★★★★

Docker uses namespaces to isolate processes, network, filesystem, and users — but containers share the host kernel, so isolation is weaker than a VM's. Compensate with least privilege:

bash
docker run --cap-drop=ALL myapp   # drop unneeded Linux capabilities

Linux capabilities (e.g. NET_BIND_SERVICE to bind privileged ports) grant a specific privilege without full root access — much narrower than "give the container root."

Secrets, Vulnerability Scanning & Trusted Images

bash
trivy image myapp:latest   # scan for known CVEs in OS packages, deps, base image

Never bake secrets into an image (ENV DB_PASSWORD=...) — use AWS Secrets Manager, BuildKit secrets, or Vault instead. Prefer trusted base images (node:18-alpine); for stronger reproducibility, pin by digest (image@sha256:...) so you're guaranteed the exact image content, not just a mutable tag.

Supply Chain Security & Production Checklist

Supply chain: protect the path from source code → build → image → registry → production using image signing (cosign/Sigstore) and an SBOM (Software Bill of Materials) documenting exactly what's inside the image.

  • ✓ Non-root user
  • ✓ Minimal trusted base image
  • ✓ No secrets inside the image
  • ✓ .dockerignore in place
  • ✓ Scan images (e.g. Trivy)
  • ✓ Keep dependencies updated
  • ✓ Drop unnecessary capabilities
  • ✓ Read-only filesystem where practical
  • ✓ Pin production images when reproducibility matters
  • ✓ Generate/maintain an SBOM
  • ✓ Sign and verify images
✅ Master these first, in order: non-root containers → secrets management → vulnerability scanning → trusted/minimal images.

4. Docker + AWS — ECR, ECS & Fargate

ECR — Image Storage Only

★★★★★
push to ECR
docker build -t node-api .
docker tag node-api:latest 123456789012.dkr.ecr.us-east-1.amazonaws.com/node-api:latest
aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin 123456789012.dkr.ecr.us-east-1.amazonaws.com
docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/node-api:latest
🚨 ECR does not run your container — it only stores the image. Running it is ECS's job.

ECS: Task Definition, Task & Service

Task Definition — the blueprint (image, CPU, memory, port, env, secrets, IAM role, logging)
↓
Task — an actual running instance of that blueprint
↓
Service — maintains desired task count, handles rolling deploys & replaces crashed tasks
task definition (conceptual)
{
  "family": "node-api-task",
  "cpu": "512", "memory": "1024",
  "containerDefinitions": [{
    "name": "node-api",
    "image": "123456789012.dkr.ecr.us-east-1.amazonaws.com/node-api:latest",
    "portMappings": [{ "containerPort": 3000 }]
  }]
}

Changing the image or config creates a new task-definition revision (v1, v2, v3...) — you don't mutate the old one in place.

Fargate & IAM Roles

ECS + EC2 means you manage the underlying instances yourself. ECS + Fargate means AWS manages the compute — you just declare CPU/memory and Fargate runs it. Fargate is a strong default starting point.

RoleGrants
Execution RoleECS/Fargate infrastructure actions — pull image from ECR, send logs to CloudWatch
Task RoleYour application's own AWS permissions — e.g. secretsmanager:GetSecretValue
🚨 Never hardcode AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY in the image. The Task Role gives the container exactly the AWS permissions it needs, nothing more.

VPC, Subnets, Security Groups & ALB

Internet
↓
Public Subnet — ALB
↓
Private Subnet — ECS Tasks
↓
Private Subnet — RDS, ElastiCache
security group chain
ALB Security Group:  inbound 80/443 from 0.0.0.0/0
ECS Security Group:  inbound 3000 from ALB Security Group only
RDS Security Group:  inbound 5432 from ECS Security Group only

Requests flow Internet → ALB → Target Group → ECS Tasks; the target group performs health checks (e.g. GET /health expecting 200) and stops routing to any task that fails repeatedly.

🚨 The database and Redis should never be directly reachable from the internet — only from the application layer, via security groups scoped to each other, not to 0.0.0.0/0.

CloudWatch, Env Vars & Auto Scaling

Node.js / Pino
↓ stdout
ECS awslogs driver
↓
CloudWatch Logs — /ecs/node-api

Environment variables and secrets are set in the task definition, not baked into the image — sensitive values (JWT_SECRET, DATABASE_URL, REDIS_PASSWORD) come from Secrets Manager. Auto Scaling adjusts the ECS Service's desired task count based on signals like CPU/memory utilization or ALB request count (e.g. CPU > 70% → scale up, CPU < 30% → scale down).

Rolling Deployments (v1 → v2)

Task 1: v1, Task 2: v1
↓ deploy v2
Task 1: v1, Task 2: v2 (new task health-checked before traffic shifts)
↓
Task 1: v2, Task 2: v2

ECS replaces old tasks with new ones gradually, keeping traffic flowing throughout — the foundation of zero/minimal-downtime deployment.

5. Production AWS Architecture

Why RDS & ElastiCache Instead of Containers

★★★★★

Local development

Docker Compose: Node + PostgreSQL container + Redis container — fast, disposable, fine for dev.

Production

ECS runs Node only. PostgreSQL moves to RDS, Redis to ElastiCache — AWS handles backups, patching, storage, monitoring, Multi-AZ, and recovery.

Your production system shouldn't depend on a database container running alongside the app in ECS.

Full Production Request Flow

User → HTTPS → ALB
↓
Target Group → ECS Fargate Task (Node/Express)
↓
RDS PostgreSQL / ElastiCache Redis
↓
Response → ALB → User

All logs flow separately: Node.js → Pino → stdout → ECS → CloudWatch Logs, in parallel to the request/response path.

↓

Interview Q&A
💡 Interview Q&A
Standard Questions
Why should a Node app inside a container listen on 0.0.0.0 instead of localhost?
Binding to localhost can restrict the server to only accept connections that originate from inside the container itself. 0.0.0.0 tells the app to accept connections on any network interface, which is required for traffic coming in through Docker's published ports to actually reach it.
What's the difference between an ECS Task Definition and an ECS Task?
A Task Definition is a static blueprint — image, CPU, memory, ports, environment, IAM roles. A Task is an actual running instance created from that blueprint. Multiple tasks can run from the same task definition, and changing the definition creates a new revision rather than mutating the old one.
What does ECR actually do, and what doesn't it do?
ECR is a private Docker image registry — it stores images you push to it. It does not run containers; that responsibility belongs entirely to ECS (with Fargate or EC2 providing the compute).
Why does production typically use RDS and ElastiCache instead of running Postgres/Redis as containers in ECS?
Managed services handle backups, patching, storage scaling, monitoring, Multi-AZ failover, and recovery automatically. Running a stateful database as just another container in ECS means you'd have to build all of that operational tooling yourself, and risks data loss if the container's storage isn't carefully managed.
What is the difference between the ECS Execution Role and the ECS Task Role?
The Execution Role lets ECS/Fargate itself perform infrastructure actions — pulling the image from ECR and shipping logs to CloudWatch. The Task Role grants permissions to your actual application code, e.g. reading a specific secret from Secrets Manager. Conflating them would either over-grant the infrastructure or block the app from doing its job.
Tricky / Follow-Up Questions
If your ALB health check passes but users still report errors, what's a likely explanation?
The health check endpoint (e.g. /health) may only verify that the process is alive, not that dependent services like the database or Redis are reachable. A shallow healthcheck can report "healthy" while the actual business endpoints fail due to a broken downstream dependency — health checks should ideally reflect real readiness, not just process liveness.
Why does Docker's default logging model (stdout/stderr) matter specifically for ECS/CloudWatch integration?
ECS's awslogs driver captures whatever the container writes to stdout/stderr and forwards it to CloudWatch automatically. If an app logs to a file inside the container instead, that log never reaches CloudWatch through this mechanism — you'd have to build a separate log-shipping process, defeating the simplicity of container-native logging.
During a rolling deployment from v1 to v2, why does ECS wait for new tasks to pass health checks before removing old ones?
If ECS killed old tasks immediately and the new v2 tasks turned out to be broken, there would be a period with no healthy tasks serving traffic — an outage. Waiting for the new tasks to report healthy via the target group's health check before shifting traffic and removing old tasks is what keeps the deployment at zero or minimal downtime.
Why is --cap-drop=ALL combined with adding back only specific capabilities better than the container's default capability set?
Docker's default capability set grants more than most applications actually need. Dropping everything and adding back only what's required (e.g. NET_BIND_SERVICE if binding to a privileged port) follows least privilege — a compromised process has meaningfully fewer avenues to escalate or affect the host compared to leaving the broader default set in place.
Frequently Asked
What problem do BuildKit secrets solve that a Dockerfile ARG or ENV doesn't?
ARG/ENV values used during a build can end up cached in image layers or metadata, persisting in the final image even if seemingly "removed" in a later step. BuildKit's secret mount makes a value available only to the specific build step that needs it, without writing it into any layer of the resulting image.
Why pin a production image by digest instead of by tag?
A tag like latest or even node:18-alpine can point to different actual image content over time as it gets rebuilt upstream. A digest (@sha256:...) references the exact, immutable content of a specific image, guaranteeing that every deploy uses precisely the same bytes.
Why should the database's security group only allow traffic from the ECS security group, not from a specific IP range?
Referencing another security group as the source means the rule automatically stays correct as ECS tasks are replaced, rescheduled, or scaled — their IPs change, but they're still members of the same security group. Hardcoding IP ranges would require constant updates and risks either blocking legitimate new tasks or overly permissive rules to compensate.
Coding / Theoretical
Write a Node.js graceful shutdown handler that also enforces a maximum shutdown timeout.
shutdown.js
const SHUTDOWN_TIMEOUT_MS = 10000;

process.on("SIGTERM", () => {
  console.log("SIGTERM received, shutting down gracefully...");

  const forceExit = setTimeout(() => {
    console.error("Forced shutdown after timeout");
    process.exit(1);
  }, SHUTDOWN_TIMEOUT_MS);

  server.close(async () => {
    try {
      await db.close();
      await redis.quit();
      clearTimeout(forceExit);
      process.exit(0);
    } catch (err) {
      console.error("Error during shutdown", err);
      process.exit(1);
    }
  });
});

Why this shape: the timeout guards against a hung connection close (e.g. a stuck DB client) preventing the process from ever exiting, which would force the orchestrator to SIGKILL it anyway — better to fail fast and predictably than to hang indefinitely.

Explain, in three layers, why "ALB → Target Group → ECS Tasks" is a more resilient design than pointing the ALB directly at task IPs.
Each layer solves a specific problem: ECS tasks are ephemeral — they get replaced on crashes, deploys, and scaling events, so their IPs constantly change; a target group is a stable registration point that ECS automatically keeps in sync with the current live tasks, so the ALB never needs to be reconfigured by hand. The target group's health checks mean traffic is only ever routed to tasks that are actually responding correctly, so a single unhealthy task doesn't silently receive user requests. And because the ALB only knows about the target group, not individual tasks, rolling deployments and auto-scaling can add or remove tasks freely — the target group absorbs that churn without the ALB's configuration needing to change at all.
