8. Docker + Node.js

Goal: Build this real architecture

Client │ ↓ Node / Express :3000 / \ ↓ ↓ PostgreSQL Redis :5432 :6379 │ ↓ Docker Volume

With Docker Compose:

docker-compose.yml │ ├── API container ├── PostgreSQL container ├── Redis container ├── Network └── PostgreSQL Volume
8.1

Dockerize Express API

Suppose your Node project looks like:

my-api/ │ ├── src/ │ └── server.js │ ├── package.json ├── package-lock.json ├── Dockerfile └── .dockerignore

Simple Express application:

src/server.js
const express = require("express");

const app = express();

app.use(express.json());

app.get("/", (req, res) => {
  res.json({
    message: "API is running"
  });
});

app.listen(3000, "0.0.0.0", () => {
  console.log("Server running on port 3000");
});

Why 0.0.0.0?

This is important with Docker.

If you use:

javascript
app.listen(3000, "localhost");

the application may only listen inside the container.

Use:

javascript
app.listen(3000, "0.0.0.0");

so the application accepts connections coming through the container's network interface.

8.2

Node.js Dockerfile

A basic Dockerfile:

Dockerfile
FROM node:18-alpine

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 3000

CMD ["node", "src/server.js"]

Build:

bash
docker build -t node-api .

Run:

bash
docker run -d \
--name node-api \
-p 3000:3000 \
node-api

Now:

Browser ↓ localhost:3000 ↓ Docker ↓ Node container :3000
8.3

NODE_ENV

Node applications commonly use:

development test production

Example:

bash
NODE_ENV=production

In Node:

javascript
console.log(process.env.NODE_ENV);

You can change application behavior:

javascript
if (process.env.NODE_ENV === "production") {
  // production configuration
}

In Docker:

Dockerfile
ENV NODE_ENV=production

However, for production deployments, environment-specific configuration is often better injected at runtime rather than baking all configuration into the image.

8.4

npm install vs npm ci

This is important for Docker.

npm install

bash
npm install

It installs dependencies and can modify/update package-lock.json.

npm ci

bash
npm ci

is designed for clean, reproducible installations.

It uses:

package.json + package-lock.json

and installs the locked dependency versions.

For production Docker builds, generally prefer:

Dockerfile
RUN npm ci

or:

Dockerfile
RUN npm ci --omit=dev

for the final production image.

8.5

Why node_modules Should Not Be Copied

Your local machine may have:

node_modules/

But you shouldn't do:

Dockerfile
COPY . .

and accidentally send your local node_modules into the image.

Use:

.dockerignore
.dockerignore
node_modules
.git
.env
npm-debug.log

Then Docker creates node_modules itself:

Dockerfile
COPY package*.json ./
RUN npm ci

This also avoids problems caused by host-specific binaries, especially when developing on Windows and running Linux containers.

8.6

PostgreSQL Container

Instead of installing PostgreSQL directly on your machine:

Windows └── PostgreSQL

Docker can run:

Docker └── PostgreSQL container

Use the official image:

yaml
image: postgres:16

Postgres requires configuration such as:

POSTGRES_USER POSTGRES_PASSWORD POSTGRES_DB

Example:

yaml
postgres:
  image: postgres:16
  environment:
    POSTGRES_USER: postgres
    POSTGRES_PASSWORD: password
    POSTGRES_DB: myapp
8.7

PostgreSQL Volume

Without a volume:

Postgres container ↓ container deleted ↓ data potentially lost

So:

yaml
volumes:
  - postgres-data:/var/lib/postgresql/data

Architecture:

Postgres container │ ↓ /var/lib/postgresql/data │ ↓ postgres-data volume

Define the volume:

yaml
volumes:
  postgres-data:

Now:

Container deleted ↓ Volume remains ↓ Database data remains

For local Docker development this is extremely useful.

For production, databases are often better hosted using a managed database service such as Amazon RDS rather than running PostgreSQL inside an application container.

8.8

Redis Container

Redis can similarly run as a container:

yaml
redis:
  image: redis:7

Redis commonly handles:

Caching Sessions Rate limiting Queues Temporary data

For example:

Node API │ ├── PostgreSQL → permanent application data │ └── Redis → cache/session/queue data

The Node application connects to Redis using:

redis:6379

not:

localhost:6379

because redis is the Docker Compose service name.

8.9

API + PostgreSQL + Redis

Now we can create the complete Compose file.

docker-compose.yml
services:

  api:
    build: .
    container_name: node-api
    ports:
      - "3000:3000"

    environment:
      NODE_ENV: development
      PORT: 3000
      DATABASE_URL: postgresql://postgres:password@postgres:5432/myapp
      REDIS_HOST: redis
      REDIS_PORT: 6379

    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_started

  postgres:
    image: postgres:16
    container_name: postgres

    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: password
      POSTGRES_DB: myapp

    volumes:
      - postgres-data:/var/lib/postgresql/data

    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d myapp"]
      interval: 5s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7
    container_name: redis

volumes:
  postgres-data:

Run:

bash
docker compose up --build

Now Compose creates a network automatically:

Docker Network │ ┌──────────────┼──────────────┐ ↓ ↓ ↓ API Postgres Redis :3000 :5432 :6379
8.10

How Node Connects to PostgreSQL

Inside the API container:

DATABASE_URL= postgresql://postgres:password@postgres:5432/myapp

Break it down:

postgresql:// postgres → username : password → password @ postgres → Docker service/container hostname : 5432 → PostgreSQL port / myapp → database

The important part is:

@postgres:5432

not:

@localhost:5432

Because:

localhost

inside the API container means:

API container

while:

postgres

means:

PostgreSQL container
8.11

How Node Connects to Redis

Similarly:

env
REDIS_HOST=redis
REDIS_PORT=6379

Architecture:

Node API │ │ redis:6379 ↓ Redis container

Docker's internal DNS resolves:

redis

to the Redis container.

8.12

Development vs Production · Development

This distinction is very important.

Development

You want:

Fast code changes Hot reload Debugging Source code mounted

Typical setup:

Host │ ├── src/ │ ↓ bind mount Container │ └── nodemon

For example:

yaml
api:
  build:
    context: .
    target: development

  volumes:
    - .:/app
    - /app/node_modules

  command: npm run dev

And:

package.json
{
  "scripts": {
    "dev": "nodemon src/server.js"
  }
}

Now you modify:

src/server.js

and nodemon restarts the application.

8.13

Production Container

Production should generally be different.

You don't want:

Host source code ↓ bind mounted ↓ production container

Instead:

Source code ↓ Docker build ↓ Production image ↓ Container

The production image should contain only what is required to run the application.

For example:

Dockerfile
FROM node:18-alpine

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY . .

USER node

EXPOSE 3000

CMD ["node", "src/server.js"]

So:

Development Host → bind mount → Container → nodemon Production Dockerfile → Image → Container → Node
9. Production Docker

Take Section 8 and make it production-grade

Now we take the application we built in Section 8 and make it production-grade.

The goal is:

Secure Small Fast Reproducible Observable Resilient
9.1

Multi-stage Builds

A multi-stage Dockerfile has multiple FROM statements.

Example:

Dockerfile
FROM node:18-alpine AS build

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build


FROM node:18-alpine AS production

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY --from=build /app/dist ./dist

USER node

EXPOSE 3000

CMD ["node", "dist/server.js"]

Concept:

BUILD STAGE ─────────── Source Dev dependencies Build tools Compiler │ ↓ dist/ │ ↓ PRODUCTION STAGE ─────────────── Runtime Production dependencies dist/

The final image doesn't need the build tools.

9.2

Minimal Base Images

Instead of:

Dockerfile
FROM node:18

you might use:

Dockerfile
FROM node:18-alpine

Alpine is much smaller.

Another option is:

Distroless

Distroless images contain very little beyond the application runtime.

The principle is:

Less software ↓ Smaller image ↓ Smaller attack surface

But don't choose Alpine/distroless blindly. Some Node native dependencies can have compatibility considerations. Test your actual application.

9.3

Image Size Optimization

Bad:

Huge base image + dev dependencies + unnecessary files + node_modules copied from host

Better:

Minimal base + production dependencies + only application files

Use:

Dockerfile
RUN npm ci --omit=dev

and:

.dockerignore

For Debian-based images, package-manager caches should be cleaned appropriately. But don't add cleanup commands mechanically—design the RUN instruction so unnecessary package cache isn't left in the resulting layer.

9.4

Layer Optimization

Bad:

Dockerfile
COPY . .
RUN npm install

Better:

Dockerfile
COPY package*.json ./
RUN npm ci
COPY . .

Suppose you change:

server.js

The dependency layer remains cached.

package.json ↓ npm ci ↓ CACHED ↓ server.js changed ↓ only later layer rebuilds

This can make CI/CD builds significantly faster.

9.5

BuildKit

Modern Docker uses BuildKit for builds.

It provides features such as:

Better caching Parallel build operations Build secrets Cache mounts Improved build performance

One particularly important security feature is secret mounting.

Instead of putting a secret into:

Dockerfile
ENV SECRET=value

or:

Dockerfile
COPY secret.txt .

BuildKit can provide secrets temporarily during a build.

Conceptually:

Secret ↓ Build step only ↓ not stored in final image

This is useful when a build needs private package registry credentials or similar build-time secrets.

9.6

Non-root User

By default, some containers may run processes as root.

That's unnecessary for most applications.

Use:

Dockerfile
USER node

with the Node official image's existing node user.

Conceptually:

Container │ └── Node process ↓ node user

instead of:

Container │ └── Node process ↓ root

If an attacker exploits the application, reducing privileges limits what the compromised process can do.

9.7

Read-only Filesystem

You can run:

bash
docker run --read-only myapp

Now the container's root filesystem can't normally be written to.

Conceptually:

Application │ ├── Read files ✓ └── Modify files ✗

If your application needs temporary writable storage, provide something like a tmpfs mount:

bash
--tmpfs /tmp

This is defense in depth.

9.8

Healthchecks

A container being "running" doesn't necessarily mean the application is healthy.

Example:

Container running ✓ Node process running ✓ Database connection broken ✗ API actually usable ✗

A healthcheck can test the application.

For example:

Dockerfile
HEALTHCHECK \
  --interval=30s \
  --timeout=5s \
  --retries=3 \
  CMD wget --spider -q http://localhost:3000/health || exit 1

Your API should have:

javascript
app.get("/health", (req, res) => {
  res.status(200).json({
    status: "ok"
  });
});

Now Docker can determine whether the application responds.

9.9

Graceful Shutdown

This is especially important for Node.js production applications.

Suppose ECS/Kubernetes/Docker wants to stop your container.

It typically sends:

SIGTERM

Your Node application should:

Receive SIGTERM ↓ Stop accepting new requests ↓ Finish in-flight requests ↓ Close DB connections ↓ Close Redis connections ↓ Exit

Example:

javascript
process.on("SIGTERM", async () => {
  console.log("SIGTERM received");

  server.close(async () => {
    await db.close();
    await redis.quit();

    process.exit(0);
  });
});

This prevents requests from being abruptly terminated during deployments.

9.10

Resource Limits

Containers can consume excessive resources.

For example:

bash
docker run \
  --memory=512m \
  --cpus=1 \
  myapp

Means approximately:

Memory → 512 MB CPU → 1 CPU

This helps prevent one container from consuming unlimited resources on a shared host.

In orchestrated environments such as ECS, equivalent CPU/memory resource configuration is normally defined at the task/container level.

9.11

Restart Policies

Docker can restart containers automatically.

Example:

bash
docker run \
  --restart=on-failure \
  myapp

Common policies:

no always on-failure unless-stopped

For example:

Application crashes ↓ Docker detects exit ↓ Restart container

In production orchestrators like ECS, you generally rely on the orchestrator's service/task restart behavior rather than treating Docker's standalone restart policy as your entire availability strategy.

9.12

Production Environment Variables and Secrets

Avoid:

Dockerfile
ENV DB_PASSWORD=myPassword

and don't put real secrets into:

Git Dockerfile Docker image

Instead:

Production │ ↓ Secrets Manager │ ↓ ECS │ ↓ Container environment │ ↓ Node.js

For example:

javascript
process.env.DATABASE_URL

Your image remains reusable:

Same Docker Image │ ├── Dev ├── Test └── Production

Only configuration changes.

Final Production Node.js Docker Architecture

Putting Sections 8 and 9 together:

Docker Build │ ↓ Multi-stage Build │ ↓ Production Image ┌───────────────┐ │ Node Runtime │ │ App Code │ │ Prod Deps │ │ Non-root user │ └───────┬───────┘ │ ↓ API Container :3000 │ ┌───────┴───────┐ ↓ ↓ PostgreSQL Redis │ │ Persistent Cache/Queue/ Storage Sessions

And in AWS, the architecture you have been learning becomes:

Developer ↓ Dockerfile ↓ docker build ↓ Docker Image ↓ Amazon ECR ↓ ECS ↓ ECS Task ↓ Node.js Container │ ├── CloudWatch Logs ├── Secrets Manager ├── RDS PostgreSQL └── ElastiCache Redis
Key production mindset: Docker should package the application; it should not necessarily replace managed infrastructure. For example, locally you can run Node + PostgreSQL + Redis in Compose, while in AWS a common production architecture is Node on ECS + PostgreSQL on RDS + Redis on ElastiCache.
10. Docker Security

Goal: harder to compromise, limited damage

Goal: Make containers harder to compromise and limit the damage if something goes wrong.

1

Container Isolation

Docker uses Linux namespaces to isolate:

  • Processes
  • Network
  • Filesystem
  • Users

But containers share the host kernel, so they aren't as strongly isolated as VMs.

2

Least Privilege

Give the container only the permissions it actually needs.

Example:

bash
docker run --cap-drop=ALL myapp

Instead of giving the container unnecessary Linux privileges.

3

Non-root Containers

Don't run your application as root.

Dockerfile:

Dockerfile
USER node

If the application is compromised, the attacker has fewer privileges.

4

Linux Capabilities

Linux capabilities provide specific privileges without giving full root access.

For example:

NET_BIND_SERVICE

allows binding to privileged ports.

Instead of:

Full root privileges

you can grant only the capability required.

5

Secrets Management

Never do:

Dockerfile
ENV DB_PASSWORD=secret123

because the secret can become part of the image/configuration.

Use:

AWS Secrets Manager Docker/BuildKit secrets Vault ECS secrets

For your AWS setup:

AWS Secrets Manager ↓ ECS ↓ Node container
6

Image Vulnerability Scanning

Your image may contain vulnerable packages.

Use tools such as:

bash
trivy image myapp:latest

It can identify known CVEs in:

OS packages Node dependencies Base image Libraries

Then update the vulnerable package/base image.

7

Trusted Base Images

Prefer trusted images:

Dockerfile
FROM node:18-alpine

rather than unknown/untrusted images.

For stronger reproducibility, production systems can pin an image by digest:

image@sha256:...

This ensures you're using the exact image content.

8

Supply Chain Security

This protects the software from being tampered with between:

Source Code ↓ Build ↓ Docker Image ↓ Registry ↓ Production

Common technologies:

Image signing → cosign / Sigstore SBOM → Software Bill of Materials

An SBOM tells you what components/packages are inside your image.

Production Security Checklist

For your Node.js Docker application, remember:

  • ✓ Non-root user
  • ✓ Minimal trusted base image
  • ✓ No secrets inside image
  • ✓ .dockerignore
  • ✓ Scan images with Trivy
  • ✓ Keep dependencies updated
  • ✓ Drop unnecessary capabilities
  • ✓ Use read-only filesystem where practical
  • ✓ Pin production images when reproducibility matters
  • ✓ Generate/maintain SBOM
  • ✓ Sign and verify images for stronger supply-chain security

The most important things to master first are non-root containers + secrets management + vulnerability scanning + trusted/minimal images.

11. Docker Logging & Monitoring

Goal: Gain visibility into running containers

  • stdout / stderr — Docker's logging model expects apps to log to stdout/stderr, not files.
  • Docker Logging Drivers — json-file (default), syslog, fluentd, awslogs, etc.
  • Structured Logging — JSON-formatted logs for easier parsing by log aggregators.
  • Log Rotation — Configuring max-size/max-file to prevent disk from filling up.
  • Health Monitoring — Combining HEALTHCHECK with orchestrator-level monitoring.
  • Metrics — docker stats, cAdvisor, Prometheus exporters for CPU/memory/network metrics.
  • Container Observability — Centralized logging/metrics/tracing stacks (ELK, Loki+Grafana, Prometheus+Grafana).

Practice: Set up log rotation on a container and pipe logs into a local ELK or Grafana Loki stack via Compose.

12. Docker + AWS

From laptop Docker to real production

This is one of the most important parts of Docker for your production-level learning, because here you move from:

Docker on your laptop ↓ Docker image ↓ AWS ↓ Real production application
12.1

Overall Architecture

Before learning each AWS service, understand the complete flow:

Developer │ │ docker build ↓ Docker Image │ │ docker push ↓ AWS ECR │ │ ECS pulls image ↓ ECS Fargate │ │ runs container ↓ Application Load Balancer │ │ HTTP/HTTPS ↓ Node.js API │ ├──────────────→ RDS PostgreSQL │ └──────────────→ ElastiCache Redis │ ↓ CloudWatch Logs

The important distinction is:

  • ECR stores your Docker image
  • ECS decides how/where the container runs
  • Fargate provides the compute
  • ALB receives public traffic
  • VPC provides networking
  • Security Groups control traffic
  • IAM controls permissions
  • CloudWatch stores logs/metrics
  • RDS stores PostgreSQL data
  • ElastiCache provides Redis
12.2

ECR — Elastic Container Registry

Amazon Elastic Container Registry

ECR is basically a private Docker registry inside AWS.

Normally you might do:

bash
docker build -t my-api .
docker push docker.io/myusername/my-api

With AWS:

Docker Image ↓ ECR ↓ ECS

Example

You create:

ECR Repository ↓ node-api

Then build:

bash
docker build -t node-api .

Tag:

bash
docker tag node-api:latest \
123456789012.dkr.ecr.us-east-1.amazonaws.com/node-api:latest

Login:

bash
aws ecr get-login-password --region us-east-1 |
docker login --username AWS --password-stdin \
123456789012.dkr.ecr.us-east-1.amazonaws.com

Push:

bash
docker push \
123456789012.dkr.ecr.us-east-1.amazonaws.com/node-api:latest

Now AWS has your image:

ECR └── node-api └── latest

Important

ECR does not run your container.

It only stores the image.

ECR = Docker image storage
12.3

ECS — Elastic Container Service

Amazon Elastic Container Service

ECS is responsible for running and managing containers.

Think:

ECR ↓ "Here is my Docker image" ECS ↓ "I will run this image"

For example:

ECS │ ├── Task 1 → node-api container ├── Task 2 → node-api container └── Task 3 → node-api container

If you configure:

Desired count = 3

ECS tries to keep 3 running tasks.

If one crashes:

Task 1 ❌ Task 2 ✅ Task 3 ✅ ↓ ECS starts replacement Task 1 → new task ✅ Task 2 ✅ Task 3 ✅

That's one of the major reasons we don't simply run:

bash
docker run node-api

in production.

ECS provides orchestration.

12.4

ECS Task Definition

This is extremely important.

A Task Definition is essentially the configuration/blueprint for your container.

It tells ECS:

Which image? How much CPU? How much RAM? Which port? Which environment variables? Which IAM role? Which logs? Which secrets?

Example conceptually:

json
{
  "family": "node-api-task",
  "cpu": "512",
  "memory": "1024",

  "containerDefinitions": [
    {
      "name": "node-api",

      "image": "123456789012.dkr.ecr.us-east-1.amazonaws.com/node-api:latest",

      "portMappings": [
        {
          "containerPort": 3000
        }
      ]
    }
  ]
}

So:

Task Definition │ ├── Image ├── CPU ├── Memory ├── Port ├── Environment variables ├── Secrets ├── IAM role └── CloudWatch logging

Task Definition ≠ Running container

This distinction is important:

Task Definition ↓ Blueprint ECS Task ↓ Actual running instance of that blueprint

If you change your Docker image/configuration, you normally create a new task-definition revision.

Example:

Revision 1 node-api:v1 Revision 2 node-api:v2 Revision 3 node-api:v3
12.5

ECS Task

A Task is an actual running instance of your task definition.

For example:

Task Definition node-api-task:3 │ ├── CPU: 0.5 vCPU ├── RAM: 1 GB └── Container: node-api ↓ Running

If you run 3 replicas:

Task Definition │ ├── Task 1 ├── Task 2 └── Task 3

Each task can run your Docker container.

12.6

ECS Service

An ECS Service manages your running tasks.

For example:

Service: node-api-service Desired count = 3

ECS maintains:

Task 1 ✅ Task 2 ✅ Task 3 ✅

If Task 2 crashes:

Task 1 ✅ Task 2 ❌ Task 3 ✅

ECS launches another:

Task 1 ✅ Task 2 → replacement ✅ Task 3 ✅

Service responsibilities

ECS Service │ ├── Desired task count ├── Deployment ├── Rolling update ├── Load balancer integration ├── Health checks └── Task replacement
12.7

Fargate

AWS Fargate

ECS needs compute infrastructure to actually run containers.

There are two major options:

ECS │ ├── EC2 │ └── Fargate

ECS + EC2

You manage:

EC2 instances ↓ Operating system ↓ CPU/RAM capacity ↓ ECS containers

More infrastructure management.

ECS + Fargate

AWS manages the underlying servers for you:

ECS ↓ Fargate ↓ Container

You specify:

CPU = 0.5 vCPU Memory = 1 GB

and AWS handles the underlying compute.

For learning and many production workloads:

ECS + Fargate

is a very good starting architecture.

12.8

IAM

AWS Identity and Access Management

IAM controls:

Who can access what?

Example:

Your ECS container needs to read secrets from Secrets Manager.

Don't put:

AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=...

inside your Docker image.

Instead:

ECS Task ↓ IAM Task Role ↓ Secrets Manager

The IAM role grants only the required permission.

For example:

Task Role │ └── secretsmanager:GetSecretValue

Another important role is:

Task Execution Role

which allows ECS/Fargate to perform things such as:

Pull image from ECR + Send logs to CloudWatch

Two roles to understand

Execution Role ↓ ECS/Fargate infrastructure actions Task Role ↓ Your application actions

This distinction is important in production.

12.9

VPC

Amazon Virtual Private Cloud

VPC is your private AWS network.

Think of it as:

AWS └── VPC │ ├── Public Subnet │ └── Private Subnet

Production architecture commonly looks like:

Internet ↓ Internet Gateway ↓ Public Subnet ↓ ALB ↓ Private Subnet ↓ ECS ↓ RDS

Your database should generally not be directly exposed to the internet.

12.10

Public vs Private Subnet

Public subnet

Usually contains resources that need direct internet-facing connectivity.

Example:

ALB

Private subnet

Usually contains internal application/data resources.

Example:

ECS RDS Redis

So:

INTERNET │ ↓ Public Subnet │ ALB │ ↓ Private Subnet │ │ ECS RDS │ Redis

There are variations, but this is the important production mental model.

12.11

Security Groups

AWS security groups

Security Groups act like virtual firewalls.

Suppose:

ALB ↓ ECS

You don't want everyone on the internet to directly access ECS.

Instead:

ALB Security Group

Inbound: HTTP 80 → 0.0.0.0/0 HTTPS 443 → 0.0.0.0/0

ECS Security Group

Inbound: Port 3000 Source = ALB Security Group

Therefore:

Internet ↓ ALB SG ↓ ALB ↓ ECS SG ↓ ECS :3000

This is much better than:

ECS :3000 ↑ 0.0.0.0/0
12.12

Application Load Balancer

Application Load Balancer

ALB is the public entry point for your API.

Without ALB:

Internet ↓ ECS Task

With ALB:

Internet ↓ ALB ↓ ECS Tasks

Suppose you have:

ECS Service Task 1 → 10.0.1.10:3000 Task 2 → 10.0.2.20:3000 Task 3 → 10.0.3.30:3000

ALB distributes requests:

Request 1 → Task 1 Request 2 → Task 2 Request 3 → Task 3 Request 4 → Task 1
12.13

Target Group

ALB normally works with a Target Group.

Flow:

Internet ↓ ALB ↓ Target Group ↓ ECS Tasks

Example:

Target Group ├── Task 1 :3000 ├── Task 2 :3000 └── Task 3 :3000

The target group also performs health checks.

For example:

GET /health

Expected:

200 OK

If Task 2 returns:

500

repeatedly, ALB marks it unhealthy and stops routing traffic to it.

12.14

CloudWatch Logs

Amazon CloudWatch

Your Node.js application produces logs:

javascript
console.log("Server started");

or:

javascript
logger.info("User logged in");

Inside ECS:

Node.js ↓ stdout / stderr ↓ ECS logging configuration ↓ CloudWatch Logs

Example:

CloudWatch └── Log Group └── /ecs/node-api ├── Task 1 logs ├── Task 2 logs └── Task 3 logs

This is why your Pino logs can appear in CloudWatch when configured through the ECS awslogs log driver.

For example:

Pino ↓ stdout ↓ ECS ↓ CloudWatch

You don't normally SSH into every container just to inspect logs.

12.15

Environment Variables

Your Node application might need:

PORT DATABASE_URL REDIS_HOST JWT_SECRET

Don't build them into your image:

Dockerfile
ENV JWT_SECRET=my-secret

Instead:

ECS Task Definition ↓ Environment / Secrets ↓ Node.js container

For sensitive values:

AWS Secrets Manager ↓ ECS ↓ Container

Example:

DATABASE_URL JWT_SECRET REDIS_PASSWORD

can be managed through Secrets Manager rather than putting them in Git or the Docker image.

12.16

Auto Scaling

Suppose you have:

ECS Service Desired count = 2

Normal traffic:

Task 1 Task 2

Traffic increases:

CPU = 85%

Auto Scaling can increase:

2 tasks ↓ 4 tasks

When traffic decreases:

4 tasks ↓ 2 tasks

Common scaling signals:

CPU utilization Memory utilization ALB request count Custom CloudWatch metrics

Example:

CPU > 70% ↓ Increase tasks CPU < 30% ↓ Decrease tasks

Now connect everything.

Step 1 — Build

ECS ├── Task 1 │ └── node-api:v1 │ └── Task 2 └── node-api:v1

Application:

http

The request travels:

User │ │ HTTPS ↓ ALB │ │ health/target routing ↓ ECS Fargate Task │ │ Node.js / Express ↓ PostgreSQL │ │ result ↓ Node.js │ ↓ ALB │ ↓ User

12.19

What Happens When You Deploy v2?

Suppose you currently have:

v1 Task 1 → v1 Task 2 → v1

You modify your Node.js application.

Build:

bash
docker build -t node-api:v2 .

Push:

node-api:v2 ↓ ECR

Create:

Task Definition Revision 2

Now ECS performs a rolling deployment:

Before: Task 1 → v1 Task 2 → v1 Deploy v2: Task 1 → v1 Task 2 → v2 Then: Task 1 → v2 Task 2 → v2

During a properly configured deployment, traffic can continue flowing while the new tasks become healthy.

This is the foundation of zero/minimal-downtime deployments.

The Most Important Mental Model

Don't think:

Docker → AWS

Think:

AWS │ ┌─────────┴─────────┐ │ │ ECR VPC │ │ Docker Image ┌────┴─────┐ │ │ │ ↓ ALB Private Network ECS │ │ │ ↓ │ Fargate ECS Tasks │ │ │ │ │ ┌────┴────┐ │ │ ↓ ↓ │ │ RDS Redis │ │ │ └────────→ CloudWatch ←───┘

13. Production AWS Container Architecture

Combine everything into a real production architecture

INTERNET │ HTTPS :443 │ ↓ ┌───────────────────┐ │ ALB │ │ Load Balancer │ └─────────┬─────────┘ │ Target Group │ ┌─────────┼─────────┐ ↓ ↓ ↓ ECS Task 1 ECS Task 2 ECS Task 3 Fargate Fargate Fargate │ │ │ └──────────┼──────────┘ │ Node.js API / Express │ ┌─────┴─────┐ ↓ ↓ RDS PostgreSQL ElastiCache Redis │ │ └─────┬─────┘ ↓ CloudWatch Logs + Metrics

But there is another important piece:

Developer / CI │ │ docker build ↓ Docker Image │ │ docker push ↓ ECR │ │ ECS pulls ↓ Fargate Tasks

So the complete picture is:

DEVELOPMENT / CI │ docker build ↓ Docker Image │ docker push ↓ ECR │ ECS pulls image ↓ ECS Fargate │ ↓ ALB │ ↓ Node.js API │ │ ↓ ↓ RDS Redis │ │ └─────┬─────┘ ↓ CloudWatch
13.1

Why RDS Instead of PostgreSQL Container?

For learning, you can run:

Docker ├── Node └── PostgreSQL

But production commonly uses:

ECS ↓ Node.js RDS ↓ PostgreSQL

Because AWS handles many database operations such as:

  • backups
  • patching
  • storage management
  • monitoring
  • Multi-AZ options
  • recovery mechanisms

Your application shouldn't normally depend on a PostgreSQL container running alongside it in ECS for a production system.

13.2

Why ElastiCache Instead of Redis Container?

Same concept.

Development:

Docker Compose ├── Node ├── PostgreSQL └── Redis

Production:

ECS ↓ Node.js │ └──→ ElastiCache Redis

AWS manages the Redis infrastructure.

13.3

Production Network Design

A more realistic design:

INTERNET │ ↓ Internet Gateway │ Public Subnets │ ALB │ ┌─────────────┴─────────────┐ │ │ Private Subnet Private Subnet │ │ ECS Task 1 ECS Task 2 │ │ └─────────────┬─────────────┘ │ ┌─────┴─────┐ ↓ ↓ RDS PostgreSQL ElastiCache Private Subnet Private Subnet

This gives you a strong separation:

Public ↓ ALB Private ↓ Application Private ↓ Database / Redis
13.4

Production Security Groups

A clean setup could be:

Internet │ ↓ ALB Security Group │ │ 443 ↓ ECS Security Group │ ├── 5432 ↓ RDS Security Group ECS Security Group │ ├── 6379 ↓ Redis Security Group

Meaning:

Internet → ALB ALB → ECS ECS → PostgreSQL ECS → Redis

But:

Internet → PostgreSQL ❌ Internet → Redis ❌ Internet → ECS:3000 ❌

That is a much better production network model.

13.5

Production Deployment Flow

Eventually your workflow should look like:

Developer │ ↓ Git Push │ ↓ CI/CD │ ├── npm test ├── Docker build ├── Security scan └── Docker push │ ↓ ECR │ ↓ ECS Deployment │ ┌──────┴──────┐ ↓ ↓ Old Tasks New Tasks │ │ │ Health Check │ ↓ │ Healthy ✅ │ │ └──────→ Traffic moves to v2

That is the production-level direction you should eventually learn.
