Docker Compose — Full Guide

Interview notes & cheat sheet — what Compose is, when to use it, commands, and how it compares to plain Docker.

What & Why Examples Commands & Internals Dev vs Prod Interview Q&A
💡 Core idea: Docker manages containers individually. Docker Compose manages multiple related containers as one application stack. Everything you do with Compose can be done with normal docker commands — Compose just makes multi-service setups far easier.
🔑 Key Ideas at a Glance
📄
compose.yaml: Declarative description of services, networks, volumes, env vars, ports, and dependencies.
🚀
docker compose up -d: One command starts the entire application stack (network + containers).
🧩
Multi-container: Best when you have Backend + Postgres + Redis + Frontend (or similar) that belong together.
🔁
up vs run: docker run = one container; docker compose up = whole stack from config.
🧹
down vs stop: stop keeps containers; down stops and removes containers + network.
🏭
Production: Compose is great for local/dev; production often moves to ECS, Kubernetes, or similar.
1. What is Docker Compose & When to Use It

Without Compose vs With Compose

Without Compose you manually manage each container:

manual docker
docker network create my-network

docker run -d --name postgres \
  --network my-network \
  -e POSTGRES_PASSWORD=1234 \
  postgres

docker run -d --name backend \
  --network my-network \
  -p 3000:3000 \
  my-backend

You have to remember: container names, networks, environment variables, ports, volumes, images, and startup order.

With Compose you describe everything in compose.yaml:

compose.yaml
services:
  postgres:
    image: postgres
    environment:
      POSTGRES_PASSWORD: 1234

  backend:
    image: my-backend
    ports:
      - "3000:3000"
    depends_on:
      - postgres

Then one command starts everything:

terminal
docker compose up -d
Compose creates and manages the required containers and network automatically.

When should you use Compose?

The biggest reason is multiple related containers. Example application stack:

Your Application | ┌───────────┴───────────┐ ↓ ↓ Backend Frontend | ┌─────┴─────┐ ↓ ↓ Postgres Redis

That’s 4 containers: frontend, backend, postgres, redis.

Without Compose you run several docker run ... commands and configure everything manually.

With Compose:

terminal
docker compose up -d

One command starts the whole application stack.

Can we do everything without Compose?

Yes. Compose is convenience and orchestration for a group of containers, not a separate runtime.

ComposeNormal Docker equivalent
docker compose updocker run (for each service)
docker compose downdocker stop + docker rm
docker compose restartdocker restart
docker compose stopdocker stop
docker compose startdocker start
docker compose execdocker exec
docker compose logsdocker logs
docker compose psdocker ps
docker compose builddocker build
docker compose pulldocker pull
The important difference: Compose manages a group of containers as one application.
2. Practical Examples

Single application container — Compose not needed

Suppose you have a Node.js app image already built:

terminal
docker build -t my-node-app:1.0 .

docker run -d \
  --name my-node-container \
  -p 3000:3000 \
  my-node-app:1.0
For a single simple container, normal Docker commands are perfectly fine. You do not need Compose.

Node.js + PostgreSQL — without Compose

Two containers that need to talk to each other:

without-compose
# 1. Create a shared network
docker network create app-network

# 2. Run PostgreSQL
docker run -d \
  --name postgres \
  --network app-network \
  -e POSTGRES_PASSWORD=1234 \
  postgres

# 3. Run Node app
docker run -d \
  --name backend \
  --network app-network \
  -p 3000:3000 \
  my-node-app:1.0

Your Node app can connect to postgres:5432 because both containers are on the same Docker network. This works completely without Compose.

Same stack with Compose

Instead of remembering all those commands, create compose.yaml:

compose.yaml
services:
  backend:
    image: my-node-app:1.0
    ports:
      - "3000:3000"
    depends_on:
      - postgres

  postgres:
    image: postgres
    environment:
      POSTGRES_PASSWORD: 1234

Then:

terminal
docker compose up -d
That’s the major benefit — one declarative file + one command for the whole stack.

Why Compose becomes really useful

Imagine a larger project:

  • Frontend
  • Backend
  • PostgreSQL
  • Redis
  • Nginx
  • Adminer

Without Compose you need many docker run commands and must remember ports, networks, volumes, env vars, names, images, and dependencies.

With Compose:

terminal
docker compose up -d     # start the whole stack
docker compose down         # stop and tear down the stack
3. Commands, Internals & Key Differences

What does docker compose up actually do?

Given a file with several services, Compose roughly:

Read compose.yaml ↓ Create network ↓ Pull/build required images ↓ Create containers ↓ Configure networking ↓ Configure volumes ↓ Configure environment variables ↓ Start containers

So Compose is essentially an orchestration / configuration tool for your local Docker application stack.

docker compose up vs docker run

docker run — “Create and start this one container.”

terminal
docker run -d --name redis redis

docker compose up — “Read my application configuration and create/start all the required services.”

terminal
docker compose up -d

docker compose down vs docker stop

Normal Docker

terminal
docker stop backend     # stops the container; it still exists
docker ps -a            # you can still see it
docker start backend    # start it again

Compose

terminal
docker compose down      # stops AND removes Compose-managed containers + network
docker compose up -d    # creates/starts them again

Compose command reference

compose commands
docker compose up                       # start all services
  -d        detached (run in background)
  --build   rebuild images before starting

docker compose down                     # stop and remove containers/networks
  -v          also remove named volumes
  --rmi all   also remove images

docker compose restart <service>       # restart a single service

docker compose stop / start <service>  # stop/start without removing

docker compose exec <service> sh        # shell into a running service
  (no -it needed — interactive by default in Compose)

docker compose logs                     # view logs for all services
  -f            follow live
  <service>     logs for just one service

docker compose ps                       # list services and their status

docker compose build                    # rebuild images
  --no-cache    ignore build cache

docker compose config                   # validate and print the resolved config

docker compose pull                     # pull images for all services

4. Development vs Production & Learning Path

Why developers use Compose

Mainly for development and testing. A typical company stack:

React ↓ Node.js ↓ PostgreSQL ↓ Redis

A new developer joins. Instead of “install Postgres, install Redis, configure ports, create databases, set passwords…”, you give them:

terminal
docker compose up -d

All required development services are running.

Is Compose used in production?

It can be, but the common distinction is:

Local development — very common:

Docker Compose ↓ Backend + Postgres + Redis + Frontend

Production — often moves to:

  • AWS ECS
  • Kubernetes
  • Docker Swarm
  • Other cloud platforms

Example AWS path you may already know:

Docker image ↓ ECR ↓ ECS ↓ ECS Task ↓ Container

You don’t need Docker Compose to run that ECS container.

Simple rule of thumb

SituationWhat to use
One container (e.g. single Node.js API)docker run
Multiple containers that belong to one appdocker compose up
Production container orchestrationECS / Kubernetes / similar

Recommended learning path

1. Docker Images ↓ 2. Docker Containers ↓ 3. docker run ↓ 4. Ports ↓ 5. Volumes ↓ 6. Networks ↓ 7. Environment variables ↓ 8. Dockerfile ↓ 9. Docker Compose ↓ 10. Docker Registry / ECR ↓ 11. ECS ↓ 12. Production deployment
Compose is the next level after you’re comfortable running individual containers. Key concept: Docker manages containers individually. Docker Compose manages multiple related containers as one application stack.
Interview Q&A
💡 Interview Q&A — Docker Compose
Core Concepts
Is Docker Compose mandatory?
No. Everything you do with Compose can generally be done with normal docker commands. Compose mainly makes it easier when your application has multiple containers/services that need to work together.
What is Docker Compose in one sentence?
Compose is a tool that lets you define and run multi-container Docker applications using a declarative YAML file (compose.yaml), so you can start/stop the whole stack with single commands like docker compose up and docker compose down.
When should you use Compose vs plain docker run?
Use plain docker run for a single simple container. Use Compose when you have multiple related containers (backend + database + cache + frontend, etc.) that form one application stack and share networks, volumes, and dependencies.
Commands & Behavior
What’s the difference between docker compose up and docker run?
docker run creates and starts one container. docker compose up reads your Compose file and creates/starts all the services defined there (plus the network and any other shared resources).
What’s the practical difference between docker compose down and docker compose stop?
stop halts the containers but leaves them (and their networks) in place so you can start them again. down stops and also removes the containers and the Compose-managed network. Add -v to also remove named volumes, or --rmi all to also remove images.
Why doesn’t docker compose exec need -it the way docker exec usually does?
Compose’s exec is interactive and allocates a TTY by default, because shelling into a running service is a very common workflow. Plain docker exec requires you to opt in explicitly with -it.
How do you see logs only for one service in a Compose project?
docker compose logs <service> scopes output to that service. Add -f to follow live.
Architecture & Production
Can you run a multi-container app without Compose?
Yes. Create a network with docker network create, then run each container with docker run --network ..., set env vars, ports, and volumes yourself. Compose just automates and centralizes that configuration.
Is Docker Compose used in production?
It can be used in production for simpler setups, but many teams use it primarily for local development and testing, then deploy with ECS, Kubernetes, Docker Swarm, or a cloud platform’s orchestration for production.
What does docker compose up do under the hood (high level)?
It reads compose.yaml, creates the project network, pulls or builds images, creates the containers, wires networking/volumes/env vars, and starts the services (respecting depends_on where defined).
Practical / Coding
Write a minimal compose.yaml for a Node API + Postgres.
compose.yaml
services:
  backend:
    image: my-node-app:1.0
    ports:
      - "3000:3000"
    depends_on:
      - postgres

  postgres:
    image: postgres
    environment:
      POSTGRES_PASSWORD: 1234
How would you fully tear down a Compose project including volumes and images?
teardown
docker compose down -v --rmi all
docker compose ps          # confirm nothing left from this project

-v removes named volumes; --rmi all removes the images used by the services. Prefer this over a broad docker system prune when you only want to clean one project.
