1.1 What Problem Does Docker Actually Solve?

Start with the problem, not the tool. A running application is never just source code. A Node.js API is really a stack of dependencies that all have to line up correctly at the same time:

Your application code ↓ needs A specific Node.js version ↓ needs Installed npm packages (exact versions) ↓ some of which need Native OS libraries (e.g. for bcrypt, sharp, canvas) ↓ needs Correct runtime configuration (port, env vars, working user)

Historically, every layer in that stack was installed independently, directly on whatever machine happened to be running the app — your laptop, a teammate's laptop, the CI runner, the production server. Nobody coordinated those installs. That's the root cause of the most famous sentence in software:

"It works on my machine!"

This isn't a joke about clumsy developers — it's the predictable outcome of every machine assembling its own version of the stack independently. Two people can both say "I have Node installed" and still be running incompatible environments.

A concrete example, side by side:

Your machineTeammate's machine
Node1820
PostgreSQL1615
CacheRedis 7Redis 6
OSUbuntuWindows

None of these differences are exotic edge cases — they're the default state of two independently-configured machines. And each one can break your app in a specific, realistic way:

  • A package with native bindings compiled for Node 18 crashes when loaded under Node 20.
  • A migration using a SQL feature only present in Postgres 16 fails silently — or loudly — on Postgres 15.
  • Windows line endings, path separators, or a missing Linux-only binary break a script that "always worked" on Linux/macOS.
  • A Redis command you rely on locally (Redis 7) doesn't exist yet in CI's Redis 6, so tests pass locally and fail in the pipeline.

Docker's core idea is deceptively simple: instead of assembling the stack separately on every machine, you package the app together with everything it needs — Node version, dependencies, OS libraries, and config — into one self-contained, portable unit called a container.

┌───────────────────────────────┐ │ Container │ │ │ │ Node.js runtime │ │ Your application code │ │ npm dependencies │ │ Required OS libraries │ │ Runtime configuration │ │ │ └───────────────────────────────┘

The container carries its own consistent environment wherever it goes. The host machine underneath — your laptop, a Windows box, an ECS instance — can be completely different. It doesn't matter, because the application never actually touches the host's Node install, the host's Postgres client libraries, or the host's OS packages. It only sees what's inside the container.

Without Docker

Every machine independently installs Node, npm packages, OS libraries, and config. Any mismatch between machines is a live bug waiting to surface — often only in production, which is the worst possible place to discover it.

With Docker

The environment is defined once, as code (a Dockerfile), and packaged into an image. Every machine runs the exact same image. There is nothing left to "independently install" — it's already baked in.

What Docker deliberately does not do — worth being precise about this, because overclaiming leads to confusion later:

  • It is not a programming language, framework, or replacement for Node.js — you still write and run Node code, Docker just standardizes how it's packaged and executed.
  • It is not a virtual machine (the distinction is important enough to get its own section — 1.2).
  • It does not automatically make an application production-ready. You still design the Dockerfile, environment variables, networking, and health checks yourself.
  • It does not replace the database itself. Postgres running inside a container is still ordinary Postgres — Docker just packages and isolates the process running it.

The mental model to carry forward:

Write Node.js code ↓ Describe how to run it (Dockerfile) ↓ Build an image (a frozen snapshot of "everything it needs") ↓ Run a container (a live process started from that snapshot) ↓ Same app behaves identically everywhere
The single idea to remember: Docker packages the application plus its entire runtime environment, so the app stops depending on whatever happens to already be installed on whichever machine runs it.
1.2 Docker vs Virtual Machine

This is the concept most people get wrong the first time they hear "container," because the natural assumption is "a container is just a tiny, fast virtual machine." That mental model is wrong, and it causes confusion later on (especially around security and isolation), so it's worth slowing down here.

A virtual machine virtualizes hardware. A hypervisor (VirtualBox, VMware, Hyper-V, KVM) sits between the physical machine and each guest, and every guest boots a complete, independent operating system on top of it — its own kernel, its own init system, its own package manager, its own set of users.

Physical Server │ ├── Host OS │ ├── VM 1 │ ├── Guest OS (full kernel + init) │ └── Application │ ├── VM 2 │ ├── Guest OS (full kernel + init) │ └── Application │ └── VM 3 ├── Guest OS (full kernel + init) └── Application

Because each VM owns a complete OS, isolation between VMs is extremely strong — strong enough that a Windows guest can run on top of a Linux host. But that strength has a real cost: every VM has to boot its own kernel, which is slow and heavy.

Virtual MachineContainer
Startup timeTens of seconds to minutes (full OS boot)Milliseconds to a few seconds (just starts a process)
Disk footprintGigabytes (full OS + app)Megabytes to a few hundred MB (app + libraries only)
KernelIts own dedicated guest kernelShares the host's kernel
Isolation strengthVery strong — hardware-level boundaryStrong process isolation, but a lighter boundary than a VM
Density per hostA handful of VMsDozens to hundreds of containers

A container, by contrast, virtualizes the process environment, not the hardware. Every container on a host shares one thing in common: the host's kernel. There's no guest OS to boot at all.

Physical Server │ ├── Host OS │ ├── Docker Engine │ ├── Container 1 │ └── Node.js Application │ ├── Container 2 │ └── PostgreSQL │ └── Container 3 └── Redis

This is exactly why you can run an API, a Postgres instance, and a Redis instance on your laptop as three containers without ever booting three operating systems — they are three isolated processes, all running on top of the one kernel your laptop already has.

How does Docker get isolation without a separate kernel per container? Three specific Linux kernel features do the work:

namespaces — what a process is allowed to see

Namespaces isolate a process's view of the system: its own process ID space (so it can't see other containers' processes), its own network stack, its own mounted filesystem, its own hostname, its own users. By default, one container simply cannot see into another container — not because of a permission check, but because it literally doesn't exist in that container's view of the world.

cgroups — how many resources a process may consume

Control groups cap how much CPU, memory, and I/O a container can use. This is what stops one runaway container from starving the entire host — a memory leak in one service doesn't take down every other container on the machine.

union filesystems — how images are stored efficiently

Images are built as stacked, read-only layers that can be shared across many containers, with a thin writable layer added on top for each running container. This is also what makes builds fast — unchanged layers get reused instead of rebuilt (more on this in Section 2).

On macOS and Windows, there's a subtlety worth knowing: Docker Desktop actually runs a small Linux VM in the background, and your containers run inside that VM, sharing its kernel. You still don't get a dedicated kernel per container — just one shared Linux kernel inside that one background VM.

The important distinction to hold onto: Docker containers are isolated processes, not miniature virtual machines. That has real consequences:

  • A container built for a Windows kernel cannot run directly on a Linux host (or vice versa) without a VM layered in between somewhere.
  • Because containers share a kernel, a kernel-level exploit is a theoretical risk across all containers on that host — a VM boundary is harder to break through than a container boundary. This is exactly why production practices like running containers as a non-root user and applying least-privilege matter (covered later in the security section).
  • You don't "log into an OS" inside a container the way you'd SSH into a VM. You're running a single process (or a small handful). docker exec -it container sh is a debugging convenience, not the normal way an application "lives" inside a container.

Reach for a VM when…

You genuinely need a different OS or kernel, very strong multi-tenant isolation between untrusted workloads, or you're running a full desktop/server environment rather than a single app process.

Reach for a container when…

You want to ship one application (or one service) bundled with its runtime, start it in milliseconds, and run many of them efficiently on the same host — the standard Node.js / Postgres / Redis situation.

The one-line version: a VM boots an operating system; a container starts a process. Containers share the host's kernel — that's the entire source of their speed and their (slightly weaker) isolation trade-off.
1.3 Docker Architecture

Docker is not one program — it's a client–server system. That single fact explains a lot of "why did this error happen" moments later, so it's worth being explicit about the three pieces involved and how they talk to each other.

Docker Registry (Docker Hub / Amazon ECR) ↑ │ pull / push │ ┌──────────────┐ │ │ Docker CLI │─────┤ │ │ │ │ docker run │ │ │ docker build │ │ │ docker pull │ │ └──────┬───────┘ │ │ API request over a Unix socket ↓ ┌──────────────────┐ │ Docker Daemon │ │ dockerd │ │ │ │ containers │ │ images │ │ networks │ │ volumes │ └──────────────────┘
  1. Docker CLI — the client. This is what you type: docker run, docker build, docker ps. Crucially, the CLI does not create containers itself — it packages your command into an API request and sends it somewhere else.
  2. Docker Daemon (dockerd) — the server. A long-running background process that actually owns and manages every image, container, network, and volume on the machine. This is "the brain" — all the real work happens here.
  3. Registry — remote storage for images, sitting outside your machine entirely. Docker Hub is the public default; Amazon ECR is a common private registry used inside AWS. The daemon is the one that talks to the registry over the network, not the CLI directly.

On Linux, the CLI and daemon typically communicate through a Unix socket:

/var/run/docker.sock

This client–server split explains one of the most common early error messages:

"Cannot connect to the Docker daemon" doesn't mean the CLI is broken — it means the server half (the daemon / Docker Desktop) isn't running. The client is perfectly fine; it just has nobody to talk to.

Tracing one command all the way through — this single example ties the whole architecture together:

bash
docker run nginx
You type: docker run nginx
↓
CLI sends an API request to dockerd
↓
Daemon checks: is the nginx image already local?
↓
If missing → pull it from the registry
↓
Daemon creates a container from the image
↓
Daemon starts the nginx process inside it

Four everyday commands map to four distinct jobs the daemon performs — worth memorizing this table, since it explains what's "actually happening" every time you type one of these:

CommandWho's involvedWhat actually happens
docker pulldaemon + registryDownloads image layers and stores them locally
docker builddaemonReads your Dockerfile + build context, produces a new image
docker rundaemonCreates and starts a container from an image (pulling first if it's missing)
docker pushdaemon + registryUploads your local image layers up to a registry

Note that you, as the user, never talk to the lower-level pieces (containerd, runc — covered next) directly. The daemon sits in front of them and orchestrates everything on your behalf.

The one-line version: docker in your terminal is a client, nothing more. The daemon is the actual worker that builds images and runs containers — the CLI just relays instructions to it.
1.4 Docker Engine

When people casually say "Docker is running," what they actually mean is "the Engine is running." But "Engine" is itself a stack of three distinct layers, not a single binary — and this layering exists for a real reason: container technology was standardized under the OCI (Open Container Initiative), so different tools could share the same low-level plumbing instead of each reinventing it.

Docker Engine │ ├── dockerd (high-level manager) │ ├── containerd (lifecycle supervisor) │ └── runc (actually starts the process)

Walking down the stack from the top:

dockerd — the high-level manager

This is the piece that exposes the API the CLI talks to, and it owns the concepts that are specifically Docker's: building images from Dockerfiles, handling docker network and docker volume, deciding when an image needs pulling, and keeping track of container metadata like names, ports, and restart policies. It doesn't do the actual low-level "create an isolated Linux process" work itself — it delegates that downward.

containerd — the lifecycle supervisor

Sitting beneath dockerd, this is a general-purpose container runtime — general enough that Kubernetes can (and often does) use it directly, without any Docker CLI involved at all. Its job: pull and store image content, create/start/stop/delete containers, and supervise the running processes — if a container's main process dies unexpectedly, containerd is the thing that notices. What it deliberately does not do is understand Docker-specific concepts like Compose files or the Dockerfile build syntax — that logic lives one layer up, in dockerd.

runc — the low-level runtime

This is the piece that finally touches the kernel. Given a config describing the root filesystem, which namespaces to use, and which cgroup limits apply, runc sets everything up and then execs the actual process — node src/server.js, nginx, whatever the image's CMD specifies. Once that process is launched, runc's job is essentially done and it exits; containerd is the one left watching the running process afterward.

Put together, the full call chain behind a single docker run looks like this:

docker CLI ↓ (API request) dockerd ↓ containerd ↓ runc ↓ Linux kernel (namespaces + cgroups applied) ↓ your process (node / nginx / postgres, actually running)

You'll almost never interact with containerd or runc directly as a developer — but understanding they exist explains a few real behaviors:

  • If the daemon restarts, already-running containers don't necessarily die with it, because their lifecycle is tracked one layer down in containerd, separate from the CLI/daemon connection.
  • Orchestrators like ECS/Fargate and Kubernetes don't all rely on the Docker CLI at all — but they still rely on the same underlying idea (an image, plus a runtime that starts an isolated process from it), often via containerd directly.
  • "Docker is installed but nothing runs" is almost always "the Engine/daemon isn't started" — not a missing or broken runc binary somewhere.
The one-line version: Engine = dockerd (API, images, networks, volumes) hands off to containerd (lifecycle tracking) which hands off to runc (actually starts the Linux process). You only ever talk to the CLI at the very top.
1.5 Docker CLI

The CLI is deliberately "thin" — almost every command follows the exact same pattern: parse the flags you typed → translate them into an API request → send that request to the daemon → print back whatever the daemon responds with. That consistency is valuable: the same commands behave identically whether you're pointed at Docker Desktop on your laptop, a remote daemon, or a CI runner — the language never changes, only where it's being sent.

bash
docker run nginx
docker ps
docker images
docker build -t myapp .
docker pull nginx
docker push myimage
docker stop mycontainer

Rather than memorizing commands individually, it helps to group them by what they operate on — this grouping is exactly the structure the rest of these notes (images, containers, networks, volumes, Compose) follows:

GroupCommandsOperates on
Imagespull build images rmi tag pushRead-only templates
Containersrun ps start stop rm exec logsRunning (or stopped) instances
Networksnetwork ls / create / connectHow containers talk to each other
Volumesvolume ls / create / rmPersistent data
Composedocker compose up / downAn entire multi-service application stack

Reading a real command, piece by piece:

docker run -d --name api -p 3000:3000 node-api │ │ │ │ │ │ │ │ │ │ │ └── the image to run │ │ │ │ └── map host port 3000 → container port 3000 │ │ │ └── give the container a name │ │ └── run detached (in the background) │ └── the verb: create + start a container └── the CLI client itself

Where Compose fits in this picture: it isn't a separate engine or a replacement for anything described above — docker compose is still just talking to the same daemon underneath. The difference is scope: plain docker commands work on one image, one container, one network, or one volume at a time; docker compose describes an entire group of services declaratively in YAML and manages them together. The daemon does the actual work either way.

A few habits worth building from day one:

  • docker --help and, more specifically, docker run --help — the meaning of a flag can change per command (-f means "force" on docker rm, but "follow" on docker logs).
  • If a command appears to hang the first time you run it, it's very often docker pull quietly downloading layers in the background — not a freeze.
  • "Cannot connect to the Docker daemon" always means the Engine isn't running yet — start Docker Desktop (or the daemon service) first, before troubleshooting anything else.
  • You don't need to memorize every flag up front. Later sections introduce flags in the context where they're actually used — treat the full command list as a lookup table, not something to cram.
The one-line version: the CLI is simply how humans talk to the daemon. Commands are organized around five things — images, containers, networks, volumes, and Compose — and that grouping is the map for everything that follows.
1.6 Image vs Container — the distinction that matters most

Every later topic — layers, Compose, ECS task definitions — becomes confusing if this single distinction stays fuzzy. Get this one fully solid before moving on.

Analogy
Programming conceptDocker equivalent
A class / blueprintAn image
An object / instanceA container
You can new() many objects from one classYou can run many containers from one image

Image — a read-only template

Take node:18-alpine as an example — it contains everything needed to run Node, packaged up. An image is made of:

  • A stacked, layered filesystem — OS files, the Node binary, your node_modules, your source code — each piece its own layer.
  • Metadata — the default command to run (CMD), which ports it expects to use, default environment variables, the working directory.
  • A name in the form repository:tag (e.g. node:18-alpine), or a content-addressed digest (@sha256:...).

Images never "run" on their own — they sit inert on disk (or up in a registry) until something creates a container from them. A critical fact worth repeating: deleting a container never deletes the image it was created from. Rebuilding with the same tag can move the tag to point at a new image, but any containers already created from the old image keep using that old image until you explicitly recreate them.

Container — a running (or created) instance

Image │ ├── Container 1 ├── Container 2 └── Container 3

When a container starts, Docker adds one more thing on top of all the image's read-only layers: a thin writable layer, unique to that container. Anything the running process writes — application logs to a file, temporary uploads, a crash dump — lands in that writable layer. It disappears the moment the container is removed, unless the data was explicitly routed into a volume instead (that's the whole subject of Section 6, Docker Storage).

One image, many independent containers — this is a genuinely common pattern, not a theoretical example:

bash
docker run --name api1 node:18-alpine
docker run --name api2 node:18-alpine
docker run --name api3 node:18-alpine

All three containers share the exact same underlying image — nothing about the image itself is duplicated three times. What can still differ between them is entirely runtime-level:

  • Different container names (api1 / api2 / api3)
  • Different published ports (-p 3001:3000 vs. -p 3002:3000)
  • Different environment variables (-e NODE_ENV=production)
  • Completely separate writable layers — files one container creates at runtime are invisible to the others

How the lifecycle relates to the image underneath it:

docker pull / docker build → image exists (read-only, untouched by anything below) ↓ docker run / docker create → a container is created from that image ↓ running ↓ docker stop → container stopped — image still sitting there, unaffected ↓ docker start → the very same container resumes, same writable layer as before ↓ docker rm → container is gone — image still sitting there ↓ docker rmi → image is finally removed (only works if no container still references it)

Note that docker run is really shorthand for "create, then start." That's exactly why beginners assume run is what "downloads nginx" — the very first time, yes, the daemon also has to pull the image because it isn't local yet. Every time after that, docker run nginx simply reuses the already-local image and creates one more independent container from it.

Seeing the difference live, on your own machine:

bash
docker images          # images  — the templates
docker ps -a           # containers — the instances (running AND stopped)

If docker ps comes back empty while docker images still lists nginx, nothing is broken — that's expected. You still have the blueprint sitting on disk; you simply don't currently have any running instance of it.

The one-line version — arguably the single most important sentence in these notes: an image is a read-only template; a container is a running instance of that template. One image can produce many containers. Stopping or removing a container never removes the image it came from.
1.7 Docker Hub / Registry

A registry is simply remote storage for images — the place images live before you have a local copy, and the place you push them to so others (or production infrastructure) can pull them down.

Docker Hub │ ├── nginx ├── node ├── postgres └── redis

When you run:

bash
docker pull nginx

the daemon reaches out to a registry (Docker Hub by default) and downloads that image's layers to your machine.

In an AWS-based setup, the equivalent private registry is:

Amazon ECR

A typical production flow looks like this — this is directly relevant if you're working with AWS/ECS:

Developer
↓
docker build
↓
Docker Image
↓
Amazon ECR
↓
ECS
↓
Container
1.8 Basic Practice

Run:

bash
docker run hello-world

Then check:

bash
docker ps

Nothing shows up — hello-world prints its message and exits immediately, so it's not "running" anymore by the time you check. Look for it here instead, which shows stopped containers too:

bash
docker ps -a

Now try something that actually stays running:

bash
docker run -d --name nginx-demo -p 8080:80 nginx

Check again:

bash
docker ps

Then open in a browser:

localhost:8080

That's a real Nginx container, running, reachable from your host — the image → container → port-mapping chain from this whole section, working end to end.
