1. What Problem Docker Solves & Docker vs VM

The "It Works on My Machine" Problem

★★★★★

A running application is never just source code — it's a stack of dependencies that all have to line up correctly at the same time: a specific runtime version, exact package versions, native OS libraries, and correct runtime configuration.

Application code
↓ needs
Specific runtime version (e.g. Node 18)
↓ needs
Installed packages, exact versions
↓ some need
Native OS libraries (bcrypt, sharp, canvas)
↓ needs
Correct runtime config — ports, env vars, user

Historically every layer was installed independently on whatever machine ran the app — your laptop, a teammate's laptop, CI, production. Nobody coordinated those installs. That mismatch is the entire root cause of "it works on my machine."

Your machineTeammate's machine
Node1820
PostgreSQL1615
CacheRedis 7Redis 6
OSUbuntuWindows

None of these are exotic edge cases — they're the default state of two independently-configured machines, and each can break the app in a specific way: native bindings compiled for the wrong Node version, a SQL feature missing on an older Postgres, Windows-only path/line-ending issues, or a Redis command that doesn't exist yet in CI.

❌ Without Docker

Every machine independently installs the runtime, packages, OS libraries, and config. Any mismatch is a live bug waiting to surface — often only in production.

✅ With Docker

The environment is defined once, as code (a Dockerfile), and packaged into an image. Every machine runs the exact same image — nothing left to independently install.

⚠️ Docker is not a language, a VM replacement, or something that makes an app production-ready on its own. It doesn't replace Postgres either — Postgres in a container is still ordinary Postgres, just packaged and isolated.

Docker vs Virtual Machine

The common wrong mental model is "a container is just a tiny, fast VM." A VM virtualizes hardware — every guest boots a complete OS with its own kernel. A container virtualizes the process environment — every container shares the host's kernel, with no guest OS boot at all.

Virtual MachineContainer
Startup timeTens of seconds to minutesMilliseconds to a few seconds
Disk footprintGigabytesMegabytes to a few hundred MB
KernelIts own dedicated guest kernelShares the host's kernel
Isolation strengthVery strong — hardware-levelStrong process isolation, lighter boundary
Density per hostA handful of VMsDozens to hundreds of containers

Three Linux kernel features give containers isolation without a separate kernel per container:

  • namespaces — isolate what a process can see: its own PID space, network stack, filesystem, hostname, users.
  • cgroups — cap how much CPU, memory, and I/O a container can consume, so one runaway container can't starve the host.
  • union filesystems — images are stacked, read-only layers shared across containers, with a thin writable layer per running container.
💡 On macOS/Windows, Docker Desktop runs a small Linux VM in the background — your containers run inside that VM, sharing its one kernel. You still don't get a dedicated kernel per container.

Reach for a VM when…

You need a different OS/kernel, very strong multi-tenant isolation, or a full desktop/server environment.

Reach for a container when…

You want to ship one app bundled with its runtime, start it in milliseconds, and run many efficiently on one host.

🚨 Because containers share a kernel, a kernel-level exploit is a theoretical risk across all containers on that host — a stronger reason than usual to run containers as non-root with least privilege.
2. Docker Architecture & the Engine

Client–Server Architecture

★★★★★

Docker is not one program — it's a client–server system with three pieces:

  1. Docker CLI — the client. Packages your command (docker run, docker build) into an API request; it never creates containers itself.
  2. Docker Daemon (dockerd) — the server. A long-running process that actually owns and manages every image, container, network, and volume.
  3. Registry — remote image storage outside your machine (Docker Hub, Amazon ECR). The daemon talks to it, not the CLI directly.
⚠️ "Cannot connect to the Docker daemon" doesn't mean the CLI is broken — it means the server half (the daemon / Docker Desktop) isn't running yet.
You type: docker run nginx
↓
CLI sends an API request to dockerd
↓
Daemon checks: is the nginx image already local?
↓
If missing → pull it from the registry
↓
Daemon creates a container from the image
↓
Daemon starts the nginx process inside it
CommandWho's involvedWhat happens

Docker Engine — dockerd → containerd → runc

"The Engine" is a stack of three layers, standardized under the OCI (Open Container Initiative) so different tools can share the same low-level plumbing.

docker CLI
↓ API request
dockerd — high-level manager (images, networks, volumes, builds)
↓
containerd — lifecycle supervisor (pull, create, start, stop, watch)
↓
runc — low-level runtime (touches the kernel, execs the process)
↓
Linux kernel (namespaces + cgroups applied) → your process
  • dockerd exposes the CLI's API and owns Docker-specific concepts: building from Dockerfiles, docker network/volume, container metadata.
  • containerd is general-purpose enough that Kubernetes uses it directly with no Docker CLI involved — it pulls/stores images, manages container lifecycle, and notices if a process dies.
  • runc sets up namespaces/cgroups/rootfs from a config, then execs the real process and exits — containerd is left watching afterward.
💡 If the daemon restarts, already-running containers don't necessarily die with it — their lifecycle is tracked one layer down in containerd, separate from the CLI/daemon connection.
3. Docker CLI, Image vs Container & Registry

The CLI — Thin by Design

★★★★★

Almost every command follows the same pattern: parse flags → translate to an API request → send to the daemon → print the response. Commands group around five things:

Imagespull build images rmi tag pushRead-only templates

//   run      → create + start a container
//   -d       → detached (background)
//   --name   → name the container
//   -p 3000:3000 → map host port → container port
//   node-api → the image to run
💡 docker compose isn't a separate engine — it still talks to the same daemon. It just describes a whole group of services declaratively instead of one resource at a time.

Image vs Container — the Distinction That Matters Most

Analogy
Programming conceptDocker equivalent
A class / blueprintAn image
An object / instanceA container
You can new() many objects from one classYou can run many containers from one image

Image — a read-only template: stacked layered filesystem, metadata (CMD, ports, env, working dir), and a repository:tag name. Images never run on their own, and deleting a container never deletes the image it came from.

Container — a running (or created) instance. Starting one adds a thin, container-specific writable layer on top of the image's read-only layers. Anything the process writes lands there and disappears when the container is removed, unless it was routed into a volume.

one image, many containers
docker run --name api1 node:18-alpine
docker run --name api2 node:18-alpine
docker run --name api3 node:18-alpine

All three share the exact same image — nothing about it is duplicated. What differs is purely runtime-level: names, published ports, env vars, and each container's separate writable layer.

docker pull / build → image exists (read-only)
↓
docker run / create → container created from image
↓
docker stop → container stopped, image unaffected
↓
docker start → same container resumes, same writable layer
↓
docker rm → container gone, image still there
↓
docker rmi → image removed (only if no container still references it)
✅ docker run is shorthand for "create, then start." The very first run also pulls the image if it isn't local; every run after that just reuses it and creates a new independent container.

Interview Q&A
💡 Interview Q&A
Standard Questions
What problem does Docker actually solve?
It eliminates "works on my machine" bugs by packaging an application together with its entire runtime environment — language runtime, dependencies, OS libraries, and config — into one portable, self-contained unit, so every machine runs the exact same environment instead of independently assembling it.
What's the fundamental difference between a container and a virtual machine?
A VM virtualizes hardware and boots a full guest OS with its own kernel. A container virtualizes the process environment and shares the host's kernel via namespaces and cgroups — no separate OS boot, which is why containers start in milliseconds and are far lighter on disk.
What is the difference between a Docker image and a Docker container?
An image is a read-only template — layered filesystem plus metadata. A container is a running (or created) instance of that template, with its own thin writable layer on top. One image can produce many independent containers, and removing a container never removes the image it came from.
What are the three pieces of Docker's client-server architecture?
The Docker CLI (client, sends API requests), the Docker Daemon / dockerd (server, actually owns and manages images/containers/networks/volumes), and a registry (remote image storage like Docker Hub or Amazon ECR) that the daemon talks to.
What are the three layers of the Docker Engine, from top to bottom?
dockerd (high-level manager exposing the API and owning Docker-specific concepts), containerd (general-purpose lifecycle supervisor that pulls images and tracks running containers), and runc (the low-level OCI runtime that actually sets up namespaces/cgroups and execs the process).
Tricky / Follow-Up Questions
If Kubernetes doesn't use the Docker CLI, how can it still run containers?
Kubernetes talks to containerd (or another OCI-compatible runtime) directly, bypassing dockerd and the Docker CLI entirely. Since container standards are defined by the OCI, any orchestrator can drive the same underlying runtime without needing Docker's higher-level tooling.
Why doesn't restarting the Docker daemon kill already-running containers?
Container lifecycle is tracked by containerd, one layer below dockerd, not by the CLI-to-daemon connection itself. As long as containerd keeps running, containers it's supervising can survive a `dockerd` restart.
Why is container isolation considered weaker than VM isolation, and does that actually matter in practice?
Because all containers on a host share one kernel, a kernel-level exploit is a theoretical cross-container risk in a way that doesn't apply to VMs, which each have a separate kernel. In practice this is why production guidance emphasizes running containers as non-root and applying least-privilege — the isolation is strong for normal workloads but not as absolute as a hardware-level VM boundary.
If you delete a container, is the data it wrote gone forever?
Yes, unless that data was explicitly routed into a volume. Anything written to the container's own writable layer — logs, temp files, uploads — disappears the moment the container is removed, since that writable layer belongs only to that container instance.
Frequently Asked
Why does docker run hello-world disappear from docker ps almost immediately?
hello-world prints a message and exits right away — its process is done, so it's no longer "running." docker ps only shows running containers; docker ps -a shows stopped ones too, where it will still appear.
What does the error "Cannot connect to the Docker daemon" actually mean?
It means the server half of Docker — dockerd / Docker Desktop — isn't running, not that the CLI itself is broken. The CLI has nothing to send its API requests to until the daemon starts.
On macOS or Windows, do containers share your machine's actual kernel?
Not directly — Docker Desktop runs a small Linux VM in the background, and your containers run inside that VM, sharing its one Linux kernel. You still don't get a dedicated kernel per container; there's just one extra VM layer involved compared to native Linux.
Coding / Theoretical
Given the command docker run -d --name api -p 3000:3000 node-api, trace exactly what happens end to end.
trace
// 1. CLI parses flags and sends an API request to dockerd
// 2. dockerd checks whether the 'node-api' image is already local
//    - if missing, it pulls it from the configured registry first
// 3. dockerd delegates to containerd to create a container from the image
// 4. containerd hands off to runc, which sets up namespaces + cgroups
//    and execs the image's CMD (e.g. node server.js) inside them
// 5. runc exits once the process is launched; containerd keeps watching it
// 6. -d means the container runs detached (in the background)
// 7. -p 3000:3000 maps host port 3000 to container port 3000
// 8. --name api gives the running container the name "api"

Why this shape: each flag maps to a distinct, independently-understandable piece of the request — naming, networking, and run mode are all orthogonal to which image is used or how the process actually gets started at the kernel level.

Explain, in three layers, why "one image, many containers" is safe and efficient rather than risky or wasteful.
Each layer of the design supports this: the image's layers are read-only, so multiple containers can share the exact same underlying files on disk without any risk of one container's writes corrupting another's view of the image. Each container gets its own thin writable layer, so runtime changes (logs, temp files) are fully isolated per container even though they all started from identical content. And because containers are isolated processes via namespaces, each one gets its own PID space, network stack, and filesystem view, so running many containers from one image is closer to running many independent instances of a program than to "sharing" a single mutable environment.
