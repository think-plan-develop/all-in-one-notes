💡 Important framing: -d (detached/background) and -f (force / follow, depending on command) show up across almost every command group. Flag meaning can shift by context — always check --help when unsure.
🔑 Key Terms at a Glance
🖼️
-t (build): Tags the built image with a name:tag so it can be referenced later.
🎛️
-d: Runs a container (or Compose stack) detached, in the background.
⚡
-f: Context-dependent — "force" on rm/rmi, "follow" on logs.
🛑
stop vs kill: stop sends SIGTERM then SIGKILL after a timeout; kill sends SIGKILL immediately.
🧹
prune: Removes unused resources — add --volumes with real caution, it can delete persistent data.
🧩
Compose: Same daemon underneath, just scoped to a whole multi-service stack instead of one resource at a time.
1. Images & Containers

Images — Pull, Build, List, Tag, Inspect

images
docker pull <image>              # download an image

docker build -t name:tag .       # build image from Dockerfile
  -t             tag the image with a name:tag
  --no-cache     rebuild ignoring cache
  -f <file>      use a different Dockerfile

docker images                     # list local images

docker rmi <image>               # remove an image
  -f             force remove even if in use

docker tag <image> new:tag       # add a tag to an image

docker history <image>          # show image layers

docker inspect <image>          # full image metadata

🔍 Deep dive: docker build -t name:tag . — see exactly what each part means and how . / .. / a subfolder path changes what Docker can see.
1
-t name:tag — names the image, like labeling a file. name is the image name (e.g. myapp), tag is the version label (e.g. v1, latest). If you skip the tag, Docker defaults to :latest.
2
. at the end is the build context — the folder Docker looks in for the Dockerfile and any files (source code, configs) it needs to copy into the image. . = current folder, .. = parent folder, or you can point at any path like myapp/.
3
A Dockerfile must exist inside whichever folder you point to. Docker will not search outside that folder — it can only read files from inside the build context.

Example 1 — terminal already inside the project folder

myapp/ ├── Dockerfile ├── app.py └── requirements.txt
from inside myapp/
docker build -t myapp:v1 .

myapp:v1 → name is myapp, tag is v1. . → build context is the current folder, so Docker finds the Dockerfile right there.

Example 2 — terminal is one level above the project

projects/ └── myapp/ ├── Dockerfile ├── app.py └── requirements.txt
from inside projects/
docker build -t myapp:v1 myapp/

Point at myapp/ directly — not . (that would be projects/, with no Dockerfile) and not .. (that would go further up, away from the Dockerfile).

Example 3 — using -f for a differently-named Dockerfile

custom dockerfile
docker build -t myapp:v1 -f Dockerfile.prod .

Context (.) stays the same, but -f Dockerfile.prod tells Docker to use that file instead of the default Dockerfile.

Example 4 — ignoring the build cache

no-cache
docker build -t myapp:v1 --no-cache .

Docker normally reuses unchanged layers from previous builds (faster). --no-cache forces every step to rerun — useful when you suspect a stale cached layer is causing a bug.

PartRole
-t name:tagnames/labels the resulting image
. / .. / path/the build context — where Docker looks for the Dockerfile + files
-f <file>overrides which file is treated as the Dockerfile
--no-cacheforces every build step to rerun, ignoring cached layers
✅ Rule of thumb: the path at the end of docker build is always "where do I look for the Dockerfile and files," never "where does the output go." The output is the image itself, stored in Docker's internal image store and referenced later by the name:tag you gave it with -t.

Containers — Run, List, Start, Stop, Kill, Remove

containers
docker run <image>               # create + start a container
  -d                 detached (background, prints container ID)
  -it                interactive + allocate a terminal (for shells)
  --rm               auto-remove container when it stops
  -p 8080:80         map host:container ports
  -e KEY=value       set an environment variable
  --env-file .env    load env vars from a file
  --name myapp       give it a custom name
  -v vol:/data       attach a volume or bind mount
  --network mynet    attach to a specific network
  --restart=always   restart policy

docker ps                          # list running containers
  -a    show all (including stopped)
  -q    only show container IDs (useful in scripts)

docker start <id>                # start a stopped container
  -a    attach to its output
  -i    interactive

docker stop <id>                 # gracefully stop (SIGTERM, then SIGKILL after timeout)
  -t <sec>   custom timeout before force-kill

docker restart <id>              # stop then start again

docker kill <id>                 # force stop immediately (SIGKILL)

docker rm <id>                   # remove a stopped container
  -f    force remove even if running
  -v    also remove associated anonymous volumes
CommandWhat it does
docker run <image>create + start a container
docker pslist running containers
docker start <id>start a stopped container
docker stop <id>gracefully stop (SIGTERM, then SIGKILL after timeout)
docker restart <id>stop then start again
docker kill <id>force stop immediately (SIGKILL)
docker rm <id>remove a stopped container
🔍 Deep dive: container commands with examples — running, listing, starting, stopping, killing, and removing, worked through one container.

Example 1 — docker run: start an nginx web server

run
docker run -d --name webserver -p 8080:80 nginx

-d runs it in the background and prints a container ID. --name webserver lets you refer to it by name instead of that ID. -p 8080:80 maps port 8080 on your machine to port 80 inside the container, so http://localhost:8080 reaches nginx.

Example 2 — docker run: env vars, a volume, and a network

run with env + volume
docker run -d --name db \
  -e POSTGRES_PASSWORD=secret \
  -v pgdata:/var/lib/postgresql/data \
  --network mynet \
  --restart=always \
  postgres

-e POSTGRES_PASSWORD=secret sets a config value the postgres image reads on startup. -v pgdata:/var/lib/postgresql/data attaches a named volume so the database's data survives even if the container is removed. --network mynet puts it on a custom network so other containers (like an app container) can reach it by name. --restart=always means Docker restarts it automatically after a crash or reboot.

Example 3 — docker run -it --rm: a throwaway interactive shell

interactive + auto-remove
docker run -it --rm ubuntu bash

-it gives you an interactive terminal attached to the container (type commands, see output live). --rm deletes the container the moment you exit the shell — nothing left lying around. Great for quickly poking around inside an image without cluttering docker ps -a.

Example 4 — docker ps: listing containers

ps
docker ps                    # only shows the running webserver + db containers
docker ps -a                 # also shows the exited ubuntu container from Example 3
docker stop $(docker ps -q)  # -q gives just IDs, so this stops every running container

Example 5 — docker start: restarting a stopped container

start
docker start webserver       # starts it again in the background
docker start -a -i webserver  # starts it and attaches your terminal to its output/input

Unlike docker run, start doesn't create a new container — it resumes the existing one with the same name, config, and any data in its writable layer.

Example 6 — docker stop vs docker kill

stop vs kill
docker stop webserver          # SIGTERM, waits 10s default, then SIGKILL if still up
docker stop -t 30 webserver    # give it 30s to shut down gracefully before force-kill
docker kill webserver          # SIGKILL immediately, no grace period

Use stop for normal shutdowns (lets nginx finish in-flight requests). Reach for kill only when a container is unresponsive and stop isn't working.

Example 7 — docker restart

restart
docker restart webserver   # equivalent to stop + start, e.g. after editing a config volume

Example 8 — docker rm: cleaning up containers

rm
docker rm webserver        # fails if webserver is still running
docker rm -f webserver     # force: kills it first, then removes it — no graceful shutdown
docker rm -v webserver     # also deletes any anonymous volumes it created (named volumes are kept)
CommandTypical use
docker run -d -p ... --name ...launch a long-running service (web server, database)
docker run -it --rm ...one-off interactive debugging, nothing left behind
docker ps -a -qscript-friendly listing to pipe into stop/rm
docker start -a -iresume a stopped container and watch/interact with it
docker stop -t <sec>graceful shutdown with a custom grace period
docker killlast resort when a container won't respond to SIGTERM
docker rm -f -vforce-delete a container and its anonymous volumes together
⚠️ Watch out: docker rm -f skips the graceful SIGTERM window entirely — it's the same abruptness as kill, just followed immediately by deletion. Prefer stop then rm for anything that should shut down cleanly.

Interview Q&A
💡 Interview Q&A
Standard Questions
What's the difference between docker stop and docker kill?
docker stop sends a SIGTERM first, giving the process a chance to shut down gracefully, then follows up with SIGKILL if it hasn't stopped after a timeout (customizable via -t). docker kill skips straight to SIGKILL, terminating the process immediately with no cleanup opportunity.
What's the difference between docker rm and docker rmi?
docker rm removes a container (an instance). docker rmi removes an image (the template). A container must generally be stopped and removed before its image can be removed, unless you force it.
Why does -f mean different things on different commands?
Docker's flags are defined per-command rather than globally, so short flags get reused for different but locally sensible meanings — -f is "force" on rm/rmi/system prune, but "follow" on logs. Always check --help for the specific command when the meaning isn't obvious.
What does --rm do on docker run, and when is it useful?
It auto-removes the container as soon as it stops, instead of leaving a stopped container sitting around. Useful for short-lived, one-off tasks (like running a script or a quick debug shell) where you don't need to inspect the container afterward.
In docker build -t name:tag ., what exactly is the . for, and what happens if I use .. instead?
The trailing path is the build context — the folder Docker scans for the Dockerfile and any files it needs to copy into the image. . means "current folder"; .. means "parent folder." Whichever one you pick, a Dockerfile must exist directly inside it, or the build fails with "unable to find Dockerfile." Switching to .. only makes sense if your Dockerfile actually lives one level up from where you're standing — it doesn't change where the built image is stored, only where Docker looks for source material.
Tricky / Follow-Up Questions
If you run docker rm -f <id> on a running container, does the process get a graceful shutdown chance?
No — the -f force flag on rm effectively kills the container immediately (SIGKILL-equivalent) before removing it, skipping the graceful SIGTERM period that a plain docker stop would give it.
Why would docker system prune -a --volumes be dangerous to run casually?
It removes not just dangling images but every unused image, plus every unused volume — including named volumes holding persistent data like a database's files, if nothing is currently using them. Running it without checking what's actually unused can silently delete data you meant to keep.
Why doesn't docker compose exec need -it the way docker exec usually does?
Compose's exec is interactive and allocates a TTY by default, since shelling into a running service is such a common workflow in Compose-based development. Plain docker exec requires you to explicitly opt in with -it for the same interactive behavior.
What's the difference between docker image prune and docker image prune -a?
Without -a, only dangling images — untagged images left behind by rebuilds — are removed. With -a, every image not currently referenced by any container is removed, including tagged images you might still want to keep around for later use.
Frequently Asked
How do you see logs only for one service in a Compose project?
docker compose logs <service> scopes the output to just that service instead of interleaving logs from the whole stack; add -f to follow it live.
What does docker ps -q return, and why is that useful in scripts?
Just the container IDs, with no other columns — useful for piping into other commands, e.g. docker stop $(docker ps -q) to stop every running container in one line.
What's the practical difference between docker compose down and docker compose stop?
stop halts the containers but leaves them (and their networks) in place, ready to be started again with start. down stops and also removes the containers and networks entirely — add -v to also remove named volumes, or --rmi all to also remove the images.
If your Dockerfile is named Dockerfile.prod instead of Dockerfile, how do you build with it?
Keep the same build context but point Docker at the file explicitly: docker build -t myapp:v1 -f Dockerfile.prod .. The . still tells Docker where to look for source files; -f just overrides which file it treats as the build instructions.
Coding / Theoretical
Write a one-off cleanup sequence to fully tear down a Compose project including its volumes and images, and confirm nothing's left running.
teardown.sh
# stop and remove containers, networks, named volumes, and images
docker compose down -v --rmi all

# confirm nothing from this project is still running
docker compose ps

# optional broader cleanup of anything left dangling on the host
docker system prune -f

Why this order: compose down -v --rmi all is scoped precisely to this project's resources, so it's the safe first step. Only after confirming with compose ps would you reach for a broader system prune, since that command isn't scoped to one project and could remove unrelated unused resources too.

Explain, in three layers, why Docker separates "stop" (graceful), "kill" (immediate), and "rm" (deletion) into distinct commands rather than one combined action.
Each command addresses a different concern: stop exists because most real processes need a chance to flush buffers, close connections, or finish an in-flight request before exiting — SIGTERM gives them that window. kill exists for the case where a process is hung or graceful shutdown isn't working, and you need it gone immediately regardless of cleanup. rm is separate from both because a stopped container might still be useful to inspect (its logs, its exit code, its filesystem state) — deleting it is a distinct, deliberate decision from merely stopping it, which is exactly why rm -f requires an explicit force flag to skip straight from "running" to "gone."
