Normalization is a database design technique used to organize data into multiple related tables to reduce data duplication, avoid data inconsistency, and maintain data integrity.

In simple words: normalization means dividing a large table into smaller, logically related tables and connecting them using Primary Keys and Foreign Keys. It is an important concept in database design and is frequently asked in SQL interviews.
1. Why do we need Normalization?

Consider an orders table. Before normalization:

order_idcustomer_namecustomer_cityproduct_nameprice
101RahulHyderabadLaptop50000
102RahulHyderabadMouse1000
103AmitMumbaiKeyboard2000
104RahulHyderabadMonitor15000
  • Rahul’s name is repeated three times.
  • Rahul’s city is repeated three times.
  • Customer information is mixed with order information.
  • Updating customer information requires updating multiple records.

Three anomalies

AnomalyExample
1. Update anomalyRahul moves from Hyderabad to Bangalore. You need to update all three records; if you update only two, the database holds inconsistent information.
2. Insert anomalyA new customer, Priya, registers but hasn’t placed an order. You cannot insert her easily if the table requires an order_id.
3. Delete anomalyAmit’s only order is deleted. You may accidentally lose Amit’s customer information as well.
Solution: normalization. Separate customer, order, and product information into different tables.

There are several normal forms. The most important ones for practical SQL development:

3. First Normal Form (1NF)

Rule: every column should contain a single (atomic) value. No multiple values in a single cell and no repeating groups.

Not in 1NF

student_idstudent_namesubjects
1RahulJava, SQL
2AmitReact, Node
3PriyaPython, SQL

Problem: the subjects column contains multiple values in one cell.

In 1NF

student_idstudent_namesubject
1RahulJava
1RahulSQL
2AmitReact
2AmitNode
3PriyaPython
3PriyaSQL

Now every cell contains a single value. PostgreSQL example:

student_subjects.sql
CREATE TABLE student_subjects (
    student_id INT,
    student_name VARCHAR(100),
    subject VARCHAR(100)
);
Remember: one cell = one value. No comma-separated multiple values. No repeating columns such as subject1, subject2, subject3.
4. Second Normal Form (2NF)

Rule: the table must already be in 1NF, and every non-key column must depend on the entire candidate key, not just a part of a composite key.

A composite key is a primary key created using two or more columns. Consider student_courses:

student_id (PK)course_id (PK)student_namecourse_name
1101RahulJava
1102RahulSQL
2101AmitJava

The composite primary key is (student_id, course_id). Problem: student_name depends only on student_id, and course_name depends only on course_id. Neither depends on the entire composite key — this is called a partial dependency.

Convert into 2NF

Students

course_id (PK)course_name

Student Courses

student_id (FK)course_id (FK)
1101
1102

  • Student name depends on student ID.
  • Course name depends on course ID.
  • The relationship between students and courses uses both keys.
Remember: 2NF removes partial dependency.
Interview point: if a table has a single-column candidate key, it cannot have a partial dependency on a composite key, so if it is already in 1NF, it is automatically in 2NF.
5. Third Normal Form (3NF)

Rule: the table must already be in 2NF, and there should be no transitive dependency between non-key attributes. Consider an employee table:

employee_id (PK)employee_namedepartment_iddepartment_name
1Rahul101IT
2Amit102HR
3Priya101IT
employee_id→department_id→department_name

The department name depends on the department ID, not directly on the employee ID. This is called transitive dependency.

Convert into 3NF

Employees

employee_id (PK)employee_namedepartment_id (FK)
1Rahul101
2Amit102
3Priya101

Departments

department_id (PK)department_name
101IT
102HR

PostgreSQL implementation:

3nf.sql
CREATE TABLE departments (
    department_id INT PRIMARY KEY,
    department_name VARCHAR(100)
);

CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name VARCHAR(100),
    department_id INT REFERENCES departments(department_id)
);
Remember: 3NF removes transitive dependency.
Memory aid: every non-key column should depend on the key, the whole key, and nothing but the key. (A simplified aid, particularly useful when learning 2NF and 3NF.)
6. BCNF (Boyce-Codd Normal Form)

BCNF is a stronger version of 3NF. Rule: for every non-trivial functional dependency, the determinant must be a superkey. In simpler terms, every column (or combination) that determines another column must be capable of uniquely identifying a row.

Student_Instructor

student_idinstructorcourse
1AmitJava
2AmitJava
3RahulSQL
  • Each instructor teaches only one course.
  • A student can study under multiple instructors.
  • A student-instructor combination uniquely identifies a row.

Dependencies: (student_id, instructor) → course and instructor → course. Here instructor determines course, but instructor alone is not a superkey. This violates BCNF.

Remember: BCNF removes certain remaining dependency problems that 3NF can allow.
7. Fourth Normal Form (4NF)

Rule: the table must be in BCNF and should not contain independent multivalued dependencies. Consider a student who has multiple skills and multiple hobbies:

student_details

student_idskillhobby
1JavaCricket
1JavaMusic
1SQLCricket
1SQLMusic

Student 1 has two skills (Java, SQL) and two hobbies (Cricket, Music). Skills and hobbies are independent of each other, which creates unnecessary combinations.

Convert into 4NF

Student_Skills

student_idskill
1Java
1SQL

Student_Hobbies

student_idhobby

Remember: 4NF removes independent multivalued dependencies.
8. Fifth Normal Form (5NF)

Rule: the table must be in 4NF and should not contain join dependencies that can be further decomposed without losing information. It deals with complex relationships where information can be split into smaller tables and reconstructed through joins.

Example: a company works with suppliers, products and projects. A combined table may contain:

supplierproductproject
S1LaptopP1
S1MouseP1
S2LaptopP2

In certain cases this can be decomposed into three smaller relationship tables: Supplier_Products, Supplier_Projects and Product_Projects. The decomposition is valid only when the original relationship can be reconstructed exactly through joins without introducing extra combinations.

Remember: 5NF handles complex join dependencies and is relatively uncommon in everyday application database design.
9. All Normal Forms — Comparison
Normal formMain purpose
1NFRemove multiple values in a cell
2NFRemove partial dependency

5NFRemove non-trivial join dependencies

Normalization progression

1NF: atomic values→2NF: no partial dependency→3NF: no transitive dependency→BCNF → 4NF → 5NF: stronger dependency rules
10. Normalization in real-world projects

How normalization is used in an actual e-commerce application built with Node.js, React and PostgreSQL. A poorly designed database might have one table:

orders

order_idcustomer_namecustomer_emailproduct_nameproduct_price
1Rahulrahul@gmail.comLaptop50000
2Rahulrahul@gmail.comMouse1000

Instead, you create separate tables:

TableColumns
customerscustomer_id (PK), customer_name, email
ordersorder_id (PK), customer_id (FK), order_date
productsproduct_id (PK), product_name, price
order_itemsorder_item_id (PK), order_id (FK), product_id (FK), quantity, price_at_purchase

Why this structure?

  1. Customer details are stored once.
  2. Products can be reused across multiple orders.
  3. An order can contain multiple products.
  4. Updating a customer’s email doesn’t require updating every order.
  5. Order history remains available even if the current product price changes.
Notice price_at_purchase: it is intentionally stored in order_items because product prices may change later. We need to preserve the historical price paid by the customer.

Does normalization affect JOIN queries?

Yes. Since data is distributed across multiple tables, we use JOINs to retrieve complete information.

join.sql
SELECT
    o.order_id,
    c.customer_name,
    p.product_name,
    oi.quantity,
    oi.price_at_purchase
FROM orders o
JOIN customers c
    ON o.customer_id = c.customer_id
JOIN order_items oi
    ON o.order_id = oi.order_id
JOIN products p
    ON oi.product_id = p.product_id;
11. Normalization vs Denormalization

These two concepts are opposites in terms of their main goals.

NormalizationDenormalization
Reduces duplicate dataMay introduce duplicate data
Uses multiple related tablesCombines or duplicates data
Improves data consistencyCan improve read performance
Requires JOINsMay reduce JOIN requirements
Common in transactional databasesCommon in reporting and read-heavy systems

When do we use denormalization?

Suppose an application has millions of orders and frequently needs to display the customer name, order count and total order amount. Instead of calculating everything through multiple JOINs for every request, we might maintain a summary table or materialized view. This can improve read performance, but requires additional logic to keep the duplicated or aggregated data updated.

Industry practice: start with a well-normalized design, then denormalize selectively when actual performance requirements justify it.
