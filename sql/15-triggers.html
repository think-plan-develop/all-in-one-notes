A trigger in PostgreSQL is a database mechanism that automatically executes a function when a specific event occurs on a table or view. You don’t call a trigger manually — PostgreSQL executes it automatically when the configured event happens.

1. Why do we use Triggers?

Triggers are mainly used to automate database operations. Common use cases:

Use caseWhat it does
Audit logsTrack who updated or deleted a record and when.
Automatic timestampsUpdate updated_at whenever a record changes.
Data validationPrevent invalid data from being inserted.
Business logicAutomatically update related records.
History trackingMaintain old and new values of records.
2. Types of Triggers

PostgreSQL supports triggers based on different events.

TriggerWhen it executes
INSERTWhen a new record is inserted
UPDATEWhen an existing record is updated
DELETEWhen a record is deleted
TRUNCATEWhen a table is truncated

Based on execution timing

TypeDescription
BEFOREExecutes before the operation
AFTERExecutes after the operation
INSTEAD OFExecutes instead of the operation (views)

Based on execution level

TypeDescription
FOR EACH ROWExecutes for every affected row
FOR EACH STATEMENTExecutes once per SQL statement
3. Trigger Function

In PostgreSQL, a trigger requires a function to execute. A trigger function must return TRIGGER.

update_timestamp.sql
CREATE OR REPLACE FUNCTION update_timestamp()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.updated_at = CURRENT_TIMESTAMP;

    RETURN NEW;
END;
$$;

Important concepts

  • NEW: contains the new record (INSERT/UPDATE).
  • OLD: contains the existing record (UPDATE/DELETE).
  • RETURN NEW: returns the new record.
  • RETURN OLD: returns the old record.
4. Create a Trigger

Suppose we have an employees table.

employees.sql
CREATE TABLE employees (
    employee_id SERIAL PRIMARY KEY,
    employee_name VARCHAR(100),
    salary NUMERIC(10,2),
    updated_at TIMESTAMP
);

Create a trigger:

trigger.sql
CREATE TRIGGER employee_update_trigger
BEFORE UPDATE
ON employees
FOR EACH ROW
EXECUTE FUNCTION update_timestamp();

Now update an employee:

update.sql
UPDATE employees
SET salary = 80000
WHERE employee_id = 1;
PostgreSQL automatically executes the trigger before updating the record and updates updated_at. You don’t need to call the trigger function yourself.
5. OLD vs NEW

This is one of the most important concepts in triggers.

OperationOLDNEW
INSERTNot availableNew record
UPDATEPrevious recordUpdated record
DELETEDeleted recordNot available

Example: validate salary

check_salary.sql
CREATE OR REPLACE FUNCTION check_salary()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    IF NEW.salary < 0 THEN
        RAISE EXCEPTION 'Salary cannot be negative';
    END IF;

    RETURN NEW;
END;
$$;

Create trigger:

salary_validation.sql
CREATE TRIGGER salary_validation
BEFORE INSERT OR UPDATE
ON employees
FOR EACH ROW
EXECUTE FUNCTION check_salary();

Now:

insert.sql
INSERT INTO employees(employee_name, salary)
VALUES ('Rahul', -5000);
Error: PostgreSQL prevents the insertion because the salary is negative.
6. Real Industry Example — Audit Log

Suppose an organization wants to track every salary change. Whenever an employee’s salary changes, automatically store the old salary, new salary, and change date in an audit table.

Step 1 — create audit table

employee_audit.sql
CREATE TABLE employee_audit (
    audit_id SERIAL PRIMARY KEY,
    employee_id INT,
    old_salary NUMERIC(10,2),
    new_salary NUMERIC(10,2),
    changed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

Step 2 — create trigger function

log_salary_change.sql
CREATE OR REPLACE FUNCTION log_salary_change()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO employee_audit (
        employee_id,
        old_salary,
        new_salary
    )
    VALUES (
        OLD.employee_id,
        OLD.salary,
        NEW.salary
    );

    RETURN NEW;
END;
$$;

Step 3 — create trigger

salary_audit_trigger.sql
CREATE TRIGGER salary_audit_trigger
AFTER UPDATE
ON employees
FOR EACH ROW
WHEN (OLD.salary IS DISTINCT FROM NEW.salary)
EXECUTE FUNCTION log_salary_change();

Step 4 — update salary

update.sql
UPDATE employees
SET salary = 90000
WHERE employee_id = 1;

Step 5 — check audit log

check.sql
SELECT * FROM employee_audit;

Example result:

employee_idold_salarynew_salary
17000090000
The audit record is inserted automatically.
7. How a Trigger Works Internally
Application executes UPDATE employees SET salary = 90000→PostgreSQL detects trigger event→Trigger function executes: stores old and new salary→Audit table gets updated
8. Function vs Trigger vs Stored Procedure
FeatureFunctionTriggerProcedure
ExecutionCalled explicitlyAutomaticallyCalled explicitly
PurposeReusable logicAutomatic event handlingBusiness operations
ReturnMust return a value or voidTrigger function returns TRIGGERNo return value required
Can execute independently?YesNoYes
Common useCalculations, fetching dataAudit logs, validationComplex workflows
Remember: Function = you call it. Trigger = the database calls it automatically. Procedure = you call it to execute a set of operations, potentially including transaction control.
9. Useful Trigger Commands
commands.sql
-- List triggers
SELECT *
FROM information_schema.triggers;

-- Delete trigger
DROP TRIGGER salary_audit_trigger ON employees;

-- Delete trigger function
DROP FUNCTION log_salary_change();

-- Disable trigger
ALTER TABLE employees
DISABLE TRIGGER salary_audit_trigger;

-- Enable trigger
ALTER TABLE employees
ENABLE TRIGGER salary_audit_trigger;
10. Important Industry Points
  1. Triggers execute inside the transaction that caused them. If the transaction rolls back, trigger changes also roll back.
  2. Avoid putting heavy business logic inside triggers because they can affect application performance.
  3. Triggers can execute other database operations, including INSERT, UPDATE and DELETE.
  4. Be careful with recursive triggers and triggers that modify the same table.
  5. Use AFTER triggers for audit logging and BEFORE triggers for validation or modifying incoming data.
Recommendation: understand BEFORE, AFTER, OLD, NEW, FOR EACH ROW, and WHEN thoroughly. These are the most useful concepts when working with PostgreSQL triggers in real projects.
