Triggers

Automatic actions that fire on INSERT, UPDATE, DELETE or TRUNCATE. They run a function before or after the event — or instead of it on a view.

1 What is a Trigger? & Why do we use Triggers?
A trigger is an automatic event listener on a table. When data changes, the trigger fires and runs your function — you never call it yourself, so it can't be forgotten.

Q: What is a trigger in PostgreSQL and why do we use it?

A: A trigger is a database mechanism that automatically executes a function in response to a data change event (INSERT, UPDATE, DELETE) on a table. Triggers are used for audit trails, auto-timestamps, validation and business rules at the database layer — guaranteeing the logic runs regardless of which application or user modifies the data.

🧠 Analogy: A trigger is a motion-sensor light. Nobody flips the switch — the sensor notices movement (a data change) and turns the light on by itself, every single time, no matter who walked in.

2 Trigger Types — BEFORE · AFTER · INSTEAD OF · INSERT / UPDATE / DELETE

Timing — when does it fire?

⏮️ BEFORE Trigger

Fires before the row is written. Can modify NEW or cancel the operation.

Use for: validation, auto-fill fields, normalising data.

RETURN NEW → allow (with modified values)
RETURN NULL → silently cancel

⏭️ AFTER Trigger

Fires after the row is written. Cannot change the row. Can read OLD and NEW.

Use for: audit logging, notifications, updating related tables.

Return value is ignored — RETURN NULL is fine.

🔄 INSTEAD OF Trigger

Fires instead of the operation. Works only on views — makes a non-updatable view accept INSERT / UPDATE / DELETE by redirecting to the base tables.

Use for: making complex views updatable.

Event — what does it fire on?

📥 INSERT Trigger

Fires when a row is inserted.

NEW = the row being inserted
OLD = NULL (nothing existed before)

Use: auto-fill created_at, generate slugs, queue a welcome-email job in an outbox table.

✏️ UPDATE Trigger

Fires when a row is updated.

NEW = row with new values
OLD = row with old values

Use: auto-set updated_at, audit what changed, protect certain fields.

🗑️ DELETE Trigger

Fires when a row is deleted.

NEW = NULL (nothing coming in)
OLD = the row being deleted

Use: soft-delete, custom cascade logic, archive deleted rows.

3 How to Create a Trigger — Trigger Function + CREATE TRIGGER
📌 Two-step process. In PostgreSQL a trigger is always created in two steps:
Step 1 — create a trigger function that returns TRIGGER
Step 2 — create the trigger that binds that function to a table and event

Step 1 — Trigger Function

✅ A trigger function must: take no parameters (it receives NEW / OLD automatically), return TRIGGER, and be written in PL/pgSQL (or another procedural language — plain sql can't be a trigger function).
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at := NOW();   -- modify the new row before saving
  RETURN NEW;                -- MUST return NEW (or NULL to cancel)
END;
$$;
-- Audit log trigger function
CREATE OR REPLACE FUNCTION log_user_changes()
RETURNS TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO audit_log (
    table_name, action, old_data, new_data, changed_at, changed_by
  ) VALUES (
    TG_TABLE_NAME,           -- auto-variable: which table
    TG_OP,                   -- auto-variable: INSERT / UPDATE / DELETE
    to_jsonb(OLD),           -- old row as JSON (NULL on INSERT)
    to_jsonb(NEW),           -- new row as JSON (NULL on DELETE)
    NOW(),
    current_user
  );
  RETURN COALESCE(NEW, OLD); -- works for INSERT, UPDATE and DELETE
END;
$$;

Step 2 — CREATE TRIGGER

-- Syntax
CREATE TRIGGER trigger_name
  { BEFORE | AFTER | INSTEAD OF }
  { INSERT | UPDATE [ OF column ] | DELETE | TRUNCATE } [ OR ... ]
  ON table_name
  [ FOR EACH ROW | FOR EACH STATEMENT ]
  [ WHEN (condition) ]
  EXECUTE FUNCTION function_name();


-- ✅ Auto-set updated_at on every UPDATE
CREATE TRIGGER trg_users_updated_at
  BEFORE UPDATE ON users
  FOR EACH ROW
  EXECUTE FUNCTION set_updated_at();


-- ✅ Audit log on INSERT, UPDATE, DELETE
CREATE TRIGGER trg_users_audit
  AFTER INSERT OR UPDATE OR DELETE ON users
  FOR EACH ROW
  EXECUTE FUNCTION log_user_changes();


-- ✅ WHEN condition — only fire if email changed
CREATE TRIGGER trg_email_change
  AFTER UPDATE ON users
  FOR EACH ROW
  WHEN (OLD.email IS DISTINCT FROM NEW.email)
  EXECUTE FUNCTION notify_email_change();
-- Manage triggers
ALTER TABLE users DISABLE TRIGGER trg_users_audit;   -- pause
ALTER TABLE users ENABLE  TRIGGER trg_users_audit;   -- resume
DROP TRIGGER IF EXISTS trg_users_audit ON users;     -- delete

-- List all triggers on a table
SELECT trigger_name, event_manipulation, action_timing, action_orientation
FROM   information_schema.triggers
WHERE  event_object_table = 'users';
💡 EXECUTE FUNCTION needs PostgreSQL 11+ (older versions use EXECUTE PROCEDURE). From PostgreSQL 14 you can also write CREATE OR REPLACE TRIGGER to redefine a trigger without dropping it first.
4 How Triggers Work — NEW · OLD · FOR EACH ROW · FOR EACH STATEMENT

NEW and OLD records

🟢 NEW — the incoming row

  • ✅ Available in INSERT triggers (the row being inserted)
  • ✅ Available in UPDATE triggers (row with new values)
  • ❌ NULL in DELETE triggers (nothing coming in)
  • 💡 BEFORE trigger: you can modify NEW before saving
  • NEW.column_name to read / write any field
  • RETURN NEW → save the row (with your changes)
  • RETURN NULL → cancel the operation (BEFORE only)

🟠 OLD — the existing row

  • ✅ Available in UPDATE triggers (row before change)
  • ✅ Available in DELETE triggers (row being deleted)
  • ❌ NULL in INSERT triggers (nothing existed before)
  • 💡 Read-only — you can't modify OLD
  • OLD.column_name to read previous values
  • Used for: audit logging, detecting what changed
  • OLD.email IS DISTINCT FROM NEW.email → email changed?
-- Using NEW to auto-fill fields (BEFORE INSERT)
CREATE OR REPLACE FUNCTION before_insert_user()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  NEW.email      := LOWER(NEW.email);   -- normalize email case
  NEW.created_at := NOW();              -- auto-fill timestamp
  NEW.slug       := LOWER(REPLACE(NEW.name, ' ', '-'));
  RETURN NEW;    -- return modified row — this is what gets saved
END; $$;


-- Using OLD and NEW to detect changes (AFTER UPDATE)
CREATE OR REPLACE FUNCTION after_update_status()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  IF OLD.status IS DISTINCT FROM NEW.status THEN   -- NULL-safe compare
    INSERT INTO status_history(order_id, from_status, to_status, changed_at)
    VALUES (NEW.id, OLD.status, NEW.status, NOW());
  END IF;
  RETURN NEW;
END; $$;


-- Using OLD in BEFORE DELETE to block the delete
CREATE OR REPLACE FUNCTION before_delete_order()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  IF OLD.status = 'paid' THEN
    RAISE EXCEPTION 'Cannot delete a paid order (id=%)', OLD.id;
  END IF;
  RETURN OLD;   -- BEFORE DELETE: return OLD to allow it (NEW is NULL here!)
END; $$;
⚠️ Common bug: in a BEFORE DELETE trigger NEW is NULL. Writing RETURN NEW there returns NULL and silently cancels every delete. Return OLD — or COALESCE(NEW, OLD) in a function shared by several events.

FOR EACH ROW vs FOR EACH STATEMENT

📍 FOR EACH ROW

Fires once per affected row. UPDATE 500 rows → the trigger fires 500 times.

✅ Has NEW and OLD for that specific row
✅ Can modify individual rows (BEFORE only)
⚠️ 500 updated rows = 500 trigger calls

Use for: per-row logging, per-row validation, auto-fill fields.

📦 FOR EACH STATEMENT

Fires once per SQL statement, however many rows changed. UPDATE 500 rows → 1 call.

❌ No NEW / OLD row variables
✅ Much faster for bulk operations
✅ Ideal for cache invalidation, one notification

Use for: bulk side effects, cache invalidation.

-- FOR EACH ROW — fires per row (has NEW/OLD)
CREATE TRIGGER trg_row_level
  AFTER UPDATE ON orders
  FOR EACH ROW                    -- ← fires once per updated row
  EXECUTE FUNCTION log_order_change();

-- FOR EACH STATEMENT — fires once per query (no NEW/OLD)
CREATE TRIGGER trg_stmt_level
  AFTER UPDATE ON orders
  FOR EACH STATEMENT              -- ← fires once regardless of rows affected
  EXECUTE FUNCTION invalidate_order_cache();

-- Practical difference:
UPDATE orders SET status = 'shipped' WHERE created_at < '2024-01-01';
-- affects 50,000 rows
-- FOR EACH ROW       → trigger fires 50,000 times ← potentially slow!
-- FOR EACH STATEMENT → trigger fires 1 time       ← fast
💡 A statement-level trigger has no NEW / OLD, but on PostgreSQL 10+ it can still see every changed row through transition tables:
CREATE TRIGGER trg_orders_bulk
  AFTER UPDATE ON orders
  REFERENCING OLD TABLE AS old_rows NEW TABLE AS new_rows
  FOR EACH STATEMENT
  EXECUTE FUNCTION log_bulk_update();
-- inside log_bulk_update():  SELECT COUNT(*) FROM new_rows;
5 Performance & Best Practices — Production Use Cases

🔴 Use case 1 — Auto updated_at timestamp

CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END; $$;

CREATE TRIGGER trg_users_updated_at
  BEFORE UPDATE ON users
  FOR EACH ROW
  EXECUTE FUNCTION set_updated_at();

-- Apply the same trigger function to multiple tables
CREATE TRIGGER trg_orders_updated_at
  BEFORE UPDATE ON orders
  FOR EACH ROW
  EXECUTE FUNCTION set_updated_at();   -- reuse the same fn!

🔴 Use case 2 — Full audit log

CREATE TABLE audit_log (
  id         SERIAL PRIMARY KEY,
  table_name TEXT,
  action     TEXT,
  old_data   JSONB,
  new_data   JSONB,
  changed_at TIMESTAMPTZ DEFAULT NOW(),
  changed_by TEXT DEFAULT current_user
);

CREATE OR REPLACE FUNCTION audit_trigger_fn()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO audit_log(table_name, action, old_data, new_data)
  VALUES (
    TG_TABLE_NAME, TG_OP,
    CASE WHEN TG_OP = 'INSERT' THEN NULL ELSE to_jsonb(OLD) END,
    CASE WHEN TG_OP = 'DELETE' THEN NULL ELSE to_jsonb(NEW) END
  );
  RETURN COALESCE(NEW, OLD);
END; $$;

CREATE TRIGGER trg_users_audit
  AFTER INSERT OR UPDATE OR DELETE ON users
  FOR EACH ROW
  EXECUTE FUNCTION audit_trigger_fn();

🟡 Use case 3 — Validation: block an invalid state

CREATE OR REPLACE FUNCTION validate_order_status()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  -- Block delete of paid orders
  IF TG_OP = 'DELETE' AND OLD.status = 'paid' THEN
    RAISE EXCEPTION 'Cannot delete paid order id=%', OLD.id;
  END IF;
  -- Prevent rolling back from 'paid' to 'pending'
  -- (check TG_OP first: NEW is NULL during a DELETE)
  IF TG_OP = 'UPDATE' AND OLD.status = 'paid' AND NEW.status = 'pending' THEN
    RAISE EXCEPTION 'Cannot revert a paid order to pending';
  END IF;
  RETURN COALESCE(NEW, OLD);
END; $$;

CREATE TRIGGER trg_order_validation
  BEFORE UPDATE OR DELETE ON orders
  FOR EACH ROW
  EXECUTE FUNCTION validate_order_status();

🟡 Use case 4 — Soft delete: turn DELETE into UPDATE

CREATE OR REPLACE FUNCTION soft_delete_user()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  UPDATE users
  SET    deleted_at = NOW(), active = FALSE
  WHERE  id = OLD.id;
  RETURN NULL;   -- cancel the real DELETE — the row stays, just flagged
END; $$;

CREATE TRIGGER trg_soft_delete
  BEFORE DELETE ON users
  FOR EACH ROW
  EXECUTE FUNCTION soft_delete_user();
⚠️ Soft delete must RETURN NULL. Returning OLD lets the DELETE carry on — the row would be flagged and then physically deleted anyway. This is a BEFORE trigger on a table; INSTEAD OF only exists for views.

Performance & safety checklist

PracticeWhy
Use WHEN (...) to skip needless callsThe condition is checked before the function runs — no function-call cost for rows that don't match
Prefer FOR EACH STATEMENT for bulk workOne call instead of one per row
Know the firing orderSeveral triggers on the same event run alphabetically by trigger name — name them deliberately
Avoid trigger loopsA trigger that updates its own table re-fires itself; guard with pg_trigger_depth() = 0 or a WHEN clause
Index the audit tableAudit tables grow fast — index table_name and changed_at, and partition or archive old rows
Keep the function shortIts cost is paid on every write to the table
6 Advantages & Disadvantages of Triggers

✅ Advantages

  • 🔒
    Guaranteed execution — fires for every INSERT/UPDATE/DELETE, whichever app, ORM or user makes the change. Can't be bypassed by normal DML.
  • 📋
    Automatic audit logging — track every data change (who, what, when) without touching app code.
  • ⏱️
    Auto-timestamps — updated_at stays accurate even for manual SQL and data migrations.
  • 🛡️
    Data integrity at DB level — rules survive ORM changes, API changes and developer mistakes.
  • ♻️
    Reusable logic — one trigger function can serve many tables (e.g. set_updated_at).
  • 🔌
    Decoupled — the app needn't know about audit logging, timestamps or cascades.

❌ Disadvantages

  • 👻
    Hidden side effects — a simple INSERT triggers an audit row, a notification and an update elsewhere; new developers can't see it in app code.
  • 🐢
    Performance overhead — FOR EACH ROW on a 100k-row UPDATE = 100k trigger calls.
  • 🐛
    Hard to debug — errors surface as errors in the DML statement, with confusing context. Harder to test than app code.
  • 🔄
    Trigger cascades — a trigger updates table B, whose trigger updates table C. An invisible chain that's hard to trace.
  • 🧩
    Logic in two places — some rules in the app, some in triggers: split brain about where rules live.
  • 📦
    Migration risk — triggers may be missing from ORM migration files, so a fresh clone behaves differently.

✅ Golden rules: Keep trigger functions short and fast — do one thing. Never put complex business logic or external calls in triggers. Use triggers for timestamps, audit logs and simple validation; use application code for emails, API calls and complex workflows. Document your triggers — they're invisible to the app layer and will surprise future developers.
