1️⃣  INNER JOIN
INNER JOIN
Only the overlapping rows — both sides must have a match

Returns only rows that match in BOTH tables. If a row exists in the left table but not the right (or vice versa), it is excluded entirely.

✅ One-liner "Give me only the rows that exist on both sides." — Ravi disappears. Order 104 disappears.
inner_join.sql
SELECT u.name, o.id AS order_id, o.total
FROM   users  u
INNER JOIN orders o ON o.user_id = u.id;

🎯 Use when You only want rows that have a valid match. Most common join (~70% of real queries). Default when you write plain JOIN.
2️⃣  LEFT JOIN  (LEFT OUTER JOIN)
LEFT JOIN
All of left table. Right side = NULL where no match

Returns ALL rows from the left table, and the matching rows from the right. Where no match exists in the right table, those columns are filled with NULL.

✅ One-liner "Give me everyone from the left table, and attach right-table data where it exists." — Ravi appears with NULL totals.
left_join.sql
SELECT u.name, o.id AS order_id, o.total
FROM   users  u
LEFT JOIN orders o ON o.user_id = u.id;

-- BONUS: Anti-join — find users with ZERO orders
SELECT u.name
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE  o.id IS NULL;   -- only Ravi

🧠 Anti-join pattern LEFT JOIN … WHERE right.id IS NULL → finds rows in the left table that have no match at all in the right. Classic "find users with no orders."
🎯 Use when You need every row from the left regardless of whether the right side has data. Second most common (~25%).
3️⃣  RIGHT JOIN  (RIGHT OUTER JOIN)
RIGHT JOIN
All of right table. Left side = NULL where no match

Returns ALL rows from the right table + matching rows from the left. The mirror image of LEFT JOIN. Where no match exists on the left, left columns are NULL.

✅ One-liner "Give me every order — even orphan ones with no user." — Order 104 (user_id=99) now appears with NULL user data.
right_join.sql
SELECT u.name, o.id AS order_id, o.total
FROM   users  u
RIGHT JOIN orders o ON o.user_id = u.id;

-- Identical result using LEFT JOIN (flip table order):
SELECT u.name, o.id AS order_id, o.total
FROM   orders o
LEFT JOIN users u ON u.id = o.user_id;

⚠️ Avoid in practice RIGHT JOIN is redundant. Any RIGHT JOIN can be rewritten as a LEFT JOIN by swapping the table order. Most teams ban RIGHT JOIN in code reviews for readability. Always flip to LEFT JOIN.
4️⃣  FULL OUTER JOIN
FULL OUTER JOIN
Every row from both tables. NULLs on whichever side has no match

Returns every row from BOTH tables. Where there's a match, rows are combined. Where there's no match on either side, that side's columns are NULL. Both Ravi and Order 104 appear.

✅ One-liner "Give me everything from both tables — match where possible, NULL where not." Nothing is excluded.
full_outer_join.sql
SELECT u.name, o.id AS order_id, o.total
FROM   users  u
FULL OUTER JOIN orders o ON o.user_id = u.id;

-- Find ALL mismatches on BOTH sides
SELECT u.name, o.id
FROM   users u
FULL OUTER JOIN orders o ON o.user_id = u.id
WHERE  u.id IS NULL OR o.id IS NULL;
-- Returns: Ravi (no orders) + Order 104 (no user)

-- MySQL doesn't support FULL OUTER JOIN — simulate it:
SELECT u.name, o.total FROM users u LEFT JOIN  orders o ON o.user_id = u.id
UNION
SELECT u.name, o.total FROM users u RIGHT JOIN orders o ON o.user_id = u.id;

5️⃣  CROSS JOIN  (Cartesian Product)
CROSS JOIN
Every row in A paired with every row in B. No ON condition.

Returns every possible combination of rows from both tables. No ON condition — every row in A is paired with every row in B. 3 users × 4 orders = 12 rows.

⚠️ Danger 1,000 rows × 1,000 rows = 1,000,000 rows. CROSS JOIN on large tables is a performance disaster. Only use it intentionally.
cross_join.sql
-- All size × color combinations for a product
SELECT s.size, c.color
FROM   sizes  s
CROSS JOIN colors c;

-- sizes:  S, M, L       (3 rows)
-- colors: Red, Blue     (2 rows)
-- Result: 6 rows → S-Red, S-Blue, M-Red, M-Blue, L-Red, L-Blue

-- CROSS JOIN has NO ON clause

6️⃣  SELF JOIN  (Table joined with itself)
SELF JOIN
One table, two aliases — join a row to another row in the same table

A table joined with itself using two different aliases. Used when a table has a self-referencing foreign key — like manager_id pointing back to employees.id.

📌 Not a new join type SELF JOIN is not a separate SQL keyword. It's just a regular INNER JOIN or LEFT JOIN where both sides reference the same table with different aliases.
self_join.sql
-- employees(id, name, manager_id)
-- manager_id → references employees.id (same table!)

-- LEFT JOIN so top-level manager (no manager_id) still shows
SELECT
  e.name  AS employee,
  m.name  AS manager
FROM  employees e
LEFT JOIN employees m ON m.id = e.manager_id;

-- Find employees earning more than their manager
SELECT e.name, e.salary, m.name AS manager, m.salary AS mgr_salary
FROM  employees e
INNER JOIN employees m ON m.id = e.manager_id
WHERE e.salary > m.salary;

📐 ANSI Joins — The Standard & Old Implicit Style

What is ANSI SQL?

ANSI (American National Standards Institute) published the SQL standard in 1986 and updated it in 1992 (SQL-92). The explicit JOIN … ON syntax is part of ANSI SQL-92. Before it, SQL used the old comma-join style.

📋 The two eras Pre-ANSI (old style) — comma-separated tables in FROM, conditions in WHERE.
ANSI SQL-92 (modern) — explicit JOIN … ON syntax, readable and safe.

Old Style — Implicit JOIN (comma syntax)

Before ANSI SQL-92, joins were written by listing tables separated by commas in the FROM clause. The join condition went into the WHERE clause.

old_implicit_join.sql
-- ❌ OLD STYLE — Implicit join (avoid in new code)

-- Two tables
SELECT u.name, o.total
FROM   users u, orders o
WHERE  o.user_id = u.id;

-- Three tables
SELECT u.name, o.total, d.name AS dept
FROM   users u, orders o, departments d
WHERE  o.user_id  = u.id
  AND  u.dept_id  = d.id
  AND  u.active   = 1;

-- ⚠️ Accidental CROSS JOIN if you forget the WHERE condition:
SELECT u.name, o.total
FROM   users u, orders o;
-- → 3 users × 4 orders = 12 rows (Cartesian explosion!)
⚠️ Why old style is dangerous If you accidentally forget one join condition in the WHERE clause, you silently get a Cartesian product (CROSS JOIN) — millions of rows, no error, wrong results. The ANSI style makes this impossible because the ON condition is attached to the JOIN itself.

ANSI Style — Explicit JOIN (modern standard)

ANSI SQL-92 introduced the JOIN … ON syntax. Every major database supports it. This is the only style you should write today.

ansi_explicit_join.sql
-- ✅ ANSI SQL-92 — Explicit JOIN (use this always)

-- Two tables
SELECT u.name, o.total
FROM   users  u
INNER JOIN orders o ON o.user_id = u.id;

-- Three tables — each JOIN has its own ON
SELECT
  u.name       AS user_name,
  o.total      AS order_total,
  d.name       AS department
FROM   users       u
INNER JOIN orders      o  ON  o.user_id = u.id
INNER JOIN departments d  ON  d.id      = u.dept_id
WHERE  u.active = 1
ORDER BY u.name;
