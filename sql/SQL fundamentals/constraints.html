🛡️ PostgreSQL Constraints – Complete Guide

Rules applied to table columns that control what data can be inserted, updated, or deleted — keeping your data accurate, consistent and reliable.

Constraint typesPRIMARY KEYFOREIGN KEYUNIQUENOT NULLCHECKDEFAULTALTERExamplePractice

Constraints are rules applied to table columns to control what data can be inserted, updated, or deleted in a database.

They help maintain

🎯AccuracyPrevent invalid values.
🔗IntegrityKeep relationships between tables correct.
📐ConsistencyEnsure data follows predefined rules.
🛡️ReliabilityPrevent accidental or incorrect records.

For example, imagine an employee table

employee_idemployee_nameemailagesalary
1Rahulrahul@gmail.com2530000
2Amitamit@gmail.com2845000
3Priyapriya@gmail.com2235000

What if someone tries to insert:

  • ❓ An employee without an ID?
  • ❓ Two employees with the same email?
  • ❓ An employee aged 15?
  • ❓ An employee with a negative salary?
Constraints help prevent these problems.

Let's understand each one with syntax, examples, alternate options, and practical use cases.

1. PRIMARY KEY
🔑

PRIMARY KEY

Purpose: Uniquely identifies every record in a table.

A primary key has two important properties:

  • It cannot contain duplicate values.
  • It cannot contain NULL values.

Example

primary-key.sql
CREATE TABLE employees (
    employee_id INTEGER PRIMARY KEY,
    employee_name VARCHAR(100),
    email VARCHAR(100)
);

Here, employee_id uniquely identifies every employee.

employee_idemployee_name
1Rahul
2Amit
3Priya

Invalid examples:

pk-invalid.sql
-- Duplicate employee_id
INSERT INTO employees VALUES (1, 'John', 'john@gmail.com');

-- NULL employee_id
INSERT INTO employees VALUES (NULL, 'Sam', 'sam@gmail.com');
Both will fail because of the primary key constraint.

A. Auto-generated PRIMARY KEY

In most real-world tables, you don't want to manually provide IDs.

pk-identity.sql
CREATE TABLE employees (
    employee_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    employee_name VARCHAR(100)
);

PostgreSQL automatically generates IDs. You can also use:

pk-serial.sql
employee_id SERIAL PRIMARY KEY

SERIAL is an older PostgreSQL shorthand.

B. Named PRIMARY KEY

pk-named.sql
CREATE TABLE employees (
    employee_id INTEGER,
    employee_name VARCHAR(100),

    CONSTRAINT pk_employees
        PRIMARY KEY (employee_id)
);

C. Composite PRIMARY KEY

A primary key can consist of multiple columns.

pk-composite.sql
CREATE TABLE enrollments (
    student_id INTEGER,
    course_id INTEGER,

    CONSTRAINT pk_enrollments
        PRIMARY KEY (student_id, course_id)
);

Here, the combination of student_id and course_id must be unique.

student_idcourse_idResult
1101Allowed
1102Allowed
2101Allowed
1101Rejected

The same student can enroll in different courses, but cannot enroll in the same course twice.

Important: A table can have only one primary key constraint, but that primary key can contain multiple columns.
2. FOREIGN KEY
🔗

FOREIGN KEY

Purpose: Connects two tables and maintains referential integrity.
In simple words: a foreign key ensures that a value in one table refers to an existing record in another table.

Example: Customers and Orders

First, create the parent table:

customers.sql
CREATE TABLE customers (
    customer_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL
);

Now create the child table:

orders.sql
CREATE TABLE orders (
    order_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id INTEGER,

    CONSTRAINT fk_order_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id)
);

How does it work?

Customers

customer_idcustomer_name
1Rahul
2Amit
3Priya

Orders

order_idcustomer_id
1011
1021
1032

Customer 1 can have multiple orders. This is a one-to-many relationship.

✅ Valid insert:

fk-valid.sql
INSERT INTO orders (customer_id)
VALUES (1);

Customer 1 exists.

❌ Invalid insert:

fk-invalid.sql
INSERT INTO orders (customer_id)
VALUES (10);

Customer 10 doesn't exist, so PostgreSQL rejects it.

A. Alternate syntax (Inline FOREIGN KEY)

Instead of a named constraint:

fk-inline.sql
CREATE TABLE orders (
    order_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id INTEGER REFERENCES customers(customer_id)
);

Both approaches create a foreign key.

B. ON DELETE options

What happens when you delete a parent record that has child records? You can control this using ON DELETE.

1ON DELETE CASCADE
on-delete-cascade.sql
CONSTRAINT fk_order_customer
    FOREIGN KEY (customer_id)
    REFERENCES customers(customer_id)
    ON DELETE CASCADE

Deleting a customer automatically deletes their related orders.

2ON DELETE SET NULL
on-delete-set-null.sql
FOREIGN KEY (customer_id)
REFERENCES customers(customer_id)
ON DELETE SET NULL

Deleting a customer sets the related customer_id in orders to NULL. The column must allow NULL.

3ON DELETE RESTRICT
on-delete-restrict.sql
FOREIGN KEY (customer_id)
REFERENCES customers(customer_id)
ON DELETE RESTRICT

Prevents deleting a customer if related orders exist.

4ON DELETE NO ACTION
on-delete-no-action.sql
FOREIGN KEY (customer_id)
REFERENCES customers(customer_id)
ON DELETE NO ACTION

Checks referential integrity when the constraint is checked. This is the default behaviour in PostgreSQL.

C. ON UPDATE options

You can also control what happens when the referenced key is updated.

on-update.sql
FOREIGN KEY (customer_id)
REFERENCES customers(customer_id)
ON UPDATE CASCADE

If a customer's ID changes, PostgreSQL automatically updates the related foreign keys.

Orders → CustomersAttendance → EmployeesPayments → OrdersReviews → ProductsEnrollments → Students and Courses
3. UNIQUE constraint
✨

UNIQUE constraint

Purpose: Prevents duplicate values in a column or combination of columns.

For example, two employees should not have the same email address.

A. Single-column UNIQUE

unique.sql
CREATE TABLE employees (
    employee_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    employee_name VARCHAR(100),
    email VARCHAR(100) UNIQUE
);

Example:

employee_idemployee_nameemail
1Rahulrahul@gmail.com
2Amitamit@gmail.com
3Priyapriya@gmail.com
Trying to insert another employee with rahul@gmail.com will fail.

B. Named UNIQUE constraint

unique-named.sql
CREATE TABLE employees (
    employee_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    employee_name VARCHAR(100),
    email VARCHAR(100),

    CONSTRAINT uq_employees_email
        UNIQUE (email)
);

Here, uq_employees_email is the custom constraint name.

C. Composite UNIQUE

You can apply UNIQUE to multiple columns.

unique-composite.sql
CREATE TABLE attendance (
    attendance_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    employee_id INTEGER,
    attendance_date DATE,

    CONSTRAINT uq_employee_attendance
        UNIQUE (employee_id, attendance_date)
);

This prevents the same employee from having two attendance records on the same date.

employee_idattendance_dateResult
1012026-11-01Allowed
1022026-11-01Allowed
1012026-11-02Allowed
1012026-11-01Rejected

D. UNIQUE vs PRIMARY KEY

PRIMARY KEYUNIQUE
Uniquely identifies each rowPrevents duplicate values
Cannot contain NULLAllows NULL by default
Only one per tableMultiple per table
Can contain multiple columnsCan contain multiple columns
Important: By default, PostgreSQL treats NULL values as distinct in a UNIQUE constraint. This means multiple NULL values are allowed.

PostgreSQL also supports UNIQUE NULLS NOT DISTINCT, which treats NULL values as duplicates.

nulls-not-distinct.sql
email VARCHAR(100),
CONSTRAINT uq_email UNIQUE NULLS NOT DISTINCT (email)

This allows at most one NULL email.

4. NOT NULL constraint
🚫

NOT NULL constraint

Purpose: Prevents a column from storing NULL values.

NULL means the value is missing or unknown. It is different from an empty string ('') or zero (0).

A. Example

not-null.sql
CREATE TABLE employees (
    employee_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    employee_name VARCHAR(100) NOT NULL,
    email VARCHAR(100) NOT NULL,
    age INTEGER
);

Here:

  • employee_name cannot be NULL.
  • email cannot be NULL.
  • age can be NULL.

✅ Valid insert:

nn-valid.sql
INSERT INTO employees (employee_name, email, age)
VALUES ('Rahul', 'rahul@gmail.com', 25);

❌ Invalid insert:

nn-invalid.sql
INSERT INTO employees (employee_name, email, age)
VALUES (NULL, 'rahul@gmail.com', 25);
This fails because employee_name is NOT NULL.

B. Add NOT NULL later

nn-alter.sql
ALTER TABLE employees
ALTER COLUMN email SET NOT NULL;

Remove NOT NULL:

nn-drop.sql
ALTER TABLE employees
ALTER COLUMN email DROP NOT NULL;

C. Important difference: NOT NULL vs CHECK

These are not equivalent:

check-null.sql
age INTEGER CHECK (age >= 18)
This allows NULL because a CHECK constraint does not reject an expression that evaluates to UNKNOWN.

To make age mandatory:

check-not-null.sql
age INTEGER NOT NULL CHECK (age >= 18)

Now both conditions are enforced.

Real-world use cases
Employee nameOrder dateProduct nameRequired customer IDTransaction amount
5. CHECK constraint
✅

CHECK constraint

Purpose: Validates whether a value satisfies a specific condition.

Think of CHECK as an if condition in JavaScript.

if-condition.js
if (salary > 0) {
    // Accept salary
} else {
    // Reject salary
}

In PostgreSQL:

check-salary.sql
salary NUMERIC(10,2) CHECK (salary > 0)

A. Common CHECK examples

RequirementSQL condition
Age must be 18 or aboveCHECK (age >= 18)
Salary must be positiveCHECK (salary > 0)
Stock cannot be negativeCHECK (stock >= 0)
Discount between 0 and 50CHECK (discount BETWEEN 0 AND 50)
Status must be validCHECK (status IN ('Active', 'Inactive'))
Rating between 1 and 5CHECK (rating BETWEEN 1 AND 5)
Quantity must be positiveCHECK (quantity > 0)

B. Complete example

check-products.sql
CREATE TABLE products (
    product_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL,
    price NUMERIC(10,2),
    discount NUMERIC(5,2),
    stock INTEGER,

    CONSTRAINT chk_product_price
        CHECK (price > 0),

    CONSTRAINT chk_product_discount
        CHECK (discount BETWEEN 0 AND 50),

    CONSTRAINT chk_product_stock
        CHECK (stock >= 0)
);

C. Multiple conditions in one CHECK

You can combine conditions using AND and OR.

check-and.sql
CONSTRAINT chk_employee_details
    CHECK (age >= 18 AND salary > 0)

Both conditions must be satisfied. Another example:

check-or.sql
CONSTRAINT chk_payment_method
    CHECK (payment_method IN ('UPI', 'Card', 'Cash'))

Only these three payment methods are allowed.

D. CHECK between two columns

You can also compare two columns.

check-two-columns.sql
CREATE TABLE projects (
    project_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    start_date DATE NOT NULL,
    end_date DATE,

    CONSTRAINT chk_project_dates
        CHECK (end_date IS NULL OR end_date >= start_date)
);

This ensures the end date cannot be earlier than the start date.

E. Named CHECK vs inline CHECK

Named:

check-named.sql
CONSTRAINT chk_salary
    CHECK (salary > 0)

Inline:

check-inline.sql
salary NUMERIC(10,2) CHECK (salary > 0)

Both are valid.

6. DEFAULT constraint
⚙️

DEFAULT constraint

Purpose: Automatically provides a value when you don't supply one during INSERT.

For example, whenever a new employee is created, their status should automatically be Active.

A. Example

default.sql
CREATE TABLE employees (
    employee_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    employee_name VARCHAR(100) NOT NULL,
    status VARCHAR(20) DEFAULT 'Active',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

Insert:

default-insert.sql
INSERT INTO employees (employee_name)
VALUES ('Rahul');

Result:

employee_idemployee_namestatuscreated_at
1RahulActiveAutomatically generated

You didn't provide status or created_at, so PostgreSQL supplied their default values.

B. Different DEFAULT examples

RequirementSyntax
Default active statusDEFAULT 'Active'
Default stockDEFAULT 0
Default current dateDEFAULT CURRENT_DATE
Default current timestampDEFAULT CURRENT_TIMESTAMP
Default BooleanDEFAULT TRUE
Default payment methodDEFAULT 'Cash'

C. Add DEFAULT later

default-alter.sql
ALTER TABLE employees
ALTER COLUMN status SET DEFAULT 'Active';

Remove DEFAULT:

default-drop.sql
ALTER TABLE employees
ALTER COLUMN status DROP DEFAULT;

D. Important: DEFAULT vs NOT NULL

These are different:

default-only.sql
status VARCHAR(20) DEFAULT 'Active'

If you explicitly insert NULL, PostgreSQL accepts NULL.

default-null.sql
INSERT INTO employees (employee_name, status)
VALUES ('Rahul', NULL);
The default is not applied because you explicitly supplied NULL.

If you want to prevent NULL:

default-not-null.sql
status VARCHAR(20) NOT NULL DEFAULT 'Active'

Now:

Omitted→ Active
NULL→ Error
Inactive→ Accepted

How to modify constraints after creating a table
🛠️

How to modify constraints after creating a table

You don't always need to drop and recreate a table. PostgreSQL provides ALTER TABLE.

OperationSyntax
Add UNIQUEALTER TABLE employees ADD CONSTRAINT uq_email UNIQUE (email);
Add CHECKALTER TABLE employees ADD CONSTRAINT chk_salary CHECK (salary > 0);
Add FOREIGN KEYALTER TABLE orders ADD CONSTRAINT fk_customer FOREIGN KEY (customer_id) REFERENCES customers(customer_id);
Add PRIMARY KEYALTER TABLE employees ADD CONSTRAINT pk_employee PRIMARY KEY (employee_id);
Drop a named constraintALTER TABLE employees DROP CONSTRAINT chk_salary;

For NOT NULL and DEFAULT, use column-specific commands:

alter-column.sql
-- Add NOT NULL
ALTER TABLE employees
ALTER COLUMN email SET NOT NULL;

-- Remove NOT NULL
ALTER TABLE employees
ALTER COLUMN email DROP NOT NULL;

-- Add DEFAULT
ALTER TABLE employees
ALTER COLUMN status SET DEFAULT 'Active';

-- Remove DEFAULT
ALTER TABLE employees
ALTER COLUMN status DROP DEFAULT;
Important: When adding constraints to an existing table, PostgreSQL checks existing data. If existing rows violate the new constraint, the operation can fail.
Complete real-world example – Attendance management
🏢

Complete real-world example – Attendance management

Let's combine the constraints you have learned.

attendance.sql
CREATE TABLE attendance (
    attendance_id INTEGER GENERATED ALWAYS AS IDENTITY,
    employee_id INTEGER NOT NULL,
    attendance_date DATE NOT NULL,
    status VARCHAR(10) NOT NULL DEFAULT 'Present',
    working_hours NUMERIC(4,2),

    CONSTRAINT pk_attendance
        PRIMARY KEY (attendance_id),

    CONSTRAINT fk_attendance_employee
        FOREIGN KEY (employee_id)
        REFERENCES employees(employee_id),

    CONSTRAINT chk_attendance_status
        CHECK (status IN ('Present', 'Absent', 'Leave')),

    CONSTRAINT chk_working_hours
        CHECK (working_hours BETWEEN 0 AND 24),

    CONSTRAINT uq_employee_attendance
        UNIQUE (employee_id, attendance_date)
);

Let's understand what each constraint does:

ConstraintRule
pk_attendanceEach attendance record has a unique ID
fk_attendance_employeeEmployee must exist in employees table
chk_attendance_statusOnly Present, Absent, Leave are accepted
chk_working_hoursWorking hours must be between 0 and 24
uq_employee_attendanceOne attendance record per employee per date
NOT NULLEmployee and attendance date are mandatory
DEFAULTStatus becomes Present if omitted
Note: working_hours can be NULL in this example. If it must always be provided, add NOT NULL.
Important differences – Quick revision
📋

Important differences – Quick revision

ConstraintDuplicate allowed?NULL allowed?Multiple per table?
PRIMARY KEYNoNoNo
FOREIGN KEYYesYes, unless NOT NULLYes
UNIQUENo, for non-NULL values by defaultYesYes
NOT NULLYesNoYes
CHECKDepends on conditionUsually yesYes
DEFAULTDepends on column rulesYes, if explicitly supplied and nullableYes

A few important points

  • A table can have only one PRIMARY KEY constraint.
  • A table can have multiple FOREIGN KEY constraints.
  • A table can have multiple UNIQUE constraints.
  • A table can have multiple CHECK constraints.
  • FOREIGN KEY must reference a primary key or unique key (or another suitable unique constraint/index).
  • DEFAULT is technically a column default, rather than a named table constraint.
  • NOT NULL is also a column property in PostgreSQL, not a normally named constraint.

Practice exercises

Constraint practice 5 exercises
1Employee table

Create an employees table with an auto-generated primary key, employee_name NOT NULL, email UNIQUE, age at least 18, salary greater than 0, and status DEFAULT 'Active' with only Active or Inactive allowed.

Show hint
💡 Use GENERATED ALWAYS AS IDENTITY PRIMARY KEY. For status you need both a DEFAULT and a CHECK (status IN (...)).
2Products table

Create a products table with a primary key, product_name NOT NULL, price greater than 0, stock at least 0, discount between 0 and 50, and a unique product_code.

Show hint
💡 Put UNIQUE on product_code. Use BETWEEN 0 AND 50 for discount and >= 0 for stock.
3Orders table

Create an orders table with an auto-generated primary key, a foreign key referencing customers, amount greater than 0, status defaulting to Pending, and status restricted to Pending, Shipped, Delivered, or Cancelled.

Show hint
💡 Use REFERENCES customers(customer_id). Combine DEFAULT 'Pending' with a CHECK listing all four statuses.
4Attendance table

Create an attendance table referencing employees. Employee and date must be mandatory. Status must be Present, Absent, or Leave. An employee can have only one attendance record per date.

Show hint
💡 Add NOT NULL to employee and date, then a composite UNIQUE (employee_id, attendance_date).
5Course enrollment

Create an enrollments table with a composite primary key using student_id and course_id, foreign keys to students and courses, marks between 0 and 100, and enrollment_date defaulting to the current date.

Show hint
💡 Declare PRIMARY KEY (student_id, course_id) at table level. Use DEFAULT CURRENT_DATE for enrollment_date.
