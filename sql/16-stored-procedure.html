1 What is a Stored Procedure? & Why use one?
A procedure is a saved, reusable set of SQL instructions stored in the database. You call it by name instead of rewriting the same SQL — and, unlike a function, it can COMMIT or ROLLBACK inside its body.

Q: What is a stored procedure in PostgreSQL?

A: A stored procedure is a named block of SQL and optional PL/pgSQL logic stored permanently in the database and executed with CALL. It can hold multiple statements, conditions, loops and variables, and it can control transactions with COMMIT and ROLLBACK — which functions cannot.

🧠 Analogy: A procedure is a recipe in a recipe book. Instead of spelling out every step each time you cook, you say "make the transfer" and the saved recipe runs all the steps in order.
-- WITHOUT a procedure — repeat these steps every time
BEGIN;
  UPDATE accounts SET balance = balance - 500 WHERE id = 1;
  UPDATE accounts SET balance = balance + 500 WHERE id = 2;
  INSERT INTO transfer_log VALUES (1, 2, 500, NOW());
COMMIT;
-- WITH a procedure — write once, call anywhere
CALL transfer_funds(p_from => 1, p_to => 2, p_amount => 500);

Why use procedures?

1

Reusability

Write complex logic once, call it from the app, scripts or other procedures.

2

Transaction control

Only procedures can COMMIT / ROLLBACK inside the body.

3

Security

Grant EXECUTE on a procedure without exposing the underlying tables.

4

Fewer round-trips

Many statements run in one CALL — and PL/pgSQL caches its query plans per session.

5

Encapsulation

Hide complex business logic behind a clean interface.

6

Batch jobs

Process millions of rows in chunks, committing as you go.

📌 Version note: CREATE PROCEDURE + CALL arrived in PostgreSQL 11. Before that you had to use functions — which cannot contain COMMIT / ROLLBACK.
2 CREATE PROCEDURE — Full Syntax
CREATE [OR REPLACE] PROCEDURE procedure_name (
  param1  data_type,
  param2  data_type
)
LANGUAGE plpgsql          -- use 'sql' for simple single-statement procedures
AS $$
DECLARE
  variable_name  data_type;   -- optional local variables
BEGIN
  -- your SQL logic here
  -- INSERT / UPDATE / DELETE / IF / LOOP / EXCEPTION
END;
$$;
1

CREATE OR REPLACE PROCEDURE name

OR REPLACE updates the procedure if it exists — no drop needed. Use a clear name like transfer_funds.

2

Define parameters in ( )

List inputs with their types. There is no RETURNS clause — that's a function's job. Modes: IN (default), INOUT, OUT.

3

LANGUAGE plpgsql

Use plpgsql for IF / loops / variables / exceptions. Use sql only for a simple sequence of statements.

4

AS $$ DECLARE … BEGIN … END; $$

Dollar-quoting wraps the body, so you needn't escape single quotes. DECLARE holds variables; logic lives between BEGIN and END.

Example 1 — Simple procedure (no variables)

-- Deactivate a user by ID
CREATE OR REPLACE PROCEDURE deactivate_user(p_user_id INT)
LANGUAGE plpgsql
AS $$
BEGIN
  UPDATE users
  SET    is_active = false,
         deactivated_at = NOW()
  WHERE  id = p_user_id;
END;
$$;

Example 2 — Local variables and validation

CREATE OR REPLACE PROCEDURE apply_discount(
  p_product_id    INT,
  p_discount_pct  NUMERIC
)
LANGUAGE plpgsql
AS $$
DECLARE
  v_current_price  NUMERIC;   -- local variable to hold fetched price
  v_new_price      NUMERIC;   -- calculated discounted price
BEGIN
  -- Step 1: fetch current price into a local variable
  SELECT price INTO v_current_price
  FROM   products
  WHERE  id = p_product_id;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'Product % not found', p_product_id;
  END IF;

  -- Step 2: calculate new price
  v_new_price := v_current_price * (1 - p_discount_pct / 100);

  -- Step 3: validate before applying
  IF v_new_price <= 0 THEN
    RAISE EXCEPTION 'New price cannot be zero or negative: %', v_new_price;
  END IF;

  -- Step 4: apply the discount
  UPDATE products
  SET    price = v_new_price
  WHERE  id = p_product_id;

  RAISE NOTICE 'Price updated: % → %', v_current_price, v_new_price;
END;
$$;
3 CALL — How to Execute a Procedure

Use the CALL keyword to run a procedure. Functions use SELECT; CALL is a standalone statement and cannot be embedded in a SELECT list.

-- Positional arguments
CALL deactivate_user(42);

-- Named parameters (recommended — clearer, order-independent)
CALL apply_discount(p_product_id => 15, p_discount_pct => 20);

-- Call from inside a DO block (anonymous block)
DO $$
BEGIN
  CALL deactivate_user(42);
  CALL deactivate_user(43);
END;
$$;

Manage procedures

-- List all procedures in the database
SELECT proname, prokind
FROM   pg_proc
WHERE  prokind = 'p';   -- 'p' = procedure, 'f' = function

-- View the source code of a procedure
SELECT pg_get_functiondef(oid)
FROM   pg_proc
WHERE  proname = 'deactivate_user';

-- Drop a procedure (must specify argument types)
DROP PROCEDURE IF EXISTS deactivate_user(INT);

-- Grant execute permission to a role
GRANT EXECUTE ON PROCEDURE deactivate_user(INT) TO app_user;
💡 Named-argument syntax: name => value is the standard form; the older name := value still works.
✅ Remember: CALL = procedures, SELECT = functions. SELECT deactivate_user(42) fails for a procedure.
4 Parameter Modes — IN, OUT, INOUT

Parameters have three modes that control data flow between the caller and the procedure.

ModeDirectionDefault?Use CaseExample
INCaller → Procedure✅ YesPass values into the procedurep_user_id INT
OUTProcedure → CallerNoReturn values without RETURN (PG 14+)OUT p_count INT
INOUTBoth directionsNoPass a value in and get the modified value backINOUT p_count INT
-- INOUT: value goes in, modified value comes back
CREATE OR REPLACE PROCEDURE apply_tax(
  INOUT p_price NUMERIC,
  p_tax_rate    NUMERIC DEFAULT 18
)
LANGUAGE plpgsql
AS $$
BEGIN
  p_price := p_price * (1 + p_tax_rate / 100);
END;
$$;

-- Calling an INOUT procedure from a DO block
DO $$
DECLARE
  v_price NUMERIC := 1000;
BEGIN
  CALL apply_tax(v_price);
  RAISE NOTICE 'Price with tax: %', v_price;  -- 1180
END;
$$;
💡 Default values: add DEFAULT value after the type to make a parameter optional.
📌 On PostgreSQL 11–13 procedures support only IN and INOUT; OUT parameters need PostgreSQL 14+. INOUT works everywhere.
5 Variables, IF, LOOP — Procedural Logic

DECLARE block

Declare all local variables before BEGIN. Format: variable_name TYPE := initial_value; — the initial value is optional.

Assignment

Use := for direct assignment: v_total := v_price * v_qty;. Use SELECT … INTO to assign from a query, then test FOUND to see if a row came back.

IF / ELSIF / ELSE

Conditional logic: IF condition THEN … ELSIF condition THEN … ELSE … END IF;

LOOP

Basic loop: LOOP … EXIT WHEN condition; END LOOP;. Also FOR i IN 1..10 LOOP, WHILE condition LOOP and FOR rec IN SELECT … LOOP.

RAISE NOTICE

Prints a message to the client: RAISE NOTICE 'Value is: %', v_count; — each % is replaced by the next argument.

RAISE EXCEPTION

Throws an error and aborts the current transaction (rolling back its work): RAISE EXCEPTION 'Error: %', detail_msg;

CREATE OR REPLACE PROCEDURE process_order(p_order_id INT)
LANGUAGE plpgsql
AS $$
DECLARE
  v_total      NUMERIC;
  v_status     TEXT;
  v_item_count INT := 0;
BEGIN
  -- Fetch order details into variables
  SELECT total_amount, status
  INTO   v_total, v_status
  FROM   orders
  WHERE  id = p_order_id;

  -- Check order exists
  IF NOT FOUND THEN
    RAISE EXCEPTION 'Order % not found', p_order_id;
  END IF;

  -- Conditional logic on status
  IF v_status = 'pending' THEN
    UPDATE orders SET status = 'processing' WHERE id = p_order_id;
    RAISE NOTICE 'Order % → processing', p_order_id;

  ELSIF v_status = 'processing' THEN
    UPDATE orders SET status = 'shipped' WHERE id = p_order_id;
    RAISE NOTICE 'Order % → shipped', p_order_id;

  ELSE
    RAISE EXCEPTION 'Cannot process order in status: %', v_status;
  END IF;

  -- Count items in a loop (SELECT COUNT(*) is faster — loop shown to demo FOR)
  FOR rec IN SELECT * FROM order_items WHERE order_id = p_order_id LOOP
    v_item_count := v_item_count + 1;
  END LOOP;

  RAISE NOTICE 'Processed order % with % items, total %',
               p_order_id, v_item_count, v_total;
END;
$$;
6 Procedure Transactions — The Key Differentiator

The single most important feature separating procedures from functions: a procedure can contain COMMIT and ROLLBACK. A function cannot — it always runs inside the caller's transaction.

Function — one transaction for everything
Caller BEGIN
→
Function runs all SQL
→
Caller COMMIT (or ROLLBACK all)
→
❌ No mid-way checkpoint
Procedure — controls its own transactions
CALL proc
→
Batch 1 → COMMIT ✅
→
Batch 2 → COMMIT ✅
→
Batch 3 → COMMIT ✅

Example 1 — Atomic fund transfer

CREATE OR REPLACE PROCEDURE transfer_funds(
  p_from   INT,
  p_to     INT,
  p_amount NUMERIC
)
LANGUAGE plpgsql
AS $$
DECLARE
  v_balance NUMERIC;
BEGIN
  -- Lock the sender's row and read the balance
  SELECT balance INTO v_balance
  FROM   accounts
  WHERE  id = p_from
  FOR UPDATE;           -- row-level lock

  IF v_balance < p_amount THEN
    RAISE EXCEPTION 'Insufficient funds. Balance: %, Required: %',
                    v_balance, p_amount;
  END IF;

  UPDATE accounts SET balance = balance - p_amount WHERE id = p_from;
  UPDATE accounts SET balance = balance + p_amount WHERE id = p_to;

  INSERT INTO transfer_log (from_id, to_id, amount, transferred_at)
  VALUES (p_from, p_to, p_amount, NOW());

  COMMIT;   -- ← commit all three changes together
  RAISE NOTICE 'Transfer of % successful.', p_amount;
END;
$$;

CALL transfer_funds(p_from => 1, p_to => 2, p_amount => 500.00);
📌 If anything fails before the COMMIT — including the RAISE EXCEPTION — the whole transaction aborts and none of the three changes are saved. No EXCEPTION block is needed for that (and see the warning below for why adding one here would break the COMMIT).

Example 2 — Batch processing with mid-loop COMMITs

CREATE OR REPLACE PROCEDURE archive_old_orders(p_days_old INT)
LANGUAGE plpgsql
AS $$
DECLARE
  v_batch_size INT := 1000;
  v_processed  INT;
BEGIN
  LOOP
    -- Move one batch of 1000 rows to the archive table
    WITH batch AS (
      DELETE FROM orders
      WHERE  id IN (
        SELECT id FROM orders
        WHERE  created_at < NOW() - make_interval(days => p_days_old)
        LIMIT  v_batch_size
      )
      RETURNING *
    )
    INSERT INTO orders_archive SELECT * FROM batch;

    GET DIAGNOSTICS v_processed = ROW_COUNT;

    COMMIT;   -- ← commit each batch: frees locks, reduces WAL pressure
    RAISE NOTICE 'Archived % rows.', v_processed;

    EXIT WHEN v_processed < v_batch_size;   -- no more rows left
  END LOOP;

  RAISE NOTICE 'Archiving complete.';
END;
$$;

CALL archive_old_orders(90);
⚠️ Rule 1: don't CALL a procedure that commits from inside an open transaction (BEGIN … COMMIT in your app, or from a function / SELECT). Its internal COMMIT fails with "invalid transaction termination". Always CALL it at the top level.
⚠️ Rule 2: a BEGIN … END block that has an EXCEPTION clause cannot contain COMMIT or ROLLBACK (it runs inside a subtransaction). Keep the handler in an inner block and put the COMMIT outside it — see Topic 7.
7 EXCEPTION Block — Handle Errors Gracefully

Add an EXCEPTION section at the end of a BEGIN … END block to catch errors. When an exception is raised, PostgreSQL rolls back the work done in that block and jumps to the matching handler, where you can log, skip or re-raise.

CREATE OR REPLACE PROCEDURE safe_update(p_id INT, p_value NUMERIC)
LANGUAGE plpgsql
AS $$
DECLARE
  v_err TEXT;
BEGIN
  BEGIN   -- inner block: has the handler, contains NO commit
    UPDATE some_table SET amount = p_value WHERE id = p_id;

    IF NOT FOUND THEN
      RAISE EXCEPTION 'Row with id % not found', p_id;
    END IF;
  EXCEPTION
    -- Catch a specific error: unique violation
    WHEN unique_violation THEN
      v_err := 'Duplicate key for id ' || p_id;

    -- Catch any other error
    WHEN OTHERS THEN
      -- SQLERRM = the error message, SQLSTATE = the error code
      v_err := SQLERRM || ' (' || SQLSTATE || ')';
  END;

  IF v_err IS NOT NULL THEN
    INSERT INTO error_log (message, occurred_at) VALUES (v_err, NOW());
    RAISE NOTICE 'Failed for id %: %', p_id, v_err;
  ELSE
    RAISE NOTICE 'Updated id % successfully.', p_id;
  END IF;

  COMMIT;   -- outside the handler block, so it is allowed
END;
$$;
💡 The failed UPDATE was already rolled back when the handler ran, so the COMMIT only saves the log row. If you also want the caller to see the failure, COMMIT first and then RAISE EXCEPTION '%', v_err;.

9 Interview Q&A + Cheat Sheet

Q: When was CREATE PROCEDURE added to PostgreSQL?

A: PostgreSQL 11. Before that, functions were the workaround — but they cannot contain COMMIT / ROLLBACK.

Q: Can a procedure return a value?

A: Not with a RETURN statement. INOUT parameters (and OUT on PG 14+) pass values back to the caller. For result sets, use a function with RETURNS TABLE or RETURNS SETOF.

Q: What happens if RAISE EXCEPTION is called inside a procedure?

A: It aborts the current transaction, rolling back its work. If the code is inside a block with an EXCEPTION clause, only that block's work is rolled back and you can handle the error — log it, skip it, or re-raise.

Q: Can you call a procedure from inside another procedure?

A: Yes — use CALL in the body. A nested procedure can still COMMIT as long as every level was started with CALL (or a DO block) at the top level — not from a function or an open transaction block.
