1. INNER JOIN
Matching rows only
Both sides must have a match.

Returns only rows that match in both tables. Rows without a matching partner are excluded.

Remember it: “Give me only the rows that exist on both sides.” Ravi and Order 104 do not appear.
inner_join.sql
SELECT u.name, o.id AS order_id, o.total
FROM users u
INNER JOIN orders o ON o.user_id = u.id;

Use when: you only want records with a valid match in both tables. Plain JOIN means INNER JOIN in standard SQL.
2. LEFT JOIN (LEFT OUTER JOIN)
All left rows
Unmatched right-side columns become NULL.

Returns every row from the left table and matching rows from the right table. If no match exists, right-side columns contain NULL.

Remember it: “Keep everyone on the left and attach right-side data when available.” Ravi appears with NULL order values.
left_join.sql
SELECT u.name, o.id AS order_id, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;

-- Find users with no orders (anti-join)
SELECT u.name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;

3. RIGHT JOIN (RIGHT OUTER JOIN)
All right rows
Unmatched left-side columns become NULL.

Returns every row from the right table plus matching rows from the left. It is the mirror image of a LEFT JOIN.

Remember it: “Keep every order, even if its user record is missing.” Order 104 appears with NULL user data.
right_join.sql
SELECT u.name, o.id AS order_id, o.total
FROM users u
RIGHT JOIN orders o ON o.user_id = u.id;

-- Equivalent: swap the table order
SELECT u.name, o.id AS order_id, o.total
FROM orders o
LEFT JOIN users u ON u.id = o.user_id;

Practical tip: RIGHT JOIN can always be rewritten as LEFT JOIN by swapping table order. Many teams prefer LEFT JOIN because it is easier to read consistently.
4. FULL OUTER JOIN
All rows from both
Unmatched columns on either side become NULL.

Returns every row from both tables. Matching rows are combined; unmatched rows from either side are still included, with NULL on the missing side.

Remember it: “Keep everything from both sides.” Both Ravi and Order 104 appear.
full_outer_join.sql
SELECT u.name, o.id AS order_id, o.total
FROM users u
FULL OUTER JOIN orders o ON o.user_id = u.id;

-- Find unmatched rows from either side
SELECT u.name, o.id
FROM users u
FULL OUTER JOIN orders o ON o.user_id = u.id
WHERE u.id IS NULL OR o.id IS NULL;

5. CROSS JOIN (Cartesian product)
Every combination
No ON condition is required.

Pairs every row in the first table with every row in the second. Three users × four orders produces 12 combinations.

Be careful: 1,000 rows × 1,000 rows = 1,000,000 result rows. Use CROSS JOIN intentionally.
cross_join.sql
-- Generate every size × color combination
SELECT s.size, c.color
FROM sizes s
CROSS JOIN colors c;

-- 3 sizes × 2 colors = 6 rows

Typical uses: product variants, test-data generation, scheduling grids (time slot × room), and combinations for comparisons or tournament fixtures.
6. SELF JOIN (a table joined to itself)
Same table, two aliases
Connect one row to another row in that table.

A SELF JOIN uses the same table twice with different aliases. It is useful for self-referencing relationships such as an employee’s manager_id pointing to another employee’s id.

Important: SELF JOIN is not a separate SQL keyword. It is commonly written using an INNER JOIN or LEFT JOIN with two aliases of the same table.
self_join.sql
-- employees(id, name, manager_id)
SELECT
    e.name AS employee,
    m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;

-- Find employees earning more than their manager
SELECT e.name, e.salary, m.name AS manager, m.salary AS manager_salary
FROM employees e
INNER JOIN employees m ON m.id = e.manager_id
WHERE e.salary > m.salary;

Use cases: employee-manager trees, parent-child categories, comparing rows (such as salaries), and relationships such as friends or followers. Use LEFT JOIN when rows without a parent should still appear.
7. ANSI JOINs — old implicit style vs modern explicit style

What is ANSI SQL?

ANSI SQL-92 standardized the explicit JOIN ... ON syntax. Older SQL often listed tables separated by commas in FROM and put join conditions in WHERE.

Two styles: old implicit style — comma-separated tables in FROM, join conditions in WHERE. Modern ANSI style — explicit JOIN with its own ON condition.

Old implicit join — legacy style

old_implicit_join.sql
-- Legacy syntax: avoid in new code
SELECT u.name, o.total
FROM users u, orders o
WHERE o.user_id = u.id;

-- If you omit the WHERE join condition, this becomes
-- a Cartesian product.
SELECT u.name, o.total
FROM users u, orders o;
Why it is risky: forgetting a join condition can silently produce a Cartesian product. Explicit JOIN syntax keeps the join condition next to the join, making queries easier to review.

Modern ANSI explicit join

ansi_explicit_join.sql
SELECT u.name, o.total
FROM users u
INNER JOIN orders o ON o.user_id = u.id;

-- Multiple joins: each join has its own ON clause
SELECT u.name AS user_name, o.total, d.name AS department
FROM users u
INNER JOIN orders o ON o.user_id = u.id
INNER JOIN departments d ON d.id = u.dept_id
WHERE u.active = 1
ORDER BY u.name;

Final takeaway
INNER keeps matches; LEFT keeps every left row; RIGHT keeps every right row; FULL keeps rows from both sides; CROSS creates every combination; SELF JOIN relates rows within one table.
