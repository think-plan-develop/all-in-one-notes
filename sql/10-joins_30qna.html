🔴 Section 1 — JOIN Fundamentals

Q1 · What is a JOIN in SQL and why do we need it?
🔴 CriticalConceptBeginner

Q: What is a JOIN in SQL and why do we need it?

A: A JOIN combines rows from two or more tables based on a related column between them. We need JOINs because relational databases store data across multiple normalized tables to avoid redundancy — JOINs let us reconstruct meaningful, combined results at query time.

Without JOINs, you'd have to query each table separately and manually match related data in application code — inefficient and error-prone.
join_basic.sql
-- customers table has customer_id, name -- orders table has order_id, customer_id, amount SELECT c.name, o.amount FROM customers c JOIN orders o ON c.customer_id = o.customer_id;
Normalization splits data into tables → JOINs reunite it when querying.
Q2 · What is the difference between INNER JOIN and OUTER JOIN?
🔴 CriticalConcept

Q: What is the difference between INNER JOIN and OUTER JOIN?

A: INNER JOIN returns only the rows where there is a match in BOTH tables. OUTER JOIN (LEFT, RIGHT, or FULL) also returns unmatched rows from one or both tables, filling missing values with NULL.

TypeMatched rowsUnmatched LEFTUnmatched RIGHT
INNER JOIN✅❌❌
LEFT JOIN✅✅ (NULLs on right)❌
RIGHT JOIN✅❌✅ (NULLs on left)
FULL OUTER JOIN✅✅✅
INNER JOIN: A ∩ B LEFT JOIN: A + (A ∩ B) RIGHT JOIN: B + (A ∩ B) FULL OUTER: A ∪ B
Q3 · What does LEFT JOIN return when there is no matching row?
🔴 CriticalConcept

Q: What does LEFT JOIN return when there is no matching row in the right table?

A: It returns all rows from the LEFT table regardless. For columns that come from the RIGHT table, it fills them with NULL where no match was found.

left_join.sql
SELECT c.name, o.order_id FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id; -- Result: customers with no orders get NULL for order_id -- name: Alice | order_id: 1001 -- name: Bob | order_id: NULL ← no matching order
Use LEFT JOIN to find customers who have never placed an order: add WHERE o.order_id IS NULL
Q4 · What is the difference between LEFT JOIN and RIGHT JOIN?
🟡 High ImpactConcept

Q: What is the difference between LEFT JOIN and RIGHT JOIN?

A: LEFT JOIN keeps all rows from the first (left) table. RIGHT JOIN keeps all rows from the second (right) table. They are mirror images — any RIGHT JOIN can be rewritten as a LEFT JOIN by swapping the table order. In practice, RIGHT JOIN is rarely used because swapping tables is cleaner.

left_vs_right.sql
-- These two queries return the same result: SELECT * FROM A LEFT JOIN B ON A.id = B.id; SELECT * FROM B RIGHT JOIN A ON A.id = B.id;
Most teams prefer LEFT JOIN by convention — same power, better readability.
Q5 · What is the Cartesian Product and which JOIN produces it?
🔴 CriticalConcept

Q: What is the Cartesian product and which JOIN produces it?

A: The Cartesian product is every possible combination of rows from two tables. If Table A has 3 rows and Table B has 4 rows, the result is 3 × 4 = 12 rows. CROSS JOIN produces this intentionally. An INNER JOIN without an ON condition also produces it accidentally.

customers (3 rows) × products (4 rows) = 12 combined rows [Alice,ProductA] [Alice,ProductB] [Alice,ProductC] [Alice,ProductD] [Bob,ProductA] [Bob,ProductB] [Bob,ProductC] [Bob,ProductD] [Carol,ProductA] [Carol,ProductB] [Carol,ProductC] [Carol,ProductD]
Accidental Cartesian products on large tables can crash your database. Always double-check your ON clause!

🔴 Section 2 — JOIN Types Deep Dive

Q6 · What is a FULL OUTER JOIN and when would you use it?
🔴 CriticalJOIN Type

Q: What is FULL OUTER JOIN and when would you use it?

A: FULL OUTER JOIN returns all rows from both tables. Where there is no match, NULL fills the columns from the other table. Use it when you need to see ALL data from both sides — matched and unmatched — such as reconciling two systems for discrepancies.

full_outer.sql
SELECT a.id AS a_id, b.id AS b_id, a.name, b.name FROM system_a a FULL OUTER JOIN system_b b ON a.id = b.id; -- Rows only in system_a: b.id IS NULL -- Rows only in system_b: a.id IS NULL -- Matched rows: both sides filled
Real use: finding records that exist in System A but not B, and vice versa — perfect for data migration audits.
Q7 · What is a CROSS JOIN and what does it produce?
🟡 High ImpactJOIN Type

Q: What is CROSS JOIN and what does it produce?

A: CROSS JOIN produces the Cartesian product — every row in the left table paired with every row in the right table. There is no ON clause. It's intentional when you need all combinations, like generating a size/colour matrix for a clothing catalogue.

cross_join.sql
SELECT s.size, c.colour FROM sizes s CROSS JOIN colours c; -- sizes: S, M, L (3 rows) -- colours: Red, Blue (2 rows) -- Result: 6 combinations — S/Red, S/Blue, M/Red, M/Blue, L/Red, L/Blue
Also useful for generating date ranges or test data grids.
Q8 · What is a SELF JOIN and give a real-world example?
🔴 CriticalJOIN Type

Q: What is a SELF JOIN? Give a real-world example.

A: A SELF JOIN joins a table to itself. It's not a special syntax — you simply use two different aliases for the same table. The classic example is an employees table where each row has a manager_id pointing to another row in the same table.

self_join.sql
-- Find each employee and their manager's name SELECT e.name AS employee, m.name AS manager FROM employees e LEFT JOIN employees m ON e.manager_id = m.employee_id; -- Result: -- Alice | NULL (CEO, no manager) -- Bob | Alice (reports to Alice) -- Carol | Bob (reports to Bob)
SELF JOIN is essential for hierarchical data: org charts, category trees, bill-of-materials.
Q9 · What is a NATURAL JOIN and why is it considered risky?
🟡 High ImpactJOIN Type

Q: What is a NATURAL JOIN and why is it avoided in production?

A: NATURAL JOIN automatically joins on all columns with the same name in both tables — no ON clause needed. It's risky because if someone adds a column to either table with a matching name, the join condition silently changes and the query returns wrong results with no error.

natural_join.sql
-- Risky: joins on ALL shared column names (customer_id, AND maybe 'status' too) SELECT * FROM customers NATURAL JOIN orders; -- Safe: always be explicit SELECT * FROM customers c JOIN orders o ON c.customer_id = o.customer_id;
NATURAL JOIN is a maintenance time-bomb. Schema changes silently alter query behaviour. Never use in production code.
Q10 · What is the difference between ON and USING?
🟡 High ImpactSyntax

Q: What is the difference between ON and USING in a JOIN?

A: Both specify the join condition. ON is flexible — you can join on different column names, apply expressions, or use multiple conditions. USING is shorthand when both tables share an identically-named column; it also de-duplicates that column in SELECT *.

on_vs_using.sql
-- ON: flexible, explicit SELECT * FROM customers c JOIN orders o ON c.customer_id = o.customer_id; -- USING: shorthand when column names match SELECT * FROM customers JOIN orders USING (customer_id); -- customer_id appears once in result, not twice
USING only works when column names are identical. ON handles everything else — different names, ranges, computed conditions.

🟡 Section 3 — Advanced JOINs

Q11 · What is an equi-join vs a non-equi-join?
🟡 High ImpactSyntax

Q: What is an equi-join versus a non-equi-join?

A: An equi-join uses the equality operator (=) in the ON clause — the most common type. A non-equi-join uses other operators: <, >, BETWEEN, !=. Non-equi-joins are useful for range lookups like salary bands or price tiers.

non_equi_join.sql
-- Non-equi-join: find which salary band each employee falls into SELECT e.name, e.salary, sb.band_name FROM employees e JOIN salary_bands sb ON e.salary BETWEEN sb.min_salary AND sb.max_salary;
Q12 · How do you JOIN more than two tables in a single query?
🔴 CriticalSyntax

Q: Can you join more than two tables, and how?

A: Yes. You chain JOIN clauses sequentially. Each JOIN adds another table to the result set built so far. The database processes them left to right, and each new ON clause can reference any previously-joined table.

multi_join.sql
SELECT c.name AS customer, o.amount, p.name AS product, s.city AS shipped_to FROM customers c JOIN orders o ON c.customer_id = o.customer_id JOIN products p ON o.product_id = p.product_id LEFT JOIN shipments s ON o.order_id = s.order_id; -- Mix JOIN types freely — e.g. LEFT JOIN for optional shipment data
You can freely mix INNER JOIN and LEFT JOIN in the same query — choose per relationship based on whether the link is mandatory.
Q13 · Can you join on multiple columns — how and when?
🟡 High ImpactSyntax

Q: Can you use multiple conditions in a JOIN?

A: Yes, use AND inside the ON clause. This is necessary when the relationship between two tables requires multiple columns to be equal — typically for composite primary keys, or when a single column is not unique enough to correctly identify the match.

multi_condition.sql
-- Composite key join: order lines matched by both order_id AND product_id SELECT ol.quantity, p.name, p.price FROM order_lines ol JOIN products p ON ol.product_id = p.product_id AND ol.warehouse_id = p.warehouse_id; -- Both columns must match for a valid join
Q14 · What is the purpose of table aliases in JOIN queries?
🟡 High ImpactSyntax

Q: What is the purpose of table aliases (c, o, e, etc.) in JOIN queries?

A: Aliases shorten long table names to readable abbreviations, resolve ambiguity when multiple tables share column names, and are mandatory in SELF JOINs where the same table needs two distinct references in the same query.

aliases.sql
-- Without aliases: verbose and ambiguous SELECT customers.name, orders.amount FROM customers JOIN orders ON customers.customer_id = orders.customer_id; -- With aliases: clean and required for SELF JOIN SELECT c.name, o.amount FROM customers c JOIN orders o ON c.customer_id = o.customer_id; -- SELF JOIN: aliases are mandatory SELECT e.name, m.name FROM employees e JOIN employees m ON e.manager_id = m.employee_id;
Q15 · What is a LATERAL JOIN and how is it different from a regular JOIN?
🟡 High ImpactAdvanced

Q: What is a LATERAL JOIN and how does it differ from a regular JOIN?

A: A LATERAL JOIN (or CROSS JOIN LATERAL) allows the subquery on the right side to reference columns from tables on the left side — something a regular subquery cannot do. It's like a correlated subquery but usable as a join, often used to fetch the "top N per group".

lateral_join.sql
-- Get the 3 most recent orders per customer SELECT c.name, recent.order_id, recent.amount FROM customers c CROSS JOIN LATERAL ( SELECT order_id, amount FROM orders o WHERE o.customer_id = c.customer_id -- references outer table ← LATERAL magic ORDER BY created_at DESC LIMIT 3 ) recent;
In MySQL this is JOIN … SUBQUERY. In PostgreSQL and modern SQL it's LATERAL. The key feature: the subquery sees each row of the outer table.
Q16 · What is the difference between JOIN and UNION?
🟡 High ImpactConcept

Q: What is the difference between JOIN and UNION?

A: JOIN combines tables horizontally — it adds more columns by matching rows. UNION combines tables vertically — it stacks rows on top of each other. JOIN requires a relationship condition; UNION requires the same number and type of columns in both queries.

JOIN → horizontal (more columns): customers + orders = [customer_id | name | order_id | amount] UNION → vertical (more rows): SELECT name FROM customers UNION SELECT name FROM suppliers = stacked list of all names
JOIN = wider result. UNION = taller result.

🟡 Section 4 — NULLs, Duplicates & WHERE vs ON

Q17 · What happens when you JOIN on a column that has NULL values?
🔴 CriticalGotcha

Q: What happens when you JOIN on a column that has NULL values?

A: NULL never equals anything, including another NULL. So NULL = NULL evaluates to UNKNOWN, not TRUE. This means rows with NULL in the join column will never match any row — they are silently excluded from INNER JOIN results. In a LEFT JOIN, the left-side NULL row appears but never finds a match on the right.

null_join.sql
-- employees: id=1 dept_id=NULL, id=2 dept_id=10 -- departments: id=10 name='HR' SELECT e.name, d.name FROM employees e JOIN departments d ON e.dept_id = d.id; -- Only returns id=2 / HR. Employee with NULL dept_id is excluded.
NULL in join columns = silent data loss in INNER JOIN. Always check for unexpected NULLs in foreign key columns.
Q18 · The critical difference: WHERE vs ON in a LEFT JOIN
🔴 CriticalGotcha

Q: How does a LEFT JOIN behave differently when a filter is in ON vs WHERE?

A: Condition in ON: filters rows during the join — unmatched left rows still appear (with NULLs). Condition in WHERE: filters after the join — this effectively converts the LEFT JOIN into an INNER JOIN because left rows with NULL right-side columns get filtered out.

on_vs_where.sql
-- Filter in ON → keeps all customers, shows only 2024 orders (or NULL) SELECT c.name, o.amount FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.year = 2024; -- ← in ON clause -- Filter in WHERE → converts to INNER JOIN (customers with no 2024 orders disappear!) SELECT c.name, o.amount FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id WHERE o.year = 2024; -- ← in WHERE clause
This is one of the most common SQL interview gotcha questions. Moving a filter from ON to WHERE in a LEFT JOIN changes the semantics entirely.
Q19 · How do duplicate matching rows affect JOIN results?
🟡 High ImpactGotcha

Q: How do duplicate matching rows affect the result of a JOIN?

A: A JOIN produces one output row for every pair of matching rows. If the right table has 3 rows matching a single left row, you get 3 output rows — the left row is duplicated. This is called a fan-out and can dramatically inflate result counts, especially if both sides have duplicates (multiplicative effect).

duplicates.sql
-- Customer Alice has 3 orders → 3 output rows for Alice -- If orders also JOIN to tags with 2 tags each → 3×2 = 6 rows for Alice! -- Fix: use DISTINCT or aggregate SELECT DISTINCT c.name, o.amount FROM customers c JOIN orders o ON c.customer_id = o.customer_id; -- Or use EXISTS instead of JOIN to avoid fan-out SELECT c.name FROM customers c WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
If your row count seems too high after a JOIN, suspect fan-out. Check for one-to-many relationships on both sides.
Q20 · How do you find rows in Table A that have no match in Table B?
🔴 CriticalPattern

Q: How do you find rows in Table A that have no match in Table B?

A: Use a LEFT JOIN and then filter WHERE the right-side key IS NULL. This is called an anti-join pattern. You can also use NOT EXISTS or NOT IN, but LEFT JOIN + IS NULL is often the most performant.

anti_join.sql
-- Customers who have NEVER placed an order SELECT c.name FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id WHERE o.customer_id IS NULL; -- Equivalent with NOT EXISTS (often same performance) SELECT c.name FROM customers c WHERE NOT EXISTS ( SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id );
LEFT JOIN + WHERE IS NULL = "anti-join". One of the most-asked SQL patterns in interviews.
Q21 · What is the difference between JOIN and subquery — when to prefer which?
🟡 High ImpactConcept

Q: What is the difference between JOIN and subquery — when do you prefer one over the other?

A: JOINs are better when you need columns from both tables in the result. Subqueries are cleaner when you only need data from one table but need to filter based on a condition from another. Modern query planners often produce the same execution plan for both, so readability matters most.

ScenarioPrefer
Need columns from both tablesJOIN
Check existence onlyEXISTS subquery
Anti-join (no match)LEFT JOIN IS NULL or NOT EXISTS
Aggregated filter (e.g. WHERE dept avg salary > X)Subquery or CTE
Top N per groupLATERAL JOIN or window function
Q22 · What is the difference between EXISTS and JOIN for checking related rows?
🟡 High ImpactConcept

Q: What is the difference between EXISTS and JOIN for checking related rows?

A: EXISTS stops as soon as it finds the first match (short-circuits) and never duplicates left-side rows. JOIN finds ALL matches and creates one row per pair. Use EXISTS when you only need to check presence — it's semantically clearer and avoids fan-out.

exists_vs_join.sql
-- JOIN: can duplicate customers with multiple orders SELECT DISTINCT c.name FROM customers c JOIN orders o ON c.customer_id = o.customer_id; -- EXISTS: no duplication, stops at first match, cleaner SELECT c.name FROM customers c WHERE EXISTS ( SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id );
Q23 · What happens if join columns have different data types?
🟡 High ImpactGotcha

Q: What happens if the join columns have different data types?

A: The database attempts implicit type casting. This can silently produce wrong results (e.g. '007' vs 7 as integers) and — critically — prevents index usage because the index is on the original type. The query becomes a full table scan, which kills performance on large tables.

type_mismatch.sql
-- BAD: user_id is INT in users but VARCHAR in logs → implicit cast, no index SELECT * FROM users u JOIN logs l ON u.user_id = l.user_id; -- slow! -- FIX: explicit cast to match types SELECT * FROM users u JOIN logs l ON u.user_id = CAST(l.user_id AS INT);
Type mismatches on join columns are a hidden performance killer. Always align data types — fix them at the schema level, not the query level.

🟡 Section 5 — Performance & Optimization

Q24 · What is the impact of missing indexes on JOIN performance?
🔴 CriticalPerformance

Q: What is the impact of missing indexes on JOIN performance?

A: Without an index on the join column, the database performs a full table scan for every row lookup — O(n) instead of O(log n). On a 1 million-row table joined to another 1 million-row table, this can mean trillions of comparisons. Adding an index on the foreign key column is the single most impactful JOIN performance fix.

indexes.sql
-- Always index foreign key columns used in JOINs CREATE INDEX idx_orders_customer_id ON orders (customer_id); -- Composite index for multi-column joins CREATE INDEX idx_order_lines_composite ON order_lines (order_id, product_id); -- Check what indexes exist EXPLAIN ANALYZE SELECT * FROM customers c JOIN orders o ON c.customer_id = o.customer_id; -- Look for: 'Index Scan' (good) vs 'Seq Scan' (might need index)
Index the foreign key side of every JOIN. Primary keys are already indexed — it's the FK column on the child table that's often missing.
Q25 · When would you use EXPLAIN ANALYZE for a join query?
🟡 High ImpactPerformance

Q: When would you use EXPLAIN ANALYZE for a join query?

A: Use EXPLAIN ANALYZE when a join query is slow or you want to verify it's using indexes. It shows the actual query plan — which join algorithm was chosen, whether indexes were used, actual vs estimated row counts, and where the most time was spent. It's the first diagnostic tool for slow joins.

explain.sql
EXPLAIN ANALYZE SELECT c.name, o.amount FROM customers c JOIN orders o ON c.customer_id = o.customer_id WHERE c.country = 'India'; -- What to look for in output: -- "Index Scan" → good, using index -- "Seq Scan" → might need index or table is small -- "Hash Join" / "Nested Loop" → join algorithm chosen -- rows=X (actual=Y) → large mismatch = stale statistics, run ANALYZE
In PostgreSQL: use EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) for even richer output. In MySQL: use EXPLAIN FORMAT=JSON.
Q26 · How would you optimise a slow JOIN query — step by step?
🔴 CriticalPerformance

Q: How would you optimise a slow JOIN query — what steps would you take?

A: Systematic approach:

  1. Run EXPLAIN ANALYZE — identify the bottleneck (Seq Scan? Hash Join on huge table?)
  2. Check indexes — add index on FK columns involved in the join
  3. Filter early — add WHERE clauses to reduce rows before the join
  4. Check data types — ensure join column types match (no implicit cast)
  5. Update statistics — run ANALYZE / UPDATE STATISTICS
  6. Consider query rewrite — CTE, EXISTS, or subquery may be more efficient
  7. Check for fan-out — unexpected row count explosion
  8. Partition large tables if filtering on a partition key
Start with EXPLAIN ANALYZE → find the slowest node → fix indexes → re-check plan. Repeat until satisfied.

🟡 Section 6 — JOIN Algorithms & Internals

Q27 · How does a JOIN work internally — what algorithms does the database use?
🔴 CriticalInternals

Q: What are hash join, merge join, and nested loop join — when does the planner choose each?

A: There are three main join algorithms:

AlgorithmHow it worksBest forComplexity
Nested LoopFor each row in outer table, scan inner tableSmall tables, indexed innerO(n × m)
Hash JoinBuild hash table of smaller table, probe with largerLarge unsorted tables, equality joinsO(n + m)
Merge JoinBoth tables sorted on join key, scan in parallelPre-sorted data or index on join keyO(n log n + m log m)
join_algorithms.sql
-- Force a specific algorithm (PostgreSQL) for testing: SET enable_hashjoin = off; SET enable_nestloop = off; -- Now only merge join will be chosen -- See which algorithm was actually used: EXPLAIN SELECT * FROM A JOIN B ON A.id = B.id; -- Output: "Hash Join" / "Merge Join" / "Nested Loop"
The query planner picks the algorithm automatically based on table sizes and statistics. You can influence it with indexes and by running ANALYZE to update statistics.
Q28 · How do you remove duplicate rows after a JOIN?
🟡 High ImpactPattern

Q: How do you remove duplicate rows that appear after a JOIN?

A: Several approaches depending on the cause: DISTINCT to deduplicate the final result, GROUP BY to aggregate duplicates, EXISTS instead of JOIN to avoid fan-out entirely, or a window function like ROW_NUMBER() to pick one row per group.

dedup.sql
-- Method 1: DISTINCT (quick but may hide problems) SELECT DISTINCT c.name FROM customers c JOIN orders o ...; -- Method 2: GROUP BY (when you need aggregation) SELECT c.name, COUNT(o.order_id) AS order_count FROM customers c JOIN orders o ... GROUP BY c.name; -- Method 3: ROW_NUMBER() — pick 1 row per customer (most recent order) WITH ranked AS ( SELECT c.name, o.amount, ROW_NUMBER() OVER (PARTITION BY c.customer_id ORDER BY o.created_at DESC) rn FROM customers c JOIN orders o ON c.customer_id = o.customer_id ) SELECT name, amount FROM ranked WHERE rn = 1;
Q29 · How do you JOIN a table to itself to find hierarchical data?
🟡 High ImpactPattern

Q: How do you JOIN a table to itself to find hierarchical data like employees and managers?

A: Use a SELF JOIN with two aliases. The table plays two roles simultaneously — once as the "child" and once as the "parent". Use LEFT JOIN so the top-level nodes (with no parent) also appear in results.

hierarchy.sql
-- employees: emp_id | name | manager_id -- manager_id references emp_id in the SAME table SELECT e.name AS employee, m.name AS manager, COALESCE(m.name, 'Top Level') AS reports_to FROM employees e LEFT JOIN employees m ON e.manager_id = m.emp_id ORDER BY m.name NULLS LAST, e.name; -- For unlimited depth hierarchies, use recursive CTEs instead: WITH RECURSIVE org_tree AS ( SELECT emp_id, name, manager_id, 0 AS level FROM employees WHERE manager_id IS NULL UNION ALL SELECT e.emp_id, e.name, e.manager_id, ot.level + 1 FROM employees e JOIN org_tree ot ON e.manager_id = ot.emp_id ) SELECT * FROM org_tree;
For hierarchy with known depth → SELF JOIN. For unlimited depth → Recursive CTE. Both are interview favourites.
