CTE 1 — What is a CTE and Why Do We Need It?

🔴 Critical Foundation Beginner

Q: What is a CTE in PostgreSQL?

A: CTE stands for Common Table Expression. It is a temporary, named result set that you define at the start of a query using the WITH keyword. It lives only for the duration of that one query. Think of it as giving a name to a subquery so you can refer to it clearly and reuse it.

🧠 Analogy: Writing a long essay — instead of cramming everything into one giant sentence, you break it into clear paragraphs with headings. Each CTE is a named paragraph. The final SELECT is the conclusion that uses all the paragraphs.
WITHOUT CTE (nested, hard to read): ───────────────────────────────────────── SELECT d.name, ds.avg_sal FROM departments d JOIN (SELECT dept_id, AVG(salary) AS avg_sal FROM employees GROUP BY dept_id HAVING AVG(salary) > 60000) AS ds ON d.id = ds.dept_id; WITH CTE (named steps, easy to read): ───────────────────────────────────────── WITH high_paying AS ( SELECT dept_id, AVG(salary) AS avg_sal FROM employees GROUP BY dept_id HAVING AVG(salary) > 60000 ) SELECT d.name, h.avg_sal FROM departments d JOIN high_paying h ON d.id = h.dept_id;
✅ CTE = a named temporary result set. Defined with WITH before the main query. Makes complex SQL readable, debuggable, and reusable within the same query.
🔴 Critical — Syntax

CTE 2 — WITH Clause — Full Syntax Explained

🔴 Critical Syntax
Syntax skeleton: ────────────────────────────────────────────────── WITH cte_name AS ( -- your inner query here SELECT ... FROM ... WHERE ... ) SELECT ... ← main query uses cte_name like a table FROM cte_name WHERE ...;
1
Start with WITH

Write WITH before your main SELECT. This opens the CTE block.

2
Give it a name

Choose a meaningful name like high_salary_employees or dept_summary.

3
Write the inner query inside AS ( )

Any valid SELECT goes here. This becomes a virtual table.

4
Use the name in the main query

After the closing ), write your main SELECT using the CTE name like any table.

with_syntax.sql
── Example 1: Basic CTE ─────────────────────────────────────────────── -- Find employees earning above average salary WITH avg_salary AS ( SELECT AVG(salary) AS avg_sal FROM employees ) SELECT name, salary FROM employees, avg_salary WHERE salary > avg_sal; ── Example 2: CTE with filtering ───────────────────────────────────── WITH senior_employees AS ( SELECT id, name, salary, dept_id FROM employees WHERE years_of_experience >= 5 ) SELECT se.name, se.salary, d.name AS department FROM senior_employees se JOIN departments d ON d.id = se.dept_id ORDER BY se.salary DESC; ── Example 3: CTE used in UPDATE ───────────────────────────────────── WITH top_performers AS ( SELECT id FROM employees WHERE performance_score >= 9 ) UPDATE employees SET salary = salary * 1.15 WHERE id IN (SELECT id FROM top_performers); -- CTE works with UPDATE, DELETE, INSERT too — not just SELECT
✅ CTE is available for the entire duration of that single query — SELECT, INSERT, UPDATE, or DELETE. It vanishes once the query finishes.
💡 Column aliasing tip: You can optionally name the CTE's columns upfront: WITH cte(col1, col2) AS (SELECT ...) — useful when the inner query uses expressions without aliases.
🟡 High Impact — Advanced

CTE 3 — Chaining Multiple CTEs — Write Once, Build on Each Other

🟡 High Impact Advanced

Q: Can you define more than one CTE in a single query?

A: Yes. Separate each CTE with a comma. Later CTEs can reference earlier ones — building logic step by step like a pipeline. This is the key power of CTEs over subqueries.

WITH step1 AS ( SELECT ... ), ← first CTE step2 AS ( SELECT ... FROM step1 ),← references step1! step3 AS ( SELECT ... FROM step2 ) ← references step2! SELECT ... FROM step3; ← final query
multiple_cte.sql
── Real Example: Sales Pipeline Analysis ───────────────────────────── -- Step 1: Get total revenue per customer -- Step 2: Classify customers into tiers -- Step 3: Count customers per tier WITH -- CTE 1: revenue per customer customer_revenue AS ( SELECT customer_id, SUM(amount) AS total_revenue FROM orders WHERE status = 'completed' GROUP BY customer_id ), -- CTE 2: classify into tiers (references CTE 1) customer_tiers AS ( SELECT customer_id, total_revenue, CASE WHEN total_revenue >= 10000 THEN 'Gold' WHEN total_revenue >= 5000 THEN 'Silver' ELSE 'Bronze' END AS tier FROM customer_revenue -- ← uses CTE 1 ), -- CTE 3: summary per tier (references CTE 2) tier_summary AS ( SELECT tier, COUNT(*) AS customer_count, SUM(total_revenue) AS tier_revenue FROM customer_tiers -- ← uses CTE 2 GROUP BY tier ) -- Final query: uses CTE 3 SELECT tier, customer_count, tier_revenue FROM tier_summary ORDER BY tier_revenue DESC;
✅ Each CTE in the chain is separated by a comma. Only the last CTE has no comma after it. Then the main SELECT follows.
📌 Debugging tip: You can test each CTE independently — just run the inner SELECT on its own to verify it returns what you expect before combining them.
🔴 Interview Favourite — Comparison

CTE 4 — CTE vs Subquery — Side-by-Side Comparison

🔴 Interview Favourite Comparison

Subquery

  • Inline — no name
  • Cannot be reused in same query
  • Messy when nested 2+ levels
  • Can't be tested in isolation
  • Good for simple one-liner cases
  • No recursion support

CTE (WITH)

  • Named — readable and clear
  • ✅ Can be referenced multiple times
  • ✅ Clean for multi-step logic
  • ✅ Each CTE testable independently
  • ✅ Works with UPDATE/DELETE too
  • ✅ Recursive queries supported
cte_vs_subquery.sql
── Same logic — Subquery version (messy) ───────────────────────────── SELECT d.name, ds.avg_salary, ds.headcount FROM departments d JOIN (SELECT dept_id, AVG(salary) AS avg_salary, COUNT(*) AS headcount FROM employees GROUP BY dept_id) AS ds ON d.id = ds.dept_id WHERE ds.avg_salary > 60000; ── Same logic — CTE version (clean) ────────────────────────────────── WITH dept_stats AS ( SELECT dept_id, AVG(salary) AS avg_salary, COUNT(*) AS headcount FROM employees GROUP BY dept_id ) SELECT d.name, ds.avg_salary, ds.headcount FROM departments d JOIN dept_stats ds ON d.id = ds.dept_id WHERE ds.avg_salary > 60000; ── CTE referenced TWICE — impossible with subquery ─────────────────── WITH dept_stats AS ( SELECT dept_id, AVG(salary) AS avg_sal, MAX(salary) AS max_sal FROM employees GROUP BY dept_id ) SELECT d.name, ds.avg_sal, ds.max_sal, ds.max_sal - ds.avg_sal AS spread FROM departments d JOIN dept_stats ds ON d.id = ds.dept_id;
✅ Rule of thumb: Subquery for simple one-off filters. CTE when logic has multiple steps, the result is used more than once, or the query is complex enough to need named clarity.
🔴 Critical — Recursive

CTE 5 — Recursive CTE — Querying Hierarchical Data

🔴 Critical Recursive

Q: What is a Recursive CTE and when do you need one?

A: A Recursive CTE is a CTE that references itself. It works in two parts: an Anchor query (the starting point) and a Recursive query (which builds on the previous result). PostgreSQL keeps running the recursive part, adding new rows, until no more rows are returned. Use it for hierarchical or graph-like data — org charts, folder trees, category hierarchies.

🧠 Analogy: Climbing a tree — you start at the root (anchor). Then you keep finding the children of what you found (recursive step). You stop when a level has no children left.
WITH RECURSIVE cte_name AS ( -- PART 1: Anchor — starting rows (runs ONCE) SELECT ... FROM table WHERE condition UNION ALL -- PART 2: Recursive step — joins CTE to itself (runs REPEATEDLY) SELECT ... FROM table JOIN cte_name ON ... ← references itself! ) SELECT * FROM cte_name; Execution flow: Anchor runs → produces Set 1 Recursive step on Set 1 → produces Set 2 Recursive step on Set 2 → produces Set 3 ... until empty set → STOP
recursive_cte.sql
── Classic example: Employee → Manager org hierarchy ───────────────── -- employees(id, name, manager_id) WITH RECURSIVE org_chart AS ( -- Anchor: start at the CEO (no manager) SELECT id, name, manager_id, 0 AS level FROM employees WHERE manager_id IS NULL UNION ALL -- Recursive: find each employee's direct reports SELECT e.id, e.name, e.manager_id, oc.level + 1 FROM employees e JOIN org_chart oc ON e.manager_id = oc.id -- self-join! ) SELECT REPEAT(' ', level) || name AS name_indented, level FROM org_chart ORDER BY level, name;
⚠️ Infinite loop risk: Always ensure the recursive step makes progress toward termination. Add a WHERE level < 10 guard clause during development to prevent runaway queries on cyclic data.
📌 PostgreSQL also supports WITH RECURSIVE for number series generation: SELECT n FROM generate_series(1,100) AS n is preferred, but recursive CTEs work cross-database for portability.
