🔴 Numeric Types

01 Numeric Types — Integer, Float, Exact Decimal
🔴 CriticalNumbers

Q: What numeric types does PostgreSQL offer?

A: Three families — integers (whole numbers, no decimals), floating point (approximate decimals, fast), and numeric/decimal (exact decimals, used for money). Choose based on whether you need exact precision or are OK with approximation.

🔢 Integer Types

SMALLINT
2 bytes · -32,768 to 32,767
Tiny whole numbers. Save space when range is small.
age SMALLINT
INTEGER / INT
4 bytes · -2.1B to 2.1B
Standard whole number. Default choice for IDs and counts.
quantity INT
BIGINT
8 bytes · ±9.2 quintillion
Large whole numbers. Use for user IDs, event IDs at scale.
user_id BIGINT
SERIAL
4 bytes · auto-increment
Auto-incrementing INTEGER. Shorthand for sequence + default.
id SERIAL PRIMARY KEY
BIGSERIAL
8 bytes · auto-increment
Auto-incrementing BIGINT. Use when SERIAL's 2.1B limit isn't enough.
id BIGSERIAL PRIMARY KEY
SMALLSERIAL
2 bytes · rare
Auto-incrementing SMALLINT. Almost never used in practice.
id SMALLSERIAL

🔣 Floating Point Types

REAL
4 bytes · ~6 decimal digits
Single-precision float. Approximate — small rounding errors. Fast.
temperature REAL
DOUBLE PRECISION
8 bytes · ~15 decimal digits
Double-precision float. More accurate than REAL. Still approximate.
score DOUBLE PRECISION

💰 Exact Decimal Types

NUMERIC(p,s)
Variable · exact precision
Exact decimal. p = total digits, s = digits after decimal. Use for money, tax, financial data where rounding errors are unacceptable.
price NUMERIC(10,2)
DECIMAL(p,s)
Same as NUMERIC
Alias for NUMERIC. Identical behaviour — NUMERIC is preferred in PostgreSQL.
amount DECIMAL(12,4)
numeric_types.sql
CREATE TABLE demo_numeric ( id BIGSERIAL PRIMARY KEY, age SMALLINT, -- 0-32767, saves space quantity INTEGER, -- standard whole number views BIGINT, -- large counts temperature REAL, -- ~25.6 (approximate OK) score DOUBLE PRECISION, -- more decimal places price NUMERIC(10,2), -- 99999999.99 — exact! tax_rate NUMERIC(5,4) -- 0.1875 — exact! ); -- Float rounding issue (use NUMERIC for money!) SELECT 0.1::REAL + 0.2::REAL; -- 0.3000000119... ❌ rounding! SELECT 0.1::NUMERIC + 0.2::NUMERIC; -- 0.3 ✅ exact!
⚠️ Never use REAL or DOUBLE PRECISION for money. Floating point has rounding errors — use NUMERIC(p,s) for any financial value.
✅ Integer for whole numbers · NUMERIC for exact decimals (money) · REAL/DOUBLE for science/approximations

🔴 Text / String Types

02 Text Types — VARCHAR, TEXT, CHAR
🔴 CriticalText

Q: What are the text types in PostgreSQL and which should you use?

A: PostgreSQL has three: TEXT (unlimited length, recommended), VARCHAR(n) (limited length), and CHAR(n) (fixed length, pads with spaces). In PostgreSQL, TEXT and VARCHAR have identical performance — there is no speed advantage to using VARCHAR over TEXT. Use TEXT by default.

TEXT
Variable · unlimited length
Best general-purpose string type. No length limit. Same performance as VARCHAR. Preferred in PostgreSQL.
description TEXT
VARCHAR(n)
Variable · max n characters
Like TEXT but enforces a max length. Useful when you want the DB to reject strings that are too long (email, username).
email VARCHAR(255)
CHAR(n)
Fixed n characters · pads with spaces
Always stores exactly n characters. Pads short strings with spaces. Almost never useful — avoid it.
code CHAR(3) → 'US '
text_types.sql
CREATE TABLE users ( username VARCHAR(50), -- max 50 chars enforced email VARCHAR(255), -- max 255 chars bio TEXT, -- unlimited — no length concern country_code CHAR(2) -- always 2 chars: 'US', 'IN', 'GB' ); -- TEXT and VARCHAR — identical performance in PostgreSQL SELECT length('hello'::TEXT); -- 5 SELECT length('hello'::CHAR(10)); -- 5 (trailing spaces trimmed on length) SELECT 'hi'::CHAR(5) = 'hi '; -- true (spaces added) -- Useful text functions SELECT UPPER('hello'); -- HELLO SELECT LOWER('WORLD'); -- world SELECT TRIM(' hi '); -- hi SELECT SUBSTRING('hello', 1, 3); -- hel SELECT 'hello' || ' world'; -- hello world (concatenate)
💡 PostgreSQL recommendation: use TEXT for most columns. Use VARCHAR(n) only when you want the DB to enforce a max length as a constraint. Avoid CHAR(n) entirely.

🔴 Boolean Type

03 BOOLEAN — True, False, Unknown
🔴 CriticalBoolean

Q: How does BOOLEAN work in PostgreSQL?

A: BOOLEAN stores TRUE, FALSE, or NULL (unknown). PostgreSQL accepts many input formats — 'true', 'yes', '1', 't' all become TRUE. It uses 1 byte of storage. Never use an INTEGER column to store 0/1 flags — use BOOLEAN instead for clarity and type safety.

boolean.sql
CREATE TABLE products ( id SERIAL PRIMARY KEY, name TEXT, is_active BOOLEAN DEFAULT true, in_stock BOOLEAN DEFAULT false ); -- All of these are TRUE: SELECT 'true'::BOOLEAN; -- t SELECT 'yes'::BOOLEAN; -- t SELECT '1'::BOOLEAN; -- t SELECT 'on'::BOOLEAN; -- t -- Filter boolean columns SELECT * FROM products WHERE is_active = true; SELECT * FROM products WHERE is_active; -- same thing SELECT * FROM products WHERE NOT is_active; -- false rows SELECT * FROM products WHERE is_active IS NULL; -- unknown
✅ 1 byte · TRUE/FALSE/NULL · Use it for all flag/status columns. WHERE is_active is cleaner than WHERE is_active = true.

🟡 Date & Time Types

04 Date & Time — DATE, TIME, TIMESTAMP, INTERVAL
🟡 High ImpactTemporal

Q: What date/time types exist in PostgreSQL and which should you use?

A: PostgreSQL has DATE (date only), TIME (time only), TIMESTAMP (date + time, no timezone), TIMESTAMPTZ (date + time + timezone — recommended), and INTERVAL (a duration). Always use TIMESTAMPTZ over TIMESTAMP in production — it stores UTC internally and converts to local time on read.

DATE
4 bytes · date only
Year, month, day only. No time component. Range: 4713 BC to 5874897 AD.
birth_date DATE → '1990-06-15'
TIME
8 bytes · time of day
Time only, no date. TIME WITH TIME ZONE also available but rarely used.
opening_time TIME → '09:30:00'
TIMESTAMP
8 bytes · no timezone
Date + time, no timezone info stored. Ambiguous across timezones. Avoid in production.
created_at TIMESTAMP ⚠️
TIMESTAMPTZ
8 bytes · with timezone ✅
Date + time stored as UTC, displayed in session timezone. The correct choice for production timestamps.
created_at TIMESTAMPTZ ✅
INTERVAL
16 bytes · duration
A period of time — days, hours, months. Used for date arithmetic.
duration INTERVAL → '3 hours 30 mins'
datetime.sql
CREATE TABLE events ( id BIGSERIAL PRIMARY KEY, event_date DATE, -- '2024-03-15' start_time TIME, -- '09:00:00' created_at TIMESTAMPTZ DEFAULT NOW(), -- always use TZ ✅ duration INTERVAL -- '2 hours 30 minutes' ); -- Useful date/time operations SELECT NOW(); -- current timestamp with TZ SELECT CURRENT_DATE; -- today's date SELECT NOW() - INTERVAL '7 days'; -- 7 days ago SELECT AGE(NOW(), '1990-06-15'); -- how long ago SELECT DATE_TRUNC('month', NOW()); -- first of current month SELECT EXTRACT(YEAR FROM NOW()); -- 2025 SELECT '2024-01-01'::DATE + INTERVAL '30 days'; -- Jan 31 -- INTERVAL literals SELECT INTERVAL '1 year 2 months 3 days'; SELECT INTERVAL '04:30:00'; -- 4 hours 30 minutes
⚠️ Always use TIMESTAMPTZ not TIMESTAMP in production. TIMESTAMP has no timezone info — when your app moves servers or changes timezone, stored times become ambiguous and wrong.

🟡 Binary Type

05 BYTEA — Binary Data Storage
🟡 Know ItBinary

Q: What is BYTEA and when do you use it?

A: BYTEA stores raw binary data — image bytes, file contents, encrypted blobs, hashes. It stores any byte sequence including null bytes. It's the PostgreSQL equivalent of BLOB in other databases.

bytea.sql
CREATE TABLE files ( id SERIAL PRIMARY KEY, filename TEXT, content BYTEA, -- raw binary checksum BYTEA -- MD5/SHA hash bytes ); -- Insert binary data (hex escape notation) INSERT INTO files (filename, content) VALUES ('photo.jpg', '\xFFD8FFE0...'::BYTEA); -- Store hash as BYTEA SELECT digest('hello', 'sha256')::BYTEA; -- Get byte length SELECT length(content) FROM files; -- Convert to hex string SELECT encode(content, 'hex') FROM files; SELECT encode(content, 'base64') FROM files;
💡 For large files (images, PDFs), store them in object storage (S3, GCS) and keep only the URL in PostgreSQL. BYTEA is best for small blobs — hashes, keys, thumbnails under ~1MB.

🟡 Network Address Types

06 INET, CIDR, MACADDR — Network Types
🟡 UsefulNetwork

Q: Why use network types instead of TEXT for IP addresses?

A: Network-specific types give you built-in validation (rejects invalid IPs), indexing, and network operators like "is this IP in this subnet?". Storing IPs as TEXT loses all of that — you'd have to validate and query manually.

INET
7-19 bytes
IPv4 or IPv6 address, optionally with subnet mask. Most common network type.
ip INET → '192.168.1.1'
CIDR
7-19 bytes
Network address (host bits must be zero). Strictly for network ranges, not individual host IPs.
network CIDR → '192.168.0.0/24'
MACADDR
6 bytes
MAC hardware address. Useful for device tracking, network logs.
mac MACADDR → '08:00:2b:01:02:03'
network_types.sql
CREATE TABLE access_log ( id BIGSERIAL PRIMARY KEY, client_ip INET, mac_addr MACADDR, created_at TIMESTAMPTZ DEFAULT NOW() ); -- Network operators SELECT * FROM access_log WHERE client_ip <<= '192.168.1.0/24'; -- IPs in this subnet SELECT '192.168.1.5'::INET << '192.168.1.0/24'; -- true (in subnet) SELECT host('192.168.1.5/24'::INET); -- '192.168.1.5' SELECT masklen('192.168.1.0/24'::CIDR); -- 24
✅ INET validates IP format automatically. Use it over TEXT for any IP address column — you get subnet operators and GiST index support for free.

🟡 Geometric Types

07 Geometric Types — POINT, LINE, POLYGON, CIRCLE
🟡 SpecialistGeometry

Q: What geometric types does PostgreSQL support natively?

A: PostgreSQL has built-in geometric types for 2D shapes: POINT, LINE, LSEG, BOX, PATH, POLYGON, and CIRCLE. They come with geometric operators for distance, intersection, containment, and area. For serious geospatial work, use the PostGIS extension which adds full GIS capability.

POINT
16 bytes · (x,y)
A single point in 2D space. Most commonly used geometric type.
location POINT → '(1.5, 2.3)'
LINE / LSEG
32 bytes
LINE = infinite line. LSEG = finite line segment between two points.
path LSEG → '[(0,0),(1,1)]'
BOX
32 bytes
Rectangular box defined by two corner points.
area BOX → '(0,0),(1,1)'
POLYGON
Variable
Closed shape defined by a list of points.
region POLYGON → '((0,0),(1,0),(1,1))'
CIRCLE
24 bytes
Centre point + radius.
zone CIRCLE → '<(0,0),5>'
PostGIS
Extension
Full GIS extension — GEOMETRY, GEOGRAPHY, spatial indexes, coordinate systems. Use for real mapping applications.
GEOGRAPHY(POINT,4326)
geometric.sql
CREATE TABLE locations ( id SERIAL PRIMARY KEY, name TEXT, position POINT, -- (longitude, latitude) zone CIRCLE -- service area ); INSERT INTO locations (name, position, zone) VALUES ('HQ', '(12.97, 77.59)', '<(12.97,77.59),0.5>'); -- Distance between two points SELECT '(0,0)'::POINT <-> '(3,4)'::POINT; -- 5.0 (Pythagorean) -- Is point inside circle? SELECT '(1,1)'::POINT <@ '<(0,0),2>'::CIRCLE; -- true
💡 For GPS coordinates (lat/long), use PostGIS extension with GEOGRAPHY type — it handles Earth's curvature for accurate distance calculations. Native POINT treats the world as flat.

🟡 Special Types

08 Special Types — MONEY, SERIAL, XML, TSVECTOR, OID
🟡 Know ExistsSpecial
TypeSizeWhat it storesExample / Note
MONEY 8 bytes Currency amount with fixed 2 decimal places. Locale-dependent — avoid in new code. price MONEY → $1,234.56 ⚠️ Use NUMERIC(p,2) instead
XML Variable Stores valid XML documents. PostgreSQL validates XML on insert and has XPath query support. config XML — use JSONB unless XML is required
TSVECTOR Variable Pre-processed full-text search document. Used with TSQUERY for fast keyword search. search_tokens TSVECTOR
TSQUERY Variable A full-text search query — combined with TSVECTOR for document search. to_tsvector('hello world') @@ to_tsquery('hello')
OID 4 bytes Internal PostgreSQL object identifier. Used in system catalogs. Not for application use. Used in pg_class, pg_proc etc.
VOID — Return type for functions that return nothing. Cannot store in a column. RETURNS VOID in functions
special_types.sql
── Full-Text Search with TSVECTOR ──────────────────────────────────── CREATE TABLE articles ( id SERIAL PRIMARY KEY, title TEXT, body TEXT, tokens TSVECTOR -- pre-processed search tokens ); -- Populate tsvector column UPDATE articles SET tokens = to_tsvector('english', title || ' ' || body); -- Full-text search SELECT title FROM articles WHERE tokens @@ to_tsquery('english', 'postgres & replication'); -- Index for fast full-text search CREATE INDEX idx_articles_fts ON articles USING GIN (tokens); -- MONEY type (avoid — locale issues) SELECT '$1,234.56'::MONEY; -- locale-dependent ⚠️ -- Better: NUMERIC(10,2) for money
⚠️ Avoid MONEY type — it's locale-dependent and doesn't work well across different system locales. Always use NUMERIC(p,2) for currency values.
