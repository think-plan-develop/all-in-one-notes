1 What is a Transaction?
A transaction is an all-or-nothing operation. Transfer ₹5,000 from Account A to B — both the debit and the credit must succeed together, or neither happens.

Q: What is a transaction in SQL?

A: A transaction is a group of one or more SQL statements treated as a single unit of work. Either all of them succeed and are saved with COMMIT, or all are undone with ROLLBACK — no in-between state is ever visible.

Classic bank-transfer problem — without a transaction
Step 1Deduct ₹5,000 from A ✓
→
💥 System crashes
→
A lost ₹5,000, B got nothing
The same crash — with a transaction
Step 1Deduct ₹5,000 from A
→
💥 System crashes
→
Everything rolled back — A keeps its money ✅
2 Why Do We Use Transactions?
1

Data integrity across steps

When an operation spans several statements, transactions guarantee they all complete or all undo — no partial updates.

2

Recovery from failures

Server crash, network drop or app error mid-operation — the database returns to its last consistent state automatically.

3

Concurrent access safety

User A's half-done update is invisible to User B until it is committed.

4

Consistent business operations

Order placement = reduce inventory + create order + charge payment. All three together, or none.

📦 Real-world scenarios needing transactions

  • 💰 Bank transfer (debit + credit must pair)
  • 🛒 E-commerce order (stock + order + payment)
  • ✈️ Flight booking (seat + payment + confirmation)
  • 📊 Payroll (calculate + update all salaries atomically)
  • 🔄 Data migration (transform + insert + delete old)
  • 🏦 Ledger entries (debit must always equal credit)
3 ACID Properties

ACID is the set of four properties that make transactions reliable. PostgreSQL is fully ACID-compliant.

A
Atomicity
All statements succeed or none do. If step 5 of 10 fails, steps 1–4 are rolled back automatically.
C
Consistency
The database moves from one valid state to another. Constraints and rules hold before AND after.
I
Isolation
Concurrent transactions don't see each other's uncommitted changes.
D
Durability
Once committed, data is permanent — even if the server crashes right after. WAL is flushed before COMMIT is confirmed.
PropertyGuaranteesPostgreSQL mechanism
AtomicityAll or nothingROLLBACK + MVCC (aborted row versions are simply invisible)
ConsistencyValid state → valid stateConstraints, triggers, CHECK
IsolationTransactions don't interfereMVCC (Multi-Version Concurrency Control)
DurabilityCommitted data survives crashesWAL (Write-Ahead Logging), fsync

Q: What does ACID stand for, and how does PostgreSQL provide it?

A: Atomicity (all-or-nothing), Consistency (valid state transitions), Isolation (no interference between concurrent transactions) and Durability (committed data survives crashes). PostgreSQL achieves isolation through MVCC and durability through the write-ahead log (WAL).

✅ Success path → COMMIT

All statements run without error → constraints pass → COMMIT → changes are permanently written → locks released → other transactions see the new data.

❌ Failure path → ROLLBACK

Any statement fails → ROLLBACK → all changes undone → the database is back to its state at BEGIN → locks released → no data harmed.

📌 Constraints are checked per statement; only DEFERRABLE constraints wait until COMMIT. What a transaction "sees" depends on its isolation level (Topic 8).
5 BEGIN · COMMIT · ROLLBACK

▶ BEGIN

Starts a transaction block. Every following statement belongs to it until COMMIT or ROLLBACK.

BEGIN;
START TRANSACTION;

Identical in PostgreSQL.

✅ COMMIT

Makes all changes permanent, releases all locks, and lets other transactions see the data.

COMMIT;
COMMIT WORK;

After COMMIT, changes cannot be undone.

↩ ROLLBACK

Undoes all changes since BEGIN and releases all locks.

ROLLBACK;
ROLLBACK WORK;

Called on error or to cancel the operation.

-- Basic transaction structure
BEGIN;
  UPDATE accounts SET balance = balance - 5000 WHERE id = 1;
  UPDATE accounts SET balance = balance + 5000 WHERE id = 2;
COMMIT;                    -- both succeed → save permanently

-- Rollback on error
BEGIN;
  UPDATE accounts SET balance = balance - 5000 WHERE id = 1;
  -- error occurs here...
ROLLBACK;                  -- undo everything, money safe

-- PostgreSQL error state: once an error occurs in a transaction,
-- all later commands fail until ROLLBACK is issued:
-- ERROR: current transaction is aborted, commands ignored until end of transaction block
6 SAVEPOINT · ROLLBACK TO SAVEPOINT · RELEASE SAVEPOINT
A savepoint is a named checkpoint inside a transaction. Roll back to it and only the work after it is undone — the transaction stays active.
BEGIN;

  INSERT INTO users (name, email) VALUES ('Aman', 'a@x.com');

  SAVEPOINT after_user;       -- checkpoint 1

  INSERT INTO orders (user_id, total) VALUES (currval('users_id_seq'), 500);

  SAVEPOINT after_order;      -- checkpoint 2

  INSERT INTO payments (order_id, amount) VALUES (currval('orders_id_seq'), 500);
  -- payment fails!

ROLLBACK TO SAVEPOINT after_order;   -- undo only payment, keep user + order

  INSERT INTO payments (order_id, amount, method)
  VALUES (currval('orders_id_seq'), 500, 'UPI');    -- retry with UPI

RELEASE SAVEPOINT after_order;      -- clean up the savepoint

COMMIT;                             -- all saved!

-- KEY DIFFERENCE:
ROLLBACK TO SAVEPOINT sp1;  -- undo to sp1, transaction STILL ACTIVE
ROLLBACK;                   -- undo EVERYTHING, transaction ENDS
💡 Why currval('orders_id_seq') and not lastval()? Sequences are not rolled back. After the failed payment insert, lastval() would return the payments sequence value, not the order id. currval('sequence_name') always returns the one you mean (in apps, prefer RETURNING id).
CommandWhat it doesTransaction still active?
SAVEPOINT nameCreates a named checkpoint inside the transaction✅ Yes
ROLLBACK TO SAVEPOINT nameUndoes all work done after this savepoint✅ Yes — continues!
RELEASE SAVEPOINT nameRemoves the savepoint, keeps all changes✅ Yes
ROLLBACKUndoes everything from BEGIN❌ No — ends
7 Auto Commit vs Manual Commit

⚡ Auto Commit (default)

PostgreSQL wraps every statement in its own transaction and commits immediately.

UPDATE users SET name='Aman' WHERE id=1;
→ automatically: BEGIN → UPDATE → COMMIT

⚠️ Each statement commits independently — no rollback across several statements.

🛡️ Manual Commit (explicit BEGIN)

Write BEGIN yourself to control when changes commit. Several statements run as one atomic unit.

✅ All succeed together or all roll back together.

-- Auto commit: each statement is its own transaction
UPDATE accounts SET balance = balance - 5000 WHERE id = 1; -- committed!
UPDATE accounts SET balance = balance + 5000 WHERE id = 2; -- if this fails: money GONE 💸

-- Manual commit: safe
BEGIN;
  UPDATE accounts SET balance = balance - 5000 WHERE id = 1;
  UPDATE accounts SET balance = balance + 5000 WHERE id = 2;
COMMIT;                  -- if the second UPDATE fails → ROLLBACK, A keeps money ✅

-- In psql: wrap each statement in an implicit transaction block
\set AUTOCOMMIT off

-- In app code:
-- Python psycopg2:  conn.autocommit = False   (the default)
-- Node.js pg:       client.query('BEGIN')
-- Java JDBC:        conn.setAutoCommit(false)
8 Transaction Isolation Levels

Isolation levels control how much one transaction can see of another's concurrent changes. Higher isolation = more safety, usually more conflicts and retries.

The three concurrency problems

💀 Dirty Read

A reads data that B changed but has not committed. If B rolls back, A read data that never officially existed.

⚠️ Non-Repeatable Read

A reads a row, B updates and commits it, A reads the same row again and gets a different value — same query, different result.

👻 Phantom Read

A runs a range query, B inserts a matching row and commits, A repeats the query and sees a new "phantom" row.

Isolation LevelDirty ReadNon-RepeatablePhantomIn PostgreSQL
READ UNCOMMITTEDPossible*PossiblePossibleTreated as READ COMMITTED — dirty reads never happen
READ COMMITTEDPreventedPossiblePossibleDefault. Each statement sees a fresh snapshot
REPEATABLE READPreventedPreventedPossible*One snapshot per transaction — phantoms are also prevented
SERIALIZABLEPreventedPreventedPreventedStrictest; may fail with 40001 — retry
📌 *The first three columns show the SQL standard. PostgreSQL is stricter: READ UNCOMMITTED behaves as READ COMMITTED, and REPEATABLE READ already prevents phantom reads. Thanks to MVCC, readers never block writers and writers never block readers.
BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;    -- default
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Or set it right after BEGIN (before any query)
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Check the current level
SHOW transaction_isolation;

-- Use SERIALIZABLE for critical financial operations
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
  SELECT balance FROM accounts WHERE id = 1;
  UPDATE accounts SET balance = balance - 500 WHERE id = 1;
COMMIT;   -- may fail with serialization_failure (40001): retry the transaction

Q: What is PostgreSQL's default isolation level, and which anomalies does it allow?

A: READ COMMITTED. It prevents dirty reads, but a repeated query inside the same transaction can see other transactions' committed changes (non-repeatable and phantom reads). Use REPEATABLE READ or SERIALIZABLE when you need a stable view.

9 Locks & Concurrency (Basic)

MVCC handles most read/write scenarios without locks, but write/write conflicts need explicit locking. PostgreSQL provides row-level locks through SELECT … FOR.

🔓 Shared lock — FOR SHARE

Many transactions can hold a shared lock at once; it blocks writers only.

SELECT * FROM orders WHERE id=1 FOR SHARE;

🔒 Exclusive lock — FOR UPDATE

Only one transaction can hold it. Others wait until it's released at COMMIT / ROLLBACK.

SELECT * FROM orders WHERE id=1 FOR UPDATE;

-- FOR UPDATE: lock the row before modifying it (prevents lost updates)
BEGIN;
  SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
  UPDATE accounts SET balance = balance - 500 WHERE id = 1;
COMMIT;

-- NOWAIT: fail immediately if the row is locked
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
-- ERROR: could not obtain lock on row in relation "accounts"

-- SKIP LOCKED: skip locked rows (perfect for job queues)
SELECT * FROM tasks
WHERE  status = 'pending'
ORDER BY id
LIMIT  1
FOR UPDATE SKIP LOCKED;  -- pick the next unlocked task safely

-- View current locks
SELECT pid, relation::regclass, mode, granted
FROM   pg_locks WHERE relation IS NOT NULL;
10 Deadlock (Basic)
A deadlock is a circular wait: two transactions each hold a lock the other needs. PostgreSQL detects it automatically and kills one transaction (the "victim") with error 40P01.
How a deadlock happens
Transaction Aholds Row 1
→
wants Row 2waiting for B
Transaction Bholds Row 2
→
wants Row 1waiting for A
→
ERROR: deadlock detectedone is rolled back
BEGIN;
UPDATE accounts
SET balance = balance - 100
WHERE id = 1;   -- holds row 1

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;   -- WAITS for B
BEGIN;
UPDATE accounts
SET balance = balance - 200
WHERE id = 2;   -- holds row 2

UPDATE accounts
SET balance = balance + 200
WHERE id = 1;   -- WAITS for A
-- Fix: always lock rows in a consistent order (lowest id first)
BEGIN;
  SELECT * FROM accounts
  WHERE  id IN (1, 2)
  ORDER BY id            -- same order in ALL transactions
  FOR UPDATE;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
⚠️ Your application must handle deadlocks. PostgreSQL rolls back the victim and raises error code 40P01. Catch it and retry the whole transaction — never assume it won't happen.

Q: What is a deadlock and how do you prevent it?

A: Two transactions wait for each other's locks in a cycle. PostgreSQL detects it and aborts one with 40P01. Prevent it by locking rows in a consistent order, keeping transactions short, and retrying the aborted transaction in the application.

11 Best Practices

✅ DO

  • ⚡
    Keep transactions short — lock time = blocked time for other users. Do the minimum inside BEGIN…COMMIT.
  • 🛡️
    Always handle errors and ROLLBACK — catch exceptions in app code. Leaving a transaction open is dangerous.
  • 📋
    Use SAVEPOINTs for partial recovery — in batch jobs, savepoint per item so one failure doesn't cancel the batch.
  • 🔒
    Lock in consistent order — e.g. by primary key ASC — to prevent deadlocks.
  • 🔄
    Retry on 40P01 and 40001 — deadlock victims and serialization failures must be retried.
  • 📊
    Choose the right isolation level — READ COMMITTED is fine for most work; use SERIALIZABLE only when needed.

❌ DON'T

  • 🐢
    Don't do heavy work inside a transaction — external APIs, emails or long reports hold locks the whole time.
  • 👻
    Don't leave transactions open — "idle in transaction" sessions hold locks and block VACUUM cleanup. Consider idle_in_transaction_session_timeout.
  • 🎭
    Don't ignore transaction errors — after an error the transaction is aborted; every command fails until you ROLLBACK.
  • 🔄
    Don't try to nest transactions — PostgreSQL has no true nesting; a second BEGIN only warns. Use SAVEPOINTs.
  • 💥
    Don't use SERIALIZABLE everywhere — more conflicts and retries. Profile first, escalate only when needed.
🏦 Real Example — E-Commerce Order Transaction

Placing an order takes six statements: lock the product, reduce stock, create the order, add the order item, record the payment and mark the order paid. All must succeed together — or everything rolls back, the customer's money is safe and the stock is restored.

What must happen atomically
Lock product
→
Reduce stock
→
Create order
→
Add order item
→
Record payment
→
Mark paid
📌 If the payment step fails → everything before it rolls back (or roll back to a savepoint and retry). Stock is restored, no orphan order.

Schema

CREATE TABLE products (
  id    SERIAL PRIMARY KEY, name TEXT,
  price NUMERIC(10,2), stock INT CHECK (stock >= 0)  -- can't go negative!
);
CREATE TABLE orders (
  id SERIAL PRIMARY KEY, user_id INT,
  total NUMERIC(10,2), status TEXT DEFAULT 'pending', created_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE TABLE order_items (
  id SERIAL PRIMARY KEY, order_id INT REFERENCES orders(id),
  product_id INT REFERENCES products(id), qty INT, unit_price NUMERIC(10,2)
);
CREATE TABLE payments (
  id SERIAL PRIMARY KEY, order_id INT REFERENCES orders(id),
  amount NUMERIC(10,2), method TEXT, status TEXT DEFAULT 'success'
);

The transaction — user 1 buys 2 × product 5

BEGIN;

  -- Step 1: Lock the product row to prevent concurrent oversell
  SELECT id, price, stock FROM products WHERE id = 5 FOR UPDATE;

  -- Step 2: Reduce stock (the CHECK constraint stops overselling)
  UPDATE products SET stock = stock - 2 WHERE id = 5;
  -- If stock was 1: CHECK (stock >= 0) fails → ERROR → the transaction is
  -- aborted; issue ROLLBACK (nothing is saved)

  SAVEPOINT stock_reduced;  -- checkpoint after stock OK

  -- Step 3: Create the order
  INSERT INTO orders (user_id, total, status)
  VALUES (1, (SELECT price * 2 FROM products WHERE id = 5), 'pending')
  RETURNING id;  -- returns the new order id (101 in this example)

  -- Step 4: Add the order item (101 = id returned above)
  INSERT INTO order_items (order_id, product_id, qty, unit_price)
  VALUES (101, 5, 2, (SELECT price FROM products WHERE id = 5));

  SAVEPOINT order_created;  -- checkpoint after order

  -- Step 5: Create the payment record
  INSERT INTO payments (order_id, amount, method)
  VALUES (101, 1000, 'Card');
  -- if the payment gateway fails → ROLLBACK TO SAVEPOINT order_created
  -- then retry with UPI, or ROLLBACK fully

  -- Step 6: Mark the order paid
  UPDATE orders SET status = 'paid' WHERE id = 101;

COMMIT;  -- all steps saved atomically!

Same logic as a reusable PL/pgSQL function

CREATE OR REPLACE FUNCTION place_order(
  p_user_id INT, p_product_id INT, p_qty INT, p_method TEXT
) RETURNS INT LANGUAGE plpgsql AS $$
DECLARE
  v_price NUMERIC; v_order_id INT; v_total NUMERIC;
BEGIN
  SELECT price INTO v_price FROM products WHERE id = p_product_id FOR UPDATE;
  IF NOT FOUND THEN RAISE EXCEPTION 'Product % not found', p_product_id; END IF;

  v_total := v_price * p_qty;
  UPDATE products SET stock = stock - p_qty WHERE id = p_product_id;
  INSERT INTO orders (user_id, total) VALUES (p_user_id, v_total) RETURNING id INTO v_order_id;
  INSERT INTO order_items (order_id, product_id, qty, unit_price) VALUES (v_order_id, p_product_id, p_qty, v_price);
  INSERT INTO payments (order_id, amount, method) VALUES (v_order_id, v_total, p_method);
  UPDATE orders SET status = 'paid' WHERE id = v_order_id;
  RETURN v_order_id;
END;
$$;

-- A function call is a single statement, so it is already atomic:
SELECT place_order(1, 5, 2, 'UPI');
-- Any error inside aborts the whole statement — nothing is half-saved.
💡 No EXCEPTION WHEN OTHERS THEN RAISE is needed: an unhandled error already aborts the statement, and an unnecessary handler adds subtransaction overhead. Wrap the call in BEGIN … COMMIT only when you combine it with other statements.
🧠 ACID demonstrated in this example
Atomicity — all six steps commit together or none do.
Consistency — CHECK (stock >= 0) prevents overselling.
Isolation — FOR UPDATE locks the product row so two simultaneous orders can't both reduce the same stock.
Durability — after COMMIT, the order survives a server crash.
