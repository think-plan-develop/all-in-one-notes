1 What is a Transaction?

A transaction is a group of one or more SQL statements treated as a single unit of work. Either all succeed (COMMIT) or all are undone (ROLLBACK) — no in-between state ever exists.

✅ One-linerA transaction is an all-or-nothing operation. Transfer ₹5,000 from Account A to B — both the debit and credit must succeed together, or neither happens.
📋 Classic Bank Transfer ProblemStep 1: Deduct ₹5,000 from Account A → succeeds
Step 2: Add ₹5,000 to Account B → system crashes!

Without transaction: A lost ₹5,000, B got nothing. Money vanished. 💸
With transaction: Crash → entire operation rolled back. A keeps its money. ✅
2 Why Do We Use Transactions?
1
Data integrity across multiple steps

When an operation spans multiple SQL statements, transactions guarantee they all complete or all undo — no partial updates.

2
Recovery from failures

Server crash, network drop, app error mid-operation — ROLLBACK brings the DB back to its last consistent state automatically.

3
Concurrent access safety

Transactions isolate users from each other. User A's half-done update is invisible to User B until committed.

4
Consistent business operations

Order placement = reduce inventory + create order + charge payment. All three must succeed together or not at all.

📦 Real-world scenarios needing transactions
  • 💰 Bank transfer (debit + credit must pair)
  • 🛒 E-commerce order (stock + order + payment)
  • ✈️ Flight booking (seat + payment + confirmation)
  • 📊 Payroll (calculate + update all salaries atomically)
  • 🔄 Data migration (transform + insert + delete old)
  • 🏦 Ledger entries (debit must always equal credit)
3 ACID Properties

ACID is the set of four properties that guarantee database transactions are processed reliably. PostgreSQL is fully ACID-compliant.

A
Atomicity
All statements succeed or none do. No partial results. If step 5 of 10 fails, steps 1–4 are rolled back automatically.
C
Consistency
The database moves from one valid state to another. All constraints, rules, and triggers must hold before AND after the transaction.
I
Isolation
Concurrent transactions don't see each other's uncommitted changes. Each transaction runs in its own private snapshot of the database.
D
Durability
Once committed, data is permanently saved — even if the server crashes immediately after. PostgreSQL writes to WAL before confirming.
PropertyGuaranteesPostgreSQL mechanism
AtomicityAll or nothingROLLBACK, transaction log
ConsistencyValid state → valid stateConstraints, triggers, CHECK
IsolationTransactions don't interfereMVCC (Multi-Version Concurrency Control)
DurabilityCommitted data survives crashesWAL (Write-Ahead Logging), fsync
🎯 Interview answerACID = Atomicity (all-or-nothing), Consistency (valid state transitions), Isolation (no dirty reads between transactions), Durability (committed data survives crashes). PostgreSQL achieves isolation via MVCC and durability via WAL.

✅ Success Path → COMMIT
All SQL statements execute without error → constraints pass → COMMIT called → changes permanently written to disk → locks released → other transactions see the new data.
❌ Failure Path → ROLLBACK
Any statement fails (error, constraint violation, app error) → ROLLBACK → all changes undone → database returns to the state at BEGIN → locks released → no data was harmed.
5 BEGIN · COMMIT · ROLLBACK
▶ BEGIN
Starts a transaction block. All subsequent statements belong to this transaction until COMMIT or ROLLBACK.

BEGIN;
START TRANSACTION;

Both are identical in PostgreSQL. BEGIN is more common.
✅ COMMIT
Makes all changes permanent. Writes to disk. Releases all locks. Other transactions can now see the committed data.

COMMIT;
COMMIT WORK;

After COMMIT, changes cannot be undone.
↩ ROLLBACK
Undoes all changes since BEGIN. Restores the DB to its pre-transaction state. Releases all locks.

ROLLBACK;
ROLLBACK WORK;

Called on error or to cancel the operation.
begin_commit_rollback.sql
PostgreSQL
-- Basic transaction structure
BEGIN;
  UPDATE accounts SET balance = balance - 5000 WHERE id = 1;
  UPDATE accounts SET balance = balance + 5000 WHERE id = 2;
COMMIT;                    -- both succeed → save permanently

-- Rollback on error
BEGIN;
  UPDATE accounts SET balance = balance - 5000 WHERE id = 1;
  -- error occurs here...
ROLLBACK;                  -- undo everything, money safe

-- PostgreSQL error state: once an error occurs in a transaction,
-- all subsequent commands fail until ROLLBACK is issued
-- ERROR: current transaction is aborted, commands ignored until ROLLBACK
6 SAVEPOINT · ROLLBACK TO SAVEPOINT · RELEASE SAVEPOINT

A SAVEPOINT is a named checkpoint inside a transaction. You can roll back to it without cancelling the entire transaction — only the work done after the savepoint is undone. The transaction remains active.

savepoint.sql
PostgreSQL
BEGIN;

  INSERT INTO users (name, email) VALUES ('Aman', 'a@x.com');

  SAVEPOINT after_user;       -- checkpoint 1

  INSERT INTO orders (user_id, total) VALUES (lastval(), 500);

  SAVEPOINT after_order;      -- checkpoint 2

  INSERT INTO payments (order_id, amount) VALUES (lastval(), 500);
  -- payment fails!

ROLLBACK TO SAVEPOINT after_order;   -- undo only payment, keep user + order

  INSERT INTO payments (order_id, amount, method)
  VALUES (lastval(), 500, 'UPI');    -- retry with UPI

RELEASE SAVEPOINT after_order;      -- clean up the savepoint

COMMIT;                             -- all saved!


-- KEY DIFFERENCE:
ROLLBACK TO SAVEPOINT sp1;  -- undo to sp1, transaction STILL ACTIVE
ROLLBACK;                   -- undo EVERYTHING, transaction ENDS
CommandWhat it doesTransaction still active?
SAVEPOINT nameCreates a named checkpoint inside the transaction✅ Yes
ROLLBACK TO SAVEPOINT nameUndoes all work done after this savepoint✅ Yes — continues!
RELEASE SAVEPOINT nameRemoves the savepoint, keeps all changes✅ Yes
ROLLBACKUndoes everything from BEGIN❌ No — ends
7 Auto Commit vs Manual Commit
⚡ Auto Commit (Default)
PostgreSQL is in auto-commit mode by default. Every SQL statement is automatically wrapped in its own transaction and committed immediately.

UPDATE users SET name='Aman' WHERE id=1;
→ Automatically: BEGIN → UPDATE → COMMIT

⚠️ Danger: each statement commits independently — no rollback across multiple statements.
🛡️ Manual Commit (Explicit BEGIN)
Explicitly write BEGIN to control when changes commit. Multiple statements run as one atomic unit.

BEGIN;
UPDATE accounts SET balance=balance-5000 WHERE id=1;
UPDATE accounts SET balance=balance+5000 WHERE id=2;
COMMIT;

✅ All succeed together or all roll back together.
autocommit.sql
PostgreSQL
-- Auto commit: each statement is its own transaction
UPDATE accounts SET balance = balance - 5000 WHERE id = 1; -- committed!
UPDATE accounts SET balance = balance + 5000 WHERE id = 2; -- if this fails: money GONE 💸

-- Manual commit: safe
BEGIN;
  UPDATE accounts SET balance = balance - 5000 WHERE id = 1;
  UPDATE accounts SET balance = balance + 5000 WHERE id = 2;
COMMIT;                  -- if second UPDATE fails → ROLLBACK, A keeps money ✅

-- Disable auto-commit in psql
\set AUTOCOMMIT off

-- In app code:
-- Python psycopg2:  conn.autocommit = False
-- Node.js pg:       client.query('BEGIN')
-- Java JDBC:        conn.setAutoCommit(false)
8 Transaction Isolation Levels

Isolation levels control how much one transaction can see of another's concurrent changes. Higher isolation = more safety, lower performance.

The three concurrency problems

💀 Dirty Read
Transaction A reads data that B changed but not committed. If B rolls back, A read data that never existed permanently.
⚠️ Non-Repeatable Read
A reads a row, B updates + commits it, A reads same row again and gets different value. Same query, different result in same transaction.
👻 Phantom Read
A runs a range query, B inserts a matching row + commits, A runs same query again and sees new phantom rows that weren't there before.
Isolation LevelDirty ReadNon-Repeatable ReadPhantom ReadPerformance
READ UNCOMMITTED✗ Possible✗ Possible✗ PossibleFastest
READ COMMITTED✓ Prevented✗ Possible✗ PossibleFast (default)
REPEATABLE READ✓ Prevented✓ Prevented✗ PossibleMedium
SERIALIZABLE✓ Prevented✓ Prevented✓ PreventedSlowest
📌 PostgreSQL notePostgreSQL does NOT implement READ UNCOMMITTED — it behaves as READ COMMITTED. Default is READ COMMITTED. PostgreSQL uses MVCC so readers never block writers and writers never block readers.
isolation.sql
PostgreSQL
BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;    -- default
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Or set after BEGIN
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Check current level
SHOW transaction_isolation;

-- Use SERIALIZABLE for financial operations
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
  SELECT balance FROM accounts WHERE id = 1;
  UPDATE accounts SET balance = balance - 500 WHERE id = 1;
COMMIT;
9 Locks & Concurrency (Basic)

When multiple transactions access the same data, PostgreSQL uses locks to prevent conflicts. MVCC handles most read/write scenarios without locks — but write/write conflicts need explicit locking.

🔓 Shared Lock — SELECT FOR SHARE
Multiple transactions can hold shared locks simultaneously. Readers don't block readers.

SELECT * FROM orders WHERE id=1 FOR SHARE;
🔒 Exclusive Lock — SELECT FOR UPDATE
Only one transaction can hold an exclusive lock. Others must wait until it's released at COMMIT/ROLLBACK.

SELECT * FROM orders WHERE id=1 FOR UPDATE;
locks.sql
PostgreSQL
-- FOR UPDATE: lock row before modifying (prevent lost updates)
BEGIN;
  SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
  UPDATE accounts SET balance = balance - 500 WHERE id = 1;
COMMIT;

-- NOWAIT: fail immediately if locked, don't wait
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
-- ERROR: could not obtain lock on row

-- SKIP LOCKED: skip locked rows (perfect for job queues)
SELECT * FROM tasks
WHERE  status = 'pending'
LIMIT  1
FOR UPDATE SKIP LOCKED;  -- pick next unlocked task safely

-- View current locks
SELECT pid, relation::regclass, mode, granted
FROM   pg_locks WHERE relation IS NOT NULL;
10 Deadlock (Basic)

A deadlock occurs when two transactions each wait for a lock held by the other — a circular wait neither can escape. PostgreSQL detects this automatically and kills one transaction (the "victim").

📋 How deadlock happensTransaction A: Holds lock on Row 1 → wants lock on Row 2 (waiting for B)
Transaction B: Holds lock on Row 2 → wants lock on Row 1 (waiting for A)

🔴 Neither can proceed. PostgreSQL detects the cycle and rolls back one transaction automatically.
Error: ERROR: deadlock detected (PostgreSQL error code: 40P01)
deadlock.sql
PostgreSQL
-- Session A                          Session B
BEGIN;                               BEGIN;
UPDATE accounts                      UPDATE accounts
SET balance = balance - 100          SET balance = balance - 200
WHERE id = 1;  ← holds Row 1        WHERE id = 2;  ← holds Row 2

UPDATE accounts                      UPDATE accounts
SET balance = balance + 100          SET balance = balance + 200
WHERE id = 2;  ← WAITING for B     WHERE id = 1;  ← WAITING for A
-- DEADLOCK! PostgreSQL kills one transaction automatically

-- Fix: always lock in consistent order (lower id first)
BEGIN;
  SELECT * FROM accounts
  WHERE  id IN (1, 2)
  ORDER BY id            -- same order in ALL transactions
  FOR UPDATE;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
⚠️ Application must handle deadlocksPostgreSQL rolls back the victim and raises error code 40P01. Your application must catch this error and retry the transaction. Never assume it won't happen.
11 Best Practices

✅ DO

  • ⚡
    Keep transactions short — Lock time = blocked time for other users. Do minimum work inside BEGIN…COMMIT.
  • 🛡️
    Always handle errors and ROLLBACK — Catch exceptions in app code and always issue ROLLBACK. Leaving a transaction open is dangerous.
  • 📋
    Use SAVEPOINTs for partial recovery — For batch processing, savepoint after each item so one failure doesn't cancel the whole batch.
  • 🔒
    Lock in consistent order — Always lock multiple rows in the same order (e.g. by primary key ASC) to prevent deadlocks.
  • 🔄
    Retry on deadlock (error 40P01) — PostgreSQL kills one victim. Application must detect and retry automatically.
  • 📊
    Choose the right isolation level — READ COMMITTED is fine for most use cases. Use SERIALIZABLE only when you truly need it.

❌ DON'T

  • 🐢
    Don't do heavy work inside a transaction — Calling external APIs, sending emails, or long reports inside BEGIN…COMMIT holds locks for the entire duration.
  • 👻
    Don't leave transactions open — Uncommitted transactions hold locks, consume memory, and block VACUUM. Always COMMIT or ROLLBACK.
  • 🎭
    Don't ignore transaction errors — Once a PostgreSQL transaction hits an error it's aborted. Every subsequent command fails until you ROLLBACK.
  • 🔄
    Don't try to nest transactions — PostgreSQL doesn't support true nesting. Use SAVEPOINTs for partial rollback capability instead.
  • 💥
    Don't use SERIALIZABLE everywhere — Higher isolation = more conflicts and retries. Profile first, escalate isolation only when needed.
🏦 Real Example — E-Commerce Order Transaction

An e-commerce order requires 5 operations: reduce inventory, create order, add order items, create payment, and mark order paid. All 5 must succeed together, or everything rolls back — customer money is safe and inventory is restored.

📋 What must happen atomically1. Lock + reduce product stock  →  2. Create order  →  3. Add order items  →  4. Create payment record  →  5. Mark order as paid

If step 4 (payment) fails → steps 1–3 all roll back. Stock restored. No orphan order.
ecommerce_order.sql
PostgreSQL
-- Schema
CREATE TABLE products (
  id    SERIAL PRIMARY KEY, name TEXT,
  price NUMERIC(10,2), stock INT CHECK (stock >= 0)  -- can't go negative!
);
CREATE TABLE orders (
  id SERIAL PRIMARY KEY, user_id INT,
  total NUMERIC(10,2), status TEXT DEFAULT 'pending', created_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE TABLE order_items (
  id SERIAL PRIMARY KEY, order_id INT REFERENCES orders(id),
  product_id INT REFERENCES products(id), qty INT, unit_price NUMERIC(10,2)
);
CREATE TABLE payments (
  id SERIAL PRIMARY KEY, order_id INT REFERENCES orders(id),
  amount NUMERIC(10,2), method TEXT, status TEXT DEFAULT 'success'
);

-- THE TRANSACTION: place order for user 1, product 5, qty 2
BEGIN;

  -- Step 1: Lock the product row to prevent concurrent oversell
  SELECT id, price, stock FROM products WHERE id = 5 FOR UPDATE;

  -- Step 2: Reduce stock (CHECK constraint catches oversell automatically)
  UPDATE products SET stock = stock - 2 WHERE id = 5;
  -- If stock was 1: violates CHECK(stock >= 0) → ERROR → auto ROLLBACK

  SAVEPOINT stock_reduced;  -- checkpoint after stock OK

  -- Step 3: Create the order
  INSERT INTO orders (user_id, total, status)
  VALUES (1, (SELECT price * 2 FROM products WHERE id = 5), 'pending')
  RETURNING id;  -- returns order_id (e.g. 101)

  -- Step 4: Add order item
  INSERT INTO order_items (order_id, product_id, qty, unit_price)
  VALUES (101, 5, 2, (SELECT price FROM products WHERE id = 5));

  SAVEPOINT order_created;  -- checkpoint after order

  -- Step 5: Create payment record
  INSERT INTO payments (order_id, amount, method)
  VALUES (101, 1000, 'Card');
  -- if payment gateway fails → ROLLBACK TO SAVEPOINT order_created
  -- then retry with UPI, or ROLLBACK fully

  -- Step 6: Mark paid
  UPDATE orders SET status = 'paid' WHERE id = 101;

COMMIT;  -- all 5 steps saved atomically!


-- Same logic as a reusable PL/pgSQL function
CREATE OR REPLACE FUNCTION place_order(
  p_user_id INT, p_product_id INT, p_qty INT, p_method TEXT
) RETURNS INT LANGUAGE plpgsql AS $$
DECLARE
  v_price NUMERIC; v_order_id INT; v_total NUMERIC;
BEGIN
  SELECT price INTO v_price FROM products WHERE id = p_product_id FOR UPDATE;
  IF NOT FOUND THEN RAISE EXCEPTION 'Product % not found', p_product_id; END IF;

  v_total := v_price * p_qty;
  UPDATE products SET stock = stock - p_qty WHERE id = p_product_id;
  INSERT INTO orders (user_id, total) VALUES (p_user_id, v_total) RETURNING id INTO v_order_id;
  INSERT INTO order_items (order_id, product_id, qty, unit_price) VALUES (v_order_id, p_product_id, p_qty, v_price);
  INSERT INTO payments (order_id, amount, method) VALUES (v_order_id, v_total, p_method);
  UPDATE orders SET status = 'paid' WHERE id = v_order_id;
  RETURN v_order_id;
EXCEPTION WHEN OTHERS THEN
  RAISE;  -- re-raise triggers ROLLBACK in caller
END;
$$;

-- Call the function atomically
BEGIN;
  SELECT place_order(1, 5, 2, 'UPI');
COMMIT;
🧠 ACID demonstrated in this example Atomicity — all 5 steps commit together or none do.
Consistency — CHECK(stock >= 0) prevents overselling even under concurrency.
Isolation — FOR UPDATE locks the product row so two simultaneous orders can't both reduce the same stock.
Durability — after COMMIT, the order survives a server crash immediately after.
