📖 What is Normalization?

Normalization is the process of structuring a relational database to reduce data redundancy (storing the same data in multiple places) and improve data integrity (ensuring data stays correct and consistent).

✅ Core idea Each Normal Form adds one more rule. You can't skip ahead — 3NF requires 2NF, which requires 1NF. Think of them as layers of data hygiene.
🎯 Interview tip "What is normalization?" — Answer: It's the process of organizing tables to eliminate redundancy and dependency anomalies using a series of progressive rules called Normal Forms.
📐 The Normal Forms
1NF

First Normal Form

Every cell must hold one atomic value. No lists, no sets, no comma-separated values in a single cell. Each row must be unique (Primary Key required).

📌 Definition Each cell must hold one atomic value. No lists in a single column. Each row must be unique (Primary Key). If a column stores multiple values, it cannot be filtered, joined, or indexed correctly.
❌ VIOLATION
skills = 'Node.js, React, SQL'
← three values crammed in one cell
✅ FIX
skills(user_id, skill)
← one row per skill, fully queryable
2NF

Second Normal Form

Must be in 1NF. Every non-key column must depend on the whole composite primary key — not just part of it. Only matters when the Primary Key is composite (2+ columns).

📌 Definition Every non-key column must depend on the WHOLE composite key — no partial dependencies. If a column depends only on part of the key, it belongs in a separate table for that part.
❌ VIOLATION
enrollments(student_id, course_id, student_name)
← student_name depends only on student_id, not the full composite key
✅ FIX
Move student_name → students(id, name)
← depends on its own full PK
3NF

Third Normal Form

Must be in 2NF. No non-key column should depend on another non-key column — no transitive dependencies. Every column must depend directly on the Primary Key, and nothing else.

📌 Definition No non-key column should depend on another non-key column — no transitive dependencies. If column C depends on column B, and column B depends on the PK, then C has a transitive dependency and must be moved to its own table.
❌ VIOLATION
employees(id, dept_id, dept_name)
← dept_name depends on dept_id, not directly on id
✅ FIX
Move dept_name → departments(id, name)
← employees keeps only dept_id as FK
BCNF

Boyce-Codd Normal Form

Must be in 3NF. For every functional dependency X → Y, X must be a superkey. Handles rare edge cases that 3NF misses with overlapping candidate keys.

📌 Definition For every functional dependency X → Y, X must be a superkey. 3NF allows some exceptions when Y is part of a candidate key. BCNF removes that exception entirely. In practice, most well-designed 3NF tables already satisfy BCNF — you'll rarely need to act on it.
💡 In practice BCNF violations only occur with overlapping candidate keys — rare in typical apps. Most 3NF tables are already BCNF without any extra work.
Denorm

Denormalization — Breaking the Rules on Purpose

Denormalization is the deliberate introduction of redundancy for READ performance. Once normalized, some reads need too many expensive JOINs. That's when you selectively add redundancy back.

📌 Definition Deliberate introduction of redundancy for READ performance — reduces expensive JOINs at query time. EXAMPLE: store total_order_amount on orders instead of computing it from order_items every time. Always normalize first, then denormalize only where profiling shows a real bottleneck.
Normalize
Optimizes write performance & data integrity

One place to update. No risk of data going out of sync. Preferred for transactional, write-heavy systems.

Denormalize
Optimizes read performance

Store pre-computed or redundant data to skip JOINs. Preferred for analytics, dashboards, or caching layers.

⚠️ Warning Denormalization creates update anomalies — if you cache item_count on the orders table, you must update it every time an item is added or removed. Always normalize first, then denormalize only where profiling shows a real bottleneck.
🧠 Remember Normalize for correctness. Denormalize for speed. Never denormalize without measuring first.

💻 SQL — Before & After
normalization.sql 
-- ❌ BEFORE: one giant table — violates 1NF, 2NF, 3NF
CREATE TABLE bad_orders (
  order_id  INT,
  customer  VARCHAR(100),
  email     VARCHAR(100),
  skills    TEXT,           -- 'Node.js, React' — not atomic (1NF ❌)
  dept_name VARCHAR(100)    -- transitive via dept_id (3NF ❌)
);

-- ✅ 1NF: atomic values, primary key
CREATE TABLE customers (
  id    SERIAL PRIMARY KEY,
  name  VARCHAR(100) NOT NULL,
  email VARCHAR(100) UNIQUE NOT NULL
);

-- ✅ 2NF: skill gets its own table — no partial dependency
CREATE TABLE customer_skills (
  customer_id INT NOT NULL,
  skill       VARCHAR(50) NOT NULL,
  PRIMARY KEY (customer_id, skill),
  FOREIGN KEY (customer_id) REFERENCES customers(id)
);

-- ✅ 3NF: dept_name lives in departments — no transitive dependency
CREATE TABLE departments (
  id   SERIAL PRIMARY KEY,
  name VARCHAR(100) NOT NULL
);

CREATE TABLE employees (
  id      SERIAL PRIMARY KEY,
  name    VARCHAR(100) NOT NULL,
  dept_id INT REFERENCES departments(id) -- only FK, not dept_name
);

-- ⚡ DENORMALIZATION: store computed value for read performance
CREATE TABLE orders (
  id           SERIAL PRIMARY KEY,
  customer_id  INT REFERENCES customers(id),
  total_amount NUMERIC(10,2),  -- redundant but skips a SUM() join
  item_count   INT            -- redundant but skips a COUNT() join
);

⚡ Denormalization — When to Break the Rules

Denormalization is the deliberate introduction of redundancy for performance. Once you've fully normalized, you may find that certain reads require too many expensive JOINs. That's when you selectively add back redundancy.
