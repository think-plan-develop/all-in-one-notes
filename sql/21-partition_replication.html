🔴 What is Table Partitioning?

PART 1 What is Partitioning and Why Do We Need It?
🔴 CriticalFoundationBeginner

Q: What is table partitioning in SQL?

A: Partitioning is splitting one large table into smaller physical pieces called partitions, while it still looks like one table to the application. Each partition stores a subset of the data based on a rule — like date range, country code, or a hash of the ID. The database automatically routes reads and writes to the right partition.

🧠 Analogy: Imagine a library with 10 million books all in one room — finding one book takes forever. Partitioning is like splitting the library into 12 rooms, one per month of the year. To find a February book, you only search the February room — 11 rooms are ignored completely.
BEFORE partitioning — one giant table: orders (500 million rows — 2018 to 2024) Every query scans all 500M rows unless indexed. AFTER partitioning — same logical table, split physically: orders_2018 (60M rows) orders_2019 (65M rows) orders_2020 (70M rows) orders_2021 (75M rows) orders_2022 (80M rows) orders_2023 (85M rows) orders_2024 (65M rows — in progress) Query: WHERE order_date >= '2024-01-01' → Only scans orders_2024 (65M rows) — others ignored ✅
✅ Partitioning = one logical table, many physical storage pieces. Queries only touch the relevant partitions — massive speed gains on large tables.

Why use partitioning?

  • Query speed: Partition pruning skips irrelevant partitions entirely
  • Faster deletes: Drop old partition instead of DELETE millions of rows
  • Better maintenance: VACUUM, ANALYZE, backup per partition
  • Parallel queries: PostgreSQL can query multiple partitions in parallel
  • Smaller indexes: Each partition has its own index — fits in memory
⚠️ Partitioning helps when: table has 10M+ rows, you always filter on the partition key, and you regularly purge old data. For small tables, partitioning adds overhead with no benefit.

🔴 Range Partitioning

PART 2 RANGE Partitioning — By Date, Number, or Sequence
🔴 CriticalPartition Type

Q: What is Range partitioning and when do you use it?

A: Range partitioning divides data by a continuous range of values — most commonly by date (month, year, quarter) or by numeric ranges (IDs 1–1000, 1001–2000). Each partition stores rows where the key falls within a defined range. It's the most common type — perfect for time-series data, logs, and order history.

🧠 Analogy: Filing cabinet drawers labelled January, February, March… Each document goes in the drawer for its month. To find January documents, you only open the January drawer.
range_partition.sql
── Step 1: Create the parent table PARTITIONED BY RANGE ─────────────── CREATE TABLE orders ( id BIGSERIAL, customer_id INT NOT NULL, amount NUMERIC NOT NULL, order_date DATE NOT NULL, status TEXT ) PARTITION BY RANGE (order_date); -- ← partition key ── Step 2: Create child partitions with their ranges ────────────────── CREATE TABLE orders_2023 PARTITION OF orders FOR VALUES FROM ('2023-01-01') TO ('2024-01-01'); CREATE TABLE orders_2024 PARTITION OF orders FOR VALUES FROM ('2024-01-01') TO ('2025-01-01'); CREATE TABLE orders_2025 PARTITION OF orders FOR VALUES FROM ('2025-01-01') TO ('2026-01-01'); ── Step 3: Insert data — PostgreSQL routes automatically ────────────── INSERT INTO orders (customer_id, amount, order_date) VALUES (1, 250.00, '2024-03-15'); -- Automatically goes into orders_2024 ✅ ── Step 4: Query — PostgreSQL auto-prunes ──────────────────────────── SELECT * FROM orders WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01'; -- Only scans orders_2024 — 2023 and 2025 ignored ✅ ── Monthly partitions (finer grain) ────────────────────────────────── CREATE TABLE orders_2024_jan PARTITION OF orders FOR VALUES FROM ('2024-01-01') TO ('2024-02-01'); CREATE TABLE orders_2024_feb PARTITION OF orders FOR VALUES FROM ('2024-02-01') TO ('2024-03-01'); ── Range partition on numeric ID ────────────────────────────────────── CREATE TABLE users ( id BIGINT NOT NULL, name TEXT ) PARTITION BY RANGE (id); CREATE TABLE users_1_to_1m PARTITION OF users FOR VALUES FROM (1) TO (1000001); CREATE TABLE users_1m_to_2m PARTITION OF users FOR VALUES FROM (1000001) TO (2000001);
✅ Range is the most common partition type. Best for: time-series data (logs, orders, events), anything you query by date range, and anything you regularly purge by age.
💡 FROM/TO is exclusive on the upper bound. FROM ('2024-01-01') TO ('2025-01-01') stores January 2024 through December 31, 2024 — not including Jan 1, 2025.

🔴 List Partitioning

PART 3 LIST Partitioning — By Discrete Values
🔴 CriticalPartition Type

Q: What is List partitioning?

A: List partitioning assigns rows to partitions based on exact discrete values — like country code, region, status, or category. Each partition explicitly lists which values it holds. Use it when the column has a known, limited set of values you want to separate.

🧠 Analogy: Post office sorting bins — one bin labelled "USA", one "India", one "Europe". Every letter goes into its country's bin. To find all India letters, you only check the India bin.
list_partition.sql
── Partition customers by region ────────────────────────────────────── CREATE TABLE customers ( id BIGSERIAL, name TEXT NOT NULL, region TEXT NOT NULL, email TEXT ) PARTITION BY LIST (region); -- Each partition lists exactly which values it handles CREATE TABLE customers_asia PARTITION OF customers FOR VALUES IN ('IN', 'CN', 'JP', 'SG', 'KR'); CREATE TABLE customers_americas PARTITION OF customers FOR VALUES IN ('US', 'CA', 'BR', 'MX'); CREATE TABLE customers_europe PARTITION OF customers FOR VALUES IN ('GB', 'DE', 'FR', 'IT', 'ES'); -- DEFAULT partition catches anything not listed above CREATE TABLE customers_other PARTITION OF customers DEFAULT; ── Insert — routed automatically ────────────────────────────────────── INSERT INTO customers (name, region, email) VALUES ('Alice', 'IN', 'alice@example.com'); -- Goes to customers_asia ✅ ── Query — only scans the right partition ──────────────────────────── SELECT * FROM customers WHERE region = 'IN'; -- Only scans customers_asia ✅ SELECT * FROM customers WHERE region IN ('US', 'CA'); -- Only scans customers_americas ✅ ── List partition on status ─────────────────────────────────────────── CREATE TABLE orders_by_status ( id BIGSERIAL, status TEXT NOT NULL, amount NUMERIC ) PARTITION BY LIST (status); CREATE TABLE orders_active PARTITION OF orders_by_status FOR VALUES IN ('pending', 'processing'); CREATE TABLE orders_completed PARTITION OF orders_by_status FOR VALUES IN ('delivered', 'closed'); CREATE TABLE orders_cancelled PARTITION OF orders_by_status FOR VALUES IN ('cancelled', 'refunded');
⚠️ A value not covered by any partition and without a DEFAULT partition causes an error on INSERT. Always create a DEFAULT partition to catch unexpected values.
✅ List partition = partition by exact values. Best for: country codes, regions, status, category — anything with a known finite set of string values.

🟡 Hash Partitioning

PART 4 HASH Partitioning — Even Distribution
🟡 High ImpactPartition Type

Q: What is Hash partitioning and when is it the right choice?

A: Hash partitioning applies a hash function to the partition key and assigns the row to a partition based on the hash modulo the number of partitions. It distributes data evenly across all partitions. Use it when you have no natural range or list grouping, but want to spread load evenly — like sharding by user_id.

🧠 Analogy: Dealing cards evenly to 4 players. You don't know which player gets which card — it depends on the card's number mod 4. Every player gets roughly the same number of cards.
hash_partition.sql
── Hash partition on user_id — even spread across 4 partitions ──────── CREATE TABLE events ( id BIGSERIAL, user_id INT NOT NULL, event TEXT NOT NULL, created_at TIMESTAMPTZ DEFAULT NOW() ) PARTITION BY HASH (user_id); -- MODULUS = total partitions, REMAINDER = which one (0 to modulus-1) CREATE TABLE events_p0 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 0); CREATE TABLE events_p1 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 1); CREATE TABLE events_p2 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 2); CREATE TABLE events_p3 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 3); -- Insert — hash(user_id) % 4 determines partition INSERT INTO events (user_id, event) VALUES (42, 'login'); -- hash(42) % 4 = 2 → goes to events_p2 -- Query by user_id — pruned to one partition SELECT * FROM events WHERE user_id = 42; -- PostgreSQL computes hash(42)%4=2 → only scans events_p2 ✅
Hash(user_id) % 4: user_id=1 → hash%4=1 → events_p1 user_id=42 → hash%4=2 → events_p2 user_id=99 → hash%4=3 → events_p3 user_id=8 → hash%4=0 → events_p0 Result: ~25% of data in each partition (evenly distributed)
💡 Hash partition does NOT support fast range queries like Range partition does. It's purely for even distribution. If you need WHERE event_date BETWEEN … use Range instead.

🟡 Partition Pruning

PART 5 Partition Pruning — The Performance Magic
🔴 CriticalPerformance

Q: What is partition pruning?

A: Partition pruning is PostgreSQL's ability to skip partitions that cannot possibly contain rows matching the query's WHERE clause. It's the main performance benefit of partitioning. If you have 12 monthly partitions and query for January data, the planner only touches the January partition — the other 11 are completely skipped.

pruning.sql
── Verify pruning with EXPLAIN ──────────────────────────────────────── EXPLAIN (ANALYZE, VERBOSE) SELECT * FROM orders WHERE order_date >= '2024-01-01' AND order_date < '2024-04-01'; -- EXPLAIN output shows: -- Append (cost=...) ← checks multiple partitions? -- -> Seq Scan on orders_2024 ← only 2024 scanned ✅ -- Partitions Pruned: orders_2023, orders_2025 ← these skipped ── Pruning works with these operators ──────────────────────────────── WHERE order_date = '2024-03-15' -- ✅ pruned to one partition WHERE order_date >= '2024-01-01' -- ✅ pruned to 2024+ WHERE order_date BETWEEN '2024-01-01' AND '2024-12-31' -- ✅ pruned WHERE region = 'IN' -- ✅ list partition pruned WHERE user_id = 42 -- ✅ hash partition pruned ── Pruning does NOT work when ──────────────────────────────────────── WHERE YEAR(order_date) = 2024 -- ❌ function wrapping defeats pruning WHERE order_date::text LIKE '2024%' -- ❌ cast defeats pruning -- always use the column directly, never wrap in a function ── Enable runtime pruning (dynamic params) ─────────────────────────── SET enable_partition_pruning = on; -- on by default in PG 11+
⚠️ Golden rule: Never wrap the partition key in a function in WHERE clauses. WHERE DATE_TRUNC('year', order_date) = '2024-01-01' defeats pruning and scans ALL partitions. Use WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01' instead.
✅ Pruning = the database's ability to skip partitions. You get it for free when your WHERE clause uses the partition key directly without function wrapping.

🟡 Indexes on Partitioned Tables

PART 6 Indexes on Partitions — Local vs Global
🟡 High ImpactPerformance

Q: How do indexes work on partitioned tables in PostgreSQL?

A: When you create an index on the parent table, PostgreSQL automatically creates the same index on every child partition. These are called local indexes — each partition has its own index covering only its data. This is much more efficient than one giant index over 500M rows, since each partition's index fits in memory and is faster to scan.

partition_indexes.sql
── Create index on parent → auto-creates on all partitions ─────────── CREATE INDEX idx_orders_customer ON orders (customer_id); -- Automatically creates: -- idx_orders_2023_customer (on orders_2023) -- idx_orders_2024_customer (on orders_2024) -- idx_orders_2025_customer (on orders_2025) ── Index on partition key is recommended ───────────────────────────── CREATE INDEX idx_orders_date ON orders (order_date); ── Unique index — must INCLUDE the partition key ───────────────────── -- PostgreSQL requires partition key in unique/PK on partitioned tables CREATE UNIQUE INDEX idx_orders_unique ON orders (id, order_date); -- ← order_date (partition key) must be here ── Partial index — only index recent active rows ───────────────────── CREATE INDEX idx_orders_active ON orders (customer_id) WHERE status = 'active'; ── Index only on one specific partition ────────────────────────────── CREATE INDEX idx_orders_2024_amount ON orders_2024 (amount); -- only on 2024 partition ── Check indexes on partitions ─────────────────────────────────────── SELECT tablename, indexname FROM pg_indexes WHERE tablename LIKE 'orders%' ORDER BY tablename;
One 500M-row table — ONE huge index: idx_orders_customer → 500M entries → 12GB → doesn't fit in RAM Every query does expensive disk I/O Partitioned into 5 yearly tables — 5 small indexes: idx_orders_2020_customer → 60M entries → 1.5GB → fits in RAM ✅ idx_orders_2021_customer → 65M entries → 1.6GB → fits in RAM ✅ ... Query only touches one year's index → all in memory → fast ✅
💡 For PostgreSQL, a unique constraint across the entire partitioned table must include the partition key column. This is a known limitation of local indexes.

🟡 Partition Management

PART 7 Adding, Dropping, and Detaching Partitions
🟡 High ImpactManagement

Q: How do you add a new partition and remove old data efficiently?

A: Add a new partition with CREATE TABLE … PARTITION OF. To remove old data, DROP the old partition — this is instantaneous and far faster than DELETE on millions of rows. You can also DETACH a partition to keep the data as a standalone table before archiving.

partition_management.sql
── Add a new partition for next year ───────────────────────────────── CREATE TABLE orders_2026 PARTITION OF orders FOR VALUES FROM ('2026-01-01') TO ('2027-01-01'); -- Do this before 2026-01-01 or inserts fail (no matching partition) ── Drop old partition — INSTANT deletion of millions of rows ───────── DROP TABLE orders_2018; -- Removes all 60M rows instantly — no row-by-row DELETE needed ✅ ── Detach partition — keep data as standalone table ────────────────── ALTER TABLE orders DETACH PARTITION orders_2018; -- orders_2018 is now a regular table, not part of orders -- You can archive, export, or move it separately ── Re-attach a partition ───────────────────────────────────────────── ALTER TABLE orders ATTACH PARTITION orders_2018 FOR VALUES FROM ('2018-01-01') TO ('2019-01-01'); ── List all partitions of a table ──────────────────────────────────── SELECT child.relname AS partition_name, pg_size_pretty(pg_total_relation_size(child.oid)) AS size FROM pg_inherits JOIN pg_class parent ON pg_inherits.inhparent = parent.oid JOIN pg_class child ON pg_inherits.inhrelid = child.oid WHERE parent.relname = 'orders' ORDER BY child.relname;
✅ DROP TABLE on a partition is the fastest way to delete large amounts of old data — it removes the entire partition in milliseconds, regardless of row count.
⚠️ Always create the next period's partition BEFORE the period starts. If a row comes in with no matching partition, PostgreSQL throws an error on INSERT (unless you have a DEFAULT partition).

Q: What are the three types of partitioning in PostgreSQL?

A: Range (by continuous values like dates or numbers), List (by exact discrete values like country or status), and Hash (by hash function for even distribution).

Q: When would you NOT use partitioning?

A: When the table is small (under a few million rows), when you rarely query by the partition key, or when you need global unique indexes — PostgreSQL's local indexes make true global uniqueness across partitions complex.

Q: What is the fastest way to delete one year of old data from a partitioned table?

A: DROP TABLE on the partition. It removes the entire physical storage instantly with no row-by-row processing. A DELETE WHERE order_date < '2018-01-01' on 60M rows takes hours; DROP TABLE orders_2018 takes milliseconds.

🔴 What is Database Replication?

REP 1 What is Replication and Why Do We Need It?
🔴 CriticalFoundationBeginner

Q: What is database replication?

A: Replication is the process of continuously copying data from one database server (called the Primary or Master) to one or more other servers (called Replicas, Standbys, or Read Replicas). Every change on the primary is sent to and applied on the replicas, keeping them in sync.

🧠 Analogy: A Google Doc shared with 10 people — when you type, everyone sees the update instantly. The Google Doc is your primary, and all the other people's screens are replicas. If your screen breaks, someone else can take over immediately.
PRIMARY (writes + reads) ┌─────────────────────┐ │ PostgreSQL Primary │ │ Port 5432 │──── WAL stream ──► REPLICA 1 (read-only) │ All writes here │──── WAL stream ──► REPLICA 2 (standby/failover) └─────────────────────┘──── WAL stream ──► REPLICA 3 (analytics reads)

Why replicate?

  • High Availability: If the primary server crashes, promote a replica to take over — minimal downtime
  • Disaster Recovery: Replica in a different data centre — safe from regional failures
  • Scale reads: Route SELECT queries to replicas — primary handles only writes
  • Zero-downtime maintenance: Upgrade replica, failover, upgrade old primary
  • Backups: Take backups from replica — no load on primary
✅ Replication = automatic copying of data from primary to one or more replicas. Gives you high availability, disaster recovery, and read scaling.

🔴 Streaming Replication

REP 2 Streaming Replication — PostgreSQL's Physical Replication
🔴 CriticalReplication Type

Q: What is streaming replication in PostgreSQL?

A: Streaming replication continuously sends WAL (Write-Ahead Log) records from the primary to standby servers in real time over a network connection. The standby applies these WAL records to stay in sync. The standby is an exact byte-for-byte copy of the primary — same PostgreSQL version, same all-databases, same everything.

HOW STREAMING REPLICATION WORKS: Primary Standby ────────────────────────────── ────────────────────────── 1. App writes: INSERT INTO orders 2. Change written to WAL file 3. WAL record sent over network ──────────────────────────► 4. Standby receives WAL 5. Standby applies WAL 6. Standby now has same data ✅ This happens in near-real-time (milliseconds lag typically)
streaming_replication_setup.sql
── On PRIMARY: postgresql.conf settings ────────────────────────────── -- wal_level = replica (minimum for streaming) -- max_wal_senders = 5 (how many standbys can connect) -- wal_keep_size = 1GB (keep WAL files for late standbys) ── On PRIMARY: create replication user ─────────────────────────────── CREATE USER replicator WITH REPLICATION LOGIN PASSWORD 'strong_password'; ── On PRIMARY: pg_hba.conf — allow standby to connect ──────────────── -- host replication replicator 10.0.0.2/32 md5 ── On STANDBY: take base backup from primary ───────────────────────── -- (run in terminal, not psql) -- pg_basebackup -h primary_host -U replicator -D /var/lib/postgresql/data -Fp -Xs -P ── On STANDBY: create standby.signal file (PG 12+) ────────────────── -- touch /var/lib/postgresql/data/standby.signal ── On STANDBY: postgresql.conf ─────────────────────────────────────── -- primary_conninfo = 'host=primary_host port=5432 user=replicator password=...' -- hot_standby = on (allow read queries on standby) ── Monitor replication lag on PRIMARY ──────────────────────────────── SELECT client_addr, state, sent_lsn, write_lsn, flush_lsn, replay_lsn, write_lag, flush_lag, replay_lag FROM pg_stat_replication; ── Check replication lag from STANDBY ──────────────────────────────── SELECT NOW() - pg_last_xact_replay_timestamp() AS replication_lag; -- If this is 0 or small → standby is nearly in sync
✅ Streaming replication = physical copy of entire database cluster. The standby is an exact replica. It runs continuously in real time and keeps the standby ready for failover.

🔴 Synchronous vs Asynchronous Replication

REP 3 Synchronous vs Asynchronous — The Safety vs Speed Trade-off
🔴 Critical InterviewTrade-off

Q: What is the difference between synchronous and asynchronous replication?

A: In asynchronous replication (the default), the primary commits the transaction and immediately returns success to the app — the WAL is sent to the standby afterward. There can be a small lag. In synchronous replication, the primary waits for at least one standby to confirm it has received and written the WAL before committing. Zero data loss — but slower writes.

ASYNCHRONOUS (default): App → Write to primary → PRIMARY COMMITS → ✅ returns to app ↓ (later, ms to seconds) sends WAL to standby Risk: if primary crashes BEFORE standby receives WAL → data loss ⚠️ Benefit: fast writes, standby lag doesn't block primary ✅ SYNCHRONOUS: App → Write to primary → sends WAL to standby → standby confirms receipt → PRIMARY COMMITS → ✅ returns to app Risk: standby slowdown or network issue BLOCKS writes on primary ⚠️ Benefit: ZERO data loss — guaranteed ✅
sync_vs_async.sql
── Configure SYNCHRONOUS replication ───────────────────────────────── -- In postgresql.conf on PRIMARY: -- synchronous_standby_names = 'standby1' -- or for multiple standbys: -- synchronous_standby_names = 'FIRST 1 (standby1, standby2)' -- FIRST 1 = wait for any 1 of the listed standbys to confirm ── Configure ASYNCHRONOUS (default — no change needed) ─────────────── -- synchronous_standby_names = '' (empty = async) ── Check current sync status ───────────────────────────────────────── SELECT application_name, sync_state FROM pg_stat_replication; -- sync_state: 'sync' or 'async' or 'potential' ── Per-transaction sync control ────────────────────────────────────── -- Override for a specific critical transaction: SET synchronous_commit = 'on'; -- wait for standby (sync) BEGIN; INSERT INTO critical_payments VALUES (...); COMMIT; -- waits for standby confirmation -- For non-critical fast writes: SET synchronous_commit = 'off'; -- don't wait (async) INSERT INTO analytics_events VALUES (...);

Data loss risk⚠️ Small window of loss✅ Zero data loss

💡 Best practice: Use asynchronous replication for read replicas. Use synchronous for your primary failover standby when zero data loss is critical (banking, payments).

🟡 Logical Replication

REP 4 Logical Replication — Selective Table-Level Replication
🟡 High ImpactReplication Type

Q: What is logical replication and how is it different from streaming replication?

A: Logical replication replicates specific tables or databases — not the entire cluster. It sends logical changes (INSERT/UPDATE/DELETE events) rather than raw WAL bytes. The subscriber can have a different PostgreSQL version, different schema structure, or even be a different database engine. Streaming replication copies everything physically; logical replication is selective and flexible.

Streaming Replication

  • Copies entire database cluster
  • Sends raw WAL bytes (physical)
  • Standby must be same PG version
  • Standby is read-only
  • Perfect for HA failover

Logical Replication

  • Select specific tables or DBs
  • Sends logical row changes (INSERT/UPDATE/DELETE)
  • ✅ Different PG versions allowed
  • ✅ Subscriber can also write
  • Perfect for migrations, analytics pipelines
logical_replication.sql
── ON PUBLISHER (primary) ───────────────────────────────────────────── -- postgresql.conf: wal_level = logical (not just replica) -- Create a publication (what to replicate) CREATE PUBLICATION orders_pub FOR TABLE orders, customers; -- only these two tables -- Or replicate all tables in the database CREATE PUBLICATION all_tables_pub FOR ALL TABLES; ── ON SUBSCRIBER (replica) ──────────────────────────────────────────── -- Tables must exist on subscriber first CREATE TABLE orders ( -- same structure as publisher id BIGINT PRIMARY KEY, customer_id INT, amount NUMERIC, order_date DATE, status TEXT ); -- Create subscription (connect and start receiving changes) CREATE SUBSCRIPTION orders_sub CONNECTION 'host=primary_host port=5432 dbname=mydb user=replicator password=...' PUBLICATION orders_pub; ── Monitor logical replication ──────────────────────────────────────── -- On publisher: check active subscriptions SELECT * FROM pg_stat_replication; SELECT * FROM pg_publication; SELECT * FROM pg_replication_slots; -- On subscriber: check subscription status SELECT subname, subenabled, received_lsn, latest_end_lsn FROM pg_stat_subscription; ── Manage logical replication ───────────────────────────────────────── ALTER SUBSCRIPTION orders_sub DISABLE; -- pause ALTER SUBSCRIPTION orders_sub ENABLE; -- resume DROP SUBSCRIPTION orders_sub; DROP PUBLICATION orders_pub;
✅ Logical replication shines for: zero-downtime major version upgrades (PG 15 → PG 17), selective table sync to analytics databases, and feeding data pipelines (Debezium, Kafka CDC).
⚠️ Logical replication does NOT replicate DDL (ALTER TABLE, CREATE INDEX). Schema changes must be applied manually on the subscriber before data changes arrive.

🟡 Write-Ahead Log (WAL)

REP 5 WAL — The Engine Behind Replication
🟡 High ImpactInternals

Q: What is the Write-Ahead Log (WAL) and why is it central to replication?

A: WAL is PostgreSQL's durability mechanism — before any data page is modified, the change is first written to the WAL log file. This guarantees that even if the server crashes mid-write, the data can be recovered from the WAL. Replication works by streaming these WAL records to standbys, which then replay them to stay in sync. WAL is the single source of truth for all changes.

🧠 Analogy: A bank's double-entry ledger. Before any transaction changes the actual account balance, it's first written in the ledger (WAL). If the bank burns down, you rebuild everything from the ledger. Replication is sending a copy of that ledger to a branch office in real time.
WRITE flow with WAL: App sends: INSERT INTO orders VALUES (...) Step 1: WAL record written to WAL file on disk ← crash-safe Step 2: WAL record sent to standby (streaming) Step 3: Data written to actual table file Step 4: COMMIT returned to app WAL levels (wal_level setting): minimal → minimum for crash recovery only replica → enough for streaming replication ← default logical → includes info for logical replication (more detail)
wal_monitoring.sql
── Check current WAL position ───────────────────────────────────────── SELECT pg_current_wal_lsn(); -- on primary SELECT pg_last_wal_replay_lsn(); -- on standby ── Calculate replication lag in bytes ──────────────────────────────── SELECT client_addr, pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes FROM pg_stat_replication; ── View WAL files on disk ───────────────────────────────────────────── SELECT * FROM pg_ls_waldir() ORDER BY modification DESC LIMIT 10; ── Configure WAL settings (postgresql.conf) ────────────────────────── -- wal_level = replica (streaming) or logical (logical rep) -- max_wal_senders = 10 (max standby connections) -- wal_keep_size = 1024MB (keep 1GB of WAL for late standbys) -- archive_mode = on (archive WAL for PITR backups) -- archive_command = 'cp %p /archive/%f' (where to archive) ── Point-in-Time Recovery (PITR) uses WAL ──────────────────────────── -- Take a base backup, archive WAL files continuously -- Restore to any point in time by replaying WAL up to that moment -- recovery_target_time = '2024-06-15 14:30:00'
✅ WAL = the change log of the entire database. Replication works by shipping WAL records to standbys. PITR (Point-in-Time Recovery) works by replaying archived WAL. WAL is fundamental to both replication and backup strategies.

🟡 Read Replicas — Scale Your Reads

REP 6 Read Replicas — Offload SELECT Queries
🟡 High ImpactScalability

Q: What is a read replica and how does it help performance?

A: A read replica is a standby server with hot_standby = on — it accepts SELECT queries while continuously applying WAL from the primary. You route all read-heavy queries (reports, analytics, dashboards) to replicas and only send writes to the primary. This removes read load from the primary, keeping it fast for writes.

Without read replicas: Primary ← ALL reads (reports, dashboards, APIs) + ALL writes Primary is overloaded → everything slows down With read replicas: Primary ← only writes (INSERT/UPDATE/DELETE) Replica 1 ← reporting queries, BI dashboards Replica 2 ← API read traffic Replica 3 ← analytics, data science Primary stays fast. Reads distributed across replicas. ✅
read_replicas.sql

💡 Cloud services (AWS RDS, Google Cloud SQL, Azure) make read replicas one-click to create. On-premise you set up streaming replication with hot_standby = on.

🟡 Failover & High Availability

REP 7 Failover — Promoting a Standby to Primary
🟡 High ImpactHA

Q: What happens when the primary database fails? What is failover?

A: When the primary crashes, a standby must be promoted to become the new primary. This is called failover. It can be manual (you run a command) or automatic (tools like Patroni, repmgr, or cloud services detect the crash and promote the standby automatically). The goal is minimal downtime — typically seconds to a few minutes.

NORMAL OPERATION: App → Primary (write) → Standby (replicated) PRIMARY CRASHES: App → Primary ❌ (down) ↓ Standby detects no heartbeat FAILOVER (promote standby): Standby promoted → new Primary ✅ App reconnects to new Primary Old primary repaired → becomes new standby Recovery Time Objective (RTO): time to promote = seconds to minutes Recovery Point Objective (RPO): data loss = 0 (sync) or seconds (async)

── Manual failover: promote standby to primary ──────────────────────── -- Method 1: pg_ctl (command line) -- pg_ctl promote -D /var/lib/postgresql/data -- Method 2: trigger file (older method) -- touch /tmp/postgresql.trigger (standby watches for this file) -- Method 3: SQL command (PG 12+) SELECT pg_promote(); -- Run this on the standby to promote it ── After promotion: verify it's now primary ────────────────────────── SELECT pg_is_in_recovery(); -- should return false (no longer in recovery) ── Automatic failover tools ─────────────────────────────────────────── -- Patroni (most popular) — uses etcd/consul for leader election -- repmgr — PostgreSQL-native HA tool -- AWS RDS / Aurora — automatic failover built in -- Stolon — Kubernetes-native HA for PostgreSQL ── Monitor primary health ───────────────────────────────────────────── SELECT pg_is_in_recovery(); -- false = primary, true = standby SELECT * FROM pg_stat_replication; -- connected standbys SELECT * FROM pg_stat_activity; -- current connections ── Reattach old primary as new standby ─────────────────────────────── -- After fixing the old primary, use pg_rewind to sync it quickly: -- pg_rewind --target-pgdata=/var/lib/postgresql/data -- --source-server="host=new_primary port=5432 user=replicator" -- Then start it as standby pointing to new primary
✅ RTO (Recovery Time Objective) = how fast you recover. RPO (Recovery Point Objective) = how much data you can afford to lose. Synchronous replication = RPO of 0. Async = RPO of seconds.

⭐ Replication Interview Q&A + Cheat Sheet
⭐⭐⭐⭐⭐ Must MasterInterview

Q: What is replication lag and why does it matter?

A: Replication lag is the delay between when a change is committed on the primary and when it appears on the replica. In async replication, lag can be milliseconds to seconds. It matters because reading from a replica with high lag may return stale data. Monitor it with pg_stat_replication and pg_last_xact_replay_timestamp().

Q: What is the difference between streaming and logical replication?

A: Streaming replication is physical — it sends raw WAL bytes and creates an exact byte-for-byte copy of the whole cluster. Logical replication sends row-level changes (INSERT/UPDATE/DELETE) for selected tables. Streaming is for HA/failover; logical is for selective sync, cross-version migrations, and CDC pipelines.

Q: Can you write to a standby (replica) in PostgreSQL?

A: No — a streaming replication standby is read-only (SELECT only). With logical replication, the subscriber is a normal writable table but you must manage write conflicts yourself. Cloud managed services sometimes offer multi-primary (active-active) at extra complexity.

Q: What is a replication slot?

A: A replication slot is a PostgreSQL mechanism that ensures WAL files are not deleted until all subscribers have received them. It guarantees no data loss for slow standbys but can cause WAL to accumulate indefinitely if a subscriber goes offline permanently — monitoring disk space on the primary is critical when using slots.
