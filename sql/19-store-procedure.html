Introduction

What is a Stored Procedure?

A stored procedure is a named block of SQL (and optional PL/pgSQL logic) stored permanently inside the database. You write it once, name it, and call it whenever needed. It can contain multiple SQL statements, conditional logic, loops, variables, and — unlike functions — it can COMMIT or ROLLBACK transactions inside its body.

✅ Simple definition: A procedure = a saved, reusable set of SQL instructions stored in the database. You call it by name instead of writing the same SQL over and over.

Analogy — The Recipe Book: ───────────────────────────────────────────────────────────────── WITHOUT procedure — repeat these 4 steps every time: BEGIN; UPDATE accounts SET balance = balance - 500 WHERE id = 1; UPDATE accounts SET balance = balance + 500 WHERE id = 2; INSERT INTO transfer_log VALUES (1, 2, 500, NOW()); COMMIT; WITH procedure — write once, call anywhere: CALL transfer_funds(from_id := 1, to_id := 2, amount := 500); ─────────────────────────────────────────────────────────────────

Why Use Procedures?

  • Reusability — write complex logic once, call from anywhere (app, scripts, triggers)
  • Transaction control — only procedures can COMMIT / ROLLBACK inside the body
  • Security — grant EXECUTE on a procedure without exposing the underlying tables
  • Performance — PostgreSQL pre-parses and plans the procedure once
  • Encapsulation — hide complex business logic behind a clean interface

📌 PostgreSQL version note: Stored procedures (CREATE PROCEDURE + CALL) were added in PostgreSQL 11. On older versions, you had to use functions instead — but functions cannot contain COMMIT/ROLLBACK.

Syntax

CREATE PROCEDURE — Full Syntax

CREATE [OR REPLACE] PROCEDURE procedure_name ( param1 data_type, param2 data_type ) LANGUAGE plpgsql ← use 'sql' for simple single-statement procedures AS $$ DECLARE variable_name data_type; ← optional local variables BEGIN -- your SQL logic here -- INSERT / UPDATE / DELETE / IF / LOOP / EXCEPTION END; $$;
1

CREATE OR REPLACE PROCEDURE name

OR REPLACE updates the procedure if it already exists — no need to drop and recreate. Choose a clear, descriptive name like transfer_funds or archive_old_orders.

2

Define parameters in ( )

List all input parameters with their data types. No return type here — that's a function's job. Parameters default to IN mode; also supports INOUT and OUT.

3

LANGUAGE plpgsql

Use plpgsql for full procedural logic — IF/ELSE, loops, variables, exception blocks. Use sql only for very simple single-statement procedures with no logic.

4

AS $$ DECLARE … BEGIN … END; $$

Dollar-quoting $$ wraps the body — no need to escape single quotes inside. The DECLARE block holds local variables. All logic lives between BEGIN and END.

Example 1 — Simple Procedure (No Variables)

simple_procedure.sql 
-- Deactivate a user by ID
CREATE OR REPLACE PROCEDURE deactivate_user(p_user_id INT)
LANGUAGE plpgsql
AS $$
BEGIN
  UPDATE users
  SET    is_active = false,
         deactivated_at = NOW()
  WHERE  id = p_user_id;
END;
$$;

Example 2 — With Local Variables and Validation

procedure_with_variables.sql 
CREATE OR REPLACE PROCEDURE apply_discount(
  p_product_id    INT,
  p_discount_pct  NUMERIC
)
LANGUAGE plpgsql
AS $$
DECLARE
  v_current_price  NUMERIC;   -- local variable to hold fetched price
  v_new_price      NUMERIC;   -- calculated discounted price
BEGIN
  -- Step 1: fetch current price into local variable
  SELECT price INTO v_current_price
  FROM   products
  WHERE  id = p_product_id;

  -- Step 2: calculate new price
  v_new_price := v_current_price * (1 - p_discount_pct / 100);

  -- Step 3: validate before applying
  IF v_new_price <= 0 THEN
    RAISE EXCEPTION 'New price cannot be zero or negative: %', v_new_price;
  END IF;

  -- Step 4: apply the discount
  UPDATE products
  SET    price = v_new_price
  WHERE  id = p_product_id;

  RAISE NOTICE 'Price updated: % → %', v_current_price, v_new_price;
END;
$$;
Execution

CALL — How to Execute a Procedure

Use the CALL keyword to execute a procedure. This is different from functions, which use SELECT. CALL is a standalone statement — it cannot be embedded inside a SELECT list.

Syntax: CALL procedure_name(arg1, arg2); Named parameters (recommended — clearer, order-independent): CALL procedure_name(param_name := value, other_param := value);
call_examples.sql 
-- Positional arguments
CALL deactivate_user(42);

-- Named parameters (recommended)
CALL apply_discount(p_product_id := 15, p_discount_pct := 20);

-- Call from inside a DO block (anonymous block)
DO $$
BEGIN
  CALL deactivate_user(42);
  CALL deactivate_user(43);
END;
$$;

-- ── Manage Procedures ────────────────────────────────────────────

-- List all procedures in the database
SELECT proname, prokind
FROM   pg_proc
WHERE  prokind = 'p';   -- 'p' = procedure, 'f' = function

-- View the source code of a procedure
SELECT pg_get_functiondef(oid)
FROM   pg_proc
WHERE  proname = 'deactivate_user';

-- Drop a procedure (must specify argument types)
DROP PROCEDURE IF EXISTS deactivate_user(INT);

-- Grant execute permission to a role
GRANT EXECUTE ON PROCEDURE deactivate_user(INT) TO app_user;

✅ Remember: CALL = procedures. SELECT = functions. You cannot do SELECT deactivate_user(42) — that only works for functions.

Parameters

Parameter Modes — IN, OUT, INOUT

Parameters in procedures have three modes that control data flow between caller and procedure.

ModeDirectionDefault?Use CaseExample
INCaller → Procedure✅ YesPass values into the procedurep_user_id INT
OUTProcedure → CallerNoReturn values without using RETURNOUT p_count INT
INOUTBoth directionsNoPass a value in and get modified value backINOUT p_count INT
parameter_modes.sql 
-- INOUT: value goes in, modified value comes back
CREATE OR REPLACE PROCEDURE apply_tax(
  INOUT p_price NUMERIC,
  p_tax_rate    NUMERIC DEFAULT 18
)
LANGUAGE plpgsql
AS $$
BEGIN
  p_price := p_price * (1 + p_tax_rate / 100);
END;
$$;

-- Calling INOUT procedure from a DO block
DO $$
DECLARE
  v_price NUMERIC := 1000;
BEGIN
  CALL apply_tax(v_price);
  RAISE NOTICE 'Price with tax: %', v_price;  -- 1180
END;
$$;

💡 Default parameter values: Use DEFAULT value after the type to make a parameter optional. Callers who don't pass it get the default automatically.

PL/pgSQL Logic

Variables, IF, LOOP — Procedural Logic

DECLARE block
Declare all local variables here, before BEGIN. Format: variable_name TYPE := initial_value; — the initial value is optional.
Assignment
Use := for direct assignment: v_total := v_price * v_qty;. Use SELECT INTO to assign from a query: SELECT count(*) INTO v_count FROM orders;
IF / ELSIF / ELSE
Standard conditional logic. Syntax: IF condition THEN ... ELSIF condition THEN ... ELSE ... END IF;
LOOP
Basic loop: LOOP ... EXIT WHEN condition; END LOOP;. Also supports FOR i IN 1..10 LOOP and WHILE condition LOOP.
RAISE NOTICE
Prints a debug message to the client: RAISE NOTICE 'Value is: %', v_count; — the % is replaced by the variable value.
RAISE EXCEPTION
Throws an error, automatically rolling back the current transaction: RAISE EXCEPTION 'Error: %', detail_msg;
plpgsql_logic.sql 
CREATE OR REPLACE PROCEDURE process_order(p_order_id INT)
LANGUAGE plpgsql
AS $$
DECLARE
  v_total      NUMERIC;
  v_status     TEXT;
  v_item_count INT   := 0;
BEGIN
  -- Fetch order details into variables
  SELECT total_amount, status
  INTO   v_total, v_status
  FROM   orders
  WHERE  id = p_order_id;

  -- Check order exists
  IF NOT FOUND THEN
    RAISE EXCEPTION 'Order % not found', p_order_id;
  END IF;

  -- Conditional logic on status
  IF v_status = 'pending' THEN
    UPDATE orders SET status = 'processing' WHERE id = p_order_id;
    RAISE NOTICE 'Order % → processing', p_order_id;

  ELSIF v_status = 'processing' THEN
    UPDATE orders SET status = 'shipped' WHERE id = p_order_id;
    RAISE NOTICE 'Order % → shipped', p_order_id;

  ELSE
    RAISE EXCEPTION 'Cannot process order in status: %', v_status;
  END IF;

  -- Count items in loop
  FOR rec IN SELECT * FROM order_items WHERE order_id = p_order_id LOOP
    v_item_count := v_item_count + 1;
  END LOOP;

  RAISE NOTICE 'Processed order % with % items, total %',
               p_order_id, v_item_count, v_total;
END;
$$;
Transactions

Procedure Transactions — The Key Differentiator

The single most important feature that separates procedures from functions: a procedure can contain COMMIT and ROLLBACK inside its body. A function cannot — it always runs inside the caller's transaction.

FUNCTION — one transaction for everything: Caller BEGIN → Function runs all SQL → Caller COMMIT (or ROLLBACK all) ❌ Cannot checkpoint mid-way PROCEDURE — controls its own transaction: CALL proc → batch 1 → COMMIT ✅ → batch 2 → COMMIT ✅ → batch 3 → COMMIT ✅ ✅ Each batch saved independently — partial work is preserved

Example 1 — Atomic Fund Transfer

fund_transfer.sql 
CREATE OR REPLACE PROCEDURE transfer_funds(
  p_from   INT,
  p_to     INT,
  p_amount NUMERIC
)
LANGUAGE plpgsql
AS $$
DECLARE
  v_balance NUMERIC;
BEGIN
  -- Lock the row and read balance
  SELECT balance INTO v_balance
  FROM   accounts
  WHERE  id = p_from
  FOR UPDATE;           -- row-level lock

  IF v_balance < p_amount THEN
    RAISE EXCEPTION 'Insufficient funds. Balance: %, Required: %',
                    v_balance, p_amount;
  END IF;

  UPDATE accounts SET balance = balance - p_amount WHERE id = p_from;
  UPDATE accounts SET balance = balance + p_amount WHERE id = p_to;

  INSERT INTO transfer_log (from_id, to_id, amount, transferred_at)
  VALUES (p_from, p_to, p_amount, NOW());

  COMMIT;   -- ← commit all three operations atomically
  RAISE NOTICE 'Transfer of % successful.', p_amount;

EXCEPTION
  WHEN OTHERS THEN
    ROLLBACK;
    RAISE;
END;
$$;

CALL transfer_funds(p_from := 1, p_to := 2, p_amount := 500.00);

Example 2 — Batch Processing with Mid-Loop COMMITs

batch_archive.sql 
CREATE OR REPLACE PROCEDURE archive_old_orders(p_days_old INT)
LANGUAGE plpgsql
AS $$
DECLARE
  v_batch_size INT := 1000;
  v_processed  INT;
BEGIN
  LOOP
    -- Move one batch of 1000 rows to archive table
    WITH batch AS (
      DELETE FROM orders
      WHERE  id IN (
        SELECT id FROM orders
        WHERE  created_at < NOW() - (p_days_old || ' days')::INTERVAL
        LIMIT  v_batch_size
      )
      RETURNING *
    )
    INSERT INTO orders_archive SELECT * FROM batch;

    GET DIAGNOSTICS v_processed = ROW_COUNT;

    COMMIT;   -- ← commit each batch — frees locks, reduces WAL pressure
    RAISE NOTICE 'Archived % rows.', v_processed;

    EXIT WHEN v_processed < v_batch_size;   -- no more rows left
  END LOOP;

  RAISE NOTICE 'Archiving complete.';
END;
$$;

CALL archive_old_orders(90);

⚠️ Critical rule: Never call a procedure with COMMIT/ROLLBACK from inside an active transaction block (BEGIN … COMMIT in your app). The procedure's internal COMMIT will throw an error. Always CALL procedures at the top level, outside any transaction.

Exception Handling

EXCEPTION Block — Handle Errors Gracefully

Add an EXCEPTION section at the end of the BEGIN…END block to catch errors. When an exception is raised, PostgreSQL jumps to this block. You can log the error, ROLLBACK, and optionally re-raise it.

exception_handling.sql 
CREATE OR REPLACE PROCEDURE safe_update(p_id INT, p_value NUMERIC)
LANGUAGE plpgsql
AS $$
BEGIN
  UPDATE some_table SET amount = p_value WHERE id = p_id;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'Row with id % not found', p_id;
  END IF;

  COMMIT;
  RAISE NOTICE 'Updated id % successfully.', p_id;

EXCEPTION
  -- Catch specific error: unique violation
  WHEN unique_violation THEN
    ROLLBACK;
    RAISE NOTICE 'Duplicate key — skipping id %', p_id;

  -- Catch any other error
  WHEN OTHERS THEN
    ROLLBACK;
    -- SQLERRM = the error message, SQLSTATE = the error code
    INSERT INTO error_log (message, state, occurred_at)
    VALUES (SQLERRM, SQLSTATE, NOW());
    RAISE;   -- re-raise to caller
END;
$$;

Common Exception Names

  • unique_violation — duplicate key error (SQLSTATE 23505)
  • foreign_key_violation — FK constraint fails (SQLSTATE 23503)
  • not_null_violation — NULL in a NOT NULL column (SQLSTATE 23502)
  • division_by_zero — divide by zero error (SQLSTATE 22012)
  • no_data_found — SELECT INTO returned no rows
  • OTHERS — catches any exception not matched above

Interview

Interview Q&A + Cheat Sheet

Q: When was CREATE PROCEDURE added to PostgreSQL?

PostgreSQL 11. Before that, functions were used as a workaround — but they cannot contain COMMIT/ROLLBACK.

Q: Can a procedure return a value?

Not directly. Procedures have no RETURN statement. However, INOUT and OUT parameters can pass values back to the caller. For result sets, use a function with RETURNS TABLE or RETURNS SETOF.

Q: What happens if RAISE EXCEPTION is called inside a procedure?

It automatically triggers a ROLLBACK of the current transaction. You can catch it with an EXCEPTION block, log it, and decide to re-raise, skip, or continue.

Q: Can you call a procedure from inside another procedure?

Yes. Use CALL inside the procedure body to call another procedure. Each nested CALL participates in or extends the current transaction state.
