🔴 UUID

TYPE 1 UUID — Universally Unique Identifier
🔴 CriticalIdentityDistributed Systems

Q: What is UUID and why use it over SERIAL/INTEGER?

A: UUID is a 128-bit value guaranteed to be unique across all machines and all time — no central counter needed. Use it when you have multiple databases, microservices, or need to generate IDs on the client before inserting into the database. SERIAL is fine for single-database apps but breaks in distributed setups.

🧠 Analogy: SERIAL is like numbering tickets at one counter (1, 2, 3…). UUID is like giving everyone a passport — globally unique, no counter needed.
uuid.sql
-- Enable UUID extension (PostgreSQL 13+ has gen_random_uuid() built-in) CREATE EXTENSION IF NOT EXISTS "pgcrypto"; -- older PG -- Create table using UUID primary key CREATE TABLE users ( id UUID DEFAULT gen_random_uuid() PRIMARY KEY, name TEXT NOT NULL, created_at TIMESTAMPTZ DEFAULT NOW() ); -- Insert — ID auto-generated INSERT INTO users (name) VALUES ('Alice'); -- Or generate UUID manually before insert SELECT gen_random_uuid(); -- → a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11 -- Query by UUID SELECT * FROM users WHERE id = 'a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11';

⚠️ Gotcha: Random UUIDs cause index fragmentation because inserts are not sequential. In write-heavy tables, consider ULIDv7 or uuid_generate_v7() (time-ordered UUIDs) to keep index efficient.
✅ Rule: Use UUID for any system that will ever scale, sync, or have multiple servers. Use SERIAL only for simple, single-DB apps.

🔴 ENUM

TYPE 2 ENUM — Fixed Set of Allowed Values
🔴 CriticalType Safety

Q: What is an ENUM type and when should you use it?

A: ENUM is a custom data type with a fixed list of allowed string values. PostgreSQL stores it as a tiny integer internally but displays it as the label. Use it for columns like status, role, or priority — where only a known set of values is valid. It's safer than plain TEXT because the DB rejects invalid values automatically.

🧠 Analogy: ENUM is like a dropdown menu — users can only pick from the defined options, not type anything they want.
enum.sql
-- Step 1: Create the ENUM type CREATE TYPE order_status AS ENUM ( 'pending', 'processing', 'shipped', 'delivered', 'cancelled' ); -- Step 2: Use it as a column type CREATE TABLE orders ( id UUID DEFAULT gen_random_uuid() PRIMARY KEY, status order_status DEFAULT 'pending' ); -- Insert valid value ✅ INSERT INTO orders (status) VALUES ('shipped'); -- Insert invalid value ❌ — DB rejects it INSERT INTO orders (status) VALUES ('on_the_way'); -- ERROR: invalid input value for enum order_status: "on_the_way" -- Filter and compare SELECT * FROM orders WHERE status = 'pending'; SELECT * FROM orders WHERE status IN ('pending', 'processing'); -- Add a new value to existing ENUM (PostgreSQL 9.1+) ALTER TYPE order_status ADD VALUE 'refunded' AFTER 'cancelled'; -- List all enum values SELECT unnest(enum_range(NULL::order_status));
⚠️ Gotcha 1: You cannot remove or rename ENUM values easily — it requires creating a new type and migrating the column. Plan your values carefully upfront.
⚠️ Gotcha 2: Adding a new value with ADD VALUE cannot be done inside a transaction block in older PostgreSQL versions.
💡 Alternative: Some teams prefer a CHECK constraint on TEXT (CHECK (status IN ('a','b','c'))) because it's easier to modify. ENUM wins on storage and type safety; CHECK wins on flexibility.

🟡 ARRAY

TYPE 3 ARRAY — Ordered List Inside One Column
🟡 High ImpactCollections

Q: What is an ARRAY type in PostgreSQL and when should you use it?

A: ARRAY lets you store a list of values of the same type inside a single column — like tags on a blog post or phone numbers for a contact. Any base type can be arrayed: TEXT[], INT[], UUID[], etc. Use it when you want to avoid a separate join table for simple one-to-many data.

🧠 Analogy: Instead of having a separate "tags" table with a join, you can store ['sql','postgres','database'] right inside the post row.
array.sql
-- Create table with ARRAY column CREATE TABLE posts ( id SERIAL PRIMARY KEY, title TEXT, tags TEXT[] -- array of text values ); -- Insert using ARRAY literal INSERT INTO posts (title, tags) VALUES ('Learn SQL', '{sql, postgres, database}'); -- Or using ARRAY constructor INSERT INTO posts (title, tags) VALUES ('Web Dev', ARRAY['html', 'css', 'js']); -- Access element by index (1-based, NOT 0!) SELECT tags[1] FROM posts; -- 'sql' (first element) SELECT tags[2] FROM posts; -- 'postgres' -- Find posts that contain a specific tag SELECT * FROM posts WHERE 'sql' = ANY(tags); -- Find posts that have ALL of these tags SELECT * FROM posts WHERE tags @> ARRAY['sql', 'postgres']; -- Append an element to array UPDATE posts SET tags = array_append(tags, 'beginner') WHERE id = 1; -- Remove an element from array UPDATE posts SET tags = array_remove(tags, 'beginner') WHERE id = 1; -- Get array length SELECT array_length(tags, 1) FROM posts; -- Expand array into individual rows SELECT id, unnest(tags) AS tag FROM posts;
⚠️ Gotcha: PostgreSQL arrays are 1-indexed (start at 1), not 0-indexed like most languages. tags[1] is the first element.
💡 Index it: Add a GIN index for fast @> and ANY() searches on large tables: CREATE INDEX ON posts USING GIN (tags);
✅ When to use: Simple lists where you won't query individual elements heavily. If you need to JOIN, filter, or aggregate elements often → use a proper join table instead.

🟡 JSON

TYPE 4 JSON — Text-Stored JSON (Validated)
🟡 Know the DifferenceSemi-Structured

Q: What is the JSON type in PostgreSQL?

A: JSON stores your data as plain text, but validates it is valid JSON on insert. It preserves the original format — key order, whitespace, and even duplicate keys. Every time you read a JSON value, PostgreSQL re-parses the text from scratch, which makes reads slower.

🧠 Analogy: JSON is like storing a letter in an envelope. The post office checks it's a real letter before accepting it, but every time someone reads it, they have to open and read it fresh.
json_type.sql
-- JSON preserves everything as-is SELECT '{ "b": 2, "a": 1, "a": 99 }'::json; -- → { "b": 2, "a": 1, "a": 99 } (whitespace kept, both "a" kept) -- vs JSONB — parses and cleans it up SELECT '{ "b": 2, "a": 1, "a": 99 }'::jsonb; -- → {"a": 99, "b": 2} (whitespace gone, keys sorted, last "a" wins) -- Basic extraction from JSON (same operators as JSONB) SELECT '{"name":"Alice","age":30}'::json->>'name'; -- → Alice
📌 When to use JSON (not JSONB): When you receive an API response and need to store and return the exact original payload — byte for byte. Example: audit log of raw webhook events.
✅ In almost every other case, use JSONB. It's faster to query, supports GIN indexes, and is what PostgreSQL recommends.

🟡 JSONB

TYPE 5 JSONB — Binary JSON (Fast & Indexable)
🟡 High ImpactSemi-Structured

Q: What is JSONB and how is it different from JSON?

A: JSONB stores data in a decomposed binary format — parsed once on write, fast to read. It does not preserve key order or duplicate keys. It supports GIN indexes and the powerful @>, ? operators. It's the right choice for querying, filtering, and indexing flexible data.

🧠 Analogy: JSONB is like a pre-sorted filing cabinet. It takes a moment to file things in order, but finding anything later is very fast.
📌 Simple rule: Always use JSONB unless you specifically need to preserve original JSON formatting.

🟡 Generated Columns

TYPE 6 Generated Columns — Always-Computed Values
🟡 High ImpactComputed

Q: What is a Generated Column and when would you use one?

A: A Generated Column is a column whose value is automatically computed from other columns. You define the formula once; PostgreSQL calculates and stores it on every INSERT or UPDATE. You never need to manually keep it in sync. PostgreSQL supports STORED generated columns (value saved to disk).

🧠 Analogy: Like a spreadsheet formula cell — you type values in columns A and B, and column C automatically shows A + B. You never edit C directly.
generated_columns.sql
-- Example 1: Full name from first + last CREATE TABLE employees ( id SERIAL PRIMARY KEY, first_name TEXT, last_name TEXT, full_name TEXT GENERATED ALWAYS AS (first_name || ' ' || last_name) STORED ); INSERT INTO employees (first_name, last_name) VALUES ('Alice', 'Smith'); SELECT full_name FROM employees; -- → Alice Smith (auto-generated) -- Example 2: Price with tax CREATE TABLE products ( id SERIAL PRIMARY KEY, price NUMERIC, price_w_tax NUMERIC GENERATED ALWAYS AS (price * 1.18) STORED ); -- Example 3: Extract a JSONB key (use with index for fast queries) CREATE TABLE orders ( id SERIAL PRIMARY KEY, metadata JSONB, status TEXT GENERATED ALWAYS AS (metadata->>'status') STORED ); -- Index the generated column — now fast B-tree on a JSONB field! CREATE INDEX idx_orders_status ON orders (status); -- Fast query — uses B-tree index SELECT * FROM orders WHERE status = 'pending'; -- You CANNOT insert/update a generated column manually UPDATE orders SET status = 'done' WHERE id = 1; -- ERROR: column "status" can only be updated to DEFAULT
⚠️ Gotcha: You cannot insert into or update a generated column — PostgreSQL manages it. Trying to do so gives an error.
⚠️ Gotcha 2: Generated columns can only reference columns in the same row — no subqueries, no other tables, no functions with side effects.
✅ Best use case: Extracting a frequently-filtered JSONB key into a Generated Column + B-tree index. Much lighter than a full GIN index when you only query one key.

Indexes CREATE INDEX idx_users_prefs ON users USING GIN (preferences); CREATE INDEX idx_users_perms ON users USING GIN (permissions); CREATE INDEX idx_users_role ON users (role); -- 4. Insert a row INSERT INTO users (email, first_name, last_name, role, permissions, preferences) VALUES ( 'alice@example.com', 'Alice', 'Smith', 'admin', ARRAY['read', 'write', 'delete'], '{"theme":"dark","lang":"en","notifications":true}' ); -- 5.
