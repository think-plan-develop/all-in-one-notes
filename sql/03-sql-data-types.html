🔢 Numeric Types
01
What numeric types does PostgreSQL offer, and when do you use each?
ANSWER

Three families — integers (whole numbers, no decimals), floating point (approximate decimals, fast), and numeric/decimal (exact decimals, used for money). Choose based on whether you need exact precision or are OK with approximation.

Integer Types
SMALLINT
2 bytes · -32,768 to 32,767
Tiny whole numbers. Saves space when range is small.
age SMALLINT
INTEGER / INT
4 bytes · -2.1B to 2.1B
Standard whole number. Default choice for IDs and counts.
quantity INT
BIGINT
8 bytes · ±9.2 quintillion
Large whole numbers. Use for IDs at scale.
user_id BIGINT
SERIAL
4 bytes · auto-increment
Auto-incrementing INTEGER.
id SERIAL PRIMARY KEY
BIGSERIAL
8 bytes · auto-increment
Auto-incrementing BIGINT for high-volume tables.
id BIGSERIAL PRIMARY KEY
SMALLSERIAL
2 bytes · rare
Auto-incrementing SMALLINT. Rarely used.
id SMALLSERIAL
Floating Point
REAL
4 bytes · ~6 digits
Single-precision float. Approximate, fast.
temperature REAL
DOUBLE PRECISION
8 bytes · ~15 digits
More accurate than REAL. Still approximate.
score DOUBLE PRECISION
Exact Decimal
NUMERIC(p,s)
Variable · exact precision
p = total digits, s = digits after decimal. Use for money.
price NUMERIC(10,2)
DECIMAL(p,s)
Same as NUMERIC
Alias — NUMERIC is preferred in PostgreSQL.
amount DECIMAL(12,4)
numeric_types.sql
CREATE TABLE demo_numeric (
  id            BIGSERIAL PRIMARY KEY,
  age           SMALLINT,
  quantity      INTEGER,
  price         NUMERIC(10,2)          -- exact! never REAL for money
);

-- Float rounding issue
SELECT 0.1::REAL + 0.2::REAL;     -- 0.3000000119... ❌
SELECT 0.1::NUMERIC + 0.2::NUMERIC; -- 0.3 ✅
⚠️ Never use REAL or DOUBLE PRECISION for money — use NUMERIC(p,s) for any financial value.
✅ Integer for whole numbers · NUMERIC for money · REAL/DOUBLE for approximations
🔤 Text / String Types
02
What are the text types, and which should you default to?
ANSWER

TEXT (unlimited, recommended), VARCHAR(n) (limited length), CHAR(n) (fixed length, pads with spaces). TEXT and VARCHAR have identical performance in PostgreSQL — use TEXT by default.

TEXT
Unlimited length
Best general-purpose string type. Preferred in PostgreSQL.
description TEXT
VARCHAR(n)
Max n characters
Enforces a max length as a constraint.
email VARCHAR(255)
CHAR(n)
Fixed n · pads spaces
Almost never useful — avoid it.
code CHAR(3) → 'US '
text_types.sql
CREATE TABLE users (
  username     VARCHAR(50),
  email        VARCHAR(255),
  bio          TEXT,
  country_code CHAR(2)   -- 'US', 'IN', 'GB'
);

SELECT 'hi'::CHAR(5) = 'hi   ';   -- true (spaces added)
SELECT 'hello' || ' world';        -- concatenate
💡 Use TEXT for most columns. Use VARCHAR(n) only to enforce a max length. Avoid CHAR(n) entirely.
☑️ Boolean Type
03
How does BOOLEAN work in PostgreSQL?
ANSWER

Stores TRUE, FALSE, or NULL. Accepts many input formats ('true', 'yes', '1', 't'). Uses 1 byte. Never use INTEGER 0/1 for flags — use BOOLEAN.

boolean.sql
CREATE TABLE products (
  id        SERIAL PRIMARY KEY,
  is_active BOOLEAN DEFAULT true,
  in_stock  BOOLEAN DEFAULT false
);

SELECT * FROM products WHERE is_active;      -- same as = true
SELECT * FROM products WHERE NOT is_active;
✅ 1 byte · TRUE/FALSE/NULL · use for every flag/status column.
📅 Date & Time Types
04
What date/time types exist, and which should you use in production?
ANSWER

DATE, TIME, TIMESTAMP (no timezone), TIMESTAMPTZ (with timezone — recommended), and INTERVAL (duration). Always use TIMESTAMPTZ over TIMESTAMP — it stores UTC and converts on read.

DATE
4 bytes · date only
Year, month, day. No time.
birth_date DATE
TIME
8 bytes · time only
Time of day, no date.
opening_time TIME
TIMESTAMP
8 bytes · no timezone
Ambiguous across timezones. Avoid in production.
created_at TIMESTAMP ⚠️
TIMESTAMPTZ
8 bytes · with timezone
Correct choice for production timestamps.
created_at TIMESTAMPTZ ✅
INTERVAL
16 bytes · duration
A period of time for date arithmetic.
duration INTERVAL
datetime.sql
CREATE TABLE events (
  id         BIGSERIAL PRIMARY KEY,
  event_date DATE,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  duration   INTERVAL
);

SELECT NOW() - INTERVAL '7 days';
SELECT DATE_TRUNC('month', NOW());
⚠️ Always use TIMESTAMPTZ, not TIMESTAMP — TIMESTAMP has no timezone info and becomes ambiguous across servers.
📦 Binary Type
05
What is BYTEA, and when do you use it?
ANSWER

BYTEA stores raw binary data — file contents, encrypted blobs, hashes. It's the PostgreSQL equivalent of BLOB in other databases.

bytea.sql
CREATE TABLE files (
  id       SERIAL PRIMARY KEY,
  content  BYTEA,
  checksum BYTEA
);

SELECT encode(content, 'hex') FROM files;
💡 For large files, store them in object storage (S3, GCS) and keep only the URL in PostgreSQL. BYTEA fits small blobs — hashes, keys, thumbnails.
🌐 Network Address Types
06
Why use network types instead of TEXT for IP addresses?
ANSWER

Network types give built-in validation, indexing, and operators like "is this IP in this subnet?" — all lost if you store IPs as TEXT.

INET
7–19 bytes
IPv4/IPv6, optionally with subnet mask.
ip INET
CIDR
7–19 bytes
Network ranges, not individual hosts.
network CIDR
MACADDR
6 bytes
MAC hardware address.
mac MACADDR
network_types.sql
CREATE TABLE access_log (
  id         BIGSERIAL PRIMARY KEY,
  client_ip  INET
);

SELECT * FROM access_log
WHERE  client_ip <<= '192.168.1.0/24';
✅ INET validates IP format automatically and gives subnet operators for free.
📐 Geometric Types
07
What geometric types does PostgreSQL support natively?
ANSWER

POINT, LINE, LSEG, BOX, PATH, POLYGON, CIRCLE — with operators for distance, intersection, and containment. For real GIS work, use the PostGIS extension.

POINT
16 bytes · (x,y)
A single point in 2D space.
location POINT
CIRCLE
24 bytes
Centre point + radius.
zone CIRCLE
POLYGON
Variable
Closed shape from a list of points.
region POLYGON
geometric.sql
SELECT '(0,0)'::POINT <-> '(3,4)'::POINT;  -- 5.0
SELECT '(1,1)'::POINT <@ '<(0,0),2>'::CIRCLE;  -- true
💡 For GPS coordinates, use PostGIS's GEOGRAPHY type — native POINT treats the world as flat.
✨ Special Types
08
What other special types exist, and which should you avoid?
TypeWhat it storesNote
MONEYCurrency, fixed 2 decimalsLocale-dependent ⚠️ — use NUMERIC(p,2)
XMLValid XML documentsUse JSONB unless XML is required
TSVECTORPre-processed search documentPairs with TSQUERY
OIDInternal object identifierSystem use only
special_types.sql
CREATE TABLE articles (
  id     SERIAL PRIMARY KEY,
  title  TEXT,
  body   TEXT,
  tokens TSVECTOR
);

UPDATE articles SET tokens = to_tsvector('english', title || ' ' || body);

SELECT title FROM articles
WHERE  tokens @@ to_tsquery('english', 'postgres & replication');

CREATE INDEX idx_articles_fts ON articles USING GIN (tokens);
⚠️ Avoid MONEY — locale-dependent. Always use NUMERIC(p,2) for currency.

🧑‍💻 Practice — Coding Section Uses only types covered above
P1
Design a request_log table
TASK

Using only the types covered above, design a request_log table recording: a large-scale auto-increment key, the client IP (validated), a length-limited status code, a success flag, a whole-number response time, a timezone-correct timestamp, a processing duration, and an optional small binary hash.

request_log.sql
CREATE TABLE request_log (
  id              BIGSERIAL PRIMARY KEY,      -- §01
  client_ip       INET,                       -- §06
  status_code     VARCHAR(10),               -- §02
  succeeded       BOOLEAN DEFAULT true,     -- §03
  response_ms     INTEGER,                    -- §01
  requested_at    TIMESTAMPTZ DEFAULT NOW(),  -- §04
  processing_time INTERVAL,                   -- §04
  payload_hash    BYTEA                       -- §05
);
✅ Every type traces back to a section above — no new type introduced.
BIGSERIAL used for a high-volume log table, not SERIAL
INET used instead of TEXT for the IP column
TIMESTAMPTZ used instead of TIMESTAMP
INTERVAL used for a duration, not a raw integer of ms
