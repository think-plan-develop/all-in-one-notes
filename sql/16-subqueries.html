🔴 Topic 1 & 2 — What is a Subquery & Why Use It?

Q1 What is a Subquery?
🔴 CriticalConceptFoundation

Q: What is a subquery in SQL?

A: A subquery is a query written inside another query. The inner query (subquery) runs first and its result is handed to the outer query. It is always written inside parentheses ( ).

🧠 Analogy: You ask your friend "Who earns more than the average salary?" Your friend first calculates the average (inner query), then finds people above it (outer query). Two steps, one question.
SELECT name FROM employees WHERE salary > (SELECT AVG(salary) FROM employees); ────────────────────────────────── ↑ This is the subquery Runs FIRST → returns one value Outer query uses that value
subquery_intro.sql
-- Find employees earning more than the average salary SELECT name, salary FROM employees WHERE salary > (SELECT AVG(salary) FROM employees); -- Step 1 (inner): SELECT AVG(salary) FROM employees → 55000 -- Step 2 (outer): SELECT name FROM employees WHERE salary > 55000
✅ Subquery = a query inside a query. Always in ( ). Inner runs first, outer uses the result.
Q2 Why Do We Use Subqueries?
🔴 CriticalConcept

Q: Why do we use subqueries instead of just writing one query?

A: Subqueries let you use the result of one query as input to another — solving problems that a single flat query cannot handle. They are used when you need a calculated value (like AVG), a list of IDs, or an existence check from another table before filtering your main result.

Use CaseExample ProblemSubquery Solves It By
Dynamic filter valueEmployees above average salaryComputing AVG inside the WHERE
Membership checkCustomers who placed an orderReturning a list of IDs with IN
Existence checkOrders with at least one itemEXISTS returns true/false
Derived dataTop 5 departments by headcountSubquery in FROM creates a temp table
Row-by-row calculationEach employee's rank in their deptCorrelated subquery references outer row
✅ Simple rule: use a subquery when the WHERE condition depends on data you need to calculate first from the same or another table.

🔴 Topic 3 — Types of Subqueries

Q3 4 Types of Subqueries — Explained Simply
🔴 CriticalTypes
TYPE 1

Single Row Subquery

Returns exactly one row, one column. Used with single-value operators: = > < >= <= <>

TYPE 2

Multiple Row Subquery

Returns multiple rows. Used with set operators: IN NOT IN ANY ALL

TYPE 3

Correlated Subquery

References a column from the outer query. Runs once for every row in the outer query. Slower but powerful.

TYPE 4

Non-Correlated Subquery

Completely independent of the outer query. Runs once, result is reused. Faster than correlated.

subquery_types.sql
─── TYPE 1: Single Row ──────────────────────────────────────────────── -- Returns ONE value: the max salary SELECT name, salary FROM employees WHERE salary = (SELECT MAX(salary) FROM employees); -- Inner query returns: 95000 (one row, one column) -- Outer query: WHERE salary = 95000 ─── TYPE 2: Multiple Row ────────────────────────────────────────────── -- Returns MANY values: all dept IDs where avg salary > 60000 SELECT name FROM employees WHERE dept_id IN ( SELECT dept_id FROM employees GROUP BY dept_id HAVING AVG(salary) > 60000 ); -- Inner query returns: (2, 5, 7) (multiple rows) -- Outer query: WHERE dept_id IN (2, 5, 7) ─── TYPE 3: Correlated ──────────────────────────────────────────────── -- References outer 'e1.dept_id' — runs once PER outer row SELECT e1.name, e1.salary FROM employees e1 WHERE e1.salary > ( SELECT AVG(e2.salary) FROM employees e2 WHERE e2.dept_id = e1.dept_id -- ← references outer query's row ); -- For each employee, compares their salary to THEIR OWN dept average ─── TYPE 4: Non-Correlated ──────────────────────────────────────────── -- Completely independent — runs ONCE, result reused for all outer rows SELECT name FROM employees WHERE salary > (SELECT AVG(salary) FROM employees); -- Inner runs once → 55000. All rows checked against 55000.
Correlated vs Non-Correlated: Non-Correlated: Inner runs ONCE → outer uses same value for all rows Faster ✅ Correlated: Inner runs once PER outer row → N times for N rows Slower ⚠️ but can reference outer row's values
⚠️ Correlated subquery gotcha: If your outer table has 1 million rows, the correlated subquery runs 1 million times. Always check if it can be replaced with a JOIN or window function.

🔴 Topic 4 — Comparison Operators with Subqueries

Q4 Comparison Operators: = > < >= <= <>
🔴 CriticalOperators

Q: Which comparison operators can be used with subqueries and when?

A: Standard comparison operators work when the subquery returns exactly one value (single-row subquery). If the subquery returns more than one row and you use =, PostgreSQL throws an error: "more than one row returned by a subquery used as an expression".

=
Equal to
salary = (SELECT MAX...)
>
Greater than
salary > (SELECT AVG...)
<
Less than
salary < (SELECT MIN...)
>=
Greater or equal
price >= (SELECT AVG...)
<=
Less or equal
age <= (SELECT AVG...)
<>
Not equal
id <> (SELECT MAX...)
comparison_ops.sql
-- = : find the employee with max salary SELECT name, salary FROM employees WHERE salary = (SELECT MAX(salary) FROM employees); -- > : above average salary SELECT name, salary FROM employees WHERE salary > (SELECT AVG(salary) FROM employees); -- < : products cheaper than average price SELECT name, price FROM products WHERE price < (SELECT AVG(price) FROM products); -- <> : all employees except the highest paid SELECT name FROM employees WHERE salary <> (SELECT MAX(salary) FROM employees); -- >= : employees at or above 90th percentile salary SELECT name, salary FROM employees WHERE salary >= (SELECT PERCENTILE_CONT(0.9) WITHIN GROUP (ORDER BY salary) FROM employees);
⚠️ Critical rule: Comparison operators (= > < etc.) only work when the subquery returns exactly 1 row and 1 column. For multiple rows, use IN / ANY / ALL instead.
💡 Use aggregate functions (MAX, MIN, AVG, COUNT) inside single-row subqueries — they always return exactly one value.

🔴 Topic 5 — Special Operators: IN, NOT IN, EXISTS, NOT EXISTS, ANY, ALL

Q5 Special Operators — Each One Explained
🔴 CriticalOperators
IN
Checks if a value is in the subquery's result list. True if it matches any returned value.
WHERE dept_id IN (SELECT id FROM depts WHERE budget > 100000)
NOT IN
Opposite of IN. True if value is NOT in the list. Beware NULL values — one NULL makes all rows disappear.
WHERE id NOT IN (SELECT customer_id FROM orders)
EXISTS
Returns TRUE if subquery returns at least 1 row. Doesn't care about the values — just checks if rows exist. Fast.
WHERE EXISTS (SELECT 1 FROM orders WHERE orders.cust_id = c.id)
NOT EXISTS
Returns TRUE if subquery returns zero rows. Best way to find "has no related records" — safer than NOT IN with NULLs.
WHERE NOT EXISTS (SELECT 1 FROM orders WHERE orders.cust_id = c.id)
ANY / SOME
Returns TRUE if the comparison is true for at least one value in the subquery result. ANY and SOME are synonyms.
WHERE salary > ANY (SELECT salary FROM employees WHERE dept_id = 5)
ALL
Returns TRUE only if the comparison is true for ALL values in the subquery result. Very strict.
WHERE salary > ALL (SELECT salary FROM employees WHERE dept_id = 5)
special_operators.sql
── IN ───────────────────────────────────────────────────────────────── -- Customers who placed at least one order SELECT name FROM customers WHERE id IN (SELECT customer_id FROM orders); ── NOT IN ───────────────────────────────────────────────────────────── -- Customers who NEVER placed an order SELECT name FROM customers WHERE id NOT IN (SELECT customer_id FROM orders WHERE customer_id IS NOT NULL); -- ← must filter NULLs! ── EXISTS ───────────────────────────────────────────────────────────── -- Customers who have at least one order (safer than IN for large sets) SELECT c.name FROM customers c WHERE EXISTS ( SELECT 1 -- SELECT 1 is convention — value doesn't matter, only row existence FROM orders o WHERE o.customer_id = c.id ); ── NOT EXISTS ───────────────────────────────────────────────────────── -- Customers with zero orders (anti-join pattern) SELECT c.name FROM customers c WHERE NOT EXISTS ( SELECT 1 FROM orders o WHERE o.customer_id = c.id ); ── ANY ──────────────────────────────────────────────────────────────── -- Employees earning more than SOME (any one) person in Dept 5 SELECT name, salary FROM employees WHERE salary > ANY ( SELECT salary FROM employees WHERE dept_id = 5 ); -- True if salary > at least ONE salary in Dept 5 -- Equivalent to: salary > MIN(salary in dept 5) ── ALL ──────────────────────────────────────────────────────────────── -- Employees earning more than EVERYONE in Dept 5 SELECT name, salary FROM employees WHERE salary > ALL ( SELECT salary FROM employees WHERE dept_id = 5 ); -- True only if salary > EVERY salary in Dept 5 -- Equivalent to: salary > MAX(salary in dept 5)
⚠️ NOT IN + NULL = silent disaster. If any value returned by the subquery is NULL, NOT IN returns no rows at all — because NULL comparisons are UNKNOWN, not FALSE. Always add WHERE col IS NOT NULL inside NOT IN subqueries, or use NOT EXISTS instead.
IN vs EXISTS — when to prefer which: IN → small result list, simple membership check EXISTS → large tables, when you only need "does it exist?" (stops at first match) ANY → "more than at least one" → equivalent to > MIN(...) ALL → "more than every single one" → equivalent to > MAX(...)

🟡 Topic 6 — Subquery in WHERE Clause

Q6 Subquery in WHERE Clause — Most Common Use
🔴 CriticalWHERE

Q: How and why do we use subqueries in the WHERE clause?

A: The WHERE clause filters rows. A subquery in WHERE provides a dynamic filter value — something you don't know at the time of writing the query, but can calculate from the data itself. This is the most common place to use a subquery.

where_subquery.sql
── Example 1: Single value filter ───────────────────────────────────── -- Who earns more than the average salary? SELECT name, salary FROM employees WHERE salary > (SELECT AVG(salary) FROM employees); ── Example 2: List filter with IN ───────────────────────────────────── -- Employees in departments located in 'New York' SELECT name, dept_id FROM employees WHERE dept_id IN ( SELECT id FROM departments WHERE location = 'New York' ); ── Example 3: Correlated subquery in WHERE ──────────────────────────── -- Employees earning above their own department's average SELECT e.name, e.salary, e.dept_id FROM employees e WHERE e.salary > ( SELECT AVG(e2.salary) FROM employees e2 WHERE e2.dept_id = e.dept_id -- links to outer query's current row ); ── Example 4: EXISTS in WHERE ───────────────────────────────────────── -- Show only departments that have at least one employee SELECT d.name FROM departments d WHERE EXISTS ( SELECT 1 FROM employees e WHERE e.dept_id = d.id ); ── Example 5: Date-based dynamic filter ─────────────────────────────── -- Orders placed after the most recent cancelled order SELECT * FROM orders WHERE order_date > ( SELECT MAX(order_date) FROM orders WHERE status = 'cancelled' );
✅ WHERE subquery = dynamic filter. The value to compare against is computed live from the data, not hardcoded.

🟡 Topic 7 — Subquery in FROM Clause (Derived Table)

Q7 Subquery in FROM Clause — The Derived Table
🟡 High ImpactFROM

Q: What is a derived table and how does a subquery in FROM work?

A: When you put a subquery in the FROM clause, the result acts as a temporary table — called a derived table or inline view. The outer query then queries this "virtual table" as if it were a real table. You must give it an alias.

🧠 Analogy: You create a temporary spreadsheet (inner query), then run another filter/calculation on top of that spreadsheet (outer query). The temp spreadsheet never gets saved — it only exists for this query.
from_subquery.sql
── Example 1: Department summary then filtered ──────────────────────── -- First get avg salary per dept, then filter depts above 60000 SELECT dept_id, avg_salary FROM (SELECT dept_id, AVG(salary) AS avg_salary -- inner: build summary FROM employees GROUP BY dept_id) AS dept_summary -- ← MUST have alias WHERE avg_salary > 60000; -- outer: filter it -- Why not just HAVING? You can, but derived tables let you -- do further joins, calculations, or transformations on top. ── Example 2: Derived table joined with another table ───────────────── SELECT d.name, ds.avg_salary, ds.headcount FROM departments d JOIN (SELECT dept_id, AVG(salary) AS avg_salary, COUNT(*) AS headcount FROM employees GROUP BY dept_id) AS ds ON d.id = ds.dept_id ORDER BY ds.avg_salary DESC; ── Example 3: Top 3 customers by revenue ───────────────────────────── SELECT c.name, top.total_revenue FROM customers c JOIN (SELECT customer_id, SUM(amount) AS total_revenue FROM orders GROUP BY customer_id ORDER BY total_revenue DESC LIMIT 3) AS top ON c.id = top.customer_id;
⚠️ A derived table MUST have an alias — AS some_name after the closing parenthesis. Forgetting the alias gives a syntax error.
📌 Derived table vs CTE: Both create a temporary result set. CTE (WITH) is cleaner for complex queries — same logic, more readable. Derived tables are older syntax but equally powerful.

🟡 Topic 8 — Subquery in SELECT Clause (Scalar Subquery)

Q8 Subquery in SELECT Clause — Scalar Subquery
🟡 High ImpactSELECT

Q: What is a scalar subquery in the SELECT clause?

A: A subquery inside the SELECT list — used to add a computed column to each row in the result. It must return exactly one row and one column (a scalar value). It acts like a calculated extra column, often correlated to reference the current row.

🧠 Analogy: For each employee row, you want to show their salary alongside the company average. You can't JOIN for this without grouping — a SELECT subquery computes a value and attaches it to each row automatically.
select_subquery.sql
── Example 1: Show each employee's salary vs company average ────────── SELECT name, salary, (SELECT AVG(salary) FROM employees) AS company_avg, salary - (SELECT AVG(salary) FROM employees) AS diff_from_avg FROM employees; ── Example 2: Correlated scalar — each customer's total order count ─── SELECT c.name, c.email, (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.id) AS total_orders -- one value per customer FROM customers c; ── Example 3: Latest order date per customer ────────────────────────── SELECT c.name, (SELECT MAX(order_date) FROM orders o WHERE o.customer_id = c.id) AS last_order_date FROM customers c; ── Example 4: Department name lookup ───────────────────────────────── SELECT e.name, e.salary, (SELECT d.name FROM departments d WHERE d.id = e.dept_id) AS department_name FROM employees e;
⚠️ Performance warning: A correlated scalar subquery in SELECT runs once per row. For 100,000 employees, the subquery runs 100,000 times. For large tables, rewrite using LEFT JOIN or window functions instead.
💡 Better alternative for large tables: 
SELECT e.name, e.salary, d.name AS dept_name
FROM   employees e
LEFT JOIN departments d ON d.id = e.dept_id;
Same result, runs once.

🟡 Topic 9 — Nested Subqueries

Q9 Nested Subqueries — Subquery inside a Subquery
🟡 High ImpactNested

Q: What is a nested subquery and how deep can they go?

A: A nested subquery is a subquery inside another subquery — three or more levels of queries stacked. They are read from innermost to outermost. PostgreSQL supports many levels of nesting but beyond 2-3 levels, readability suffers badly — use CTEs instead.

Execution order — innermost runs first: SELECT name FROM employees WHERE dept_id IN ( SELECT id FROM departments ← Level 2 (runs second) WHERE location_id IN ( SELECT id FROM locations ← Level 1 (runs FIRST) WHERE country = 'India' ) ) ↑ Level 3 (runs last, uses Level 2 result)
nested_subqueries.sql
── 2-level nest: employees in NY departments ────────────────────────── SELECT name FROM employees WHERE dept_id IN ( SELECT id FROM departments WHERE location = 'New York' -- Level 1 runs first ); ── 3-level nest: employees in Indian city departments ───────────────── SELECT name FROM employees WHERE dept_id IN ( SELECT id FROM departments WHERE location_id IN ( -- Level 2 SELECT id FROM locations WHERE country = 'India' -- Level 3 (innermost, runs first) ) ); ── Same query rewritten as CTE (much more readable!) ────────────────── WITH indian_locations AS ( SELECT id FROM locations WHERE country = 'India' ), indian_depts AS ( SELECT id FROM departments WHERE location_id IN (SELECT id FROM indian_locations) ) SELECT name FROM employees WHERE dept_id IN (SELECT id FROM indian_depts);
⚠️ Beyond 2 levels of nesting, always convert to a CTE — it's the same logic but each step is named and readable. Deeply nested subqueries are a maintenance nightmare.
✅ Nested subqueries run inside-out. The innermost query runs first. Its result feeds the next level, and so on until the outermost query runs.

🟡 Topic 10 — Subquery vs JOIN

Q10 Subquery vs JOIN — When to Use Which
🔴 Critical InterviewComparison

Q: What is the difference between a subquery and a JOIN — when do you prefer one over the other?

A: JOIN combines rows from multiple tables horizontally. Subquery uses the result of one query to filter or compute in another. In many cases they produce the same result but modern query planners often make them equally fast. The choice is mainly about readability and intent.

ScenarioPreferWhy
Need columns from both tablesJOINSubquery can't easily return multi-table columns
Just check if a match existsEXISTS subqueryCleaner intent, stops at first match
Anti-join (no match)NOT EXISTS or LEFT JOIN IS NULLNOT IN breaks with NULLs
Aggregate then filterSubquery or CTECleaner than HAVING for complex conditions
Row-level calculation vs another tableCorrelated subqueryJOIN would need GROUP BY to avoid duplicates
Large table, performance criticalJOIN with indexCorrelated subquery runs N times
subquery_vs_join.sql
── Same result — three ways ─────────────────────────────────────────── -- Find customers who placed at least one order -- Way 1: Subquery with IN SELECT name FROM customers WHERE id IN (SELECT customer_id FROM orders); -- Way 2: JOIN (may produce duplicates — needs DISTINCT) SELECT DISTINCT c.name FROM customers c JOIN orders o ON c.id = o.customer_id; -- Way 3: EXISTS (best for this use case — no duplicates, fast) SELECT c.name FROM customers c WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id); ── When JOIN is clearly better ──────────────────────────────────────── -- Need customer name AND order amount together SELECT c.name, o.amount, o.order_date FROM customers c JOIN orders o ON c.id = o.customer_id; -- A subquery cannot return columns from both tables in one row ── When subquery is clearly better ─────────────────────────────────── -- Employees earning more than their own department average -- (subquery is cleaner here — JOIN would need extra GROUP BY) SELECT e.name, e.salary FROM employees e WHERE e.salary > (SELECT AVG(e2.salary) FROM employees e2 WHERE e2.dept_id = e.dept_id);
✅ Decision rule: Need columns from both tables → JOIN. Just checking existence → EXISTS. Filtering based on calculated value → Subquery or CTE. When unsure → write both, check EXPLAIN.

🟡 Topic 11 — Subquery vs CTE

Q11 Subquery vs CTE — Readability, Reuse & Performance
🟡 High ImpactComparison

Q: What is the difference between a subquery and a CTE? When do you prefer CTE?

A: Both produce a temporary result set. A CTE (Common Table Expression) is defined with the WITH keyword before the main query and gives the result a name. This makes it reusable in the same query and far more readable for complex logic. Subqueries are inline — fine for simple cases, messy when nested deeply.

SubqueryCTE (WITH)
SyntaxInline inside the main queryDefined before with a name
ReadabilityGets messy when nested✅ Clean, named steps
Reusability❌ Must repeat if used twice✅ Write once, reference multiple times
DebuggingHard — can't run inner part alone✅ Can run each CTE independently
Recursive queries❌ Not possible✅ WITH RECURSIVE supported
PerformancePlanner usually optimises wellIn PostgreSQL 12+, same as subquery
subquery_vs_cte.sql
── Same logic — subquery version (gets messy) ───────────────────────── SELECT d.dept_name, ds.avg_salary FROM departments d JOIN (SELECT dept_id, AVG(salary) AS avg_salary FROM employees GROUP BY dept_id HAVING AVG(salary) > 60000) AS ds ON d.id = ds.dept_id ORDER BY ds.avg_salary DESC; ── Same logic — CTE version (clean & readable) ──────────────────────── WITH high_paying_depts AS ( SELECT dept_id, AVG(salary) AS avg_salary FROM employees GROUP BY dept_id HAVING AVG(salary) > 60000 ) SELECT d.dept_name, h.avg_salary FROM departments d JOIN high_paying_depts h ON d.id = h.dept_id ORDER BY h.avg_salary DESC; ── CTE referenced TWICE — impossible with plain subquery ────────────── WITH dept_stats AS ( SELECT dept_id, AVG(salary) AS avg_sal, COUNT(*) AS headcount FROM employees GROUP BY dept_id ) SELECT d.dept_name, ds.avg_sal, ds.headcount, ds.avg_sal * ds.headcount AS total_salary_budget FROM departments d JOIN dept_stats ds ON d.id = ds.dept_id; -- dept_stats used once but its columns (avg_sal, headcount) used multiple times ── Recursive CTE — not possible with subquery ───────────────────────── WITH RECURSIVE org_chart AS ( SELECT id, name, manager_id, 0 AS level FROM employees WHERE manager_id IS NULL -- CEO (root) UNION ALL SELECT e.id, e.name, e.manager_id, oc.level + 1 FROM employees e JOIN org_chart oc ON e.manager_id = oc.id -- next level down ) SELECT name, level FROM org_chart ORDER BY level;
✅ Rule: Use subquery for simple one-liners. Switch to CTE when the logic has multiple steps, the result is used more than once, or you need recursion.

⭐ Topic 12 — Performance & Best Practices

Q12 Performance & Best Practices — Write Fast Subqueries
⭐ Must KnowPerformance

Q: How do you optimise subqueries for performance?

A: The biggest wins come from: avoiding correlated subqueries on large tables, replacing NOT IN with NOT EXISTS, using EXISTS instead of IN for large result sets, and always running EXPLAIN ANALYZE to see the actual execution plan.

🔴 Rule 1 — Replace Correlated Subquery with JOIN or Window Function

perf_1_correlated.sql
-- ❌ Slow: correlated subquery runs once per employee row SELECT name, (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.id) AS total FROM customers c; -- ✅ Fast: single LEFT JOIN with GROUP BY — runs once SELECT c.name, COUNT(o.id) AS total FROM customers c LEFT JOIN orders o ON o.customer_id = c.id GROUP BY c.name; -- ✅ Also fast: window function (keeps all columns) SELECT c.name, COUNT(o.id) OVER (PARTITION BY c.id) AS total FROM customers c LEFT JOIN orders o ON o.customer_id = c.id;

🔴 Rule 2 — Use NOT EXISTS Instead of NOT IN (NULL Safety)

perf_2_not_in.sql
-- ❌ Dangerous: NOT IN breaks silently if subquery returns ANY NULL SELECT name FROM customers WHERE id NOT IN (SELECT customer_id FROM orders); -- If ANY customer_id in orders is NULL → returns zero rows! -- ✅ Safe: NOT EXISTS handles NULLs correctly SELECT c.name FROM customers c WHERE NOT EXISTS ( SELECT 1 FROM orders o WHERE o.customer_id = c.id ); -- ✅ Also safe: LEFT JOIN anti-join pattern SELECT c.name FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.customer_id IS NULL;

🟡 Rule 3 — Use EXISTS for Large Sets, IN for Small Sets

perf_3_exists_in.sql
-- IN: builds the full list in memory, then checks each row against it -- Fine for small result sets (hundreds of rows) SELECT name FROM customers WHERE country_id IN (SELECT id FROM countries WHERE region = 'Asia'); -- countries is small → IN is fine -- EXISTS: stops as soon as it finds ONE matching row (short-circuit) -- Better for large tables where you only need existence check SELECT c.name FROM customers c WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.amount > 1000); -- orders may have millions of rows — EXISTS stops at first match

🟡 Rule 4 — Always Check with EXPLAIN ANALYZE

perf_4_explain.sql
-- Always test slow queries with EXPLAIN ANALYZE EXPLAIN ANALYZE SELECT name FROM employees WHERE salary > (SELECT AVG(salary) FROM employees); -- What to look for: -- "InitPlan" → non-correlated subquery (runs once) ✅ -- "SubPlan" → correlated subquery (runs per row) ⚠️ -- "Seq Scan" → might need an index -- actual time vs estimated rows — big mismatch = stale stats

🟡 Rule 5 — Filter Early Inside the Subquery

perf_5_filter_early.sql
-- ❌ Filter happens late — inner query scans all orders first SELECT name FROM customers WHERE id IN ( SELECT customer_id FROM orders -- all orders scanned ) AND country = 'India'; -- filter happens in outer -- ✅ Push filters into the subquery — smaller result set earlier SELECT name FROM customers WHERE country = 'India' -- filter first, smaller set AND id IN ( SELECT customer_id FROM orders WHERE order_date >= '2024-01-01' -- filter inside subquery too );
Performance Decision Tree: Need existence check? → Use EXISTS (not IN) — short-circuits, faster for large tables Correlated subquery in SELECT or WHERE with large outer table? → Replace with LEFT JOIN + GROUP BY or window function Using NOT IN? → Switch to NOT EXISTS — immune to NULL problems Deep nested subquery (3+ levels)? → Rewrite as CTE — same performance, readable Query feels slow? → Run EXPLAIN ANALYZE — find SubPlan nodes, Seq Scans
Anti-PatternProblemFix
Correlated subquery in SELECTRuns N times for N rowsLEFT JOIN + GROUP BY
NOT IN with nullable columnReturns zero rows if any NULLNOT EXISTS or LEFT JOIN IS NULL
IN with huge result setLarge memory for listEXISTS or JOIN
3+ level nested subqueriesUnreadable, hard to debugCTE (WITH clause)
= on multi-row subqueryRuntime errorUse IN or ANY instead
✅ Golden rules: Avoid correlated subqueries on large tables. Never use NOT IN without NULL check. Use EXISTS for large sets. Deep nesting → CTE. Always EXPLAIN ANALYZE when something is slow.
