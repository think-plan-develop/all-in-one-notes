Part 2 — Triggers

Automatic actions that fire on INSERT, UPDATE, or DELETE. Runs a function before or after the event — or instead of it.

4 What is a Trigger? & Why do we use Triggers?

A trigger is a database object that automatically fires a function when a specified event (INSERT, UPDATE, DELETE) happens on a table. You don't call a trigger — the database calls it.

✅ One-liner A trigger is an automatic event listener on a table. When data changes, the trigger fires and runs your function — before you can forget to call it.

Why use triggers?

Auto-record who changed what and when — without touching app code.

2

Set updated_at = NOW() on every UPDATE automatically.

3

Reject invalid data at DB level — enforce rules no ORM can bypass.

4

Auto-update a total or item_count when child rows change.

5
Enforcing business rules

Prevent delete of a paid order. Block status rollback. Enforce at DB level, not just app level.

🎯 Interview answer "A trigger is a database mechanism that automatically executes a function in response to a data change event (INSERT, UPDATE, DELETE) on a table. They are used for audit trails, auto-timestamps, data validation, and enforcing business rules at the database layer — guaranteeing the logic runs regardless of which application or user modifies the data."
⚠️ Key rule Triggers are invisible to applications. The app inserts a row, the trigger fires silently. This is a double-edged sword — great for guarantees, dangerous when the trigger causes unexpected side effects.
5 Trigger Types — BEFORE · AFTER · INSTEAD OF · INSERT / UPDATE / DELETE
⏮️ BEFORE Trigger
Fires before the row is written. Can modify NEW (change values) or cancel the operation (RETURN NULL).

Use for: validation, auto-fill fields, coerce data format.

RETURN NEW → allow with (possibly modified) values
RETURN NULL → silently cancel the operation
⏭️ AFTER Trigger
Fires after the row is committed to the table. Cannot modify the row (row already written). Can read OLD and NEW.

Use for: audit logging, sending notifications, updating related tables.

RETURN NEW or RETURN NULL — makes no difference (row already saved)
🔄 INSTEAD OF Trigger
Fires instead of the operation. Used only on views — makes an otherwise non-updatable view accept INSERT/UPDATE/DELETE by redirecting the operation to the base tables.

Use for: making complex views updatable.

Event types — what triggers fire on

📥 INSERT Trigger
Fires when a row is inserted.

NEW = the row being inserted
OLD = NULL (nothing existed before)

Use: auto-fill created_at, generate slugs, send welcome email trigger.
✏️ UPDATE Trigger
Fires when a row is updated.

NEW = row with new values
OLD = row with old values

Use: auto-set updated_at, audit log what changed, prevent certain field changes.
🗑️ DELETE Trigger
Fires when a row is deleted.

NEW = NULL (nothing coming in)
OLD = the row being deleted

Use: soft-delete instead of hard delete, cascade custom logic, audit deleted rows.

6 How to Create a Trigger — Trigger Function + CREATE TRIGGER
📌 Two-step process In PostgreSQL, creating a trigger is always two steps:
Step 1 — Create a trigger function that returns TRIGGER
Step 2 — Create the trigger that binds the function to a table and event

Step 1 — Trigger Function

trigger_function.sql
PostgreSQL
-- A trigger function MUST:
-- 1. Take NO parameters (gets NEW/OLD automatically)
-- 2. Return TRIGGER type
-- 3. Use LANGUAGE plpgsql

CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at := NOW();   -- modify the new row before saving
  RETURN NEW;                 -- MUST return NEW (or NULL to cancel)
END;
$$;


-- Audit log trigger function
CREATE OR REPLACE FUNCTION log_user_changes()
RETURNS TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO audit_log (
    table_name, action, old_data, new_data, changed_at, changed_by
  ) VALUES (
    TG_TABLE_NAME,               -- auto-variable: which table
    TG_OP,                       -- auto-variable: INSERT/UPDATE/DELETE
    row_to_json(OLD),            -- old row as JSON
    row_to_json(NEW),            -- new row as JSON
    NOW(),
    current_user
  );
  RETURN NEW;
END;
$$;

Step 2 — CREATE TRIGGER

create_trigger.sql
PostgreSQL
-- Syntax
CREATE TRIGGER trigger_name
  { BEFORE | AFTER | INSTEAD OF }
  { INSERT | UPDATE | DELETE | TRUNCATE } [OR ...]
  ON table_name
  [FOR EACH ROW | FOR EACH STATEMENT]
  [WHEN (condition)]
  EXECUTE FUNCTION function_name();


-- ✅ Auto-set updated_at on every UPDATE
CREATE TRIGGER trg_users_updated_at
  BEFORE UPDATE ON users
  FOR EACH ROW
  EXECUTE FUNCTION set_updated_at();


-- ✅ Audit log on INSERT, UPDATE, DELETE
CREATE TRIGGER trg_users_audit
  AFTER INSERT OR UPDATE OR DELETE ON users
  FOR EACH ROW
  EXECUTE FUNCTION log_user_changes();


-- ✅ WHEN condition — only fire if email changed
CREATE TRIGGER trg_email_change
  AFTER UPDATE ON users
  FOR EACH ROW
  WHEN (OLD.email IS DISTINCT FROM NEW.email)
  EXECUTE FUNCTION notify_email_change();


-- Manage triggers
ALTER TABLE  users DISABLE TRIGGER trg_users_audit;   -- pause
ALTER TABLE  users ENABLE  TRIGGER trg_users_audit;   -- resume
DROP TRIGGER IF EXISTS trg_users_audit ON users;       -- delete

-- List all triggers on a table
SELECT trigger_name, event_manipulation, action_timing, action_orientation
FROM   information_schema.triggers
WHERE  event_object_table = 'users';
7 How Triggers Work — NEW · OLD · FOR EACH ROW · FOR EACH STATEMENT

NEW and OLD records

🟢 NEW — the incoming row
  • ✅ Available in INSERT triggers (the row being inserted)
  • ✅ Available in UPDATE triggers (row with new values)
  • ❌ NULL in DELETE triggers (nothing coming in)
  • 💡 BEFORE trigger: you can modify NEW before saving
  • NEW.column_name to read/write any field
  • RETURN NEW → save the row (with your modifications)
  • RETURN NULL → cancel the operation (BEFORE only)
🟠 OLD — the existing row
  • ✅ Available in UPDATE triggers (row before change)
  • ✅ Available in DELETE triggers (row being deleted)
  • ❌ NULL in INSERT triggers (nothing existed before)
  • 💡 Read-only — you can't modify OLD
  • OLD.column_name to read previous values
  • Used for: audit logging, detecting what changed
  • OLD.email IS DISTINCT FROM NEW.email → email changed?
new_old_examples.sql
PostgreSQL
-- Using NEW to auto-fill fields (BEFORE INSERT)
CREATE OR REPLACE FUNCTION before_insert_user()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  NEW.email      := LOWER(NEW.email);   -- normalize email case
  NEW.created_at := NOW();              -- auto-fill timestamp
  NEW.slug       := LOWER(REPLACE(NEW.name, ' ', '-'));
  RETURN NEW;    -- return modified row — this is what gets saved
END; $$;


-- Using OLD and NEW to detect changes (AFTER UPDATE)
CREATE OR REPLACE FUNCTION after_update_status()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  IF OLD.status != NEW.status THEN
    INSERT INTO status_history(order_id, from_status, to_status, changed_at)
    VALUES (NEW.id, OLD.status, NEW.status, NOW());
  END IF;
  RETURN NEW;
END; $$;


-- Using OLD in DELETE to save deleted row
CREATE OR REPLACE FUNCTION before_delete_order()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  -- Block delete of paid orders
  IF OLD.status = 'paid' THEN
    RAISE EXCEPTION 'Cannot delete a paid order (id=%)', OLD.id;
  END IF;
  RETURN OLD;   -- for DELETE trigger, return OLD (not NEW)
END; $$;


-- Special trigger variables (auto-available in every trigger fn)
-- TG_OP          → 'INSERT' | 'UPDATE' | 'DELETE' | 'TRUNCATE'
-- TG_TABLE_NAME  → name of the table that fired the trigger
-- TG_WHEN        → 'BEFORE' | 'AFTER' | 'INSTEAD OF'
-- TG_LEVEL       → 'ROW' | 'STATEMENT'
-- TG_NARGS       → number of arguments passed to trigger
-- TG_ARGV[0]     → first argument passed (if any)

FOR EACH ROW vs FOR EACH STATEMENT

📍 FOR EACH ROW
Fires once per affected row. If you UPDATE 500 rows, the trigger fires 500 times.

✅ Has access to NEW and OLD for that specific row
✅ Can modify individual rows (BEFORE only)
⚠️ Performance: 500 UPDATEs = 500 trigger calls

Use for: per-row logging, per-row validation, auto-fill fields
📦 FOR EACH STATEMENT
Fires once per SQL statement, regardless of how many rows were affected. UPDATE of 500 rows = 1 trigger call.

❌ NO access to NEW or OLD (statement level)
✅ Much faster for bulk operations
✅ For invalidating a cache, sending one notification

Use for: bulk operation side effects, cache invalidation
for_each.sql
PostgreSQL
-- FOR EACH ROW — fires per row (has NEW/OLD)
CREATE TRIGGER trg_row_level
  AFTER UPDATE ON orders
  FOR EACH ROW                    -- ← fires once per updated row
  EXECUTE FUNCTION log_order_change();

-- FOR EACH STATEMENT — fires once per query (no NEW/OLD)
CREATE TRIGGER trg_stmt_level
  AFTER UPDATE ON orders
  FOR EACH STATEMENT              -- ← fires once regardless of rows affected
  EXECUTE FUNCTION invalidate_order_cache();

-- Practical difference:
UPDATE orders SET status = 'shipped' WHERE created_at < '2024-01-01';
-- affects 50,000 rows
-- FOR EACH ROW     → trigger fires 50,000 times ← potentially slow!
-- FOR EACH STATEMENT → trigger fires 1 time    ← fast

══════════════════════════════════════════════════
  USE CASE 2: Full audit log
══════════════════════════════════════════════════
CREATE TABLE audit_log (
  id         SERIAL PRIMARY KEY,
  table_name TEXT,
  action     TEXT,
  old_data   JSONB,
  new_data   JSONB,
  changed_at TIMESTAMPTZ DEFAULT NOW(),
  changed_by TEXT DEFAULT current_user
);

CREATE OR REPLACE FUNCTION audit_trigger_fn()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO audit_log(table_name, action, old_data, new_data)
  VALUES (
    TG_TABLE_NAME, TG_OP,
    CASE WHEN TG_OP = 'INSERT' THEN NULL ELSE row_to_json(OLD)::JSONB END,
    CASE WHEN TG_OP = 'DELETE' THEN NULL ELSE row_to_json(NEW)::JSONB END
  );
  RETURN COALESCE(NEW, OLD);
END; $$;

CREATE TRIGGER trg_users_audit
  AFTER INSERT OR UPDATE OR DELETE ON users
  FOR EACH ROW
  EXECUTE FUNCTION audit_trigger_fn();


══════════════════════════════════════════════════
  USE CASE 3: Validation — block invalid state
══════════════════════════════════════════════════
CREATE OR REPLACE FUNCTION validate_order_status()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  -- Prevent rolling back from 'paid' to 'pending'
  IF OLD.status = 'paid' AND NEW.status = 'pending' THEN
    RAISE EXCEPTION 'Cannot revert a paid order to pending';
  END IF;
  -- Block delete of paid orders
  IF TG_OP = 'DELETE' AND OLD.status = 'paid' THEN
    RAISE EXCEPTION 'Cannot delete paid order id=%', OLD.id;
  END IF;
  RETURN COALESCE(NEW, OLD);
END; $$;

CREATE TRIGGER trg_order_validation
  BEFORE UPDATE OR DELETE ON orders
  FOR EACH ROW
  EXECUTE FUNCTION validate_order_status();


══════════════════════════════════════════════════
  USE CASE 4: Soft delete — INSTEAD OF delete
══════════════════════════════════════════════════
CREATE OR REPLACE FUNCTION soft_delete_user()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  UPDATE users
  SET    deleted_at = NOW(), active = FALSE
  WHERE  id = OLD.id;
  RETURN OLD;   -- must return OLD for DELETE triggers
END; $$;

CREATE TRIGGER trg_soft_delete
  BEFORE DELETE ON users
  FOR EACH ROW
  EXECUTE FUNCTION soft_delete_user();
9 Advantages & Disadvantages of Triggers

✅ Advantages

  • 🔒
    Guaranteed execution — fires for every INSERT/UPDATE/DELETE, regardless of which app, ORM, or user makes the change. Cannot be bypassed.
  • 📋
    Automatic audit logging — track every data change with who, what, when — without touching a single line of app code.
  • ⏱️
    Auto-timestamps — updated_at is always accurate, even for manual SQL updates or data migrations.
  • 🛡️
    Data integrity at DB level — enforce business rules that survive ORM changes, API changes, and developer mistakes.
  • ♻️
    Reusable logic — one trigger function can be shared across multiple tables (e.g., set_updated_at on all tables).
  • 🔌
    Decoupled — app doesn't need to know about audit logging, timestamps, or cascades. DB handles it transparently.

❌ Disadvantages

  • 👻
    Hidden side effects — a simple INSERT triggers an audit log, a notification, and an update to another table. New developers can't see this from the app code.
  • 🐢
    Performance overhead — FOR EACH ROW on bulk operations (UPDATE 100k rows) = 100k trigger calls. Can turn a fast bulk update into a slow one.
  • 🐛
    Hard to debug — errors in triggers appear as errors in the DML statement, with confusing stack traces. Harder to test than application code.
  • 🔄
    Trigger cascades — a trigger updates Table B. Table B has a trigger that updates Table C. This chain is invisible and hard to trace.
  • 🧩
    Business logic in two places — some logic in app, some in DB triggers = split brain. Hard to reason about where rules live.
  • 📦
    Schema migration risk — triggers don't appear in ORM migration files. New team members clone the DB without the triggers and wonder why things break.

Summary — When to use

Use caseTrigger?Why
Auto updated_at on every UPDATE✅ YesCannot be forgotten, works for all callers
Audit log — who changed what✅ YesGuaranteed capture regardless of app layer
Validate business rules (block paid order delete)✅ YesDB-level enforcement cannot be bypassed
Soft delete✅ YesBEFORE DELETE converts to UPDATE cleanly
Sending emails on row insert❌ NoTriggers can't make HTTP calls — use app-layer events
Complex multi-step business logic⚠️ CarefulMove to application layer or stored procedures — triggers are hard to debug
Bulk UPDATE on millions of rows❌ No/CarefulFOR EACH ROW × 1M = serious performance problem
🧠 Golden rules Keep trigger functions short and fast. Do one thing. Never put complex business logic or external calls in triggers. Use triggers for: timestamps, audit logs, simple validation. Use application code for: emails, API calls, complex workflows. Always document your triggers — they're invisible to the app layer and will surprise future developers.
