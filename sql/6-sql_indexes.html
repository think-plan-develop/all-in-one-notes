📖 What is an Index?

An index is a separate data structure that the database maintains alongside a table. It stores a sorted copy of one or more columns and a pointer back to the original row — so the database can find rows without scanning the entire table.

✅ Real-world analogy A database table without an index is like a book with no table of contents. To find "normalization", you read every page. An index is the table of contents — jump straight to page 94.
🐢 Without index — Full Table Scan
SQL reads every single row from disk, one by one, and checks if it matches the WHERE clause.

SELECT * FROM users WHERE email = 'aman@x.com'

→ Scans 1,000,000 rows to find 1 match.
→ Time: O(n) — grows with table size.
→ Called Full Table Scan (Seq Scan in PostgreSQL).
⚡ With index — Index Seek
SQL jumps directly to the matching rows using the sorted index structure.

SELECT * FROM users WHERE email = 'aman@x.com'

→ Traverses ~20 B-Tree nodes to find 1 match.
→ Time: O(log n) — barely grows with table size.
→ Called Index Seek or Index Scan.
🧠 The tradeoff Indexes speed up reads (SELECT, WHERE, JOIN, ORDER BY) but slow down writes (INSERT, UPDATE, DELETE) because the index must be updated every time the table changes. Storage also increases. This tradeoff is the core of index design.
🌳 B-Tree Index — How it works internally

The B-Tree (Balanced Tree) is the default index type in PostgreSQL, MySQL, SQL Server, and Oracle. Understanding it explains why indexes work the way they do.

B-Tree Structure

A B-Tree has three levels: Root (1 node at top), Branch nodes (internal navigation nodes), and Leaf nodes (actual sorted data + row pointers). All leaf nodes are at the same depth — that's what "balanced" means.

Step-by-step search flow — WHERE id = 35

1
Start at Root Node
Root contains [25 | 50 | 75]. We're looking for 35. Since 25 < 35 < 50, go to the second branch (between 25 and 50). One comparison, one pointer jump.
2
Navigate Branch Node
Branch contains [30 | 40]. Since 30 < 35 < 40, go to the leaf between 30 and 40. Another single pointer jump.
3
Find in Leaf Node
Leaf contains [32→row#8, 35→row#16, 38→row#3]. Found 35 → row#16. The leaf holds a pointer directly to the physical row on disk.
4
Fetch row from disk
Use the row pointer (row#16) to jump directly to that row on disk. Return the full row. Total: 3 node reads instead of scanning 1,000,000 rows. This is O(log n).
📋 Why O(log n)? A B-Tree with 1 million rows has about 20 levels deep (log₂ 1,000,000 ≈ 20). That means at most 20 node reads to find any row. Compare that to reading 1,000,000 rows sequentially — indexes are not just faster, they're a fundamentally different complexity class.

Range scans — why leaf links matter

Leaf nodes are linked to each other in sorted order (like a doubly-linked list). This makes range queries like WHERE age BETWEEN 25 AND 35 very efficient — find the start point with a tree traversal, then walk the linked leaves left to right.

btree_queries.sql
-- All of these use B-Tree efficiently:

SELECT * FROM users WHERE id = 35;                    -- exact lookup  O(log n)
SELECT * FROM users WHERE age BETWEEN 25 AND 35;     -- range scan    O(log n + k)
SELECT * FROM users WHERE name LIKE 'Am%';           -- prefix scan   O(log n + k)
SELECT * FROM users ORDER BY created_at;              -- sorted output O(n) but index-ordered

-- These do NOT use B-Tree efficiently:
SELECT * FROM users WHERE name LIKE '%man';          -- leading wildcard → full scan
SELECT * FROM users WHERE UPPER(email) = 'A@X.COM';  -- function on column → full scan
SELECT * FROM users WHERE age != 25;                -- NOT EQUAL → usually full scan
🗂️ Index Types — All Explained
🌳 B-Tree Index Default
The default index. Stores sorted key values in a balanced tree. Supports =, <, >, BETWEEN, LIKE 'x%', ORDER BY.

CREATE INDEX idx_email ON users(email);

Works in: PostgreSQL, MySQL, SQL Server, Oracle. ✅ Production standard
🔑 Unique Index
B-Tree index that also enforces uniqueness. Auto-created when you add UNIQUE or PRIMARY KEY. Rejects duplicate values at write time.

CREATE UNIQUE INDEX idx_u_email ON users(email);

✅ Use for: emails, usernames, SSN, any unique identifier
📋 Composite Index (Multi-column)
Index on multiple columns. Order matters — index on (a, b) can answer queries on a alone or a AND b together, but NOT b alone.

CREATE INDEX idx_name_dept ON employees(dept_id, name);

✅ Use for: queries that filter on multiple columns together
⚙️ Partial Index
Index only a subset of rows matching a condition. Smaller and faster than full index. PostgreSQL and SQLite support it; MySQL does not.

CREATE INDEX idx_active ON users(email) WHERE active = true;

✅ Use for: soft-deletes, status filters, selective queries
🏎️ Covering Index
Index includes all columns the query needs, so the DB never has to touch the actual table rows ("index-only scan"). Include non-key columns with INCLUDE.

CREATE INDEX idx_cov ON orders(user_id) INCLUDE (total, created_at);

✅ Use for: high-frequency queries where every ms matters
🔍 Full-Text Index
Special index for searching text content — tokenises words, handles stemming, relevance ranking. For search boxes, article search, document search.

CREATE FULLTEXT INDEX idx_ft ON articles(body); (MySQL)

⚠️ Not a B-Tree — different structure, different rules
🗃️ Hash Index
Maps key → hash → row pointer. Only for exact equality (=). Cannot support range queries, ORDER BY, or LIKE at all. Faster than B-Tree for pure = lookups.

CREATE INDEX idx_hash ON users USING HASH (id); (PostgreSQL)

⚠️ Limited use. B-Tree is usually preferred even for =
🌐 GiST / GIN (PostgreSQL)
Specialized indexes for complex data types: GiST for geometric/spatial data, ranges, fuzzy search. GIN for array columns, JSONB, full-text.

CREATE INDEX idx_gin ON docs USING GIN(tags);

⚠️ PostgreSQL only. Use for arrays, JSONB, geospatial data
✅ When TO Use an Index
✅ Index these columns
  • 🔍
    WHERE clause columns — WHERE email = ?, WHERE status = 'active'. Any column used to filter rows.
  • 🔗
    JOIN columns (foreign keys) — orders.user_id joined to users.id. Without an index here, every JOIN is a full scan.
  • 📊
    ORDER BY columns — ORDER BY created_at DESC. B-Tree delivers pre-sorted results, skipping a sort step.
  • 🔢
    High-cardinality columns — columns with many unique values (email, user_id, UUID). Index is most selective here.
  • 🔎
    Prefix LIKE patterns — LIKE 'Am%'. B-Tree can seek the prefix. Not LIKE '%man'.
  • 📅
    Range query columns — BETWEEN, >, < on dates, ages, prices.
  • 🏆
    Primary key & unique constraints — automatically indexed. Always fast.
🚫 Don't index these
  • 🎨
    Low-cardinality columns — gender (M/F), boolean flags, status (3 values). Index barely helps — DB may ignore it.
  • 📝
    Rarely queried columns — if a column only appears in one slow monthly report, the write-time overhead isn't worth it.
  • 🐣
    Small tables (<1000 rows) — full table scan is faster than B-Tree traversal overhead for tiny tables.
  • ✏️
    Frequently updated columns — every UPDATE rebuilds the index entry. Heavy-write columns with indexes hurt write throughput.
  • 🧪
    Columns only used with functions — WHERE UPPER(name) = 'AMAN' skips the index. Function-based index needed instead.
  • 🗑️
    Columns in bulk-load tables — drop indexes before batch inserts of millions of rows, rebuild after. Massive speed improvement.
when_to_index.sql
-- ✅ GOOD indexes — high value, commonly needed

-- 1. Email login — equality lookup on unique high-cardinality column
CREATE UNIQUE INDEX idx_users_email ON users(email);

-- 2. FK on orders — every JOIN benefits
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- 3. Date range filtering — dashboard "last 30 days"
CREATE INDEX idx_orders_created ON orders(created_at);

-- 4. Multi-column — filter by dept THEN sort by name
CREATE INDEX idx_emp_dept_name ON employees(dept_id, name);

-- 5. Partial — only index active users (skip deleted/inactive)
CREATE INDEX idx_active_users ON users(email) WHERE active = TRUE;

-- 6. Covering — query needs user_id + total — no table fetch needed
CREATE INDEX idx_orders_cover ON orders(user_id) INCLUDE (total);
🚫 When NOT to Use an Index — & How Indexes Get Skipped

Indexes can be silently ignored by the query planner even when they exist. These are the most common reasons your index isn't being used:

index_killers.sql
-- ❌ 1. FUNCTION wrapping the column — index is useless
SELECT * FROM users WHERE UPPER(email) = 'AMAN@X.COM';   -- full scan
SELECT * FROM users WHERE YEAR(created_at) = 2024;       -- full scan
-- Fix: store the computed value, or use a function-based index
SELECT * FROM users WHERE email = LOWER('AMAN@X.COM');   -- ✅ function on VALUE, not column

-- ❌ 2. Leading wildcard — B-Tree can't seek from the middle
SELECT * FROM users WHERE name LIKE '%man';              -- full scan
SELECT * FROM users WHERE name LIKE '%am%';             -- full scan
-- Fix: use Full-Text search, or reverse-index trick
SELECT * FROM users WHERE name LIKE 'Am%';              -- ✅ prefix = B-Tree works

-- ❌ 3. OR across different columns — planner often skips index
SELECT * FROM users WHERE email = 'a@x.com' OR name = 'Aman';
-- Fix: UNION instead of OR
SELECT * FROM users WHERE email = 'a@x.com'
UNION
SELECT * FROM users WHERE name  = 'Aman';                -- ✅ each half uses its index

-- ❌ 4. Implicit type conversion
SELECT * FROM users WHERE id = '123';                    -- id is INT, '123' is string
-- DB casts every row's id to string → full scan
-- Fix: match types
SELECT * FROM users WHERE id = 123;                      -- ✅ integer literal

-- ❌ 5. NOT / != / NOT IN — usually forces full scan
SELECT * FROM orders WHERE status != 'cancelled';        -- full scan
-- Fix: rewrite as positive equality or partial index
SELECT * FROM orders WHERE status IN ('pending', 'paid');  -- ✅ better

-- ❌ 6. Skipping leading column of composite index
CREATE INDEX idx ON employees(dept_id, name);              -- composite index
SELECT * FROM employees WHERE name = 'Aman';             -- ❌ skips dept_id → full scan
SELECT * FROM employees WHERE dept_id = 10;              -- ✅ uses index (leading col)
SELECT * FROM employees WHERE dept_id = 10 AND name = 'A'; -- ✅ uses both cols
⚠️ Too many indexes Every index on a table must be updated on every INSERT, UPDATE, DELETE. A table with 12 indexes on it will have write performance 12× worse than a table with 1 index. Don't index "just in case" — profile first, index second.

🛠️ How to Create, Check & Drop Indexes
index_management.sql
── CREATE ───────────────────────────────────────────────────

-- Basic B-Tree
CREATE INDEX idx_users_email ON users(email);

-- Unique
CREATE UNIQUE INDEX idx_users_email ON users(email);

-- Composite (dept first — more selective)
CREATE INDEX idx_emp_dept_name ON employees(dept_id, name);

-- Partial (PostgreSQL / SQLite)
CREATE INDEX idx_active_email ON users(email) WHERE active = TRUE;

-- Covering (PostgreSQL)
CREATE INDEX idx_orders_cov ON orders(user_id) INCLUDE (total, created_at);

-- Concurrent (PostgreSQL) — doesn't lock table during build
CREATE INDEX CONCURRENTLY idx_big_table ON big_table(col);

── CHECK EXPLAIN ────────────────────────────────────────────

-- PostgreSQL — see if index is being used
EXPLAIN ANALYZE
SELECT * FROM users WHERE email = 'aman@x.com';
-- Look for: "Index Scan" or "Index Only Scan" (good)
--           "Seq Scan" (bad — no index used)

-- MySQL
EXPLAIN SELECT * FROM users WHERE email = 'aman@x.com';
-- Look at 'key' column — shows which index was used
-- Look at 'rows' column — lower is better

── LIST INDEXES ─────────────────────────────────────────────

-- PostgreSQL
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'users';

-- MySQL
SHOW INDEX FROM users;

── DROP ─────────────────────────────────────────────────────

DROP INDEX idx_users_email;                         -- PostgreSQL
DROP INDEX idx_users_email ON users;               -- MySQL
DROP INDEX IF EXISTS idx_users_email;               -- safe drop
❌ How NOT to Use Indexes — Common Mistakes
❌ Over-indexing every column
CREATE INDEX ON users(name);
CREATE INDEX ON users(age);
CREATE INDEX ON users(city);
CREATE INDEX ON users(gender);
CREATE INDEX ON users(created_at);
CREATE INDEX ON users(last_login);

Every insert/update now rebuilds 6+ indexes. Write performance collapses. Index bloat wastes storage. The query planner gets confused choosing between overlapping indexes.
❌ Wrong column order in composite
-- Wrong: name first (low cardinality per dept)
CREATE INDEX ON emp(name, dept_id);

-- Right: dept_id first (narrows down quickly)
CREATE INDEX ON emp(dept_id, name);

Rule: put the most selective column (highest cardinality) first. Then sort column. The left-prefix rule means column order matters enormously.
❌ Indexing before you measure
Adding indexes "just in case" on all columns you think might be queried. You end up with 15 indexes that slow every write, and only 3 are ever used.

Correct flow:
1. Identify slow queries with EXPLAIN ANALYZE
2. Confirm it's a Seq Scan that should be an Index Scan
3. Add the targeted index
4. Re-run EXPLAIN to confirm it's used
❌ Forgetting to index foreign keys
-- orders.user_id references users.id
-- But no index on orders.user_id!

Every JOIN users ON orders.user_id = users.id becomes a full scan of orders. This is the most common missed index in real apps.

Rule: Every foreign key column should have an index. Always.
🎯 Interview pattern "How do you know when to add an index?" → Profile first. Use EXPLAIN ANALYZE to find Seq Scans on large tables with WHERE or JOIN conditions. Add a targeted index. Verify it switches to Index Scan. Never add indexes speculatively.

✅ DO

1
Index foreign key columns

Every FK should have an index. JOINs depend on it.

2
Index WHERE and ORDER BY columns

Most read queries benefit from these.

3
Use EXPLAIN ANALYZE before adding

Confirm the query does a Seq Scan first.

4
Put high-cardinality col first in composite

Left-prefix rule: most selective column leads.

5
Drop indexes before bulk inserts

Rebuild after loading. 10× faster bulk load.

🚫 DON'T

1
Don't wrap indexed columns in functions

UPPER(col), YEAR(col), LENGTH(col) kill the index.

2
Don't index low-cardinality columns alone

Boolean, gender, 3-value status — barely selective.

3
Don't create duplicate or redundant indexes

Index on (a) + index on (a, b) = (a) is redundant.

4
Don't use leading wildcard LIKE '%x'

B-Tree can't seek from the middle of a string.

5
Don't index everything speculatively

Measure first. Every unused index costs write time.

🧠 Golden Rule Indexes are not free. Every index costs storage, slows writes, and must be maintained. The right strategy: normalize your schema → identify slow queries → add targeted indexes → verify with EXPLAIN → done. Never guess.
