Part 1 — Functions

Reusable SQL logic stored in the database. Called on demand, return a value or a table, and encapsulate business rules.

1 What is a Function? & Why do we use them?
A function is a method saved inside PostgreSQL. You write the logic once and call it anywhere — in SELECT, WHERE, triggers, or other functions.

Q: What is a function in PostgreSQL?

A: A function is a named, reusable block of SQL or PL/pgSQL logic stored in the database. You call it by name, pass optional parameters, and it returns a value — a scalar, a set of rows, or nothing.

🧠 Analogy: A function is like a saved recipe card. You write the steps once; every cook (query) just says the recipe's name and the ingredients (parameters), and gets the dish (result) back. Fix the recipe once and every cook benefits.

Why use functions?

1

Reusability

Write once, use in queries, triggers and other functions. Change it once — all callers benefit.

2

Encapsulate business logic

Tax, discount rules, age computation — lives in the DB, not scattered across apps.

3

Security

Grant EXECUTE on a function instead of SELECT on tables. Users call it without seeing the tables.

4

Fewer network round-trips

Run complex multi-step logic in one DB call instead of many back-and-forth queries from the app.

5

Powers triggers

Every trigger calls a trigger function. Functions are the engine behind trigger logic.

6

Consistency

Every app, report and script uses the same rule, so results never drift between teams.

-- Without a function: the rule is repeated everywhere
SELECT name, (price * 1.18) AS price_with_gst
FROM products;

-- With a function: the logic lives in one place
CREATE OR REPLACE FUNCTION add_gst(price NUMERIC)
RETURNS NUMERIC AS $$
  SELECT price * 1.18;
$$ LANGUAGE sql;

SELECT name, add_gst(price) AS price_with_gst
FROM products;

-- Change the GST rate once — all queries update

2 CREATE FUNCTION — Syntax, Parameters, Return Types, Calling

Full anatomy of a function

CREATE OR REPLACE FUNCTION function_name (
  param1  data_type,             -- IN param (default)
  param2  data_type DEFAULT 0    -- optional param with a default
)
RETURNS return_type              -- NUMERIC, TEXT, TABLE(...), VOID, SETOF ...
LANGUAGE plpgsql                 -- sql | plpgsql (python / javascript need extensions)
SECURITY INVOKER                 -- run as caller (DEFINER = run as owner)
STABLE                           -- VOLATILE | STABLE | IMMUTABLE
AS $$
DECLARE
  var1 NUMERIC;                  -- local variables
BEGIN
  -- logic
  RETURN var1;
END;
$$;

Parameters — IN, OUT, INOUT, DEFAULT

-- IN param (default) — input only
CREATE OR REPLACE FUNCTION square(n NUMERIC)
RETURNS NUMERIC LANGUAGE sql AS $$
  SELECT n * n;
$$;
SELECT square(5);  -- 25

-- DEFAULT param — optional
CREATE OR REPLACE FUNCTION greet(name TEXT, greeting TEXT DEFAULT 'Hello')
RETURNS TEXT LANGUAGE sql AS $$
  SELECT greeting || ', ' || name || '!';
$$;
SELECT greet('Aman');              -- 'Hello, Aman!'
SELECT greet('Aman', 'Namaste');   -- 'Namaste, Aman!'

-- OUT params — multiple return values without a composite type
-- (with OUT params, RETURNS is not written)
CREATE OR REPLACE FUNCTION min_max(
  arr NUMERIC[],
  OUT minimum NUMERIC,
  OUT maximum NUMERIC
) LANGUAGE sql AS $$
  SELECT MIN(x), MAX(x) FROM unnest(arr) x;
$$;
SELECT * FROM min_max(ARRAY[3,1,7,2]::NUMERIC[]);  -- minimum=1, maximum=7

Calling functions

-- In SELECT
SELECT add_gst(price) FROM products;
SELECT UPPER(name), square(age) FROM users;

-- In WHERE
SELECT * FROM products WHERE add_gst(price) < 1000;

-- Standalone call (VOID or table-returning functions)
SELECT my_void_function();
SELECT * FROM get_active_users();

-- Named parameter style
SELECT greet(name => 'Aman', greeting => 'Hey');

-- Drop a function
DROP FUNCTION IF EXISTS square(NUMERIC);
DROP FUNCTION IF EXISTS greet(TEXT, TEXT);  -- must give param types if overloaded
⚠️ Overloading: PostgreSQL identifies a function by name + argument types. CREATE OR REPLACE with different parameter types creates a second function instead of replacing — and DROP FUNCTION name alone fails when it's ambiguous.
💡 Wrapping a column in a function inside WHERE (like add_gst(price) < 1000) stops a normal index on price from being used. Compare against the raw column when you can, or build an expression index (see Topic 4).
3 Function Types — Scalar, Table-Returning, Void, PL/pgSQL

🔢 Scalar Function — returns one value

Returns a single value of any type. Used in SELECT, WHERE and expressions. The most common type.

CREATE OR REPLACE FUNCTION
  full_name(first TEXT, last TEXT)
RETURNS TEXT
LANGUAGE sql IMMUTABLE AS $$
  SELECT first || ' ' || last;
$$;

SELECT full_name('Aman', 'Sharma');
-- → 'Aman Sharma'

CREATE OR REPLACE FUNCTION
  age_in_years(dob DATE)
RETURNS INT
LANGUAGE sql STABLE AS $$
  SELECT DATE_PART('year',
    AGE(CURRENT_DATE, dob))::INT;
$$;

📋 Table-Returning — returns rows

Returns a result set. Used with SELECT * FROM fn(). Two styles: RETURNS TABLE or RETURNS SETOF.

-- RETURNS TABLE style
CREATE OR REPLACE FUNCTION
  get_user_orders(uid INT)
RETURNS TABLE(
  order_id INT,
  total    NUMERIC,
  status   TEXT
)
LANGUAGE sql AS $$
  SELECT id, total, status
  FROM   orders
  WHERE  user_id = uid;
$$;

SELECT * FROM get_user_orders(42);
-- Returns multiple rows like a table

🔇 Void Function — returns nothing

Performs an action (INSERT, UPDATE, logging) and returns nothing. Like a "procedure" in other languages.

CREATE OR REPLACE FUNCTION
  archive_old_orders(days INT)
RETURNS VOID
LANGUAGE plpgsql AS $$
BEGIN
  -- move rows atomically: delete + insert in one statement
  WITH moved AS (
    DELETE FROM orders
    WHERE created_at < NOW() - make_interval(days => days)
    RETURNING *
  )
  INSERT INTO orders_archive SELECT * FROM moved;
END;
$$;

SELECT archive_old_orders(90);

🧩 PL/pgSQL Function — multi-step logic

Full procedural language with variables, IF/ELSE, loops and exception handling. Needed for logic beyond one SQL statement.

CREATE OR REPLACE FUNCTION
  classify_order(amount NUMERIC)
RETURNS TEXT
LANGUAGE plpgsql IMMUTABLE AS $$
DECLARE
  category TEXT;
BEGIN
  IF    amount >= 10000 THEN category := 'Premium';
  ELSIF amount >= 1000  THEN category := 'Standard';
  ELSE                       category := 'Small';
  END IF;
  RETURN category;
END;
$$;

4 Volatility, Security & Best Practices

Q: What is the difference between VOLATILE, STABLE and IMMUTABLE?

A: They tell the planner how much it may trust the result. IMMUTABLE always gives the same output for the same input, so it can be pre-evaluated and used in indexes. STABLE is constant within a single query. VOLATILE (default) can change at any call, so it is re-run every time.

CategoryExampleCan the planner cache it?
IMMUTABLEsquare(n), full_name()Yes — pre-evaluated, allowed in expression indexes
STABLEage_in_years() (uses today's date)Once per query only
VOLATILEarchive_old_orders(), anything calling random()Never — runs on every call
-- Expression index: the function MUST be IMMUTABLE
CREATE INDEX idx_users_full_name
  ON users (full_name(first_name, last_name));

-- SECURITY DEFINER: always pin the search_path
CREATE OR REPLACE FUNCTION get_salary(emp_id INT)
RETURNS NUMERIC
LANGUAGE sql STABLE
SECURITY DEFINER
SET search_path = public, pg_temp
AS $$
  SELECT salary FROM employees WHERE id = emp_id;
$$;

-- Lock it down: only the app role may call it
REVOKE EXECUTE ON FUNCTION get_salary(INT) FROM PUBLIC;
GRANT  EXECUTE ON FUNCTION get_salary(INT) TO app_user;
⚠️ Never label a function IMMUTABLE if it reads tables or depends on the date/time. PostgreSQL trusts the label: an index or cached value built on a wrong IMMUTABLE function silently returns stale or wrong results.
⚠️ SECURITY DEFINER without SET search_path lets a caller plant a same-named object in their own schema and hijack the function while it runs with the owner's rights. Always pin search_path, and revoke EXECUTE from PUBLIC.
📌 Simple LANGUAGE sql functions can be inlined by the planner into the calling query, so they often cost nothing extra. PL/pgSQL functions are a black box to the planner — prefer plain SQL when a single statement is enough.
✅ Golden rules: Use sql for one statement, plpgsql for logic. Mark volatility honestly. Pin search_path on SECURITY DEFINER. Don't wrap indexed columns in functions inside WHERE.
