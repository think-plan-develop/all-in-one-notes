1 What is a View? ⭐⭐⭐⭐⭐

A View is a named, saved SQL query stored in the database. When you query a view, PostgreSQL runs the underlying query on the fly and returns the result — as if it were a real table.

✅ One-line definition A view is a virtual table — it has no data of its own. It's just a saved SELECT statement with a name. Every time you query it, the SELECT runs against the real tables.

How it works

Base Tablesusers, orders
→
VIEWsaved SELECT query
→
Application / Userqueries the view like a table
📋 Mental model Think of a view like a camera pointing at the tables. The camera doesn't store the photo — it just shows you what the tables look like through a specific lens (your SELECT) at the moment you look.
what_is_view.sql
PostgreSQL
-- Base tables exist with real data
-- users(id, name, email, active)
-- orders(id, user_id, total, status, created_at)

-- Create a view = save a SELECT with a name
CREATE VIEW active_users AS
SELECT id, name, email
FROM   users
WHERE  active = TRUE;

-- Query the view exactly like a table
SELECT * FROM active_users;
SELECT * FROM active_users WHERE name LIKE 'A%';

-- PostgreSQL internally expands this to:
SELECT id, name, email
FROM   users
WHERE  active = TRUE
  AND  name LIKE 'A%';
-- The view is substituted inline — NOT run as a separate query first
🎯 Interview answer "A view is a named stored SELECT query. It behaves like a virtual table — you can SELECT from it, JOIN it, and filter it. It stores no data itself; every access re-runs the underlying query against the base tables."
2 Why Do We Use Views? ⭐⭐⭐⭐⭐
1
Simplify complex queries

Wrap a 50-line JOIN + GROUP BY into a simple name. App devs query SELECT * FROM monthly_revenue instead of writing the full aggregation every time.

2
Security — hide sensitive columns

Expose only allowed columns to a role. Grant SELECT on public_users view (no password/SSN) instead of the full users table.

3
Reusability — single source of truth

Business logic lives in one view. All apps and reports use the same definition. Change it once, all consumers benefit.

4
Abstraction — decouple app from schema

If you rename a column or restructure a table, update the view — the app doesn't change. Views act as a stable API over your tables.

5
Row-level security

A view can filter rows by the current user. WHERE tenant_id = current_setting('app.tenant_id') enforces multi-tenant isolation at the DB level.

why_views.sql
PostgreSQL
-- 1. SIMPLIFY — wrap complex JOIN
CREATE VIEW user_order_summary AS
SELECT
  u.id, u.name, u.email,
  COUNT(o.id)   AS total_orders,
  SUM(o.total)  AS lifetime_value
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name, u.email;

-- App now just writes:
SELECT * FROM user_order_summary
WHERE lifetime_value > 10000;


-- 2. SECURITY — hide password column
CREATE VIEW public_users AS
SELECT id, name, email, created_at
FROM   users;
-- password, ssn, internal_notes never visible

GRANT SELECT ON public_users TO readonly_role;


-- 5. ROW-LEVEL — each user sees own rows
CREATE VIEW my_orders AS
SELECT * FROM orders
WHERE user_id = current_setting('app.user_id')::INT;

4 View vs Materialized View ⭐⭐⭐⭐⭐
👁️ Regular View
  • No data stored — runs query live on every access
  • Always shows latest data (real-time)
  • Cannot be indexed directly
  • Performance = underlying query performance
  • No storage cost
  • No refresh needed
  • Good for: real-time data, simple logic
🗄️ Materialized View
  • Data IS physically stored (like a cached table)
  • Data can be stale — must manually REFRESH
  • Can be indexed — very fast reads
  • Performance = reading pre-computed rows (fast!)
  • Uses disk storage
  • Must REFRESH to update data
  • Good for: reports, dashboards, heavy aggregations
FeatureViewMaterialized View
Data stored?❌ No✅ Yes
Data freshnessAlways liveStale until REFRESH
SpeedDepends on queryFast (pre-computed)
Indexable?❌ No✅ Yes
Storage costNoneYes — disk space
Refresh needed?NeverYes — manually or scheduled
Best forReal-time, security, abstractionReports, dashboards, heavy aggregations
📋 When to pick which View → data must always be current (order status, user info, live filters)
Materialized View → data is expensive to compute and a few minutes of staleness is OK (monthly revenue, analytics dashboards, recommendation scores)
5 CREATE VIEW · CREATE OR REPLACE · ALTER VIEW · DROP VIEW ⭐⭐⭐⭐⭐
view_ddl.sql
PostgreSQL
──────────────────────────────────────────────────────────
  CREATE VIEW
──────────────────────────────────────────────────────────
CREATE VIEW active_users AS
SELECT id, name, email
FROM   users
WHERE  active = TRUE;

-- With column aliases in the view definition
CREATE VIEW order_totals (user_name, total_spent) AS
SELECT u.name, SUM(o.total)
FROM   users u
JOIN   orders o ON o.user_id = u.id
GROUP BY u.name;


──────────────────────────────────────────────────────────
  CREATE OR REPLACE VIEW — update without DROP
──────────────────────────────────────────────────────────
CREATE OR REPLACE VIEW active_users AS
SELECT id, name, email, created_at  -- added created_at
FROM   users
WHERE  active = TRUE;
-- ✅ Safe — existing GRANTs and dependent queries preserved
-- ⚠️ New columns can only be APPENDED (cannot remove or reorder existing ones)


──────────────────────────────────────────────────────────
  ALTER VIEW — rename or change owner / options
──────────────────────────────────────────────────────────
-- Rename a view
ALTER VIEW active_users RENAME TO live_users;

-- Change owner
ALTER VIEW active_users OWNER TO new_owner;

-- Rename a column in the view
ALTER VIEW active_users RENAME COLUMN email TO contact_email;

-- Set check option (prevents inserts/updates that would disappear from view)
ALTER VIEW active_users SET (check_option = local);


──────────────────────────────────────────────────────────
  DROP VIEW
──────────────────────────────────────────────────────────
DROP VIEW             active_users;           -- error if other views depend on it
DROP VIEW IF EXISTS   active_users;           -- safe drop
DROP VIEW             active_users CASCADE;  -- also drops dependent views!
DROP VIEW             active_users RESTRICT; -- default — refuses if dependencies exist


──────────────────────────────────────────────────────────
  INSPECT A VIEW DEFINITION
──────────────────────────────────────────────────────────
SELECT definition
FROM   pg_views
WHERE  viewname = 'active_users';

-- Or use psql shortcut:
\d+ active_users
⚠️ CREATE OR REPLACE rule You can only add columns at the end. You cannot remove columns, reorder them, or change their data types with OR REPLACE. To do that, you must DROP VIEW and CREATE VIEW again.
6 View with JOIN ⭐⭐⭐⭐⭐

Views are most valuable when they wrap complex multi-table JOINs. Instead of writing the same JOIN in 10 different queries, define it once in a view.

view_with_join.sql
PostgreSQL
-- Schema
-- users(id, name, email, dept_id)
-- orders(id, user_id, total, status, created_at)
-- departments(id, name)


── INNER JOIN VIEW ──────────────────────────────────────
CREATE VIEW orders_with_user AS
SELECT
  o.id         AS order_id,
  o.total,
  o.status,
  o.created_at,
  u.name       AS customer_name,
  u.email      AS customer_email
FROM   orders o
INNER JOIN users u ON u.id = o.user_id;

-- Use it:
SELECT * FROM orders_with_user WHERE status = 'pending';
SELECT * FROM orders_with_user WHERE customer_name = 'Aman';


── THREE-TABLE JOIN VIEW ────────────────────────────────
CREATE VIEW employee_details AS
SELECT
  e.id,
  e.name        AS employee,
  d.name        AS department,
  m.name        AS manager
FROM   employees e
INNER JOIN departments d  ON d.id  = e.dept_id
LEFT  JOIN employees   m  ON m.id  = e.manager_id;

-- Clean, simple access:
SELECT employee, department, manager
FROM   employee_details
WHERE  department = 'Engineering'
ORDER BY employee;


── JOIN A VIEW WITH ANOTHER TABLE ────────────────────────
SELECT v.customer_name, v.total, p.name AS product
FROM   orders_with_user v
JOIN   order_items oi ON oi.order_id = v.order_id
JOIN   products    p  ON p.id = oi.product_id
WHERE  v.status = 'paid';
💡 View on view You can build views on top of other views. Keep the chain shallow (max 2–3 levels) — deeply nested views make debugging and performance analysis very hard.
7 Aggregate Views — GROUP BY, COUNT, SUM, AVG ⭐⭐⭐⭐⭐

Aggregate views are one of the most common real-world uses — wrapping GROUP BY queries that would otherwise be repeated in every report or dashboard query.

aggregate_views.sql
PostgreSQL
── COUNT — total orders per user ───────────────────────
CREATE VIEW user_order_count AS
SELECT
  u.id,
  u.name,
  COUNT(o.id)                             AS total_orders,
  COUNT(o.id) FILTER (WHERE o.status = 'paid') AS paid_orders
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name;

SELECT * FROM user_order_count ORDER BY total_orders DESC;


── SUM + AVG — revenue stats ──────────────────────────
CREATE VIEW monthly_revenue AS
SELECT
  DATE_TRUNC('month', created_at)   AS month,
  COUNT(*)                           AS order_count,
  SUM(total)                         AS total_revenue,
  AVG(total)                         AS avg_order_value,
  MAX(total)                         AS largest_order,
  MIN(total)                         AS smallest_order
FROM   orders
WHERE  status = 'paid'
GROUP BY 1
ORDER BY 1 DESC;

-- Simple to query:
SELECT month, total_revenue
FROM   monthly_revenue
WHERE  month >= '2024-01-01';


── HAVING inside view — filter aggregated results ──────
CREATE VIEW high_value_customers AS
SELECT
  u.id,
  u.name,
  COUNT(o.id)  AS orders,
  SUM(o.total) AS lifetime_value
FROM   users u
JOIN   orders o ON o.user_id = u.id
GROUP BY u.id, u.name
HAVING   SUM(o.total) > 50000;       -- only customers > ₹50k

SELECT name, lifetime_value
FROM   high_value_customers
ORDER BY lifetime_value DESC;
⚠️ Aggregate views are NOT updatable Any view containing GROUP BY, COUNT, SUM, AVG, DISTINCT, HAVING, or UNION is read-only. You cannot INSERT, UPDATE, or DELETE through it.
8 Materialized View & REFRESH ⭐⭐⭐⭐⭐

A Materialized View physically stores the result of the SELECT query. It's like a cached snapshot of an expensive query. You must REFRESH it to pull in new data.

materialized_view.sql
PostgreSQL
──────────────────────────────────────────────────────────
  CREATE MATERIALIZED VIEW
──────────────────────────────────────────────────────────
CREATE MATERIALIZED VIEW monthly_revenue_mat AS
SELECT
  DATE_TRUNC('month', created_at)  AS month,
  COUNT(*)                          AS order_count,
  SUM(total)                        AS total_revenue,
  AVG(total)                        AS avg_order_value
FROM   orders
WHERE  status = 'paid'
GROUP BY 1
ORDER BY 1 DESC;


── ADD INDEX — this is the big advantage over regular views
CREATE INDEX idx_mat_month ON monthly_revenue_mat (month);
CREATE INDEX idx_mat_rev   ON monthly_revenue_mat (total_revenue DESC);


──────────────────────────────────────────────────────────
  REFRESH — update the stored data
──────────────────────────────────────────────────────────
-- Full refresh (locks the mat view during rebuild — readers blocked)
REFRESH MATERIALIZED VIEW monthly_revenue_mat;

-- CONCURRENTLY — no read lock (PostgreSQL 9.4+)
-- Requires a UNIQUE index on the mat view
CREATE UNIQUE INDEX idx_mat_month_uniq ON monthly_revenue_mat (month);
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_revenue_mat;
-- ✅ Readers can still query while refresh runs


──────────────────────────────────────────────────────────
  SCHEDULE REFRESH — using pg_cron extension
──────────────────────────────────────────────────────────
CREATE EXTENSION IF NOT EXISTS pg_cron;

-- Refresh every night at 2 AM
SELECT cron.schedule(
  'refresh-monthly-revenue',
  '0 2 * * *',
  $$REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_revenue_mat$$
);


──────────────────────────────────────────────────────────
  INSPECT / DROP
──────────────────────────────────────────────────────────
-- List materialized views
SELECT matviewname, definition, ispopulated
FROM   pg_matviews
WHERE  schemaname = 'public';

-- Check when it was last refreshed (via pg_stat_user_tables)
SELECT relname, last_autoanalyze, last_analyze
FROM   pg_stat_user_tables
WHERE  relname = 'monthly_revenue_mat';

DROP MATERIALIZED VIEW             monthly_revenue_mat;
DROP MATERIALIZED VIEW IF EXISTS   monthly_revenue_mat;
DROP MATERIALIZED VIEW             monthly_revenue_mat CASCADE;
📌 CONCURRENTLY requirement REFRESH CONCURRENTLY requires a UNIQUE index on the materialized view. Without it, PostgreSQL cannot detect which rows changed and falls back to a full relock. Always add a unique index on the natural key column before using concurrent refresh.
9 Performance — Do Views improve performance? Indexes? ⭐⭐⭐⭐⭐
❌ Regular View — NO performance gain
A regular view does not cache results. Every query against the view re-runs the full underlying SELECT. Performance is identical to writing the query inline.

You cannot add indexes to a regular view.

The only "performance" benefit is cleaner code — not faster execution. In fact, deeply nested views can make the query planner's job harder.
✅ Materialized View — REAL performance gain
Stores the pre-computed result. Reads hit the cached data, not the base tables.

You CAN add indexes on a materialized view — B-Tree, partial, composite, covering — all of them.

Result: a query that took 8 seconds (heavy GROUP BY over 50M rows) now takes 3ms because it reads from a pre-built indexed table.
view_performance.sql
PostgreSQL
── Regular view — check EXPLAIN (re-runs underlying query) ──
EXPLAIN ANALYZE
SELECT * FROM monthly_revenue WHERE month = '2024-01-01';
-- PostgreSQL inlines the view:  HashAggregate → Seq Scan on orders
-- Execution Time: 8420ms  ← full GROUP BY on 50M rows every time


── Materialized view — hits pre-built data ───────────────────
EXPLAIN ANALYZE
SELECT * FROM monthly_revenue_mat WHERE month = '2024-01-01';
-- Index Scan using idx_mat_month on monthly_revenue_mat
-- Execution Time: 0.3ms  ← indexed pre-computed row


── Can indexes on BASE TABLES help regular views? ──────────
-- YES — because the view's query runs against the base tables
-- If orders.created_at is indexed, the view query benefits from it

CREATE INDEX idx_orders_created ON orders(created_at);

EXPLAIN ANALYZE
SELECT * FROM monthly_revenue
WHERE  month >= '2024-01-01';
-- PostgreSQL can now use idx_orders_created to filter before grouping
-- Much faster than without the base table index


── VIEW query inlining — PostgreSQL is smart ───────────────
-- PostgreSQL does NOT run the view as a separate subquery first
-- It merges the view SQL with the outer query (view merging / inlining)
-- This means outer WHERE filters are pushed INTO the view query
-- and base table indexes are fully used

SELECT * FROM active_users WHERE name = 'Aman';
-- Executed as: SELECT id,name,email FROM users WHERE active=TRUE AND name='Aman'
-- Index on users.name is used!  ← view inlining at work
ScenarioRegular ViewMaterialized View
Simple filter (WHERE on indexed col)Fast — base index used via inliningFast — own index
Heavy GROUP BY on millions of rowsSlow — runs full aggregation every timeFast — pre-computed
Multi-table JOIN (indexed FKs)OK — depends on base indexesFast — result cached
Real-time data requirement✅ Always current❌ Stale until REFRESH
Dashboard / report (hourly refresh OK)Too slow for heavy queries✅ Ideal
10 Advantages & Disadvantages of Views ⭐⭐⭐⭐⭐

✅ Advantages

  • 🔒
    Security — expose only allowed columns/rows. Grant SELECT on a view instead of the whole table. Hide passwords, SSNs, internal fields.
  • ♻️
    Reusability — write complex JOIN once, use everywhere. 10 dashboards all read from one view definition.
  • 🧹
    Simplicity — application code stays clean. SELECT * FROM user_order_summary vs a 40-line query.
  • 🔌
    Abstraction — decouple app from schema. Rename a column in the view; app doesn't change. Views are a stable API.
  • 📐
    Consistency — business logic (active users, paid orders) defined once. No risk of 5 developers writing 5 slightly different definitions.
  • 🏠
    Row-level filtering — filter data per user/tenant at the DB level without touching application code.
  • 💾
    No extra storage (regular views) — zero disk cost. The view is just a stored SQL string.

❌ Disadvantages

  • 🐢
    No performance gain (regular view) — re-runs the query every time. A slow query in a view is still slow. Developers may not realize.
  • 🔐
    Limited updatability — views with JOINs, GROUP BY, DISTINCT, subqueries, or window functions are read-only. You can't INSERT/UPDATE through them.
  • 🕸️
    Nested view complexity — views built on views become impossible to debug. The query planner's output becomes unreadable. Performance is hard to predict.
  • 🔄
    Materialized view staleness — mat views need manual or scheduled REFRESH. Forgetting to refresh means stale data reaches users with no error.
  • 💾
    Materialized view storage cost — stores a full copy of the result. A mat view over 500M rows uses significant disk space + must be maintained on REFRESH.
  • 🔒
    Dependency trap — other views, functions, and apps depending on a view make it hard to alter. DROP VIEW CASCADE can silently destroy dependent objects.
  • 🧩
    Hidden complexity — a view named orders looks like a table but has completely different performance characteristics. New team members are often confused.

🧠 Golden rule Views = simplicity + security.  Materialized Views = performance.
Use regular views for abstraction and access control. Use materialized views when query time matters more than data freshness. Never use views to "fix" a missing index — fix the index instead.
