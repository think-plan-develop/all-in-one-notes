Kubernetes with kind — Beginner Setup Guide

What each tool does and why you need it — before memorizing any commands.

1. First, Understand What We're Creating

Before any commands: here's the overall picture of what you're about to build.

Your Windows/Mac/Linux machine │ ▼ kind │ ▼ Kubernetes Cluster │ ├── Control Plane │ └── Worker Node(s) │ └── Your Pods │ └── Your Application
💬 Kubernetes is a system for running and managing containers.

Your Node.js app already goes through this journey today, with Docker alone:

Node.js application ↓ Docker image ↓ Container

Docker can run that container directly:

docker
docker run my-node-app

Kubernetes adds another layer on top — it doesn't run your container directly, it runs it inside a Pod:

Kubernetes ↓ Pod ↓ Container ↓ Your Node.js application
2. What Is kind?
💬 kind stands for Kubernetes IN Docker.
It creates a Kubernetes cluster on your own computer, using Docker containers as the cluster's "nodes."

Instead of spinning up a cluster on AWS, Azure, or GCP, you can create one locally, for free, in seconds:

Your Computer │ ├── Docker │ └── kind │ └── Kubernetes Cluster
create cluster
kind create cluster --name ms-demo

This creates a Kubernetes cluster called ms-demo.

3. kind vs Minikube

Both are tools for running Kubernetes locally — they just take different paths to get there.

📦
kind
kind → Docker → Kubernetes. Creates Kubernetes nodes as Docker containers. Good fit if you're already comfortable with Docker.
💻
Minikube
Minikube → VM/container → Kubernetes. Runs the cluster inside a dedicated VM (or container), a bit more isolated from your host.
✅ Recommendation for you: go with kind + kubectl — since you're already learning Docker and containers, kind builds directly on knowledge you already have.
4. What Is kubectl?

This is one of the most important concepts to get straight early on.

💬 kubectl is the command-line client used to communicate with Kubernetes.
You
→
kubectl
→
Kubernetes API Server
→
Kubernetes Cluster
kubectl get nodes"Kubernetes, show me the nodes in this cluster."
kubectl get pods"Show me the Pods running in the cluster."
💡 kind creates/manages your local cluster. kubectl talks to and operates whatever cluster is currently active. Keeping these two roles separate in your head will save a lot of confusion later.
5. What Is Helm?

Your install command includes helm — a separate Kubernetes tool.

💬 Helm is a package manager for Kubernetes applications — the same idea as npm, just one layer up.
📦
npm
npm → installs Node.js packages into your project.
⚓
Helm
Helm → installs "charts" (templated, bundled sets of Kubernetes YAML) into your cluster.
⚠️ You don't need Helm to understand your first Kubernetes cluster — it becomes useful once you're tired of hand-writing lots of individual YAML files. Learn it later.
6. Installing Everything

The classic install command you may have seen:

macOS + Homebrew
brew install kind kubectl helm
⚠️ This is specifically for macOS with Homebrew. You're on Windows — don't run this unless you have a separate Homebrew-on-Windows setup. Use Windows-compatible install methods instead. Docker Desktop + WSL2 (which you already have) is a solid environment for this.

On Linux (or inside WSL2's Ubuntu), kind installs like this:

Ubuntu (WSL2)
curl -Lo ./kind https://kind.sigs.k8s.io/dl/latest/kind-linux-amd64
chmod +x ./kind
sudo mv ./kind /usr/local/bin/kind
curl <URL>Downloads something from a URL.
-LFollow redirects (the download link often redirects once).
-o ./kindSave the downloaded file as ./kind.
chmod +xMarks the file as executable.
mv → /usr/local/binMoves it onto your PATH so kind works from anywhere.

Before creating anything, verify each tool installed correctly:

verify
kind version
kubectl version --client
helm version
✅ At this point: kind installed, kubectl installed, helm installed.
7. Create Your Kubernetes Cluster
create cluster
kind create cluster --name ms-demo
kind"I want to work with a local Kubernetes cluster."
create cluster"Create a Kubernetes cluster."
--name ms-demoGive the cluster the name ms-demo.

What happens internally — kind builds the cluster on top of Docker:

Docker │ └── kind │ └── Kubernetes cluster │ └── Node
docker ps
docker ps

CONTAINER ID    NAME
xxxxxx          ms-demo-control-plane

That row is your entire Kubernetes "node" — under the hood, it's just a Docker container. (Exact name/output can vary.)

💡 What is a Node? A machine Kubernetes uses to run workloads. With kind it's a Docker container; in production it could be an EC2 instance, a VM, or a physical server.
Kubernetes Cluster │ ▼ Node │ ├── Pod │ └── Container │ └── Pod └── Container
8. Nodes, Roles & Contexts

Confirm the cluster itself is alive:

cluster-info
kubectl cluster-info
kubectl
→
Kubernetes API Server
→
Cluster information

If this returns info instead of an error, kubectl can talk to Kubernetes. ✅

Now list the actual nodes:

get nodes
kubectl get nodes

NAME                     STATUS   ROLES           AGE   VERSION
ms-demo-control-plane    Ready    control-plane   1m    v1.xx.x
STATUS: ReadyKubernetes considers this node available to run workloads.
ROLES: control-planeHandles the Kubernetes API, scheduling, and desired-state management. Your first kind cluster may only have this one node.

Next — a different question, answered locally rather than by the cluster:

get-contexts
kubectl config get-contexts

CURRENT   NAME             CLUSTER          AUTHINFO
*         kind-ms-demo     kind-ms-demo     kind-ms-demo

This doesn't ask Kubernetes "what nodes do you have?" — it asks your local kubectl config: "what clusters/contexts do I know about?" The * marks the currently active one.

💬 A context is how kubectl switches between multiple clusters — local, dev, prod — without you re-configuring anything by hand each time.
kubectl │ ├── kind-ms-demo │ ├── dev-cluster │ └── prod-cluster

You can switch explicitly:

switch context
kubectl config use-context kind-ms-demo

After that, every kubectl command operates against kind-ms-demo until you switch again. kind sets this context up for you automatically the moment it creates the cluster.

Kubernetes │ ▼ Deployment │ ▼ Pod │ ▼ Container │ ▼ Node.js application

🧠 The mental model to keep:
Docker → runs containers
kind → creates a local Kubernetes cluster
Kubernetes → manages applications/containers
kubectl → talks to Kubernetes
Node → machine where workloads run
Pod → Kubernetes's basic unit for running containers
➡️ Next logical topic: Kubernetes architecture — Cluster → Control Plane → API Server → Scheduler → Controller Manager → etcd → Node → Kubelet → Pod → Container. Understanding this before writing YAML makes everything afterward much easier.
