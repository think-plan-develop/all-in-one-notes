The practical, backend-developer subset: why a Pod failed, how traffic actually reaches it, and how to start/stop/restart things correctly.

1. Debug a Failed Pod

As a backend developer, the core skill is simple: knowing how to figure out why a Pod isn't working.

Step 1 — Check Pod status

get pods
kubectl get pods

NAME       READY   STATUS             RESTARTS
backend    0/1     CrashLoopBackOff   3
StatusMeaning
RunningPod is running
PendingPod hasn't started successfully
ContainerCreatingContainer is being created
CrashLoopBackOffContainer keeps crashing/restarting
ImagePullBackOffKubernetes cannot pull the image
ErrorContainer/application exited with an error
CompletedContainer finished successfully

Step 2 — Check what happened

describe pod
kubectl describe pod backend

... scroll to the bottom ...
Events:

The Events section at the bottom is the goldmine here — it surfaces: image pull failures, containers that can't start, volume problems, scheduling problems, and configuration problems.

Step 3 — Check application logs

logs
kubectl logs backend

Error: DATABASE_URL is not defined

Now you know: the problem is your app's configuration, not Kubernetes itself.

Step 4 — If the container already crashed

previous logs
kubectl logs backend --previous

Pulls logs from the previous, already-dead container — essential when a Pod is stuck in CrashLoopBackOff and the current container has no useful output yet.

Common failure patterns

🔁
CrashLoopBackOff
App starts → crashes → Kubernetes restarts it → crashes again. Check kubectl logs backend for the actual error.
🖼️
ImagePullBackOff
Wrong image name/tag, private registry auth issue, or the image doesn't exist. Check kubectl describe pod → Events.
⏳
Pending
Kubernetes hasn't started the Pod yet — often a scheduling or resource issue. Check kubectl describe pod → Events.
💬 Don't memorize twenty commands — remember the flow.
Pod not working
↓
kubectl get pods
↓ what is the STATUS?
kubectl describe pod <pod>
↓ check Events
kubectl logs <pod>
↓
Find application/container error
↓
Fix the problem
✅ The 4 commands to know: kubectl get pods · kubectl describe pod <pod> · kubectl logs <pod> · kubectl logs <pod> --previous
2. Understand Ingress Practically

What you really need to understand: how an external HTTP request reaches your Kubernetes application.

What is Ingress?

💬 Ingress is a Kubernetes resource that defines rules for incoming HTTP/HTTPS traffic, routing requests to different Services.
Browser
→
Ingress
→
Service
→
Pod
→
Node.js app
https://api.example.com ↓ Ingress ↓ backend-service ↓ backend Pod

Why do we need it?

Say you have two apps — a frontend and a backend, each with their own Service. Without Ingress you'd expose each separately via NodePort or LoadBalancer. Ingress lets you define all HTTP routing rules in one place:

example.com ↓ frontend-service api.example.com ↓ backend-service

Ingress vs Service — don't mix these up

🔌
Service
Connects traffic to Pods. Service → Pods.
🚦
Ingress
Routes HTTP/HTTPS traffic to Services. Ingress → Service → Pods.
⚠️ Don't think Ingress → Pod. It's always Ingress → Service → Pod.

What is an Ingress Controller?

An Ingress resource only holds the rules — something has to actually implement them. That's the Ingress Controller.

Ingress rules ↓ Ingress Controller ↓ Service ↓ Pod
⚙️
NGINX Ingress Controller
Most common choice for local (kind) clusters.
🚏
Traefik
Popular alternative, dynamic config-focused.
☁️
Cloud controllers
AWS/GCP/Azure-managed Ingress controllers in production.

Simple Ingress example

Backend Service backend-service, Node.js listening on port 3000:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: backend-ingress

spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: backend-service
                port:
                  number: 3000

Meaning: requests to api.example.com get sent to backend-service on port 3000.

Host-based routing

api.example.com → backend-service admin.example.com → admin-service example.com → frontend-service

Path-based routing

example.com/ → frontend-service example.com/api → backend-service
rules:
  - host: example.com
    http:
      paths:
        - path: /api
          pathType: Prefix
          backend:
            service: { name: backend-service, port: { number: 3000 } }

        - path: /
          pathType: Prefix
          backend:
            service: { name: frontend-service, port: { number: 80 } }

Checking Ingress

get / describe ingress
kubectl get ingress

NAME              CLASS   HOSTS             ADDRESS
backend-ingress   nginx   api.example.com   localhost

kubectl describe ingress backend-ingress

Practical debugging — walk the whole chain

chain check
kubectl get ingress
kubectl describe ingress backend-ingress
kubectl get svc
kubectl get endpoints
kubectl get pods
Ingress ↓ ? Service ↓ ? Pod ↓ ? Node.js

You're checking each link in the chain individually until you find where it breaks.

🚨 Important: creating an Ingress resource does NOT automatically make your app reachable — you also need an Ingress Controller actually running in the cluster to implement those rules.

3. Pod Start / Stop / Restart Commands
🚨 Important correction first: a standalone Pod can't really be "stopped" and "started" the way a Docker container can. For Pods, the normal operation is delete → recreate. If a Pod belongs to a Deployment, use the Deployment-level commands instead.

Main Pod commands

pods
# Create a Pod quickly
kubectl run my-pod --image=nginx

# List all Pods
kubectl get pods

# List Pods with more details (IP, Node)
kubectl get pods -o wide

# Get details of a particular Pod
kubectl describe pod my-pod

# Show Pod logs
kubectl logs my-pod

# Follow Pod logs continuously
kubectl logs -f my-pod

# Show logs from the previous crashed container
kubectl logs my-pod --previous

# Open a shell inside the Pod
kubectl exec -it my-pod -- sh

# Execute one command inside the Pod
kubectl exec my-pod -- env

# Watch Pods continuously
kubectl get pods -w

# Delete a particular Pod
kubectl delete pod my-pod

# Force delete a stuck Pod
kubectl delete pod my-pod --grace-period=0 --force

Start / Stop / Restart — the important part

▶️
"Start" a stopped Pod
There's no kubectl start pod. Recreate it instead: kubectl apply -f pod.yaml, or kubectl run my-pod --image=nginx.
⏹️
"Stop" a running Pod
There's no kubectl stop pod either. For a standalone Pod: kubectl delete pod my-pod. Bring it back with kubectl apply -f pod.yaml.
🔄
Restart a standalone Pod
Delete then recreate: kubectl delete pod my-pod followed by kubectl apply -f pod.yaml.
♻️
Restart a Deployment-managed Pod
Don't recreate manually. Just delete it — the Deployment creates a replacement automatically: kubectl delete pod <pod-name>.

Restart every Pod in a Deployment at once

rollout restart
kubectl rollout restart deployment backend

Check what happened after a restart

verify
kubectl get pods
kubectl get pods -w            # watch Pods being recreated live
kubectl logs <pod-name>

The main thing to remember

Standalone Pod ↓ delete → recreate Deployment-managed Pod ↓ delete Pod → Deployment creates replacement Restart entire application ↓ kubectl rollout restart deployment <name>
✅ Core commands to memorize first:
kubectl run my-pod --image=nginx    # Create
kubectl get pods                            # Check
kubectl describe pod my-pod         # Details/debug
kubectl logs my-pod                    # Logs
kubectl logs -f my-pod               # Follow logs
kubectl exec -it my-pod -- sh       # Enter Pod
kubectl delete pod my-pod          # Delete
kubectl get pods -w                    # Watch
kubectl rollout restart deployment X # Restart app
