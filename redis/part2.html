Redis — Caching & Cache Invalidation

The Cache-Aside pattern, a real Node.js implementation, and how to keep Redis from serving stale data.

1. Why Caching 2. Cache-Aside Pattern 3. Node.js Implementation 4. Cache Invalidation 5. Strategies & Trade-offs Interview Q&A
💡 Core idea: Caching means keeping frequently needed data in Redis so your application doesn't have to query the main database every time. The database stays the source of truth; Redis is a fast copy.
🔑 Key Terms at a Glance
🎯
Cache-Aside: The application checks Redis first; on a miss it fetches from the database and writes the result back into Redis.
✅
Cache Hit: Redis already has the data — the database is never touched.
❌
Cache Miss: Redis doesn't have the data yet — fall through to the database, then populate Redis.
🗑️
Cache Invalidation: Removing or updating cached data when the underlying database record changes.
⏱️
TTL ≠ Invalidation: TTL is time-based expiry; invalidation is data-change-based removal. You typically use both.
🌀
Stale data: The main risk of caching — Redis still serving an old value after the database has already changed.
1. Why Do We Need Caching?

Without Redis vs With Redis

Without Redis: Client ↓ API ↓ PostgreSQL / MongoDB ↓ Response
With Redis: Client ↓ API ↓ Redis ↓ Data found? ├── YES → Return data │ └── NO ↓ Database ↓ Store in Redis ↓ Return data

Suppose GET /users/101 is requested repeatedly. Without Redis, every single request hits the database:

Request 1 → Database Request 2 → Database Request 3 → Database Request 4 → Database ...

With Redis, only the first request touches the database — everything after that is served from memory:

Request 1 → Redis ❌ → Database → Redis ✅ Request 2 → Redis ✅ Request 3 → Redis ✅ Request 4 → Redis ✅
✅ Redis absorbs the repeated reads, so your database only handles genuinely new lookups instead of every single request.
2. Cache-Aside Pattern ⭐⭐⭐⭐⭐
💬 The simple idea: the application checks Redis first. If the data isn't there, it fetches from the database and puts a copy into Redis. The application manages the cache itself — that's why it's called Cache-Aside.

The complete flow: GET /users/101

Client │ ↓ Node.js API │ ↓ Redis │ Data exists? / \ YES NO │ │ ↓ ↓ Return data Database │ ↓ Get data │ ↓ Store Redis │ ↓ Return data

Step 1 — Client sends the request

Client ↓ GET /users/101

Step 2 — API checks Redis

check cache
const cachedUser = await redis.get("user:101");

Step 3 — Two possibilities

Case A — Cache Hit
→
Return Redis data, DB untouched
Case B — Cache Miss
→
Query Database
→
Store in Redis
→
Return data
3. Real Node.js Implementation

The full Cache-Aside function

user.service.js
const cachedUser = await redis.get(`user:${userId}`);

if (cachedUser) {
  return JSON.parse(cachedUser);
}

const user = await User.findById(userId);

await redis.set(
  `user:${userId}`,
  JSON.stringify(user),
  {
    EX: 300
  }
);

return user;

Step 1 — Build the Redis key

If userId = 101, `user:${userId}` becomes user:101.

Step 2 — Check Redis

Redis returns either a JSON string, or null if the key doesn't exist.

Cache Hit vs Cache Miss

Cache Hit — the fast path

GET /users/101 ↓ Redis ↓ user:101 exists ✅ ↓ JSON.parse() ↓ Return user

The database isn't called at all.

Cache Miss

Redis ↓ MISS ❌ ↓ MongoDB

Once MongoDB returns the record, that result is written into Redis with a TTL:

store result
await redis.set(
  `user:${userId}`,
  JSON.stringify(user),
  { EX: 300 }
);
Key: user:101 Value: {"id":101,"name":"Shivam"} TTL: 300 seconds

For the next 5 minutes, GET /users/101 is a guaranteed cache hit — the database isn't queried again until the TTL expires.

Why JSON.stringify() / JSON.parse()?

Redis stores values as strings, so JavaScript objects need to be serialized before storing and parsed back after reading:

JavaScript Object ↓ JSON.stringify() ↓ Redis ↓ JSON.parse() ↓ JavaScript Object

Why TTL is used

You don't normally want cached data to live forever — { EX: 300 } means "expire after 300 seconds":

10:00 → Cache created 10:01 → Cache available 10:03 → Cache available 10:05 → Cache expires 10:06 → Redis MISS

After expiration, the very next request naturally refreshes the cache — miss → database → store → return.

4. Cache Invalidation ⭐⭐⭐⭐⭐
🚨 The problem: if the database data changes, make sure Redis doesn't keep serving the old value. This is the main risk you need to manage in any caching setup.

How stale data happens

Database: Redis (cached copy): user:101 user:101 name = Shivam name = Shivam role = user role = user ✅ synchronized

Now the user updates their name via PUT /users/101:

Database becomes: Redis still has: user:101 user:101 name = Rahul name = Shivam ❌

The next GET /users/101 checks Redis first and returns Shivam — stale data — even though the database already says Rahul.

The fix: delete cache after update

update handler
await User.findByIdAndUpdate(userId, updateData);

await redis.del(`user:${userId}`);
UPDATE USER ↓ Update Database ↓ Delete Redis Cache

Now the next GET is a guaranteed miss, which naturally repopulates Redis with the fresh value:

GET /users/101 ↓ Redis ↓ MISS ↓ Database ↓ Rahul ↓ Store in Redis ↓ Return Rahul
✅ Database and Redis are synchronized again — both now say Rahul.

Delete vs Update the cache

ApproachWhat happens
Delete cache ⭐Next request gets fresh data from the DB (Cache-Aside repopulates it)
Update cacheImmediately put the new data into Redis — avoids the next miss, but you must be careful the cached shape is exactly correct
update-in-place variant
const updatedUser = await User.findByIdAndUpdate(
  userId,
  updateData,
  { new: true }
);

await redis.set(
  `user:${userId}`,
  JSON.stringify(updatedUser),
  { EX: 300 }
);

The simpler and safer default for most applications is: update the database, then delete the cache, and let Cache-Aside repopulate it on the next read.

5. Strategies, Trade-offs & What To Cache

CREATE / UPDATE / DELETE — the pattern to memorize

GET
Check Redis → HIT: return. MISS: query DB → store in Redis → return.
UPDATE
Update Database → delete the Redis cache key.
DELETE
Delete the Database record → delete the Redis cache key.
CREATE
Insert into Database → invalidate any affected list/aggregate cache keys, if they exist.
delete handler
await User.findByIdAndDelete(userId);

await redis.del(`user:${userId}`);
⚠️ The real rule isn't "whenever the database changes, delete Redis" — it's "whenever data changes, invalidate every cache entry that depends on it." A single record can be duplicated across several cached keys (e.g. product:501, products:page:1, category:electronics).

TTL vs Invalidation — not the same thing

MechanismTrigger
TTLTime-based — the key disappears automatically after N seconds, regardless of whether the data changed
InvalidationData-change-based — the application explicitly deletes/updates a key because the underlying record changed

In practice you usually use both together — TTL as a safety net, invalidation for immediate correctness:

Cache created ↓ TTL = 5 minutes ↓ If data changes before 5 minutes ↓ Invalidate immediately

What's worth caching (and what isn't)

Good candidatesBe careful caching
Product detailsBank account balance
Product categoriesPayment status
User profileInventory count
Configuration / reference dataAnything highly volatile or sensitive to staleness
Dashboard summaries—

The pattern for a good candidate: frequently read + doesn't change often + expensive to fetch.

Advantages

Faster responses
Redis reads are far faster than hitting the primary database.
Less DB load
Redis absorbs most repeated reads; only misses reach the database.
Simple control
Your application explicitly decides when to read, write, and invalidate the cache.

Disadvantages

Stale data
Redis can serve an outdated value if invalidation is missed.
Invalidation complexity
Knowing every cache key that depends on a changed record isn't always obvious.
First-miss cost
The first request after expiry still pays the full database cost.
Cache stampede
A popular key expiring under heavy load can send many requests to the DB at once. Just know the problem exists for now.
Interview Q&A
💡 Interview Q&A
Standard Questions
What is the Cache-Aside pattern?
The application checks Redis first for a given key. On a hit, it returns the cached value directly. On a miss, it queries the database, stores the result in Redis (usually with a TTL), and then returns it. The application — not Redis itself — is responsible for managing what gets cached and when.
What is cache invalidation, in one sentence?
Removing or updating cached data when the underlying database record changes, so Redis doesn't keep serving an old value after the source of truth has moved on.
Why use JSON.stringify() before storing an object in Redis?
Redis stores values as strings. A JavaScript object has to be serialized to a JSON string to store it, and parsed back with JSON.parse() when reading it out again.
What's the difference between TTL and invalidation?
TTL is time-based — the key expires automatically after a fixed duration regardless of whether anything changed. Invalidation is data-change-based — the application explicitly deletes or updates a key the moment it knows the underlying record changed. Most real systems use both together.
Tricky / Follow-Up Questions
If you only delete product:501 after a price change, is that always enough?
Not necessarily. The same product may also be duplicated inside other cached results — like products:page:1, category:electronics, or homepage:featured-products. You need to invalidate every cache entry that depends on the changed record, not just the record's own key.
Why not just always update the cache instead of deleting it?
Updating avoids the next cache miss, but it requires you to construct the exact correct representation of the new state every time you write to Redis — any mismatch introduces a subtle bug. Deleting is simpler and safer: you let Cache-Aside naturally repopulate the key from the database on the next read.
Should you cache a bank account balance the same way you'd cache product details?
No — good caching candidates are frequently read, don't change often, and are expensive to fetch. A balance changes with every transaction and staleness has real consequences, so it needs careful consistency handling rather than a blind Cache-Aside TTL.
What is a "cache stampede"?
When a popular cache key expires and a burst of simultaneous requests all experience a miss at once, all of them can hit the database in parallel — momentarily defeating the purpose of the cache. You don't need to master prevention techniques yet, just recognize the failure mode.
The One You Should Be Ready For
How would you implement Redis caching for GET /users/:id?
"I'd use the Cache-Aside pattern. The API checks Redis using a key like user:{id}. If it exists, that's a cache hit and I return the cached data directly. If it doesn't, that's a cache miss — I fetch the user from the database, store the result in Redis with an appropriate TTL, and return it. When the user is updated or deleted, I invalidate the corresponding Redis key so the next read fetches the fresh value instead of stale data."
