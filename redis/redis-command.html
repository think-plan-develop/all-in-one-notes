🔑 Key Terms at a Glance
🏓
PING → PONG: The universal "is Redis alive?" health check.
🔢
(integer) reply: Redis's native numeric response type — used for counts, booleans (1/0), and TTL seconds.
🔍
SCAN vs KEYS: SCAN iterates safely without blocking; KEYS blocks the whole server on large datasets — avoid it in production.
🐳
Redis on Docker: No local install needed — pull the image, run it detached, and connect with redis-cli inside the container.
⏳
TTL responses: A positive number = seconds left. -1 = no expiry set. -2 = key doesn't exist at all.
🧱
TYPE: Tells you which structure a key holds — string, hash, list, set, zset, or none.

2. Expiration / TTL & Counters

Expiration / TTL

ttl
EXPIRE user:101 300
# Sets key "user:101" to auto-delete after 300 seconds (5 min)
# Response: (integer) 1 if expiry was set, 0 if key doesn't exist

TTL user:101
# Checks remaining time-to-live (in seconds) for "user:101"
# Response: seconds left, -1 if no expiry set, -2 if key doesn't exist

SET token:101 "abc" EX 900
# Stores "abc" under "token:101" AND sets it to expire in 900 seconds (15 min)
# Shortcut for SET + EXPIRE in one command — common for auth tokens/OTPs
# Response: OK

SET token:101 "abc" EX 900Sets value + expiry in one shotOK
💡 SET ... EX <seconds> is the shortcut you'll use constantly for auth tokens and OTPs — one command instead of SET followed by a separate EXPIRE.

3. Hashes & Discovering Keys Safely

Hash (object-like data)

hash
HSET user:101 name "Shivam"
# Sets field "name" to "Shivam" inside hash "user:101"
# A hash can hold multiple fields, like a mini JSON object
# Response: (integer) 1 if new field, 0 if field was updated

HGET user:101 name
# Reads only the "name" field from hash "user:101"
# Response: "Shivam"

HGETALL user:101
# Reads ALL fields and values from hash "user:101"
# Response: field1, value1, field2, value2, ...
# Example: name "Shivam" role "admin"
CommandWhat it doesResponse
HSET user:101 name "Shivam"Sets one field inside a hash(integer) 1 new field, 0 updated
HGET user:101 nameReads a single field from a hash"Shivam"
HGETALL user:101Reads every field + value from a hashFlat list: name "Shivam" role "admin"

Discovering Keys Safely

discovery
SCAN 0 MATCH user:*
# Iterates over keys matching pattern "user:*" without blocking Redis
# Safer alternative to KEYS command in production (KEYS blocks server on large datasets)
# Response: cursor (for next scan) + list of matching keys
# Repeat SCAN with returned cursor until cursor = 0 (full scan done)

TYPE user:101
# Returns the data type stored at "user:101"
# Response: string, hash, list, set, zset, or none (key doesn't exist)
CommandWhat it doesResponse
SCAN 0 MATCH user:*Safely iterates matching keys without blocking the serverCursor + list of matching keys
TYPE user:101Returns the data structure stored at a keystring / hash / list / set / zset / none
🚨 Avoid KEYS * in production. It blocks the entire Redis server while it scans, which can stall every other client on a large dataset. SCAN does the same job incrementally, without blocking.

Interview Q&A
💡 Interview Q&A
Standard Questions
What does SET token:101 "abc" EX 900 actually do, in one command?
It stores the value "abc" under token:101 AND sets it to expire in 900 seconds — a shortcut that combines what would otherwise be a separate SET followed by EXPIRE. This pattern is the standard way to store auth tokens and OTPs.
What do TTL's three possible response ranges mean?
A positive number is the number of seconds remaining before the key expires. -1 means the key exists but has no expiry set. -2 means the key doesn't exist at all.
Why use INCR instead of reading a value, adding 1 in your app, and writing it back?
INCR is atomic at the Redis server level — the read-modify-write happens as one indivisible operation. Doing it manually in application code introduces a race condition under concurrent requests, where two increments could both read the same starting value and clobber each other.
Tricky / Follow-Up Questions
Why is KEYS * dangerous in production but SCAN isn't?
KEYS walks the entire keyspace in one blocking operation — on a large dataset, that can freeze the Redis server for every other connected client while it runs. SCAN does the same discovery incrementally, returning a small batch plus a cursor each call, so the server stays responsive between calls.
If you run docker stop redis and then docker start redis, do you lose your cached data?
No — stop/start operate on the same container, which retains its filesystem between the two commands. You'd only lose data if you removed the container entirely (docker rm redis) without a persistent volume attached, or if the data was never configured to persist to disk in the first place.
What does docker exec -it redis redis-cli actually let you avoid?
Installing Redis (or its CLI tools) on your host machine at all. The redis-cli binary already lives inside the official Redis image, so you open an interactive shell into the running container and use its bundled client directly.
