What It Is

Sharding, In One Line

Sharding is MongoDB's method of horizontal scaling — instead of one big server holding all your data, the data is split into chunks and distributed across multiple servers called shards, so each machine only holds a slice of the total dataset.

Why it matters: a single server has limits on storage, RAM, and throughput. Sharding lets a cluster grow by adding more machines rather than bigger ones.

Key Components

Building Blocks of a Sharded Cluster

Shard
A single server (or replica set) that stores a subset of the cluster's data. Each shard can itself be a replica set for high availability.
Mongos (Query Router)
The router your application actually talks to. It figures out which shard(s) hold the relevant data and routes queries accordingly.
Config Servers
Store the cluster's metadata — which chunks of data live on which shard. Without them, mongos wouldn't know where anything is.
Shard Key
A field (or combination of fields) chosen from your documents that MongoDB uses to decide how data is distributed across shards. Picking a good shard key is the most important design decision in sharding.
Chunk
A contiguous range of shard key values. MongoDB splits collections into chunks and distributes/balances them across shards.

Components

  • mongos → Receives all client requests and routes them.
  • Shard → Stores actual data.
  • Config Servers → Store metadata (which chunk belongs to which shard).
How It Distributes Data

Distribution Strategies

StrategyHow it WorksGood For
Ranged Sharding Documents are split into chunks based on ranges of the shard key value Range-based queries (e.g. date ranges)
Hashed Sharding A hash of the shard key determines chunk placement, spreading data more evenly Avoiding hotspots on sequential keys (like timestamps or auto-increment IDs)
Zoned Sharding Specific ranges of shard key values are pinned to specific shards/zones Geo-based data locality or tiered hardware
Behind the Scenes

Balancing & Migration

  • The balancer process runs in the background, moving chunks between shards to keep data evenly distributed.
  • As data grows, large chunks automatically split into smaller ones.
  • If one shard has too many chunks, migrations move some to less-loaded shards.

Choosing a poor shard key (e.g. low-cardinality fields, or monotonically increasing values like timestamps) can create "hot" shards that absorb most of the traffic, defeating the purpose of sharding.

Hands-On

Setting Up Sharding — Step by Step

Interview Tip: You never connect directly to a shard to configure sharding. Every sharding command is run against mongos, the query router that acts as the cluster's entry point.

1

Connect to mongos

Never execute sharding commands directly on a shard.

shell
mongosh mongodb://mongos-host:27017

Verify you're actually connected to the router:

mongosh
db.adminCommand({ hello: 1 })
2

Enable sharding on a database

mongosh
sh.enableSharding("myDatabase")

This does not shard any collections. It only marks the database as allowed to contain sharded collections — think of it as turning sharding ON for the database.

3

Choose a shard key

The shard key determines how MongoDB distributes documents across shards. For a document like:

document
{
   _id: ObjectId(),
   userId: 101,
   name: "John",
   city: "Delhi"
}

Possible shard keys: userId, city, or email. Choosing the right one is the most important decision in sharding.

4

Create an index on the shard key

Required before sharding a collection for ranged sharding.

mongosh
db.myCollection.createIndex({ userId: 1 })

Verify it was created:

mongosh
db.myCollection.getIndexes()
5

Shard the collection — range-based

mongosh
sh.shardCollection(
    "myDatabase.myCollection",
    { userId: 1 }
)

MongoDB divides data into contiguous ranges (e.g. 1→1000 on Shard 1, 1001→2000 on Shard 2). This is excellent for range queries:

query
db.users.find({
    userId: { $gte: 1000, $lte: 2000 }
})

Monotonically increasing keys (like auto-increment IDs) cause all new inserts to land on the last shard, creating a hot shard.

6

Shard the collection — hashed

mongosh
sh.shardCollection(
    "myDatabase.myCollection",
    { userId: "hashed" }
)

MongoDB hashes the shard key so writes spread evenly instead of piling onto the last shard — ideal for equality lookups:

query
db.users.find({ userId: 12345 })
7

Add a new shard

mongosh
sh.addShard(
   "shardReplSet/host1:27018,host2:27018"
)

MongoDB registers the new replica set as a shard, then the balancer gradually migrates chunks onto it.

8

View sharding status

mongosh
sh.status()

Sample output (simplified):

output
Sharding Status

Database
  myDatabase

Collection
  users

Shard Key
  userId

Chunks
  Shard A    20
  Shard B    18
  Shard C    22

Shows sharded databases, sharded collections, shard keys, number of chunks, chunk distribution, registered shards, and balancer status. This is usually the first command used to troubleshoot a sharded cluster.

Chunk Migration (Automatic Balancing)

MongoDB stores data in chunks, not individual documents. Example placement:

chunk map
Chunk 1 → Shard A
Chunk 2 → Shard A
Chunk 3 → Shard B
Chunk 4 → Shard C

If Shard A becomes overloaded, the balancer automatically moves chunks to even things out:

Before After Shard A 30 Chunks Shard A 17 Chunks Shard B 10 Chunks Shard B 17 Chunks Shard C 10 Chunks Shard C 16 Chunks

This keeps storage and load balanced across the cluster.

Replica Set Setup (Each Shard in Production)

In production, every shard should be its own replica set for high availability. Here's how to stand one up:

mongosh
// Start each node (run once per server/port)
mongod --replSet "rs0" --port 27017 --dbpath /data/rs0 --bind_ip localhost
// Connect to one node and initiate the set
rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "localhost:27017" },
    { _id: 1, host: "localhost:27018" },
    { _id: 2, host: "localhost:27019" }
  ]
})
// Check status of all members
rs.status()
// See which member is currently primary
rs.isMaster()

Interview Prep

Common Interview Questions

1. Why do we enable sharding on a database first?

Because MongoDB must know that the database is allowed to contain sharded collections. Enabling sharding does not shard any collections by itself.

2. Why do we create an index before sharding?

For range-based sharding, MongoDB requires an index on the shard key to efficiently split and route data. It also improves query performance.

3. Why are sharding commands run on mongos instead of a shard?

mongos is the query router. It communicates with the config servers to update cluster metadata and coordinates all shards. Individual shards only store their portion of the data and do not manage cluster-wide configuration.

4. What happens after adding a new shard?

MongoDB's balancer automatically redistributes chunks from existing shards to the new shard to balance storage and workload.

5. When should I choose a hashed shard key?

Use a hashed shard key when writes are very frequent, you need even distribution across shards, and your queries are mostly equality lookups (e.g. userId = 12345).

6. When should I choose a ranged shard key?

Use a ranged shard key when your application frequently performs range queries ($gte, $lte), data is naturally accessed in sequential ranges, and you can avoid hotspots with a well-chosen shard key or compound key.

Best Practices ⭐⭐⭐⭐⭐

Best Practices

  • Execute all sharding administration commands through mongos, never directly on a shard.
  • Choose a high-cardinality shard key with many unique values.
  • Avoid monotonically increasing keys (like auto-increment IDs) for range sharding unless necessary.
  • Prefer hashed sharding for write-heavy workloads and range sharding for range-query-heavy workloads.
  • Monitor sh.status() and the balancer regularly to ensure chunks remain evenly distributed.
  • In production, configure each shard as a Replica Set to achieve both scalability (sharding) and high availability (replication).
Takeaway

Summary

Sharding = splitting a large dataset across multiple servers to scale storage and throughput horizontally. The shard key determines how data is split, mongos routes queries, config servers track metadata, and the balancer keeps everything evenly spread. It's a MongoDB feature you turn to when a single server (even a beefy one) can't keep up with your data or traffic.
