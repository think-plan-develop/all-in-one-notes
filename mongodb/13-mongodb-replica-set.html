Replica Sets in MongoDB

A replica set is a group of MongoDB servers that keep the same data in sync, so your application keeps running even if one of the servers goes down.

Introduction

What is a Replica Set?

A replica set is MongoDB's built-in mechanism for data redundancy and high availability. Instead of running a single MongoDB server, you run a group of mongod processes that all maintain the exact same data set.

One member is elected the Primary and accepts all write operations. The remaining members are Secondaries, which replicate the primary's data by continuously applying its operation log (the oplog). If the primary ever becomes unavailable, the remaining members automatically hold an election and promote a new primary — with no manual intervention required.

In short: a replica set = one primary + multiple secondaries + automatic failover, giving you a database that survives server crashes, network partitions, and planned maintenance without downtime.
Core Concept

What is a Replica?

A replica is simply one copy of the data — a single mongod server instance that holds the same data as the other members in the group. It's the individual unit; it is not the whole system.

A replica set, on the other hand, is the entire collection of these replicas working together as one logical database — with a primary, one or more secondaries, and automatic failover between them.

Simple way to remember: a replica = one node/copy of the data. A replica set = the whole group of replicas (primary + secondaries) managed as a single unit.

Terminology

Key Terms

Primary
The only member of the replica set that accepts write operations. There is always at most one primary at a time.
Secondary
Replicates data from the primary by applying oplog entries. Can serve read requests if the client opts in with an appropriate read preference.
Arbiter
A member that holds no data and doesn't accept reads or writes. It exists only to vote in elections, useful for keeping an odd number of voters without adding another full data-bearing server.
Oplog (Operation Log)
A special capped collection on the primary that records every write operation. Secondaries tail this log and re-apply the operations locally to stay in sync.
Election
The process by which remaining members choose a new primary when the current one becomes unreachable, using a Raft-derived consensus protocol.
Replication Lag
The delay between a write being applied on the primary and that same write being applied on a secondary.
Hidden / Delayed Member
A secondary that is invisible to application read traffic (hidden) or intentionally kept behind by a fixed delay (delayed), often used for backups or reporting.
Architecture

How the Members Are Connected

A typical production replica set has three data-bearing members (the minimum recommended for automatic failover with majority voting):

┌─────────────────────────────────────────────┐ │ APPLICATION │ └───────────────────────┬─────────────────────┘ │ writes / reads ▼ ┌───────────────────┐ │ PRIMARY │ │ (accepts writes)│ └─────────┬─────────┘ │ oplog replication ┌──────────┴──────────┐ ▼ ▼ ┌───────────────┐ ┌───────────────┐ │ SECONDARY 1 │ │ SECONDARY 2 │ │ (replicates) │ │ (replicates) │ └───────────────┘ └───────────────┘ If PRIMARY goes down → members vote → one SECONDARY is elected new PRIMARY
Why an odd number of members? Elections require a majority vote. With 3 members, 2 votes elect a primary; a 4-member set (2 vs 2) risks a tie, so an arbiter is often added to break it.
Failover Workflow

Elections & Automatic Failover

1

Heartbeat Failure

Every member sends heartbeats to every other member roughly every 2 seconds. If a secondary doesn't hear from the primary within the configured electionTimeoutMillis (default 10s), it assumes the primary is down.

2

Nomination

An eligible secondary calls for an election and requests votes from the rest of the set.

3

Voting

Members vote based on data freshness (highest priority and most up-to-date oplog wins). A candidate needs a majority of votes to become primary.

4

New Primary

The winning member transitions to primary state and starts accepting writes. The driver on the application side automatically detects this and redirects traffic — no code change needed.

Watch out: during an election (usually a few seconds), the replica set has no primary, so write operations will fail or block until a new primary is elected.
Setup Example

Initializing a Replica Set

Start three mongod instances with the same --replSet name, then initiate the set from the shell:

mongosh
// Start each node (run once per server/port)
mongod --replSet "rs0" --port 27017 --dbpath /data/rs0 --bind_ip localhost

// Connect to one node and initiate the set
rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "localhost:27017" },
    { _id: 1, host: "localhost:27018" },
    { _id: 2, host: "localhost:27019" }
  ]
})

// Check status of all members
rs.status()

// See which member is currently primary
rs.isMaster()
Tip: your MongoDB connection string should list all members so the driver can find the primary automatically: mongodb://host1:27017,host2:27018,host3:27019/?replicaSet=rs0

Use Cases

When Replica Sets Matter Most

  • Production applications that cannot tolerate downtime during server failure or maintenance
  • Read-heavy workloads that want to offload reporting/analytics queries to secondaries
  • Geographically distributed teams that want a nearby secondary for lower-latency local reads
  • Disaster recovery setups using a delayed secondary to recover from accidental data corruption

Comparison

Replication vs Sharding

Replication and sharding solve two different problems, and it's easy to mix them up. Here's how they compare:

ReplicationSharding
Copies the same data to multiple servers.Splits data across multiple servers.
Provides High Availability.Provides Horizontal Scaling.
Used for fault tolerance and disaster recovery.Used to handle very large datasets and high write/read workloads.
All nodes contain the same data (except replication lag).Each shard stores only a portion of the total data.
Interview tip: a common architecture in production combines both concepts — each shard is itself a replica set, giving you horizontal scaling through sharding and high availability through replication.
Common Mistakes

Pitfalls to Avoid

  1. Running only 2 data-bearing members — a tie during elections can leave the set without a primary
  2. Assuming a replica set is a backup strategy — it protects against hardware failure, not accidental deletes or corrupted writes (use proper backups too)
  3. Reading from secondaries without understanding replication lag, then being surprised by stale data
  4. Forgetting to include all hosts in the connection string, causing the driver to miss a failover
Quick Q&A

Frequently Asked Questions

Q: Can a replica set have more than one primary at the same time?

No. MongoDB guarantees only a single primary at any given moment, which is what keeps writes consistent.

Q: Is a replica set the same thing as sharding?

No. A replica set is about redundancy and availability (same data copied everywhere). Sharding is about horizontal scaling (data split across separate replica sets called shards). Sharded clusters are typically built on top of replica sets.

Q: What is the minimum number of members for automatic failover?

Three data-bearing members is the recommended minimum, since it allows a majority vote to succeed even if one member fails.
Remember: a replica set = primary + secondaries + oplog replication + automatic election on failure. It's the foundation of high availability in MongoDB.
