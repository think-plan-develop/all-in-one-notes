What It Means

Relationships in a Document Database

MongoDB is not a relational database, so it has no foreign keys or JOIN clause by default. But real applications still have related data — a user has orders, a blog post has comments, a student takes many courses. MongoDB gives you two core strategies to model these relationships:

In short: either embed related data directly inside a document, or store it separately and reference it by _id — the right choice depends on how the data is accessed, how fast it grows, and whether it's read together most of the time.
Two Core Approaches

Embedding vs Referencing

EmbeddingReferencing
Related data is nested inside the parent document.Related data lives in a separate collection, linked by an _id.
One read gets everything — no joins needed.Requires a separate query or a $lookup to combine data.
Best for data that's always read together and doesn't grow unbounded.Best for data that's large, shared across parents, or grows without limit.
Risk: documents can hit the 16MB size limit if arrays grow too large.Risk: extra queries/joins add latency and complexity.
Rule of thumb: embed data that's "owned" by and always viewed with the parent (e.g. an address on a user profile). Reference data that's independent, reused, or could grow very large (e.g. millions of orders for a user).
One-to-One

One-to-One Relationship

Example: a user and their profile details. Usually modeled by embedding, since the profile is small and always read with the user.

embedded (recommended)
{
  _id: ObjectId("u1"),
  name: "Asha",
  profile: {
    bio: "Backend engineer",
    avatarUrl: "https://..."
  }
}

If the sub-document is large or optional and rarely fetched, referencing works too:

referenced
// users collection
{ _id: ObjectId("u1"), name: "Asha", profileId: ObjectId("p1") }

// profiles collection
{ _id: ObjectId("p1"), bio: "Backend engineer" }
One-to-Many

One-to-Many Relationship

Example: a blog post and its comments. Three common patterns depending on scale:

1

Embed an array (small, bounded lists)

post document
{
  _id: ObjectId("post1"),
  title: "Intro to MongoDB",
  comments: [
    { user: "Raj", text: "Great post!" },
    { user: "Meera", text: "Very helpful" }
  ]
}

Simple and fast to read, but risky if comments can grow into the thousands (16MB document limit, degraded write performance).

2

Reference with a parent pointer (large, unbounded lists)

comments collection
{ _id: ObjectId(), postId: ObjectId("post1"), user: "Raj", text: "Great post!" }
{ _id: ObjectId(), postId: ObjectId("post1"), user: "Meera", text: "Very helpful" }

Query comments for a post with:

query
db.comments.find({ postId: ObjectId("post1") })

This scales to millions of comments per post, at the cost of needing a separate query (or $lookup).

3

Reference with a child array of IDs (medium-sized, static-ish lists)

post document
{
  _id: ObjectId("post1"),
  title: "Intro to MongoDB",
  commentIds: [ ObjectId("c1"), ObjectId("c2") ]
}

Keeps the parent document lean while still tracking the relationship — but requires a second query to fetch the actual comments.

Many-to-Many

Many-to-Many Relationship

Example: students and courses — a student takes many courses, and a course has many students. Modeled with arrays of references on one or both sides.

students collection
{
  _id: ObjectId("s1"),
  name: "Vikram",
  courseIds: [ ObjectId("c1"), ObjectId("c2") ]
}
courses collection
{
  _id: ObjectId("c1"),
  title: "Databases 101",
  studentIds: [ ObjectId("s1"), ObjectId("s2") ]
}
Watch out: storing the relationship on both sides (two-way referencing) means every enrollment change has to update two documents — easy to get out of sync. Many teams instead use a third "join" collection, similar to a relational many-to-many table.
enrollments collection (join collection)
{ _id: ObjectId(), studentId: ObjectId("s1"), courseId: ObjectId("c1") }
{ _id: ObjectId(), studentId: ObjectId("s1"), courseId: ObjectId("c2") }
Joining Data

Joining Referenced Data with $lookup

When data is referenced across collections, $lookup in the aggregation pipeline performs a left-outer-join-style operation to bring it back together.

aggregation pipeline
db.posts.aggregate([
  {
    $lookup: {
      from: "comments",
      localField: "_id",
      foreignField: "postId",
      as: "comments"
    }
  }
])

This attaches a comments array to each post, populated with all matching documents from the comments collection — similar to a SQL LEFT JOIN.

Note: $lookup is powerful but not free — it runs at query time and can be slower than embedding, especially without an index on foreignField. Index the field being joined on for good performance.
Common Mistakes

Pitfalls to Avoid

  1. Embedding unbounded arrays (e.g. all comments ever made) that can eventually breach the 16MB document size limit.
  2. Overusing $lookup as a crutch to mimic SQL joins, when the access pattern would be far simpler and faster with embedding.
  3. Two-way referencing without a plan to keep both sides in sync, leading to orphaned or mismatched references.
  4. Forgetting to index the foreign field used in $lookup, causing slow joins at scale.
  5. Modeling every relationship the same way regardless of read/write patterns — the right choice is workload-specific, not one-size-fits-all.
Interview Prep

Important Interview Q&A

1. Does MongoDB support relationships like a relational database?

Not natively through foreign keys or joins. It supports relationships through document design — embedding related data, or referencing it by _id and combining it manually or via $lookup.

2. When should you choose embedding over referencing?

When the related data is small, bounded in size, always read together with the parent, and doesn't need to be queried independently.

3. When should you choose referencing over embedding?

When the related data is large, grows without a clear bound, is shared across multiple parents, or is frequently queried on its own.

4. What is $lookup and how does it behave like SQL?

$lookup is an aggregation stage that joins documents from another collection based on matching field values, similar to a SQL LEFT OUTER JOIN.

5. What is the 16MB document size limit and why does it matter for relationships?

Every MongoDB document has a hard 16MB size limit. It matters for relationship modeling because embedding an ever-growing array (like all comments on a viral post) can eventually hit that limit and start failing writes.

6. How do you model many-to-many relationships in MongoDB?

Either with arrays of references on both sides (simple but can get out of sync), or with a dedicated join/enrollment collection that stores each pairing as its own document, similar to a relational join table.

7. What's a hybrid approach to modeling relationships?

Many real schemas mix both: embed a small preview or summary of related data (e.g. the last 3 comments) for fast reads, while also referencing the full related collection for when more data is needed.

8. Is $lookup as performant as embedding?

Generally no — $lookup performs the join at query time and adds overhead, especially without proper indexes on the joined field. Embedding avoids that cost entirely by keeping related data in one document.

Best Practices ⭐⭐⭐⭐⭐

Best Practices

  • Model your schema around how the application reads data, not around how a relational schema would look.
  • Embed data that's small, bounded, and always accessed together with its parent.
  • Reference data that's large, shared, or queried independently of its parent.
  • Always index the field used as the join key before relying on $lookup in production.
  • For many-to-many relationships at scale, prefer a dedicated join collection over two-way array references.
  • Revisit your schema as access patterns change — document modeling is iterative, not fixed at design time.

Takeaway

Summary

MongoDB models relationships through document design rather than foreign keys: embed when data is small and always read together, reference when data is large, shared, or queried independently, and use $lookup to join referenced data when needed. One-to-one and small one-to-many relationships usually favor embedding; large one-to-many and most many-to-many relationships favor referencing, often through a dedicated join collection.
