What It Is

What Is an Index in MongoDB?

An index is a special data structure that stores a small, sorted portion of a collection's data, allowing MongoDB to quickly locate documents without scanning every single one.

Without an index, MongoDB has to perform a collection scan — reading every document to find matches. With the right index, it can jump directly to the relevant documents, similar to using the index at the back of a book instead of reading every page.

In short: indexes trade a small amount of extra storage and slightly slower writes for dramatically faster reads on the fields you query, sort, or filter by most.
Index Types

Types of Indexes

Single Field Index
Indexes one field, in ascending (1) or descending (-1) order. The most common and simplest index type.
Compound Index
Indexes multiple fields together in a defined order. Supports queries that filter/sort on a prefix of the indexed fields (the "prefix rule").
Multikey Index
Automatically created when you index a field that holds an array — MongoDB indexes each array element separately.
Text Index
Supports text search queries on string content, with basic word-based matching, stemming, and relevance scoring.
Geospatial Index (2dsphere / 2d)
Supports efficient queries on location data, such as "find all points within this radius."
Hashed Index
Stores a hash of the field's value. Commonly used as a shard key to distribute writes evenly across a sharded cluster.
Wildcard Index
Indexes all fields (or a specified subset) dynamically — useful for collections with unpredictable or highly variable schemas.
Unique / Partial / TTL Index
Modifiers rather than separate types: unique enforces no duplicate values, partial only indexes documents matching a filter, and TTL automatically deletes documents after a set time.
Commands

Creating Indexes

1

Single field index

mongosh
db.users.createIndex({ email: 1 })

Creates an ascending index on email. Use -1 for descending.

2

Compound index

mongosh
db.orders.createIndex({ userId: 1, createdAt: -1 })

Speeds up queries that filter on userId alone, or on userId + createdAt together, thanks to the prefix rule.

3

Unique index

mongosh
db.users.createIndex(
  { email: 1 },
  { unique: true }
)

Rejects any insert or update that would create a duplicate email value.

4

Partial index

mongosh
db.orders.createIndex(
  { status: 1 },
  { partialFilterExpression: { status: "pending" } }
)

Only indexes documents where status: "pending", keeping the index small when most documents don't match.

5

TTL index

mongosh
db.sessions.createIndex(
  { createdAt: 1 },
  { expireAfterSeconds: 3600 }
)

Automatically deletes documents 1 hour after createdAt — great for sessions, logs, or temporary tokens.

6

Text index

mongosh
db.articles.createIndex({ title: "text", body: "text" })

// query it with
db.articles.find({ $text: { $search: "mongodb indexing" } })
7

Geospatial index

mongosh
db.places.createIndex({ location: "2dsphere" })
Checking Index Usage

How to Check & Scan Queries/Commands for Indexing

This is the part interviewers love to probe: knowing an index exists isn't enough — you need to prove a specific query is actually using it.

1

List all indexes on a collection

mongosh
db.users.getIndexes()

Returns every index defined on the collection, including the default _id index.

2

Explain a query's execution plan

mongosh
db.users.find({ email: "a@x.com" }).explain("executionStats")

This is the command for checking whether a query is scanning the collection or using an index. Look at these two fields in the output:

explain output (simplified)
{
  winningPlan: {
    stage: "IXSCAN",     // good: used an index
    indexName: "email_1"
  },
  executionStats: {
    totalKeysExamined: 1,
    totalDocsExamined: 1,
    executionTimeMillis: 0
  }
}
Red flag: if stage shows COLLSCAN instead of IXSCAN, the query is scanning the entire collection — no usable index was found.
3

Compare docs examined vs docs returned

A healthy, well-indexed query has totalKeysExamined and totalDocsExamined close to the number of documents actually returned. If MongoDB is examining thousands of documents to return just a few, the index isn't selective enough — or isn't being used.

4

Check index usage statistics

mongosh
db.users.aggregate([{ $indexStats: {} }])

Shows how many times each index has actually been used since the server started — great for spotting indexes that are never hit (candidates for removal).

5

Find slow queries with the profiler

mongosh
// Log all queries slower than 100ms
db.setProfilingLevel(1, { slowms: 100 })

// Review the logged slow queries
db.system.profile.find().sort({ ts: -1 }).limit(10)

The database profiler records queries that exceed a time threshold, which is often the first place to look when hunting for missing indexes in production.

6

Watch currently running operations

mongosh
db.currentOp({ "secs_running": { $gt: 3 } })

Useful for catching a long-running, unindexed query while it's actively happening on a live system.

7

Force a specific index (testing only)

mongosh
db.users.find({ email: "a@x.com" }).hint({ email: 1 })

hint() forces the query planner to use a specific index — handy for comparing performance between two candidate indexes, but not something to leave in production code long-term.

Query Plan Stages Cheat Sheet

StageMeaning
COLLSCANFull collection scan — no index used. Slow on large collections.
IXSCANIndex scan — the query used an index to find matching documents.
FETCHAfter finding index entries, MongoDB fetches the full documents from disk.
SORTAn in-memory sort was needed because no index provided the sorted order.
SORT_KEY_GENERATORPrecedes an in-memory sort stage — another signal a sort index would help.
Management

Managing Existing Indexes

mongosh
// Drop one index by name
db.users.dropIndex("email_1")

// Drop all indexes except _id
db.users.dropIndexes()

// Rebuild indexes (reclaims space, fixes fragmentation)
db.users.reIndex()

// Build an index in the background without blocking other ops (default behavior in modern MongoDB)
db.users.createIndex({ email: 1 }, { background: true })
Tip: in recent MongoDB versions index builds are non-blocking by default, but they still consume CPU and I/O — schedule large index builds during low-traffic windows on busy production systems.
Common Mistakes

Pitfalls to Avoid

  1. Creating an index for every field "just in case" — each extra index slows down writes and uses more RAM/disk.
  2. Ignoring the compound index prefix rule — a query that skips the first field(s) of a compound index often can't use it efficiently.
  3. Not checking explain() before assuming a slow query is indexed correctly.
  4. Using a low-cardinality field (like a boolean) as the sole index — it won't narrow down results much.
  5. Forgetting that a leading wildcard regex (/^.*abc/) can't use a standard index at all.
Interview Prep

Important Interview Q&A

1. What is the default index MongoDB creates automatically?

Every collection automatically gets a unique index on the _id field — it can't be dropped.

2. How do you check if a query is using an index?

Run .explain("executionStats") on the query and check whether winningPlan.stage is IXSCAN (index used) or COLLSCAN (full scan, no index used).

3. What is the "index prefix rule" for compound indexes?

A compound index on { a: 1, b: 1, c: 1 } can support queries on a, or a + b, or a + b + c — but not on b or c alone, since the index is only efficiently searchable from its leftmost field onward.

4. What's the difference between a covered query and a regular indexed query?

A covered query is satisfied entirely from the index itself, without ever fetching the actual documents — the index must contain every field the query needs (both filter and projection). This skips the FETCH stage entirely and is faster than a normal index scan.

5. Why can too many indexes hurt performance?

Every index must be updated on every insert, update, and delete, which adds write overhead. Indexes also consume RAM and disk, and MongoDB's query planner has to evaluate more candidate plans, which adds a small amount of query-planning overhead too.

6. What is a multikey index, and what's a key limitation?

A multikey index is created automatically when you index an array field, indexing each element separately. The limitation: you cannot create a compound index with more than one array field, since MongoDB can't efficiently represent the cross-product of two arrays in one index.

7. When would you use a TTL index?

For data that should automatically expire, like session tokens, temporary verification codes, cached data, or log entries — instead of writing a separate cleanup job.

8. What does ESR (Equality, Sort, Range) mean when designing a compound index?

It's a guideline for ordering fields in a compound index: put Equality-match fields first, then Sort fields, then Range-query fields last — this ordering lets MongoDB narrow down results as early as possible.

9. How do you find unused indexes in production?

Run db.collection.aggregate([{ $indexStats: {} }]) — it reports how many operations have used each index since the last server restart. Indexes with near-zero usage over a meaningful time window are candidates to drop.

10. Does an index guarantee faster performance?

Not always. Indexes speed up selective reads but add write overhead, use memory/disk, and can even be ignored by the query planner if it estimates a collection scan would be faster (e.g., very small collections).

Best Practices ⭐⭐⭐⭐⭐

Best Practices

  • Always run explain("executionStats") before and after adding an index to confirm it actually helped.
  • Follow the ESR rule (Equality, Sort, Range) when ordering fields in compound indexes.
  • Periodically check $indexStats and drop indexes that see no real usage.
  • Use partial indexes when only a subset of documents are ever queried on a field.
  • Avoid creating overlapping/redundant indexes — a compound index on {a:1, b:1} already covers queries that a single index on {a:1} would.
  • Schedule large index builds for low-traffic periods; monitor with currentOp() during the build.
✓ explain() before shipping ✓ ESR field ordering ✓ Drop unused indexes ✓ Watch write overhead ✓ Use partial/TTL where relevant
Takeaway

Summary

Indexes let MongoDB find data without scanning every document, at the cost of extra storage and slower writes. The single most important habit is checking .explain("executionStats") to confirm a query hits IXSCAN rather than COLLSCAN, and using $indexStats to spot indexes that are quietly doing nothing. Design compound indexes with the ESR rule, avoid over-indexing, and treat indexing as an ongoing tuning process — not a one-time setup step.
